When I was younger, I was fascinated by modified games and Android rooting. I kept wondering how people could change the way software behaved. As I grew older, that curiosity developed into an interest in reverse engineering, networking, operating systems, and eventually cybersecurity.

During college, I started taking this interest more seriously by building my own labs, working on security projects, and earning certifications. I also realized that understanding security requires strong fundamentals, so I invested time in networking, Linux, Windows, and cloud computing.

What really confirmed my decision was getting hands-on experience through internships. At CloudSEK, I worked on real-world security assessments and learned how to approach security problems methodically. My other experiences also exposed me to digital forensics and incident response, helping me understand cybersecurity from different perspectives.

Over time, I explored different areas of computer science, but cybersecurity was the field I consistently came back to, even when nobody was asking me to study it. I enjoy the continuous learning, the problem-solving, and the challenge of understanding how systems can fail.

What motivates me now is not just finding vulnerabilities, but using that understanding to build systems that are secure, resilient, and trustworthy. That's why I want to build my career in cybersecurity, particularly in security engineering.

GitHub Repo Analysis

Who has found bugs and got bounties by analysing GitHub repos?
Now the question is: **How do you scale it for real-world testing?**

If you have 2,000 GitHub repos, how will you analyse them?
The task was given by a BFSI client
1. Check HTTP status codes — write a Python script (checked which repos have 200, meaning the repo was live; 301, meaning it was redirecting to the original repo; 401, meaning the repo was made private or deleted) then I brought down the count to 1500, so we directly removed 500 repositories
2. Handle IP rate limiting — make a new script, add a delay
3. Analyse for secrets using tools — use Gitleaks or TruffleHog (faster); came down to 700 repositories which had committed some secrets like API keys, usernames, and passwords
4. Keep only verified keys (saw only the "true" values, manually checked some Gemini API keys, uploaded files on it; don't know where it went); came down to 400 repos
5. Check which repos have employee email commits; make a Python script to check if a commit was from company@email.com; came down to 100
6. Remove test keys; came down to 5
7. Remove duplicates
8. finally came down to 2 repositories and reported them to the client
