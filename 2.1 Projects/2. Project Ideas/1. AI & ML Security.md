# AI & ML Security

Securing AI/LLM systems, AI red-teaming, and AI/ML applied to offensive & defensive security.

### Three portfolio projects to build

A useful project gives a reviewer evidence of how you investigated a risk, implemented a control and checked the result. Keep the scope small enough to finish and document properly.

Build these projects in environments you control, using fictional data. Follow the scope of any training lab, and mock actions such as sending emails or changing records. If you use a hosted model API, set a spending limit where available and keep API keys out of the repository.

### Project 1: Build and harden a ticket summariser

Build a small Python app that uses a model to summarise fictional support tickets.

Start with a clear summarisation prompt. For every test, save the ticket, model response, model identifier, and relevant settings. Run a set of normal tickets first to establish a baseline.

Then introduce prompt injection.

**Test two routes**:

- **Direct injection**: Put an instruction in the user message that asks the model to return **PRACTICE_MARKER** instead of a summary.
- **Indirect injection**: Place the same harmless instruction inside a retrieved support ticket.

Next, add a mocked record-update tool. It should only log update requests and never change real data.

Test whether an injected ticket can make the model request an update. Then add an application-level permission check that blocks updates in the summarise-only workflow.

You can explore more controls in the [**Prompt Defence room**](https://tryhackme.com/room/promptdefence).

After each change, rerun the same attack cases and the original clean tickets. Check whether the controls stop unwanted behaviour without hurting summary quality.

Keep attempted tool calls separate from actions the application actually allows. Run each test several times and report the results alongside the model configuration.

**Your repository should include**:

- The Python application
- Clean and adversarial test cases
- A simple data-flow diagram
- A short before-and-after report

In the report, explain where the injected instruction entered the system, what happened before the controls were added, and what each defence changed.

The project demonstrates prompt-injection testing, defensive application design, and careful interpretation of model behaviour.

**Recommended:** [TryHackMe's Prompt Injection room](https://tryhackme.com/room/promptinjectionls) provides guided practice with both direct and indirect injection methods.

### Project 2: Test document access in a RAG assistant

Build a question-answering assistant over around ten fictional documents.

Include a mix of public guidance and one restricted HR document containing a distinctive fake value.

Create two test users with different access rights. For every request, record which passages are retrieved and which ones are sent to the model.

Use the [**RAG Security Fundamentals room**](https://tryhackme.com/room/ragsecurityfundamentals) to understand how retrieval works.

Then introduce an indirect prompt injection. Add an instruction to a public document telling the assistant to reveal information from the restricted HR note.

Before judging the model’s response, check whether the injected passage actually reached the model.

Next, test whether the unauthorized user can access the restricted information through:

- Normal questions
- Indirect prompt injection
- Different wording or retrieval queries

Then add the main control: enforce document permissions before retrieved content enters the model context.

Use the authenticated user’s permissions to filter results. Restricted documents should never reach the model for users who cannot access them.

Add an approval step for changes to the document collection as well. This creates a record of who added or changed content and how it entered the knowledge base.

Retest both users after the changes.

The authorized user should still receive the permitted information. The restricted passage should never appear in the unauthorized user’s model context.

**Your project should include**:

- A simple retrieval and data-flow diagram
- Test cases for both users
- A test matrix showing expected and actual results
- Redacted retrieval traces
- The access-control changes
- A short before-and-after analysis

In your report, explain the difference between the model choosing not to follow a malicious instruction and the application preventing sensitive information from reaching the model at all.

The project demonstrates secure RAG design, access control, retrieval testing, and protection of sensitive data throughout the application.

### Project 3: Create an AI supply chain release check

Build a small Python checker that reviews a JSON manifest before an AI artefact is approved for a toy deployment.

Keep the exercise focused on metadata and file integrity. Use harmless dummy files rather than real model artefacts.

For each artefact, record:

- Source
- Version
- Expected file hash
- Dependency versions

Maintain a separate trusted baseline that defines what is approved.

**Then create four test cases**:

- An approved artefact
- A file whose contents have changed
- An artefact from an unapproved source
- An artefact with an unpinned dependency

Your checker should compare each case with the trusted baseline and reject anything that breaks the release policy.

Save a readable report for every run explaining why the artefact passed or failed.

Use the [**AI Supply Chain Security module**](https://tryhackme.com/module/ai-supply-chain-security) to frame the exercise around provenance, tampering, dependencies, and release controls.

Be clear about what the hash check proves. A matching hash confirms that the file matches the expected copy. It does not prove that the file itself is safe.

Do not load or execute untrusted model files. Keep the project limited to metadata checks and file inspection.

**Your repository should include**:

- The Python checker
- Sample JSON manifests
- Dummy artefact files
- Test outputs for all four cases
- A short release policy

The release policy should explain who maintains the trusted baseline, who can approve changes, and when additional review is required.

The project demonstrates release automation, provenance checks, integrity verification, and security judgment. A reviewer should be able to run the examples, see why a release was blocked, and understand which risks still need deeper review.

### AI Prompt Security Gateway (AI Firewall)
Build a proxy that sits between the user and an AI model (using **OpenRouter** free models).

**Workflow**
```
User
   ↓
Prompt
   ↓
Your Security Engine
   ↓
Checks if prompt is malicious
(Prompt Injection, Jailbreak, Malware, Sensitive Data, etc.)
   ↓
Safe? ── Yes ──► OpenRouter LLM
        │
        No
        │
     Block & Log
```

**What it does**
- Receives every user prompt.
- Uses a free LLM from **OpenRouter** to classify whether the prompt is **safe or malicious**.
- If the prompt is safe → forwards it to the target AI model.
- If malicious → blocks it and logs the reason.
- Acts as an **AI Firewall / AI Security Gateway** for LLMs.

**In one line:** An AI-powered security proxy that scans prompts using OpenRouter before they reach an LLM, blocking malicious prompts such as prompt injection, jailbreaks, and other unsafe requests.

## AI Security Projects (curated: Beginner → Advanced)

### Beginner

**1. LLM Prompt Injection Attack Lab**
- **Description:** Craft prompt injection payloads against open-source LLMs and document how they bypass safety guardrails.
- **Tools/Tech Stack:** Python, Ollama, LangChain, Burp Suite

**2. AI-Powered Phishing Detection Tool**
- **Description:** Build a classifier that detects phishing emails using NLP and compare it against traditional rule-based filters.
- **Tools/Tech Stack:** Python, Scikit-learn, HuggingFace, Gmail API

**3. Malware Classification With Machine Learning**
- **Description:** Train a model to classify malware families from static features and benchmark detection accuracy.
- **Tools/Tech Stack:** Python, Scikit-learn, VirusTotal API, Pandas

### Intermediate

**4. Jailbreak-as-a-Service Threat Landscape Study**
- **Description:** Map and categorize real-world LLM jailbreak techniques and publish a structured threat taxonomy.
- **Tools/Tech Stack:** Python, GPT-4 API, Claude API, MITRE ATLAS

**5. AI Agent Security Testing Lab**
- **Description:** Deploy an autonomous AI agent and attack its tool-use layer, file access, API calls, and memory injection.
- **Tools/Tech Stack:** Python, LangChain or AutoGPT, Docker, Burp Suite

**6. RAG Poisoning Attack Simulation**
- **Description:** Poison a retrieval-augmented generation pipeline with malicious documents and measure output manipulation.
- **Tools/Tech Stack:** Python, LangChain, ChromaDB, OpenAI API

### Advanced

**7. Steganographic Prompt Injection in Vision Models**
- **Description:** Embed hidden instructions inside images and exploit VLMs to execute attacker-controlled commands.
- **Tools/Tech Stack:** Python, OpenCV, GPT-4V, Claude Vision, PIL

**8. LLM Container Escape & Isolation Testing**
- **Description:** Test whether a compromised LLM deployment can break out of its container boundary into the host.
- **Tools/Tech Stack:** Docker, Kubernetes, Python, Trivy, Falco

**9. Adversarial Attack on AI-Based IDS**
- **Description:** Craft adversarial inputs that fool an ML-based intrusion detection system without triggering alerts.
- **Tools/Tech Stack:** Python, TensorFlow or PyTorch, Foolbox, NSL-KDD Dataset

**10. AI Red Team Full Exercise**
- **Description:** Run a complete red team operation against an LLM-powered application — prompt injection, data exfiltration, and model abuse.
- **Tools/Tech Stack:** Python, Burp Suite, Garak, PyRIT, MITRE ATLAS
