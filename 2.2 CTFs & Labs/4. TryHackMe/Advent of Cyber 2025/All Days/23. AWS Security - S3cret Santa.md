# Task 2 IAM: Users, Roles, Groups and Policies

## IAM Roles

An IAM Role is a temporary identity that can be assumed by a user, as well as by services or external accounts, to get certain permissions. 

Think of Sir Carrotbane, and how, depending on the battle ahead, he might need to assume the role of an attacker or a defender. When becoming an attacker, he will get permission to wield his shiny swords, but when assuming the role of a defender, he will instead get permission to carry a shield to better defend King Malhare.

## IAM Policies

Access provided to any user, group or role is controlled through IAM policies. A policy is a JSON document that defines the following:
- What action is allowed (Action)
- On which resources (Resource)
- Under which conditions (Condition)
- For whom (Principal)

Consider the following hypothetical policy
```powershell
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "AllowSpecificUserReadAccess",
      "Effect": "Allow",
      "Principal": {
        "AWS": "arn:aws:iam::123456789012:user/Alice"
      },
      "Action": [
        "s3:GetObject"
      ],
      "Resource": "arn:aws:s3:::my-private-bucket/*"
    }
  ]
}
```
This policy grants access to the AWS user Alice (Principal) to get an object from an S3 bucket (Action) for the S3 bucket named my-private-bucket (Resource).

## Enumerating User Policies

**Inline policies** are assigned directly in the user (or group/role) profile and hence will be deleted if the identity is deleted.
**Attached policies**, also called managed policies, can be considered reusable. An attached policy requires only one change in the policy, and every identity that policy is attached to will inherit that change automatically.

see what inline policies are assigned to Sir Carrotbane by running the following command.

`aws iam list-user-policies --user-name sir.carrotbane`

Maybe, Sir Carrotbane has some policies attached to their account. We can find out by running the following command.

`aws iam list-attached-user-policies --user-name sir.carrotbane`

we can check if Sir Carrotbane is part of a group. Let's run this command to do that.

# Task 4 Assuming Roles

There's a role named `bucketmaster`, and it can be assumed by `sir.carrotbane`.

Just as users, roles can have inline policies and attached policies. To check the inline policies, we can run the following command.

There is one policy assigned to this role. Before checking that policy, let's see if there are any attached policies assigned to the role as well.

`aws iam list-attached-role-policies --role-name bucketmaster`

Looks like we only have the inline policy assigned. Let's see what permissions we can get from the policy.

## 🧠 Big picture (one sentence first)

You are a user (**sir.carrotbane**) who is allowed to **temporarily become another identity (a role)** called **bucketmaster** to gain extra permissions.

---

## STEP 1: Why are we doing this?

Earlier, we found this permission:

`sts:AssumeRole`

### What this means (in plain words)

> “This user is allowed to temporarily act as another role.”

So now the question is:  
👉 **What roles exist that we can become?**

---

## STEP 2: List all roles in the AWS account

Command:

`aws iam list-roles`

### What this does

It asks AWS:

> “Show me all the roles that exist in this account.”

### Result (important part)

`RoleName: bucketmaster`

And inside its policy:

`Principal: sir.carrotbane Action: sts:AssumeRole`

### Meaning

✅ **sir.carrotbane is allowed to assume the bucketmaster role**

This is the key discovery.

---

## STEP 3: Find out what this role can do

Roles don’t do anything by themselves — **policies give them permissions**.

Roles can have:

- Inline policies (written directly on the role)
    
- Attached policies (separate managed policies)
    

---

### 3.1 Check inline policies

Command:

`aws iam list-role-policies --role-name bucketmaster`

Result:

`BucketMasterPolicy`

So there is **one inline policy**.

---

### 3.2 Check attached policies (just in case)

Command:

`aws iam list-attached-role-policies --role-name bucketmaster`

Result:

`(no attached policies)`

So all permissions come from the **inline policy**.

---

## STEP 4: Read the policy to see permissions

Command:

`aws iam get-role-policy --role-name bucketmaster --policy-name BucketMasterPolicy`

### What permissions does bucketmaster have?

#### Permission 1

`"s3:ListAllMyBuckets"`

➡️ Can list **all S3 buckets** in the account

#### Permission 2

`"s3:ListBucket"`

➡️ Can list contents of:

- `easter-secrets-123145`
    
- `bunny-website-645341`
    

#### Permission 3

`"s3:GetObject"`

➡️ Can **download files** from:

- `easter-secrets-123145`
    

### Why this matters

👉 This role gives access to **S3 data**  
👉 That’s likely where **secrets or flags** are stored

---

## STEP 5: Actually assume the role

So far, we only **looked** at permissions.  
Now we **become** the role.

Command:

`aws sts assume-role \   --role-arn arn:aws:iam::123456789012:role/bucketmaster \   --role-session-name TBFC`

### What this does (simple)

You are asking AWS STS:

> “Give me temporary credentials so I can act as bucketmaster.”

---

## STEP 6: Understand the output

AWS gives you **temporary credentials**:

- `AccessKeyId`
    
- `SecretAccessKey`
    
- `SessionToken`
    
- Expiration time
    

⚠️ These are **temporary**, not permanent.

---

## STEP 7: Tell your terminal to use these credentials

You must export them so AWS CLI uses them.

`export AWS_ACCESS_KEY_ID="ASIA..." export AWS_SECRET_ACCESS_KEY="..." export AWS_SESSION_TOKEN="..."`

### What this means

> “From now on, every AWS command I run uses the bucketmaster role.”

---

## STEP 8: Confirm you are now the role

Command:

`aws sts get-caller-identity`

### Expected result

You should see something like:

`arn:aws:sts::123456789012:assumed-role/bucketmaster/TBFC`

✅ This confirms:

- You are **no longer just sir.carrotbane**
    
- You are now acting as **bucketmaster**
