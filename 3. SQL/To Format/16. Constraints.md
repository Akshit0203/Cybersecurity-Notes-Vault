# CHECK

it can limit the values allowed in a column

```sql

id INT PRIMARY KEY,
city VARCHAR(50),
age INT,
CONSTRAINT age_check CHECK (age >= 18 AND city="Delhi")
);
```

```sql
CREATE TABLE newTab (
 age INT CHECK (age >= 18)
```

**Introduction to Constraints**

"Now let's talk about some constraints. Whenever we were defining a table, to define the table, when we write our column name, we have to specify two things along with the column name. One is what data type we will keep for the column, and the second is what constraint we will keep for the column. We already know that we can keep any column name of our choice, we have read about data types, and now we are talking about what constraints we can keep with our columns.

In SQL, **constraints mean some specific rules**. Rules like, let's suppose, if I kept my column name as `age`. If I am storing age-type data, whose data type is integer, and I want to store only those ages which are above 18, meaning 18+ ages, then there I will have to apply some condition on my data. Or let's say I want to store some ID of integer type, or I want to store some roll number of integer type, but I want this roll number to become a primary key, so I will have to apply a constraint on it. Primary key constraint means it should have not null and unique values. So what is that? I specified a rule—what kind of data can be stored inside this column, and those are what we call SQL constraints. Although we have many constraints, we will talk about the most common and popular constraints."

**1. NOT NULL Constraint**

"The very first of these is our **NOT NULL** **constraint**. Whichever column we put the `NOT NULL` constraint in front of, we can never keep null values inside that column, meaning we can never leave it empty. Like, here we have written Column 1 Integer Not Null, so inside Column 1, we will always have to store some value."

**2. UNIQUE Constraint**

"The second constraint we have is for **unique values**. Whichever column we have given this unique constraint, only unique values will always come inside it. Like, if we wrote Column 2 Int Unique, then the value of Column 2 must always be unique.

Let's test this once by creating a table. Let's suppose we created a table:

```
CREATE TABLE temp1 (
    id INT UNIQUE
);
```

Inside `temp1`, we make one column, let's call it `id`, and make it of integer type, and let's call it `unique`. So we have made this Table 1. Let's execute this, so we got Table 1. Let's refresh inside Tables, so this is our `temp1` table.

Now, let's add some data inside this table, so we can write:

```
INSERT INTO temp1 VALUES (101);
```

First of all, if we have to add the ID, then I am going to add ID `101`. In this way, we can add our ID `101`. Let's copy this, and again I will add ID `101`. So, the first time, the ID will get executed and it will get added. We can check by selecting: `SELECT * FROM temp1`. Our ID `101` has been added inside the table, so it is visible to us here.

Now, when we run the same thing the second time—I want to add `101` again—then what will happen for that? For that, an error will come here. The error coming is: **'Error Code: Duplicate entry '101' for key 'temp1.id''**. This is because we gave it a unique constraint, so we cannot store duplicate IDs inside it. So, this is the job of our unique constraint. For example, in some case we might want that every student should have unique courses in the college, so we can apply a unique constraint for that."

**3. PRIMARY KEY Constraint**

"The third is our **PRIMARY KEY** **constraint**. The primary key constraint makes any column unique as well as not null. But we can make only one column the primary key. Like, here it is written: 'It can be only used for one primary key.' So the primary key by default makes any column unique and not null, and there are two ways to define a primary key.

The first way is that we write our column's name, write its type as `INT`, and then we write `PRIMARY KEY` in the constraint. For example, if inside the table, inside `temp1`, we want to make our ID a primary key, then for that we can write `id INT PRIMARY KEY`. So, the first way is to make the primary key in this manner.

The second way is, let's suppose we defined many different things inside a table, like we defined ID of integer type, we defined our name of varchar type, besides that we defined age, age became integer for us (let's write it in small, or...) and along with that, we defined some city, let's also make it varchar 20. So, in this way, we defined a lot of data. Now, from this data, we have to choose who we want to make the primary key. So, to make ID the primary key, we can either write primary key right here, or we can put a comma and write at the bottom: `PRIMARY KEY` and in brackets the name of that column which we want to make the primary key. So what did we do? Here we made ID our primary key. So this is the second syntax to make any column our primary key.

If, let's suppose, we want to make a mixture of two things our primary key—that I want every child's ID and their name together to become the primary key—then for that, we can write here:

```
PRIMARY KEY (id, name)
```

So, the combination of these two will be the primary key. In that case, it might happen that ID becomes duplicate, it might happen that name becomes duplicate, but the combination of both will never be duplicate. To explain this, it means that if two columns become the primary key, then it could be that we have this ID, we have this name—it might be that one child's ID is 101, the second child's ID is also 101, maybe this one's is 102, this one's is 103. It could be that one child's name is Ram, this one's name is also Ram, but this one's name will always be Shyam. Meaning, the combination of both will always remain unique. This might be duplicate, this might be duplicate, but the combination will remain unique. When the combination remains unique, we can also make the combination of two columns our primary key."

**4. FOREIGN KEY Constraint**

"The next constraint we will talk about is our **FOREIGN KEY** **constraint**. The basic job of a foreign key is to link two tables, like we talked earlier that it links our city and our student tables. So to protect from this link [meaning to establish this relationship safely], we declare our foreign key.

For example, first of all, let's assume we made some table `temporary`. Inside `temporary`, we wrote `customer_id INT`. So this became our normal column. Now we know that we have this table named `temporary`, but there is already another table created by the name of `customer`. And inside the `customer` table, there is its own ID, and what is this ID? This ID is a primary key. And we know that inside this `customer_id` [of our temporary table], we will also store the primary key of this [customer] table. So what can we do? We can declare this `customer_id` as a foreign key.

To declare it, we write `FOREIGN KEY` and inside it we write which column we want to make our foreign key—our `customer_id`. And we write `REFERENCES customer` (meaning the name of that table) and that table's primary key. So from which table we will bring our foreign key, we define that table and column, and whom we will make our foreign key, we define that column. This column [the foreign key] belongs to our new table, and this table and column belong to our old, already existing table.

So in this way, we write `FOREIGN KEY (column_name) REFERENCES parent_table(parent_column)`. This is the syntax for our foreign key, and in the middle we write 'references'. 'References' basically means here that this column references this column, meaning it refers to it, it talks about it, and its values are defined from it. So in this way, we can declare our foreign key. So we won't go into too much detail about this right now; later when we talk about larger tables, we will write and see foreign keys there."

**5. DEFAULT Constraint**

"Apart from this, there is another important constraint of **DEFAULT**. The job of `DEFAULT` is to set the default value of any column. Let's suppose that if we have created some table named `employees`, for that we are making a column for salary—so this became our table like this, and inside this table, we made a column, let's suppose this is our ID and we made this the salary column. Now inside salary, we know every employee's own salary will come.

But we want that if someone does not know the salary, then by default, `25000` should get added as their salary. So if someone has written 35000, 40000, 20000, 15000, in that case, whatever value is being inserted will come, and in other cases, the default value should be used. So to set the default value, we can write `salary`, then its type, and then we can write our constraint `DEFAULT` and after that our default value. That, okay, the default value will be set, but how much value will be set, we can define that.

Let's test this once. For example, let's suppose we can create a table here—we create a table named `employee`. Inside `employee`, one can be its ID, second we can also have its salary, so salary will also be of integer type, but here we will define the default constraint that salary becomes `25000`. Writing this much, we can create our table. So our table got successfully created. Now let's insert values inside it, so `INSERT INTO employee` table `VALUES`—what we will do is, we will write only our integer ID. So here we want to insert ID only inside the integer, so we will keep the ID as `10`. As soon as we write only this much and we enter it (let's write our table name as `employee`)—so let's execute this once.

We will execute it, and now we will look at our table: `SELECT * FROM employee`. So what happened inside the employee table? The ID came—this is our ID column—and by default, the salary became `25000`. Why did the salary become `25000` by default? Because we defined our default constraint here as `25000`—that in the case where salary is not received, in that case, by default make the salary `25000`. So that thing has come to us here. So this is the advantage we get with the default constraint."

**6. CHECK Constraint**

"Apart from this, we have another important constraint: the **CHECK** **constraint**. With the `CHECK` constraint, we can apply limits on the values. Like, what does the check constraint do? Before adding a value, it applies a check.

For example, here we defined a table named `city`. Now inside `city`, when the city table is created like this, then inside city, first we will have an ID. On the ID, we have already applied the primary key constraint. Second, we will have the city's name, so let's call it `city`. Third, we will have some `age`—integer `age`. Now, these are random values; why is age coming inside city? There is no logic to it, but basically these are random values that we are storing.

So, to apply the constraint check, we can write `CONSTRAINT` keyword, after that we will write our constraint's name. So this `age_check` is just the constraint's name; we can skip it if we want, or we can write it if we want—we can write anything here. So, `CONSTRAINT`, then constraint name, then we can write `CHECK`, and inside `CHECK` we can apply any of our checks. Check means we can apply any condition. My condition is that my age must always be greater than or equal to 18, and inside city, there should be 'Delhi'. So what did I do? I applied a constraint here. So now we won't be able to add any such row in which the age is not greater than 18 and in which the city name is anything other than Delhi.

Apart from this, there can be another example: along with applying the check, like `age` is the column name, integer is the type, we can simply write `CHECK (age >= 18)`. So this is also a way to apply our check.

So these were our most popular and most commonly used constraints which we are going to use further. We won't go into too much detail right now, but as we create new tables, we will see many constraints."
