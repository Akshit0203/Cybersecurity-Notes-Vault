# Proxies, VPNs, and Tunneling

> [!tip] One-Liner
> A **proxy** is a middleman that handles/forwards connections on your behalf. A **VPN** carries your original packets through an encrypted tunnel to another network endpoint.

---

## 1. What Is a Proxy?

A proxy is an **intermediary** between a client and a destination server.

```
WITHOUT PROXY:    Client ──────────────────► Server

WITH PROXY:       Client ──────► Proxy ──────► Server
```

The proxy receives the client's request and communicates with the destination on the client's behalf.

**Why use proxies?**
- Security inspection & policy enforcement
- Web filtering & blocking malicious sites
- Logging & monitoring activity
- Caching for performance
- IP masking (destination sees proxy's IP, not yours)
- Routing traffic through other networks

> [!warning]
> A proxy is **not automatically anonymous**. The proxy itself can see your traffic and real IP. HTTP headers like `X-Forwarded-For` or `Forwarded` can also reveal the original client IP to the destination.

---

## 2. Proxy vs Router

| Concept | Layer              | What It Does                               |
| ------- | ------------------ | ------------------------------------------ |
| Router  | Network layer      | Forwards IP packets based on addresses     |
| Proxy   | Application level  | Acts as intermediary for application traffic |

A router forwards packets. A proxy **terminates and re-initiates** connections.

---

## 3. Forward Proxy vs Reverse Proxy

This is the **most important distinction** to understand.

### Forward Proxy — Represents the Client

```
Client ──────► Forward Proxy ──────► Internet
                    ↑
                represents
                  CLIENT
```

**Use cases:** Corporate internet access, web filtering, outbound traffic control, client anonymity.

### Reverse Proxy — Represents the Server

```
Internet ──────► Reverse Proxy ──────► Backend Servers
                      ↑
                  represents
                    SERVER
```

The client thinks it's talking to `example.com`, but the request actually goes through the reverse proxy to a backend.

**Use cases:**

| Capability       | Description                                                     |
| ---------------- | --------------------------------------------------------------- |
| Load balancing   | Distributes requests across multiple backend servers            |
| TLS termination  | Handles HTTPS so backends don't have to                        |
| Caching          | Returns cached responses without hitting the backend           |
| Security / WAF   | Inspects requests, blocks malicious traffic before it reaches backends |
| Hiding backends  | Backend servers aren't directly exposed to the internet        |

**Reverse proxy load balancing architecture:**

```
             Reverse Proxy
                  │
        ┌─────────┼─────────┐
        ▼         ▼         ▼
     Server 1  Server 2  Server 3
```

**Reverse proxy + WAF architecture:**

```
Internet → WAF/Reverse Proxy → Web Application
                │
                ├── Malicious → BLOCK
                └── Legitimate → Backend
```

> [!important] Interview Answer
> *"A forward proxy acts on behalf of clients making outbound requests, while a reverse proxy sits in front of servers and handles inbound requests on their behalf."*

| Aspect            | Forward Proxy           | Reverse Proxy                    |
| ----------------- | ----------------------- | -------------------------------- |
| Represents        | Clients                 | Servers                          |
| Client awareness  | Client knows about proxy | Client may not know backend exists |
| Traffic direction | Outbound                | Inbound                         |
| Common uses       | Filtering, access control | Load balancing, TLS, WAF, CDN   |

## 4. Proxy Types

### HTTP Proxy

Designed primarily for **HTTP/HTTPS** traffic.

```
Browser → HTTP Proxy (192.168.1.100:8080) → Web Server
```

The browser sends its request to the proxy, which forwards it. The proxy can inspect:
- URLs, HTTP methods, headers, cookies, request/response bodies

Because **plain HTTP isn't encrypted**, the proxy sees everything.

### HTTPS Proxying — The CONNECT Method

For HTTPS, the client asks the proxy to create a **TCP tunnel**:

```
Step 1:  Browser connects to Proxy:8080
Step 2:  Browser sends: CONNECT example.com:443 HTTP/1.1
Step 3:  Proxy connects to example.com:443
Step 4:  Proxy responds: HTTP/1.1 200 Connection Established
Step 5:  Browser establishes TLS through the tunnel
```

```
Browser ──encrypted TLS──► Proxy ──forwards encrypted bytes──► Web Server
```

The proxy is just **forwarding encrypted traffic** — it normally **cannot read the HTTP contents** (only metadata like destination IP, port, connection timing, traffic volume).

> [!tip] CONNECT in One Sentence
> *"Proxy, connect me to this destination, and then just carry the encrypted traffic."*

### TLS Inspection (HTTPS Interception)

Organizations can deliberately inspect HTTPS by creating **two separate TLS connections**:

```
Client ──TLS #1──► Inspection Proxy ──TLS #2──► Server
```

The proxy decrypts, inspects, then re-encrypts toward the server. Requires deploying a trusted CA certificate to managed clients.

**Used for:** DLP, malware detection, content filtering, security monitoring.

> [!warning]
> Improper certificate handling in TLS inspection can create serious security risks.

### SOCKS Proxy

SOCKS is **general-purpose** — it proxies network connections, not just HTTP.

```
HTTP Proxy: "I understand HTTP."
SOCKS:      "Give me a connection to this destination."
```

```
Application → SOCKS Proxy → Destination (any supported protocol)
```

| Feature          | SOCKS4         | SOCKS5                                    |
| ---------------- | -------------- | ----------------------------------------- |
| TCP              | ✅              | ✅                                         |
| UDP              | ❌              | ✅                                         |
| Authentication   | ❌              | ✅                                         |
| Status           | Older / simpler | Newer / more capable                      |

**SOCKS is critical for pentesting** — it's how you route tools through a pivot (see [Pivoting](#7-pivoting-through-a-proxy) below).

### HTTP Proxy vs SOCKS — Comparison

|                    | HTTP Proxy                | SOCKS Proxy                  |
| ------------------ | ------------------------- | ---------------------------- |
| Designed for       | HTTP                      | General network connections  |
| Understands HTTP   | Yes                       | Not necessarily              |
| Web browsing       | Yes                       | Yes                          |
| SSH / other        | Not normally              | Yes                          |
| Common pentest use | Burp / web app testing    | Pivoting                     |
| Concept level      | Application-specific      | Connection-level proxying    |

### Transparent Proxy

Intercepts traffic **without client configuration**. The network infrastructure redirects traffic through the proxy — the user may not even know it exists.

```
Client → Network → Transparent Proxy → Internet
```

**Used for:** Enterprise content filtering, monitoring, security inspection.

### Intercepting Proxy (Burp Suite)

The most important proxy type for **web application security testing**.

```
Browser → Burp Suite → Web Application
```

Allows you to:
- Intercept, inspect, and modify requests/responses
- Replay requests
- Manipulate parameters, headers, cookies
- Test authentication and authorization
- Analyze APIs and investigate vulnerabilities

> Burp Suite is called an "intercepting proxy" because you deliberately place it between your browser and the target to intercept and manipulate traffic.

## 5. Proxy Headers

HTTP proxies can add forwarding information:

```
X-Forwarded-For: 203.0.113.10
Forwarded: for=203.0.113.10
```

This tells the backend the original client's IP.

> **A proxy does not automatically mean the client's identity is hidden** — check for forwarding headers.

---

## 6. Proxy Chaining

Multiple proxies in sequence:

```
Client → Proxy 1 → Proxy 2 → Proxy 3 → Internet
```

**Use cases:** Network segmentation, routing through different networks, testing, security research.

> More proxies don't automatically mean better anonymity — you're just adding more intermediaries, each of which is a trust point.

## 7. Pivoting Through a Proxy

> [!important] Critical OSCP Concept

**Scenario:** Your Kali can reach a compromised server, but the compromised server has access to an internal network you can't directly reach.

```
ATTACKER (Kali)              COMPROMISED SERVER           INTERNAL SERVER
10.10.14.5          →        10.10.11.20                  192.168.1.50
                              192.168.1.20         →      (unreachable from Kali)
```

**Solution:** Use the compromised server as a **pivot/SOCKS proxy**:

```
Kali ──proxied traffic──► Compromised Server ──internal traffic──► 192.168.1.50
```

Now your tools can reach internal services through the compromised host.

**Tools & techniques for pivoting:**
- SOCKS proxies
- Proxychains
- SSH dynamic port forwarding (`ssh -D`)
- Port forwarding
- Tunneling

## 8. Proxy vs VPN

### Proxy

```
Application → Proxy → Destination
```

- Acts as **middleman** for specific application traffic
- **No inherent encryption** (encryption comes from HTTPS/TLS, not the proxy)
- Usually configured per-application

```
Chrome ─────► Proxy ─────► Internet
SSH ─────────────────────► Internet   ← may not use the proxy
```

### VPN

```
Computer → [Encrypted VPN Tunnel] → VPN Server → Destination
```

- Creates a **network-level encrypted tunnel**
- Routes traffic from **multiple applications** through the tunnel
- Creates a virtual network interface (`tun0`, `wg0`)

```
Chrome ──┐
SSH ─────┤
Nmap ────┤
         ▼
      VPN Tunnel → VPN Server → Destination
```

### Comparison Table

|                                     | **Proxy**                         | **VPN**                           |
| ----------------------------------- | --------------------------------- | --------------------------------- |
| Main idea                           | Intermediary                      | Encrypted tunnel                  |
| Scope                               | Application/connection-specific   | System/network-wide               |
| Encryption                          | ❌ Not inherent                    | ✅ Typically encrypted             |
| Routes multiple apps?               | Usually no (per-app)              | ✅ Yes                             |
| Hides client from destination?      | ✅ Usually                         | ✅ Usually                         |
| Main pentest use                    | Burp, SOCKS, pivoting             | Lab/network access                |
| Main trust point                    | Proxy server                      | VPN server/provider               |

> [!important] Interview Answer
> *"A proxy is an intermediary that forwards traffic between a client and destination, often for a particular application or connection. A VPN establishes an encrypted tunnel between the client and a VPN endpoint and can route traffic from multiple applications through that tunnel. A proxy itself doesn't inherently provide encryption, while a VPN normally does."*

### Common Misconceptions

> ❌ "A proxy encrypts my traffic." — **No.** Encryption comes from HTTPS/TLS, not the proxy.
> ❌ "SOCKS encrypts traffic." — **No.** SOCKS is a proxying protocol. Encryption comes from another layer.
> ❌ "VPN = magical anonymity." — **No.** The VPN provider is a trust point and can observe traffic.
> ❌ "Proxy = application layer, VPN = network layer." — **Oversimplification.** Remember the functional distinction instead.

## 9. What Is a Tunnel? (Encapsulation)

> **A tunnel is a communication channel inside another communication channel.**

### How It Works — Encapsulation

Your original packet gets **wrapped inside another packet**:

```
Original packet:
┌─────────────────────────────┐
│ IP Header                   │
│ TCP Header                  │
│ HTTP Data                   │
└─────────────────────────────┘
              ↓
         VPN encapsulates it
              ↓
┌──────────────────────────────────────────┐
│ Outer IP Header                          │
│ VPN/Transport information                │
│ ┌──────────────────────────────────────┐ │
│ │ Original IP Header                   │ │
│ │ TCP Header                           │ │
│ │ HTTP Data                            │ │
│ └──────────────────────────────────────┘ │
└──────────────────────────────────────────┘
```

**Analogy:** Putting a letter inside another envelope. The outer envelope gets delivered to the VPN server, which removes the outer layer and gets your original packet.

### VPN Tunnel Process

```
Original packet → Encrypt → Encapsulate → VPN tunnel → Decapsulate → Decrypt → Forward to destination
```

### With vs Without VPN

**Without VPN:**
```
You → ISP (sees "I want 8.8.8.8") → 8.8.8.8
```

**With VPN:**
```
You → ISP (sees "encrypted traffic to VPN Server") → VPN Server → extracts original → 8.8.8.8
```

The ISP sees the VPN connection; the VPN server is where the tunneled traffic exits.

> [!tip] Tunneling ≠ Encryption
> **Tunneling** = traffic encapsulated inside another connection.
> **Encryption** = data transformed so unauthorized parties can't read it.
> VPNs commonly do **both**, but they are separate concepts.

### VPN Interface on Linux (OSCP Context)

After connecting to a VPN:

```
$ ip addr
→ tun0 appears

Kali
 ├── eth0 → Your normal network
 └── tun0 → OffSec VPN tunnel → Lab network
```

Traffic to lab targets routes through `tun0`:

```
Nmap → tun0 → VPN tunnel → OffSec VPN server → Lab network → Target (10.x.x.x)
```

## 10. Proxy vs VPN — The Core Distinction

| Concept | How It Works                                                          |
| ------- | --------------------------------------------------------------------- |
| Proxy   | *"I'll make the connection to the destination **for** you."*          |
| VPN     | *"I'll carry your original packets through a protected tunnel to another endpoint."* |

A proxy is an **application-level middleman**. A VPN **encapsulates your original network packets** inside tunnel traffic.

```
PROXY:   Client ───────► Proxy ───────► Server
                           └─ acts as middleman

VPN:     Client ──► [Encrypted + Encapsulated Tunnel] ──► VPN Server ──► Destination
```

---

## 11. Security Risks of Proxies

| Risk                       | Description                                                      |
| -------------------------- | ---------------------------------------------------------------- |
| Single point of failure    | Proxy goes down → everyone's traffic fails                       |
| Single point of compromise | Attacker controls proxy → visibility over all traffic            |
| Privacy concern            | Proxy sees client IPs, destinations, URLs, credentials (if decrypted) |
| Misconfiguration           | Can expose internal systems, leak info, bypass security controls |

## 12. Complete Mental Model

```
                    PROXIES
                       │
          ┌────────────┴────────────┐
          │                         │
     FORWARD PROXY            REVERSE PROXY
          │                         │
      represents                represents
       CLIENT                     SERVER
          │                         │
Client → Proxy → Internet    Internet → Proxy → Backend
```

**Proxy Type Taxonomy:**
```
├── HTTP Proxy         → HTTP/HTTPS traffic
├── HTTPS CONNECT      → TLS tunnel through proxy
├── SOCKS4 / SOCKS5    → General-purpose proxying
├── Transparent Proxy  → No client config needed
└── Intercepting Proxy → Burp Suite / web testing
```

**Security Applications:**
```
├── Web Testing    → Burp Suite, ZAP
├── Pivoting       → SOCKS proxy through compromised host
└── Filtering      → Corporate proxy, WAF
```

## 14. Key Sentences to Memorize

1. **HTTP proxy** → application-specific intermediary primarily for HTTP traffic
2. **HTTPS CONNECT** → asks the proxy to establish a tunnel to the HTTPS destination
3. **Normal HTTPS through a proxy** → TLS protects the application data from the proxy
4. **SOCKS** → general-purpose proxying, not tied specifically to HTTP
5. **VPN** → creates a broader encrypted tunnel, carrying traffic from many applications
6. **Tunnel** → a mechanism for carrying original packets inside another connection, usually with encryption
7. **Pivoting** → routing tools through a compromised host to reach otherwise unreachable networks
