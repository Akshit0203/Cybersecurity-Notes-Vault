contains:

`read` normally reads from **standard input (`stdin`)**.

Keyboard → stdin → read → name

That's why your keyboard input automatically ends up in the variable.

> "The input is finished; give this line to the variable."

So the general pattern you'll see constantly in Bash is:

read variable

followed later by:

in bash scripting why cant we give spaces ; name="Akshit"

Because in Bash, **spaces are meaningful syntax**. Bash uses spaces to separate different parts of a command.

So this works:

name="Akshit"

But this does **not**:

name = "Akshit"

### Why?

Bash interprets:

name="Akshit"

as one single thing:

> **Assign the value `"Akshit"` to the variable `name`.**

There is no space between `name`, `=`, and `"Akshit"`.

But when you write:

name = "Akshit"

Bash sees **three separate words**:

name

=

"Akshit"

Bash therefore thinks you're trying to **execute a command called `name`**, with `=` and `"Akshit"` as arguments.

It's essentially interpreted like:

command_name argument1 argument2

Since there is normally no command called `name`, you get something like:

name: command not found

### The important Bash rule

For variable assignment:

variable=value

**No spaces around `=`.**

Examples:

name="Akshit"

age=21

city="Delhi"

If the value contains spaces, that's completely fine:

name="Akshit"

The quotes protect the space **inside the value**.

So:

name="Akshit "

means:

variable → name

value    → Akshit 

while:

name = "Akshit"

means:

command → name

argument → =

argument → Akshit

This is one of those Bash rules that looks weird initially, but it comes from Bash's fundamental idea that **whitespace separates shell words/tokens**.
