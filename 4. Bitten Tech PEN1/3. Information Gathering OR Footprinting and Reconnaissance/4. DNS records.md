# DNS Records

> [!info] What are DNS records?
> Instructions stored in DNS that tell the internet **what a domain name means** and **where different services are located**.
> For OSCP, DNS records can reveal **subdomains, IP addresses, mail servers, and internal infrastructure** during enumeration.

## Common DNS Record Types

| Record | Purpose | Example |
|---|---|---|
| **A** | Domain → IPv4 address | `example.com → 10.10.10.5` |
| **AAAA** | Domain → IPv6 address | `example.com → 2001:db8::1` |
| **CNAME** | Alias → another domain | `www → example.com` |
| **MX** | Specifies mail server | `example.com → mail.example.com` |
| **NS** | Specifies authoritative DNS servers | `ns1.example.com` |
| **TXT** | Arbitrary text; often verification/security data | SPF, domain verification |
| **SOA** | Administrative information about the DNS zone | Primary NS, serial, timers |
| **PTR** | IP → domain name (reverse DNS) | `10.10.10.5 → server.example.com` |

---

## How Each Record Helps You During a Pentest

### A Record

Maps domain → **IP address**.

```bash
dig A example.com
nslookup example.com
```

➡️ Gives you an **IP address** to investigate and port-scan.

---

### CNAME

Shows that one domain is an **alias** for another.

```bash
dig CNAME www.example.com
```

➡️ Reveals infrastructure relationships — e.g. `dev.example.com` might alias to an S3 bucket or another server, exposing how the organisation deploys systems.

---

### MX

Identifies which servers handle **email** for the domain.

```bash
dig MX example.com
```

➡️ Maps the organisation's email infrastructure and may expose additional attack surface (e.g. self-hosted mail servers).

---

### NS

Shows the **authoritative DNS servers** for the domain.

```bash
dig NS example.com
```

➡️ Useful for further DNS enumeration (e.g. attempting zone transfers against these servers).

---

### TXT

Contains arbitrary text — often security/config data (SPF, DKIM, DMARC, domain verification tokens).

```bash
dig TXT example.com
```

➡️ Usually **informational** rather than an immediate vulnerability, but can reveal cloud provider details, verification tokens, etc.

---

### PTR (Reverse DNS)

Maps IP → **hostname** (the reverse of an A record).

```bash
dig -x 10.10.10.5
```

➡️ Can reveal **hostname naming conventions** that hint at a machine's role:
- `db-prod-01.example.com` → database server
- `webdev.example.com` → dev web server

---

## 🔥 Why DNS Matters in OSCP

### Scenario

You're given: `example.com`

After DNS enumeration you discover:
- `dev.example.com` → 10.10.10.15
- `mail.example.com` → 10.10.10.20
- `vpn.example.com` → 10.10.10.25

You've gone from **1 known target → several potential targets**. The production site may be hardened, but the **dev server** might be poorly configured.

> [!important] Key mental model
> Don't think: *"I found an MX record. How do I exploit MX?"*
>
> Instead think: **"What does this DNS information tell me about the target?"**
>
> **DNS → discover infrastructure → identify hosts → enumerate services → find vulnerabilities.**

## OSCP Enumeration Workflow

When you get a domain, run through these:

```bash
# All records at once
dig any example.com

# Individual record types
dig A example.com
dig AAAA example.com
dig MX example.com
dig NS example.com
dig TXT example.com
dig CNAME www.example.com

# Reverse DNS
dig -x <IP>

# Attempt zone transfer (try against each NS server)
dig axfr example.com @ns1.example.com

# Quick lookup
nslookup example.com
host example.com
```

## OSCP Priority Rating

> [!tip] ⭐ 6/10 — Know them, but don't over-study them.
> - Understand what A, CNAME, MX, NS, TXT, PTR records mean
> - Be comfortable with `dig`, `nslookup`, `host`
> - Main OSCP value is **reconnaissance** — mapping infrastructure and expanding attack surface
> - Don't spend hours memorising every DNS record type

### In Real-World Cybersecurity — **Much more important**

| Use Case | Description |
|---|---|
| **Reconnaissance** | Map an organisation's external infrastructure |
| **Subdomain discovery** | `dev.example.com`, `vpn.example.com`, etc. |
| **Cloud discovery** | Identify services hosted on cloud providers |
| **Email security** | SPF, DKIM, DMARC analysis |
| **Incident response** | Investigate suspicious DNS queries |
| **DNS tunnelling detection** | Identify covert data transfer through DNS |
| **Domain takeover** | Dangling CNAMEs and abandoned services |
| **Active Directory** | AD heavily relies on DNS for locating domain controllers and services |
