# Task 3 — Active Directory

## AD Object Types

### Users

Users are **security principals** — they can be authenticated by the domain and assigned privileges over resources.

Two types of user entities:
- **People:** Employees who need network access
- **Services:** Accounts used by services like IIS or MSSQL (only have privileges needed for their specific service)

### Machines

- For every computer that joins the domain, a **machine object** is created
- Machines are also **security principals** with their own account
- Machine account naming: computer name + `$` (e.g., `DC01` → `DC01$`)
- Machine passwords are **automatically rotated** and typically 120 random characters

> [!tip] Pentesting Relevance
> Machine account passwords rotate automatically and are virtually impossible to crack. User passwords are human-created, shorter, and much easier to target.

### Security Groups

Groups assign access rights to entire groups instead of single users.

| Security Group | Description |
|----------------|-------------|
| **Domain Admins** | Administrative privileges over the entire domain, including DCs |
| **Server Operators** | Can administer DCs, cannot change admin group memberships |
| **Backup Operators** | Can access any file (ignoring permissions) for backups |
| **Account Operators** | Can create or modify other accounts |
| **Domain Users** | All existing user accounts in the domain |
| **Domain Computers** | All existing computers in the domain |
| **Domain Controllers** | All existing DCs on the domain |

Full list: [Microsoft Documentation](https://docs.microsoft.com/en-us/windows/security/identity-protection/access-control/active-directory-security-groups)

## GPO Distribution — SYSVOL

GPOs are distributed via a network share called **SYSVOL**, stored on the DC.

```
          Domain Controller
                │
       ┌────────┴────────┐
       │                 │
     AD DS             SYSVOL
       │                 │
  Users, Groups,     GPO files
  Computers, etc.   Scripts, etc.
```

Default path: `C:\Windows\SYSVOL\sysvol\`

**SYSVOL structure:**

```
DC01
│
└── SYSVOL
     │
     └── domain.local
          │
          └── Policies
               │
               ├── {GPO-ID-1}
               ├── {GPO-ID-2}
               └── {GPO-ID-3}
```

Access via UNC path:

```
\\domain.local\SYSVOL
\\DC01\SYSVOL
```

> [!warning] Security Relevance
> SYSVOL is readable by domain machines/users. Historically, admins stored credentials in GPO files — **SYSVOL enumeration is an important step during AD security assessments**.

**Force GPO sync:**

```powershell
PS C:\> gpupdate /force
```

> GPOs normally take up to **2 hours** to propagate; `gpupdate /force` syncs immediately.

# Task 7 — Authentication Methods

Two protocols for network authentication in Windows domains:

| Protocol | Status | Method |
|----------|--------|--------|
| **Kerberos** | Default in modern domains | Ticket-based |
| **NetNTLM** | Legacy (kept for compatibility) | Challenge-response |

---

## Kerberos Authentication

### Core Concept

> **Authenticate once, receive tickets, use tickets to access services.**

Instead of sending your password every time:

```
Login → Get TGT → Use TGT to request TGS → Use TGS to access service
```

### The 3 Key Components

| Component | Think of it as |
|-----------|---------------|
| **KDC** (Key Distribution Center) | Ticket authority (runs on DC) |
| **TGT** (Ticket Granting Ticket) | "I have authenticated" ticket |
| **TGS** (Ticket Granting Service) | "I'm allowed to access THIS service" ticket |

```
TGT → used to get TGS
TGS → used to access service
```

### KDC Structure

```
            Domain Controller
                   │
                  KDC
                   │
      ┌────────────┴────────────┐
      │                         │
 AS (Authentication        TGS (Ticket Granting
    Service)                   Service)
      │                         │
   Gives TGT              Gives service tickets
```

---

### Step 1 — User Requests a TGT (AS-REQ → AS-REP)

User authenticates to the KDC:

```
User
 │
 │ Username + timestamp
 │ encrypted using key derived from password
 ▼
KDC
```

The timestamp proves the request is fresh.

**KDC responds with:**

```
KDC
 │
 ├── TGT (encrypted with krbtgt account's password hash)
 │
 └── Session Key
        ↓
       User
```

> The TGT is **not readable by the user** — it's encrypted with the `krbtgt` account's hash.

**Inside the TGT:**

```
TGT
┌──────────────────────────┐
│ User information          │
│ Session Key (copy)        │
│ Other Kerberos data       │
└──────────────────────────┘
        │ encrypted with
        ▼ krbtgt-derived key
```

The KDC doesn't need to store Session Keys separately — it can recover them by decrypting the TGT.

![](attachments/Pasted%20image%2020261004152654.png)

---

### Step 2 — User Requests a TGS (TGS-REQ → TGS-REP)

User wants to access a service (e.g., `\\FILE01\Finance`):

```
User sends to KDC:
├── Username
├── Timestamp encrypted with Session Key
├── TGT
└── SPN (Service Principal Name)
```

**SPN (Service Principal Name)** = the identity/name of a particular service:

```
cifs/FILE01         → CIFS/SMB service on FILE01
HTTP/webserver      → HTTP service on webserver
MSSQLSvc/database   → MSSQL service on database
```

**KDC responds with:**

```
KDC
 │
 ├── TGS (encrypted using Service Owner Hash)
 │
 └── Service Session Key
```

> A TGS is **specific to the service** — `TGS for FILE01 ≠ TGS for SQL01 ≠ TGS for WEB01`

The TGS is encrypted using a key derived from the **Service Owner Hash** (the account under which the service runs). The service can decrypt/validate the ticket using its own account's secret.

![](attachments/Pasted%20image%2020261004152707.png)

---

### Step 3 — TGS Goes to the Service (AP-REQ)

User presents TGS to the service:

```
User
 │
 │ TGS
 ▼
FILE01 → validates ticket → Access granted
```

The service decrypts the TGS using its configured account's password hash and validates the Service Session Key.

![](attachments/Pasted%20image%2020261004152718.png)

---

### Complete Kerberos Flow

```
          AS-REQ
User ──────────────► KDC
                     │
          AS-REP     │
User ◄───────────────┘
       TGT + Session Key


          TGS-REQ
User ──────────────► KDC
                     │
          TGS-REP    │
User ◄───────────────┘
       TGS + Service Session Key


          AP-REQ
User ──────────────► Service
                       │
                       ▼
                     Access
```

> [!tip] Memory Trick — The Hotel Analogy
> 1. **TGT** = You prove your identity at reception → get a **master hotel pass**
> 2. **TGS** = You take your pass to reception and say "I need Room 301" → get a **room-specific ticket**
> 3. **Service** = You present the room ticket to the lock → **access granted**

### Why Kerberos is Useful — Single Sign-On

```
Without Kerberos:               With Kerberos:
User                            User
 ├── password → FILE01           └── authenticate once
 ├── password → SQL01                    ↓
 ├── password → WEB01                   TGT
 └── password → SERVER01                ↓
                                 ┌──────┼──────┐
                                TGS    TGS    TGS
                                 │      │      │
                              FILE01  SQL01  WEB01
```

### Memorize This

```
AS-REQ → TGT
TGT → TGS-REQ
TGS → Service
```

## NetNTLM Authentication

### Core Concept

> **Challenge-response authentication — the password is NEVER sent across the network.**

```
Server: "Prove that you know the password."
         ↓
Server → Random challenge
Client → Response calculated from password hash + challenge
         ↓
If response correct → authenticated
```

![](attachments/Pasted%20image%2020261004152730.png)

### The 6-Step Process

**Setup:** Client `PC01` (user `CORP\Akshit`) wants to access `FILE01`

#### Step 1 — Client requests authentication

```
PC01 ──── Authentication request ────► FILE01
```

#### Step 2 — Server sends a challenge

```
FILE01 ──── Challenge: ABC123... ────► PC01
```

#### Step 3 — Client calculates a response

```
Password-derived hash + Challenge + Other data
                    ↓
                Calculation
                    ↓
                 Response

PC01 ──── Response ────► FILE01
```

> The password/hash is **NOT** sent — only the calculated response.

#### Step 4 — Server asks the Domain Controller

For domain accounts, FILE01 doesn't have the hash locally:

```
FILE01 ──── Challenge + Response ────► DC01
```

#### Step 5 — DC verifies the response

```
DC calculates: Challenge + User's hash → Expected response
Compare: Expected == Received? → Success/Failure
```

#### Step 6 — Result goes back

```
DC01 ──── Result ────► FILE01 ──── Result ────► PC01
```

### Complete NetNTLM Flow

```
       CLIENT              SERVER                DC
          │                   │                   │
          │ Authentication   │                   │
          ├──────────────────►│                   │
          │                   │                   │
          │◄── Challenge ─────│                   │
          │                   │                   │
          │── Response ──────►│                   │
          │                   │                   │
          │                   │ Challenge +       │
          │                   │ Response           │
          │                   ├──────────────────►│
          │                   │                   │
          │                   │◄── Result ─────────│
          │                   │                   │
          │◄── Result ────────│                   │
          │                   │                   │
```

### Domain Account vs. Local Account

| Account Type | Verification Path |
|-------------|-------------------|
| Domain (`CORP\Akshit`) | `PC01 → FILE01 → DC01` |
| Local (`FILE01\Akshit`) | `PC01 → FILE01 → FILE01's SAM` |

> Local accounts are verified against the local **SAM (Security Account Manager)** — no DC needed.

## Kerberos vs. NetNTLM Comparison

| | **Kerberos** | **NetNTLM** |
|---|---|---|
| Main concept | Tickets | Challenge-response |
| Default in modern AD | Yes | Fallback/legacy |
| Password sent directly? | No | No |
| Uses DC? | KDC on DC | Domain accounts → DC verification |
| Key terms | TGT, TGS, SPN, KDC | Challenge, response, NTLM hash |

**Memory trick — K-T-S vs C-R:**

```
Kerberos: KDC → TGT → TGS → Service
NetNTLM:  Challenge → Response → Verification
```

### Important Terminology Distinction

| Term | Meaning |
|------|---------|
| **NTLM** | Authentication protocol/family |
| **NetNTLM** | Network challenge-response authentication |
| **NT hash** | Password-derived hash/credential material |

> Don't confuse "NTLM hash" with "NetNTLM authentication response" — related but **not the same**.

### Why NetNTLM Matters for Security

The challenge + response exchange can potentially be **captured and subjected to offline password cracking**. Related attack concepts:

```
NTLM, NetNTLMv2, Challenge, Response, SMB, LLMNR, NBT-NS, WPAD, Responder
```

> The password wasn't sent — but **authentication exchange material was exposed**, providing material for offline cracking.

## Trees

When a company expands (e.g., new country with different laws), it may need multiple domains sharing the same namespace:

```
        thm.local        ← root domain
            │
    ┌───────┴───────┐
    ▼               ▼
uk.thm.local    us.thm.local   ← subdomains
```

Each branch has its own DC, managing only its own resources. Policies can be configured independently per domain.

> [!note] Enterprise Admins
> A new security group — **Enterprise Admins** — grants administrative privileges over **all domains** in the enterprise. Each domain still has its own Domain Admins for single-domain control.

## Forests

When companies with **different namespaces** merge (e.g., `thm.local` acquires `mht.local`), connecting these domain trees creates a **forest**.

A forest is the **highest security boundary** in Active Directory.

![](attachments/Pasted%20image%2020261004173534.png)

## Trust Relationships

Trusts allow users in one domain to access resources in another domain.

### One-Way Trust

If `Domain AAA` trusts `Domain BBB`:
- BBB's users **can** access AAA's resources
- AAA's users **cannot** access BBB's resources

```
Direction of trust:    AAA ──trusts──► BBB
Direction of access:   BBB ──────────► AAA
```

> The direction of trust is **contrary** to the direction of access.

![](attachments/Pasted%20image%2020261004173546.png)

### Two-Way Trust

Both domains mutually authorise users from each other. **Default** when joining domains under a tree or forest.

> [!warning] Trust ≠ Automatic Access
> Having a trust relationship **doesn't automatically grant access** to all resources. It only creates the **possibility** to authorise users across domains — actual permissions must still be configured.

### Trust Types

| Type | Description |
|------|-------------|
| **One-Way** | One domain trusts the other (unidirectional) |
| **Two-Way** | Mutual trust (bidirectional) |
| **Transitive** | Trust extends through the chain (if A→B and B→C, then A→C) |
| **Non-transitive** | Trust limited to the two domains only |
