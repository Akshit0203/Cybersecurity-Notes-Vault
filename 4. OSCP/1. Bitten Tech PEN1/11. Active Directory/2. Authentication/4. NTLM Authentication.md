### **[Part 1: Introduction to NTLM & Challenge-Response Mechanism]**

Hello friends. In this video, we are going to talk about **New Technology LAN Manager (NTLM)**. Actually, this is an authentication mechanism that we use to store passwords—meaning hashing it to authenticate. It is a mechanism, an algorithm, a type of hashing algorithm.

What happens in this? LM has versions 1 and 2, and NTLM has versions 1 and 2. That means if you combine LM and NTLM, it forms NTLM itself—it is a mixture of both: LM + NTLM. It works on a **Challenge-Response protocol**. This means that when I want to authenticate someone, I will ask them a question, and if they give the correct answer to that question—which only they know—then I will understand that the user entering the password is indeed the user whose password it is. That is its primary advantage.

---

### **[Part 2: Domain Accounts vs. Local Accounts Authentication Flow]**

When you want to authenticate to a server—whether local or remote—first you enter your username and password. When you enter the password, it sends a request to the domain authentication service running inside the Domain Controller.

If the account is a **domain account**, it authenticates with the controller of the domain you belong to. When your account is registered in the Domain Controller, and your PC or server is authenticated and added to the Domain Controller as part of that domain, that account is called a domain account and gets verified with the Domain Controller.

However, if it is a **local account**—meaning it resides on that specific system and hasn't gone anywhere outside—it is an account created locally on that machine, so we check its local database. We check its SAM file, and by matching the password with the SAM file, you get authenticated. In most enterprise cases, domain accounts are used rather than local accounts.

---

### **[Part 3: Core Operations of NTLM: Authentication, Signing, and Sealing]**

The three **core operations of NTLM** are:

1. **Authentication**: Performs authentication using the Challenge-Response protocol. You send your password along with the answer to whatever challenge the server poses.
2. **Signing**: Applies digital signatures using a symmetric signature scheme (Message Authentication Code / MAC). This verifies that the Challenge-Response message is digitally signed and comes from the legitimate sender. A common shared key exists between the sender and receiver; if anyone else attempts to send it, it will fail.
3. **Sealing**: Refers to message encryption via the NTLM Security Support Provider (NTLMSP). Whatever is transmitted across the network is encrypted so that if an attacker eavesdrops or performs a man-in-the-middle attack, they cannot capture the password. Symmetric encryption is used because it is fast.

---

### **[Part 4: NTLM vs. Kerberos & The Challenge-Response Flow Example]**

NTLM is not as commonly used today as **Kerberos**, which is more secure, more efficient, and serves as the modern default protocol in Windows environments. However, NTLM is still widely encountered alongside Kerberos.

The authentication workflow functions as follows: When a user (such as Sheila) requests authentication to a service or server, she enters her password. The password is hashed, and that hash is sent toward the Domain Controller. In the Domain Controller's database, Sheila's password hash is stored. When the Domain Controller receives the request, it issues a **challenge**, and Sheila's system returns a **response**. The Domain Controller verifies whether the response matches the stored password hash. If they match, the user is authenticated and granted a service pass.

That covers how the NTLM Challenge-Response protocol operates. Keep watching, keep learning, and goodbye!
