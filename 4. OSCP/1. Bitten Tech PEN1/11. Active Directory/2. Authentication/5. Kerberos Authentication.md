
Kerberos Authentication:
Kerberos version 5 provides mechanism for mutual authentication between client and server or two servers.
The Kerberos Key Distribution Center (KDC) uses the domain's Active Directory service database as it's security account database.
The communication takes place on the active Internet, where an attacker can easily impersonate as either client or a server and can eavesdrop or tamper with communication between legitimate clients and servers.

Main entities involved in Kerberos flow:
Client: Initiates the communication for a service request. Acts on behalf of the user.
Server: The server with the service the user wants to access.
SHIT Authentication Sever (AS): Performs client authentication. The AS issues a ticket called TGT (Ticket Granting Ticket) that proves to other servers that client has been authenticated.

Main entities involved in Kerberos flow:
Key Distribution Center (KDC): Authentication server is logically separated into three parts: Database (db), Authentication Server (AS) and Ticket Granting Server (TGS)., all existing in a single server called Key Distribution Center.
Ticket Granting Server (TGS): An application server which provides the issuing of service tickets as a service.\

### **[Part 1: Introduction to Kerberos Authentication & Key Distribution Center]**

Hello friends. In this video, we are going to talk about a very important topic: **Kerberos Authentication**. We have already studied NTLM, and as an advancement over it, Microsoft introduced Kerberos authentication for user account management and authentication in modern Windows environments. Currently, Kerberos operates on Version 5 and provides mutual authentication between a client and a server or between two servers.

Many distinct terms and concepts are introduced in Kerberos. In this architecture, an administrative server called the **Key Distribution Center (KDC)** is formed by combining two core servers to manage and distribute keys.

---

### **[Part 2: Active Directory Integration & Remote Authentication]**

The KDC relies directly on Active Directory to manage the security accounts database containing all user and computer accounts. Any authentication that occurs is verified against this Active Directory database.

Kerberos authentication is not limited to a local network; communication occurs over the active internet. Regardless of where you are located, you can authenticate with a remote server through access controls—for example, connecting from Australia to a remote server located in Germany over the internet.

---

### **[Part 3: Security Risks, Entities, and the Client/Server Roles]**

When authentication traffic is exposed to the internet, security risks such as eavesdropping or rogue clients and servers arise. Therefore, robust encryption and secure authentication are necessary to prevent interception.

The main entities involved in Kerberos are:

- **Client**: Software that initiates access requests on behalf of a human user who needs access to a specific network service (such as a printer, a file share, a web server, or an application).
- **Server**: The target workstation or host where the desired service (such as SAP, FTP, or SSH) is hosted and executed.
- **Authentication Server (AS)**: The component that receives the initial authentication request and verifies whether the user's entered credentials are correct.

---

### **[Part 4: Authentication Server (AS) & Ticket Granting Ticket (TGT)]**

When you enter your password, the request first reaches the Authentication Server (AS). Once the AS validates your password against the database, it issues a **Ticket Granting Ticket (TGT)**.

The TGT is an encrypted ticket that proves to other servers that you have successfully authenticated. However, holding a TGT alone does not grant direct access to a specific service yet—your authentication is only halfway complete.

---

### **[Part 5: Ticket Granting Server (TGS) & Key Distribution Center (KDC)]**

To obtain access to a specific service, you interact with the **Ticket Granting Server (TGS)**. The TGS evaluates your request and grants a **Service Ticket**, which you present to the target application server to access the resource.

Combining the **Authentication Server (AS)** and the **Ticket Granting Server (TGS)** alongside the Active Directory database forms the **Key Distribution Center (KDC)**. All three components reside on a single server structure known as the KDC.

---

### **[Part 6: Detailed 6-Step Kerberos Authentication Flow]**

The complete Kerberos authentication mechanism operates through six core steps:

1. **User Authentication Request**: The user enters their username and password, sending an initial request to the Authentication Server (AS) inside the KDC.
2. **AS Verification & TGT Issuance**: The AS verifies the password against the database. Upon successful verification, the AS encrypts a Ticket Granting Ticket (TGT) using a secret session key shared strictly between the AS and the TGS, and sends the encrypted TGT back to the client.
3. **Client Holds TGT**: The client receives the encrypted TGT. Because the client lacks the AS-TGS shared key, the client cannot decrypt or alter the TGT.
4. **Request to TGS**: The client sends the encrypted TGT along with the **Service Principal Name (SPN)**—the specific name of the desired service—to the Ticket Granting Server (TGS).
5. **TGS Decryption & Service Ticket Issuance**: The TGS uses its shared key with the AS to decrypt and validate the TGT. Once validated, the TGS issues a **Service Ticket** encrypted with a key shared between the TGS and the target application server.
6. **Service Access**: The client presents the Service Ticket to the target application server, which decrypts it and grants access to the requested service.

---

### **[Part 7: Password Hashing vs. Authentication Protocols]**

It is important to note that Kerberos itself is an authentication protocol defining the data flow across servers, whereas password hashing still relies on the NTLM algorithm.

Because tickets (TGT and Service Tickets) are encrypted using shared keys known only to the KDC servers and application servers, clients cannot decrypt, tamper with, or manipulate ticket data to request unauthorized services. Everything is systematically validated across the network.
