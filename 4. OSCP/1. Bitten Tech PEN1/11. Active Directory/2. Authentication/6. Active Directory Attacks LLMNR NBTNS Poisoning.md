
LLMNR/NBT-NS
Poisoning

Link-Local Multicast Name Resolution (LLMNR) and NetBIOS Name Service (NBTNS) are components of Microsoft Windows systems that are alternate methods
of host identification when DNS fails.
▰ LLMNR and NBT-NS can be spoofed by listening for LLMNR (UDP 5455) or NBTNS (UDP 137) broadcasts going over the wire and respond to them.
▰ The attacker can then trick the target into sending the NTLMv2 or v1 hash which
is used for network level authentication making access to network resources
seamless for the end user.

### **[Part 1: Introduction to LLMNR / NBT-NS Poisoning & Protocol Overview]**

Hello friends. From this video, we are starting to learn about Active Directory attacks. Here I will explain both theory and practicals to you. We have built the lab, and now using that lab, we will perform attacks and do testing in that environment. We need an attacking machine like Kali and a victim, which could be our Windows 10 server or our user machine. In many cases, the server is not involved; the work gets done directly through the user machine. In this course, I am discussing two attacks that I feel are very important and that you must know. So in this video, we are going to start with an attack named **LLMNR and NBT-NS Poisoning**.

First of all, you need to know the full form of these protocols and their meanings:

- **LLMNR**: Link-Local Multicast Name Resolution.
- **NBT-NS**: NetBIOS Name Service.

A local link refers to services (like DNS or DHCP) operating on the same local network segment, a convention primarily used in IPv6 contexts. LLMNR is the modern successor to NetBIOS Name Service, but both protocols function similarly within Windows environments. Microsoft created these proprietary protocols as fallback mechanisms to perform host name-to-IP address resolution when DNS fails to identify a host.

---

### **[Part 2: DNS Failures, Multicast Requests, and Attacker Exploitation]**

DNS fails when a user attempts to access a network resource (such as a shared folder on the C drive) but misspells or enters an incorrect hostname. When the request reaches the Domain Controller, the Domain Controller cannot resolve the misspelled hostname. It notifies the client that it has no record for that host, leaving the client with no choice but to query the entire local network.

The client issues a multicast/broadcast request asking all hosts on the local network: _"Does anyone know the location of this host?"_. Attackers leverage this behavior similarly to ARP spoofing. If an attacker is present on the local network and observes a client searching for a hostname, the attacker responds: _"Yes, I know that host; send me your NTLM hash to authenticate, and I will connect you"_.

For example, if a user attempts to access a shared folder named `hackme` but accidentally types `hackm`, the Domain Controller rejects the query. The client broadcasts `hackm` across the network. The attacker intercepts this broadcast, claims to be `hackm`, and requests the user's NTLM authentication hash. The client transmits its NTLM hash, which the attacker captures.

---

### **[Part 3: Responder Tool Setup & Command Configuration]**

To perform this attack, we use **Responder**, a Python-based listener utility pre-installed on Kali Linux located at `/usr/share/responder/Responder.py`. Responder listens on network interfaces to capture and poison local broadcast and multicast traffic. As a best practice during penetration tests, Responder should be kept running in the background to document and capture network traffic.

Key Responder CLI parameters:

- `-i eth0`: Specifies the active network interface (`eth0`).
- `-r`: Enables responses for NetBIOS suffix queries.
- `-d`: Enables responses for NetBIOS domain suffix queries.
- `-w`: Starts a rogue WPAD proxy server to capture web authentication requests.
- `-v`: Enables verbose output logging.

Starting the listener command:

```
python3 Responder.py -i eth0 -rdwv
```

Responder initializes its listeners for LLMNR, NBT-NS, MDNS, and SMB services, waiting for incoming network queries.

### **[Part 4: Executing the Poisoning Attack & Capturing NTLMv2 Hashes]**

On the Windows 10 victim machine (logged in as domain user `ansh_b` under the domain `bittu_tech`), navigating in File Explorer to an invalid UNC path or directly to the attacker's IP address (`\\192.168.75.131`) triggers an authentication request.

The client automatically sends its **NetNTLMv2 (NTLMv2)** authentication hash over the SMB protocol to Responder. Responder intercepts the request and dumps the full NTLMv2 hash string, displaying the account username (`ansh_b`), domain name (`bittu_tech`), victim IP address, and challenge-response structure.

---

### **[Part 5: Cracking NetNTLMv2 Hashes with Hashcat]**

Once captured, copy the NTLMv2 hash string from Responder and save it to a file named `hash.txt`.

To crack the hash offline:

1. Identify Hashcat's hash mode for NetNTLMv2 by filtering Hashcat help:
    
    ```
    hashcat --help | grep -i NTLM
    ```
    
    Mode `5600` corresponds to **NetNTLMv2**.
2. Execute Hashcat using the `rockyou.txt` wordlist:
    
    ```
    hashcat -m 5600 hash.txt rockyou.txt --force -O
    ```
    
3. To view cracked credentials:
    
    ```
    hashcat -m 5600 hash.txt rockyou.txt --show
    ```
    

Hashcat cracks the 11-character password (`Password12222223`) in approximately **2 seconds** due to GPU acceleration.

---

### **[Part 6: Mitigations & Defense Mechanisms]**

To defend against LLMNR and NBT-NS poisoning:

1. **Disable LLMNR via Group Policy (GPO)**: Navigate to `Computer Configuration -> Administrative Templates -> Network -> DNS Client` and set **Turn off Link-Local Multicast Name Resolution** to **Enabled**.
2. **Disable NBT-NS (NetBIOS over TCP/IP)**: In Network Adapter Properties -> TCP/IPv4 Properties -> Advanced -> WINS tab, select **Disable NetBIOS over TCP/IP**.
3. **Network Security & Access Controls**: Deploy Network Access Control (NAC), network segmentation, and firewalls to prevent unauthorized rogue devices from joining local network segments.
4. **Enforce Complex Passphrases**: Require complex domain passphrases of at least 16 characters to resist offline wordlist cracking attacks.
