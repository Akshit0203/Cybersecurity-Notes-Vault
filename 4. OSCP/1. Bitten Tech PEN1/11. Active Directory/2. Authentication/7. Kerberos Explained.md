### **[Section 1: Introduction to Kerberos & Historical Context]**

Hello friends, I am Ansh, and in this video, we will talk about the **Kerberos Protocol**. This is a very important part of Active Directory authentication, and there are many attacks related to it that are used in AD today. Learning this is crucial for us, as all our concepts will be included here regarding NTLM hashing and authentication. Everything we have studied before will be useful here.

To share a little history on where the name Kerberos came from: the name originated from Greek mythology, specifically a figure depicting a three-headed dog that served as a guard named Cerberus. From that derivation came the name Kerberos. This protocol was originally invented by **MIT** for network authentication. Later, Microsoft standardized it, and today **Kerberos Version 5** is used in modern systems for authentication. It also incorporates NTLM hashing algorithms.

---

### **[Section 2: Improvements over NTLM & Mutual Authentication]**

Significant security improvements were made over the legacy NTLM challenge-response protocol. While security is maintained to a large extent, certain design-level misconfigurations exist that allow specific attack vectors to succeed. Kerberos is a network authentication protocol used in an Active Directory environment to authenticate users or objects.

Version 5 is currently used for **mutual authentication**, meaning not only does the client authenticate to the server, but servers also authenticate to the client, and servers authenticate with each other.

The Kerberos implementation is managed by the **Key Distribution Center (KDC)**, which utilizes the Active Directory database to identify users and verify credentials. The security account database is provided by the Active Directory Domain Services running directly on the **Domain Controller (DC)**. The KDC operates as a core feature on the Domain Controller platform and consists of two main components:

1. **Authentication Server (AS)**
2. **Ticket Granting Server (TGS)**

---

### **[Section 3: Protocol Characteristics: Statelessness & Ticketing]**

Key technical characteristics of Kerberos include:

- **Stateless Protocol**: Kerberos does not maintain session state between steps. If communication occurs in Step 5, the involved parties do not track information from Steps 3 or 4. Every request must include all necessary metadata to complete that specific transaction.
- **Symmetric Key Encryption**: Relies on shared secret keys and temporary session keys to secure all network communications.
- **Ticketing System**: Operates on a ticket-based access model similar to an event ticket or food court pass. Once authenticated, a user receives a ticket stamped with a specific validity period (e.g., default 10 hours). While valid, the ticket grants access to specified network services without requiring re-authentication. Once expired, the ticket must be renewed.

---

### **[Section 4: Key Components & Database Integration]**

The Key Distribution Center (KDC) comprises three primary elements:

1. **Authentication Service (AS)**: Authenticates the user during initial logon to verify that they are a legitimate domain object holding valid credentials.
2. **Ticket Granting Service (TGS)**: Issues specific Service Tickets allowing the user to access network resources (such as file servers, printers, or shares).
3. **Account Database**: Stores user identifiers, passwords, and secret keys. In Active Directory, credentials may be stored in LDAP, the SAM database (for local accounts), or the **`ntds.dit`** database file on Domain Controllers (for domain users and administrators).

---

### **[Section 5: The 3 Request-Response Communication Pairs]**

The Kerberos authentication workflow consists of three distinct request-response pairs:

1. **`AS-REQ` / `AS-REP` (Authentication Service Exchange)**:
    
    - **`AS-REQ`**: The client sends an initial request containing their username/ID, requested service ID, client IP address, and a timestamp encrypted with the user's secret key (NTLM/NT hash).
    - **`AS-REP`**: The AS verifies the user ID against the database, retrieves the user's NT hash, and attempts to decrypt the timestamp. If successful, the AS returns two messages:
        - _Message A_: A client-TGS session key encrypted with the user's secret key (decryptable by the client).
        - _Message B_: The **Ticket Granting Ticket (TGT)** containing the client ID, IP, validity period, and session key. The TGT is encrypted with a secret key known **only to the KDC** (`krbtgt` account hash), making it tamper-proof and unreadable to the client.
2. **`TGS-REQ` / `TGS-REP` (Ticket Granting Service Exchange)**:
    
    - **`TGS-REQ`**: The client presents the unmodified TGT alongside the **Service Principal Name (SPN)** of the target resource and an authenticator block (client ID + timestamp encrypted with the client-TGS session key).
    - **`TGS-REP`**: The TGS decrypts the TGT using its KDC secret key, verifies that the TGT has not expired, validates the authenticator, and checks if the client has permissions for the requested SPN. If approved, the TGS returns:
        - _Message E_: The **Service Ticket** containing a new client-service session key and client details, encrypted with the target service account's secret key (`K_service`).
        - _Message F_: The client-service session key encrypted with the client-TGS session key (decryptable by the client).
3. **`AP-REQ` / `AP-REP` (Application Server Exchange)**:
    
    - **`AP-REQ`**: The client sends the Service Ticket (Message E) and an authenticator encrypted with the client-service session key to the target application/service server.
    - **`AP-REP`**: The application server decrypts the Service Ticket using its service account secret key (`K_service`), extracts the client-service session key, decrypts the authenticator, verifies ticket validity, and grants access to the resource. All subsequent session traffic is encrypted using the client-service session key.

---

### **[Section 6: Summary & Core Benefits of Kerberos]**

Key operational advantages of Kerberos include:

- **Granular Access Control**: Automated enforcement of ticket expiration times limits unauthorized window access.
- **Single Sign-On (SSO)**: Users authenticate once with the AS to obtain a TGT, allowing them to request multiple Service Tickets across the domain without re-entering passwords.
- **Mutual Authentication**: Both clients and servers verify each other's identities before establishing trust.
- **Strong Encryption Standards**: Uses modern AES encryption algorithms rather than deprecated RC4 ciphers.

---

### **[Section 7: Attack Vectors & Vulnerabilities in Active Directory]**

Despite its robust protocol design, specific design characteristics and misconfigurations give rise to major Active Directory attack vectors:

1. **Golden Ticket Attacks**: If an attacker compromises the secret key of the KDC (`krbtgt` account NTLM hash), they can forge arbitrary TGTs with Domain Admin privileges and custom expiration dates.
2. **Kerberoasting**: Because Service Tickets are encrypted with the service account's secret key (NTLM hash), any authenticated domain user can request a Service Ticket for any SPN, extract the encrypted ticket from memory, and crack the service account's password offline.
3. **Pass-the-Hash / Overpass-the-Hash**: NTLM hashes can be used directly to request Kerberos TGTs or authenticate without cracking the underlying plaintext password.
4. **Pass-the-Ticket (PtT)**: Extracted valid TGTs or Service Tickets can be re-injected into memory sessions to hijack administrative access.

Mastering these core Kerberos mechanics is essential for understanding both offensive penetration testing and defensive hardening within Active Directory environments.
