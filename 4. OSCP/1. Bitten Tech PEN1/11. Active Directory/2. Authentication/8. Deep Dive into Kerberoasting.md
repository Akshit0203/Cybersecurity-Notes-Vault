# Kerberoasting — Theory

---

## What Is Kerberoasting?

- An attack that exploits the **Kerberos TGS ticket exchange** design to crack service account passwords offline.
- Any **authenticated domain user** can request a Service Ticket (TGS) for any SPN.
- The returned ticket is encrypted with the **NTLM hash of the service account** — enabling offline password cracking.
- First demonstrated by **Tim Medin** at DerbyCon 2014.

> [!IMPORTANT]
> Kerberoasting targets **user accounts configured with SPNs**, not computer accounts. It exploits a protocol design choice, not a software bug.

## Service Principal Names (SPNs)

- An **SPN** is a unique identifier assigned to each instance of a Windows service.
- Services include: file shares, IIS, CIFS, SQL Server, printers, etc.
- In AD, services run under a specific account's security context.
- Administrators often create **domain user accounts** to act as service accounts (e.g., a domain user running MSSQL).

## The Authorization Void — Why Kerberoasting Works

```
Authenticated User                    TGS
      │                                │
      ├── TGS-REQ (TGT + SPN) ───────►│
      │                                │
      │   TGS does NOT check if the    │
      │   user is authorised for that  │
      │   service — it just issues     │
      │   the ticket.                  │
      │                                │
      │◄── TGS-REP (Service Ticket) ──┤
      │                                │
      │   Ticket is encrypted with     │
      │   the service account's        │
      │   NTLM hash                    │
```

- The TGS **does not verify authorisation** — it does not check if the requesting user should have access to that service.
- Actual authorisation is deferred until the client presents the ticket to the application server.
- This means **any domain user** can request a ticket for **any SPN**.

---

## Offline Cracking Mechanics

1. Attacker requests a Service Ticket for a target SPN.
2. The ticket is encrypted with the service account's NT hash.
3. Attacker **extracts the encrypted ticket from memory**.
4. Attacker performs **offline cracking** (Hashcat, John) on their own machine.
5. Because cracking happens offline — **no network traffic** to DC, no detection, no lockouts.

## User Accounts vs. Computer Accounts

| | User Accounts (Target ✅) | Computer Accounts (Not a target ❌) |
|---|---|---|
| **Password set by** | Administrator (manually) | Active Directory (automatically) |
| **Password length** | Typically short (8–16 chars) | 120+ characters |
| **Password rotation** | Rarely changed | Rotated frequently |
| **Crackability** | Vulnerable to wordlist attacks | Virtually impossible to crack |

---

## Prerequisites

1. **Valid domain credentials** — attacker must already have initial access as an authenticated domain user (to obtain a TGT).
2. **Non-null SPN attribute** — the target domain user account must have a populated `servicePrincipalName` attribute.

| Tool | Usage |
|---|---|

| **John the Ripper** (`krb5tgs` format) | Crack `$krb5tgs$` hashes |

## Mitigations

| Mitigation | Detail |
|---|---|
| **Enable AES encryption** | Switch from RC4 (`RC4_HMAC_MD5`) to AES-128/AES-256 for service accounts — significantly increases cracking difficulty |
| **Strong passwords (25+ chars)** | Service account passphrases must be long and complex. Consider **Group Managed Service Accounts (gMSA)** — AD auto-rotates 128-char passwords |
| **Least privilege** | Never make service accounts Domain Admins. Assign minimal necessary rights |
