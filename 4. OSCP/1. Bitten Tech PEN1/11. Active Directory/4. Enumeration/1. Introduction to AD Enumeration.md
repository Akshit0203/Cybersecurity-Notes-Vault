### **[Section 1: Introduction to Active Directory Enumeration & Initial Access Context]**

Hello friends, I am Ansh, and from this video, we are starting the **Active Directory enumeration step**. This is a very important step—it is essentially the first step when you begin doing anything in Active Directory. Typically, initial access is obtained through non-Active Directory vectors. Most of the time, this is how it works: you obtain initial access through non-AD means. This is because your Active Directory work truly begins only after you enter the system. Prior to that, the tasks typically involve random services running on the web or across the network, which follow standard testing procedures where Active Directory does not yet play a role.

When does the Active Directory component actually come into play? It comes into play when you actually gain access to a domain-joined workstation using a **domain account**. Whenever Active Directory is involved, there are users and services present. Therefore, you need access to at least one user account or at least one service before Active Directory techniques apply. So, initial access in an Active Directory environment is standard, and it is during post-exploitation or privilege escalation that you begin the enumeration process.

---

### **[Section 2: Prerequisites & User vs. Service Enumeration]**

Our primary prerequisite is having **low-privileged access** on a domain workstation as a domain user that belongs to that domain, along with an interactive shell to perform your work. It is not necessary to have administrator privileges or `SYSTEM` access; any ordinary, low-privileged user account is sufficient.

Now, the two primary avenues for enumeration are **users** and **services**. These are the two primary components we care about. Let's discuss services first, as they can yield very interesting findings. What types of services exist? There are many types of services across both Linux and Windows. A service simply enables work to be done—users in a domain perform their daily company work and exchange information, while servers host and run specific services. These can include database servers, FTP servers, web servers, or mail servers.

---

### **[Section 3: Service Accounts & Complex Enterprise Applications]**

All of these services run within a specific security context, executing under a **service account** that defines their privileges, limitations, and policies. Every operating system service runs under the context of an OS user known as a service account. In addition to default Microsoft services, complex enterprise applications—such as IIS, Microsoft SQL Server, or Microsoft Exchange—typically run under the context of domain user accounts.

Often, a specific domain user account is created to run a service, such as creating a dedicated SQL user for SQL Server, an IIS user for IIS, or an HTTP user. You see the same pattern in Linux, where dedicated service accounts exist for MySQL, FTP, or SMTP. Thus, services can execute directly under domain user accounts.

---

### **[Section 4: Service Principal Names (SPNs) and Instance Identifiers]**

A **Service Principal Name (SPN)** is a unique identifier used to uniquely identify a service. Just as user accounts have identifiers like User IDs or the combined SID and RID string, services also have identifiers, but an SPN is a distinct identifier used for services. Technically, an SPN is not just a service identifier; it is an **instance identifier**. A service can have multiple running instances across the network, and the identifier for each specific instance is its Service Principal Name.

By defining configurations, multiple instances of a service can be created, and each instance receives a unique SPN that associates the service instance with its underlying service account. As noted earlier, every service requires an account in order to run.

---

### **[Section 5: The Significance of Service Enumeration & Kerberoasting Target Discovery]**

How do we enumerate services, and what is the significance of doing so? In Kerberos authentication, accessing a service requires obtaining a **Service Ticket**. These Service Tickets are encrypted, and if you crack that encryption, you obtain access to the underlying service account.

Therefore, our goal is to query which domain accounts have valid SPNs associated with them. If a valid SPN is linked to an account, that account can potentially be targeted for attack. To achieve this, we first query all domain accounts to identify how many exist and inspect their SPN values to see which accounts have non-null SPNs. Every account that has a populated SPN is queried and identified as a potential target for a service-based attack. This represents the initial service enumeration step, and we can utilize various tools without limitation—such as PowerShell, BloodHound, SharpHound, and many others that we will encounter moving forward. Different tools can be used, but understanding the core concept is what matters.

---

### **[Section 6: User Enumeration & Recursive Mapping with BloodHound]**

Following service enumeration, user enumeration becomes critical for **lateral movement**. Once you obtain initial access to a user, you need to escalate privileges to achieve administrator access, followed by post-exploitation and lateral movement to compromise users on other machines. To accomplish this, an enumeration map must be constructed.

For this purpose, we use a tool called **BloodHound**. BloodHound works by recursively mapping all privileges, user accounts, access controls, attributes, and object properties across the domain, establishing the relationships between them. It is an exceptionally powerful graphical tool that we will use, and it is the primary tool relied upon during the enumeration phase. BloodHound reveals all domain accounts and their attributes—such as account names, `sAMAccountName` values, associated SPNs, creation dates, group memberships, whether an account is a high-value target, and whether it is Kerberoastable.

Because it is built for security auditing and penetration testing, whenever BloodHound discovers an issue or an interesting target, it also illustrates attack paths to exploit it.

---

### **[Section 7: High-Value Targets & Visualizing Lateral Movement Paths]**

Enumeration begins by identifying all domain users, which can be done using the `net` command or by finding currently logged-in users through Task Manager and other methods. During enumeration, we search for high-value domain groups—such as **Domain Admins**—as well as SPNs and access control lists (ACLs) to stage advanced attacks. More or less, we use BloodHound to map the domain, gather attributes for domain accounts and users, and plan subsequent attacks.

To explain this visually, consider a scenario where we have initial access to a machine called Client 1 under a user account named **Bob**. Once initial access as Bob is established on Client 1, we must enumerate the domain to identify what other workstations and Domain Admins exist. If we collect this information and discover that Bob is logged into another machine, or that Bob—while currently logged into Client 1—is actually a **local administrator on Client 2**, we can leverage Bob's privileges to gain local administrator access on Client 2. That constitutes our first lateral movement step. We use the logged-in credentials from Client 1 to log into Client 2 because Bob has full administrative access there.

---

### **[Section 8: Lateral Movement Chains & OSCP Attack Methodology]**

Once on Client 2, we enumerate that system, identify its users, map permissions, and discover that a user named **Alice** is a local administrator on Server 1. Server 1 is a Domain Controller where domain administration takes place. Even though Jeff is the Domain Admin, Server 1 is the Domain Controller, and Alice has local administrator privileges on Server 1. This means we can gain access to Server 1 through Alice.

Starting logged in as Bob on Client 2, we proceed with enumeration and exploit opportunities to acquire Alice's password hash. After obtaining Alice's hash through post-enumeration exploitation, we can perform a **Pass-the-Hash** attack to gain access to Server 1 (Server 01). Once access to Server 1 is achieved, we enumerate it further to pinpoint the Domain Admins. Actually, identifying who the Domain Admins are can already be determined from Client 1, but gaining access to Jeff's account on the Domain Controller makes you a Domain Admin.

This demonstrates a complete attack chain. In certification exams like **OSCP**, this is the exact methodology you must follow. In an Active Directory exam environment, the standard architecture today typically provides one Domain Controller and two clients. You obtain initial access on the first client, escalate privileges to administrator or `SYSTEM`, gain initial access to Client 2, escalate to `SYSTEM` on Client 2, and finally compromise the third machine—the Domain Controller—to obtain Domain Admin privileges. This complete attack chain—transitioning from a low-privileged user all the way to Domain Admin—must be executed to earn full points, and this is what we are learning in this course.

### **[Section 9: Identifying "What to Attack" vs. "How to Attack"]**

Enumeration is what reveals what you need to exploit. In OSCP, the challenge is often not _how_ to attack, but **what to attack**. Identifying _what_ to attack can be very tricky, which is why many candidates struggle. Knowing _how_ to attack is comparatively straightforward, as thousands of guides and resources are readily available; the key is determining what to target.

Regarding the tools used: as mentioned, **PowerShell** is heavily utilized. If you have interactive Windows access, PowerShell offers numerous scripts—such as PowerView and the PowerSploit suite, which include tools like PowerView and PowerUp. PowerShell syntax can sometimes feel overwhelming and tricky for many people, which is why I am keeping it brief here, though I will create a dedicated course for PowerShell to make it clear.

Beyond PowerShell, **BloodHound** is the most powerful tool, and it is what I personally recommend. BloodHound is available for Linux, while its data collector executable, **SharpHound**, runs on Windows and can be downloaded from GitHub. Both accomplish the same objective, allowing data collection from either Linux or Windows. While basic enumeration can be performed directly from the command prompt—such as running `net user /domain` to list domain users—it is far less powerful, fails to provide deep data, and requires many cumbersome commands.

Therefore, PowerShell and BloodHound are significantly better options. If you want visual aids, superior mapping, clear illustrations, and a graphical format, **BloodHound is the best tool**.
