
# Task 2 Credential Injection

Windows vs Linux

You can get incredibly far doing AD enumeration from a Kali machine. Still, if you genuinely want to do in-depth enumeration and even exploitation, you need to understand and mimic your enemy. Thus, you need a Windows machine. This will allow us to use several built-in methods to stage our enumeration and exploits. In this network, we will explore one of these built-in tools, called the `runas.exe` binary.

Runas Explained

Have you ever found AD credentials but nowhere to log in with them? Runas may be the answer you've been looking for!

In security assessments, you will often have network access and have just discovered AD credentials but have no means or privileges to create a new domain-joined machine. So we need the ability to use those credentials on a Windows machine we control.

If we have the AD credentials in the format of `<username>:<password>`, we can use Runas, a legitimate Windows binary, to inject the credentials into memory. The usual Runas command would look something like this:


```
runas.exe /netonly /user:<domain>\<username> cmd.exe
```


Let's look at the parameters:

- **/netonly** - Since we are not domain-joined, we want to load the credentials for network authentication but not authenticate against a domain controller. So commands executed locally on the computer will run in the context of your standard Windows account, but any network connections will occur using the account specified here.
- **/user** - Here, we provide the details of the domain and the username. It is always a safe bet to use the Fully Qualified Domain Name (FQDN) instead of just the NetBIOS name of the domain since this will help with resolution.
- **cmd.exe** - This is the program we want to execute once the credentials are injected. This can be changed to anything, but the safest bet is cmd.exe since you can then use that to launch whatever you want, with the credentials injected.

Once you run this command, you will be prompted to supply a password. Note that since we added the /netonly parameter, the credentials will not be verified directly by a domain controller so that it will accept any password. We still need to confirm that the network credentials are loaded successfully and correctly.

**Note:** If you use your own Windows machine, you should make sure that you run your first Command Prompt as Administrator. This will inject an Administrator token into CMD. If you run tools that require local Administrative privileges from your Runas spawned CMD, the token will already be available. This does not give you administrative privileges on the network, but will ensure that any local commands you execute, will execute with administrative privileges.


This task is teaching a very useful AD concept:

> **You can discover valid AD credentials without having a domain-joined Windows machine, and `runas.exe /netonly` lets you use those credentials for network authentication from a Windows machine you control.**

Let's break it down.

# 3. What is `runas.exe`?

`runas.exe` is a legitimate Windows program that allows you to launch a program using another set of credentials.

Basic idea:

```
Current Windows user
        │
        │ runas
        ▼
Another credential context
        │
        ▼
Program
```

For example, normally you might run:

```
runas /user:DOMAIN\user cmd.exe
```

Windows would ask for that user's password and attempt to run `cmd.exe` under that account.

But the THM task focuses on:

```
runas.exe /netonly /user:<domain>\<username> cmd.exe
```

The important part is:

```
/netonly
```

---

# 4. What does `/netonly` mean?

This is the key concept.

The THM material says:

> `/netonly` loads the credentials for network authentication but does not authenticate against the domain controller locally.

In simpler terms:

### Local identity

Your Windows machine still considers you to be your **current local Windows user**.

### Network identity

When you access something over the network, Windows can use the credentials you supplied to `runas`.

Think:

```
             Runas /netonly
                  │
          ┌───────┴────────┐
          │                │
          ▼                ▼
      Local machine      Network
          │                │
    Current account    Supplied AD
                       credentials
```

That's why the option is called:

> **NET ONLY**

---

# 5. Example

Suppose your current Windows machine is:

```
WORKSTATION
```

You're logged in locally as:

```
WORKSTATION\Akshit
```

But you've discovered:

```
ZA\john
Password123
```

You can start:

```
runas.exe /netonly /user:za.tryhackme.com\john cmd.exe
```

Windows asks:

```
Enter the password for za.tryhackme.com\john:
```

You enter the password.

A new CMD window opens.

---

# 6. Important: `whoami` can confuse you

Suppose you run:

```
whoami
```

You might still see:

```
WORKSTATION\Akshit
```

You might think:

> "The credentials didn't work!"

But that's not necessarily true.

Remember:

```
Local identity ≠ network identity
```

With `/netonly`, the local process is still running under your local account.

The supplied credentials are intended for **network authentication**.

---

# 7. Why does THM say any password is accepted?

This is a very important detail from your source.

With:

```
/netonly
```

Windows doesn't immediately verify the supplied domain credentials against the DC when creating the process.

Therefore, the `runas` command itself can accept a password even if it's incorrect.

So:

```
runas /netonly
        │
        ▼
Credentials stored for network use
        │
        ▼
Actual network connection
        │
        ▼
Credentials get tested
```

Therefore:

> **Successful `runas` does NOT prove the password is correct.**

You need to perform a network operation that requires authentication.

---

# 8. Why use the FQDN?

The command is:

```
runas.exe /netonly /user:<domain>\<username> cmd.exe
```

The source recommends using the **FQDN**.

For example:

```
za.tryhackme.com
```

rather than simply:

```
ZA
```

So you might have:

```
runas.exe /netonly /user:za.tryhackme.com\username cmd.exe
```

Why?

Because the FQDN provides the complete domain name and helps with correct name resolution in the lab.

---

# 9. What happens after the new CMD opens?

Think of the new CMD as having two identities:

```
New CMD
│
├── Local execution
│      ↓
│   Your current Windows account
│
└── Network authentication
       ↓
   Credentials supplied to /netonly
```

For example:

```
Local command
   ↓
whoami
   ↓
Your local account
```

But a network connection:

```
Network resource
   ↓
Windows authentication
   ↓
Supplied domain credentials
```

That's the entire point of `/netonly`.

---

# 10. Why does the THM note say to start CMD as Administrator?

The source says:

> If you use your own Windows machine, run your first Command Prompt as Administrator.

This is **about your local Windows privileges**, not your AD privileges.

Suppose:

```
Local Windows account
       ↓
Administrator
       ↓
Start elevated CMD
       ↓
runas /netonly
       ↓
New CMD
```

The new CMD can retain/use the local administrator token where appropriate.

But this **does NOT mean**:

```
Local Administrator
        ↓
Domain Administrator
```

Those are completely different things.

---

# 11. Very important distinction

If you have:

```
Local Administrator
```

that means:

> You have administrative privileges on your local Windows machine.

It does **not** automatically mean:

```
Domain Administrator
```

Similarly:

```
Domain User
```

doesn't automatically mean:

```
Local Administrator
```

Think:

```
LOCAL
└── WORKSTATION\Administrator

DOMAIN
└── ZA\Domain Admins
```

Different security boundaries.

---

# 12. Why is this called credential injection?

The THM task calls this **Credential Injection** because you're creating a process where alternative credentials are supplied for network authentication.

Conceptually:

```
Discovered AD credentials
          │
          ▼
   runas /netonly
          │
          ▼
 New Windows process
          │
          ▼
Network authentication
using those credentials
```

You're not changing your actual local Windows login.

You're creating a process configured to use those credentials when communicating over the network.

---

# 13. The most important mental model

Remember this:

```
runas /netonly
        │
        ├── LOCAL → your current Windows identity
        │
        └── NETWORK → supplied credentials
```

That's why:

```
whoami
```

doesn't necessarily show the domain account you supplied.

---

# 14. Kerberos connection

This also connects directly to what you just learned about Kerberos.

When the supplied domain credentials are used for appropriate network authentication, Windows can use the domain's authentication mechanisms.

Conceptually:

```
runas /netonly
       │
       ▼
Network access
       │
       ▼
Domain authentication
       │
       ▼
Kerberos / NTLM depending on context
       │
       ▼
Network resource
```

So this task is essentially teaching you:

> **"I found AD credentials, but I'm sitting on a non-domain-joined Windows machine. How can I make Windows use those credentials for network authentication?"**

Answer:

```
runas.exe /netonly
```

### Memorize this one line:

> **`/netonly` = keep my local identity, but use the supplied credentials when authenticating to network resources.**


It's Always DNS

**Note:** These next steps you only need to perform if you use your own Windows machine for the exercise. However, it is good knowledge to learn how to perform since it may be helpful on red team exercises.

After providing the password, a new command prompt window will open. Now we still need to verify that our credentials are working. The most surefire way to do this is to list SYSVOL. Any AD account, no matter how low-privileged, can read the contents of the SYSVOL directory.

SYSVOL is a folder that exists on all domain controllers. It is a shared folder storing the Group Policy Objects (GPOs) and information along with any other domain related scripts. It is an essential component for Active Directory since it delivers these GPOs to all computers on the domain. Domain-joined computers can then read these GPOs and apply the applicable ones, making domain-wide configuration changes from a central location.

Before we can list SYSVOL, we need to configure our DNS. Sometimes you are lucky, and internal DNS will be configured for you automatically through DHCP or the VPN connection, but not always (like this TryHackMe network). It is good to understand how to do it manually. Your safest bet for a DNS server is usually a domain controller. Using the IP of the domain controller, we can execute the following commands in a PowerShell window:

```powershell
$dnsip = "<DC IP>"
$index = Get-NetAdapter -Name 'Ethernet' | Select-Object -ExpandProperty 'ifIndex'
Set-DnsClientServerAddress -InterfaceIndex $index -ServerAddresses $dnsip
```

Of course, 'Ethernet' will be whatever interface is connected to the TryHackMe network. We can verify that DNS is working by running the following:

Command Prompt

```shell-session
C:\> nslookup za.tryhackme.com
```

Which should now resolve to the DC IP since this is where the FQDN is being hosted. Now that DNS is working, we can finally test our credentials. We can use the following command to force a network-based listing of the SYSVOL directory:

Command Prompt

```shell-session
C:\Tools>dir \\za.tryhackme.com\SYSVOL\
 Volume in drive \\za.tryhackme.com\SYSVOL is Windows
 Volume Serial Number is 1634-22A9

 Directory of \\za.tryhackme.com\SYSVOL

02/24/2022  09:57 PM    <DIR>          .
02/24/2022  09:57 PM    <DIR>          ..
02/24/2022  09:57 PM    <JUNCTION>     za.tryhackme.com [C:\Windows\SYSVOL\domain]
               0 File(s)              0 bytes
               3 Dir(s)  51,835,408,384 bytes free
```

We won't go too much in-depth now into the contents of SYSVOL, but note that it is also good to enumerate its contents since there may be some additional AD credentials lurking there.




IP vs Hostnames

**Question:** _Is there a difference between_ _`dir \\za.tryhackme.com\SYSVOL` and `dir \\<DC IP>\SYSVOL`_ _and why the big fuss about DNS?_

There is quite a difference, and it boils down to the authentication method being used. When we provide the hostname, network authentication will attempt first to perform Kerberos authentication. Since Kerberos authentication uses hostnames embedded in the tickets, if we provide the IP instead, we can force the authentication type to be NTLM. While on the surface, this does not matter to us right now, it is good to understand these slight differences since they can allow you to remain more stealthy during a Red team assessment. In some instances, organisations will be monitoring for OverPass- and Pass-The-Hash Attacks. Forcing NTLM authentication is a good trick to have in the book to avoid detection in these cases.

Using Injected Credentials

Now that we have injected our AD credentials into memory, this is where the fun begins. With the /netonly option, all network communication will use these injected credentials for authentication. This includes all network communications of applications executed from that command prompt window.

This is where it becomes potent. Have you ever had a case where an MS SQL database used Windows Authentication, and you were not domain-joined? Start MS SQL Studio from that command prompt; even though it shows your local username, click Log In, and it will use the AD credentials in the background to authenticate! We can even use this to [authenticate to web applications that use NTLM Authentication](https://labs.f-secure.com/blog/pth-attacks-against-ntlm-authenticated-web-applications/).  

We will be using that in the next task for our first AD enumeration technique.

### **[Section 1: RDP Access & Credential Injection with `runas.exe`]**

Finally, somehow or another, I have logged in here as Linda Franklin. Now we have RDP access, bringing us to the first task: **Credential Injection**. What credential injection means is that you inject your credentials directly into memory so that authentication can take place across the domain. Through the network, you can authenticate as a domain user.

Explaining this in simple terms as we move forward, a specific binary is explained: `runas.exe`. If you have obtained Active Directory (AD) credentials but cannot log in anywhere with them—meaning you have network access and valid user credentials (username and password) discovered during an assessment, but no direct login option or interactive prompt appears—`runas.exe` is a legitimate, genuine utility provided by Microsoft.

For example, if you hold these credentials and need to escalate privileges on the same machine, but do not know how to log in directly, you can use `runas` on any host. It also works if you need to interact with a domain-joined machine. Using `runas`, you load these credentials into memory by providing the syntax `domain\username`, followed by the program you wish to execute.

---

### **[Section 2: The `/netonly` Parameter & Network-Only Authentication Mechanics]**

An example command is provided for `runas.exe` with specific options, such as **`/netonly`**. The `/netonly` switch signifies that if your local workstation is not joined to the domain—such as when operating from your own standalone Windows machine—you need to load credentials into memory so that any authentication directed toward a domain-joined PC succeeds across the network.

Without this, any authentication request would return an "access denied" error because you are not logged in with an AD domain account and your local system is not domain-joined. For this reason, credentials are loaded directly into memory. As studied in concepts like Pass-the-Ticket or Pass-the-Hash, credentials or tickets are injected into memory so network authentication can succeed against the Domain Controller (DC).

The `/netonly` option specifically loads credentials for network authentication mechanisms such as Kerberos. Local commands executed on the local machine continue running under the context of the local account. However, whenever a network connection is initiated—such as executing `dir \\<host>\<directory>` or mounting an SMB share via `net use`—network authentication is performed using the specified domain credentials.

---

### **[Section 3: Target Syntax (`/user`), FQDN, and Spawning `cmd.exe`]**

The second core parameter is **`/user`**, where you specify the target username you wish to authenticate as. The syntax requires the format `domain\username`. While you could specify a short NetBIOS domain name, it is recommended to provide the domain's **Fully Qualified Domain Name (FQDN)**, followed by a backslash and the username.

Following the user argument, you specify `cmd.exe`. While any executable can be supplied, launching `cmd.exe` is the ideal method. When executed, the credentials inject into memory and spawn a new Command Prompt window running under the context of those injected credentials. From that authenticated Command Prompt window, all subsequent network authentication across the domain executes against the injected credentials. Running this command is essential for progressing through subsequent labs.

---

### **[Section 4: Hostname vs. IP Address (Kerberos vs. NTLM Fallback & Blue Team Evasion)]**

As shown, the RDP session disconnected again, which is why explaining the underlying theory first is preferable while reconnection issues persist.

An important architectural distinction exists when authenticating against a Domain Controller or domain computers—such as extracting Group Policy Objects (GPOs) from the DC via SYSVOL. You can supply either the DC's hostname/domain or its IP address. While this makes little difference for solving basic lab exercises, it has significant operational impact during real-world Active Directory penetration tests.

- **Specifying a Hostname**: Kerberos tickets rely strictly on hostnames by default and do not operate with IP addresses. Supplying a hostname forces the system to authenticate via **Kerberos**.
- **Specifying an IP Address**: Because Kerberos cannot resolve authentication via IP addresses, the system falls back to **NTLM**. Specifying an IP address forces NTLM authentication.

The operational significance of this behavior centers on detection and evasion. Enterprise networks feature blue team defenders and security operations centers (SOCs) monitoring alerts. Defensive detection rules are predominantly configured to monitor Kerberos traffic because Kerberos is the default standard, making it the primary vector for attacks like Pass-the-Ticket and Overpass-the-Hash.

Conversely, NTLM is a deprecated fallback protocol that often receives less immediate scrutiny. While both protocols can be inspected in modern environments, Kerberos carries a higher probability of generating noise and triggering defensive alerts. Supplying an IP address reduces network noise, although Kerberos remains mandatory if NTLM is explicitly disabled across the domain.

### **[Section 6: Microsoft Management Console (MMC) & RSAT Prerequisites]**

Moving to the next task, the focus shifts to the **Microsoft Management Console (MMC)**. MMC functions similarly to Server Manager on a Domain Controller. On the `THM-JMP1` workstation, MMC is installed, but Active Directory enumeration services are not enabled by default.

Enumerating AD requires installing the specific Active Directory snap-in: the **Remote Server Administration Tools (RSAT)**. On a custom Windows machine, RSAT must be enabled via `Start -> Apps & Features -> Optional Features` before configuring MMC.

Once prerequisites are configured, the `runas.exe` command executed previously allows MMC to function. Because MMC gathers extensive information from the Domain Controller and authenticates against domain systems, it leverages the injected credentials in memory for all network connections.

### **[Section 7: Advantages, Limitations, and Exploitation Roadmaps Beyond GUI Tools]**

Executing these steps inside the RDP session populates MMC with information covering Organizational Units (OUs), domains, domain trusts, user accounts, servers, and computers.

- **Advantages**: MMC provides a visually clear, hierarchical GUI layout representing the Active Directory environment. Double-clicking objects displays detailed attributes, and objects can be modified if administrative permissions exist.
- **Limitations**: MMC requires interactive GUI access via RDP (port 3389); it cannot be accessed through SSH command-line sessions. Furthermore, MMC cannot construct visual attack paths or build a mind map showing how to transition from low privileges to Domain Admin.

Because MMC was engineered by Microsoft as a legitimate management console rather than an exploitation framework, identifying offensive attack paths requires specialized security tooling. Constructing visual exploitation roadmaps relies on dedicated tools like BloodHound.
