# Task 2 — Credential Injection

> **Core idea:** You can discover valid AD credentials *without* having a domain-joined Windows machine, and `runas.exe /netonly` lets you use those credentials for **network authentication** from a Windows machine you control.
>
> **Memorize:** `/netonly` = keep my local identity, but use the supplied credentials when authenticating to network resources.

## Windows vs Linux

You can get incredibly far doing AD enumeration from a Kali machine. Still, if you genuinely want to do in-depth enumeration and even exploitation, you need to understand and mimic your enemy — so you need a Windows machine. This gives you access to Windows-native functionality. In this network we explore one such built-in tool: the `runas.exe` binary.

```
Kali                        Windows
 ├── nmap                     ├── runas.exe
 ├── ldapsearch               ├── PowerShell
 ├── netexec                  ├── Windows networking
 ├── Impacket                 ├── AD-integrated functionality
 └── Kerberos tools           └── Native Windows authentication
```

## The Problem `runas` Solves

Imagine you're doing an AD assessment from Kali and you discover valid AD credentials:

```
Domain: ZA
Username: bob
Password: Password123
```

But you have **no** domain-joined Windows computer, no permission to join your own machine to the domain, and no pre-configured Windows machine for that domain. How do you actually *use* these credentials? That's where **`runas.exe`** comes in — a legitimate Windows binary that launches a program using another set of credentials.

```
Current Windows user
        │  runas
        ▼
Another credential context
        │
        ▼
     Program
```

## Runas Syntax & Parameters

```
runas.exe /netonly /user:<domain>\<username> cmd.exe
```

- **/netonly** — Since we are not domain-joined, load the credentials for *network* authentication but do not authenticate against a domain controller. Commands executed locally run in the context of your standard Windows account, but any network connections occur using the account specified here.
- **/user** — The domain and username. Always use the **Fully Qualified Domain Name (FQDN)** instead of just the NetBIOS name, since this helps with resolution.
- **cmd.exe** — The program to execute once credentials are injected. Can be anything, but `cmd.exe` is safest since you can then launch whatever you want with the credentials injected.

Once you run this, you are prompted for a password. Because of `/netonly`, the credentials are **not** verified against a DC, so it will accept any password. You still need to confirm the network credentials are loaded correctly (see SYSVOL below).

> **Note:** On your own Windows machine, run your first Command Prompt **as Administrator**. This injects an Administrator token into CMD, so tools requiring local admin privileges run elevated from your Runas-spawned CMD. This does **not** grant network/domain admin — only local elevation.

## The Key Mental Model: `/netonly`

> `/netonly` loads credentials for network authentication but does not authenticate against the domain controller locally.

```
             runas /netonly
                  │
          ┌───────┴────────┐
          ▼                ▼
      Local machine      Network
          │                │
    Current account    Supplied AD
                       credentials
```

- **Local identity** — Windows still considers you to be your current local Windows user.
- **Network identity** — When you access something over the network, Windows uses the credentials you supplied to `runas`.

That's why it's called **NET ONLY**.

### Example

Current machine `WORKSTATION`, logged in locally as `WORKSTATION\Akshit`. You discovered `ZA\john` / `Password123`:

```
runas.exe /netonly /user:za.tryhackme.com\john cmd.exe
```

Windows prompts:

```
Enter the password for za.tryhackme.com\john:
```

You enter the password, and a new CMD window opens.

### `whoami` can confuse you

In the new CMD, `whoami` may still show:

```
WORKSTATION\Akshit
```

This does **not** mean the credentials failed. With `/netonly`, the local process still runs under your local account; the supplied credentials are only for **network** authentication.

```
New CMD
├── Local execution      → your current Windows account   (e.g. whoami)
└── Network authentication → credentials supplied to /netonly
```

### Why "any password is accepted"

With `/netonly`, Windows doesn't verify the supplied domain credentials against the DC when creating the process. The credentials are only tested when an actual network connection requires authentication.

```
runas /netonly → credentials stored for network use → actual network connection → credentials get tested
```

> **A successful `runas` does NOT prove the password is correct.** You must perform a network operation that requires authentication (e.g. listing SYSVOL).

### Why use the FQDN

Use `za.tryhackme.com` rather than just `ZA` — the FQDN provides the complete domain name and helps with correct name resolution in the lab.

## Local Admin ≠ Domain Admin

These are completely separate security boundaries:

```
LOCAL                          DOMAIN
└── WORKSTATION\Administrator   └── ZA\Domain Admins
```

- **Local Administrator** = admin rights on your local Windows machine only.
- Being a **Domain User** does not automatically make you a **Local Administrator**, and vice versa.

## Why it's called "Credential Injection"

You're creating a process where alternative credentials are supplied for network authentication — you are not changing your actual local Windows login.

```
Discovered AD credentials → runas /netonly → new Windows process → network authentication using those credentials
```

When those credentials are used for network authentication, Windows uses the domain's authentication mechanisms (**Kerberos / NTLM** depending on context — see below).

## Verifying Credentials: DNS + SYSVOL

> **Note:** These next steps are only needed if you use your own Windows machine. Still good to know for red team exercises.

After providing the password, a new command prompt opens. To verify credentials work, list **SYSVOL** — any AD account, no matter how low-privileged, can read it.

**SYSVOL** is a folder that exists on all domain controllers. It is a shared folder storing **Group Policy Objects (GPOs)** and related domain scripts. It's essential to AD since it delivers GPOs to all domain computers, enabling domain-wide configuration from a central location.

First configure DNS. Your safest DNS server is a domain controller. Using the DC IP, run in PowerShell:

```powershell
$dnsip = "<DC IP>"
$index = Get-NetAdapter -Name 'Ethernet' | Select-Object -ExpandProperty 'ifIndex'
Set-DnsClientServerAddress -InterfaceIndex $index -ServerAddresses $dnsip
```

(`'Ethernet'` = whatever interface is connected to the TryHackMe network.) Verify DNS works:

```shell-session
C:\> nslookup za.tryhackme.com
```

This should resolve to the DC IP since the FQDN is hosted there. Now force a network-based listing of SYSVOL:

```shell-session
C:\Tools>dir \\za.tryhackme.com\SYSVOL\
 Volume in drive \\za.tryhackme.com\SYSVOL is Windows
 Volume Serial Number is 1634-22A9

 Directory of \\za.tryhackme.com\SYSVOL

02/24/2022  09:57 PM    <DIR>          .
02/24/2022  09:57 PM    <DIR>          ..
02/24/2022  09:57 PM    <JUNCTION>     za.tryhackme.com [C:\Windows\SYSVOL\domain]
               0 File(s)              0 bytes
               3 Dir(s)  51,835,408,384 bytes free
```

It's good to enumerate SYSVOL's contents, since additional AD credentials may be lurking there.

## IP vs Hostnames (Kerberos vs NTLM) — Stealth

> **Question:** Is there a difference between `dir \\za.tryhackme.com\SYSVOL` and `dir \\<DC IP>\SYSVOL`, and why the big fuss about DNS?

It comes down to the authentication method:

- **Hostname / FQDN → Kerberos.** Network authentication attempts Kerberos first. Kerberos uses hostnames embedded in tickets.
- **IP address → NTLM.** Kerberos cannot authenticate via IP, so the system falls back to NTLM.

**Operational significance (evasion):** Blue teams / SOCs predominantly monitor **Kerberos** traffic because it is the default standard and the vector for attacks like Pass-the-Ticket and Overpass-the-Hash. NTLM is a deprecated fallback that often receives less scrutiny. Forcing NTLM (by supplying an IP) reduces noise and can help avoid detection — though Kerberos remains mandatory if NTLM is explicitly disabled across the domain.

## Using Injected Credentials

With `/netonly`, **all** network communication from that command prompt uses the injected credentials — including all network communications of applications launched from that CMD window.

Powerful example: if an MS SQL database uses Windows Authentication and you're not domain-joined, start **MS SQL Studio** from that CMD; even though it shows your local username, clicking **Log In** uses the AD credentials in the background. The same works to [authenticate to web applications that use NTLM Authentication](https://labs.f-secure.com/blog/pth-attacks-against-ntlm-authenticated-web-applications/).

## Lab Questions

| Question | Answer |
|---|---|
| What native Windows binary allows us to inject credentials legitimately into memory? | `runas.exe` |
| What parameter option of the runas binary ensures the injected credentials are used for all network connections? | `/netonly` |
| What network folder on a domain controller is accessible by any authenticated AD account and stores GPO information? | `SYSVOL` |
| When performing `dir \\za.tryhackme.com\SYSVOL`, what type of authentication is performed by default? | Kerberos Authentication (hostname/FQDN supplied, not an IP) |

# Task 3 Prep — Microsoft Management Console (MMC)

MMC functions similarly to Server Manager on a Domain Controller. On **THM-JMP1**, MMC is installed, but AD enumeration services are not enabled by default.

Enumerating AD requires the AD snap-in from the **Remote Server Administration Tools (RSAT)**. On a custom Windows machine, enable RSAT via `Start → Apps & Features → Optional Features` before configuring MMC.

Because MMC gathers extensive information from the DC and authenticates against domain systems, it leverages the **injected credentials in memory** (from `runas.exe /netonly`) for all network connections.

- **Advantages:** Visually clear, hierarchical GUI of the AD environment (OUs, domains, trusts, users, servers, computers). Double-clicking objects shows detailed attributes; objects can be modified if you have admin permissions.
- **Limitations:** Requires interactive GUI access via RDP (port 3389) — not usable over SSH. Cannot build visual attack paths / mind maps from low privilege to Domain Admin. MMC was built by Microsoft as a management console, not an exploitation framework — for offensive attack paths you need dedicated tooling like **BloodHound**.
