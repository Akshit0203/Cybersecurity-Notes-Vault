# Task 3 Enumeration through Microsoft Management Console

**Microsoft Management Console (MMC)** is a Windows framework that provides a **graphical interface for managing and configuring Windows systems**.

Think of MMC as a **container** that hosts different Windows administration tools.

### Simple mental model

```
             Microsoft Management Console
                       (MMC)
                         │
          ┌──────────────┼──────────────┐
          ▼              ▼              ▼
     Event Viewer    Services       Device Manager
          │              │              │
      View logs      Manage        Manage hardware
                     services
```

MMC itself doesn't necessarily perform the management task. Instead, it loads specialized **snap-ins**.

### What is a snap-in?

A **snap-in** is an administrative component that you add to MMC.

Examples:

|Snap-in|Purpose|
|---|---|
|`eventvwr.msc`|Event Viewer|
|`services.msc`|Windows Services|
|`devmgmt.msc`|Device Manager|
|`compmgmt.msc`|Computer Management|
|`gpedit.msc`|Local Group Policy Editor|
|`dsa.msc`|Active Directory Users and Computers|
|`certmgr.msc`|Certificates|

You can launch MMC itself with:

```
mmc.exe
```

Then you can use:

**File → Add/Remove Snap-in**

to add management tools.

### Why `.msc` files?

You'll often see commands like:

```
services.msc
```

`.msc` means **Microsoft Management Console snap-in file**.

So:

```
services.msc
      ↓
MMC loads the Services snap-in
      ↓
You get the Services management GUI
```

### In cybersecurity

MMC is important because many Windows administrative tools are built around it.

For example, in an AD environment:

```
MMC
 │
 ├── Active Directory Users and Computers
 ├── Group Policy Management
 ├── Event Viewer
 ├── Certificates
 └── Computer Management
```

Security testers may encounter MMC when enumerating **users, groups, services, policies, certificates, and domain configuration**.

### 🧠 Memory trick

> **MMC = the Windows management toolbox/container.**  
> **Snap-ins = the individual tools you put inside the toolbox.**

### **[Section 1: RDP Session as Linda Franklin & Identifying Logged-In Users via Task Manager]**

So here we have finally connected via RDP as **Linda Franklin** on this domain-joined workstation. Just now I explained to you about `runas`, but `runas` comes into play when you have a Windows machine that you are using as an attacking machine, from which you want to perform attacks and enumerate—in that case, you have to inject credentials. These are the credentials you obtained from the AD domain, which are Linda's credentials (who is a domain user).

However, here we do not need to do that because we are already joined and logged in as a domain user, so all the authentication credentials are already loaded in memory. If we want to verify this, we can go into Task Manager, and under active sessions, you will see Users. Here you can see that Linda Franklin is logged in, and another user is also logged in here.

This technique is not listed in TryHackMe, but it is a great way to find out which other users are logged into this machine. Linda Franklin is our user—meaning the account we logged in with. And there is another user: **`T1_Henry_Miller`**. He is actually an administrator, and he is currently logged in. We cannot connect directly to his session because we do not have his password. So how can we use this? As we studied in theory, if another user is logged into the same machine, we can become an administrator and dump their credentials using a tool called **Mimikatz**. We will try that as well, but you should know this technique, as it can be a straightforward method in a real engagement, in a CTF, or in an exam like OSCP to discover active users.

### **[Section 2: Launching MMC & Adding Active Directory Snap-ins]**

Now let's move forward and perform the first task: the **Microsoft Management Console (MMC)**. The steps are provided here for what you need to do. First, go to Run. If you open the Run dialog and type **`mmc`**, the MMC console will open.

By default, you do not have the Active Directory snap-ins loaded here, so to enumerate Active Directory, you must add those snap-ins. Go to **File -> Add/Remove Snap-in**. Then add the three Active Directory snap-ins:

1. **Active Directory Domains and Trusts**
2. **Active Directory Sites and Services**
3. **Active Directory Users and Computers**

Add these three and click OK. All three snap-ins will appear in the console tree, but we still need to set their forest, as the forest is not configured yet. If you expand them right now, no objects will appear—no users, computers, or OUs. You must select **Change Forest**. The forest dialog will pre-fill with your domain's FQDN. Verify that it matches your target domain and click OK.

Repeat the same process for the second snap-in. It takes a little time to load and synchronize because it authenticates with the domain in the background. (This is why `runas` is essential if you are operating from your own standalone Windows machine). Allow it some time, select Change Forest, confirm the domain name, and click OK.

For the third snap-in, **Active Directory Users and Computers**, right-click it, select **Change Domain**, confirm the domain name that appears, and click OK. The console will now fully populate.

### **[Section 5: Inspecting User & Server Object Attributes]**

If you select any user from these groups and double-click on them, all publicly accessible information for that user is displayed: First Name, Last Name, Display Name, Address details (if populated), Account settings (including Logon Name), Profile path, Organization, and Telephone.

Under the **Security** tab, you can inspect their assigned permissions and group memberships. While you cannot modify permissions or add users to groups without administrative rights, you can see where checkboxes are enabled, such as Read Personal Information or Read General Information. The **Member Of** tab shows which security groups they belong to (e.g., Domain Users, Internet Access). Under **Sessions**, you can inspect or terminate disconnected sessions, and Remote Control settings are visible. The **Object** tab displays the object class and creation timestamps.

Inspecting a server object shows its DNS name, Domain Controller type, operating system (**Windows Server 2019 Standard**), domain computer membership, delegation settings, security access controls, and creation metadata.

### **[Section 6: Targeting High-Value Accounts for Lateral Movement]**

This information is standard, but the primary goal is determining who your next target user will be. As we observed earlier in Task Manager, **`T1_Henry_Miller`** was actively logged into this machine. As noted, that is an administrative account. Inspecting the **Tier 1** OU confirms that `T1_Henry_Miller` is an admin account.

If you can compromise his credentials, you can authenticate through him and elevate yourself to a **Tier 1 admin**. From there, your next objective would be escalating to a **Tier 0 admin**, which represents the highest domain authority. Checking Henry Miller's group memberships confirms he belongs to **Domain Users** and **Tier 1 Admins**—a high-value target group that provides a direct path for privilege escalation.
