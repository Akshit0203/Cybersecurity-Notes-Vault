## BloodHound History

> *"Defenders think in lists, Attackers think in graphs." — Unknown*

For a long time, red teamers (and attackers) had the upper hand — so much so that Microsoft integrated their own version of BloodHound into Advanced Threat Protection. BloodHound lets attackers (and now defenders) visualise the AD environment as a **graph of interconnected nodes**, where each connection is a possible path to a goal. Defenders traditionally used **lists** (e.g. a list of Domain Admins, a list of hosts).

Graph-based thinking enables a **two-stage attack**:
1. Phishing for initial entry to enumerate AD info. This initial payload is usually noisy and gets detected/contained — but the attackers have already exfiltrated the enumerated data.
2. Using that data **offline** to build an attack path (graph) showing the exact hops required. In a second phishing campaign, attackers can reach their goal in minutes — often faster than the blue team's first alert fires.

This is why many blue teams now use these tools too, to understand their security posture.

## SharpHound

SharpHound and BloodHound are **not** the same. SharpHound is BloodHound's **enumeration tool** — it collects the AD information that BloodHound then displays visually. So you first run SharpHound, then view the results in BloodHound.

Three SharpHound collectors:
- **SharpHound.ps1** — PowerShell script. (Latest releases have stopped shipping the PowerShell version.) Good with RATs since it can load directly into memory, evading on-disk AV scans.
- **SharpHound.exe** — Windows executable.
- **AzureHound.ps1** — PowerShell script for Azure instances; BloodHound can ingest Azure data to find attack paths related to Azure IAM.

> **Version note:** BloodHound and SharpHound versions must match. This network was created with **BloodHound v4.1.0** — use that version with the SharpHound results, or old results may not ingest.

Collector scripts are often flagged as malware. This is where a **non-domain-joined Windows machine you control** helps: use `runas` to inject AD credentials and point SharpHound at a DC; since you control the box you can disable AV or add exceptions (already done on THMJMP1). SharpHound binaries are in `C:\Tools\` on that host.

### Running SharpHound

```
Sharphound.exe --CollectionMethods <Methods> --Domain za.tryhackme.com --ExcludeDCs
```

Parameters:
- **CollectionMethods** — what data to collect. Common options: `Default` or `All`. Since SharpHound caches, after the first run you can use the `Session` collection method to retrieve only new sessions, speeding things up.
- **Domain** — the domain to enumerate (can target a trusted parent/other domain).
- **ExcludeDCs** — don't touch domain controllers, reducing the chance of raising an alert.

### Node information categories

- **Overview** — summary info such as number of active sessions and whether the account can reach high-value targets.
- **Node Properties** — AD account info such as display name and title.
- **Extra Properties** — more detailed AD info such as distinguished name and creation date.
- **Group Membership** — groups the account belongs to.
- **Local Admin Rights** — domain-joined hosts where the account has admin privileges.
- **Execution Rights** — special privileges such as the ability to RDP into a machine.
- **Outbound Control Rights** — AD objects whose attributes this account can modify.
- **Inbound Control Rights** — AD objects that can modify this account's attributes.

Press the number next to a query for more detail (e.g. **First Degree Group Membership** shows the account is a member of two groups).

## Exploiting a Discovered Path (example)

We could exploit a path like this:

1. Use our AD credentials to RDP into **THMJMP1**.
2. Look for a privilege escalation vector on the host to gain Administrative access.
3. With Administrative access, use credential harvesting tools such as **Mimikatz**.
4. Since the **T1 Admin** has an active session on **THMJMP1**, credential harvesting yields the **NTLM hash** of that account.

This is a straightforward example; real attack paths can be far more complex and require several steps. See the [BloodHound edges documentation](https://bloodhound.readthedocs.io/en/latest/data-analysis/edges.html) for the exploits associated with each edge.

## Session Data Only

The structure of AD rarely changes in large organisations (OUs, Groups, Users, permissions stay mostly stable). What changes constantly is **active sessions and LogOn events**. Since SharpHound captures a point-in-time snapshot, session data goes stale — users log off, new sessions appear. So run SharpHound at **regular intervals**.

> SharpHound caches the data in a `.bin` file in the directory where you ran it, along with the zip file.

Recommended approach: run SharpHound with the **`All`** collection method at the start of the assessment, then run it at least **twice a day with the `Session`** method (faster, since it doesn't re-enumerate the whole structure). Best times: ~**10:00** (users' first coffee) and ~**14:00** (back from lunch, before going home).

Clear stagnant session data in BloodHound via the **Database Info** tab → **Clear Session Information** before importing new SharpHound runs.

## Mitigations

AD enumeration is hard to defend against — many techniques mimic normal network traffic and behaviour. But you can detect potentially malicious behaviour:

- Powerful techniques like SharpHound generate a **lot of LogOn events** when enumerating session info, all tied to a single AD account. Write detection rules for this behaviour from a user account.
- Write **signature detection rules** for tools that must be installed for specific techniques (SharpHound binaries, AD-RSAT tooling).
- **Monitor Command Prompt and PowerShell usage** (unless used by employees) to detect enumeration attempts from unauthorised sources.

On the flip side, the **blue team can run these same techniques** to find and fix misconfigurations — so even if an attacker enumerates AD, there's nothing exploitable to find.
