# Pass the Hash

## Overview

- Instead of cracking passwords, we dump the **SAM database** and authenticate with **NTLM hashes** directly instead of the plaintext password.
- The attacker places the hash into the **LSASS** section of memory, then uses native APIs to authenticate.
- Most common target is Windows (file and printer sharing over SMB).

**Advantages**
- Less time consuming (no offline cracking).
- No account lockout.
- Possibly admin privileges.

**Requirements**
- NTLM authentication enabled.
- SMB enabled.
- Writable SMB (`ADMIN$`) share.
- Local admin privileges.

## Core Concept — Pass-the-Hash vs. Password Cracking

In Windows, whenever authentication takes place (accessing a service, connecting to a share), Microsoft uses a **challenge-response** mechanism — as in NTLM, the client never transmits its cleartext password across the wire; credentials are always sent in hashed form. The design flaw: if you obtain another user's password hash, you can pass that hash directly to authenticate **without** needing their cleartext password.

Normally, recovering the plaintext from a captured hash requires offline cracking, which may be impossible for long/complex passwords (20–30 chars, mixed case, symbols). Pass-the-Hash removes that barrier entirely — if you have the hash, you have a guaranteed way to authenticate under that account's security context.

When an attacker obtains a valid hash, they load it into **LSASS** memory, allowing the OS to authenticate them directly.

## Gathering Hashes & Operational Advantages

The most common targets are Windows systems — network file shares (e.g. `C$`, `D$` administrative shares) and network printers — but the primary offensive objective is an interactive command prompt, reverse shell, or bind shell.

Ways to extract hashes:
- Dump the local **SAM** database (with local administrator rights).
- Dump the **`ntds.dit`** database (with Domain Admin privileges).
- Capture hashes across the network via sniffing or poisoning.

**Key operational advantages**
- **Fast and efficient** — no need to crack hashes offline.
- **No account lockouts** — not guessing passwords, so lockout thresholds are never triggered.
- **Guaranteed access** — the valid hash is submitted once and accepted directly by the server.

## Technical Prerequisites: SMB, NTLM, and Admin Rights

Modern Pass-the-Hash generally requires an **administrative account**. After security updates around 2014, Windows restricts Pass-the-Hash from standard, non-administrative accounts.

1. **NTLM authentication** — the technique does not operate over Kerberos (it does not use Kerberos hashing); NTLM must be enabled on the target.
2. **SMB protocol enabled** — the attack relies on an SMB share request: the client initiates a request, the server issues a challenge, and the client returns the computed response.
3. **Local administrator privileges** — non-admin hashes are largely ineffective on modern patched systems.

Once authenticated through the SMB share, code or hashes can be injected into memory to establish an interactive shell.

## What is LSASS?

**Local Security Authority Subsystem Service (LSASS)** is the critical Windows process responsible for enforcing local security policy and handling authentication-related operations. Its executable is:

```
C:\Windows\System32\lsass.exe
```

LSASS runs under the high-privilege **`NT AUTHORITY\SYSTEM`** account, meaning an attacker with `SYSTEM` access can extract credentials from LSASS memory without restriction.

### What LSASS does
- **Authentication** — validates user logons.
- **Security policy enforcement** — enforces local security policies.
- **Access tokens** — helps create security contexts for logged-in users.
- **Password changes** — handles password-change operations.
- **Authentication secrets** — may hold sensitive credentials/authentication material in memory, depending on Windows version and configuration.

It verifies authentication creds, keeps the user logged in, and facilitates **Single Sign-On (SSO)** so users don't re-enter credentials repeatedly. LSASS stores valuable authentication data including:
- Encrypted passwords
- NT hashes
- LM hashes
- Kerberos tickets

### How LSASS fits into Windows login
1. **User enters credentials** — username and password.
2. **Windows authentication components** — LSASS and configured authentication packages.
3. **Authentication result** — successful authentication can lead to a Windows logon session and security token.

In a domain environment, authentication may involve a Domain Controller through Kerberos or NTLM. LSASS participates in the local authentication process; it does not independently replace the Domain Controller.

### Simulating Single Sign-On
Conceptually, the attacker's system simulates LSASS memory containing the compromised hash. Whether on Windows or using Linux toolsets, the attacker simulates SSO locally. Once the hash is injected into memory, native Windows APIs authenticate to the remote target, replicating the standard authentication process between two Windows workstations.

## Mitigations

True mitigation is difficult because the challenge-response behavior exists **by design** in the OS; redesigning the authentication architecture would take years and disrupt enterprise workflows.

- **Microsoft patch 2871997** (kernels 6.1 – 6.3) addresses some PtH attacks.
- **Windows Defender Credential Guard** (Win10 and Server 2016/19 only) — uses Virtualization-Based Security to isolate LSASS memory into a protected container that standard processes cannot access.
- **Patching non-admin vectors** — Microsoft has patched non-administrative PtH vectors, limiting exploitation to administrative accounts.
- Because challenge-response auth is a **fundamental part of network authentication, it cannot be patched entirely.** If an attacker achieves full `SYSTEM` access, distinguishing legitimate admin processes from attacker manipulation remains a fundamental challenge.
