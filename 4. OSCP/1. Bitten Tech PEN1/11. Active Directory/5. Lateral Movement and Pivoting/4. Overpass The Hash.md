# Overpass the Hash

## Overview

- A **combination of Pass-the-Hash and Pass-the-Ticket**.
- Allows the creation of Kerberos tickets from an **NTLM hash or AES keys**.
- Grants access to resource services that require **Kerberos** authentication.
- Useful when **NTLM auth is disabled** and only Kerberos is allowed.

## Concept — Why Overpass-the-Hash?

Some scenarios block raw hashes: NTLM authentication is disabled, only Kerberos is enabled, or certain programs refuse NTLM hashes. For example, **Sysinternals PsExec** will not accept raw hashes for remote execution — it requires a **Ticket Granting Ticket (TGT)** present in memory. Many programs strictly demand Kerberos tickets rather than password hashes.

You may hold an NTLM hash but be unable to authenticate or move laterally with it directly. The solution is to **convert the NTLM hash into a Kerberos ticket**:

- Tools are available in **Impacket** and **Mimikatz**.
- For an interactive login (e.g. to a network share) you can use `net use`, which performs an interactive login and generates Kerberos tickets.
- Or construct the ticket manually with the Impacket toolkit.

We generate a **TGT** for the target user directly from their hash, then **pass that ticket** (hence "Overpass-the-Hash") and move laterally through it. This technique applies specifically within Kerberos environments.

## Overpass-the-Hash (Pass-the-Key) — Explained Simply

Overpass-the-Hash uses a stolen password hash to obtain a Kerberos **TGT**, instead of knowing the user's plaintext password. Think of it as using a stolen key to get a legitimate entry pass.

### Step by step
1. **Steal a password hash** — obtain a user's NTLM hash from a compromised Windows machine.
2. **Use the hash to request a Kerberos TGT** — use the hash as cryptographic key material to authenticate through Kerberos, without the plaintext password.
3. **Obtain a TGT** — if authentication succeeds, the Domain Controller issues a TGT.
4. **Request service tickets** — use the TGT to request Kerberos service tickets for resources the compromised account can access.

The flow: **Stolen NTLM hash → Kerberos authentication → TGT obtained → request service tickets.**

### Overpass-the-Hash vs. Pass-the-Hash

| Feature | Pass-the-Hash (PtH) | Overpass-the-Hash |
|---|---|---|
| Credential used | NTLM hash | NTLM hash / compatible key material |
| Authentication | Typically NTLM | Kerberos |
| Main goal | Authenticate using the hash | Obtain a Kerberos TGT using the hash |
| TGT obtained? | Not inherently | Yes, if successful |

Memory trick:
- **Pass-the-Hash:** use the hash to authenticate.
- **Overpass-the-Hash:** use the hash to get a Kerberos ticket.

### How is it different from a Silver Ticket?

| Attack | What the attacker creates or obtains |
|---|---|
| Overpass-the-Hash | Obtains a TGT through Kerberos authentication |
| Silver Ticket | Forges a service ticket (TGS) using a service account's secret |
| Golden Ticket | Forges a TGT using the `krbtgt` account's secret |

The critical difference: Overpass-the-Hash normally involves **authenticating to the Domain Controller** to obtain a TGT, whereas a forged Silver Ticket can be presented directly to its target service without requesting that ticket from the DC.
