### **[Section 2: What is Pass-the-Hash & Hash-Based Authentication Mechanics]**

I have researched many of these vectors, and in this video, we will focus specifically on **Pass-the-Hash**. You may have heard of this technique or seen me mention it previously. Pass-the-Hash literally means passing a password hash to a target service that requires authentication. Normally, when logging in or authenticating, you supply a username and a cleartext password. In many penetration testing scenarios, however, you do not have the cleartext password; you only possess its processed representation—the cryptographic hash. In Windows environments, we previously covered NTLM and Kerberos. Kerberos is a modern network authentication protocol that takes precedence over NTLM. Where Kerberos is supported, NTLM is not used, and where Kerberos is not supported, the system falls back to NTLM. Under both protocols, authentication relies on exchanging hashes—systems never transmit cleartext passwords over the network to authenticate against a server.

---

### **[Section 3: Kerberos AS-REQ, Credential Dumping, & Why Pass the Hash?]**

Even during the initial Kerberos exchange—the **`AS-REQ`**—the client encrypts a timestamp using their NT hash and submits it to the Authentication Server. The server already knows the user's NT hash from the database, meaning it validates the authentication without ever knowing the plaintext password. Every authentication protocol and file-sharing mechanism operates through hashes. Furthermore, penetration testing and privilege escalation tools that accept plaintext passwords simply compute the corresponding hash before sending it across the wire. Because the underlying protocols rely on hashes, transmitting plaintext passwords is fundamentally unnecessary. Consider an engagement where you have obtained shell access and need to move laterally, establish persistence, or escalate privileges. You dump password hashes from the local **SAM database** (for local accounts) or from the **`ntds.dit`** file on a Domain Controller (for domain accounts). Both databases provide hashes rather than plaintext credentials.

---

### **[Section 4: Technical Advantages of Pass-the-Hash]**

Once you extract a password hash, offline cracking can consume an enormous amount of time. Rather than spending hours or days cracking hashes, Pass-the-Hash allows you to authenticate directly to the domain using only the harvested hash. Because authentication protocols natively accept hashes, attackers can use those hashes directly for authentication.

**Key Advantages of Pass-the-Hash**:

- **Time Efficient**: Eliminates the delay required for offline password cracking.
- **Wordlist Independent**: Offline cracking fails if a password is long or absent from a dictionary; with Pass-the-Hash, password complexity is completely irrelevant.
- **Prevents Account Lockouts**: Guessing passwords online risks triggering account lockout policies (e.g., locking an account after 2, 5, or 10 invalid attempts within a specified timeframe). Passing a valid hash avoids lockouts entirely because the authentication attempt is valid on the first try.
- **Direct Administrative Access**: If you acquire the hash of a high-value account belonging to the **Domain Admins** group, you immediately gain administrative control over the Domain Controller.

### **[Section 5: Understanding LSASS (Local Security Authority Subsystem Service)]**

To understand how Pass-the-Hash works under the hood, we must examine **LSASS (Local Security Authority Subsystem Service)**. LSASS enforces security policies across Windows systems, interacting directly with the operating system kernel to maintain policy compliance. When a user logs onto a Windows host, LSASS verifies the credentials and enforces session settings, idle timeouts, and logoff policies.

By design, whenever an account successfully logs into a Windows system, LSASS caches those credentials inside its active process memory for the entire duration of the logon session. Within this memory space, LSASS stores highly sensitive data, including encrypted passwords, user **NT hashes**, **LM hashes**, and **Kerberos tickets**. (These cached tickets can also be targeted through Pass-the-Ticket attacks). This caching behavior is the reason penetration testing tools—such as Metasploit's `hashdump` or `smart_hashdump`—can extract hashes and cleartext credentials directly from LSASS memory on Domain Controllers.

---

### **[Section 6: The Pass-the-Hash Workflow & Memory Injection]**

The operational workflow functions in three clear steps:

1. **Hash Acquisition**: The attacker obtains the target's password hash via memory dumping, local file access, backup copies, or hardcoded configurations.
2. **Memory Injection**: The attacker simulates an LSASS process environment on their attacking machine and injects the captured hash directly into process memory.
3. **Execution**: The attacker runs a remote access command. The attacking operating system automatically pulls the injected hash from local memory and transmits it to the victim server.

This process mirrors native Windows Single Sign-On behavior: when an authenticated user connects to an authorized SMB share, Windows does not prompt for a password. Instead, the operating system transparently retrieves the cached credentials from memory and mounts the remote share. Pass-the-Hash simply repurposes this native design.

### **[Section 7: Practical Demonstration — Tooling & Metasploit PsExec Setup]**

Moving to Kali Linux for the practical demonstration, we use Metasploit, though numerous other tools support this technique. You can use Microsoft Sysinternals PsExec, PowerShell Empire, the Passing-the-Hash Toolkit, Impacket (`wmiexec`, `smbexec`, `secretsdump`, `lookupsid`, `psexec`), or Evil-WinRM. Tools are secondary; understanding the underlying mechanics is what matters.

In Metasploit, we select the module **`exploit/windows/smb/psexec`**:

- We configure the payload and set **`RHOSTS`** to the Domain Controller IP address.
- We configure **`SMBUser`**. We have two domain users: Alice and Bob. Alice is a standard user, whereas **Bob** is a member of the **Domain Admins** group. Because administrative rights are required to execute remote services via PsExec, we set `SMBUser` to Bob.
- We now need to configure **`SMBPass`** with Bob's hash rather than a plaintext password.

### **[Section 8: Dumping the `ntds.dit` Database using `ntdsutil`]**

To demonstrate where domain hashes originate, we look at **`ntds.dit`** on the Domain Controller. While local accounts reside in the SAM database, `ntds.dit` stores all Active Directory objects, including domain user accounts, computer objects, network services, group memberships, and password hashes.

Because `ntds.dit` is constantly in use by Active Directory while Windows is running, the file is locked and cannot be copied directly. Furthermore, it is encrypted using the system boot key. To extract it, administrators and testers use Volume Shadow Copies (`vssadmin`) or the native Windows diagnostic utility **`ntdsutil`**:

1. Launch PowerShell and run `ntdsutil`.
2. In the interactive prompt, execute:
    
    ```
    activate instance ntds
    ifm
    create full C:\ntdsutil
    ```
    
3. Type `quit` once snapshot creation finishes.

Navigating to `C:\ntdsutil` reveals two extracted folders containing the `ntds.dit` database (approximately 24 MB) along with the `SYSTEM` and `SECURITY` registry hives. Extracting the boot key from the SYSTEM hive allows offline decryption of all domain hashes stored in `ntds.dit`.

### **[Section 9: Hash Formatting (`LM:NT`) & Executing the Pass-the-Hash Exploit]**

Back in Metasploit, configuring `SMBPass` requires understanding hash syntax. Windows password hashes consist of two segments: the legacy **LM hash** and the modern **NT hash**. Although modern Windows environments no longer use LM hashes, tools like PsExec expect the legacy format:

```
<LM_HASH>:<NT_HASH>
```

To authenticate as Bob, we copy his full LM and NT hash string into `SMBPass`. Executing the exploit successfully creates **Meterpreter Session 1** on the Domain Controller.

To demonstrate that the LM portion is completely ignored during authentication, we replace the 32 hexadecimal characters of the LM hash with 32 zeros:

```
00000000000000000000000000000000:<BOB_NT_HASH>
```

Re-running the exploit opens **Meterpreter Session 2** without issue. This confirms that only the NT hash is evaluated, while the LM block is included strictly to satisfy tool syntax.

### **[Section 10: Mitigations, Microsoft Patches, & Credential Guard]**

Defending against Pass-the-Hash is inherently difficult:

- **Cannot Be Fully Patched**: Microsoft has issued various updates (such as KB patches for Windows kernels 6.1 and 6.3), but Pass-the-Hash cannot be completely eliminated via patching because it relies on the core design of Windows challenge-response authentication. Preventing it entirely would require fundamentally redesigning network authentication protocols.
- **Restricting Administrative Logons**: Microsoft introduced separate Security Identifiers (SIDs) for local administrator accounts to prevent local admin hashes from authenticating across remote network shares, though this does not stop compromised Domain Admin hashes.
- **Windows Defender Credential Guard**: Introduced in Windows 10 and Windows Server 2016/2019, Credential Guard uses **Virtualization-Based Security (VBS)** to isolate LSASS process memory into a secure virtualized container separate from the main operating system.

Credential Guard makes it significantly harder for attackers to dump hashes from LSASS memory. However, it does **not** stop the Pass-the-Hash attack itself if the attacker obtains the hash through another method (such as an offline backup, DCSync, or `ntds.dit` extraction). Once an administrative hash is acquired, Pass-the-Hash remains a highly reliable technique for lateral movement.
