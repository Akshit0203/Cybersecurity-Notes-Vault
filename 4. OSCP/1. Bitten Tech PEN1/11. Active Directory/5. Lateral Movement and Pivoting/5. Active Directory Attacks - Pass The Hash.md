# Active Directory Attacks — Pass the Hash

## Overview

- Instead of cracking passwords, dump the **SAM database** and use hashes directly for authentication.
- The attacker places the hash into the **LSASS** section of memory.
- Most common target is Windows (file and printer sharing).

**Advantages**
- Less time consuming.
- No account lockout.
- Possibly admin privileges.

**LSASS (Local Security Authority Subsystem Service)**
- Responsible for enforcing the security policy on the system.
- Verifies authentication creds and keeps the user logged in.
- Stores a variety of credential materials in memory: encrypted passwords, NT hashes, LM hashes, Kerberos tickets.

**Mitigations**
- Microsoft patch 2871997 (kernels 6.1 – 6.3) for some PtH attacks.
- Windows Defender Credential Guard (Win10 and Server 2016/19 only).
- Fundamental part of network auth and cannot be fully patched.

## What is Pass-the-Hash & Hash-Based Authentication

Pass-the-Hash literally means passing a password hash to a target service that requires authentication. Normally you supply a username and cleartext password; in many pentest scenarios you only possess the cryptographic **hash**.

Both **NTLM** and **Kerberos** rely on exchanging hashes — systems never transmit cleartext passwords over the network. Even during the initial Kerberos exchange (the **`AS-REQ`**), the client encrypts a timestamp using their NT hash and submits it to the Authentication Server. The server already knows the user's NT hash, so it validates authentication without ever knowing the plaintext password.

Pentest and privilege-escalation tools that accept plaintext passwords simply compute the corresponding hash before sending it. Because the underlying protocols rely on hashes, transmitting plaintext passwords is fundamentally unnecessary.

When you have shell access and need to move laterally, you dump hashes from:
- the local **SAM database** (local accounts), or
- the **`ntds.dit`** file on a Domain Controller (domain accounts).

Both provide hashes rather than plaintext credentials.

### Key advantages
- **Time efficient** — no delay for offline cracking.
- **Wordlist independent** — password complexity is irrelevant; offline cracking fails on long or non-dictionary passwords.
- **Prevents account lockouts** — a valid hash authenticates on the first try, so no lockout policy is triggered.
- **Direct administrative access** — the hash of a **Domain Admins** member immediately grants admin control over the Domain Controller.

## How LSASS Enables Pass-the-Hash

LSASS enforces security policies across Windows, interacting directly with the kernel. When a user logs onto a host, LSASS verifies credentials and enforces session settings, idle timeouts, and logoff policies.

By design, whenever an account successfully logs in, LSASS **caches those credentials in its process memory** for the entire logon session — including encrypted passwords, **NT hashes**, **LM hashes**, and **Kerberos tickets** (the cached tickets can also be targeted via Pass-the-Ticket). This caching is why tools like Metasploit's `hashdump` / `smart_hashdump` can extract hashes and cleartext credentials directly from LSASS memory.

### The Pass-the-Hash workflow
1. **Hash acquisition** — obtain the hash via memory dumping, local file access, backup copies, or hardcoded configs.
2. **Memory injection** — simulate an LSASS process environment on the attacking machine and inject the captured hash into process memory.
3. **Execution** — run a remote access command; the attacking OS pulls the injected hash from local memory and transmits it to the victim server.

This mirrors native Windows SSO: when an authenticated user connects to an authorized SMB share, Windows retrieves cached credentials from memory and mounts the share without prompting. Pass-the-Hash repurposes this native design.

## Practical Demonstration — Metasploit PsExec

Tooling that supports this technique: Microsoft Sysinternals PsExec, PowerShell Empire, the Passing-the-Hash Toolkit, Impacket (`wmiexec`, `smbexec`, `secretsdump`, `lookupsid`, `psexec`), or Evil-WinRM. Tools are secondary; understanding the mechanics is what matters.

In Metasploit we select the module **`exploit/windows/smb/psexec`**:

- Configure the payload and set **`RHOSTS`** to the Domain Controller IP.
- Configure **`SMBUser`**. Two domain users exist: Alice (standard user) and **Bob** (member of **Domain Admins**). Admin rights are required to execute remote services via PsExec, so set `SMBUser` to Bob.
- Configure **`SMBPass`** with Bob's hash rather than a plaintext password.

### Dumping `ntds.dit` with `ntdsutil`

Domain hashes originate from **`ntds.dit`** on the Domain Controller. While local accounts reside in the SAM database, `ntds.dit` stores all AD objects — domain user accounts, computer objects, services, group memberships, and password hashes.

Because `ntds.dit` is constantly in use, it is locked and cannot be copied directly, and it is encrypted with the system boot key. Extract it with Volume Shadow Copies (`vssadmin`) or the native **`ntdsutil`**:

1. Launch PowerShell and run `ntdsutil`.
2. In the interactive prompt:
    ```
    activate instance ntds
    ifm
    create full C:\ntdsutil
    ```
3. Type `quit` once snapshot creation finishes.

`C:\ntdsutil` then contains two folders with the `ntds.dit` database (~24 MB) plus the `SYSTEM` and `SECURITY` registry hives. Extracting the boot key from the SYSTEM hive allows offline decryption of all domain hashes stored in `ntds.dit`.

### Hash format (`LM:NT`) & executing the exploit

Windows password hashes have two segments: the legacy **LM hash** and the modern **NT hash**. Although modern Windows no longer uses LM hashes, tools like PsExec expect the legacy format:

```
<LM_HASH>:<NT_HASH>
```

To authenticate as Bob, copy his full LM and NT hash string into `SMBPass`. Executing the exploit creates **Meterpreter Session 1** on the Domain Controller.

To demonstrate the LM portion is ignored, replace the 32 hex chars of the LM hash with 32 zeros:

```
00000000000000000000000000000000:<BOB_NT_HASH>
```

Re-running opens **Meterpreter Session 2** without issue, confirming only the NT hash is evaluated — the LM block is included strictly to satisfy tool syntax.

## Mitigations (Detail)

- **Cannot be fully patched** — Microsoft issued updates (e.g. KB patches for kernels 6.1 and 6.3), but PtH cannot be eliminated via patching because it relies on the core design of Windows challenge-response authentication.
- **Restricting administrative logons** — Microsoft introduced separate SIDs for local administrator accounts to prevent local admin hashes from authenticating across remote shares (this does not stop compromised Domain Admin hashes).
- **Windows Defender Credential Guard** — Win10 / Server 2016/2019; uses **Virtualization-Based Security (VBS)** to isolate LSASS memory into a secure virtualized container.

Credential Guard makes dumping hashes from LSASS much harder, but it does **not** stop the attack itself if the attacker obtains the hash another way (offline backup, DCSync, `ntds.dit` extraction). Once an administrative hash is acquired, PtH remains highly reliable for lateral movement.
