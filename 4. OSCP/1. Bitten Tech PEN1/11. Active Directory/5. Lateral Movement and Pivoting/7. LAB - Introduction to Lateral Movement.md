# LAB — Introduction to Lateral Movement

## What is Lateral Movement?

Lateral movement is the group of techniques attackers use to move around a network. Once you have access to the first machine, moving is essential for:
- Reaching our goals as attackers
- Bypassing network restrictions in place
- Establishing additional points of entry to the network
- Creating confusion and avoiding detection

While many cyber kill chains reference lateral movement as one step in a linear process, it is actually part of a **cycle**: use any available credentials to move laterally → gain access to new machines → elevate privileges and extract credentials → repeat with the newfound credentials.

![](attachments/Pasted%20image%2020261009144819.png)

We usually repeat this cycle several times before reaching the final goal. If our first foothold has little access to other resources, we move laterally to hosts with more privileges.

## A Quick Example

Suppose a red team engagement's final goal is an internal **code repository**, and first compromise came via a phishing campaign. Phishing is most effective against non-technical users, so first access is a **Marketing** workstation.

Marketing workstations are typically firewalled off from critical services — admin protocols, database ports, monitoring, code repositories.

To reach sensitive hosts we move and pivot. We elevate privileges on the Marketing workstation and extract local users' password hashes. If we find a local administrator, the same account may exist on other hosts. After recon we find a workstation `DEV-001-PC`, use the local admin's password hash to access it, and confirm it belongs to a developer. From there, the target code repository is reachable.

![](attachments/Pasted%20image%2020261009144831.png)

Lateral movement also helps **evade detection**: even if Marketing had direct access to the repository, connecting through the developer's PC is less suspicious to a blue team analyst reviewing login audit logs.

## The Attacker's Perspective

The simplest approach uses standard administrative protocols — **WinRM, RDP, VNC, SSH** — to connect to other machines, emulating regular user behavior as long as coherence is maintained. An IT user connecting to the web server via RDP is normal; care must be taken not to attempt suspicious connections (e.g. *why is the local admin connecting to DEV-001-PC from Marketing-PC?*).

No technique is infallible, but we aim to be as silent as possible.

## Administrators and UAC

Most lateral movement uses administrator credentials, but there is a critical distinction between two types of administrators:
- **Local** accounts in the local Administrators group
- **Domain** accounts in the local Administrators group

The difference is restrictions imposed by **User Account Control (UAC)**:

- **Local admins** (except the default `Administrator`) cannot remotely perform administrative tasks unless using an interactive RDP session. Windows denies admin tasks via RPC, SMB, or WinRM because such accounts log in with a **filtered medium-integrity token**. Any shell spawned runs at **Medium integrity** by default, and privileged actions trigger a UAC elevation prompt.
- The only local account that gets full privileges remotely is the **default `Administrator`**.
- **Domain accounts** with local admin rights are **not** subject to this — they log in with full administrative privileges and no UAC prompts.

This feature can be disabled, so sometimes there's no difference. But if a lateral movement technique fails, it may be due to using a non-default local administrator where UAC is enforced. [Microsoft reference](https://docs.microsoft.com/en-us/troubleshoot/windows-server/windows-security/user-account-control-and-remote-restriction).

## Spawning Processes Remotely

Four common methods of remote execution. All let an account with sufficient privileges make another Windows computer execute something, using different Windows mechanisms. **None automatically bypasses permissions or grants privilege escalation** — the account still needs the relevant rights, and remote execution does not automatically grant admin/SYSTEM.

> Scenario: you have compromised credentials on `THMJMP2` and want to execute a command on `TARGET`.

### 1. PsExec — execute through a temporary service

**Port:** TCP 445 (SMB). **Permissions:** usually local administrator on the target.

PsExec is a Sysinternals tool that runs commands on a remote Windows machine. Internally it:
1. Connects to the remote **`ADMIN$`** share over SMB and copies `PSEXESVC.exe` to the target.
2. Contacts the **Service Control Manager** to create and start a service named `PSEXESVC`.
3. Uses **named pipes** to relay stdin/stdout/stderr between your machine and the remote process.
4. Displays the remote command prompt or output locally.

```
psexec64.exe \\MACHINE_IP -u Administrator -p Mypass123 -i cmd.exe
```

| Part | Meaning |
|---|---|
| `psexec64.exe` | Runs the 64-bit PsExec tool |
| `\\MACHINE_IP` | Identifies the remote computer |
| `-u Administrator` | Specifies the account |
| `-p Mypass123` | Supplies the password |
| `-i` | Requests an interactive session |
| `cmd.exe` | Starts a Windows command prompt |

Useful when you have administrator credentials, SMB access, and want an interactive remote command prompt.

### 2. WinRM — execute through remote PowerShell

**Ports:** TCP 5985 (HTTP) or 5986 (HTTPS). **Permissions:** the account must be authorized for remote management — membership in **`Remote Management Users`** can provide access, depending on configuration.

WinRM (Windows Remote Management) lets you execute commands without PsExec copying and launching its own service. On Kali, the tool **`evil-winrm`** interacts with remote WinRM services, provides an interactive shell, and supports **Pass-the-Hash** with harvested NTLM hashes.

**Method A — `winrs.exe`:**
```
winrs.exe -u:Administrator -p:Mypass123 -r:TARGET cmd
```
Asks WinRM on `TARGET` to launch `cmd.exe` using the supplied credentials.

**Method B — PowerShell remoting.** First build a credential object:
```
$username = 'Administrator'
$password = 'Mypass123'

$securePassword = ConvertTo-SecureString $password -AsPlainText -Force

$credential = New-Object System.Management.Automation.PSCredential(
    $username, $securePassword
)
```
- `ConvertTo-SecureString` converts the password string into a `SecureString`.
- `PSCredential` combines username + password into an object PowerShell can use for authentication.
- `$credential` stores that object for subsequent commands.

Then open an interactive session, or run a single command:
```
Enter-PSSession -ComputerName TARGET -Credential $credential
```
```
Invoke-Command -ComputerName TARGET `
    -Credential $credential `
    -ScriptBlock { whoami }
```
`Enter-PSSession` gives an interactive remote shell; `Invoke-Command` executes commands without staying in a shell. `whoami` reports the identity the remote command runs under.

### 3. `sc.exe` — create a remote Windows service

**Ports:** TCP 135 then a dynamic RPC port (commonly 49152–65535); TCP 445 or 139 may be used for RPC over SMB named pipes. **Permissions:** usually local administrator on the target. Internally the Service Control Manager communicates over the **`svcctl`** named pipe.

Create/start a service that runs an arbitrary binary or command:
```
sc.exe \\TARGET create THMservice binPath= "net user munra Pass123 /add" start= auto
sc.exe \\TARGET start THMservice
```

| Argument | Meaning |
|---|---|
| `\\TARGET` | Remote computer |
| `create` | Registers a new service |
| `THMservice` | Service name |
| `binPath=` | Configured service executable command line (note required space after `=`) |
| `start= auto` | Configures automatic startup |

Inspect and clean up:
```
sc.exe \\TARGET query THMservice
sc.exe \\TARGET stop THMservice
sc.exe \\TARGET delete THMservice
```

**Important caveat:** a Windows service is expected to implement the service interface. Configuring a service to launch an ordinary command like `net user` is not the same as running an arbitrary command — the process may execute then fail to initialize as a service, so results can be unreliable and output is not returned to you.

### 4. `schtasks.exe` — execute using Task Scheduler

**Permissions:** appropriate remote Task Scheduler permissions and permission to run the task under the selected account. Running as `SYSTEM` requires sufficient admin privileges.

Register a scheduled task on the target and trigger it:
```
schtasks /s TARGET /RU "SYSTEM" /create /tn "THMtask1" /tr "<command/payload to execute>" /sc ONCE /sd 01/01/1970 /st 00:00
```

| Option | Meaning |
|---|---|
| `/s TARGET` | Remote computer |
| `/RU "SYSTEM"` | Account under which the task runs |
| `/create` | Create a task |
| `/tn "THMtask1"` | Task name |
| `/tr` | Program or command to run |
| `/sc ONCE` | One-time schedule |
| `/sd` | Start date |
| `/st` | Start time |

Trigger it, then remove it:
```
schtasks /s TARGET /run /TN "THMtask1"
```
```
schtasks /S TARGET /TN "THMtask1" /DELETE /F
```

> The date `01/01/1970` is just lab example text — old dates can be rejected and date interpretation depends on locale. A task can often be registered with a future trigger and then run manually.

**Why "blind" attack?** Unlike interactive PsExec/WinRM, a scheduled task generally does **not** return the program's stdout to your terminal. The task might run, fail, or lack permissions, and you may not know which from the `/run` response — verify via logs or authorized checks on the target.

## Comparison

| Feature | PsExec | WinRM | `sc.exe` | Scheduled tasks |
|---|---|---|---|---|
| Main mechanism | Temporary service | PowerShell remoting | Windows service management | Task Scheduler |
| Typical network path | SMB, TCP 445 | TCP 5985/5986 | RPC/SMB management paths (TCP 135 + dynamic RPC) | RPC / Task Scheduler interfaces |
| Execution timing | Usually immediate | Interactive or immediate | When service starts | At a configured trigger or on demand |
| Interactive shell | Yes, commonly | Yes | Not by itself | Not usually |
| Typical legitimate use | Remote administration | Remote management | Service administration | Automation and maintenance |

| Technique | Mechanism | Main advantage | Key limitation |
|---|---|---|---|
| PsExec | SMB + temporary service | Interactive remote execution | Requires SMB and administrative access |
| WinRM | PowerShell remoting | Convenient interactive or one-off commands | WinRM must be accessible and the account authorized |
| `sc.exe` | Service Control Manager over RPC | Remote service management | Service creation requires privileges; arbitrary commands may not behave like services |
| `schtasks.exe` | Task Scheduler | Triggered or deferred execution | Task output is not automatically relayed to your terminal |

**Remember:** These are remote execution/administration mechanisms, not privilege-escalation vulnerabilities. Microsoft built them for legitimate systems management; attackers repurpose these native **living-off-the-land** utilities to stage payloads, move laterally, and establish persistence. Ports listed are typical defaults — firewall rules and configuration can change them.
