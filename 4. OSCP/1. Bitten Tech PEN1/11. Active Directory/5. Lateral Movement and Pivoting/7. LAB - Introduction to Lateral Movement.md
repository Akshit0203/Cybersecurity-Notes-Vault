
## What is Lateral Movement?

Simply put, lateral movement is the group of techniques used by attackers to move around a network. Once an attacker has gained access to the first machine of a network, moving is essential for many reasons, including the following: - Reaching our goals as attackers - Bypassing network restrictions in place - Establishing additional points of entry to the network - Creating confusion and avoid detection.

While many cyber kill chains reference lateral movement as an additional step on a linear process, it is actually part of a cycle. During this cycle, we use any available credentials to perform lateral movement, giving us access to new machines where we elevate privileges and extract credentials if possible. With the newfound credentials, the cycle starts again.

![](attachments/Pasted%20image%2020261009144819.png)


Usually, we will repeat this cycle several times before reaching our final goal on the network. If our first foothold is a machine with very little access to other network resources, we might need to move laterally to other hosts that have more privileges on the network.

  

## A Quick Example

Suppose we are performing a red team engagement where our final goal is to reach an internal code repository, where we got our first compromise on the target network by using a phishing campaign. Usually, phishing campaigns are more effective against non-technical users, so our first access might be through a machine in the Marketing department.

Marketing workstations will typically be limited through firewall policies to access any critical services on the network, including administrative protocols, database ports, monitoring services or any other that aren't required for their day to day labour, including code repositories.

To reach sensitive hosts and services, we need to move to other hosts and pivot from there to our final goal. To this end, we could try elevating privileges on the Marketing workstation and extracting local users' password hashes. If we find a local administrator, the same account may be present on other hosts. After doing some recon, we find a workstation with the name DEV-001-PC. We use the local administrator's password hash to access DEV-001-PC and confirm it is owned by one of the developers in the company. From there, access to our target code repository is available.

![](attachments/Pasted%20image%2020261009144831.png)

Notice that while lateral movement might need to be used to circumvent firewall restrictions, it is also helpful in evading detection. In our example, even if the Marketing workstation had direct access to the code repository, it is probably desirable to connect through the developer's PC. This behaviour would be less suspicious from the standpoint of a blue team analyst checking login audit logs.

  

## The Attacker's Perspective

There are several ways in which an attacker can move laterally. The simplest way would be to use standard administrative protocols like WinRM, RDP, VNC or SSH to connect to other machines around the network. This approach can be used to emulate regular users' behaviours somewhat as long as some coherence is maintained when planning where to connect with what account. While a user from IT connecting to the web server via RDP might be usual and go under the radar, care must be taken not to attempt suspicious connections (e.g. why is the local admin user connecting to the DEV-001-PC from the Marketing-PC?).

Attackers nowadays also have other methods of moving laterally while making it somewhat more challenging for the blue team to detect what is happening effectively. While no technique should be considered infallible, we can at least attempt to be as silent as possible. In the following tasks, we will look at some of the most common lateral movement techniques available.

  

## Administrators and UAC

While performing most of the lateral movement techniques introduced throughout the room, we will mainly use administrator credentials. While one might expect that every single administrator account would serve the same purpose, a distinction has to be made between two types of administrators:

- Local accounts part of the local Administrators group
- Domain accounts part of the local Administrators group

The differences we are interested in are restrictions imposed by **User Account Control (UAC)** over local administrators (except for the default Administrator account). By default, local administrators won't be able to remotely connect to a machine and perform administrative tasks unless using an interactive session through RDP. Windows will deny any administrative task requested via RPC, SMB or WinRM since such administrators will be logged in with a filtered medium integrity token, preventing the account from doing privileged actions. The only local account that will get full privileges is the default Administrator account.

Domain accounts with local administration privileges won't be subject to the same treatment and will be logged in with full administrative privileges.

This security feature can be disabled if desired, and sometimes you will find no difference between local and domain accounts in the administrator's group. Still, it's essential to keep in mind that should some of the lateral movement techniques fail, it might be due to using a non-default local administrator where UAC is enforced. You can read more details about this security feature [here](https://docs.microsoft.com/en-us/troubleshoot/windows-server/windows-security/user-account-control-and-remote-restriction).

### **[Section 3: OpSec, Evading Blue Teams, and Living-off-the-Land Protocols]**

Bypassing firewall rules is not the only reason lateral movement is required. In corporate environments, defensive **Blue Teams** actively monitor systems and triage alerts. If a marketing workstation suddenly attempts to connect directly to an internal code repository or inspect development software and development policies, that anomalous activity immediately generates high-severity security alerts. If a developer performs that same action from their own development PC, it appears completely normal.

As penetration testers and red teamers, our objective is to avoid performing actions that appear abnormal to Blue Team defenders. Our goal is to minimize network noise as much as possible. While noise levels may seem less critical when simply learning basic concepts in introductory labs, it becomes essential when conducting real-world corporate red team engagements, where bypassing detection and evading inspection mechanisms is mandatory.

Beyond firewall filters, security teams deploy numerous detection mechanisms that can identify attacker presence. To avoid detection, we leverage standard, legitimate administrative protocols to move laterally—such as **WinRM**, **RDP**, **VNC**, and **SSH**. Because administrators routinely use these protocols to manage systems, traffic traversing them is far less likely to be flagged as anomalous.

For example, when an employee contacts IT support reporting that they cannot log in or are experiencing workstation errors, IT staff routinely initiate an RDP session to the user's desktop to troubleshoot. That traffic is treated as standard business operations rather than suspicious activity.

Our operational objective is to emulate regular user behavior as closely as possible without introducing suspicious anomalies. There must be contextual coherence: an IT administrator establishing an RDP connection to an internal web server appears completely normal, whereas a marketing workstation establishing an RDP connection to a development machine under a local administrator context is highly suspicious. Therefore, we must minimize noise and avoid detection. We will explore all of these lateral movement methods in this video, while pivoting techniques will be examined in the next lesson.

### **[Section 4: Administrators, Local vs. Domain Accounts, & UAC Behavior]**

A crucial note is provided regarding Administrators and **User Account Control (UAC)**. Understanding the distinction between **Domain Accounts** and **Local Accounts** is essential.

Our primary focus is typically on administrator accounts. Each Windows machine features a local **Administrators** group containing all accounts permitted to manage that specific computer. That local Administrators group can include both local user accounts and Active Directory domain user accounts. A critical security distinction exists between local accounts that are members of the local Administrators group versus domain accounts that are members of the local Administrators group.

When a **local user account** belongs to the local Administrators group, User Account Control (UAC) restrictions are actively enforced. For example, if a new local user is created and added to the local Administrators group, any shell spawned by that user runs at a **Medium integrity level** by default rather than a High integrity level. Whenever a privileged administrative action is executed, UAC displays a prompt requiring the user to confirm whether to elevate privileges, rather than automatically granting elevated rights by default.

Conversely, when a **domain user account** is added to a workstation's local Administrators group, **UAC restrictions and elevation prompts are not enforced**. Any domain account added to a local Administrators group operates as a full local administrator on that workstation and can execute privileged actions directly without interactive prompts, eliminating the need for GUI-based RDP sessions.

UAC elevation restrictions apply strictly to custom-created local accounts added to the local Administrators group. The default, built-in **`Administrator`** account present across Windows workstations and servers is exempt from UAC enforcement. UAC applies only to non-default local accounts that have been added to the local Administrators group.

Understanding this distinction is vital during security assessments. If a privileged action fails despite your account being in the local Administrators group, active UAC policies may be restricting the operation. If you authenticate using a domain account that holds local administrator rights, UAC does not interfere with execution. However, if you are operating under a non-default local administrator account, UAC is enforced and must be bypassed. This scenario frequently appears in CTF challenges and real-world penetration tests.

### **[Section 5: Lateral Movement via PsExec (Mechanics, Named Pipes, and SMB Port 445)]**

Now we proceed to our primary task: executing lateral movement.

A widely used utility for this purpose is **PsExec**, a legitimate tool originally developed by Microsoft Sysinternals. PsExec allows creating and executing processes on remote Windows systems.

To operate, PsExec communicates over **TCP port 445** (SMB) and strictly requires membership in the **Administrators** group on the target machine. To move laterally using PsExec, you must execute it under administrative privileges. It has served as a standard remote management tool for years and can be downloaded directly from Microsoft's Sysinternals suite.

**How PsExec Functions Internally**:

1. It connects to the target machine's administrative share (**`ADMIN$`**) over SMB (port 445).
2. It uploads a service binary to the remote file system.
3. It creates and starts a Windows service to execute that uploaded binary.
4. To handle remote command interaction, it establishes **named pipes** to transmit standard input (`stdin`) and standard output (`stdout`) between the attacker and the remote service.
5. This communication flow occurs seamlessly in the background to present an interactive command session.

**PsExec Command Syntax**:

```
psexec \\<TARGET_IP> -u <USERNAME> -p <PASSWORD> cmd.exe
```

Executing this command connects to the target IP, authenticates using the supplied username and password, and spawns a remote `cmd.exe` process.

### **[Section 6: WinRM, Evil-WinRM, & Remote Management Utilities]**

Beyond PsExec, several other methods exist to move laterally.

Another common protocol is **WinRM (Windows Remote Management)**. WinRM operates on dedicated ports: **TCP port 5985** for unencrypted HTTP traffic and **TCP port 5986** for HTTPS encrypted traffic. To authenticate and execute commands over WinRM, your user account must be a member of the **Remote Management Users** group on the target system; otherwise, the connection is refused.

On Linux attacking systems like Kali, you can utilize the tool **`evil-winrm`** to interact with remote WinRM services. `evil-winrm` provides an interactive remote shell and also supports **Pass-the-Hash** authentication, allowing you to connect using harvested NTLM hashes without needing cleartext passwords.

Additionally, remote execution can be performed via PowerShell using credentials passed into `PSCredential` objects, which will be explored in later modules.

---

### **[Section 7: Service Control Manager (`sc.exe`) & Remote Service Creation]**

Another native administrative utility is the **Service Control Manager (`sc.exe`)**. Using the `sc` command, you can create, modify, and start custom Windows services on remote computers, provided you have administrative privileges on the target.

If your account belongs to the Administrators group on the remote host, you can specify the target machine's IP address, define a service name, configure the binary path (`binPath`), and start the service remotely. Internally, the Service Control Manager communicates over the **`svcctl`** named pipe.

Using `sc.exe`, an attacker can create a service that executes an arbitrary binary or runs a shell command—such as executing a command to add a new administrative user to the target operating system—and configure it to start automatically or launch it on demand. The command line accepts full execution arguments and custom payloads.

---

### **[Section 8: Scheduled Tasks (`schtasks.exe`), Native Tool Abuse, & Wrap-Up]**

Similarly, remote execution can be accomplished using **Scheduled Tasks (`schtasks`)**. Using `schtasks`, you can schedule commands, scripts, or custom payloads to execute at a specific date and time on a remote system.

Microsoft developed all of these administrative utilities for legitimate systems management and maintenance. Attackers repurpose these native, living-off-the-land utilities offensively to stage payloads, execute lateral movement, and establish persistence. This capability does not stem from a software bug or flaw, but from the intentional design of the operating system architecture, which attackers can exploit during an engagement.

# PsExec — Explained Simply

PsExec is a Windows administration tool that lets you execute commands on another Windows computer remotely. It is part of Microsoft's Sysinternals suite.

Imagine you have your Kali VM or Windows computer and want to run a command on a remote Windows machine without physically using that machine.

PsExec can help you do that, provided you have the necessary permissions and network access.

## 1. How PsExec works

Your computer (attacker/admin)

Runs PsExec with authorized credentials

SMB connection — TCP port 445

Authenticates to the remote Windows machine

Remote Windows computer

Creates and starts a temporary service to execute commands

Command output returned

You see the result on your computer

### Step by step

1. Connect: PsExec connects to the remote machine using SMB, usually over TCP port 445.
    
2. Authenticate: It uses the supplied Windows credentials. The account needs sufficient permissions on the remote machine.
    
3. Create a service: PsExec copies its service component to the remote system and uses the Windows Service Control Manager to start it.
    
4. Execute commands: The service runs the requested process on the remote computer.
    
5. Return output: PsExec relays the command output to your local terminal.

These are four common methods of remote execution in Windows and Active Directory environments. They all let an administrator—or an attacker with sufficient privileges—make another Windows computer execute something remotely, but they use different Windows mechanisms.

# 1. Remote Process Creation Using WinRM

WinRM (Windows Remote Management) lets you manage a remote Windows computer and execute commands through a remote PowerShell session.

Think of it as remotely opening a PowerShell terminal on another computer.

Your computer

PowerShell / WinRM client

WinRM connection

Usually TCP 5985 (HTTP) or 5986 (HTTPS)

Remote Windows computer

PowerShell session executes commands

Example, from PowerShell in an authorized lab:

```
Enter-PSSession -ComputerName PC01 -Credential (Get-Credential)
```

This prompts for credentials and attempts to open an interactive remote session.

How it works:

1. Connect to the target's WinRM service.
    
2. Authenticate with an account permitted to use remote management.
    
3. Establish a PowerShell remoting session.
    
4. Execute commands on the remote computer.
    

Remember: WinRM = remote PowerShell management.

# 2. Remotely Creating Services Using `sc.exe`

Windows services are background programs that can run without a user being logged in.

The Windows Service Control utility, `sc.exe`, can manage services on local or remote computers. With sufficient permissions, it can create and start a service remotely.

Administrator computer

Runs `sc.exe`

Service Control Manager (SCM)

Receives remote service-management requests

Remote Windows service

Service starts if configuration and permissions allow

Example of querying a remote service:

```
sc.exe \\PC01 query Spooler
```

This queries the Print Spooler service on `PC01`; it does not create or start a new service.

How it works:

1. Connect to the remote Service Control Manager.
    
2. Authenticate and check permissions.
    
3. Create, configure, query, or start a service, depending on the requested operation.
    
4. Windows runs the service according to its configuration.
    

Remember: `sc.exe` = remote service management.

# 3. Creating Scheduled Tasks Remotely

Windows Task Scheduler runs programs or scripts at a specified time, on a schedule, at startup, or when a configured event occurs.

An administrator can create a task on another Windows computer using `schtasks.exe`.

Administrator computer

Uses `schtasks.exe`

Remote Task Scheduler

Stores the task and its trigger

Task executes

Runs when triggered, under its configured security context

Example of listing scheduled tasks remotely:

```
schtasks /query /s PC01
```

This queries scheduled tasks on `PC01`. Creating or running a task requires the appropriate permissions and configuration.

How it works:

1. Connect to the remote Task Scheduler.
    
2. Authenticate and submit a task definition.
    
3. Configure the program, execution account, and trigger.
    
4. The task runs when its trigger fires or when manually started.
    

Remember: Scheduled task = execute later or repeatedly.

# 4. Compare all four methods

Ports below are typical defaults; firewall rules and configuration can change them.

|Feature|PsExec|WinRM|`sc.exe`|Scheduled tasks|
|---|---|---|---|---|
|Main mechanism|Temporary service|PowerShell remoting|Windows service management|Task Scheduler|
|Typical network path|SMB, TCP 445|TCP 5985/5986|RPC/SMB-related management paths|RPC/Task Scheduler interfaces|
|Execution timing|Usually immediate|Interactive or immediate|When service starts|At a configured trigger or on demand|
|Interactive shell|Yes, commonly|Yes|Not by itself|Not usually|
|Typical legitimate use|Remote administration|Remote management|Service administration|Automation and maintenance|

## 5. How to remember them for your AD labs

PsExec — Service-assisted execution

Start a process remotely through PsExec's service mechanism.

WinRM — Remote PowerShell

Open a remote management session and execute commands.

`sc.exe` — Service control

Create, configure, query, or start Windows services remotely.

Scheduled tasks — Triggered execution

Configure a program to run at a particular time or event.

The security concept connecting all four: these are remote execution or administration mechanisms, not privilege-escalation vulnerabilities by themselves. An account needs the relevant permissions, and remote execution does not automatically grant administrator or SYSTEM privileges. Attackers may abuse these mechanisms for lateral movement after compromising suitable credentials.




# Spawning Processes Remotely

This task teaches you how a user with valid credentials can execute commands on another Windows machine remotely. Since you're studying Active Directory and Windows security, the key is to understand what each technique does, which Windows component it uses, which ports it needs, and what permissions are required.

Imagine you have compromised credentials for a Windows computer called `THMJMP2` and want to execute a command on another machine called `TARGET`.

All four methods aim for remote execution, but they use different mechanisms.

## 1. Understand the big picture

Your machine — THMJMP2

You have valid credentials

PsExec

SMB + temporary service

WinRM

Remote PowerShell

sc.exe

Windows service control

schtasks

Task Scheduler

Remote Windows machine — TARGET

The requested process runs if permissions and configuration allow

## 2. PsExec — execute through a temporary service

Port: TCP 445 (SMB) Permissions: Usually local administrator privileges on the target.

PsExec is a Sysinternals tool that lets you run commands on a remote Windows machine.

### How it works

1. Connects to the remote `ADMIN$` share and copies `PSEXESVC.exe` to the target.
    
2. Contacts the Service Control Manager to create and start a service named `PSEXESVC`.
    
3. Uses named pipes to relay input, output, and errors between your machine and the remote process.
    
4. Displays the remote command prompt or command output locally.
    

The command from your notes:

```
psexec64.exe \\MACHINE_IP -u Administrator -p Mypass123 -i cmd.exe
```

|Part|Meaning|
|---|---|
|`psexec64.exe`|Runs the 64-bit PsExec tool|
|`\\MACHINE_IP`|Identifies the remote computer|
|`-u Administrator`|Specifies the account|
|`-p Mypass123`|Supplies the password|
|`-i`|Requests an interactive session|
|`cmd.exe`|Starts a Windows command prompt|

Why use it? It is useful when you have administrator credentials, SMB access, and want to interact with a remote command prompt.

## 3. WinRM — execute through remote PowerShell

Ports: TCP 5985 (HTTP) or TCP 5986 (HTTPS) Permissions: The account must be authorized for remote management; membership in `Remote Management Users` can provide access, depending on configuration.

WinRM is a Windows remote management protocol. It lets you execute commands without needing PsExec to copy and launch its own service.

### Method A: `winrs.exe`

```
winrs.exe -u:Administrator -p:Mypass123 -r:TARGET cmd
```

This asks WinRM on `TARGET` to launch `cmd.exe` using the supplied credentials.

### Method B: PowerShell remoting

First, create a credential object:

```
$username = 'Administrator'
$password = 'Mypass123'

$securePassword = ConvertTo-SecureString $password -AsPlainText -Force

$credential = New-Object System.Management.Automation.PSCredential(
    $username, $securePassword
)
```

What happens here?

- `ConvertTo-SecureString` converts the password string into a `SecureString`.
    
- `PSCredential` combines the username and password into an object PowerShell can use for authentication.
    
- `$credential` stores that object for subsequent commands.
    

Then open an interactive session:

```
Enter-PSSession -ComputerName TARGET -Credential $credential
```

Or execute a single command remotely:

```
Invoke-Command -ComputerName TARGET `
    -Credential $credential `
    -ScriptBlock { whoami }
```

The `whoami` command reports the identity under which the remote command executes.

The difference: `Enter-PSSession` gives you an interactive remote shell, while `Invoke-Command` is useful for executing commands without staying in that shell.

## 4. `sc.exe` — create a remote Windows service

Ports:

- TCP 135, followed by a dynamic RPC port (commonly 49152–65535).
    
- TCP 445 or 139 may be used for RPC over SMB named pipes.
    

Permissions: Usually local administrator privileges on the target.

Windows services are background programs managed by the Service Control Manager (SCM).

### How the connection works

1. `sc.exe`

Requests remote service management

2. RPC Endpoint Mapper — TCP 135

Finds the appropriate RPC endpoint

3. Service Control Manager

Receives the service operation

If the dynamic RPC connection fails, the client may try an SMB named-pipe transport if available.

Your notes use:

```
sc.exe \\TARGET create THMservice binPath= "net user munra Pass123 /add" start= auto
sc.exe \\TARGET start THMservice
```

Here is what the arguments mean:

- `\\TARGET` — remote computer.
    
- `create` — registers a new service.
    
- `THMservice` — name assigned to that service.
    
- `binPath=` — specifies the configured service executable command line.
    
- `start= auto` — configures automatic startup.
    

The example attempts to create a local user called `munra` when the service is started.

Important technical detail: A Windows service is expected to implement the Windows service interface. Configuring a service to launch an ordinary command such as `net user` is not the same as running an arbitrary command normally. The process may execute and then fail to initialize as a service, so the result can be unreliable and the command's output is not automatically returned to you.

To inspect and clean up the lab-created service:

```
sc.exe \\TARGET query THMservice
sc.exe \\TARGET stop THMservice
sc.exe \\TARGET delete THMservice
```

Why learn this? It demonstrates how remote service management can be abused to attempt code execution, and why defenders monitor remote service creation.

## 5. `schtasks.exe` — execute using Task Scheduler

Permissions: Appropriate remote Task Scheduler permissions and permission to run the task under the selected account. Running a task as `SYSTEM` requires sufficient administrative privileges.

Instead of starting a process directly, this technique registers a scheduled task on the target and triggers it.

### The workflow

1. Register a task on the remote computer.
    
2. Specify the program or command that the task should execute.
    
3. Choose the security context, such as `SYSTEM`, if authorized.
    
4. Start the task remotely and inspect the target to verify what happened.
    
5. Delete the task after the lab, if it is no longer needed.
    

Your notes contain this command:

```
schtasks /s TARGET /RU "SYSTEM" /create /tn "THMtask1" /tr "<command/payload to execute>" /sc ONCE /sd 01/01/1970 /st 00:00
```

This registers a task with the name `THMtask1`. The options mean:

|Option|Meaning|
|---|---|
|`/s TARGET`|Remote computer|
|`/RU "SYSTEM"`|Account under which the task runs|
|`/create`|Create a task|
|`/tn "THMtask1"`|Task name|
|`/tr`|Program or command to run|
|`/sc ONCE`|One-time schedule|
|`/sd`|Start date|
|`/st`|Start time|

The next command triggers it:

```
schtasks /s TARGET /run /TN "THMtask1"
```

And this removes it:

```
schtasks /S TARGET /TN "THMtask1" /DELETE /F
```

The date `01/01/1970` is an example from the lab material, not a universally valid scheduling date. Old dates can be rejected, and date interpretation depends on the system's locale and Task Scheduler behavior. A task can often be registered with a suitable future trigger and then run manually.

### Why is it called a blind attack?

Unlike an interactive PsExec or WinRM session, a scheduled task generally does not return the program's standard output to your terminal.

The task might run successfully, fail, or lack the permissions it needs, and you may not know which outcome occurred just from the `/run` response.

You need to verify the result using appropriate logs or authorized checks on the target.

## 6. Final comparison for your notes

|Technique|Mechanism|Main advantage|Key limitation|
|---|---|---|---|
|PsExec|SMB + temporary service|Interactive remote execution|Requires SMB and administrative access|
|WinRM|PowerShell remoting|Convenient interactive or one-off commands|WinRM must be accessible and the account authorized|
|`sc.exe`|Service Control Manager over RPC|Remote service management|Service creation requires privileges; arbitrary commands may not behave like services|
|`schtasks.exe`|Task Scheduler|Triggered or deferred execution|Task output is not automatically relayed to your terminal|

### What you should remember for the TryHackMe task

- PsExec: Copy a service binary, start the service, and relay I/O.
    
- WinRM: Use remote PowerShell or `winrs.exe`.
    
- `sc.exe`: Manage a remote Windows service through SCM.
    
- `schtasks.exe`: Register and trigger a remote scheduled task.
    

All four techniques require suitable access. None automatically bypasses Windows permissions or grants privilege escalation just because you can reach the target.
