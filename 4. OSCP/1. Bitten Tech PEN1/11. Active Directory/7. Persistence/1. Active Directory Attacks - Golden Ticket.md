# Pass-the-Ticket: Golden Ticket

> [!abstract] Overview
> A **Golden Ticket** is a forged Kerberos **Ticket Granting Ticket (TGT)** that lets an attacker impersonate any user in an Active Directory domain. It is a **Pass-the-Ticket** attack and a **Domain Dominance / persistence** technique — you must already hold initial administrative access (enough to dump the `krbtgt` hash) before you can forge one.

## Domain Dominance — Ways to Persist Administrative Access

- Dump `ntds.dit` (provides many domain password hashes)
- Creation of a (secondary/rogue) domain admin account
- Creation of a **Golden Ticket**
- Creation of a **Skeleton Key**
- Use of **DCSync / DCShadow** (abuse directory replication to copy objects between DCs — conceptually like a DNS zone transfer)

Golden Ticket falls under Domain Dominance because the goal is **persistence**: long-term access over an extended timeframe, which greatly elevates business risk.

## What Makes a Golden Ticket Special

- A special, modified TGT providing **maximum access for maximum time**.
- A standard TGT lives **10 hours** by default; a Golden Ticket bypasses expiration and can be valid up to **10 years**.
- Forged for the built-in **Administrator** account (**RID 500**) for unrestricted domain authority.

### Think of it as an entry pass

- **TGT** = a pass used to request entry tickets (service tickets) for different rooms.
- **`krbtgt` key** = the secret used to authenticate those passes.
- **Golden Ticket** = a counterfeit pass created using the real secret, so the domain trusts it.

## The Keys — Forging a Valid TGT (and a Valid PAC)

To create a valid TGT you must forge a valid **PAC (Privilege Attribute Certificate)** — a security certificate embedded inside the TGT that carries authorization data. When you present a TGT to request a service ticket, the DC inspects the PAC to determine your access rights, group memberships, and RID.

The PAC inside a TGT is protected with two keys:

| Key | Meaning |
|---|---|
| **Target LT Key** | Long-term key used by the target to validate the ticket |
| **KDC LT Key** | Long-term key used by the KDC to protect/validate Kerberos tickets |

For a TGT **both keys are the same: the NT hash of the `krbtgt` account**. The `krbtgt` account is the special AD account used by the domain's Kerberos Key Distribution Center (KDC). Extracting its hash requires prior administrative/SMB access to the DC.

> Using the Kerberos **AES keys** (instead of the legacy RC4/NT hash) lets you forge tickets in stealth mode, reducing anomalous event logs.

## Required Information

| Information | Meaning |
|---|---|
| `krbtgt` NT hash/key | Secret used to forge a valid TGT (the critical, hard-to-get piece) |
| Domain name (FQDN) | Identifies the AD domain |
| Admin account name | User to impersonate — can be **any** arbitrary name, even one that does not exist |
| Admin account SID | Security principal to impersonate |

> [!important]
> Domain name, username, and SID are generally **public/discoverable**. The only critical secret is the **`krbtgt` key**.

## Golden vs Silver Ticket

- **Golden Ticket** = forged **TGT** → governs access across the **entire domain** ("father of all tickets").
- **Silver Ticket** = forged **service ticket (TGS)** → scoped to a single service / SPN on one host.

## SID vs RID

In AD, the **SID** identifies the security object; the **RID** identifies that object within its domain SID.

| Feature | SID | RID |
|---|---|---|
| Full form | Security Identifier | Relative Identifier |
| Purpose | Uniquely identifies a security principal | Identifies a principal within a domain |
| Structure | Contains the domain SID **and** the RID | Final numeric part of a domain account's SID |
| Example | `S-1-5-21-111-222-333-500` | `500` |
| Used for | Users, groups, computers | Distinguishing objects within one domain |

**Example breakdown** of `S-1-5-21-111-222-333-1001`:

| Part | Meaning |
|---|---|
| `S-1-5-21` | SID authority and identifier prefix |
| `111-222-333` | Domain identifier |
| `1001` | RID — identifies this principal within the domain |

```
Domain SID + RID = Full SID
S-1-5-21-111-222-333  +  1001  =  S-1-5-21-111-222-333-1001
```

All objects in a domain share the same domain SID prefix (e.g. `S-1-5-21-...`); only the trailing RID differs. The OS uses RIDs as internal primary keys to distinguish principals within a domain.

### Important RIDs to remember

| RID | Common meaning |
|---|---|
| `500` | Built-in Administrator account |
| `501` | Guest account |
| `502` | KRBTGT account |
| `512` | Domain Admins group |
| `513` | Domain Users group |
| `514` | Domain Guests group |
| `515` | Domain Computers group |

> [!tip] Exam tip
> A SID ending in `-500` is the built-in Administrator. Custom user accounts and services start at RID `1000`+ and are **not** inherently privileged.

### Domain Admins vs built-in Administrator (RID 500)

- **Domain Admin privileges** can be given to *any* local/domain user by adding them to the **Domain Admins** group (RID 512).
- The built-in **Administrator** (RID 500) is a unique, default account with exclusive authority over the most sensitive operations (modifying GPOs, the AD Schema). It is the ultimate target — always aim for RID 500.

## Kerberos Flow Comparison

**Standard Kerberos authentication flow:**

1. Client → KDC: **`AS-REQ`** (encrypted timestamp to authenticate).
2. KDC → Client: **`AS-REP`** containing the TGT (PAC encrypted with the `krbtgt` NT hash).
3. Client → KDC: **`TGS-REQ`** presenting the TGT + target SPN.
4. KDC → Client: **`TGS-REP`** containing the service ticket.
5. Client presents the service ticket to the resource.

**Golden Ticket flow:** The initial authentication phase is eliminated. Because you forge the TGT locally with the `krbtgt` hash, **no `AS-REQ`/`AS-REP` occur** — you never touch the DC's Authentication Server. Communication begins directly at **`TGS-REQ`**. Because the PAC is encrypted with the genuine `krbtgt` hash, the KDC accepts the ticket and grants service tickets with admin rights.

## Properties / Characteristics

- **Created without DC interaction** (no `AS-REQ`/`AS-REP`). Kerberos is a **stateless** protocol (like HTTP): the KDC evaluates each ticket independently without verifying a prior `AS-REQ`, so forging the ticket raises no authentication-mismatch alert.
- Requires the **KDC LT Key** (`krbtgt` hash) — not easy to get.
- It's a TGT for the admin account (**RID 500**).
- Valid for **10 years** by default.
- The DC does **not** check whether the impersonated username actually exists.

### Step 1 — Get the Primary DNS Suffix (domain FQDN)

`target_ip` = domain controller IP.

```bash
python3 wmiexec.py domain/username:password@target_ip ipconfig /all
```

Output reveals the DC hostname and the Primary DNS Suffix (the FQDN), e.g. `TECHHACKER-DC` / `bittentech.local`.

![](attachments/Pasted%20image%2020261013143631.png)

### Step 2 — Get the Domain SID

`ipconfig` does not expose the SID, so use `lookupsid.py` (queries via LSA/SAMR):

```bash
python3 lookupsid.py bittentech.local/bob:Password123@192.168.164.131
```

Lists accounts/groups/SIDs (Administrator RID 500, Guest 501, krbtgt 502, custom users 1000+) and the complete **Domain SID**.

![](attachments/Pasted%20image%2020261013144001.png)

### Step 3 — Dump the `krbtgt` NT hash

```bash
python3 secretsdump.py bittentech.local/bob:Password123@192.168.164.131 -just-dc-user krbtgt
```

`-just-dc-user krbtgt` restricts extraction to the `krbtgt` account (avoids noise). Use only the **NT hash** (the last value, `krbtgt:`); ignore the legacy LM block. AES keys shown here can be used for stealthier forging.

![](attachments/Pasted%20image%2020261013144242.png)

### Step 4 — Forge the Golden Ticket

```bash
sudo python3 ticketer.py -domain bittentech.local -domain-sid S-1-5-21-15098949982252412482-3710614348 -nthash a7f6607449f2621e1adf437eaf6b2397 Administrator
```

- `-domain` — the domain FQDN
- `-domain-sid` — the harvested Domain SID
- `-nthash` — the `krbtgt` NT hash
- `Administrator` — target identity (RID 500 privileges)

Writes the ticket to disk as `Administrator.ccache`.

![](attachments/Pasted%20image%2020261013145345.png)

### Step 5 — Inject the ticket into memory (LSASS)

```bash
export KRB5CCNAME=Administrator.ccache
```

The ticket now resides in memory for subsequent Kerberos requests.

### Step 6 — Map the DC hostname (Kerberos needs names, not IPs)

```bash
gedit /etc/hosts
```

Add the DC IP and DC hostname.

![](attachments/Pasted%20image%2020261013150029.png)

### Step 7 — Interact with the domain without authentication

```bash
python3 wmiexec.py -k -no-pass -dc-ip <DC IP> <DC HOSTNAME> <command to run ex. whoami>
```

```bash
python3 wmiexec.py -k -no-pass -dc-ip 192.168.164.131 TECHHACKER-DC whoami
```

- `-k` — perform Kerberos authentication
- `-no-pass` — don't prompt for a password (use the ticket already in memory)

![](attachments/Pasted%20image%2020261013150056.png)

**Result:** We dumped the `krbtgt` NT hash through the user **Bob**, forged a Golden Ticket, passed it, and gained access to the **Administrator** account — completely owning the domain and the Domain Controller. `whoami` returns `domain\Administrator`.

![](attachments/Pasted%20image%2020261013150610.png)

It doesn't even check whether the impersonated username exists — you can forge a ticket for a **non-existent user** (e.g. `anonymous`) and the DC still accepts it, because the PAC is signed with the legitimate `krbtgt` hash.

![](attachments/Pasted%20image%2020261013150847.png)

## Mitigation

> [!warning] Reset the `krbtgt` password **twice**
> AD keeps the current **and** previous `krbtgt` password valid for ticket verification. Resetting once still lets previously forged Golden Tickets authenticate. Resetting a **second time** flushes the old password from history and permanently invalidates all forged Golden Tickets across the forest.

## Remember for Exams

- Golden Ticket = **forged TGT** + **`krbtgt` secret** + **domain/user identity info**.
- `krbtgt` NT hash is the critical ingredient; domain name/user/SID are public.
- Golden = forges TGT (whole domain); Silver = forges TGS (single service).
- Mitigation = reset `krbtgt` password **twice**.
