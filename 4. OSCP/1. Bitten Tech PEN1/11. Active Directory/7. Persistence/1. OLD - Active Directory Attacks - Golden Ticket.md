## Pass-the-Ticket: Golden Ticket — Easy Explanation

A Golden Ticket is a forged Kerberos Ticket Granting Ticket (TGT) that can let an attacker impersonate users in an Active Directory domain.

Think of a TGT as an entry pass that lets you request tickets for services.

### 1. What makes it special?

- High-level access: It can be forged to impersonate a privileged user, subject to domain configuration and other controls.
    
- Long validity: An attacker can specify ticket validity, although the KDC and services may enforce limits or other checks.
    
- Domain-wide impact: If forged successfully, it can potentially provide access to multiple domain resources.
    

### 2. What are the keys?

Your notes mention two keys:

- Target LT Key: The long-term key used by the target to validate a ticket.
    
- KDC LT Key: The long-term key used by the Key Distribution Center to protect or validate Kerberos tickets.
    

For a Golden Ticket, both correspond to the `krbtgt` account's key because a TGT is protected using that account's secret.

The `krbtgt` account is a special Active Directory account used by the domain's Kerberos Key Distribution Center.

### 3. What information is needed?

|Information|Meaning|
|---|---|
|`krbtgt` NT hash/key|Secret used to forge a valid TGT|
|Domain name|Identifies the AD domain|
|Admin account name|Identifies the user to impersonate|
|Admin account SID|Identifies the user's security principal|

Important: The domain name, username and SID are generally discoverable. The critical secret is the `krbtgt` key.

### 4. Simple analogy

Imagine a company has a ticket office:

- TGT: A pass used to request entry tickets for different rooms.
    
- `krbtgt` key: The secret used to authenticate those passes.
    
- Golden Ticket: A counterfeit pass created using the actual secret, making it appear legitimate.
    

If someone obtains the `krbtgt` secret, they may be able to forge TGTs that the domain trusts.

### Remember for exams

Golden Ticket = forged TGT + `krbtgt` secret + domain/user identity information.

It is different from a Silver Ticket: a Golden Ticket targets the TGT, while a Silver Ticket targets a specific service ticket (TGS).

In Active Directory, SID identifies the security object, while RID identifies that object within its domain SID.

## 1. SID vs RID

|Feature|SID|RID|
|---|---|---|
|Full form|Security Identifier|Relative Identifier|
|Purpose|Uniquely identifies a security principal|Identifies a principal within a domain|
|Structure|Contains the domain SID and RID|The final numeric part of a domain account's SID|
|Example|`S-1-5-21-111-222-333-500`|`500`|
|Used for|Identifying users, groups and computers|Distinguishing objects within a domain|

## 2. Example

```

```

## **Part 1: `Untitled_part1.wav`**

### **[Section 1: Introduction to Golden Tickets & Domain Dominance]**

Hello friends, in this video we will discuss the **Golden Ticket**. A Golden Ticket is a specific type of **Pass-the-Ticket** attack. We previously explored Pass-the-Hash and saw that Kerberos tickets can also be injected into LSASS process memory. Because tickets can be injected into memory, you can pass tickets across the network to authenticate, which is why Pass-the-Ticket is utilized. We will explore what a Golden Ticket is, and this represents an exceptionally important, highly powerful, and interesting attack in Active Directory.

First and foremost, a Golden Ticket is a **Domain Dominance** technique. This implies that you have already established initial administrative access within the domain, as you must possess access to specific password hashes before you can perform a Golden Ticket attack. While you already have access to Active Directory, your objective is to maintain **persistence**—ensuring long-term access over an extended timeframe, which substantially elevates organizational business risk. That is why the Golden Ticket falls under the classification of Domain Dominance.

---

### **[Section 2: Active Directory Persistence Mechanisms & Golden Ticket Overview]**

Before analyzing ticket mechanics, let us review alternative persistence techniques:

- **Dumping `ntds.dit`**: As demonstrated in the previous video, extracting the `ntds.dit` database provides access to numerous domain password hashes for persistence.
- **Creating a Secondary Domain Account**: Because you possess administrative credentials, you can create a secondary rogue domain administrator account without hindrance.
- **Creating a Golden Ticket**: The focal technique of this video.
- **Skeleton Key**: An advanced persistence mechanism that may be explored in specialized training.
- **DCSync & DCShadow**: Exploitation techniques that leverage directory replication mechanisms—conceptually similar to DNS zone transfers—to replicate directory objects between Domain Controllers.

Fundamentally, a Golden Ticket is simply a **Ticket Granting Ticket (TGT)**. If you recall the standard Kerberos authentication flow, this concept will be straightforward to follow. (If you do not recall Kerberos flow mechanics, reviewing that foundation is strongly recommended, as that knowledge is required here).

A Golden Ticket is a special, modified TGT. What makes it special is that it provides **maximum access for maximum time**. In a standard Kerberos environment, a legitimate TGT has a default lifetime of **10 hours**. In contrast, a Golden Ticket bypasses standard expiration limits to provide maximum access over an extended period.

---

### **[Section 3: Domain Admins vs. Built-in Administrator (RID 500)]**

Understanding what maximum access entails requires distinguishing between an account holding **Domain Admin privileges** versus the built-in **Administrator** account. These two concepts are entirely distinct and should not be confused. Administrative privileges can be assigned to any standard local or domain user simply by adding them to the **Domain Admins** group. When added to Domain Admins, a standard account assumes elevated administrative privileges.

However, Windows Domain Controllers feature a unique, default built-in account named **Administrator**. Gaining access to this built-in Administrator account represents your ultimate target. If you compromise this specific account, you obtain unrestricted authority across the entire domain. While accounts like Bob may belong to Domain Admins and perform administrative functions, the built-in Administrator account holds exclusive authority over sensitive operations such as modifying Group Policy Objects (GPOs) and modifying the Active Directory Schema. That built-in account represents maximum access and should always remain your primary objective.

---

### **[Section 4: Forging a Valid TGT & Understanding the PAC (Privilege Attribute Certificate)]**

A Golden Ticket functions by **forging a valid TGT**. We forge this ticket ourselves by spoofing specific directory attributes to assert that we are the domain administrator. A Golden Ticket is often referred to as the "father of all tickets" because it possesses broader authorization scope than any other ticket. In comparison, a **Silver Ticket** strictly forges service tickets (TGS) scoped to a single service or Service Principal Name (SPN), whereas a Golden Ticket forges a TGT that governs access across the entire domain.

To construct a valid TGT, you must forge a valid **PAC (Privilege Attribute Certificate)**. The PAC is a security certificate encapsulated directly inside the TGT that handles user authorization. When you present your TGT to request a service ticket, the Domain Controller inspects the PAC to determine your exact access rights, group memberships, and Relative Identifier (RID).

Within a TGT, the PAC is encrypted using two distinct keys:

1. The **Target Long-Term Key**
2. The **KDC Long-Term Key**

In the context of a TGT, both keys are identical: they are the **NT hash of the `krbtgt` account**. If you enumerate all user accounts in an Active Directory domain, you will find the default `krbtgt` service account. When a legitimate user requests a TGS, the KDC encrypts the PAC using the `krbtgt` account's NT hash. Therefore, generating a forged Golden Ticket strictly requires acquiring the **`krbtgt` NT hash**. Extracting this hash requires prior administrative and SMB access to the Domain Controller.

---

### **[Section 5: Required Parameters & Kerberos Flow Comparison]**

Beyond the `krbtgt` hash, the remaining required parameters are public and readily accessible across the domain:

- The **Domain Name** (FQDN)
- The **Domain Security Identifier (SID)**
- A **Target Username** (which can be any arbitrary username—even an account that does not exist in Active Directory)

**Standard Kerberos Authentication Flow**:

1. The client sends an **`AS-REQ`** to the Key Distribution Center (KDC) containing their encrypted timestamp to authenticate.
2. The KDC validates the credentials and returns an **`AS-REP`** containing the TGT, which encapsulates the PAC encrypted with the `krbtgt` NT hash.
3. The client submits a **`TGS-REQ`** presenting the TGT and the target Service Principal Name (SPN).
4. The KDC issues a **`TGS-REP`** containing the service ticket.
5. The client presents the service ticket to access the remote network resource.

**Golden Ticket Authentication Flow**: When utilizing a Golden Ticket, the initial authentication phase is completely eliminated. Because you forge the TGT locally using the `krbtgt` hash, **no `AS-REQ` or `AS-REP` requests occur**. You never interact with the Domain Controller's Authentication Server. Instead, your communication begins directly at the **`TGS-REQ`** phase, where you submit your forged TGT to request service tickets. Because the PAC is encrypted with the genuine `krbtgt` hash, the KDC accepts the ticket as legitimate and grants service tickets with administrative rights across the domain.

---

### **[Section 6: Kerberos Statelessness & SID vs. RID Deep Dive]**

Golden Tickets feature several distinct characteristics:

- **No Authentication Interaction with the DC**: Because Kerberos is a stateless protocol (conceptually similar to HTTP), the KDC evaluates tickets independently without verifying whether a prior `AS-REQ` occurred. Consequently, forging the ticket and altering the standard flow does not trigger authentication mismatch alerts.
- **Target RID 500**: A Golden Ticket is forged on behalf of the administrative account using Relative Identifier **RID 500**.

Understanding the distinction between an **SID** and an **RID** is essential:

- **Security Identifier (SID)**: A unique identifier generated per domain. All objects residing within that domain (users, computers, groups, services) share the exact same domain SID prefix.
- **Relative Identifier (RID)**: The variable numerical suffix appended to the end of the domain SID. The operating system relies on RIDs as internal primary keys to uniquely distinguish individual security principles and objects within the same domain.

---

### **[Section 7: PowerShell Enumeration of SIDs & 10-Year Golden Ticket Lifetime]**

Demonstrating this in PowerShell on Windows Server, executing:

```
Get-ADUser -Filter * | Select-Object Name, SID
```

enumerates domain users and displays their SIDs.

Every domain account—including `Administrator`, `Guest`, `krbtgt`, `Alice`, and `Bob`—shares the exact same hierarchical domain SID prefix (e.g., `S-1-5-21-...`). However, their trailing RIDs differ:

- **Administrator**: Always assigned **`500`**.
- **Guest**: Assigned **`501`**.
- **`krbtgt`**: Assigned **`502`**.
- **Custom User Accounts & Services**: RIDs begin sequentially at **`1000`** and above (e.g., Bob, Alice, SQLService).
- **Domain Admins Group**: Assigned default RID **`512`**.
- **Domain Computers**: Running `Get-ADComputer` displays computer accounts with unique RIDs (e.g., `1008`, `1009`).

Extracting the Domain SID is mandatory before creating a Golden Ticket. While standard Kerberos TGTs expire after **10 hours**, a forged Golden Ticket can be configured with an active validity lifetime of up to **10 years**, providing long-term persistence across the target network.

### **[Section 11: Forging the Golden Ticket with `[suspicious link removed]`]**

With all parameters gathered, we forge the Golden Ticket using Impacket's **`[suspicious link removed]`**. (If operating from Windows, Mimikatz can be utilized via `kerberos::golden` and `kerberos::ptt`).

We construct the command with our harvested values:

```
sudo python3 [suspicious link removed] -domain bittu_tech.local -domain-sid <DOMAIN_SID> -nthash <KRBTGT_NT_HASH> Administrator
```

- **`-domain`**: `bittu_tech.local`.
- **`-domain-sid`**: The harvested Domain SID string.
- **`-nthash`**: The extracted `krbtgt` NT hash.
- **Target Identity**: `Administrator` (assigning built-in RID 500 privileges).

Executing with `sudo` generates the forged Kerberos ticket and writes it to disk as a credential cache file: **`Administrator.ccache`**.

### **[Section 12: Injecting Ticket into Cache & Gaining Unauthenticated Remote Execution]**

To utilize the forged ticket for lateral movement, we inject it into our current session memory by exporting the Kerberos cache environment variable:

```
export KRB5CCNAME=Administrator.ccache
```

Once exported, the ticket resides in memory for all subsequent Kerberos authentication requests.

To interact with the Domain Controller without supplying passwords, we execute `[suspicious link removed]` with Kerberos authentication enabled:

- **`-k`**: Enforces Kerberos ticket authentication.
- **`-no-pass`**: Instructs the tool not to prompt for credentials, forcing it to pull the cached ticket from memory.

Because Kerberos authentication strictly requires resolving the target's hostname rather than an IP address, we edit `/etc/hosts` to map `[suspicious link removed]` to **`TechHackerDC`**.

Executing:

```
python3 [suspicious link removed] -k -no-pass TechHackerDC
```

establishes an authenticated administrative shell immediately. Running `whoami` returns **`bittu_tech.local\Administrator`**, and executing `ipconfig` outputs remote network configuration. We dumped the `krbtgt` hash using Bob, forged a Golden Ticket, and gained full Administrator access, achieving privilege escalation and persistence.

### **[Section 13: Forging Tickets for Non-Existent Users (`anonymous`)]**

A remarkable property of Golden Tickets is that they do not require targeting a valid, pre-existing user account. To demonstrate this, we forge a new ticket specifying a completely non-existent user: **`anonymous`**:

```
sudo python3 [suspicious link removed] -domain bittu_tech.local -domain-sid <DOMAIN_SID> -nthash <KRBTGT_NT_HASH> anonymous
```

This generates `anonymous.ccache`. We export the new ticket:

```
export KRB5CCNAME=anonymous.ccache
```

Re-executing `[suspicious link removed] -k -no-pass TechHackerDC` opens a remote administrative shell. Running `whoami` returns **`bittu_tech.local\anonymous`**.

Inspecting Active Directory Users and Computers and querying via `Get-ADUser` on the Domain Controller confirms that no account named `anonymous` exists anywhere in the directory. The Domain Controller accepts the session without question because the PAC is cryptographically signed using the legitimate `krbtgt` hash.

---

### **[Section 14: Mitigation & Remediation (Resetting the `krbtgt` Password Twice)]**

A forged Golden Ticket provides persistent access for up to 10 years, subject to one critical condition: **the `krbtgt` account password must remain unchanged**.

To remediate and invalidate forged Golden Tickets, the `krbtgt` password must be **reset twice**. Active Directory maintains password history for the `krbtgt` account, allowing tickets encrypted under both the current and immediately preceding password to remain valid. Resetting the password only once allows previously forged Golden Tickets to continue authenticating. Resetting the password a second time flushes the previous password from history, permanently invalidating all forged Golden Tickets across the forest. This completes our complete walkthrough of Golden Ticket attacks in Active Directory.
