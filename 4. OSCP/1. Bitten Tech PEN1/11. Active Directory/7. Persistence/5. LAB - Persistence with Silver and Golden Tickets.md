# LAB — Persistence Through Tickets (Golden & Silver)

> [!abstract] Overview
> Persistence through **Golden Tickets** (forged TGTs) and **Silver Tickets** (forged TGS) is far more resilient than persisting via harvested credentials — user passwords rotate frequently, but forged tickets with 10-year validity persist quietly in memory. This lab forges both with **Mimikatz** on `THMWRK1`.

## Kerberos Recap

![Kerberos authentication flow](attachments/Pasted%20image%2020261013190537.png)

1. User sends an **AS-REQ** to the KDC (DC) with a timestamp encrypted using the user's NTLM hash → request for a **TGT**.
2. The DC validates and returns the **TGT**, signed with the **KRBTGT** account's password hash (only stored on the DC).
3. User sends the TGT to request a **TGS** for a target resource.
4. If the TGT checks out, the DC returns the **TGS**, encrypted with the NTLM hash of the requested service.
5. User presents the TGS to the service, which verifies it with its own hash and grants access.

- **Golden Ticket** = forged **TGT** → bypasses steps 1–2.
- **Silver Ticket** = forged **TGS** → bypasses steps 1–4; talks directly to the service.

# Golden Ticket

## Theory (room notes)

Golden Tickets are **forged TGTs**: with the KRBTGT password hash we can sign a TGT for **any** user. Key points:

- We **don't need** the impersonated account's password hash — we bypass that step. The TGT only proves the KDC signed it; signed by the KRBTGT hash, it's declared valid **regardless of contents**.
- The KDC only validates the account in the TGT if it is **older than 20 minutes**. So a **disabled, deleted, or non-existent** account works, as long as the timestamp isn't older than 20 minutes.
- Ticket policies (e.g. 10-hour lifetime) are set **in the TGT itself**, so we can override them — e.g. make our TGT valid for **10 years** for persistence.
- By default the KRBTGT password **never changes** → persistent access forever until manually rotated.
- Blue team must rotate the KRBTGT password **twice** (current + previous are both kept valid). Rotating is painful — it breaks many services that still think they hold a valid TGT.
- Golden tickets even bypass **smart card** authentication (the card is verified by the DC before it creates the TGT).
- Can be generated on **any machine**, even one not domain-joined (e.g. your attack box), making detection harder.
- Besides the KRBTGT hash, you only need the **domain name**, **domain SID**, and **user ID** — all easy to get once you can recover the KRBTGT hash.

# Silver Ticket

## Theory (room notes)

Silver Tickets are **forged TGS tickets** — skip all KDC communication (steps 1–4) and interface directly with the target service. Key points:

- The TGS is signed by the **machine account** of the targeted host.
- **Scope**: limited to the targeted service on that specific host (vs Golden, which gets everything). With only the machine account's hash, you can impersonate users on **that host**.
- Since the TGS is forged, there's **no associated TGT and the DC was never contacted** — the only logs are on the targeted server, making it much harder for the blue team to detect.
- Permissions come from **SIDs**, so a non-existent user works as long as the ticket carries SIDs placing the user in the host's local administrators group.
- A machine account's password usually rotates every **30 days** (bad for persistence). But via the TGS you can access the host's registry and **disable that rotation**, keeping the machine account static for persistence.
- Machine accounts can be used as normal AD accounts — allowing admin access to the host **and** continued AD enumeration/exploitation.

> **Mimikatz uses `kerberos::golden` for BOTH ticket types.** The presence of a **`/service`** parameter (e.g. `/service:cifs`) plus `/target` and `/rc4` means a **Silver Ticket** (TGS). No service parameter = Golden Ticket. Mimikatz may even print "Golden ticket ... generated" for a Silver Ticket — that's a tool misnomer.

## Mimikatz Parameters Explained

| Parameter | Meaning |
|---|---|
| `/admin` | Username to impersonate — **does not have to be a valid user** (e.g. `anonymous`, `ReallyNotALegitAccount`) |
| `/domain` | FQDN of the target domain |
| `/id` | User RID. Default `500` = built-in Administrator |
| `/sid` | Domain SID |
| `/krbtgt` | **(Golden only)** NTLM hash of the KRBTGT account — the single most critical component |
| `/target` | **(Silver only)** Hostname/FQDN of the target server |
| `/rc4` | **(Silver only)** NTLM hash of the target's machine account (`HOST$`) |
| `/service` | **(Silver only)** Service for the TGS — `cifs` is a safe bet (grants file access); SQL etc. also possible |
| `/endin` | Ticket lifetime in minutes. Mimikatz defaults to **10 years**; AD default Kerberos policy is **10 hours = 600** |
| `/renewmax` | Max renewal lifetime. Mimikatz defaults to **10 years**; AD default is **7 days = 10080** |
| `/ptt` | Pass-the-ticket — inject the forged ticket directly into the current session (ready to use) |

Full example with explicit lifetimes:

```
mimikatz # kerberos::golden /admin:ReallyNotALegitAccount /domain:za.tryhackme.loc /id:500 /sid:<Domain SID> /krbtgt:<NTLM hash> /endin:600 /renewmax:10080 /ptt
```

Omitting `/endin` and `/renewmax` defaults to the maximum **10-year** duration.

## Blue Team: Golden vs Silver

| | Golden Ticket | Silver Ticket |
|---|---|---|
| Forges | TGT | TGS |
| Signed with | KRBTGT hash (forest-wide) | Target machine account hash |
| Scope | Entire domain | One service on one host |
| Detection | Easier (users don't forge TGTs; long lifetimes; `krbtgt` server in ticket) | Harder (DC never contacted; logs only on the target host) |
| Remediation | Reset `krbtgt` password **twice** → invalidates all | Reset **every machine account** password → much harder to operationalize |

Orgs prioritize remediating Golden Tickets first due to forest-wide impact.
