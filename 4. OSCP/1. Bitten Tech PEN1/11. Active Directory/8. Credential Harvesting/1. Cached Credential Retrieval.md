# Cached Credential Retrieval

> [!abstract] TL;DR
> In Windows, credentials (NTLM hashes, Kerberos tickets, and sometimes cleartext passwords) are cached in **LSASS memory** to enable Single Sign-On. The process runs as **SYSTEM**, so you need SYSTEM/admin privileges to read it. Tools like **Mimikatz** can extract these hashes and tickets — and can even inject custom TGT/TGS into LSASS. This is a **by-design** attack, not a bug.

---

## What Are Cached Credentials?

This is an attack that works **by design** — it is based on the architectural design of Kerberos and Windows security in Active Directory Domain Services, not on a misconfiguration or software bug.

When you log in, Windows caches your credentials in memory so you don't have to re-enter them for every network service or resource. When those credentials are cached in memory, they can be **retrieved in various forms** — which is what this technique exploits.

## LSASS — Local Security Authority Subsystem Service

**LSASS** is a system process that enforces security policies on any Windows workstation joined to an AD domain. Its responsibilities:

- **Login validation** — verifies whether a login is legitimate, then manages/verifies whether post-logon actions are authorized.
- **Permission management** — determines what level of access users, groups, and objects receive (also defined in Group Policy). It specifically enforces security-related Group Policy settings.
- **Security logging** — runs continuously in the background monitoring system activity. Suspicious events (e.g. repeated failed logon attempts) are written directly to the Windows Security event logs.
- **Kerberos Single Sign-On (SSO)** — when you authenticate once, LSASS caches your credentials in its process memory (in active RAM). Whenever you access a network service or local resource, LSASS supplies the cached credentials directly, so you are never re-prompted.

## Credential Formats Stored in LSASS Memory

A wide variety of authentication material can reside in LSASS memory:

- **NTLM password hashes**
- **Kerberos tickets** — TGTs and service tickets (TGS) used for ticket-based network authentication
- **Cleartext passwords** — present to support legacy protocols and Security Support Providers (SSPs) like **WDigest**, which store credentials in plaintext for backward compatibility

## The By-Design Attack Concept

Because caching fulfills the legitimate requirement of SSO, this is an **intentional architectural design**, not a vulnerability.

The security implication: if a **privileged/admin user logs into a workstation where you already have a foothold** (i.e., you have access under a separate account while a higher-privileged user is concurrently logged in), you can **extract their cached hashes from memory and compromise their account**.

## Privilege Requirement — `NT AUTHORITY\SYSTEM`

The LSASS process runs under elevated privileges. To extract credentials directly from LSASS memory you strictly require **`NT AUTHORITY\SYSTEM`** privileges.

> [!warning] Prerequisite
> You must have **already performed local privilege escalation** on the host — obtaining administrative rights or a SYSTEM context — before you can dump LSASS memory.

## Tooling & Lateral Movement

- **Mimikatz** is the most prominent tool for interacting with LSASS memory. It can dump cached passwords, NTLM hashes, and Kerberos tickets.
- Once harvested, you can:
  - **Pass-the-Hash** using extracted NTLM hashes
  - **Pass-the-Ticket** using stolen Kerberos tickets

**Methodology:** enumerate all active and disconnected logged-in users on the machine → dump their NTLM hashes → potentially recover plaintext passwords if backward-compatible providers (e.g. WDigest) are active.

> | Credential type | Purpose | Notes |
> |---|---|---|
> | NTLM hash | NTLM authentication | Usable for Pass-the-Hash |

> | Cleartext password (WDigest) | Legacy SSP backward compatibility | Only if WDigest/legacy provider is active |
