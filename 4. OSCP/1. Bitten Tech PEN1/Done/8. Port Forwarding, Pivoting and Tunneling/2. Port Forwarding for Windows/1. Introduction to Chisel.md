# Introduction to Chisel

> **Chisel** is a fast TCP/UDP tunnel, transported over HTTP, secured via SSH. It ships as a single executable containing both client and server. Written in Go (Golang), it is cross-platform and extremely useful for passing through firewalls when SSH is unavailable.

---

## Network Topology

![](attachments/Pasted%20image%2020260916111103.png)

| Role | Machine | Example IP(s) |
|---|---|---|
| **Attacker** (Chisel server) | Kali | `192.168.100.4` / `10.10.10.5` |
| **Pivot** (Chisel client) | Win1 / THM-JMP2 | `192.168.100.x` + `10.10.10.23` |
| **Target** | Internal host | `10.10.10.33` / `10.10.20.50` |

Kali cannot directly reach the internal target — we pivot through Win1.

---

## Requirements

- Chisel for Linux (attacker) — ELF binary
- Chisel for Windows (pivot) — `.exe`

> [!WARNING]
> Both client and server **must be the same version** of Chisel. Mismatched versions cause connection failures or instability.

## Reverse Port Forwarding (Single Port)

### Syntax

**On Attacker (Kali):**

```bash
chisel server -p <chisel_server_listen_port> --reverse
```

**On Pivot (Win1):**

```cmd
chisel.exe client <attacker_ip>:<chisel_server_listen_port> R:<local_port>:<target_ip>:<target_port>
```

### Parameter Breakdown

#### `server`

Tells Chisel: "I am the server." The server runs on your **attacker/Kali** machine.

#### `-p 8000`

> Chisel server listens for the Chisel client connection on TCP port 8000.

This is the **transport port** — NOT the target service port.

#### `--reverse`

Enables **reverse port forwarding** — allows the client to create a listener on the server side.

---

### Understanding `R:<local_port>:<target_ip>:<target_port>`

```
R : <port-on-server> : <destination> : <destination-port>
```

**Example:**

```
R:9000:10.10.20.50:80
```

> Create a listener on the Chisel server (Kali) at port 9000. When someone connects to it, forward that traffic through Win1 to `10.10.20.50:80`.

**Traffic flow:**

```
Kali:9000
   │
   │ Chisel tunnel
   ▼
 Win1
   │
   ▼
10.10.20.50:80
```

From Kali, access `http://127.0.0.1:9000` → traffic reaches `10.10.20.50:80`.

### Memory Trick

For `R:9000:10.10.20.50:80` read it as:

> **"On the server (Kali), open port 9000; through Win1, reach `10.10.20.50` port 80."**

For `-p 8000`:

> **"Where should the Chisel client connect to my Chisel server?"**

---

### The Three Ports — Don't Confuse Them

```
8000 = Chisel server connection port (transport)
9000 = Forwarded/listening port (on Kali)
80   = Actual target service
```

```
                    Chisel connection
Win1 ───────────────────────────────► Kali
                                      │
                                      │ :9000
                                      ▼
                                  10.10.20.50:80
```

### Concrete Example

**On Attacker:**

```bash
chisel server -p 8080 --reverse
```

**On Win1:**

```cmd
chisel.exe client 192.168.100.4:8080 R:80:10.10.10.33:80
```

Opening `localhost:80` on Kali displays the web server running on `10.10.10.33`.

## Chisel with SOCKS (Dynamic Port Forwarding)

Instead of forwarding one port at a time, SOCKS lets you proxy **any** destination through the tunnel.

### Requirements

- Chisel for Linux + Windows (same version)
- Proxychains on Kali
- `/etc/proxychains.conf` configured with: `socks5 127.0.0.1 <local_socks_port>`

### Setup

**1. Configure Proxychains** — edit `/etc/proxychains.conf`, add at the bottom:

```
socks5 127.0.0.1 9050
```

**2. On Attacker (Kali):**

```bash
chisel server -p 8000 --reverse
```

**3. On Pivot (Win1):**

```cmd
chisel.exe client <KALI_IP>:8000 R:9050:socks
```

### Breaking Down `R:9050:socks`

```
R:9050:socks
│  │   │
│  │   └── Chisel creates a SOCKS proxy
│  └────── port 9050 on Kali
└───────── reverse forwarding
```

Chisel creates a SOCKS proxy at `127.0.0.1:9050` on Kali.

### Traffic Flow

```
Kali
  │
  │ 127.0.0.1:9050
  ↓
Chisel
  ↓
Win1
  ↓
Internal network
  ↓
10.10.20.50
```

### Using Proxychains

```bash
proxychains curl http://10.10.20.50
```

```bash
proxychains nmap -sT -Pn -p 80 10.10.20.50
```

The traffic path becomes:

```
Nmap
 ↓
Proxychains
 ↓
SOCKS5 127.0.0.1:9050
 ↓
Chisel
 ↓
Win1
 ↓
Internal target
```

> [!TIP]
> Add `-q` (quiet) to `proxychains` or set `quiet_mode` in `proxychains.conf` to suppress verbose proxy logs.

### Why SOCKS is Useful

**Without SOCKS** — you need a separate forward for every service:

```
Kali:8080  → Win1 → 10.10.20.50:80
Kali:3306  → Win1 → 10.10.20.50:3306
Kali:445   → Win1 → 10.10.20.50:445
```

**With SOCKS** — one proxy handles everything:

```
Kali:9050
    ↓
   SOCKS
    ↓
   Win1
    ↓
Internal network
```

Applications specify the destination through the SOCKS protocol dynamically.

### Port Distinction Table

| Port | Purpose |
|---|---|
| `8000` | Chisel server connection port |
| `9050` | SOCKS proxy port on Kali |
| `80` | Example target service |
| `443` | Another possible target service |

### Complete Architecture Diagram

```
                    CHISEL TUNNEL
              =========================>

┌──────────────┐       ┌──────────────┐       ┌────────────────┐
│ Kali         │       │ Win1         │       │ Internal       │
│ Attacker     │       │ Pivot        │       │ Target         │
│              │       │              │       │                │
│ Proxychains  │       │ Chisel       │       │ 10.10.20.50    │
│      ↓       │       │   client     │       │                │
│ SOCKS :9050  │──────>│              │──────>│ :80             │
│              │       │              │       │ :443            │
└──────────────┘       └──────────────┘       └────────────────┘
       ↑
       │
   /etc/proxychains.conf
   socks5 127.0.0.1 9050
```

## Key Memory Tricks

> **Chisel** = builds the tunnel
> **SOCKS** = lets you choose where traffic goes through the tunnel
> **Proxychains** = makes applications use the SOCKS proxy

```
Application → Proxychains → SOCKS → Chisel → Pivot → Internal target
```

> **Port forwarding** = fixed path ("go here")
> **SOCKS** = dynamic destination ("connect me there")

## Socat vs Chisel (Quick Comparison)

| Feature | Chisel | Socat |
|---|---|---|
| Listening port opens on | **Attacker** machine (via reverse) | **Pivot** machine |
| SOCKS support | ✅ Built-in | ❌ Not supported |
| Cross-platform | ✅ Single binary | Requires DLLs on Windows |
| Firewall rules needed on pivot | Usually not | Yes (`netsh` rule) |
| SSH required | No | No |

**Socat syntax:**

```bash
socat TCP4-LISTEN:<PORT>,fork TCP4:<TARGET_IP>:<TARGET_PORT>
```

- `fork` — spawns a new process per connection (handles multiple connections)
- Opens a port on the **pivot host**, not on the attacker

**Socat firewall rule (if needed):**

```cmd
netsh advfirewall firewall add rule name="Open Port 3389" dir=in action=allow protocol=TCP localport=3389
```
