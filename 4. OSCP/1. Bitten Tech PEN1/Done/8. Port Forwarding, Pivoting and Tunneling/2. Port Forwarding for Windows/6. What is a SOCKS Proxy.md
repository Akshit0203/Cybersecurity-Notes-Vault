# What is a SOCKS Proxy?

> **A SOCKS proxy is a middleman that lets an application send its network connections through another machine.**

```
Your Kali ─────► SOCKS Proxy ─────► Target
                      ↑
                   middleman
```

In pentesting, this is essential when the target network is **not directly reachable** from Kali, but a compromised machine (pivot) can reach it.

---

## Normal Proxy vs SOCKS

### Without a Pivot

```
Kali ──────────X──────────► 10.10.20.50
                  blocked
```

### With a Pivot

```
Kali → Win1 → 10.10.20.50
```

Win1 can reach the target. You want Kali to say:

> "Win1, connect to `10.10.20.50:80` for me."

That's what SOCKS does.

---

## What Makes SOCKS Different From Other Proxies?

### HTTP Proxy

Designed around **HTTP requests** — understands `GET`, `Host:`, etc. Closely tied to web traffic.

```
Browser → HTTP Proxy → Web Server
```

### SOCKS Proxy

Works at a **lower level** — proxies TCP connections without needing to understand the application protocol.

```
Client → SOCKS → 10.10.20.50:80    (HTTP)
Client → SOCKS → 10.10.20.50:22    (SSH)
Client → SOCKS → 10.10.20.50:445   (SMB)
Client → SOCKS → 10.10.20.50:3306  (MySQL)
```

The SOCKS proxy only cares about:

> **"Where do you want me to establish a connection?"**

It doesn't inspect the application layer data. That's why it's called a **general-purpose proxy protocol**.

---

## Why SOCKS is Great for Pivoting

### Single Port Forward (Without SOCKS)

You create a **fixed path** for each service:

```
Kali:8080 → Win1 → 10.10.20.50:80
Kali:8081 → Win1 → 10.10.20.50:22
Kali:8082 → Win1 → 10.10.20.50:443
Kali:8083 → Win1 → 10.10.20.51:445
```

Tedious if you need many services across many hosts.

### SOCKS (Dynamic Forwarding)

**One proxy** handles everything:

```
                 SOCKS :9050
                      │
                      ↓
                    Win1
                      │
          ┌───────────┼───────────┐
          ↓           ↓           ↓
       10.20.50    10.20.50    10.20.51
          :80         :22         :445
```

The application tells SOCKS **which destination it wants** — dynamically.

> **Port forwarding** = fixed path ("go here")
> **SOCKS** = dynamic destination ("connect me there")

---

## How It Works Step-by-Step

When you run `proxychains curl http://10.10.20.50`:

1. `curl` wants `10.10.20.50:80`
2. Proxychains intercepts and redirects to SOCKS at `127.0.0.1:9050`
3. SOCKS client tells server: `CONNECT 10.10.20.50:80`
4. SOCKS server (on pivot) establishes: `pivot → 10.10.20.50:80`
5. Data flows through:

```
curl
 ↓
Proxychains
 ↓
SOCKS :9050
 ↓
Tunnel
 ↓
Win1
 ↓
10.10.20.50:80
```

---

## Where Chisel Fits In

Chisel creates the **tunnel** and can also provide the **SOCKS proxy endpoint**:

**Kali:**

```bash
chisel server -p 8000 --reverse
```

**Win1:**

```cmd
chisel.exe client <KALI_IP>:8000 R:9050:socks
```

Result:

```
Kali
127.0.0.1:9050
       │
       │ SOCKS
       ↓
    Chisel
       │
       ↓
     Win1
       │
       ↓
Internal Network
```

`R:9050:socks` means:

> "Create a SOCKS proxy endpoint on port 9050, carry its traffic through the Chisel connection."

---

## Where Proxychains Fits In

Proxychains makes applications that don't natively support SOCKS use the proxy.

**Configure** — `/etc/proxychains.conf`:

```
socks5 127.0.0.1 9050
```

> "Whenever I run an application through Proxychains, route its connections to the SOCKS5 proxy at `127.0.0.1:9050`."

**Usage:**

```bash
proxychains curl http://10.10.20.50
proxychains nmap -sT -Pn -p 80 10.10.20.50
```

---

## SOCKS4 vs SOCKS5

| Feature | SOCKS4 | SOCKS5 |
|---|---|---|
| Authentication | ❌ | ✅ |
| IPv6 | ❌ | ✅ |
| UDP | ❌ | ✅ |

For OSCP/pivoting, you'll commonly use:

```
socks5 127.0.0.1 9050
```

---

## Important Clarification: SOCKS ≠ Tunnel

> **SOCKS is a proxy protocol, not a tunnel.**

The tunnel is provided by something else:

| Tunnel Provider | Proxy Interface |
|---|---|
| SSH (`-D 9050`) | SOCKS |
| Chisel (`R:9050:socks`) | SOCKS |

SOCKS = the **interface** for requesting connections
SSH/Chisel = the **mechanism** that transports the traffic

### SSH SOCKS Example

```bash
ssh -D 9050 user@10.10.10.20
```

Creates a SOCKS proxy at `127.0.0.1:9050` on Kali. Verify with:

```bash
ss -lntp | grep 9050
```

---

## What Actually Happens On the Machine?

Usually nothing permanent. SSH/Chisel simply creates a **listening socket** on a port.

- It does **NOT** create a new network interface (`tun0`, `eth1`)
- It does **NOT** route the entire machine through the pivot
- It's a "proxy door" — only applications that use SOCKS go through it

```
127.0.0.1:9050
       ↑
   "proxy door"
```

That's why Proxychains exists — to make applications use that door.

---

## The Three Components — Summary

| Component | Job |
|---|---|
| **SOCKS** | Proxy interface — applications ask "connect me to X" |
| **Chisel / SSH** | Tunnel — transports the traffic between machines |
| **Proxychains** | Wrapper — makes applications use the SOCKS proxy |

```
Nmap
  ↓
Proxychains
  ↓
SOCKS
  ↓
Chisel
  ↓
Pivot
  ↓
Internal target
```

---

## Analogy

**SOCKS = receptionist** — you tell them "send this to Room 305"
**Chisel = private delivery road** — carries the package to the other side
**Pivot = person at the other end** — they can actually reach Room 305

---

## OSCP Mental Model

When you see:

```
chisel ... R:9050:socks
```

Immediately think:

```
Kali:9050 → Chisel → Pivot → Internal network
```

Then:

```
proxychains <tool> <target>
```

Means:

```
<tool> → Proxychains → SOCKS :9050 → Pivot → Target
```

### Key Sentence to Remember

> **SOCKS doesn't magically give me access to a network; it gives my applications a proxy through which they can ask the pivot machine to make connections into that network.**

### One-Sentence Definition

> **SOCKS (Socket Secure) is a general-purpose proxy protocol that allows a client application to request network connections to arbitrary destinations through a SOCKS proxy server, without the proxy needing to understand the application's protocol.**
