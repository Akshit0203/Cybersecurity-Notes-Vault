# Sensitive Credentials — Linux Privilege Escalation

> [!tip] Core Idea
> OS and applications often store **cleartext, encoded, or hashed credentials** on disk or in memory. Human error in managing these credentials is one of the most reliable privilege-escalation vectors.

## Why Cleartext Credentials Exist

- Authentication between systems (cron scripts, backups, service accounts) requires stored credentials.
- If stored in cleartext → files must be protected with strict permissions (often they aren't).
- If encrypted → encryption keys must be managed, which introduces its own problems:
  - Key hardcoded in a binary → attacker can reverse-engineer it.
  - Key transmitted over the network → attacker can intercept it.
- Due to key-management complexity, developers often assume local file storage is safe and store passwords in **cleartext**.

> [!important] Credentials ≠ Just Passwords
> Credentials include **API keys, tokens, OTPs, SSH keys, and authentication secrets** — not just user passwords.

---

## Common Locations for Sensitive Data

| Location | What to Look For |
| --- | --- |
| Configuration files | Database passwords, API keys, service credentials |
| Bash / shell history | Commands with inline passwords |
| `/etc/passwd` & `/etc/shadow` | Password hashes |
| Process memory | In-memory cleartext credentials |
| Browser vaults | Saved website passwords |
| SSH keys (`~/.ssh/`) | Misprotected private keys |
| Binary files | Hardcoded strings in compiled programs |
| Log files | Tokens, passwords appended by services |

## 1. Bash / Shell History

If passwords are typed on the command line, they get recorded in the history file.

```bash
# View all history files for current user
cat ~/.*history | less
```

**Why this happens:** When a user runs something like `mysql -u root -pPassword123!`, the password is part of the command string and gets written to `.bash_history` / `.zsh_history`.

**Safe vs. Unsafe:**

```bash
# BAD — password logged in .bash_history:
mysql -u root -pPassword123!

# GOOD — password prompted interactively, NOT logged:
mysql -u root -p
Enter password:
```

> [!note]
> When entered at an interactive prompt, input is processed inside the application's process memory (not the Bash shell context), so it never reaches the history file. Check `echo $HISTFILE` to confirm which file is active.

**Other history files to check:** `.mysql_history`, `.nano_history`, `.zsh_history`

## 2. Configuration Files

Web apps and services store database/service credentials in cleartext so they can authenticate automatically (e.g., WordPress `wp-config.php` stores DB credentials).

### Search Commands

```bash
# Search for files containing password strings
find / -type f -exec grep -i -l "PASSWORD\|PASSWD" {} /dev/null \;

# Locate specific config files
locate config.php
locate password; locate passwd

# Check mail spools
cat /var/mail/*
cat /var/spool/mail

# Recursive grep for passwords across the filesystem
grep --color=auto -rnw '/' -ie "PASSWORD\|PASSWD" --color=always 2>/dev/null
```

![](attachments/Pasted%20image%2020260918103257.png)

> [!tip]
> Finding database passwords often lets you log into the DB, extract user hashes, or attempt **password reuse** across system accounts.

## 3. SSH Keys

Users sometimes create backups of SSH private keys and fail to set correct permissions.

- SSH private keys are typically at `~/.ssh/id_rsa`
- Private keys **must** have `600` permissions (owner read/write only)
- If an elevated user's `id_rsa` is world-readable, any user can copy it and log in as that user **without a password**

```bash
# Login using a stolen private key
ssh -i id_rsa root@<target_ip>
```

> [!warning] Legacy Key Algorithm Error
> If OpenSSH returns `"No mutual signature algorithm supported"`, append:
> ```bash
> ssh -i id_rsa root@<target_ip> -o PubkeyAcceptedKeyTypes=+ssh-rsa
> ```

## 4. Recently Modified Files

Services, scripts, and login actions frequently append sensitive data to log files.

```bash
# Find files modified in the last N minutes
find / -mmin -N -xdev 2>/dev/null
```

Use this to identify active log files or recently updated configs containing credentials.

---

## 5. Credentials in Binary Files

The `strings` command extracts human-readable text from compiled binaries without full reverse engineering.

```bash
strings /tmp/process
```

May reveal hardcoded passwords, secret keys, or internal configurations.

---

## 6. Credentials in Memory

Linux processes may retain cleartext passwords in memory for active sessions (similar to LSASS in Windows).

```bash
# Find the process ID
ps -ef | grep [service_name]

# Search memory for password strings
strings /dev/mem -n10 | grep -ie "PASSWORD|PASSWD" --color=always

# Attach debugger to dump process memory
gdb -p [PID]
info proc mappings
dump memory /tmp/process <START_ADDR> <END_ADDR>
```

## 7. Credentials in Browser / Application Vaults

Browsers save passwords for auto-completion. **LaZagne** is an open-source post-exploitation tool that extracts stored credentials from local application vaults.

### Supported Modules

| Category | Examples |
| --- | --- |
| Web Browsers | Firefox, Chrome |
| Databases | PostgreSQL |
| Dev / VCS Tools | Git, SVN, Maven |
| Chat & Mail | Skype, Thunderbird, Outlook |
| System / Network | OpenSSH keys, Wi-Fi profiles, local password stores |

### Usage

```bash
# Scan all supported modules
lazagne.py all

# Target only browsers
lazagne.py browsers

# Target Firefox specifically
lazagne.py browsers -firefox
```
