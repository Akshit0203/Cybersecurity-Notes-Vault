# Introduction to Linux Capabilities

Linux capabilities are special permissions that allow a process or executable to perform certain privileged actions **without requiring full root privileges**. Misconfigured capabilities are a prime privilege escalation vector.

---

## Why Capabilities Exist

Traditionally, Linux had only two privilege levels:

| User | Permissions |
|---|---|
| Normal user | Limited permissions |
| Root | Almost unlimited permissions |

The problem with **SUID**: when a binary has the SUID bit set and is owned by root, it runs with **complete, unrestricted root authority** — even if it only needs one specific admin task. This is a massive security risk if the binary has vulnerabilities.

**Capabilities solve this** by breaking root's monolithic privileges into smaller, distinct, fine-grained units that can be independently assigned to specific executables or threads.

> [!NOTE]
> **SUID** = Run as the file owner (all-or-nothing root).
> **Capabilities** = Grant only the specific privileges a program actually needs.

### Analogy — Windows UAC vs. Linux Capabilities

| Concept | Windows | Linux |
|---|---|---|
| Full admin | Administrator token (high-integrity) | SUID root / UID 0 |
| Granular privileges | UAC consent + security tokens | Linux capabilities |
| Default state | Medium-integrity shell | Unprivileged process (EUID ≠ 0) |

---

## Privileged vs. Unprivileged Processes

Every running process falls into one of two categories:

| Category | EUID | Kernel Behavior |
|---|---|---|
| **Privileged** | `0` (root) | Bypasses all kernel permission checks |
| **Unprivileged** | Non-zero | Subject to full permission checks for every action |

- **Real UID (UID)**: Your original logged-in user identity.
- **Effective UID (EUID)**: The identity the running process currently assumes. Certain binaries temporarily modify EUID, then revert after the process terminates.

---

## Capabilities vs. SUID — Comparison

| Feature | SUID | Capabilities |
|---|---|---|
| Grants | File owner's effective UID | Specific privileges only |
| Typical example | SUID root executable | `cap_setuid=ep` |
| Scope | Potentially **all** root privileges | **Selected** privileges |
| Enumeration | `find / -perm -4000 -type f 2>/dev/null` | `getcap -r / 2>/dev/null` |
| Main risk | Vulnerable root-owned executable | Excessive or dangerous capability |
| Storage | File permission bits | Extended file attributes (`xattr`) |

> [!IMPORTANT]
> SUID discovery (`find / -perm -4000`) **will NOT find** capability-enabled binaries. You **must** also run `getcap` enumeration. Always run **both** during OSCP-style assessments.

---

## Important Capabilities for PrivEsc

| Capability | Meaning | Risk |
|---|---|---|
| `CAP_SETUID` | Change process UID | Can become UID 0 (root) — **most dangerous** |
| `CAP_SETGID` | Change process GID | Can change group privileges |
| `CAP_DAC_OVERRIDE` | Bypass file read/write permission checks | Read/modify protected files like `/etc/shadow` |
| `CAP_DAC_READ_SEARCH` | Bypass file read and directory search permissions | Read any protected file |
| `CAP_NET_BIND_SERVICE` | Bind to privileged ports (< 1024) | Bind to port 80, 22, etc. |
| `CAP_NET_RAW` | Raw network operations | Packet manipulation, ICMP (e.g., `ping`) |
| `CAP_NET_ADMIN` | Network configuration | Modify routing, firewall rules, interfaces |
| `CAP_SYS_ADMIN` | Broad sysadmin privileges | Mount filesystems, device ops — **extremely dangerous** |
| `CAP_SYS_PTRACE` | Process tracing | Expose sensitive process data |
| `CAP_CHOWN` | Change file ownership | Take ownership of any file |

> [!CAUTION]
> Pay special attention to: `cap_setuid`, `cap_dac_override`, `cap_dac_read_search`, and `cap_sys_admin`.

---

## Capability Sets

Capabilities are categorized across five distinct **sets**:

| Set | Description |
|---|---|
| **Permitted** | Limiting superset of capabilities explicitly allowed for the process |
| **Inheritable** | Capabilities passed from parent to child processes |
| **Effective** | The subset actively used by the kernel for permission checks |
| **Bounding** | Absolute upper limit of capabilities a process can inherit |
| **Ambient** | Capabilities preserved across `execve` for non-SUID programs |

During privilege escalation, focus on the **Permitted** and **Effective** sets.

### What Does `=ep` Mean?

```
cap_setuid=ep
```

| Letter | Meaning |
|---|---|
| `e` | **Effective** — capability is currently active |
| `p` | **Permitted** — capability is allowed for the process |
| `i` | **Inheritable** — can be inherited under certain conditions |

`=ep` means the capability is both permitted **and** effective — immediately usable.

## Enumeration Commands

### Find All File Capabilities (Primary Command)

```bash
getcap -r / 2>/dev/null
```

| Part | Meaning |
|---|---|
| `getcap` | Displays capabilities assigned to files |
| `-r` | Searches recursively |
| `/` | Starts from root directory |
| `2>/dev/null` | Hides permission-denied errors |

### More Focused Search

```bash
getcap -r /usr/bin /usr/sbin /usr/local/bin 2>/dev/null
```

### Check a Specific File

```bash
getcap /path/to/program
```

### Inspect Process Capabilities

```bash
cat /proc/<process_ID>/status | grep Cap
capsh --decode=<HEX_VALUE>
```

Decoding hex capability masks reveals enabled capabilities across permitted, effective, and bounding sets.

### Example Output

```
/usr/bin/python3.11 cap_setuid=ep
/usr/bin/ping cap_net_raw=ep
```

## Enumeration Workflow

1. **Check your current identity**
    ```bash
    whoami
    id
    ```

2. **Search for file capabilities**
    ```bash
    getcap -r / 2>/dev/null
    ```

3. **Inspect a suspicious executable**
    ```bash
    ls -la /path/to/program
    file /path/to/program
    ```

4. **Check the capability directly**
    ```bash
    getcap /path/to/program
    ```

5. **Identify the program and its behavior**
    ```bash
    strings /path/to/program
    ldd /path/to/program
    ```

6. **Research the capability + program combination** — check GTFOBins for breakout vectors

## Understanding `cap_setuid` Exploitation

If enumeration returns:
```
/usr/bin/python3.11 cap_setuid=ep
```

This means Python can change its Effective UID to `0` (root) and execute commands with root privileges:

```bash
python3.11 -c 'import os; os.setuid(0); os.system("/bin/bash -p")'
```

**What happens internally:**

```
Normal user (UID 1000) → Python (cap_setuid) → Change UID to 0 → Root shell
```

> [!WARNING]
> A capability listing alone does not guarantee successful escalation — the executable must actually support the operation (e.g., Python has `os.setuid()`).

---

## Understanding `cap_dac_override` / `cap_dac_read_search`

**`cap_dac_override`** bypasses file read/write permission checks. A process with this capability can:
- Read sensitive files (e.g., `/etc/shadow`)
- Modify protected files
- Access data belonging to other users

**`cap_dac_read_search`** specifically bypasses read and directory search restrictions (read-only, no write).

Example — normally blocked:
```bash
cat /etc/shadow    # Permission denied for regular users
```

With `cap_dac_override` on `vim`:
```bash
vim /etc/shadow    # Successfully opens and displays password hashes
```

## Useful Commands Reference

| Purpose | Command |
|---|---|
| Find all file capabilities | `getcap -r / 2>/dev/null` |
| Check one file | `getcap /path/to/file` |
| Show current user and groups | `id` |
| Show effective UID | `id -u` |
| Find SUID files | `find / -perm -4000 -type f 2>/dev/null` |
| Inspect executable type | `file /path/to/program` |
| List linked libraries | `ldd /path/to/program` |
| Display file permissions | `ls -la /path/to/program` |
| Decode process capability hex | `capsh --decode=<HEX_VALUE>` |
