### **[Part 1: Introduction to Service Abuse & DLL Hijacking]**

Hello friends, in this video we will discuss the fourth technique in service abuse: **DLL Hijacking**. Whenever a service runs, an executable runs alongside it, and that executable does not necessarily have to be standalone. It can have many DLLs associated with it. This is similar to the overall structure of Windows for applications. It contains many DLLs, just like GNU libraries, shared objects, and shared libraries we studied earlier. Here, we refer to shared libraries as **DLLs (Dynamic Link Libraries)**.

Much of the code is modular. As you have seen in Python, we import various modules—like `import string`, `import pycrypto`, or `import termcolor`—so we import different modules for different tasks to avoid rewriting code repeatedly. If we want to work with networking, transfer packets, or work with sockets, we use `import socket`; if we want colored text in the terminal, we use `termcolor`.

### **[Part 2: Modular Code Structure & Dynamic Link Libraries]**

Similarly, if you want to build a web server, you use `import flask` or similar packages. We simply utilize pre-written code and leverage its functionality rather than writing code from scratch. To save time and make code modular, Windows creates many DLLs. You import them into your code and use their functions.

As I mentioned in the last video, we can manipulate or hijack the path resolution search order used by Windows when it searches for files. The same concept applies here: Dynamic Link Libraries contain data that can be used by multiple applications. A single DLL—whether for graphics/visuals, audio, or utility functions—can be shared across multiple installed applications and background services. Placed in a central location, any installed application running as a service can access and use it.

---

### **[Part 3: The Mechanics of DLL Search Order Hijacking]**

What we do here is target a situation where an application searches for a required DLL but cannot find it in a specific path. When a program requests a DLL that does not exist at the expected location, and that application runs as a service on behalf of a high-privileged user, placing a custom DLL at that missing location allows us to hijack the service execution.

Where the application searches is part of the path resolution search order. If the path to a DLL is not explicitly hardcoded within the application, Windows resolves the path using the user's `PATH` environment variable. Just as in Linux, Windows maintains a `PATH` environment variable (with slightly different syntax). If the path is omitted in configurations (like in cron headers or sudoers in Linux), Windows checks the `PATH` variable of the currently logged-in user and begins searching from there.

There are several ways to exploit DLL vulnerabilities—such as replacing existing DLLs, hijacking the search order, or redirecting execution from a legitimate DLL to a malicious one. Here, we focus specifically on **DLL Search Order Hijacking**.

---

### **[Part 4: Standard Windows DLL Search Order]**

Windows follows a standard search order when an application attempts to load a DLL:

1. **Loaded Modules in Memory**: If the DLL is already loaded in memory, Windows uses the loaded instance.
2. **Known DLLs**: System-defined Known DLLs pre-configured by the operating system.
3. **Application Directory**: The directory containing the executable binary itself.
4. **System Directory (`C:\Windows\System32`)**: Contains core system DLLs provided by Windows for custom applications. This is an elevated, safe directory accessible primarily to System and Administrator accounts.
5. **16-bit System Directory**: Legacy 16-bit directory (rarely present on modern systems).
6. **Windows Directory (`C:\Windows`)**: Core operating system directory, also restricted from normal user modifications.
7. **Current Directory**: The working directory from which the application process was launched. If the working directory differs from the application directory, Windows checks here. If this directory is user-writable, it can be controlled by an attacker.
8. **Directories Listed in the `PATH` Environment Variable**: Directories specified in the system or user `PATH` environment variable.

If the DLL is found at any step in this resolution chain, the search stops immediately. If the application uses a custom search order and queries user-writable directories—such as `C:\Temp`, `AppData`, `Local`, or user home directories—the DLL can be directly hijacked.

### **[Part 5: Identifying Missing DLLs with Process Monitor (ProcMon)]**

To identify DLL hijacking opportunities, we use **Process Monitor (ProcMon)**, a utility from Microsoft's Sysinternals suite. In ProcMon, we apply two primary filters:

1. **Process Name Filter**: Filter by the service executable name that we want to audit and hijack.
2. **Result Filter (`NAME NOT FOUND`)**: Filter for DLL load events returning `NAME NOT FOUND`.

Filtering for `NAME NOT FOUND` isolates instances where the application attempted to load a missing DLL from a specific path. Next, perform permission enumeration on that target directory to verify whether your low-privileged account possesses write access.

If write permissions exist, generate a custom malicious DLL payload (rather than an executable binary) and place it in the target directory to complete the DLL Search Order Hijack.
