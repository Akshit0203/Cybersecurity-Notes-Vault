# Introduction to DNS Zones

## What is a DNS Zone?

A **DNS zone** is a **portion of the DNS namespace** managed by a specific organization or administrator.

> **Zone = a container/database that holds DNS information for a domain or portion of a domain.**

- An **administrative space** for granular control of DNS components
- A zone can contain **multiple subdomains**
- **Multiple zones** can exist on the same server
- Zones are **not physically separated** — they are strictly used for **delegating control**

### Zone ≠ Domain

| Concept    | Definition                                                 |
| ---------- | ---------------------------------------------------------- |
| **Domain** | Part of the DNS namespace (e.g., `example.com`)            |
| **Zone**   | The portion of that namespace **administered by a particular DNS authority** |

For simple domains, they may look identical. But zones can be **delegated** into smaller zones.

---

## Why Create Zones? (Delegation)

### Scenario

You own `example.com` and have subdomains:
- `shopp.example.com` — e-commerce (managed by a different team)
- `app.example.com` — application
- `example.com` — main website

If you mix all records in one file, it gets messy. Instead, you **delegate** by creating separate zones:

```
Zone 1: example.com (manages app + main site)
Zone 2: shopp.example.com (managed separately)
```

### Cloudflare Example

```
cloudflare.com
├── support.cloudflare.com  ─┐
├── community.cloudflare.com ├── Zone 1: cloudflare.com
│                            ─┘
└── blog.cloudflare.com     ──── Zone 2: blog.cloudflare.com (delegated)
```

> **Granular control** = managing changes at a micro level. Smaller, separated zones are much easier to search, update, and maintain than one massive record set.

## DNS Zone File

All zone information is stored in a **DNS zone file**:

- A **plain text file** stored on the DNS server (no encryption)
- Contains the **actual representation of the zone** — all records for every domain within the zone
- This is **exactly what we want to extract** during DNS enumeration

### Records Contained in a Zone File

```
A       → hostname → IPv4
AAAA    → hostname → IPv6
MX      → mail server
NS      → authoritative DNS server
CNAME   → alias
TXT     → text information
SOA     → zone's administrative information
```

### Example Zone File Content

```
example.com.    A      93.184.216.34
example.com.    MX     mail.example.com
example.com.    NS     ns1.example.com
www.example.com A      93.184.216.34
mail.example.com A     10.0.0.5
ftp.example.com  A     10.0.0.6
```

---

## SOA Record (Start of Authority)

Every zone file **must start** with an SOA record:

- Identifies **who holds authority** over the domain/zone
- Contains **contact information** for the zone administrator
- Configured with the registrar when purchasing a domain

> [!important] Why DNS Enumeration Matters
> The zone file contains **every single record** for a domain — a massive amount of valuable information. This is precisely why we perform DNS enumeration: **to extract this zone file** via zone transfer.

---

## Key Distinctions

### Record vs Zone

> **DNS record = one piece of information** (e.g., `www.example.com → 192.168.1.10`)  
> **DNS zone = collection of DNS records** for a domain/subdomain

### Zone vs CDN

```
DNS zone → contains DNS records (a database/file)
CDN      → network of servers used to deliver content closer to users
```

A company can **use a CDN and have DNS records pointing to it**, but the CDN itself is not a DNS zone.

---

## OSCP Relevance

DNS zones become interesting during **enumeration** via **zone transfer (AXFR)**:

```bash
dig AXFR example.com @ns1.example.com
```

If the server incorrectly allows it, you could receive:

```
dev.example.com
vpn.example.com
mail.example.com
admin.example.com
internal.example.com
staging.example.com
```

→ Reveals **hosts/subdomains not obvious from normal enumeration**.

> **Zone = DNS information container**  
> **Zone transfer = copying that container between DNS servers**
