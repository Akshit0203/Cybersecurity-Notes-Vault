### **[Part 1: Introduction to Pivoting and Network Subnets]**

Hello friends. In this video, we will start learning about pivoting[1]. We have previously studied lateral movement and what it entails[1]. Pivoting is a similar concept where we utilize redirection and tunneling[1]. Understanding its significance in this course is essential because in modern real-world penetration testing—especially in Active Directory (AD) environments, as well as non-AD environments—you will inevitably encounter this concept[1]. It is extremely useful in real-world red teaming and pentesting engagements[1].

When compromising a machine, we must enumerate its IP address, subnet, and other reachable hosts on that network to move laterally[1]. However, when scope spans an entire organization, targets do not reside on a single network 99% of the time[1][2]. Organizations distribute infrastructure across multiple private subnets, each protected by dedicated firewalls enforcing strict ingress and egress port filtering rules[2]. To switch between internal networks and target isolated systems, we must route traffic through compromised gateways rather than remaining static on a single subnet[2].

---

### **[Part 2: Gateways, Routing Tables, and Port Restrictions]**

To move across subnets, we must compromise the central gateway or dual-homed workstation connecting both networks[3]. A dual-homed pivot host possesses two routing tables: one for the external/accessible network and one for the internal isolated network[3]. Without proper routing entries or direct network paths, standard traffic cannot reach internal targets directly[3]. Furthermore, essential service ports—such as HTTP (80), HTTP-Alt (8080), MySQL (3306), SMB (445), and RDP (3389)—are typically blocked by perimeter firewalls[3][4].

Pivoting and tunneling solve this problem by jumping from one network to another through a pivot point (gateway)[4]. By updating routing tables on a compromised dual-homed workstation, we can forward traffic across allowed ports to reach hidden internal target IPs and subnets[4][5].

---

### **[Part 3: Network Architecture and Pivot Mechanics]**

Consider an architecture where the attacker machine resides on a accessible network (e.g., subnet `192.168.100.0/24`)[5]. The attacker compromises a dual-homed gateway machine equipped with two network interfaces: an external IP on the attacker's network and an internal IP (e.g., `10.10.10.23`) on the internal network[5][6].

An internal target host (e.g., `10.10.10.33`) cannot be reached directly from the attacker's machine due to routing and firewall restrictions[6]. However, because the compromised pivot workstation possesses routes to the internal `10.10.10.0/24` subnet, we can configure route forwarding through this gateway to relay traffic seamlessly from our attacking host to the internal target[6]. Mastering pivoting is vital for practical security certifications (e.g., eJPT, OSCP) and enterprise red teaming[7].

---

### **[Part 4: Introduction to SSH Port Forwarding]**

The most popular and reliable protocol for tunneling and port forwarding is **SSH (Secure Shell)**[7]. Firewalls commonly permit inbound/outbound traffic on SSH port 22 to allow remote administration[7]. Because SSH traffic is encrypted and legitimate, we can encapsulate (tunnel) arbitrary protocol traffic inside SSH packets to bypass perimeter filters[7][8].

SSH includes built-in port forwarding features, enabling two-way encrypted communication between hosts[8][9]. Port forwarding relays connections from a local port through an SSH tunnel to a destination port on a target host[8][9]. SSH port forwarding falls into three primary categories:

1. **Local Port Forwarding**[9][10]
2. **Remote Port Forwarding**[11]
3. **Dynamic Port Forwarding**[12][13]

---

### **[Part 5: Local Port Forwarding (** **ssh -L** **)]**

**Local Port Forwarding** opens a listening port on the local (attacker) machine and forwards all incoming connections through the SSH tunnel to a specified remote host and port[9][10].

The syntax for local port forwarding is:

```
ssh -L [LOCAL_IP:]LOCAL_PORT:FORWARD_HOST:FORWARD_PORT USER@PIVOT_HOST

```

- **-L**: Specifies Local Port Forwarding[10].
- **LOCAL_PORT**: The source port opened on the local attacking machine[10][14].
- **FORWARD_HOST**: The destination target host (either `127.0.0.1` on the pivot host or an internal target IP)[10][14].
- **FORWARD_PORT**: The destination service port on the target host (e.g., 80 for Web, 3306 for MySQL, 3389 for RDP)[10][14].
- **USER@PIVOT_HOST**: The SSH credentials and IP of the compromised jump host[10][14].

#### **Two Primary Use Cases for Local Port Forwarding:**

1. **Accessing Local-Only Services on the Jump Host**: If a service (e.g., port 456 or internal database on port 3306) listens exclusively on `127.0.0.1` of the remote host and is blocked externally by a firewall, local forwarding (`-L 1234:127.0.0.1:456 user@pivot`) allows the attacker to bind local port 1234 to the pivot host's loopback interface[15][16].
2. **Reaching Deep Internal Network Targets**: To access an internal server (`10.10.10.33`) behind the jump host, local forwarding (`-L 8080:10.10.10.33:80 user@pivot`) routes local traffic sent to `localhost:8080` through the SSH tunnel directly to port 80 on `10.10.10.33`[17].

---

### **[Part 6: Remote Port Forwarding (** **ssh -R** **)]**

**Remote Port Forwarding** performs the inverse operation of local forwarding[11]. It opens a listening port on the remote SSH server (pivot host) and forwards connections back through the tunnel to a specified host and port on the local (attacker) side[11][18].

The syntax for remote port forwarding is:

```
ssh -R [REMOTE_IP:]REMOTE_PORT:DESTINATION_HOST:DESTINATION_PORT USER@PIVOT_HOST

```

- **-R**: Specifies Remote Port Forwarding[11].
- **REMOTE_PORT**: The listening port opened on the remote pivot server[11][18].
- **DESTINATION_HOST**: The target host on the local side (typically the attacker's `localhost`)[11][18].
- **DESTINATION_PORT**: The local port where the attacker hosts a service or reverse handler[11][18].

#### **Primary Use Cases for Remote Port Forwarding:**

- **Exposing Local Services to Internal Targets**: If an internal target needs to fetch a payload or file hosted on the attacker's local HTTP web server (port 80), remote forwarding (`-R 8000:127.0.0.1:80 user@pivot`) exposes local port 80 as port 8000 on the pivot host[18].
- **Catching Reverse Shells**: Internal target systems cannot establish direct outbound connections to an attacker's IP across subnets[18][19]. By forwarding a remote port on the jump host back to a local Netcat/Metasploit listener, the internal target sends its reverse shell to the jump host, which routes it back to the attacker[19]. *(This operates similarly to public tunneling services like Ngrok)*[19].

---

### **[Part 7: Dynamic Port Forwarding (** **ssh -D** **) and SOCKS Proxies]**

While local and remote port forwarding establish one-to-one port mappings, **Dynamic Port Forwarding** creates a one-to-many SOCKS proxy tunnel[12][13]. Instead of binding a single port to a single destination, dynamic forwarding turns the local SSH client into a SOCKS4/SOCKS5 proxy server[13][20].

The syntax for dynamic port forwarding is:

```
ssh -D LOCAL_PROXY_PORT USER@PIVOT_HOST

```

- **-D**: Specifies Dynamic Port Forwarding[20].
- **LOCAL_PROXY_PORT**: The local port allocated as a SOCKS proxy (e.g., 9050 or 1080)[20].

#### **Advantages and Usage:**

- **Full Network Sweeps and Multi-Port Scanning**: Rather than manually forwarding individual ports one by one, dynamic forwarding routes all application traffic directed through the SOCKS proxy dynamically to any IP and port reachable by the pivot host[13][21].
- **Proxychains Integration**: By prefixing scanning and exploitation tools with `proxychains` (e.g., `proxychains nmap -sT -Pn 10.10.10.0/24`), tools automatically route their TCP packets through the SOCKS proxy tunnel across the entire internal subnet[13].
- **Bypassing Outbound Egress Restrictions**: If an internal machine cannot access the public internet directly due to firewall blocks, dynamic forwarding through an internet-connected SSH pivot server allows the internal host to tunnel its web traffic out to the internet[23][24].

---

### **[Part 8: Summary and Conclusion]**

In summary:

- **Local Port Forwarding (** **-L** **)**: Forwards a local port to a remote host/port (most common in CTFs and pentests)[10][22].
- **Remote Port Forwarding (** **-R** **)**: Forwards a remote port back to a local host/port (used for reverse shells and file delivery)[11].
- **Dynamic Port Forwarding (** **-D** **)**: Creates a SOCKS proxy to reach any IP/port reachable by the pivot host dynamically (ideal for Nmap subnet scanning)[13].

Practicing these pivoting configurations is essential for building real-world offensive security capabilities[22]. Keep watching, keep learning, and goodbye![22]






For OSCP, the easiest way to understand port forwarding is:

> **Port forwarding moves network traffic from one place to another so that you can reach a service that you normally cannot reach.**

The three types are **local**, **remote**, and **dynamic**.

---

# 1. First understand the problem

Imagine you compromise:

```
Kali
10.10.14.5
   |
   | VPN
   ↓
WEB SERVER
10.10.10.20
   |
   | internal network
   ↓
INTERNAL SERVER
10.10.20.50
   |
   └── 3306 MySQL
```

You can reach:

```
10.10.10.20
```

but **you cannot directly reach**:

```
10.10.20.50:3306
```

because the internal server isn't exposed to your Kali.

The compromised web server can reach it, though.

That's where tunneling/port forwarding comes in.

---

# 2. Local Port Forwarding

### The key idea:

> **You open a port on YOUR machine, and traffic gets forwarded through the compromised machine to an internal service.**

Think:

```
KALI                         COMPROMISED              INTERNAL
                            SERVER
127.0.0.1:8080
     │
     │
     └──────────────→ 10.10.10.20 ─────────→ 10.10.20.50:3306
                                     
                         forwarded
```

You connect to:

```
127.0.0.1:8080
```

but the traffic ultimately reaches:

```
10.10.20.50:3306
```

### Why "local"?

Because the **listening/forwarded port is created locally on your Kali**.

```
LOCAL PORT
     ↓
127.0.0.1:8080
```

---

## Example with SSH

Suppose you've obtained SSH access to:

```
10.10.10.20
```

and that machine can access:

```
10.10.20.50:3306
```

You could conceptually create:

```
ssh -L 8080:10.10.20.50:3306 user@10.10.10.20
```

Now:

```
Kali
localhost:8080
      ↓
SSH tunnel
      ↓
10.10.10.20
      ↓
10.10.20.50:3306
```

So when you run a client against:

```
localhost:8080
```

you're actually reaching the internal MySQL service.

### Memorize:

> **Local = I create the port on my machine.**

---

# 3. Remote Port Forwarding

Now reverse the situation.

Instead of creating a listening port on Kali, you create one on the **remote/compromised machine**.

```
KALI
10.10.14.5
   ↑
   |
   |
COMPROMISED SERVER
10.10.10.20
   │
   └── listening port
```

Suppose you have a service running on Kali:

```
Kali:9001
```

You want the compromised machine to be able to reach it through a forwarded port.

Conceptually:

```
COMPROMISED SERVER:8080
          ↓
        tunnel
          ↓
KALI:9001
```

With SSH:

```
ssh -R 8080:127.0.0.1:9001 user@10.10.10.20
```

Now the remote side has a forwarded port that ultimately connects to your Kali service.

### Why "remote"?

Because the **forwarded listening port is created on the remote side**.

> **Remote = I create the port on the remote machine.**

---

# 4. The easiest way to remember Local vs Remote

Think about **where the new listening port appears**.

### Local forwarding

```
MY MACHINE
localhost:8080
     ↓
    tunnel
     ↓
remote/internal service
```

**Port is on me.**

### Remote forwarding

```
remote machine
:8080
   ↓
 tunnel
   ↓
MY MACHINE / service
```

**Port is on remote.**

---

# 5. Dynamic Port Forwarding

This one is different.

Instead of saying:

> "Forward this particular local port to this particular destination."

you create a **SOCKS proxy**.

For example:

```
ssh -D 9050 user@10.10.10.20
```

Now Kali has:

```
127.0.0.1:9050
```

which acts as a SOCKS proxy.

You can then send traffic through it.

Conceptually:

```
                    SSH TUNNEL
KALI                  │
 │                    │
 │ SOCKS :9050        │
 ↓                    ↓
Browser/tool → compromised server → internal network
                                      │
                    ┌─────────────────┼──────────────┐
                    ↓                 ↓              ↓
                 10.20.1.5         10.20.1.8       10.20.1.20
                 :80               :445             :3306
```

The big advantage is:

> **You don't have to create a separate port forward for every destination.**

---

# 6. Why dynamic forwarding is powerful for OSCP

Imagine the internal network contains:

```
10.10.20.10:80
10.10.20.15:445
10.10.20.20:22
10.10.20.25:3306
```

With local forwarding, you might create individual tunnels:

```
8080 → 10.10.20.10:80
8445 → 10.10.20.15:445
2222 → 10.10.20.20:22
3306 → 10.10.20.25:3306
```

That's annoying.

With dynamic forwarding:

```
Kali
  │
  └── SOCKS :9050
          ↓
     compromised host
          ↓
     internal network
```

your applications can request different destinations through the SOCKS proxy.

# 8. OSCP mental model

When you compromise a machine, ask:

### "Who can reach what?"

For example:

```
Kali
  │
  ├──→ Compromised Server ✅
  │
  └──→ Internal Server ❌

Compromised Server
  │
  └──→ Internal Server ✅
```

That means the compromised server can act as your **pivot point**.

Then choose the appropriate forwarding method.

### One specific internal service

Use **local forwarding**:

```
Kali → tunnel → internal service
```

### Need a listening port on the remote side

Use **remote forwarding**:

```
remote → tunnel → Kali/service
```

### Need to access many internal hosts/services

Use **dynamic forwarding / SOCKS**:

```
Kali → SOCKS → pivot → internal network
```

---

# 9. Don't confuse port forwarding with VPN

A VPN generally gives your machine a route into another network:

```
Kali
 ↓
VPN
 ↓
HTB network
```

Port forwarding is more targeted:

```
Kali
 ↓
tunnel through compromised host
 ↓
specific service/network
```

In OSCP, **port forwarding becomes especially important after you compromise a machine that has access to an internal network that your Kali cannot directly access.**

### Final memory trick

Just remember:

> **Local = port on me.**  
> **Remote = port on them.**  
> **Dynamic = SOCKS proxy, choose destinations dynamically.**

And the classic SSH flags:

```
-L = Local
-R = Remote
-D = Dynamic
```

So:

```
ssh -L ...
ssh -R ...
ssh -D ...
```

That's the core you need for OSCP.
