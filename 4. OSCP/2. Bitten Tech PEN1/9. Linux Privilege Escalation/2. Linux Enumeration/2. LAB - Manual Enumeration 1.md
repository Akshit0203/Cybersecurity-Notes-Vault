Once logged in, our post-exploitation enumeration phase officially begins.

Privilege escalation may not always be a single direct jump from a low-privilege user to `root`. In real-world scenarios, it can involve multiple hops—from an initial service account to a normal user account, then to another user account with broader privileges, and finally to `root`. Regardless of the number of stages, the enumeration methodology and core techniques remain identical. We will start with manual enumeration techniques before moving on to automated tools.

### **[Section 2: Initial Privilege Check (`whoami` & `id`)]**

First, determine your current privilege level and permissions on the system:

- Running **`whoami`** displays your current username (here, it returns `user`).
- Running **`id`** displays your User ID (UID), Group ID (GID), and all secondary group memberships. Custom user accounts typically start at UID `1000` (here, UID is `1000`).

Checking group memberships is crucial because if your account belongs to a group with special permissions (such as spawning root processes or managing specific services), you might be able to escalate privileges immediately.

---

### **[Section 3: User Enumeration (`/etc/passwd` & `/home`)]**

Next, we perform **User Enumeration** to map out all user accounts on the host:

- **Inspect `/etc/passwd`**: This file lists all user accounts, including system accounts, service accounts, and custom user profiles. Focus on user accounts with UIDs of `1000` or higher, as these represent interactive custom users alongside the default `root` account (UID `0`).
- **Inspect `/home`**: Checking the `/home` directory reveals all custom user home directories on the system. The number of user folders usually corresponds to the number of human/custom user accounts.

Mapping users helps you determine whether you can escalate directly to `root` or if you need to pivot horizontally to another user account (`user` \(\rightarrow\) `user2` \(\rightarrow\) `user3` \(\rightarrow\) `root`).

---

### **[Section 4: Group Enumeration (`/etc/group` & Special Group Abuse)]**

Next, we perform **Group Enumeration** by inspecting the **`/etc/group`** file. Every user belongs to one or more groups, and specific Linux permissions are assigned based on group membership:

- **Authentication/Log Groups**: Members can read SSH authentication logs and inspect past login attempts or passwords.
- **Docker Group**: Members can run Docker container images, often leading to trivial root privilege escalation.
- **MySQL / Database Groups**: Members can read or manipulate database files directly.
- **Shadow Group**: Members can read the `/etc/shadow` file without root access and extract password hashes for offline cracking.
- **Backup Group**: Members can create or access system file backups across storage locations.
- **Sudo / Wheel Group**: Members can execute commands as other users or `root`.

Whenever you discover your account belongs to a non-standard group, research what administrative capabilities that specific group grants.

---

### **[Section 5: Hostname & Network Identity (`hostname`, `uname -a`)]**

Next, identify the system's **Hostname**:

- Running **`hostname`** (or checking the second field of **`uname -a`**) reveals the DNS name of the host on the network.
- Hostnames are critical for identifying trust relationships between internal servers, configuring exploit payloads, or executing DNS-based attacks like DNS spoofing/poisoning.

---

### **[Section 6: OS Release & Kernel Version Enumeration]**

To identify the operating system distribution and kernel version:

- **`cat /etc/issue`**: Displays system installation details and welcome banners.
- **`cat /etc/os-release`**: Displays OS distribution details, version numbers, and codenames.
- **`uname -a`**: Displays the exact Linux **Kernel version** and system CPU architecture.

You can search public vulnerability databases (like Exploit-DB) for kernel exploits corresponding to the kernel version. However, kernel exploits are rarely the intended vector in modern real-world pentests or exams like OSCP (99% of systems are patched, and kernel exploits can crash the system). Nevertheless, kernel enumeration remains essential for determining system compilation tools and software distribution requirements.

---

### **[Section 7: Process Enumeration (`ps`, `ps aux`, `top`)]**

Finally, inspect active running processes in memory:

- **`ps`**: Displays processes spawned by the current user in the current terminal session.
- **`ps aux`**: Displays all active processes across all users on the system, including process IDs (PIDs), CPU/memory usage, running commands, and associated TTYs.
- **`ps aux | grep root`**: Filters for processes running with `root` privileges. If a root process runs a script or binary that you can modify or manipulate, you can achieve root code execution.
- **`top`**: Displays real-time, dynamic system process activity and resource consumption, allowing you to filter processes interactively (e.g., pressing `u` and typing `root` to monitor root processes).
