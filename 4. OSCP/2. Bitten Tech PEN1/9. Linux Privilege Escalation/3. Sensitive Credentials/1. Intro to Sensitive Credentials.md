Sensitive Credentials
▸ OS and applications often store clear text, encoded or hashed
credentials on disk or memory.
▸ Common locations for sensitive data:
▹ Configuration files
▹ Bash history
▹ Hashes in passwd/shadow
▹ In memory credentials
▹ Browser credentials
▹ SSH key

▹ If passwords are typed in command line, they get stored in bash
history
▹ Navigate to user’s home directory, this is where his bash history is
stored in a file

▸ Configuration Files
```
▹ find / -type f –exec grep –i –l “PASSWORD\|PASSWD” {} /dev/null \;
▹ locate config.php
▹ locate password; locate passwd
▹ cat /var/mail/*, cat /var/spool/mail
▹ grep –color=auto –rnw ‘/’ –ie “PASSWORD\|PASSWD” –
color=always 2>/dev/null
```

▸ SSH Keys
▹ Users can make backup of SSH private keys and forget to properly set
permissions
▹ SSH private keys are generally under ~/.ssh/ by the name id_rsa
▹ We can login with the key as that user without a password
▹ ssh –i id_rsa root@<target_ip>


▸ Recently modified files
▹ Find all files modified by other user/service in the last n minutes
▹ find / -mmin –n –xdev 2>/dev/null

▸ Credentials in binary file
▹ Strings command can be used to extract readable information from
compiled programs
▹ strings /tmp/process

▸ Credentials in memory
▹ Cleartext credentials can be found in the memory recently entered by other
users in the session
▹ ps -ef | grep [service name] (find process id)
▹ strings /dev/mem -n10 | grep -ie “PASSWORD|PASSWD”
–color=always
▹ gdb -p [process id)
▹ info proc mappings
▹ dump memory /tmp/process<START_HEAD> <END_HEAD>

▸ Credentials in browser
▹ We can store passwords in browser if we choose to. A common scenario is
when we get a popup from the browser.
▹ laZagne is an open source application to retrieve passwords stored on a
local computer (browser retrieval is one of it’s many functions)
▹ laZagne.py all
▹ laZagne.py browsers
▹ laZagne.py browsers -firefox

### **[Part 1: Introduction to Credential Harvesting & Human Error]**
Hello friends. In this video, we will discuss another very common technique for privilege escalation. I can say that even when other techniques don't work—because some vectors are less common in real-world environments and offer fewer chances of human error—this technique remains extremely reliable. 

For example, as we saw with cron jobs, system administrators often set permissions out of habit to run automated tasks. When systems need to authenticate with other systems, administrators automate these processes to minimize human involvement—such as running server cleanup scripts or automated backups. Everything requires authentication; nothing happens without proper authorization. 

To enable this, administrators create service accounts and scripts that run at set intervals via cron or are executed manually. However, authentication still requires credentials so the receiving system can permit actions. 

The primary challenge with passwords is where and how to store them securely. If stored in cleartext, files must be protected with proper file permissions so only the owner can read them. If encrypted, the encryption keys must be managed. In production and corporate environments, human error is very common across these multi-layered configurations, leading to leaked credentials.

---

### **[Part 2: Why Applications Store Cleartext Passwords]**
Cyber attacks often start with phishing or social engineering to obtain initial credentials. Once an attacker gains a foothold, credentials act as a "beacon of trust" to move further inside the system. Credentials are not limited to user passwords—they include API keys, tokens, OTPs, and authentication secrets.

Applications frequently store passwords in cleartext because machine-to-machine authentication operates without human interaction. Encrypting stored passwords requires managing encryption keys, which is a complex task:
* The encryption key itself must be stored or encrypted securely.
* If hardcoded inside a desktop application, an attacker can reverse engineer the binary to extract the key.
* If transmitted over the network to another service, the key could be intercepted.

Because of key management complexities, developers often assume local file storage is safe from unauthorized access, leading them to store passwords in cleartext locally.

---

### **[Part 3: Extracting Passwords from Configuration Files & Command History (`.bash_history`)]**
Sensitive cleartext data and passwords can be found across several system locations:

1. **Configuration Files**: 
   * Web application configuration files (such as WordPress `wp-config.php`) store database credentials in cleartext so the web server can connect to the database. Finding database passwords often allows logging into the database, extracting user password hashes, or attempting password reuse across system accounts.
   * Service configurations for web servers, mail servers, and database applications in `/etc` or web directories often contain cleartext credentials.

2. **Shell History Files (`.bash_history`, `.zsh_history`)**:
   * When users execute commands on the command line (e.g., `mysql -u root -p password321`), the command and cleartext password get recorded in the shell history file.
   * The history file path is defined by the `$HISTFILE` environment variable. When a session exits, commands append to history files like `.bash_history` or `.zsh_history`.
   * By default, history file permissions are set to `600` (read/write only for the owner). However, if an elevated user previously logged in, typed credentials into the terminal, and exited, any attacker who later gains access as that user can inspect `.bash_history` or `.mysql_history` using wildcards (`cat ~/.bash_history` or `cat ~/*_history`) to retrieve cleartext passwords and API keys.

---

### **[Part 4: Misconfigured SSH Keys & Recently Modified Files]**
3. **SSH Private Keys (`~/.ssh/id_rsa`)**:
   * SSH key pairs are generated using `ssh-keygen` to allow passwordless authentication. This creates a public key (`id_rsa.pub`) sent to the target server, and a private key (`id_rsa`) kept by the user inside `~/.ssh/`.
   * Private keys must strictly have `600` file permissions (readable/writable only by the owner).
   * If an elevated user creates an SSH key pair but sets weak or misconfigured file permissions, another user can read `id_rsa`, copy the private key (`ssh -i id_rsa user@target_ip`), and log in directly as that elevated user without entering a password.

4. **Recently Modified Files & Log Files**:
   * Services, automated scripts, and user login actions frequently append sensitive entries, tokens, or passwords to log files.
   * You can use the `find` command with minute parameters (`find / -mmin -N`) to list files modified within the last *N* minutes to identify active log files or recently updated configuration files containing sensitive data.

---

### **[Part 5: Extracting Strings from Binaries & In-Memory Credentials]**
5. **Inspecting Binary Files (`strings`)**:
   * For compiled binaries, custom executables, or application starters located in user home directories, `/tmp`, or `/var/www`, you can extract human-readable text without full reverse engineering using the `strings` command.
   * Running `strings [binary_name]` extracts ASCII strings, which may reveal hardcoded passwords, secret keys, or internal configurations.

6. **In-Memory Credentials**:
   * Similar to LSASS in Windows, Linux processes may retain cleartext passwords in memory spaces for active sessions to perform non-interactive authentication across services without prompting the user repeatedly.
   * You can list running processes, identify target service PIDs, attach debuggers like `gdb`, or dump process memory (`/proc/[PID]/mem`) to extract in-memory credentials.

---

### **[Part 6: Extracting Stored Credentials via LaZagne]**
7. **Browser & Application Password Vaults**:
   * When users log into web applications (e.g., Facebook, Gmail, internal web portals), browsers prompt to save passwords for auto-completion.
   * **LaZagne** is an open-source post-exploitation tool (available for Linux and Windows) designed to extract stored credentials from multiple local application vaults, including:
     * **Web Browsers**: Firefox, Chrome.
     * **Databases**: PostgreSQL.
     * **Developer & Version Control Tools**: Git, SVN, Maven.
     * **Chat & Mail Clients**: Skype, Thunderbird, Outlook.
     * **System & Network Services**: OpenSSH keys, Wi-Fi profiles, and local password stores.
   * Running `lazagne all` searches across all supported application modules, while targeted flags (e.g., `lazagne browsers -firefox`) scan specific software vaults.
