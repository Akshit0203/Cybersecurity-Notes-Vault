Passwords & Keys - SSH Keys
Sometimes users make backups of important files but fail to secure them with the correct permissions.

Look for hidden files & directories in the system root:

ls -la /

Note that there appears to be a hidden directory called .ssh. View the contents of the directory:

ls -l /.ssh

Note that there is a world-readable file called root_key. Further inspection of this file should indicate it is a private SSH key. The name of the file suggests it is for the root user.

Copy the key over to your Kali box (it's easier to just view the contents of the root_key file and copy/paste the key) and give it the correct permissions, otherwise your SSH client will refuse to use it:

chmod 600 root_key

ssh -i root_key -oPubkeyAcceptedKeyTypes=+ssh-rsa -oHostKeyAlgorithms=+ssh-rsa root@10.114.149.78

### **[Part 1: Discovering Credentials in Configuration Files & `.bash_history`]**

You can use LinPEAS here, but I am not using LinPEAS right now—I will check for passwords manually first. First, let's try configuration files, as we discussed earlier. Configuration files are often located in the web server directory.

Navigating to the web server path at `/var/www/html`, we find no configuration files because no web server or web application software is installed on this host. An `index.html` file exists, but it contains no sensitive data.

Next, check the user's home directory, which may also contain configuration files or history files like `.bash_history`. Inspecting `.bash_history` reveals a command where a previous user typed the MySQL `root` administrative password directly on the command line! Having obtained this password, you can attempt to log in as root to MySQL or test password reuse across system accounts.

---

### **[Part 2: Command Context vs. Process Context for Password Logging]**

This demonstrates why passwords should **never** be entered directly on the command line. Checking the current history file environment variable (`echo $HISTFILE`) confirms that the active shell records all executed commands to this file.

When executing commands like `mysql -u root -p`, if you do not pass the password directly after `-p` on the same line, the utility prompts for the password on a separate line.

```
# BAD PRACTICE (Password is logged in .bash_history):
mysql -u root -pPassword123!

# GOOD PRACTICE (Password prompted interactively, NOT logged in .bash_history):
mysql -u root -p
Enter password:
```

When entered on a separate interactive prompt, input is processed directly inside the application's process memory rather than the Bash shell context, preventing the password from being written to `.bash_history`. The same rule applies to SSH logins.

---

### **[Part 3: Harvesting Credentials from OpenVPN Configurations (`pass.txt`)]**

Beyond shell history, inspect application configuration files located in user home directories. For example, searching user folders reveals an OpenVPN configuration file (`.ovpn`). OpenVPN configuration files store network connection settings.

Inspecting the `.ovpn` file reveals an explicit path directive referencing an external authentication file (`pass.txt`). Opening `pass.txt` discloses cleartext credentials:

```
username: root
password: <cleartext_password>
```

Storing plain text password files for OpenVPN authentication is insecure; configuring certificate-based or private-key-based authentication is far more secure.

Other history files—such as `.nano_history` or `.mysql_history`—should also be inspected, as text editors and database clients log user commands and edited file paths.

---

### **[Part 4: Root SSH Private Key Extraction (`id_rsa`) & Key-Based Auth]**

Next, evaluate **SSH Keys** for privilege escalation. In the current normal user's home directory, no `.ssh` folder exists. However, to escalate privileges to `root`, check if root's SSH private key (`/root/.ssh/id_rsa`) can be read due to weak file permissions.

Attempting to read `/root/.ssh/id_rsa` directly yields a `"Permission denied"` error. However, if root's RSA private key (`id_rsa`) is discovered in a backup folder, web directory, or world-readable location, you can copy the key text and save it to your local attacking machine as `id_rsa`.

To authenticate using an SSH private key:

1. **Set Strict Key Permissions**: Change file permissions on your local attacking machine to `600` (`chmod 600 id_rsa`), or OpenSSH will reject the key.
2. **Execute SSH Key Login**:
    
    ```
    ssh -i id_rsa root@10.8.63.160
    ```
    
3. **Troubleshoot Legacy Key Algorithms**: If OpenSSH returns a `"No mutual signature algorithm supported"` error due to legacy RSA key deprecation, append the public key type option:
    
    ```
    ssh -i id_rsa root@10.8.63.160 -o PubkeyAcceptedKeyTypes=+ssh-rsa
    ```
    

If the private key is unencrypted (no passphrase required), key-based authentication grants an immediate, passwordless `root` shell.

### **[Part 5: Automated Credential Harvesting via LinPEAS]**

Running automated enumeration scripts like **LinPEAS** (`./linpeas.sh`) automates searching for leaked credentials and sensitive configuration files.

LinPEAS scans system configurations and highlights high-confidence findings in **red and yellow**:

- It flags `PermitRootLogin` SSH settings.
- It highlights OpenVPN configuration files and extracted cleartext password files (`pass.txt`).
- It identifies active cron jobs, Tmux sessions, Redis passwords, Neo4j databases, and unprotected SSH directories.
- It searches for keywords like `pw` and `pass` across user home directories.
