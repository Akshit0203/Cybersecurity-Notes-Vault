# Introduction to SUID & SGID — Linux Privilege Escalation

> [!tip] Core Idea
> **SUID** (Set User ID) lets a program run with its **file owner's** privileges, regardless of who executes it. If a root-owned binary has SUID set, any user who runs it gets root-level execution — making misconfigured SUID binaries a prime privilege escalation target.

---

## SUID & SGID Explained

| Permission | Meaning | Effect |
| --- | --- | --- |
| **SUID** (`u+s`) | Set User ID | Program runs with the **owner's** effective UID |
| **SGID** (`g+s`) | Set Group ID | Program runs with the **group owner's** effective GID |
| **Sticky Bit** (`+t`) | Restricted deletion | Only file owner can delete files in the directory |

### Numerical Permission Bits

| Bit | Value | Standard Equivalent |
| --- | --- | --- |
| SUID | `4` | `chmod 4755` |
| SGID | `2` | `chmod 2755` |
| Sticky | `1` | `chmod 1755` |

### How to Identify SUID in `ls -l`

```
-rwsr-xr-x 1 root root ... /usr/bin/example
   ^
   SUID bit (s in owner execute position)
```

## Real User ID vs Effective User ID

- **Real UID (RUID)**: The actual user who launched the process (e.g., UID 1000)
- **Effective UID (EUID)**: The privilege level used for access checks during execution
- When a SUID binary runs, the EUID is updated to the **file owner's** UID (e.g., root = 0), while the RUID stays as the invoking user

```
Normal user (UID 1000)
   │
   │ executes SUID program
   ▼
SUID program (owned by root)
   │
   │ EUID → 0 (root)
   ▼
Runs with root privileges
```

## Legitimate SUID Use Cases

Not all SUID binaries are exploitable — many are required for normal system operation:

| Binary | Why It Needs SUID |
| --- | --- |
| `ping` | Needs raw ICMP socket access (kernel restriction bypass) |
| `passwd` | Must write new password hashes to root-owned `/etc/shadow` |
| `sudo` | Must be able to execute commands as root |

---

## SUID vs `sudo`

| | SUID | `sudo` |
| --- | --- | --- |
| **What it is** | A permission bit on a file | A utility program (with its own SUID bit) |
| **Where it's defined** | File metadata (`chmod u+s`) | `/etc/sudoers` rules |
| **Granularity** | None — runs the whole binary as the owner | Fine-grained — can restrict to specific commands, arguments, paths |
| **Authentication** | None required | Usually requires user's password |
| **Security risks** | Misconfigured binaries | Software vulnerabilities in `sudo` itself |
| **Scope** | Anyone with execute permission | Only users listed in sudoers |

```
SUID: permission attached to the PROGRAM
  /usr/local/bin/myprogram ← SUID root
  → anyone who executes it runs it as root

sudo: permission attached to the USER + COMMAND relationship
  user → sudoers rule → can run /usr/bin/find as root
  → only that specific user can elevate
```

## Finding SUID Binaries

```bash
# Find all SUID files owned by root
find / -type f -perm -4000 2>/dev/null
find / -user root -perm /4000 2>/dev/null

# Find both SUID and SGID files with details
find / -type f -a \( -perm -u+s -o -perm -g+s \) -exec ls -l {} \; 2>/dev/null
```

> [!important]
> Not all SUID binaries are exploitable. Focus on **custom or uncommon** binaries — default system binaries (like `passwd`, `ping`, `mount`) are generally safe. Use [GTFOBins](https://gtfobins.github.io/) to check if a binary has known SUID exploitation techniques.

---

## The `-p` Flag

When spawning a shell from a SUID context, always use:

```bash
/bin/bash -p
```

The `-p` (privileged mode) flag tells Bash to **preserve the elevated SUID privileges** instead of dropping them back to the unprivileged user. Without `-p`, Bash resets the EUID to the RUID, losing root access.

## SUID PrivEsc Vectors Summary

| Vector | Condition | Method |
| --- | --- | --- |
| **Known Exploits** | SUID binary has a CVE | Search Exploit-DB, Google, GitHub |
| **Shared Object Injection** | Binary loads `.so` from user-writable path | Create malicious `.so` at that path |
| **Environment Variables / PATH** | Binary calls program without absolute path | Place malicious binary earlier in `$PATH` |
| **Shell Features (Bash < 4.2-048)** | Binary calls program with absolute path | Define Bash function with same name as the path |
| **Shell Features (Bash < 4.4)** | Binary invokes Bash | Abuse `PS4` debugging variable |
| **GTFOBins** | Binary has known breakout | Check GTFOBins for the binary |
