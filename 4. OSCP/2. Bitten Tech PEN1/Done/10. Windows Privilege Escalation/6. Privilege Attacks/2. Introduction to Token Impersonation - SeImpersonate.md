# Token Impersonation — SeImpersonatePrivilege

## What is `SeImpersonatePrivilege`?

> **`SeImpersonatePrivilege` = permission for a process to impersonate another user's security token.**

A **security token** is a kernel-managed object representing the identity and privileges of a Windows process/thread.

```
Low-privileged process
        │
        │ Token
        ▼
  NT AUTHORITY\LOCAL SERVICE
```

If that process has `SeImpersonatePrivilege`, it can **impersonate a more privileged token** under certain conditions.

---

## How Impersonation Works

### Process vs Thread Tokens

| Level | Token Type | Behaviour |
| --- | --- | --- |
| Process | **Primary token** | Stays as the original account identity for the process lifetime |
| Thread | **Impersonation token** | Temporarily assigned for an elevated task, then removed |

A process can hold **two tokens simultaneously** during impersonation:
1. The original account token (process-level)
2. A temporary impersonated token (thread-level)

### The API Chain

Windows uses API calls to manage impersonation:

- **`ImpersonateLoggedOnUser`** — acquire another user's token and assume their security context
- **`AcceptSecurityContext`** — complete NTLM authentication and obtain the resulting token handle
- **`CreateProcessWithTokenW`** — launch a new process using the acquired elevated token

### COM (Component Object Model) Role

COM registers all system objects and resources. When you log on, COM grants a security token defining your permissions. The privileged token used during impersonation is granted through COM.

## Why This Enables Privilege Escalation

```
LOCAL SERVICE  →  SeImpersonatePrivilege  →  Can impersonate tokens
        ↓
Potato technique triggers a privileged Windows authentication interaction
        ↓
SYSTEM security token becomes available to impersonate
        ↓
CreateProcessWithTokenW  →  SYSTEM shell
```

> [!IMPORTANT]
> `SeImpersonatePrivilege` itself does not automatically make you SYSTEM. It provides the **capability** that Potato-family exploits abuse to steal a SYSTEM token.

### Why SYSTEM Specifically?

Many Windows services run as `NT AUTHORITY\SYSTEM`. If a SYSTEM service performs the relevant authentication interaction, the resulting security context is associated with the SYSTEM account → your process/thread impersonates it → full SYSTEM privileges.

---

## How Potato Exploits Work (NTLM Relay via COM/RPC)

All Potato exploits share the same fundamental mechanism — they differ only in **how they trigger the privileged authentication**:

```
SeImpersonatePrivilege
        ↓
Trigger privileged authentication/IPC behaviour
        ↓
Capture privileged token
        ↓
Impersonate token
        ↓
SYSTEM
```

### Detailed NTLM Relay Attack Flow

1. **Rogue Server Setup** — The exploit spawns a fake COM/RPC server on a high-numbered TCP port (e.g., port 6000).
2. **Coercing Authentication** — A malicious string/object is sent to a high-privileged SYSTEM process/service to unmarshal. The string contains a connection string pointing to our fake COM server.
3. **Triggering NTLM Negotiation** — Resolving this connection string forces the SYSTEM process to initiate NTLM authentication to our listener.
4. **Relaying to Local RPC (Port 135)**:
   - SYSTEM process sends NTLM **Type 1 (Negotiate)** → our fake server
   - We forward Type 1 → legitimate local RPC server on **port 135**
   - RPC server returns NTLM **Type 2 (Challenge)** → we relay back to SYSTEM process
   - SYSTEM process computes and returns NTLM **Type 3 (Authenticate)** response
5. **Acquiring the SYSTEM Token** — We forward Type 3 to RPC, call `AcceptSecurityContext`. COM issues a high-privileged SYSTEM token handle.
6. **Process Creation** — With `SeImpersonatePrivilege`, we capture this token and call `CreateProcessWithTokenW` → **NT AUTHORITY\SYSTEM** shell.

## Token Behaviour — Key Concepts

### Tokens Don't Expire on Their Own

A Windows access token doesn't expire just because it was given to a service. It is a **kernel-managed security object** (like an ID badge, not a temporary Wi-Fi password).

```
Service has SYSTEM badge
        ↓
You temporarily get permission to act using that identity
        ↓
A new process can be created under that security context
```

### Windows Authorisation Checks

When a thread with an impersonation token accesses a resource:

```
Thread → "Open this file"
        ↓
Windows security check:
  ├── Which token is being used?
  ├── What user/groups does it contain?
  └── Does that token have permission?
```

Windows checks the **token currently attached to the thread** — it does NOT track:
> "This token originally belonged to Service X, so I'll reject it because Service X isn't using it anymore."

Once you create a new process using the privileged security context, that new process has its **own** token — independent of the original service.

```

If you see:

```

## Where Service Accounts Get `SeImpersonatePrivilege`

Windows services frequently need to perform actions **on behalf of another user**:

```
User → request → Windows Service → perform action as user → User's resources
```

Common accounts where you encounter it:

```
NT AUTHORITY\LOCAL SERVICE
NT AUTHORITY\NETWORK SERVICE
IIS AppPool accounts
SQL Service accounts
```

## Mitigations & Remediation

### 1. Remove `SeImpersonatePrivilege` Where Unnecessary

```
Local Security Policy
 → Local Policies
   → User Rights Assignment
     → Impersonate a client after authentication
```

Review which accounts are assigned to it. If a service doesn't need impersonation, **remove the privilege**.

### 2. Least-Privilege Service Accounts

Don't run services as `SYSTEM` when a dedicated, restricted service account suffices.

### 3. Keep Windows Patched

Potato techniques depend on specific Windows authentication/IPC behaviours. Regular updates reduce the attack surface — especially critical for older variants like JuicyPotato.

### 4. Harden COM/DCOM/RPC

Review unnecessary exposure or misconfiguration of these components (but don't blindly disable them — many legitimate services depend on them).

### 5. Monitor for Suspicious Escalation

Detect:
- Service account → unexpected child process (`cmd.exe`, `powershell.exe`) → SYSTEM
- Correlate via EDR/SIEM: process creation, account identity, privilege use, parent-child relationships

### OSCP-Style Remediation Answer

> **Remove `SeImpersonatePrivilege` from service accounts that do not require it, run services under the least-privileged appropriate account, keep Windows patched, and monitor suspicious token impersonation / process creation.**

---

## Windows Mitigations Over Time

Microsoft has introduced restrictions — such as preventing COM servers from communicating over arbitrary high-numbered ports and requiring port 135 — but these attack vectors persist because they rely on fundamental Windows architectural components (COM, DCOM, RPC).
