# Introduction to Pivoting and Port Redirection

## What is Pivoting?

Pivoting is a technique to **move between networks** inside an organization by routing traffic through a compromised host that has access to multiple subnets.

> **Port forwarding moves network traffic from one place to another so that you can reach a service that you normally cannot reach.**

### Why Pivoting is Needed

- Organizations distribute infrastructure across **multiple private subnets**, each protected by dedicated firewalls with strict ingress/egress port filtering.
- After compromising a machine, you enumerate its IP, subnet, and reachable hosts — but targets rarely sit on a single network.
- Essential ports (HTTP 80, MySQL 3306, SMB 445, RDP 3389, etc.) are typically **blocked** by perimeter firewalls.
- A **dual-homed pivot host** has two interfaces/routing tables — one for the external network and one for the internal isolated network.

- You **cannot directly reach** `10.10.20.50:3306` — the internal server isn't exposed to your Kali.
- The compromised web server **can** reach it → that's where tunneling comes in.

## OSCP Decision Model

When you compromise a machine, ask: **"Who can reach what?"**

```
Kali
  │
  ├──→ Compromised Server ✅
  │
  └──→ Internal Server ❌

Compromised Server
  │
  └──→ Internal Server ✅
```

The compromised server becomes your **pivot point**. Then choose the forwarding method:

| Scenario | Method |
|---|---|
| One specific internal service | **Local forwarding** (`-L`) |
| Need a listening port on the remote side (reverse shells, file delivery) | **Remote forwarding** (`-R`) |
| Need to access many internal hosts/services | **Dynamic forwarding** (`-D`) / SOCKS |

---

## SSH Port Forwarding — Overview

SSH is the most popular tunneling protocol because:
- Firewalls commonly **permit port 22** for remote administration.
- SSH traffic is **encrypted**, so we can encapsulate arbitrary protocol traffic inside SSH packets to bypass perimeter filters.

SSH port forwarding has **three modes**:

| Mode | Flag | Where the Port Opens | Mapping |
|---|---|---|---|
| Local | `-L` | Your Kali machine | One-to-one |
| Remote | `-R` | The remote/pivot machine | One-to-one |
| Dynamic | `-D` | Your Kali machine (SOCKS proxy) | One-to-many |

---

## 1 — Local Port Forwarding (`ssh -L`)

Opens a listening port on the **local (attacker) machine** and forwards all incoming connections through the SSH tunnel to a specified remote host and port.

![534](attachments/Pasted%20image%2020260915194417.png)

### Syntax

```
ssh -L [LOCAL_IP:]LOCAL_PORT:FORWARD_HOST:FORWARD_PORT USER@PIVOT_HOST
```

- **`-L`** — Specifies Local Port Forwarding.
- **`LOCAL_PORT`** — Port opened on the local attacking machine.
- **`FORWARD_HOST`** — Destination target host (`127.0.0.1` on the pivot, or an internal target IP).
- **`FORWARD_PORT`** — Service port on the target (e.g., 80, 3306, 3389).
- **`USER@PIVOT_HOST`** — SSH credentials and IP of the compromised jump host.

### Traffic Flow

```
KALI                         COMPROMISED              INTERNAL
                            SERVER
127.0.0.1:8080
     │
     │
     └──────────────→ 10.10.10.20 ─────────→ 10.10.20.50:3306
                                     
                         forwarded
```

### Two Primary Use Cases

1. **Accessing loopback-only services on the jump host** — Service on `127.0.0.1:456` blocked externally:
   ```
   ssh -L 1234:127.0.0.1:456 user@pivot
   ```

2. **Reaching deep internal targets** — Access `10.10.10.33:80` behind the jump host:
   ```
   ssh -L 8080:10.10.10.33:80 user@pivot
   ```

### Example

```
ssh -L 8080:10.10.20.50:3306 user@10.10.10.20
```

```
Kali
localhost:8080
      ↓
SSH tunnel
      ↓
10.10.10.20
      ↓
10.10.20.50:3306
```

Connecting to `localhost:8080` now reaches the internal MySQL service.

![468](attachments/Pasted%20image%2020260915194958.png)

> **Memorize: Local = the listening port is created on MY machine.**

## 2 — Remote Port Forwarding (`ssh -R`)

Opens a listening port on the **remote SSH server (pivot host)** and forwards connections back through the tunnel to a host/port on the **local (attacker) side**.

![395](attachments/Pasted%20image%2020260915200043.png)

### Syntax

```
ssh -R [REMOTE_IP:]REMOTE_PORT:DESTINATION_HOST:DESTINATION_PORT USER@PIVOT_HOST
```

- **`-R`** — Specifies Remote Port Forwarding.
- **`REMOTE_PORT`** — Listening port opened on the remote pivot server.
- **`DESTINATION_HOST`** — Target host on the local side (typically attacker's `localhost`).
- **`DESTINATION_PORT`** — Local port where the attacker hosts a service or reverse handler.

### Traffic Flow

```
COMPROMISED SERVER:8080
          ↓
        tunnel
          ↓
KALI:9001
```

### Primary Use Cases

- **Exposing local services to internal targets** — Internal target needs a payload from your HTTP server:
  ```
  ssh -R 8000:127.0.0.1:80 user@pivot
  ```
- **Catching reverse shells** — Internal target can't connect directly to your Kali. Forward a remote port on the jump host back to your Netcat/Metasploit listener (operates similarly to Ngrok).

> **Memorize: Remote = the listening port is created on the REMOTE machine.**

## 3 — Dynamic Port Forwarding (`ssh -D`) and SOCKS Proxies

Instead of one-to-one port mapping, creates a **SOCKS proxy** — a one-to-many tunnel.

![](attachments/Pasted%20image%2020260915202850.png)

### Syntax

```
ssh -D LOCAL_PROXY_PORT USER@PIVOT_HOST
```

- **`-D`** — Specifies Dynamic Port Forwarding.
- **`LOCAL_PROXY_PORT`** — Local port allocated as a SOCKS proxy (e.g., `9050` or `1080`).

### Traffic Flow

```
                    SSH TUNNEL
KALI                  │
 │                    │
 │ SOCKS :9050        │
 ↓                    ↓
Browser/tool → compromised server → internal network
                                      │
                    ┌─────────────────┼──────────────┐
                    ↓                 ↓              ↓
                 10.20.1.5         10.20.1.8       10.20.1.20
                 :80               :445             :3306
```

### Advantages

- **Full network sweeps & multi-port scanning** — Routes all traffic dynamically to any IP/port reachable by the pivot host.
- **Proxychains integration** — Prefix tools with `proxychains`:
  ```
  proxychains nmap -sT -Pn 10.10.10.0/24
  ```
- **Bypass egress restrictions** — Tunnel web traffic out through an internet-connected SSH pivot.

### Why Dynamic is Powerful (OSCP)

With **local forwarding**, you'd create individual tunnels for each service:

```
8080 → 10.10.20.10:80
8445 → 10.10.20.15:445
2222 → 10.10.20.20:22
3306 → 10.10.20.25:3306
```

With **dynamic forwarding**, a single SOCKS proxy handles all of them:

```
Kali
  │
  └── SOCKS :9050
          ↓
     compromised host
          ↓
     internal network
```

> **Memorize: Dynamic = SOCKS proxy, choose destinations dynamically.**

## Quick Reference — Memory Tricks

> **Local = port on me.**
> **Remote = port on them.**
> **Dynamic = SOCKS proxy, choose destinations dynamically.**

SSH flags:

```
-L = Local
-R = Remote
-D = Dynamic
```

### Don't Confuse Port Forwarding with VPN

| VPN | Port Forwarding |
|---|---|
| Gives your machine a full route into another network | More targeted — tunnel through compromised host to a specific service/network |

> In OSCP, **port forwarding becomes especially important after you compromise a machine that has access to an internal network your Kali cannot directly access.**
