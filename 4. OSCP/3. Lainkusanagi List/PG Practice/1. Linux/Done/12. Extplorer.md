# Extplorer — Proving Grounds

> [!abstract] Summary
> Extplorer serves WordPress on port 80 and an **eXtplorer** file manager at `/filemanager`. The foothold is a PHP webshell in the web root (`wp-admin/simple-backdoor.php`), giving code execution as `www-data`. Reading eXtplorer's `.htusers.php` config leaks a **bcrypt** hash for the user `dora`, cracked to `doraemon`. As `dora` — who is in the **`disk`** group — `debugfs` reads the raw filesystem device and dumps `/etc/shadow`; the root **sha512crypt** hash cracks to `explorer`, giving root via `su`.

**Target:** `192.168.142.16`

## Methodology

1. Scan all TCP ports; identify WordPress + the eXtplorer file manager.
2. Get a `www-data` webshell in the web root.
3. Read eXtplorer's `.htusers.php`, crack `dora`'s bcrypt hash → `doraemon`.
4. `su dora`; note membership of the `disk` group.
5. Use `debugfs` (disk-group read of the block device) to dump `/etc/shadow`.
6. Crack root's sha512crypt hash → `explorer`; `su root`.

The site is a half-installed WordPress (it redirects to `setup-config.php`) with an **eXtplorer** file manager at `/filemanager`. eXtplorer ≤ 2.1.14 has a public auth-bypass + file-upload RCE (EDB-51067 / EDB-24018) — it, or a directly-dropped webshell, is the way to get a file into the web root.

## Foothold — webshell as `www-data`

A PHP webshell is placed in the web root (here `wp-admin/simple-backdoor.php`, the classic "Simple PHP backdoor by DK"). After uploading the payload, browse to its location to execute it — a reverse shell is triggered by requesting its path directly, while a command webshell takes a `cmd` parameter:

```
# reverse shell — request the uploaded file to execute it
http://192.168.142.16/shell.php

# command webshell — pass the command in the cmd parameter
http://192.168.142.16/shell.php?cmd=id
```

Confirming code execution:

```
curl http://192.168.142.16/wp-admin/simple-backdoor.php?cmd=whoami
# <pre>www-data </pre>
```

## Privilege escalation — `disk` group + `debugfs`

> [!info] Why `disk` group = root
> Membership of the `disk` group grants read/write access to the raw block devices under `/dev`. `debugfs` is an ext2/3/4 filesystem debugger that can read any file on a device directly — bypassing file permissions. So a `disk`-group user can read `/etc/shadow` (and in fact overwrite anything) by talking to the block device, which is effectively root-level filesystem access.

Dump `/etc/shadow` straight off the LVM block device:

```
debugfs -R "cat /etc/shadow" /dev/mapper/ubuntu--vg-ubuntu--lv 2>/dev/null
```

This yields the root sha512crypt hash:


## Lessons learned

- A `/filemanager` that is **eXtplorer** is a known RCE target (≤ 2.1.14 auth bypass + upload). Even a half-installed WordPress can be the delivery mechanism for a webshell.
- Application config files hold credentials: eXtplorer's `.htusers.php` leaked `dora`'s bcrypt hash. Always read app config after a web foothold.
- `id` matters — the `disk` group (like `lxd`, `docker`, `shadow`, `sudo`) is a privileged group. `disk` → `debugfs` reads any file off the raw device, which is a clean path to `/etc/shadow`. Don't stop at `sudo -l`; check group membership.
- The lesson the author noted: it's a habit to only check `sudo -l`, pspy and SUID — **also check group privileges**.
