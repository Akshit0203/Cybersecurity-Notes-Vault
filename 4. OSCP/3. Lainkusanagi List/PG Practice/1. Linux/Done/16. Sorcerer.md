# Sorcerer — Proving Grounds

> [!abstract] Summary
> Sorcerer runs a file-archive web app on port **7742** whose `/zipfiles/` directory leaks backup archives. One archive contains the user **`max`**'s `.ssh` directory — a private key (`id_rsa`), an `authorized_keys` that forces every SSH login through a restrictive `scp_wrapper.sh`, and the wrapper script itself. Because SSH still honours key-based auth, we upload a **modified `authorized_keys`** (same public key, restrictions stripped) using legacy-protocol `scp -O`, then SSH in as `max` for a real shell. Privilege escalation is a **SUID `start-stop-daemon`** binary, abused with the standard GTFOBins technique for a root shell.

**Target:** `192.168.143.100`

## Methodology

1. Scan all TCP ports; note NFS/rpcbind, the SORCERER app on 7742, and Tomcat on 8080.
2. Brute-force the 7742 web root and find `/zipfiles/`.
3. Download the archive leaking `max`'s `.ssh` (id_rsa, authorized_keys, scp_wrapper.sh).
4. Bypass the SCP wrapper by uploading a de-restricted `authorized_keys` with `scp -O`.
5. SSH in as `max`; escalate via SUID `start-stop-daemon`.

## Foothold — bypassing the SCP wrapper

IF YOU GET THESE 3 FILES : 
- `id_rsa` or another private key file — potentially lets us authenticate as `max`.
- `authorized_keys` — tells SSH which public keys are allowed to authenticate as `max`.
- `scp_wrapper.sh` — a custom script that controls or restricts SCP operations.

> [!info] What the wrapper does
> `max`'s `authorized_keys` pins the key to `command="/home/max/scp_wrapper.sh",no-port-forwarding ...`. That `command=` forces *every* SSH session using this key to run `scp_wrapper.sh` instead of a shell — the wrapper only allows `scp`-style operations. We can't get an interactive shell directly, but we *can* use `scp` (which the wrapper permits) to **overwrite `authorized_keys` itself** with a version that has no restrictions.

We make a modified copy:
```
cp extracted/max/.ssh/authorized_keys .
gedit authorized_keys
```
Suppose the original entry is :
```
command="/home/max/scp_wrapper.sh",no-port-forwarding ssh-rsa AAAAB3...
```
The modified entry should retain the actual public key but remove the restrictions:
```
ssh-rsa AAAAB3...
```
The public key itself is unchanged. We're removing the options that force the SSH session to execute the wrapper instead of allowing a normal shell.

then give permission to the ssh key : 
```
chmod 600 id_rsa
```

First, try the normal command:
```
scp -i id_rsa authorized_keys max@$IP:/home/max/.ssh/authorized_keys
```
Modern OpenSSH versions use SFTP as the default transport for SCP.
However, the target's custom wrapper is designed around the older SCP protocol. The SFTP request doesn't follow the protocol the wrapper expects.

Therefore, use:
```
scp -O -i id_rsa authorized_keys max@192.168.143.100:authorized_keys
```
The `-O` option means:
```
-O = Use the legacy SCP protocol instead of SFTP.
```
This makes the transfer compatible with the target's SCP wrapper.
The modified `authorized_keys` file is now uploaded to the target.

Now try:
```
ssh -i id_rsa max@192.168.143.100
```
The authentication process reads the updated `authorized_keys` file.

Because the uploaded `authorized_keys` no longer has the `command=` restriction, SSH gives a normal interactive shell as `max` (and the user flag).

## Privilege escalation — SUID `start-stop-daemon`

Enumerate SUID binaries:

```
find / -perm -4000 -type f 2>/dev/null
```

LinPEAS/`find` flags the SUID bit set on **`/usr/sbin/start-stop-daemon`**. Per GTFOBins, a SUID `start-stop-daemon` can start an arbitrary program while keeping the owner's (root) privileges:

```
start-stop-daemon -n $RANDOM -S -x /bin/sh -- -p
id
```

`-S -x /bin/sh -- -p` launches `/bin/sh -p` (preserving the elevated effective UID) as root. `id` confirms `euid=0`, and `/root/proof.txt` is now readable.

## Lessons learned

- A directory-listing of backups (`/zipfiles/`) is an information-disclosure jackpot — download everything and look for `.ssh`, config, and credential files. The `/zipfiles/` content is *not* a privesc vector itself; its job is to leak `max`'s key + wrapper.
- A `command="..."` option in `authorized_keys` only restricts the *session*, not what the key can do. If you can write back to `authorized_keys` (via the one thing the wrapper allows — `scp`), you can strip the restriction and get a shell.
- Modern OpenSSH's `scp` defaults to SFTP; a legacy SCP wrapper needs `scp -O` to speak the old protocol. Remember `-O` when `scp` to a restricted target silently fails.
- After any shell: enumerate SUID binaries. `start-stop-daemon`, like many init-related binaries, is on GTFOBins — a SUID copy is instant root.
