## Register the SPN for SQLService

Open **Command Prompt as Administrator**.

![](image-251.png)

Register a Service Principal Name (SPN) for the SQL service account:

```cmd
setspn -a Windows-DC/SQLService.DC.local:60111 DC\SQLService
```

![](image-252.png)

### What is an SPN?

An SPN (Service Principal Name) is a unique identifier that ties a **service endpoint** to an **AD account**. Creating the `SQLService` account alone only tells AD the account exists — it doesn't tell AD what service it runs, on which server, or on which port. The SPN creates that mapping.

### Command Breakdown

| Part | Meaning |
| ---- | ------- |
| `setspn` | Windows tool for managing SPNs |
| `-a` | **Add** a new SPN |
| `Windows-DC/SQLService.DC.local:60111` | The service name: server `Windows-DC`, service `SQLService.DC.local`, port `60111` |
| `DC\SQLService` | The AD account that **owns** this service |

### Why Kerberos Needs SPNs

When a user requests a service ticket:

> "Give me a ticket for `Windows-DC/SQLService.DC.local:60111`"

The Domain Controller looks up which account owns that SPN, finds `DC\SQLService`, and issues the ticket encrypted with that account's password hash. **Without an SPN, no ticket can be issued** — this is also why SPNs are critical for Kerberoasting attacks later.

**Before the command:** AD knows `SQLService` exists, but not what service it represents.
**After the command:** AD maps `Windows-DC/SQLService.DC.local:60111` → `DC\SQLService`.

### Verify SPNs

Query all SPNs in the domain:

```cmd
setspn -T DC.local -Q */*
```

| Flag | Meaning |
| ---- | ------- |
| `-T DC.local` | Search in domain `DC.local` |
| `-Q` | Query/search |
| `*/*` | Match all SPNs (wildcard) |

![](image-253.png)

Confirm the output includes:

```
CN=SQL Service,CN=Users,DC=DC,DC=local        Windows-DC/SQLService.DC.local:60111
```

✅ Domain = `DC.local`
✅ SQLService SPN is registered

## Create a Group Policy — Disable Windows Defender

Open the Start menu → search for **Group Policy Management**.

![](image-254.png)

### What is a GPO?

A **Group Policy Object (GPO)** is a set of Windows rules/settings applied to computers or users. Examples: force password complexity, disable Control Panel, run a startup script, map a network drive, install software, set wallpaper.

A GPO has two steps:
1. **Create it** — the policy exists in AD but affects nobody yet
2. **Link it** — attach the policy to a domain, OU, or site so it applies to the objects within

### Create the GPO

Expand the forest → **DC.local**. Right-click **DC.local** → **Create a GPO in this domain, and Link it here**. Name it `Disable Windows Defender`.

![](image-255.png)

![](image-256.png)

![](image-257.png)

### Edit the GPO

Right-click the new GPO → **Edit**.

![](image-258.png)

Navigate to: **Computer Configuration** → **Policies** → **Administrative Templates** → **Windows Components** → **Microsoft Defender Antivirus**.

![](image-259.png)

> [!NOTE]
> In Server 2019 and earlier, this is called **Windows Defender Antivirus** instead of Microsoft Defender Antivirus.

![](image-260.png)

Double-click **Turn off Microsoft Defender Antivirus** → set to **Enabled** → **Apply** → **OK**.

![](image-261.png)

Close the editor. Right-click the GPO → **Enforced** to ensure the policy is enforced domain-wide. Any computer that joins the domain (or receives a policy refresh) will have Defender disabled.
