# Writing a Report 1 — Exam Note-Taking Skeleton

Building the note-taking structure used while solving machines, demonstrated on the TryHackMe machine **Kenobi** (a very realistic, OSCP-like box you can solve on your own). The walkthrough was recorded in the exact format required by OffSec: screenshots, commands, terminal outputs, and the proof flag files are all logged.

---

## OneNote Organization

The master notebook is named **OSCP**, with a master section named **Exam**. Under **Exam** are two sub-sections:

1. **AD (Active Directory)**
2. **Individual Machines** (the three standalone machines)

Creating these exact sections lets you organize similar notes for easy reference during the exam.

---

## Documenting the Attack Chain & Raw Artifacts

Raw notes and command sequences were originally saved in **Sublime Text**, then transferred into OneNote. Under **Exam → Sample** the recorded Kenobi notes contain:

- **Exploits** — documented here. One exploit was actively used; a second was downloaded but ultimately not utilized.
- **Markdown commands file (`commands.md`)** — a dedicated markdown file containing all commands for better readability.
- **Reconnaissance** — the recon commands, beginning with the **Nmap scan** (always the starting point). The full scanning command is run against the target IP (just swap in your target IP). The exact command is recorded, and the complete raw Nmap output is copied and pasted into the notes.
- **Additional recon commands** — listing SMB shares, accessing SMB shares, downloading log files, enumerating NFS shares — all documented under the recon phase.
- **Initial Access** — the specific methods/exploits used, executed manually. All subsequent commands documented in sequence.
- **Privilege Escalation** — how the system was enumerated, the vulnerability identified, and exploited to escalate.

Kenobi is a straightforward box, representative of the individual machines on the exam. Active Directory notes follow the same manner using the AD structure.

Also maintained: the `commands.md` file with every executed command, plus a dedicated **flags file** listing the `user.txt` and `root.txt` proof hashes. Recording flags is essential — you must paste them into the exam control panel, document them in the final report, and easily verify no flag was misplaced or submitted into the wrong field.

## Kenobi Attack Path Summary (PoC)

A concise walkthrough file (the **Proof of Concept summary**) outlines the entire attack sequence in a short, report-ready format:

1. **Reconnaissance (Samba / SMB on Port 445)** — Nmap revealed Samba on Port 445. Enumerating Samba shares exposed a non-standard share. Browsing it revealed a log file, which was downloaded. Analyzing the log revealed that an SSH private key (`id_rsa`) for user `kenobi` was located at `/home/kenobi/.ssh/id_rsa`, but there were no direct permissions to read it.
2. **ProFTPD Exploitation (`mod_copy`)** — The log file and port scan revealed FTP running a specific version of **ProFTPD**. That version has an exploit in the `mod_copy` module allowing copying files from any arbitrary directory to another destination on the filesystem. To read the user's private key, FTP had to be combined with another service.
3. **NFS Mount Exploitation (Port 111 / RPC)** — The RPC service revealed that `/var` was shared via NFS and could be mounted remotely. Since `/var` could be mounted, any files within it could be read. Using the ProFTPD `mod_copy` exploit:
   ```
   SITE CPFR /home/kenobi/.ssh/id_rsa
   SITE CPTO /var/tmp/id_rsa
   ```
   This copied the SSH private key into the writable `/var/tmp` directory.
4. **Initial Foothold (SSH)** — Mounted the NFS `/var` share remotely on the local machine and copied the `id_rsa` private key. After setting proper permissions (`chmod 600 id_rsa`), authenticated via SSH as user `kenobi`, establishing the initial foothold and capturing `user.txt`.
5. **Privilege Escalation (SUID $PATH Hijacking)** — Discovered a custom C binary with SUID permissions: `/usr/bin/menu`. Running it presented a menu that executed system commands. Inspecting it with the `strings` utility revealed it called commands using **relative** program names rather than absolute file paths — making it vulnerable to **$PATH hijacking**. Created a custom malicious script under the same command name in `/tmp`, prepended `/tmp` to the active `$PATH`, and executed the SUID binary. It ran the malicious script instead of the legitimate utility, granting an interactive **root** shell and allowing capture of `root.txt`.

## Screenshot Strategy & Flameshot (Kali Linux)

All steps were documented in Sublime Text, with screenshots saved into a dedicated `screens/` directory — every step in the attack chain has an associated screenshot ready to insert into the report. On the screenshots, **red rectangular boxes** are drawn around critical output areas to highlight key findings.

For capturing and annotating on Kali Linux, use **Flameshot** (on Windows, the Snipping Tool provides basic editing). Install via APT:

```
sudo apt install flameshot
```

Launch it and send it to the background:

```
flameshot &
```

An icon appears in the top-right notification tray. Click it, then click-and-drag across any area to snip it.

> [!tip] Always snip the full command prompt, the executed command, and the complete output together.

Flameshot's built-in annotation tools:
- Draw highlight lines or freehand annotations.
- Draw **rectangular boxes** around text to highlight commands or IP addresses (clean and professional).
- Blur or hide sensitive data.
- Change annotation colors by right-clicking (red, black, or custom).
- Draw circles, add text, or copy directly to the clipboard.
- Save with the save icon or **`Ctrl + S`**, directly into your project's screenshot directory.

## Note-Taking Architecture (Standalone vs. Active Directory)

Under **Individual Machines**, maintain separate sections for the three standalone targets. During the exam, label them by their **target IP addresses** (e.g. `10.10.15.14`) rather than box names, so you can tell which machine is which. Replicate across Machine 1, Machine 2, Machine 3.

Each machine's notes are divided into three core phases (mirroring OffSec's required structure):
1. **Reconnaissance**
2. **Initial Access**
3. **Privilege Escalation** (with priv-esc recon folded into this phase)

Dedicated pages per phase:
- **Recon page** — Nmap scan command, full raw scan output, all auxiliary enumeration commands, step-by-step walkthrough notes, and annotated screenshots embedded beneath each point.
- **Initial Access page** — exact exploit commands, walkthrough notes, screenshots, and the **user flag** proof.
- **Privilege Escalation page** — priv-esc commands, exploitation walkthrough, annotated screenshots, and the **root flag** proof.

When compiling the final report, this complete skeleton means you simply transfer the text, expand the explanations slightly, and drop in your images — no writing from scratch.

For **Active Directory**, the structure is identical with one additional section: **Post-Exploitation / Lateral Movement** (credential dumping via Mimikatz, DCSync, Pass-the-Hash, pivoting between workstations and the Domain Controller).

## Mandatory Flag Screenshot Rule & Interactive Shell Requirements

The flag screenshot must always chain commands together:

```
ifconfig && cat user.txt
```

(or `ip a` / `ipconfig` alongside reading the flag in the same prompt).

The output must display **both** the target machine's network IP address **and** the contents of the flag file within the **exact same screenshot**. This validates the flag was retrieved directly from the compromised target through an interactive session.

> [!warning] Interactive shell is mandatory
> Proof flags must be retrieved through an **interactive shell** (SSH session or Netcat reverse shell). A **web shell does not qualify** — if you only have a web shell you get no points; you must use it to stage and catch a Netcat reverse shell, then capture your proof.

While a Meterpreter shell is interactive, **Metasploit is permitted on only one single machine** across the entire exam. Netcat across your standalone machines is much better practice. (The author did not use Metasploit once during their own exam and strongly recommends building the habit of not relying on it.)
