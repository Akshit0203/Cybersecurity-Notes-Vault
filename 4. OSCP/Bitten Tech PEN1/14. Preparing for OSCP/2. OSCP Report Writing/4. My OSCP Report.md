## Table of Contents & Typography

Whenever you update headings or add content, **update the entire table field** so all page numbers align before finalizing. The ToC follows the exact structure reviewed earlier, with only minor header differences reflecting the older OffSec logo.

**Typography styling:**
- Body text uses a standard font like **Calibri**.
- Headings are **bold** with standardized numerical indices; the heading font appears distinct and slightly heavier (the template default).
- You have flexibility to adjust fonts for visual appeal, **provided styling is consistent throughout**. Bold, clearly numbered headings paired with slightly smaller, non-bold body text ensures optimal readability.

## Nmap Scan Formatting & Table Spacing

The technical documentation begins with the **Nmap port scan**. An aggressive scan (`nmap -A`) was used to capture all detailed service information and script outputs.

When pasting large command outputs into tables, raw text can appear cramped and cluttered. To make it readable:
- Adjust table properties — row heights, cell sizes, margins.
- Or manually add clean spacing and line breaks.

Giving text sufficient breathing room makes scan data look significantly neater. You can embed terminal screenshots alongside raw scan outputs, concluding the port summary with the list of open ports and services.

---

## Organizing Commands, Outputs & Annotated Screenshots

Keeping commands and outputs visually distinct is essential:
- Place terminal commands inside **shaded code blocks**; keep screenshot backgrounds clean and white.
- Structure each finding by labeling the exact **command** run alongside its corresponding **output**.
- Cite any public exploit references / source links directly beneath the text.
- Format images cleanly: crop unnecessary borders, center the screenshot on the page, eliminate redundant whitespace above and below.
- Explicitly label each step with headings such as **"Command"** followed by **"Output"**.

Clean formatting of these visual elements comes with practice and ensures a polished report.

## Documenting Exploit Code & Highlighting Modifications

Whenever you use an exploit script to achieve execution or establish a shell, paste the **complete exploit code from beginning to end** into your report, in the designated section immediately following your initial access narrative and flag retrieval.

> [!warning] Every modification to the exploit must be explicitly highlighted.
> In the author's report, the custom parameters modified were highlighted — such as setting the target administrative username and password required to add a user. Whether you modify target IPs, port numbers, or shellcode payloads, highlight the altered lines so an evaluator reproducing your exploit can immediately identify what changed.

## Vulnerability Explanations & Payload Staging (`msfvenom`)

Following the exploit code, provide a concise explanation of the underlying vulnerability. The author's report documented the **AlwaysInstallElevated** privilege escalation vector — explaining what the policy represents, how it is configured via registry keys, and why it permits unprivileged users to execute MSI packages with elevated SYSTEM rights.

If your attack involves generating custom reverse shells, document the full creation process:
- The exact **`msfvenom`** command used to generate the payload.
- The target architecture (e.g. 64-bit Windows), payload type, and output format.
- The terminal output verifying successful generation.
- How the payload file was staged on your attacking machine and transferred to the target host.

## Exploitation Execution & AD Pivoting Architecture

Document the execution workflow in sequence: starting the **Netcat listener**, executing the exploit against the target service, and catching the incoming shell callback. The report shows the execution output, verifies the payload file executed, and displays the resulting interactive shell prompt.

The **Active Directory** section introduces greater technical complexity and confidential exam architecture. While specific exam details remain confidential, the overarching methodology mirrors the post-exploitation concepts covered throughout the course.

For network pivoting, clearly document your network routing:
- If using **Chisel**, detail the exact client command executed on the compromised pivot host.
- Document the server listener command executed on your attacking machine.
- Explain how the tunnel was established and which local ports were forwarded to reach internal target services.
- Document post-exploitation steps — extracting hashes via **Mimikatz**, cracking passwords, or performing **Pass-the-Hash** / **Pass-the-Ticket**.

## Machine 1 Compromise & Staging Lateral Movement

Detail what actions were performed on the first machine. Once the initial host was compromised and escalated, internal AD systems were found inaccessible directly from the external attacking machine — requiring a pivot.

- All tools staged on the first machine (enumeration scripts, pivoting binaries) must be documented under that host's post-exploitation section.
- Any password hashes dumped from memory or the local SAM database on Machine 1 are logged here. These credentials provide the initial access vector for Machine 2, eliminating the need to run a new exploitation chain from scratch.

---

## Compromising Machine 2 via Harvested Credentials

The initial access vector for the second AD machine is documented as an **RDP login using credentials harvested from Machine 1**.

After dumping hashes on Machine 1, the NTLM hash was either passed directly or cracked offline to recover the cleartext credential. Once the password was obtained, an interactive **RDP session** was established against Machine 2 as the verified initial foothold.

Documenting this progression clearly demonstrates the lateral movement chain. Once inside Machine 2, local privilege escalation is documented, accompanied by the mandatory screenshot verifying the local proof flag (`local.txt`) alongside the machine's IP address.

---

## Achieving Domain Dominance on the Domain Controller (DC)

In an Active Directory environment, initial access and privilege escalation on the Domain Controller often occur **simultaneously**.

If credentials/hashes harvested from Machine 2 belong to a **Domain Admin**, they can be passed directly to authenticate to the DC. By routing tools like **`psexec`** through the established Chisel port forward or proxychains, the DC was authenticated over SMB.

This immediately returned an interactive shell running as **`NT AUTHORITY\SYSTEM`**. The final step documents capturing the administrative proof flag (`proof.txt`) on the Domain Controller, completing the Active Directory compromise.

## Confidentiality & Concluding Advice

Exposing sensitive exam material carries the risk of certification revocation, so only permissible sections were shared.

Many capable students fail the OSCP **solely due to inadequate reporting** — they possess strong technical exploitation skills but lack professional technical writing and documentation habits.

- Focus heavily on report writing.
- Adhere strictly to the official exam guide.
- Document your steps thoroughly and double-check all requirements before submitting.
- Exam results typically arrive quickly — often within 24 hours to a couple of days.

Practice compiling reports and maintain disciplined documentation habits, and you will pass.
