# Introduction to Persistence & DCSync

> [!abstract] Overview
> Once a domain is compromised, authentication tickets expire quickly, so you need **persistence** to regain high-privilege access later without redoing the whole attack chain. The two most popular persistence techniques are the **Golden Ticket** and **DCSync**.

## Ticket Lifetimes (why persistence is needed)

- A **TGT** is valid for **10 hours** by default.
- A **service ticket (TGS)** is valid for even less — a few minutes to a few hours.

Once tickets expire you'd have to authenticate from scratch. Persistence lets you directly regain your desired level of compromise days or months later, using resources already gathered, instead of re-establishing a foothold, re-proving identity, and re-running every exploitation phase.

## Ways to Persist Administrative Access

- Dump `ntds.dit`
- Creation of a domain admin account
- Creation of a **Golden Ticket**
- Creation of a **Skeleton Key**
- Use of **DCSync / DCShadow**

### Golden Ticket as persistence (recap)

Forge a custom TGT locally on behalf of an administrator with a lifetime up to **10 years**. At any point in those 10 years, load the forged TGT into memory and use tools like PsExec or Pass-the-Ticket to spawn a Domain Admin shell — no re-authentication or re-exploitation needed.

## DCSync

> [!summary] One-liner
> **DCSync = abuse AD replication permissions → retrieve password hashes.** It tricks AD into handing over password hashes by pretending to be a Domain Controller performing replication.

### Why replication exists (DC redundancy)

- For redundancy and backup, domains run **more than one** Domain Controller (primary + secondary). If one DC goes down, all authentication and dependent business workflows would halt — the backup keeps processing requests until the primary returns.
- To stay consistent, DCs continuously **synchronize**: one DC requests updated object details (new passwords, new objects, etc.) from another.

### The design flaw

- For synchronization, a DC may request an update for an object from another DC, but **that request has no verification of the source**.
- AD assumes any entity requesting replication is already authenticated and authorized. The request is processed entirely on the assumption that the requesting **SID is valid and privileged** (belongs to an administrative account).
- If a request is submitted with an administrator's SID (e.g. a member of **Domain Admins**), the DC returns the synchronization data — a copy of user password hashes.
- **You don't need to authenticate to / interactively log into any DC** for this attack — but you *do* need valid credentials or an existing security context with the right privileges.

### How it works (step by step)

1. **Multiple DCs** synchronize account information.
2. **Replication**: DCs request account updates from one another.
3. **Abuse permissions**: an attacker with the required replication rights pretends to request this data as a legitimate DC.
4. **Steal hashes**: request password hashes, including Domain Admins and the `krbtgt` account.

### Simple analogy

Two offices share employee records; one is allowed to request password records from the other. An attacker who gains that same authorization abuses the process to obtain those records.

### Why hashes are great for persistence

Password hashes remain valid **indefinitely** until the user manually changes their password. Identifying a user who rarely changes their password and extracting their hash gives a reliable, long-term persistence vector (used via Pass-the-Hash or Pass-the-Ticket).

### Key terms

| Term | Meaning |
|---|---|
| DC | Domain Controller; manages AD authentication and directory data |
| Replication | Synchronizing directory data between DCs |
| DCSync | Abusing directory replication permissions to request credential data |
| Password hash | Cryptographic representation of a password (not plaintext) |
| `krbtgt` hash | Highly sensitive secret used to forge Golden Tickets |

> [!important] Privilege requirement (correction to raw notes)
> You need sufficient privileges — typically the replication rights **`DS-Replication-Get-Changes`** and **`DS-Replication-Get-Changes-All`** (held by Domain Admins). You don't need to log in interactively to a DC, but you need a security context that holds those rights.

## Attack Summary

Initiate a simulated replication request using a valid administrative SID (an account in **Domain Admins**). The targeted DC transmits a complete copy of the requested user password hashes without verification. No interactive DC login is required — the DC blindly trusts the replication request.

Dedicated tools automate this (e.g. Mimikatz `lsadump::dcsync`). See the practical lab for live demonstration.
