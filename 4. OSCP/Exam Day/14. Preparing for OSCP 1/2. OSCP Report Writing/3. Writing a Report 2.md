# Writing a Report 2 — Compiling the Official Template

Actually writing the report end-to-end, using the Kenobi machine as the worked example.

---

## Prerequisites: When to Start Writing

Once the exam is finished and you are confident you have the **70-point passing criteria**, you begin writing. If you do **not** have the flags for at least 70 points, there is no need to write a report — it is a waste of time, because without the flags a report will not pass you. Having 70 points of flags is mandatory; once that threshold is achieved, proceed to report generation.

OffSec provides an official report template — strongly recommended (the author used it): it is the most systematic, structured, and official method. The link in the slide takes you directly to that section of the **OSCP Exam Guide**.

---

## The OSCP Exam Guide & Downloading the Template

Review the OSCP Exam Guide thoroughly (the author read it 50+ times before the exam). It provides all essential guidelines: what to do and not do, which tools/techniques are permitted vs. prohibited, and how to earn **10 bonus points** by solving the course lab exercises.

The immediate concern is the suggested documentation templates:
- On Linux or without a Microsoft Word license → use the **LibreOffice template**.
- Most candidates (and the author) use Windows + Microsoft Word → download the official **Word template** (`OSCP Exam Report`).

Place the downloaded template directly into your local exam project folder for convenient access and editing.

---

## Strict Naming Conventions & the 7z Archive

The final submitted report must be in **PDF** format (exported from your edited Word doc) and named with exact precision:

```
OSCP-OS-XXXXXX-Exam-Report.pdf
```

> [!warning] Not a single character can deviate from this format, or your submission will be rejected.
> Replace `XXXXXX` with your exact 6-digit **OS ID**.

Once exported to PDF, that single PDF must be packaged inside a **7z archive** with the identical naming convention:

```
OSCP-OS-XXXXXX-Exam-Report.7z
```

Open the Word template (`OSCP Penetration Test Report`). **Do not alter the overarching design**, but customize all designated placeholders.

## Documenting Target 1: Title, Vulnerability Description & CVE

Begin the technical exploitation with Target 1 (Kenobi at `10.10.15.14`) under the Independent Challenges section:

- **Section 4.1 Target IP** — set the heading to the target machine's IP address.
- **4.1.1 Initial Access title** — follow professional reporting standards by specifying software, version, vulnerability type, and resulting impact:
  ```
  ProFTPD 1.3.5 - 'mod_copy' Unauthenticated File Copy leading to RCE (CVE-2015-3306)
  ```
- **Vulnerability description** — a concise 2–3 line summary: the `mod_copy` module allows unauthenticated remote clients to copy arbitrary files from one location on the server to another without credentials, using `SITE CPFR` and `SITE CPTO`.
- **Remediation / Fix** — state concisely: disable the `mod_copy` module in the ProFTPD configuration, or upgrade the FTP service to the latest supported release.

---

## Severity Classification & Service Enumeration (Nmap)

- **Severity: Critical.** Almost all initial access vectors and priv-esc exploits that yield Remote Code Execution (RCE) are Critical.
- **Service Enumeration (Nmap)** under *Steps to Reproduce*:
  - List the identified open ports: **21** (FTP), **22** (SSH), **80** (HTTP), **111** (RPCbind), **139 / 445** (Samba), **2049** (NFS). (You do not need to list high-numbered ephemeral ports in the 49000 range unless they played an active role in exploitation.)
  - Paste your complete, raw **Nmap aggressive scan** output into the designated grey code block in the template. Keep the code font size (e.g. size 8) uniform and cleanly formatted.

## Documenting the Initial Foothold

Document the exact command sequence and attack narrative for initial access:

1. **Samba Enumeration (Port 445)**
   - Running `smbclient` against Port 445 exposed an open `anonymous` share.
   - Connecting revealed a `log.txt` file, downloaded locally with `get log.txt`.
   - Inspecting `log.txt` disclosed that an SSH private key (`id_rsa`) was generated for user `kenobi` at `/home/kenobi/.ssh/id_rsa`.
2. **ProFTPD Exploitation (`mod_copy`)**
   - Leveraging CVE-2015-3306 on ProFTPD 1.3.5, issue unauthenticated commands to copy Kenobi's private key:
     ```
     SITE CPFR /home/kenobi/.ssh/id_rsa
     SITE CPTO /var/tmp/id_rsa
     ```
     This copied the private key into the writable `/var/tmp` directory.
3. **NFS Mount & SSH Access**
   - Enumerating RPCbind on Port 111 revealed `/var` was exposed via NFS and mountable remotely.
   - Mounted `/var` locally, retrieved `/var/tmp/id_rsa`, adjusted permissions with `chmod 600 id_rsa`, and established an interactive SSH session as user `kenobi`.
4. **Screenshots & Proof**
   - Embed clean screenshots beneath each command showing the prompt, execution syntax, and resulting output.
   - Include the mandatory **user flag** screenshot showing `cat user.txt` and `ip a` / `ifconfig` executed within the exact same prompt.

## Documenting Privilege Escalation (SUID $PATH Manipulation)

Under **Section 4.1.2 (Privilege Escalation)**:

- **Vulnerability description & title** — Custom SUID binary vulnerable to **$PATH manipulation** leading to local privilege escalation.
- **Remediation / Fix** — Modify the binary's source code to invoke system utilities using **absolute file paths** (e.g. `/usr/bin/curl`) rather than relative binary names.
- **Severity: Critical.**
- **Exploitation steps:**
  - Enumerating SUID binaries revealed a custom binary: `/usr/bin/menu`.
  - Running `strings` on the binary showed it invoked commands **without** specifying absolute paths.
  - Created a malicious executable script under `/tmp`, prepended `/tmp` to the active `$PATH`:
    ```
    export PATH=/tmp:$PATH
    ```
    then executed `/usr/bin/menu`.
  - The SUID binary executed the malicious script with elevated permissions, spawning an interactive **root** shell.
  - Insert the **root proof** screenshot displaying `cat root.txt` alongside `ip a` within the identical terminal prompt.

## Active Directory Section & Final Document Polish

For the Active Directory component, the reporting structure is identical:
- Document an overarching summary of the domain environment.

- Update the **Table of Contents** across the entire Word document so all page numbers align.

## PDF Export, 7z Packaging & Portal Submission

Once the Word document is finalized:

1. **Save and rename the Word file:**
   ```
   OSCP-OS-XXXXXX-Exam-Report.docx
   ```
2. **Export to PDF** — in Word, export via **Create PDF/XPS** to:
   ```
   OSCP-OS-XXXXXX-Exam-Report.pdf
   ```
   Inspect the exported PDF thoroughly: verify no tables split awkwardly, code blocks remain intact, and formatting did not shift.
3. **Generate the 7z archive** — using 7-Zip, archive **only the PDF** with the exact same naming syntax:
   ```
   OSCP-OS-XXXXXX-Exam-Report.7z
   ```
   Verify the archive contains strictly the single PDF and stays well below the max upload limit (typically ~20–30 MB).
4. **Portal upload & hash verification:**
   - Log into the official OffSec exam submission portal.
   - Enter your **OS ID** and the unique **MD5 hash** provided in your exam scheduling email.
   - Upload `OSCP-OS-XXXXXX-Exam-Report.7z`.
   - The portal calculates and displays the upload's MD5 checksum — **cross-reference and verify it matches your local file hash** before clicking final submit.

## Summary

Keep your write-up concise, precise, and to the point — evaluators need clearly documented commands, tool outputs, and screenshots without unnecessary filler. Manage your time during the 24-hour reporting window: drafting typically takes **3–6 hours**, plus about an hour for proofreading and hash verification.
