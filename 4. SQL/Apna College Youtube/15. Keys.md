# Keys

Primary Key
It is a column (or set of columns) in a table that uniquely identifies each row. (a unique id) There is only 1 PK & it should be NOT null.


Foreign Key
A foreign key is a column (or set of columns) in a table that refers to the primary key in another table.
There can be multiple FKs.
FKs can have duplicate & null values.

"Next, we are going to talk about **our concept of keys**. Now here, **by keys, it does not mean a real, physical key**. Basically, whatever table we create inside our databases, **inside these tables, there are some special columns**. For example, let's assume this is some special column of ours, or this is another type of special column. **So, we call these special columns our keys**.

We will talk about **two keys which are the most important**:

1. **Primary Key**
2. **Foreign Key**

Now, in English, 'Primary' means main—the most main thing. That same job is of our primary key. **A primary key can be a single column or a set of columns inside any table**. This means we will call either a mixture of two or three columns our primary key, or we will call a single column our primary key. For now, for simplicity, just think that our single column itself is our primary key.

Now, **there is a column inside a table that uniquely identifies each row (record) of that table**. Uniquely identifying means, for example, if there is a class, inside that class, we have many students. For every student, the roll number must be different. If the roll number is different for every student, then roll number can become a primary key.

But for students, we also store other information. For example, we might store names for students, but two students can have the same name, which is why **we cannot make 'name' a primary key**. Similarly, for employees, we cannot make 'name' a primary key, nor can we make their 'salary' a primary key, because two people can have the same salary. But if we go inside a company, **the employee ID we get is unique for everyone, so employee ID can be made a primary key**.

So, whatever becomes our primary key:

- First, **it uniquely identifies each row**.
- Second, **it can never be null**.

So, **a primary key is always unique as well as not null**. This means it can never happen that the primary key value is empty. We always have to store some valid value inside the primary key.

For example, suppose we created a table named `student` inside which we are storing students' data. We want to store two things: one is roll number and one is name. So we can always make roll number our primary key. This means for every student, our roll number will always be written, and for no student will its value be null or duplicate.

Similarly, we have the concept of **Foreign Key**. A foreign key is either a single column or a set of columns that **refers to the primary key of another table**.

Now, we already know the meaning of the word 'Foreign'—foreign means of another country. Similarly, **it is a column that exists inside this table, but it is actually the primary key of some other table**.

Let's see an example of this. Suppose we have a Table 1 of students, and a Table 2 of cities

Inside the cities table, we have names of all cities, like Pune, and we have given them a unique ID: Pune is 1, Mumbai is 2, Delhi is 3. So we can say that in the city table, the ID is our primary key.

On the other hand, we have a student table. Inside the student table, we have every student's ID, their name, their city's ID, and their city's name. Here we can say that 'student ID' is the primary key of the student table (which will be unique and not null). And 'city ID' is the primary key of the city table (which is also unique and not null in its own table).

But now, inside the student table, we are writing 'city ID'. Even though 'city ID' is repeating here—for example, the city ID is 1 because the city is Pune, and for another student it is also 1 because the city is Pune—**because this column is the primary key of another table, it becomes a foreign key here**.

So, **a column that is a primary key in another table becomes a foreign key inside this table**. We can say that here, 'city ID' is our foreign key.

From this, we get to know that **while a primary key must contain unique values, a foreign key does not need to be unique because values can repeat**. This is because it refers to another table.

Thus, **we can have multiple foreign keys inside any table**. For example, one foreign key can be of one table, and we can bring another foreign key of some other table too. Just like we had one foreign key here, similarly we could have separately stored marks or made a different marks table. So that marks ID or course ID will also become another foreign key for us.

Therefore:

- **There is only one primary key** in a table.
- **There can be multiple foreign keys**.
- Foreign keys can have duplicate values.
- We can also store null values inside foreign keys. There are no such obligations on foreign keys.

This is the major difference between a primary key and a foreign key. So, basically, if anyone asks us: primary keys and foreign keys are special columns. **There is only one primary key in a table, which is unique and not null**. **Foreign keys can be multiple, can have duplicate values, and can also hold null values**. And the primary key of another table is called a foreign key inside any table."
