# Prompt Engineering

> LLM fundamentals — how models process text through tokenisation, and how token IDs connect to model behaviour.

---

## Understanding Tokens

LLMs don't read text the way humans do. They break input into **tokens** — the smallest units the model can process.

- A token ≈ **3–4 characters** — most English words are 1–2 tokens
- Short common words (`the`, `cat`) → single tokens
- Longer/uncommon words get split: `ChatGPT` → `Chat` + `GPT`, `butterfly` → `butter` + `fly`

### From Text to Numbers

The model converts each token into a unique **numeric ID**, then works entirely with numbers:

```
"Hello, how are you?"  →  [15496, 11, 703, 527, 499]
```

The model predicts what number (token) should come **next** — that's how it generates language.

> **One-liner:** AI turns sentences into token numbers because computers process numbers, then predicts the next number to generate language.

---

## Tokenisation

**Tokenisation** = splitting text into pieces and assigning each piece an ID.

Tokens can be: full words, parts of words, single characters, punctuation, spaces, or symbols.

### Three Approaches

| Method | How It Splits | Example: `"Hello world"` | Trade-off |
| ------ | ------------- | ------------------------- | --------- |
| **Character-level** | Individual characters | `["H","e","l","l","o"," ","w","o","r","l","d"]` | Simple but very long sequences — rare in modern LLMs |
| **Word-level** | Whole words | `["Hello", "world"]` | Clean but vocabulary explodes — can't handle every word |
| **Subword-level** ⭐ | Useful word pieces | `["Hel", "lo", "world"]` | Best balance — what GPT, BERT, and most modern LLMs use |

### Why Subwords Win

One small set of tokens can build many words:

- `play`, `ing`, `ed`, `er` → playing, played, player
- Handles unseen words by decomposing them into known pieces

### Different Models, Different Tokenizers

| Model | Tokenisation Method |
| ----- | ------------------- |
| **GPT** | Byte-Pair Encoding (BPE) |
| **BERT** | WordPiece |

The same sentence produces **different token sequences** depending on which model you use — like two dictionaries with different page numbers for the same word.

## How Token IDs Are Assigned

Token IDs are **not meaningful scores** — they are simply **index positions** in a vocabulary list.

### The Process

```
1. Collect massive text data (books, websites, code, conversations)
2. Run tokenizer algorithm → finds common/useful text patterns
3. Build vocabulary list (ordered by algorithm's internal logic)
4. Assign each token its position number as its ID
```

### Step-by-Step Example

**Step 1 — Start small:** begin with basic units (individual letters, punctuation)

**Step 2 — Find frequent patterns:** algorithm merges common pairs iteratively
- `h` + `e` → `he`
- `he` + `llo` → `hello`
- `sec` + `urity` → `security`

**Step 3 — Set vocabulary size limit** (e.g., 30K, 50K, or 100K tokens) — keep the most useful

**Step 4 — Special tokens first, then learned tokens:**

| ID | Token |
| -- | ----- |
| 0 | `<PAD>` |
| 1 | `<UNK>` |
| 2 | `a` |
| 3 | `b` |
| 4 | `th` |
| 5 | `the` |
| 6 | `ing` |
| 7 | `world` |
| 8 | `hello` |

So `hello = 8` simply means it was placed at row 8 in this vocabulary file.

### Why IDs Seem Random

When you see `hello = 15496`, it means ~15,000 other tokens (symbols, subwords, multilingual pieces, code tokens) were placed before it. The vocabulary follows internal logic (special tokens → base characters → learned merges by frequency) — it just **looks** arbitrary from outside.

> **Analogy:** library shelf numbers — Shelf 0 = Dictionary, Shelf 1 = Physics, Shelf 2 = Cybersecurity. Number depends on arrangement, not importance.

---

## Are Token IDs Dynamic?

**No** — once a model is released, its tokenizer vocabulary is **fixed**.

- `hello` maps to the **same ID every time** for that model
- The model learned during training that ID 15496 connects to a specific embedding vector
- Changing IDs during inference would be like **swapping keyboard keys while typing**

### What *Can* Differ

| Scenario | What Changes |
| -------- | ------------ |
| **Different models** | GPT and BERT assign different IDs to the same word |
| **New model versions** | Retrained tokenizer may use a different vocabulary |
| **Different tokenizers** | `"playing"` may be one token in one, `"play" + "ing"` in another |

But within the **same released model**, token IDs never change.

---

## From Token IDs to Meaning — Embeddings

Token IDs alone carry no semantic meaning. The model uses them as **pointers** into an **embedding table**:

```
Token ID 15496  →  look up row 15496 in embedding table  →  get learned vector
```

That vector (a list of numbers) is what actually encodes the token's meaning, relationships, and context. The ID is just the address.

## Key Takeaways

| Concept | Summary |
| ------- | ------- |
| **Token** | Smallest text unit a model processes (~3–4 chars) |
| **Tokenisation** | Splitting text into tokens + assigning numeric IDs |
| **Subword tokenisation** | Dominant modern approach — balances vocab size vs sequence length |
| **Token ID** | Position index in vocabulary list — not a meaning score |
| **Vocabulary** | Built by algorithm (not random) — ordered by special tokens, then merge frequency |
| **IDs are fixed** | Per model release; different models = different IDs |
| **Embeddings** | Where actual meaning lives — IDs are just pointers into the embedding table |

## Determinism vs Nondeterminism

Ask an LLM the same question twice and you'll likely get **different answers**. This is **nondeterminism** — outputs vary even with identical inputs.

| Behaviour | Traditional Software | LLMs |
| --------- | -------------------- | ---- |
| Same input → same output? | **Always** (deterministic) | **Usually not** (nondeterministic) |
| Source of variation | None — logic is fixed | Randomness in token prediction |
| Can randomness be eliminated? | N/A | **No** — parameters like temperature reduce it, but even major providers acknowledge it can't be fully eliminated |

> **Security implication:** malware executes the same way every time, but a defence against a malicious prompt **may work once and fail the next time**. This nondeterminism is the core challenge for LLM security.

## LLM Parameters

When you prompt an LLM, you trigger a **probability machine** that weighs hundreds of thousands of potential next tokens. You can steer how that probability plays out using three key parameters.

### Temperature — The Randomness Dial

Controls how "adventurous" the model is when picking its next token. Range: typically **0.0–2.0** (varies by provider).

| Range | Behaviour | Use Case |
| ----- | --------- | -------- |
| **0.0–0.3** | Strongly favours the most probable token; closest to determinism | Code generation, data extraction, factual Q&A |
| **0.7–1.0** | Samples from a wider distribution; more variety | Brainstorming, storytelling, marketing copy |
| **1.2–1.5** | Coherence begins to break down | Experimental use only |
| **1.5+** | Low-probability tokens dominate; outputs feel "drunk" | Avoid for most tasks |

**How temperature creates "creativity":**

Temperature doesn't give the model new knowledge — it **flattens the probability distribution**, giving less-likely tokens a better chance of being selected.

```
Prompt: "The hacker gained access using a ..."

Low temp (0.2):   password=60%  phishing=20%  vulnerability=15%  → picks "password" (safe, predictable)
High temp (1.0):  password=35%  phishing=30%  vulnerability=25%  → may pick "phishing" (varied, creative)
Too high (1.8):   banana=12%   quantum=10%  ...                  → incoherent, messy
```

> Higher temperature = broader choices, not new intelligence.

---

### Max Tokens — The Length Limiter

Caps how **long** the response can be. 1 token ≈ 0.75 English words.

| Budget | Token Range | Example |
| ------ | ----------- | ------- |
| Quick answer | 50–150 | Tweet-length summary |
| Detailed explanation | 500–1,000 | Paragraph-level response |
| Full article | 2,000+ | Essay or report |

- It's a **ceiling, not a target** — the model may use fewer tokens
- Consumer APIs (e.g., OpenAI) charge per token → **length control = cost control**

---

### Top-p — Nucleus Sampling

Instead of adjusting randomness across *all* tokens (temperature), top-p **sets a shortlist** — only tokens whose cumulative probability reaches the threshold are considered.

**Example:** prompt = `"The sky is ..."`

| Token | Probability | Cumulative |
| ----- | ----------- | ---------- |
| blue | 70% | 70% |
| clear | 15% | 85% |
| gray | 10% | 95% |
| pizza | 1% | 96% |
| elephant | 0.1% | ~96% |

| Top-p Value | Candidate Pool | Result |
| ----------- | -------------- | ------ |
| **0.5** | blue only | Very safe, predictable |
| **0.9** | blue, clear, gray | Balanced variety — weird tokens excluded |
| **1.0** | All tokens allowed | Maximum randomness |

**Temperature vs Top-p:**

| | Temperature | Top-p |
| - | ----------- | ----- |
| **Mechanism** | Rescales probabilities across *all* tokens | Hard-cuts unlikely tokens from the candidate pool |
| **Best for** | General use — simpler, more intuitive | Context-adaptive creativity |

> **Rule of thumb:** adjust **temperature OR top-p**, not both. Stacking two randomness controls creates unpredictable interactions.

---

### Context Window — The Memory Limit

Every model has a maximum **working memory** measured in tokens.

| Model | Context Window |
| ----- | -------------- |
| GPT-3.5 (older) | 8K tokens |
| Claude 3.5 Sonnet | 200K tokens (~500 pages) |
| Gemini 1.5 Pro | 1M+ tokens |

Exceed this limit and the model **silently truncates** earlier context — it literally forgets the start of your conversation.

## Hands-On: Testing Parameters via OpenRouter

[OpenRouter](https://openrouter.ai) provides a **unified API key** that lets you access multiple models (GPT, Claude, Gemini, etc.) without managing separate API keys for each provider.

```python
from openai import OpenAI

client = OpenAI(
    api_key="your-openrouter-api-key",
    base_url="https://openrouter.ai/api/v1"
)

response = client.responses.create(
    model="openai/gpt-4o-mini",
    input="Explain SQL injection",
    temperature=0.0,          # try 0.0 vs 1.0
    max_output_tokens=100     # try 50 vs 500
)

print(response.output_text)
```
