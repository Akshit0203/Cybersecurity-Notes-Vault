# Host Discovery

---

When we need to conduct an internal penetration test for the entire network of a company, for example, then we should, first of all, get an overview of which systems are online that we can work with. To actively discover such systems on the network, we can use various `Nmap` host discovery options. There are many options `Nmap` provides to determine whether our target is alive or not. The most effective host discovery method is to use **ICMP echo requests**, which we will look into.

It is always recommended to store every single scan. This can later be used for comparison, documentation, and reporting. After all, different tools may produce different results. Therefore it can be beneficial to distinguish which tool produces which results.

#### Scan Network Range

        shellsession
`Akshit023@htb[/htb]$ sudo nmap 10.129.2.0/24 -sn -oA tnet | grep for | cut -d" " -f5 10.129.2.4 10.129.2.10 10.129.2.11 10.129.2.18 10.129.2.19 10.129.2.20 10.129.2.28`

|**Scanning Options**|**Description**|
|---|---|
|`10.129.2.0/24`|Target network range.|
|`-sn`|Disables port scanning.|
|`-oA tnet`|Stores the results in all formats starting with the name 'tnet'.|

This scanning method works only if the firewalls of the hosts allow it. Otherwise, we can use other scanning techniques to find out if the hosts are active or not. We will take a closer look at these techniques in "`Firewall and IDS Evasion`".

---

## Scan IP List

During an internal penetration test, it is not uncommon for us to be provided with an IP list with the hosts we need to test. `Nmap` also gives us the option of working with lists and reading the hosts from this list instead of manually defining or typing them in.

Such a list could look something like this:

        shellsession
`Akshit023@htb[/htb]$ cat hosts.lst 10.129.2.4 10.129.2.10 10.129.2.11 10.129.2.18 10.129.2.19 10.129.2.20 10.129.2.28`

If we use the same scanning technique on the predefined list, the command will look like this:

        shellsession
`Akshit023@htb[/htb]$ sudo nmap -sn -oA tnet -iL hosts.lst | grep for | cut -d" " -f5 10.129.2.18 10.129.2.19 10.129.2.20`

|**Scanning Options**|**Description**|
|---|---|
|`-sn`|Disables port scanning.|
|`-oA tnet`|Stores the results in all formats starting with the name 'tnet'.|
|`-iL`|Performs defined scans against targets in provided 'hosts.lst' list.|

In this example, we see that only 3 of 7 hosts are active. Remember, this may mean that the other hosts ignore the default **ICMP echo requests** because of their firewall configurations. Since `Nmap` does not receive a response, it marks those hosts as inactive.

---

## Scan Multiple IPs

It can also happen that we only need to scan a small part of a network. An alternative to the method we used last time is to specify multiple IP addresses.

        shellsession
`Akshit023@htb[/htb]$ sudo nmap -sn -oA tnet 10.129.2.18 10.129.2.19 10.129.2.20| grep for | cut -d" " -f5 10.129.2.18 10.129.2.19 10.129.2.20`

If these IP addresses are next to each other, we can also define the range in the respective octet.

        shellsession
`Akshit023@htb[/htb]$ sudo nmap -sn -oA tnet 10.129.2.18-20| grep for | cut -d" " -f5 10.129.2.18 10.129.2.19 10.129.2.20`

---

## Scan Single IP

Before we scan a single host for open ports and its services, we first have to determine if it is alive or not. For this, we can use the same method as before.

        shellsession
`Akshit023@htb[/htb]$ sudo nmap 10.129.2.18 -sn -oA host  Starting Nmap 7.80 ( https://nmap.org ) at 2020-06-14 23:59 CEST Nmap scan report for 10.129.2.18 Host is up (0.087s latency). MAC Address: DE:AD:00:00:BE:EF Nmap done: 1 IP address (1 host up) scanned in 0.11 seconds`

|**Scanning Options**|**Description**|
|---|---|
|`10.129.2.18`|Performs defined scans against the target.|
|`-sn`|Disables port scanning.|
|`-oA host`|Stores the results in all formats starting with the name 'host'.|

If we disable port scan (`-sn`), Nmap automatically ping scan with `ICMP Echo Requests` (`-PE`). Once such a request is sent, we usually expect an `ICMP reply` if the pinging host is alive. The more interesting fact is that our previous scans did not do that because before Nmap could send an ICMP echo request, it would send an `ARP ping` resulting in an `ARP reply`. We can confirm this with the "`--packet-trace`" option. To ensure that ICMP echo requests are sent, we also define the option (`-PE`) for this.

        shellsession
`Akshit023@htb[/htb]$ sudo nmap 10.129.2.18 -sn -oA host -PE --packet-trace  Starting Nmap 7.80 ( https://nmap.org ) at 2020-06-15 00:08 CEST SENT (0.0074s) ARP who-has 10.129.2.18 tell 10.10.14.2 RCVD (0.0309s) ARP reply 10.129.2.18 is-at DE:AD:00:00:BE:EF Nmap scan report for 10.129.2.18 Host is up (0.023s latency). MAC Address: DE:AD:00:00:BE:EF Nmap done: 1 IP address (1 host up) scanned in 0.05 seconds`

|**Scanning Options**|**Description**|
|---|---|
|`10.129.2.18`|Performs defined scans against the target.|
|`-sn`|Disables port scanning.|
|`-oA host`|Stores the results in all formats starting with the name 'host'.|
|`-PE`|Performs the ping scan by using 'ICMP Echo requests' against the target.|
|`--packet-trace`|Shows all packets sent and received|

---

Another way to determine why Nmap has our target marked as "alive" is with the "`--reason`" option.

        shellsession
`Akshit023@htb[/htb]$ sudo nmap 10.129.2.18 -sn -oA host -PE --reason  Starting Nmap 7.80 ( https://nmap.org ) at 2020-06-15 00:10 CEST SENT (0.0074s) ARP who-has 10.129.2.18 tell 10.10.14.2 RCVD (0.0309s) ARP reply 10.129.2.18 is-at DE:AD:00:00:BE:EF Nmap scan report for 10.129.2.18 Host is up, received arp-response (0.028s latency). MAC Address: DE:AD:00:00:BE:EF Nmap done: 1 IP address (1 host up) scanned in 0.03 seconds`

|**Scanning Options**|**Description**|
|---|---|
|`10.129.2.18`|Performs defined scans against the target.|
|`-sn`|Disables port scanning.|
|`-oA host`|Stores the results in all formats starting with the name 'host'.|
|`-PE`|Performs the ping scan by using 'ICMP Echo requests' against the target.|
|`--reason`|Displays the reason for specific result.|

---

We see here that `Nmap` does indeed detect whether the host is alive or not through the `ARP request` and `ARP reply` alone. To disable ARP requests and scan our target with the desired `ICMP echo requests`, we can disable ARP pings by setting the "`--disable-arp-ping`" option. Then we can scan our target again and look at the packets sent and received.

        shellsession
`Akshit023@htb[/htb]$ sudo nmap 10.129.2.18 -sn -oA host -PE --packet-trace --disable-arp-ping  Starting Nmap 7.80 ( https://nmap.org ) at 2020-06-15 00:12 CEST SENT (0.0107s) ICMP [10.10.14.2 > 10.129.2.18 Echo request (type=8/code=0) id=13607 seq=0] IP [ttl=255 id=23541 iplen=28 ] RCVD (0.0152s) ICMP [10.129.2.18 > 10.10.14.2 Echo reply (type=0/code=0) id=13607 seq=0] IP [ttl=128 id=40622 iplen=28 ] Nmap scan report for 10.129.2.18 Host is up (0.086s latency). MAC Address: DE:AD:00:00:BE:EF Nmap done: 1 IP address (1 host up) scanned in 0.11 seconds`

We have already mentioned in the "`Learning Process`," and at the beginning of this module, it is essential to pay attention to details. An `ICMP echo request` can help us determine if our target is alive and identify its system.

This section teaches **Host Discovery**—the first step before port scanning. The goal is simply to answer one question:

> **"Is the target alive?"**

If a host isn't alive, there's no point scanning its ports. This is why host discovery always comes before enumeration. The module demonstrates several ways to discover live hosts using Nmap and explains the difference between **ARP** and **ICMP** discovery. (This explanation is based entirely on the HTB section you shared.)

---

# What is Host Discovery?

Host discovery determines which machines on a network are online.

Imagine a company network:

```
10.129.2.0/24

├── 10.129.2.4
├── 10.129.2.10
├── 10.129.2.11
├── 10.129.2.18
├── 10.129.2.19
└── 10.129.2.20
```

Before scanning thousands of ports, you first ask:

> **Which of these systems are actually running?**

---

# Scan an Entire Network

Example:

```
sudo nmap 10.129.2.0/24 -sn -oA tnet
```

Breakdown:

|Option|Meaning|
|---|---|
|`10.129.2.0/24`|Scan the entire subnet|
|`-sn`|Host discovery only (no port scan)|
|`-oA tnet`|Save results in all Nmap output formats with the prefix `tnet`|

The module pipes the output through:

```
grep for | cut -d" " -f5
```

to print only the discovered IP addresses.

---

# Scan a List of IPs

Sometimes you're given a file like:

```
hosts.lst

10.129.2.4
10.129.2.10
10.129.2.11
...
```

Scan it with:

```
sudo nmap -sn -iL hosts.lst -oA tnet
```

New option:

```
-iL
```

means:

> Read targets from a file.

---

# Scan Multiple Individual IPs

Example:

```
sudo nmap -sn 10.129.2.18 10.129.2.19 10.129.2.20
```

or if they're consecutive:

```
sudo nmap -sn 10.129.2.18-20
```

Both scan only those three hosts.

---

# Scan a Single Host

```
sudo nmap 10.129.2.18 -sn -oA host
```

Result:

```
Host is up
```

At this point, you know the machine is alive.

---

# What Does `-sn` Mean?

One of the most important Nmap options.

```
-sn
```

means:

> **Don't perform a port scan. Only discover hosts.**

So instead of checking ports:

```
22
80
443
```

Nmap simply asks:

> "Are you alive?"

---

# How Does Nmap Know a Host is Alive?

The module explains an important detail.

Even if you specify:

```
-PE
```

(local-network scans often) **use ARP first**.

Why?

Because on the same local network, **ARP is more reliable** than ICMP.

---

## ARP Discovery

Example packet trace:

```
Your PC

↓

Who has 10.129.2.18?

↓

Target

↓

I do!
```

Nmap receives an **ARP reply** and concludes:

```
Host is up
```

---

# ICMP Discovery

ICMP uses the familiar ping mechanism.

Request:

```
Echo Request
```

Reply:

```
Echo Reply
```

Example:

```
You

↓

ICMP Echo Request

↓

Target

↓

ICMP Echo Reply
```

If a reply comes back, the host is alive.

---

# Force ICMP with `-PE`

```
sudo nmap 10.129.2.18 -sn -PE
```

`-PE` tells Nmap to perform an **ICMP Echo Request (ping)**.

However, as the module demonstrates, on a local network Nmap may still determine host status using **ARP** unless ARP discovery is disabled.

---

# See the Packets (`--packet-trace`)

```
sudo nmap -sn -PE --packet-trace
```

This shows every packet Nmap sends and receives.

Example from the module:

```
SENT
ARP who-has 10.129.2.18

RCVD
ARP reply
```

This confirms **ARP** was actually used.

---

# Why Did Nmap Say the Host Was Alive?

Use:

```
--reason
```

Example:

```
sudo nmap -sn --reason
```

Output:

```
Host is up,
received arp-response
```

Now you know **why** Nmap reached that conclusion.

---

# Disable ARP

If you specifically want ICMP instead:

```
sudo nmap \
10.129.2.18 \
-sn \
-PE \
--disable-arp-ping \
--packet-trace
```

Now the packet trace shows:

```
ICMP Echo Request

↓

ICMP Echo Reply
```

instead of ARP.

---

# Why This Matters

The module emphasizes paying attention to details.

For example:

```
ICMP Reply
TTL = 128
```

From this, you can often infer the operating system.

Common default TTL values:

|TTL|Likely OS|
|---|---|
|64|Linux/Unix|
|128|Windows|
|255|Network devices (often Cisco)|

This is an inference commonly used during enumeration.

---

# Commands to Remember

|Command|Purpose|
|---|---|
|`nmap -sn <target>`|Host discovery only|
|`nmap -sn 10.129.2.0/24`|Scan a subnet|
|`nmap -sn -iL hosts.lst`|Scan targets from a file|
|`nmap -sn 10.129.2.18-20`|Scan an IP range|
|`-PE`|Send ICMP Echo Requests|
|`--packet-trace`|Show packets sent and received|
|`--reason`|Show why Nmap marked a host as up/down|
|`--disable-arp-ping`|Disable ARP discovery and use ICMP instead|
