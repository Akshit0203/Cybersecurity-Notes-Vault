
# OffSec Funbox — Full Writeup

## Overview

|            |                              |
| ---------- | ---------------------------- |
| **Target** | `192.168.148.77`             |
| **OS**     | Ubuntu Linux                 |
| **Stack**  | Apache 2.4.41 · WordPress · MySQL X · ProFTPD · OpenSSH 8.2p1 |
| **Flags**  | `local.txt` · `proof.txt`   |

### Lab Description

Employ enumeration, FTP enumeration, and web enumeration techniques to identify vulnerabilities. Engage in brute force attacks and implement privilege escalation strategies. Additionally, utilize process monitoring to enhance your access. This lab is designed to capitalize on your skills in vulnerability exploitation.

In this lab, an insecure MySQL database is exploited to gain access to WordPress credentials, which are used to upload a PHP reverse shell. Privilege escalation is achieved by exploiting a custom SUID binary vulnerable to path hijacking, leading to root access.

### Learning Objectives

**After completion of this lab, learners will be able to:**

- Scan the target for open services using Nmap and identify a WordPress site and MySQL service.
- Use Hydra to brute-force MySQL root credentials and access the WordPress database.
- Replace the WordPress admin password and upload a PHP reverse shell through theme manipulation.
- Identify and exploit the custom SUID binary /usr/bin/status using path hijacking to escalate privileges.
- Gain root access, validate system compromise, and retrieve the root flag.

## 4 · Post-Exploitation — Escaping rbash

### 4.1 — Discovering the Restricted Shell

```
joe@funbox:~$ sudo -l
[sudo] password for joe: 
Sorry, user joe may not run sudo on funbox.

joe@funbox:~$ pwd
/home/joe

joe@funbox:~$ cd /home
-rbash: cd: restricted
joe@funbox:~$ cd ..
-rbash: cd: restricted
```

We can see we're in `rbash` — a restricted shell.

### 4.2 — rbash Escape Methodology

> **📝 OSCP Note:** For **OSCP**, don't memorize one trick. Memorize a **methodology**.

When you see:

```
-rbash: cd: restricted
```

Your thought process should be:

```
1. Am I really in rbash?
2. What binaries do I have?
3. Is there an easy escape?
4. Restore a normal shell.
```

**Step 1 (Fastest): Try Bash itself**

Many times, this is enough:

```
/bin/bash
```

or

```
bash
```

Then check:

```
echo $0
```

If it prints `bash`, you're done.

### 4.3 — Escaping rbash

So now we shift to a normal bash shell by entering the command:

```
bash
```

```
joe@funbox:~$ cd /home
-rbash: cd: restricted
joe@funbox:~$ /bin/bash
-rbash: /bin/bash: restricted: cannot specify `/' in command names
joe@funbox:~$ bash
joe@funbox:~$ cd /home
joe@funbox:/home$ ls
funny  joe
```

> **Note:** `/bin/bash` failed because `rbash` blocks commands containing `/`. However, the bare `bash` command succeeds because it's resolved via `$PATH` without an explicit path separator.

There are 2 users: `funny` and `joe`.

## Lessons Learned

### 1. Virtual Host Resolution
When Nmap reports an HTTP redirect to a hostname (`http-title: Did not follow redirect to ...`), always add it to `/etc/hosts`. Without this, the site won't load and you'll miss the entire web attack surface.

### 2. rbash Escape Methodology
Don't panic when you see `rbash: cd: restricted`. Follow the checklist:
1. Confirm you're in `rbash` (`echo $0`).
2. Try `bash` (not `/bin/bash` — rbash blocks `/` in command names).
3. If that fails, check what binaries are available and look for other escape routes.

### 3. World-Writable Scripts + Scheduled Execution = Root
The privilege escalation pattern here is a classic:
- **Find** a world-writable script.
- **Confirm** it runs automatically (use `pspy`).
- **Confirm** it runs as root.
- **Inject** a reverse shell and wait.

### 4. pspy Over Manual Cron Enumeration
For OSCP, `pspy` is faster and more reliable than manually checking `/etc/crontab`, `/var/spool/cron/`, and systemd timers. It shows **exactly** what runs, as which user, in real time. Don't delay by manually checking every cron directory unless `pspy` isn't an option.

### 5. Patience with Multiple Cron Schedules
When both a regular user and root execute the same script on different schedules, the first shell you catch may not be root. Don't abandon the approach — don't do anything drastic. Restart your listener and wait for the root cycle. Verify your payload is still in the script before waiting.
