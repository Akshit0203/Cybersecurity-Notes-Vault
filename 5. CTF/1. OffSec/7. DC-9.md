## About this lab

Employ enumeration and web enumeration techniques to identify vulnerabilities. Engage in exploiting SQL injections and LFI, alongside implementing password cracking and brute-force attacks. Additionally, harness privilege escalation strategies and the abuse of sudo permissions to enhance your access. This lab is designed to capitalize on your skills in vulnerability exploitation.

## Learning Objectives

**After completion of this lab, learners will be able to:**

- Perform a full nmap scan to identify open ports and services.
- Identify and exploit SQL injection to dump user credentials from the database.
- Use knockd to perform port knocking and open SSH access.
- Brute-force SSH login using extracted credentials to gain initial access.
- Exploit the Python script /opt/devstuff/dist/test/test to escalate privileges by appending a new root user to /etc/passwd.

## Lab Description

This lab challenges you to exploit SQL injection to extract credentials, brute-force SSH access, and escalate privileges by manipulating a vulnerable Python script with sudo permissions. By combining web application attacks, enumeration, and privilege escalation techniques, you will gain root access on the target.

# What just happened?

Suppose the developer wrote something like:

```
SELECT id, firstname, lastname, position, phone, email
FROM StaffDetails
WHERE firstname = '$search';
```

When you search for:

```
Mary
```

the query becomes:

```
SELECT id, firstname, lastname, position, phone, email
FROM StaffDetails
WHERE firstname = 'Mary';
```

Only Mary's row satisfies the condition.

Result:

```
Mary
```

## Now you entered

```
' OR 1=1 --
```

The application simply concatenates your input into the SQL query.

So the database receives something similar to:

```
SELECT id, firstname, lastname, position, phone, email
FROM StaffDetails
WHERE firstname = ''
OR 1=1 -- ';
```

Let's evaluate the `WHERE` clause.

### For Mary

```
firstname=''
```

False.

But

```
1=1
```

True.

So:

```
False OR True
```

↓

```
True
```

Mary is returned.

---

### For Julie

```
False OR True
```

↓

True

Returned.

---

### For Fred

Same thing.

Returned.

---

This continues for every record.

So the query is effectively behaving like:

```
SELECT *
FROM StaffDetails
WHERE TRUE;
```

That's why you got all 17 records.

# Step 2 — What does `UNION` do?

Imagine these two completely separate queries.

Query A:

```
SELECT id, firstname, lastname, position, phone, email
FROM StaffDetails;
```

returns

|id|firstname|lastname|position|phone|email|
|---|---|---|---|---|---|
|1|Mary|Moe|CEO|...|...|
|2|Julie|Dooley|HR|...|...|

---

Query B:

```
SELECT
1,
2,
3,
4,
5,
6;
```

returns

|1|2|3|4|5|6|

---

Now SQL executes

```
Query A

UNION

Query B
```

The final result becomes

|id|firstname|lastname|position|phone|email|
|---|---|---|---|---|---|
|1|Mary|Moe|CEO|...|...|
|2|Julie|Dooley|HR|...|...|
|1|2|3|4|5|6|

UNION simply **combines rows** from two compatible `SELECT` statements.

---

# Step 3 — Why exactly 6 columns?

This is the most important concept.

The original query returns

```
id
firstname
lastname
position
phone
email
```

Count them.

```
1
2
3
4
5
6
```

Exactly **6 columns**.

A UNION query **must** return the same number of columns.

So this works:

```
SELECT
1,
2,
3,
4,
5,
6
```

because it also returns **6 columns**.

If you tried

```
SELECT
1,
2,
3,
4,
5
```

SQL would reject it because the column counts don't match.

# Step 4 — Why do we use numbers?

Because we want to know **where each column appears on the page**.

The webpage showed

```
ID: 1
Name: 2 3
Position: 4
Phone: 5
Email: 6
```

That tells us exactly how the application maps SQL columns to the UI.

|SQL Column|Displayed As|
|---|---|
|1|ID|
|2|First part of Name|
|3|Second part of Name|
|4|Position|
|5|Phone|
|6|Email|

Notice that **Name** is built from **two SQL columns**:

```
echo firstname . " " . lastname;
```

That's why it displayed:

```
Name: 2 3
```

instead of just `2`.

# Step 5 — Why is this useful?

Now imagine replacing the **6** with something else.

Instead of

```
SELECT
1,
2,
3,
4,
5,
6
```

you could conceptually place a database value in that sixth column.

Because you now know:

```
Column 6
        ↓
Email field on the webpage
```

whatever the database returns in column 6 will appear there.

This is why finding the column mapping comes **before** trying to display database metadata.

# Mental model (remember this for OSCP)

Think of the webpage as having six placeholders:

```
ID        ← Column 1

Name      ← Column 2 + Column 3

Position  ← Column 4

Phone     ← Column 5

Email     ← Column 6
```

At first you filled those placeholders with simple numbers:

```
1
2
3
4
5
6
```

just to discover where each column is displayed.

Once you know the mapping, you can replace one of those numbers with a database function or metadata value (for example, the database version or a table name) and immediately know **where** it will appear on the page. That's why this enumeration step is so important.
