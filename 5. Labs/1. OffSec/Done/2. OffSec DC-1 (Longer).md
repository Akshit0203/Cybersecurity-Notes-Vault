
# OffSec DC-1 

## About This Lab

Employ enumeration, web enumeration, and Joomla enumeration techniques to identify vulnerabilities. Engage in privilege escalation strategies and harness the abuse of SUID binaries to enhance your access. This lab is designed to capitalize on your skills in vulnerability exploitation.

## Learning Objectives

**After completion of this lab, learners will be able to:**

- Perform an nmap scan to identify open ports and services on the target.
- Enumerate the Drupal CMS version and identify vulnerabilities using tools like droopescan.
- Exploit the Drupalgeddon2 vulnerability to gain remote code execution and obtain a shell.
- Perform local enumeration using linpeas to identify privilege escalation vectors.
- Escalate privileges to root by abusing the SUID permission on the find binary.

## Lab Description

In this lab, we will exploit a vulnerable Drupal 7.x web application using a Remote Code Execution (RCE) exploit known as Drupalgeddon2. After obtaining a foothold, we will escalate privileges to root by abusing an SUID binary (find) that allows us to bypass system restrictions.

This exploit is actually very simple once you ignore the URL encoding. Let's decode it step by step.

---

#### Step 1: What should happen normally?

When someone logs in, Drupal runs something conceptually like:

```shell
SELECT * FROM users
WHERE name='admin'
AND pass='password';
```

It expects **only a username**, not SQL code.

---

#### Step 2: What does the attacker send?

Instead of sending just:

```
admin
```

the attacker sends something that becomes:

```
0;
INSERT INTO users (...);
INSERT INTO users_roles (...);
#
```

Notice the **semicolon (`;`)**. It ends the original SQL statement and starts **new SQL statements**.

---

#### Step 3: First SQL statement — Create a new user

```
INSERT INTO users
(status, uid, name, pass)
SELECT
1,
MAX(uid)+1,
'admin',
'$S$DkIkdKLIvRK0...'
FROM users;
```

This simply says:

> **Create a new user.**

Let's see every value:

**status = 1**

```
1
```

Means: Enabled account. If it were `0`, the account would be disabled.

---

**uid = MAX(uid)+1**

Suppose the database currently has:

|uid|user|
|---|---|
|1|admin|
|2|john|
|3|alice|

Then `MAX(uid)` returns `3`, so `MAX(uid)+1` becomes `4`. The new user gets ID **4**.

---

**name**

```
'admin'
```

Actually the exploit replaces this with the user-supplied value. For example `user="hacker"` becomes `'hacker'`.

---

**pass**

```
'$S$DkIkdKLIvRK0...'
```

This is **not the password**. It is the **password hash**. Drupal stores hashes instead of plaintext passwords.

---

#### Step 4: Second SQL statement — Grant admin role

Now the user exists, but they're just an ordinary user. Next:

```
INSERT INTO users_roles
(uid,rid)
VALUES
(
(SELECT uid FROM users WHERE name='admin'),
3
);
```

This says: Find the user ID of the user I just created.

Example:

|uid|name|
|---|---|
|4|hacker|

Then `SELECT uid FROM users WHERE name='hacker'` returns `4`.

Now insert `uid = 4, rid = 3` into `users_roles`.

---

#### What is rid?

Drupal permissions are stored separately.

|rid|Role|
|---|---|
|1|Anonymous|
|2|Authenticated User|
|3|Administrator|

So `rid = 3` means **Administrator**.

After this statement, the table becomes:

|uid|rid|
|---|---|
|1|3|
|2|2|
|3|2|
|4|3|

User **4** is now an administrator.

---

#### Step 5: SQL comment

Finally:

```
#
```

means: Ignore everything after this. It's an SQL comment. Otherwise Drupal's original SQL would continue and produce a syntax error.

---

#### Summary of the injection flow

Before the exploit:

```
Database

admin
john
alice
```

↓ Attacker sends malicious login request
↓ SQL Injection occurs
↓ Create new user
↓ Assign Administrator role
↓

```
Database

admin
john
alice
hacker  ← Administrator
```

↓ Attacker logs in normally using the username they created and the password corresponding to the hash they inserted.

#### Why is all the `%20`, `%27`, and `%2B` there?

Those are just **URL-encoded characters** because the SQL is being sent inside an HTTP POST request.

|Encoded|Decoded|
|---|---|
|`%20`|Space ( )|
|`%27`|Single quote (`'`)|
|`%2B`|Plus sign (`+`)|
|`%3d`|Equals sign (`=`)|

So the long `post_data` string is simply the URL-encoded version of the two SQL statements shown in the comments at the top of the exploit. The comments are the human-readable SQL, while `post_data` is how that SQL is packaged into an HTTP request.

### 6.3 Privilege Escalation — Finding SUID Binaries

We'll use:

```
find / -user root -perm /4000 2>/dev/null
```

> **Learning Note — `sudo -l` vs `find / -perm /4000`:**
> 
> These two commands are both used during **Linux privilege escalation**, but they look for **completely different things**.
> 
> |Command|What it checks|Why it matters|
> |---|---|---|
> |`sudo -l`|Your **sudo permissions**|Can you run commands as root using `sudo`?|
> |`find / -user root -perm /4000 2>/dev/null`|**SUID binaries**|Are there programs that always run with root privileges?|

---

> **Learning Note — `sudo -l` explained:**
> 
> ```
> sudo -l
> ```
> 
> This asks **sudo**: "What am I allowed to run with sudo?"
> 
> Example:
> 
> ```
> User john may run the following commands:
> 
> (root) NOPASSWD: /usr/bin/vim
> (root) /usr/bin/find
> ```
> 
> This means:
> - You **already have some sudo privileges**.
> - You might be able to become root by abusing one of those commands.
> 
> For example: `sudo vim` or `sudo find ...`
> 
> If one of the allowed programs can spawn a shell, you may get a root shell.
> 
> So `sudo -l` checks **permissions assigned to your user**.

---

> **Learning Note — `find / -perm /4000` explained:**
> 
> ```
> find / -user root -perm /4000 2>/dev/null
> ```
> 
> This searches the filesystem. It asks: "Show me every file owned by root that has the SUID bit set."
> 
> Example output:
> 
> ```
> /usr/bin/passwd
> /usr/bin/su
> /usr/bin/find
> /usr/bin/vim
> ```
> 
> These programs execute with the **effective UID of their owner (root)**, even when launched by an ordinary user.
> 
> Some SUID programs are safe. Others are vulnerable or misconfigured.
> 
> For example, if `/usr/bin/find` is SUID-root, then under some circumstances it can be abused to execute commands with root privileges.
> 
> So this command checks **the filesystem**, not your sudo permissions.

---

> **Learning Note — Hotel Analogy:**
> 
> Imagine a hotel.
> 
> **`sudo -l`** → You ask the receptionist: "Which master keys am **I** allowed to borrow?" The answer depends on **who you are**.
> 
> **`find ... -perm /4000`** → You walk around the hotel looking for: "Which doors have a permanent master key attached to them?" This has nothing to do with your account. You're simply discovering which programs always run with elevated privileges.

---

> **Learning Note — When to use which command (I get confused):**
> 
> This is one of the most common points of confusion in OSCP. The trick is **don't choose one or the other—run both almost every time** after you get a low-privilege shell.
> 
> Think of them as checking **different privilege escalation paths**.
> 
> |Question|Command|
> |---|---|
> |**Can my user use `sudo`?**|`sudo -l`|
> |**Are there SUID programs I can abuse?**|`find / -user root -perm /4000 2>/dev/null`|
> 
> **Scenario 1: Shell as `www-data`**
> ```
> www-data@target:$ whoami
> www-data
> ```
> First: `sudo -l` → Possible output: `Sorry, user www-data may not run sudo.` → No luck.
> Next: `find / -user root -perm /4000 2>/dev/null` → Output might show exploitable SUID binaries.
> 
> **Scenario 2: Shell as `john`**
> ```
> john@target:$ sudo -l
> ```
> Output: `(root) NOPASSWD: /usr/bin/vim` → You don't even need to look at SUID first because you've already found a promising path through `sudo`.
> 
> **Scenario 3: `sudo -l` asks for a password you don't know**
> No problem. Move on to `find / -user root -perm /4000 2>/dev/null` — maybe a SUID binary will provide another path.

---

> **Learning Note — Privilege Escalation Checklist:**
> 
> When you first land on a Linux machine:
> 
> ```
> whoami
> id
> hostname
> uname -a
> 
> sudo -l
> find / -user root -perm /4000 2>/dev/null
> getcap -r / 2>/dev/null
> crontab -l
> ```
> 
> You're **collecting evidence**, not guessing.
> 
> **OSCP Workflow:**
> ```

## Lessons Learned

1. **Check Python version before running exploits.** The Drupalgeddon SQLi script (`34992.py`) is Python 2 — running it with Python 3 gives misleading syntax errors.

2. **`robots.txt` is a free wordlist.** Stripping `Disallow:` prefixes and feeding the result to Gobuster is a quick way to validate all exposed paths.

3. **Don't give up after one exploit fails — pivot.** The SQLi-to-webshell modification, the `35150.php` RCE exploit, and the Drupal file upload all failed. The GitHub CVE-2018-7600 PoC worked cleanly.

4. **Always run both `sudo -l` AND `find / -user root -perm /4000`** after getting a shell. They check different privilege escalation vectors, and each takes only seconds.

5. **GTFOBins is essential for SUID abuse.** Once `find` was identified as SUID-root, the escalation was trivial — but the `-p` flag on `/bin/sh` may not be supported on older Debian systems. Adapt the command.

6. **`rlwrap` improves reverse shell usability.** Wrapping netcat with `rlwrap -cAr` gives arrow key and command history support.

7. **Understand exploits before using them.** Analyzing the Drupalgeddon SQLi payload revealed how it crafts two `INSERT` statements via URL-encoded SQL injection through the `name[]` array parameter — valuable knowledge for manual SQLi testing with Burp.

8. **Burp Suite confirms injection points.** Manually testing `name[']=` and `name['hello]=` in Burp Repeater confirmed the SQL injection point — everything after the `'` gets executed by the database.
