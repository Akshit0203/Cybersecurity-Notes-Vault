## Lab Overview

Engage in enumeration and web enumeration techniques to identify vulnerabilities. Implement privilege escalation strategies and harness the abuse of sudo permissions to enhance your access. This lab is designed to capitalize on your skills in vulnerability exploitation.

**Learning Objectives:**

- Perform an nmap scan to identify open ports and services on the target.
- Enumerate the WordPress CMS using wpscan and identify user accounts.
- Generate a custom wordlist using cewl and brute-force WordPress credentials.
- Log in via SSH using the discovered credentials and bypass the restricted shell.
- Escalate privileges to root by exploiting git sudo permissions.

**Lab Description:**

In this lab, we will exploit a WordPress CMS through targeted brute-forcing using a custom wordlist generated with cewl. After gaining initial access via SSH, we will bypass a restricted shell and escalate privileges by exploiting the sudo privilege on the git binary to gain root-level access.

### 2.2 WPScan Quick Reference

For OSCP, WPScan is the standard tool for enumerating WordPress installations. Here's the reference:

| Use Case | Command |
|---|---|
| Basic scan | `wpscan --url http://TARGET` |
| Subdirectory WP | `wpscan --url http://TARGET/blog` |
| Enumerate users | `wpscan --url http://TARGET -e u` |
| Enumerate plugins | `wpscan --url http://TARGET -e p` |
| Enumerate themes | `wpscan --url http://TARGET -e t` |
| **Enumerate everything** | `wpscan --url http://TARGET -e ap,at,u` |
| HTTPS with TLS issues | `wpscan --url https://TARGET --disable-tls-checks` |
| Slow target | `wpscan --url http://TARGET --request-timeout 30` |
| Check version | `wpscan --url http://TARGET --enumerate vp` |

Where for the enumerate-everything command:
- `ap` = All Plugins
- `at` = All Themes
- `u` = Users

**Password attack (only in an authorized lab):**

Single user:

```
wpscan --url http://TARGET \
--usernames admin \
--passwords rockyou.txt
```

Multiple users:

```
wpscan --url http://TARGET \
--usernames users.txt \
--passwords rockyou.txt
```

**OSCP Workflow** — When you discover a WordPress site:

```
# Detect WordPress
wpscan --url http://TARGET

# Enumerate plugins, themes, users
wpscan --url http://TARGET -e ap,at,u

# Search for exploits
searchsploit wordpress <version>
searchsploit <plugin_name>
searchsploit <theme_name>
```

This is the workflow you'll commonly follow in penetration testing labs: identify the WordPress version, enumerate installed components and users, then investigate whether any identified versions have known vulnerabilities.

## Phase 3 — Credential Brute Force

### 3.1 Understanding CeWL

**CeWL** stands for **Custom Word List Generator**.

CeWL **reads the website** and copies all the important words into a file. These are **possible passwords** because many people use words from the website as passwords.

> **Easy way to remember:**
> - **WPScan** ➜ Finds **usernames**.
> - **CeWL** ➜ Creates a **password list** from words on the website.
> - **Password attack tool** ➜ Tries **username + password** combinations.

### 3.3 How Brute Force Works (Concept)

Now we have usernames and possible passwords. A password-testing tool tries combinations like:

```
admin : nec
admin : amet
admin : sit
...

jerry : nec
jerry : amet
...

tom : adipiscing
tom : parturient
...
```

If one combination is correct, you can log in.

### 3.4 WPScan Password Attack

Launched a password attack against the WordPress login form using WPScan:

```
wpscan --url http://dc-2/ -U user.txt -P passwords.txt --password-attack wp-login
```

#### Understanding the flags

| Flag | Meaning |
|---|---|
| `-U user.txt` | File containing usernames to test |
| `-P passwords.txt` | File containing passwords to test |
| `--password-attack wp-login` | Attack via the normal WordPress login page (`wp-login.php`) |

This tells WPScan: "Go to the WordPress site, use the usernames in `user.txt`, use the passwords in `passwords.txt`, and try logging in through the normal WordPress login page." It submits the usernames and passwords just like a real user would.

> **One-line memory trick for OSCP:** `-U` = Users, `-P` = Passwords, `wp-login` = Use the normal WordPress login page to test every username/password combination (in an authorized environment).

### 5.2 Restricted Shell Discovery

Tried to read files but hit a wall:

```

Unable to execute commands! The error is:

```
-rbash: cat: command not found
```

#### What is `rbash`?

`rbash` stands for **Restricted Bash**. It's a restricted version of the Bash shell where certain commands or actions are intentionally limited.

This **does not mean `cat` is missing from Linux.** It means you're logged into a restricted shell.

#### Why did `cat` fail?

`rbash` is preventing execution because the `PATH` has been restricted — only a small set of commands are allowed. For example, `/bin/cat` exists on the system, but your `PATH` might only contain `/home/tom/usr/bin`. So when you type `cat`, `rbash` looks only in the allowed directories, doesn't find it, and says `command not found`.

#### Why do CTFs and OSCP labs use `rbash`?

It's another obstacle. Instead of immediately reading files or running any command, you first have to **escape the restricted shell** or find another allowed program that gives you a normal shell.

### 5.3 Enumerating the Restricted Environment

**Step 1 — Confirm you're in `rbash`:**

```
echo $0
echo $SHELL
```

If you see `-rbash` or `rbash`, you're in a restricted shell.

```
tom@DC-2:~$ echo $SHELL
/bin/rbash
```

**Step 2 — Check the restricted PATH:**

```

```

Output:

/home/tom/usr/bin

That means `rbash` only searches for commands in `/home/tom/usr/bin`.

### 5.4 Escaping rbash via vi

**Step 1 — Start `vi`:**

```
vi
```

![](attachments/Pasted%20image%2020260717204733.png)

Now you are **no longer interacting with `rbash`**. You are inside the **Vim program**.

```
rbash
   │
   ▼
 Vim
```

**Step 2 — Use vi to get an unrestricted shell:**

```
tom@DC-2:~$ vi  
```

Then inside vi, enter these commands:

```
:set shell=/bin/bash  
:shell  
```

#### What does `:set shell=/bin/bash` do?

Normally, if Vim launches a shell, it uses whatever shell is configured. This command changes Vim's shell setting to `/bin/bash`. So now Vim knows: "If I'm asked to open a shell, use Bash." It **does not** start Bash yet — it only changes Vim's configuration.

#### What does `:shell` do?

This is the important command. It tells Vim: "Open a shell." Since you previously configured `shell=/bin/bash`, Vim starts `/bin/bash` instead of returning to `rbash`.

Now the picture becomes:

```
rbash
   │
   ▼
 Vim
   │
   ▼
 bash
```

You're now sitting inside a normal Bash shell that **Vim launched**, bypassing the original restrictions.

Finally, `:q` just exits Vim. The Bash shell that Vim started continues running.

**Step 3 — Fix the environment:**

After escaping the restricted shell, we export `/bin/bash` as our SHELL environment variable and `/usr/bin` as our PATH environment variable so that we can run Linux commands properly.

```
export PATH=/bin:/usr/bin:$PATH   
export SHELL=/bin/bash
```

#### Why export PATH?

When Bash starts, it inherits the restricted environment. So your PATH might still be `/home/tom/usr/bin`, which means commands like `cat`, `find`, `python` still won't be found.

```
export PATH=/bin:/usr/bin:$PATH
```

Now PATH becomes:

```
/bin
/usr/bin
/home/tom/usr/bin
```

Now Bash can find `/bin/cat`, `/bin/bash`, `/usr/bin/find`, `/usr/bin/python`, etc.

#### Why export SHELL?

```
export SHELL=/bin/bash
```

This simply tells programs: "My default shell is Bash." Many programs check the `SHELL` environment variable, so setting it avoids confusion after escaping the restricted shell.

#### Breaking down the exploit command

```

```

**Part 1: `sudo`** — Run the following command as root. So instead of jerry running git, root runs git.

```
You (jerry)          Root
    │                 │
    ▼       →         ▼
   git               git
```

**Part 2: `git`** — This starts the Git program.

**Part 3: `branch`** — Tells Git: "I want information related to the `git branch` command."

**Part 4: `--help`** — This changes the behavior completely. Instead of executing `git branch`, Git says: "Show me the manual page for `git branch`." So Git internally opens the manual and displays it using a pager (usually `less`).

**Part 5: `config`** — This part is a little unusual. The extra `config` isn't what makes the exploit work. In the GTFOBins example it's simply an additional argument that still results in the help page opening on many Git versions. The important part is that **Git launches the help viewer (`less`)**.

The exploitation path is really:

```
sudo git branch --help
```

or

```
sudo git help config
```

depending on the Git version and installed man pages.

When you run `sudo git branch --help config`:

```

Git wants to show documentation

 │

less is also running as root
```

This is the critical point. Since `less` is running with root privileges, **if** it permits shell escapes, then a shell launched from `less` also runs as root.

```

Inside `less`, the `!` command means: "Run an external shell command." So when you type `!/bin/sh`, you're telling `less`: "Execute `/bin/sh`."

Since `less` was started by **root** (through `sudo git ...`), the shell it starts also inherits those privileges—unless the program or system deliberately drops them.

That's why this technique appears on GTFOBins as a way to escalate privileges when `git` is allowed via `sudo`.

## Lessons Learned

1. **Always add hostnames to `/etc/hosts`** — Nmap's redirect detection (`Did not follow redirect to http://dc-2/`) is a clear signal that hostname resolution is required.

2. **Read the flags carefully** — Each flag in DC-2 is a breadcrumb. Flag 1 literally name-drops `cewl`. Flag 2 says "another entry point." Flag 3 hints at `su`. Ignoring hints wastes time.

3. **Custom wordlists beat generic ones** — `rockyou.txt` would not have cracked these passwords. CeWL generates wordlists from the target itself, which is especially effective when admins use site-related terms as passwords.

4. **`rbash` is not a dead end** — Restricted shells limit PATH and command execution, but any allowed program that can spawn a sub-shell (vi, less, python, awk, etc.) is a potential escape vector. Always enumerate available commands with `ls -la` on the restricted PATH directory.

5. **GTFOBins is essential** — When `sudo -l` reveals a binary that can be run as root, GTFOBins should be the first reference. The `git → less → !/bin/sh` chain is a classic pager-based privilege escalation.

6. **Non-standard SSH ports** — Always scan all 65535 ports (`-p-`). SSH on port 7744 would be missed with a default top-1000 scan.

7. **Pager-based shell escapes** — Both the rbash escape (vi → `:shell`) and the privilege escalation (less → `!/bin/sh`) use the same underlying technique: programs that can spawn sub-shells inherit the privileges of their parent process.
