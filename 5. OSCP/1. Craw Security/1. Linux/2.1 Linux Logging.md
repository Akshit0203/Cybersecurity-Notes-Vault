
> **Core Principle:**  
> The most important Linux troubleshooting skill is not memorizing commands. It's knowing **which log source contains the answer** and how to read it quickly.

---

# 1. The Linux Logging Ecosystem

Most Linux systems store logs under:

```
/var/log
```

Think of `/var/log` as the **central evidence locker** of the operating system.

Common contents:

|File/Directory|Purpose|
|---|---|
|`/var/log/syslog`|General system events|
|`/var/log/auth.log`|Authentication and sudo events|
|`/var/log/kern.log`|Kernel and hardware messages|
|`/var/log/boot.log`|Boot process messages|
|`/var/log/dpkg.log`|Package installation/removal history|
|`/var/log/nginx/`|Nginx web server logs|
|`/var/log/apache2/`|Apache web server logs|
|`/var/log/audit/`|Auditd forensic logs|
|`/var/log/wtmp`|Login history (binary)|
|`/var/log/btmp`|Failed login history (binary)|

---

## Quickly Explore Logs

```
ls -lah /var/log
```

Useful commands:

```
cat file.logless file.logtail file.logtail -f file.loggrep keyword file.log
```

# 2. syslog — The General System Timeline

Location:

```
/var/log/syslog
```

(RHEL/CentOS uses `/var/log/messages`)

---

## Purpose

Acts as a **catch-all system log**.

Contains:

- Service starts/stops
- Network events
- Cron jobs
- Hardware events
- Application messages
- Kernel messages

---

## Example

```
Feb 14 09:01:22 systemd: Started Daily apt download activityFeb 14 09:01:25 CRON: (root) CMD (/usr/bin/backup.sh)Feb 14 09:02:03 kernel: usb device attached
```

---

## Useful Commands

View latest entries:

```
tail /var/log/syslog
```

Search for failures:

```
grep -i fail /var/log/syslog
```

Search for service:

```
grep nginx /var/log/syslog
```

Watch live:

```
tail -f /var/log/syslog
```

---

## When To Check First

Check syslog when:

- You don't know what broke.
- A service suddenly stopped.
- Something happened recently and you need a timeline.

Think:

> "What happened around 2 AM?"

Start with syslog.

---

# 3. auth.log — Authentication Evidence

Location:

```
/var/log/auth.log
```

(RHEL: `/var/log/secure`)

---

## Purpose

Records:

- SSH logins
- Login failures
- Sudo commands
- PAM activity
- User authentication

This is one of the most important logs for:

- SOC analysts
- Incident responders
- Blue teams
- System administrators

---

## Example

```
Accepted publickey for userFailed password for rootInvalid user adminsudo: user ran apt update
```

---

## Common Investigations

### Successful SSH Login

```
grep "Accepted" /var/log/auth.log
```

---

### Failed SSH Login

```
grep "Failed password" /var/log/auth.log
```

---

### Invalid User Enumeration

```
grep "Invalid user" /var/log/auth.log
```

Attackers often try:

```
admintestbackuporacleguest
```

---

### Sudo Usage

```
grep sudo /var/log/auth.log
```

Shows:

- Who ran commands
- What command was executed
- When it happened

---

## SOC Perspective

Repeated lines like:

```
Failed password for rootFailed password for rootFailed password for root
```

usually indicate:

- Password spraying
- Brute-force attack
- Credential stuffing

---

# 4. kern.log — Kernel & Hardware Diagnostics

Location:

```
/var/log/kern.log
```

Alternative:

```
dmesg -T
```

---

## Purpose

Records kernel-generated events:

- Driver loading
- Hardware detection
- Disk failures
- Filesystem errors
- Network interface events
- OOM killer activity

---

## Example

```
EXT4-fs mounted filesystemeth0 link upusb device attachedOut of memory: Kill process 3120
```

---

## Most Important Event: OOM Killer

Example:

```
Out of memory:Kill process 3120 (java)
```

Meaning:

- System RAM exhausted
- Linux selected a process to kill

Common root causes:

- Memory leak
- Large Java process
- Container consuming RAM

---

## Disk Problems

Search:

```
grep -i error /var/log/kern.log
```

or

```
dmesg -T | grep -i sda
```

May reveal:

- Bad sectors
- I/O errors
- Filesystem corruption

# 5. journald & journalctl

Modern Linux distributions use:

```
systemd-journald
```

Instead of relying solely on text logs.

Logs are stored in a binary journal database.

---

## View Journal

```
journalctl
```

---

## Current Boot

```
journalctl -b
```

---

## Previous Boot

```
journalctl -b -1
```

Extremely useful after crashes.

---

## Service Logs

SSH:

```
journalctl -u ssh
```

Nginx:

```
journalctl -u nginx
```

Docker:

```
journalctl -u docker
```

---

## Time-Based Search

Today:

```
journalctl --since today
```

Last hour:

```
journalctl --since "1 hour ago"
```

Specific time:

```
journalctl --since "2026-06-05 10:00"
```

---

## Priority Filtering

Errors only:

```
journalctl -p err
```

Kernel errors:

```
journalctl -k -p err
```

---

## Follow Live Logs

```
journalctl -f
```

Equivalent of:

```
tail -f
```

---

# 6. boot.log — Startup Troubleshooting

Location:

```
/var/log/boot.log
```

Alternative:

```
journalctl -b
```

---

## Purpose

Shows startup sequence.

Example:

```
[ OK ] Mounted /boot/efi[ OK ] Started SSH[FAILED] Failed to start Docker
```

---

## Most Important Entries

### Success

```
[ OK ]
```

Service started correctly.

---

### Failure

```
[FAILED]
```

Immediate investigation required.

Example:

```
systemctl status docker
```

---

## Common Use Cases

After reboot:

- Website down
- Database missing
- Docker failed

First place to check:

```
cat /var/log/boot.log
```

# 7. Web Server Logs

---

# Nginx

Directory:

```
/var/log/nginx/
```

Files:

```
access.logerror.log
```

---

# Apache

Directory:

```
/var/log/apache2/
```

Files:

```
access.logerror.log
```

---

## access.log

Every HTTP request.

Example:

```
203.0.113.5 GET /login HTTP/1.1 200
```

Contains:

- Source IP
- Requested page
- Response code
- Timestamp

---

## Status Codes

|Code|Meaning|
|---|---|
|200|Success|
|301|Redirect|
|403|Forbidden|
|404|Not Found|
|500|Server Error|

---

## Detect Scanners

Example:

```
/admin.php/phpmyadmin/wp-login.php
```

Often indicates:

- Automated scanners
- Bots
- Reconnaissance

---

## error.log

Shows:

- PHP errors
- Missing files
- Backend failures
- Reverse proxy problems

---

# 8. Cron Logs

Cron executes scheduled tasks.

---

## Check Execution

Debian/Ubuntu:

```
grep CRON /var/log/syslog
```

RHEL:

```
cat /var/log/cron
```

---

## Example

```
CRON: (root) CMD (/usr/bin/backup.sh)
```

Meaning:

- User: root
- Command: backup.sh
- Time: logged timestamp

---

## Security Relevance

Attackers often create persistence via cron:

```
crontab -e
```

Check for suspicious entries.

---

# 9. wtmp & btmp (Binary Login History)

These are NOT text files.

Do NOT use:

```
cat /var/log/wtmp
```

---

## Successful Logins

```
last
```

Example:

```
user pts/0 still logged in
```

---

## Failed Logins

```
sudo lastb
```

Shows:

```
root ssh:notty 203.0.113.9
```

---

## Last Login Per User

```
lastlog
```

---

## Incident Response Uses

Determine:

- Who logged in
- When they logged in
- Source IP
- Login failures
- Reboots

# 10. audit.log — Digital Forensics Goldmine

Location:

```
/var/log/audit/audit.log
```

Generated by:

```
auditd
```

---

## Purpose

Records:

- System calls
- File access
- User actions
- Security-sensitive operations

Used heavily for:

- Compliance
- Threat hunting
- Forensics

---

## Query Logs

Search executed commands:

```
ausearch -m EXECVE
```

---

## Important Fields

### UID

```
uid=
```

Current user.

---

### AUID

```
auid=
```

Original logged-in user.

Very useful after:

```
susudo
```

---

### PATH

```
type=PATH
```

File touched.

Example:

```
/etc/shadow
```

---

## Why Security Teams Love Auditd

Provides:

- High-fidelity tracking
- File modification records
- Process execution history
- User accountability

# 11. Log Rotation

Without rotation:

```
syslogsyslogsyslog...
```

would eventually fill the disk.

---

## Managed By

```
logrotate
```

Configuration:

```
/etc/logrotate.conf
```

---

## Example Files

```
syslogsyslog.1syslog.2.gzsyslog.3.gz
```

Meaning:

|File|Meaning|
|---|---|
|syslog|Current|
|syslog.1|Previous|
|syslog.2.gz|Older compressed|
|syslog.3.gz|Even older|

---

## Search Compressed Logs

Instead of:

```
gunzip file.gz
```

use:

```
zcat file.gz
```

or

```
zgrep error file.gz
```

Example:

```
zgrep ssh syslog.2.gz
```

# Essential Log Analysis Commands

### Last 20 Lines

```
tail -20 file.log
```

### Live Monitoring

```
tail -f file.log
```

### Search Keyword

```
grep keyword file.log
```

### Case-Insensitive Search

```
grep -i error file.log
```

### Count Matches

```
grep -c ssh auth.log
```

### Search Recursively

```
grep -R "password" /var/log
```

### Search Compressed Logs

```
zgrep ssh *.gz
```

# Incident Response Workflow

When a Linux server breaks:

### 1. What happened?

```
tail /var/log/syslog
```

---

### 2. Was it a login issue?

```
tail /var/log/auth.log
```

---

### 3. Hardware or memory issue?

```
tail /var/log/kern.log
```

---

### 4. Service failed?

```
journalctl -u service_name
```

---

### 5. Failed after reboot?

```
journalctl -b
```

or

```
cat /var/log/boot.log
```

---

### 6. Website issue?

```
tail /var/log/nginx/error.log
```

or

```
tail /var/log/apache2/error.log
```

---

### 7. Need forensic evidence?

```
ausearch
```

and

```
audit.log
```

---

### 8. Need login history?

```
lastlastblastlog
```

---

**Golden Rule:**  
When troubleshooting Linux, start broad (**syslog/journalctl**), then narrow down (**auth.log, kern.log, audit.log, application logs**). The fastest administrators and incident responders are usually the ones who know exactly **which log file answers which question.**
