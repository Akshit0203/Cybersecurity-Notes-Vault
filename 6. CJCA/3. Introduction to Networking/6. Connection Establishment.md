# Key Exchange Mechanisms

---

Key exchange methods are used to exchange [cryptographic keys](https://www.cloudflare.com/learning/ssl/what-is-a-cryptographic-key/) between two parties securely. They typically work by allowing two parties to agree on a `shared secret key` over an insecure communication channel using mathematical operations.

> The core question: **"How do two computers securely agree on a secret key over the Internet?"**

---

## Diffie-Hellman (DH)

[Diffie-Hellman key exchange](https://www.comparitech.com/blog/information-security/diffie-hellman-key-exchange/) allows two parties to agree on a shared secret key without any prior communication or shared private information. Often used as the basis for secure communication channels, such as in [TLS](https://www.cloudflare.com/learning/ssl/transport-layer-security-tls/).

**How it works (simplified):**

```
Alice chooses: Secret = 5
Bob chooses:   Secret = 9

They exchange mathematical values (NOT the secrets themselves)

Alice → Shared Key = ABC123
Bob   → Shared Key = ABC123
```

Nobody ever sent `ABC123` across the Internet. That's the magic of DH.

> [!WARNING] Limitation — MITM Vulnerability
> DH **does not verify identities**. An attacker sitting between Alice and Bob can create separate secrets with each, reading and modifying everything. This is a **Man-in-the-Middle (MITM) attack**. Classic finite-field DH is also slower than ECDH at comparable security levels.

---

## RSA

[Rivest–Shamir–Adleman](https://web.archive.org/web/20240302211950/https://venafi.com/blog/how-diffie-hellman-key-exchange-different-rsa/) (`RSA`) uses the properties of large prime numbers. It relies on the fact that multiplying large primes is easy but factoring the result back is extremely hard.

RSA can:
- ✅ Encrypt data
- ✅ Decrypt data
- ✅ Create digital signatures
- ✅ Verify signatures

Applications include:
- Encrypting and signing messages for confidentiality and authentication
- Protecting data in transit (SSL/TLS)
- Generating and verifying digital signatures
- Authenticating users and devices ([PKINIT](https://www.ietf.org/rfc/rfc4556.txt) in Kerberos)
- Protecting sensitive information (personal data, confidential documents)

---

## ECDH

[Elliptic curve Diffie-Hellman](https://medium.com/swlh/understanding-ec-diffie-hellman-9c07be338d4a) (`ECDH`) is a variant of DH that uses elliptic curve cryptography (`ECC`). It does the **same job as DH** (creates a shared secret) but is faster, uses smaller keys, and is more secure per key size.

Applications include:
- Establishing secure communication channels (TLS)
- Providing **forward secrecy** (past communications can't be revealed if private keys are compromised)
- Authenticating users/devices in [IKE](https://docs.oracle.com/cd/E19683-01/816-7264/6md9iem1g/index.html) for VPNs

---

## ECDSA

[Elliptic Curve Digital Signature Algorithm](https://www.hypr.com/security-encyclopedia/elliptic-curve-digital-signature-algorithm) (`ECDSA`) uses ECC to generate digital signatures. It is **NOT** for encryption or key exchange — it proves: *"Yes, this message really came from me."*

---

## Algorithm Comparison

| **Algorithm** | **Acronym** | **Security** |
| --- | --- | --- |
| `Diffie-Hellman` | `DH` | Secure with strong params and authentication; slower than `ECDH` at similar security |
| `Rivest–Shamir–Adleman` | `RSA` | Widely used; more computationally heavy than `ECC` at comparable security levels |
| `Elliptic Curve Diffie-Hellman` | `ECDH` | Enhanced security and speed compared to traditional `DH` |
| `Elliptic Curve Digital Signature Algorithm` | `ECDSA` | Enhanced security and efficiency for digital signature generation |

> [!TIP] Quick Memory Tricks
> - **DH / ECDH** → Create a shared secret key
> - **RSA / ECDSA** → Prove identity (digital signatures); RSA can also encrypt
> - **DH vs ECDH** → Same destination, ECDH is just faster (old car vs sports car)
> - **RSA vs ECDSA** → Both verify identities; ECDSA = signatures only but faster

---

## Internet Key Exchange (IKE)

[Internet Key Exchange](https://www.hypr.com/security-encyclopedia/internet-key-exchange) (`IKE`) is a protocol used to establish and maintain secure communication sessions (VPNs). It combines Diffie-Hellman key exchange with other cryptographic techniques. Typically used in conjunction with RSA for digital signatures and [AES](https://www.geeksforgeeks.org/advanced-encryption-standard-aes/) for data encryption.

**IKE is the handshake before the VPN tunnel is established:**

```
VPN Client ↔ VPN Server

"Let's use AES-256." → "Okay."
"Let's use SHA-256."  → "Okay."
"Here's my public value." → "Here's mine."

Shared Key Created → Encrypted VPN starts
```

### Main Mode vs Aggressive Mode

| | **Main Mode** | **Aggressive Mode** |
| --- | --- | --- |
| Messages | 6 messages exchanged | 3 messages exchanged |
| Phases | Three phases | Two phases |
| Security | More secure — hides identities | Less secure — does **not** hide identities |
| Speed | Slower | Faster |

### Pre-Shared Keys (PSK)

A `Pre-Shared Key` is a secret value shared between VPN devices before the key exchange begins. Both devices already know the same password, and it proves: *"Yes, we're both trusted devices."*

The PSK must be securely exchanged out-of-band. If compromised via MITM, the IKE session may be compromised.

### Complete VPN Flow

```
Client
   │
IKE starts
   │
Exchange public values (DH/ECDH)
   │
Authenticate (PSK or RSA certificate)
   │
Generate shared secret
   │
Agree on AES encryption
   │
══════════════════════
Encrypted VPN Tunnel
══════════════════════
```

### Key Exchange Cheat Sheet

| Technology | Purpose | Memory Trick |
| --- | --- | --- |
| **DH** | Creates a shared secret key | **D = Decide a shared key** |
| **RSA** | Encryption + Digital Signatures | **Swiss Army knife of public-key crypto** |
| **ECDH** | Faster DH using Elliptic Curves | **DH but faster** |
| **ECDSA** | Digital Signatures only | **S = Signature** |
| **IKE** | Negotiates VPN security | **Handshake before the VPN tunnel** |
| **PSK** | Shared password for VPN authentication | **Both sides already know the same secret** |
| **AES** | Encrypts the actual VPN data | **Used after key exchange is complete** |

# Authentication Protocols

---

Authentication protocols provide a secure and standardized way of `verifying the identity` of users, devices, and other entities in a network.

> **Authentication** = Verify identity ("Who are you?")
> **Authorization** = Decide permissions ("What are you allowed to access?")

| **Protocol** | **Description** |
| --- | --- |
| `Kerberos` | Key Distribution Center (KDC) based authentication protocol that uses tickets in domain environments. |
| `SRP` | Password-based authentication using cryptography to protect against eavesdropping and MITM. |
| `SSL` | Cryptographic protocol for secure communication (obsolete — replaced by TLS). |
| `TLS` | Successor to SSL. Provides communication security over the internet. |
| `OAuth` | Open standard for authorization — lets apps access your data without your password (e.g., "Login with Google"). |
| `OpenID` | Decentralized authentication — one identity for many websites. |
| `SAML` | XML-based standard for securely exchanging authentication and authorization data (enterprise SSO). |
| `2FA` | Two-Factor Authentication — combines two different factors. |
| `FIDO` | Fast IDentity Online — open standards for strong authentication. |
| `PKI` | Public Key Infrastructure — manages certificates, public/private keys, Certificate Authorities. |
| `SSO` | Single Sign-On — one set of credentials for multiple applications. |
| `MFA` | Multi-Factor Authentication — multiple factors (something you know/have/are). |
| `PAP` | Password Authentication Protocol — sends password in **clear text**. ❌ Never use. |
| `CHAP` | Challenge-Handshake Authentication Protocol — challenge-response, password never transmitted directly. |
| `EAP` | Extensible Authentication Protocol — framework supporting multiple methods (PEAP, EAP-TLS, LEAP). |
| `SSH` | Secure Shell — encrypted remote command-line access. Can authenticate via passwords or SSH keys. |
| `HTTPS` | HTTP + TLS — secure web browsing. |
| `LEAP` | Cisco wireless authentication using RC4. ❌ Vulnerable and outdated. |
| `PEAP` | Protected EAP — uses TLS tunnel and server-side certificates. ✅ Much more secure than LEAP. |

### LEAP vs PEAP

- `PEAP` is generally more secure because it uses a server-side public key certificate and encrypts `MSCHAPv2` hash
- `LEAP` relies on a shared secret and does **not** encrypt `MSCHAPv2` hashes
- PEAP supports stronger encryption (AES, 3DES) vs LEAP's weaker RC4
- Both have been largely replaced by `EAP-TLS`

### 6 Protocols to Definitely Remember

1. **Kerberos** → Windows AD authentication (tickets)
2. **TLS/HTTPS** → Secure web traffic
3. **SSH** → Secure remote access
4. **OAuth** → "Login with Google" (authorization)
5. **SSO** → One login for multiple applications
6. **MFA / 2FA** → Multiple authentication factors

### Authentication Cheat Sheet

| Protocol | Purpose | Memory Trick |
| --- | --- | --- |
| **Kerberos** | Windows/AD authentication | 🎫 **Tickets** |
| **TLS** | Encrypts internet traffic | 🔒 **HTTPS encryption** |

# TCP/UDP Connections

---

[TCP](https://en.wikipedia.org/wiki/Transmission_Control_Protocol) and [UDP](https://en.wikipedia.org/wiki/User_Datagram_Protocol) are both protocols used for data transmission on the Internet.

- **TCP** — connection-oriented, ensures all data is received (like a telephone conversation). Reliable but slower.
- **UDP** — connectionless, no verification that data is complete. Faster but may lose data. Used for streaming, gaming.

---

## IP Packet

An [IP](https://en.wikipedia.org/wiki/Internet_Protocol) packet consists of a header and the payload. Think of it as a letter in an envelope: the envelope (header) has sender/recipient info and routing instructions, the letter (payload) is the actual data.

### IP Header Fields

| **Field** | **Description** |
| --- | --- |
| `Version` | IP protocol version |
| `Internet Header Length` | Size of the header in 32-bit words |
| `Class of Service` | Priority of the transmission |
| `Total length` | Total length of the packet in bytes |
| `Identification (ID)` | Identifies fragments when fragmented (16-bit, 0–65535) |
| `Flags` | Indicates fragmentation |
| `Fragment Offset` | Position of the current fragment |
| `Time to Live` | How long the packet may remain on the network |
| `Protocol` | Which protocol is used (TCP, UDP, etc.) |
| `Checksum` | Detects errors in the header |
| `Source/Destination` | Where the packet was sent from and where it's going |
| `Options` | Optional routing information |
| `Padding` | Pads the packet to a full word length |

### IP ID for Host Identification

If a computer has multiple IP addresses, the `IP ID` field will be different for each packet but very similar (continuous). This can reveal that two IPs belong to the same host:

```shellsession
IP 10.129.1.100.5060 > 10.129.1.1.5060: SIP, length: 1329, id 1337
IP 10.129.1.100.5060 > 10.129.1.1.5060: SIP, length: 1329, id 1338
IP 10.129.1.100.5060 > 10.129.1.1.5060: SIP, length: 1329, id 1339
IP 10.129.2.200.5060 > 10.129.1.1.5060: SIP, length: 1329, id 1340
IP 10.129.2.200.5060 > 10.129.1.1.5060: SIP, length: 1329, id 1341
IP 10.129.2.200.5060 > 10.129.1.1.5060: SIP, length: 1329, id 1342
```

Two different IPs but continuous IP IDs → strongly indicates the same host.

### IP Record-Route Field

The `Record-Route field` records the route to a destination. All devices the packet passes through are listed:

```shellsession
Akshit023@htb[/htb]$ ping -c 1 -R 10.129.143.158
PING 10.129.143.158 (10.129.143.158) 56(124) bytes of data.
64 bytes from 10.129.143.158: icmp_seq=1 ttl=63 time=11.7 ms
RR: 10.10.14.38
    10.129.0.1
    10.129.143.158
    10.129.143.158
    10.10.14.1
    10.10.14.38
```

### Traceroute (TCP Timeout Method)

1. Send a TCP SYN packet with TTL = 1. Router drops it and sends ICMP Time-Exceeded back.
2. Note the router's IP address.
3. Send another TCP SYN with TTL + 1.
4. Repeat until reaching the destination (receives TCP SYN/ACK or RST).

---

## TCP

TCP packets (called `segments`) are divided into headers and payloads, wrapped in the IP packet.

Key header fields:
- **Source/Destination Port** — which computer and service
- **Sequence Number** — order of data sent
- **Acknowledgment Number** — confirms data received
- **Control Flags** — end of message, acknowledgment, retransmit request
- **Window Size** — how much data the receiver can accept
- **Checksum** — error detection
- **Urgent Pointer** — alerts receiver of important payload data

---

## UDP

UDP transfers `datagrams` (small data packets) between two hosts. Connectionless — data is sent directly without establishing a connection first.

When `traceroute` uses UDP, you receive a `Destination Unreachable` and `Port Unreachable` message at the target. UDP traceroute is the default on Unix hosts.

---

## Blind Spoofing

`Blind spoofing` is a data manipulation attack where an attacker forges the source IP address but **cannot see the target's responses** (because they're sent to the spoofed address).

### How It Works

**Normal TCP handshake:**
```
You → SYN → Server
Server → SYN-ACK → You
You → ACK → Server
Connection Established
```

**Blind spoofing:**
```
Attacker (IP: 192.168.1.100) sends:
  SYN with Source IP = 192.168.1.50 (spoofed)

Server thinks it came from 192.168.1.50, so:
  SYN-ACK → 192.168.1.50 (NOT to the attacker)

The attacker never sees the reply → "blind"
```

### The ISN Problem

To complete the handshake, the attacker must **guess** the server's `Initial Sequence Number` (`ISN`). If they guess correctly, they can complete the TCP handshake while pretending to be the spoofed machine.

Modern operating systems generate **random ISNs**, making this extremely difficult today. Older systems used predictable ISNs.

### Uses

- Pretend to be a trusted computer
- Attempt to establish TCP connections as another host
- Launch denial-of-service attacks
- Disrupt existing network communications

> [!TIP] Analogy
> Imagine sending a letter with **someone else's return address**. The bank sends the reply to Bob's house, not yours. You have no idea what the bank replied. You're acting **blindly**.

> **Blind spoofing is an attack where an attacker forges (spoofs) the source IP address of packets but cannot see the target's responses because those responses are sent to the spoofed address instead of the attacker.**

# Cryptography

---

Encryption transforms data into a form that unauthorized persons can no longer read. Digital keys in `symmetric` or `asymmetric` encryption processes are used. With state-of-the-art cryptographic methods and extensive key lengths, they work very securely and are almost impossible to compromise.

---

## Symmetric Encryption

Uses the **same key** to encrypt and decrypt data. Both sender and receiver must have the same key.

- **AES** (Advanced Encryption Standard) — most secure symmetric algorithm today
- **DES** (Data Encryption Standard) — obsolete
- **3DES** (Triple DES) — legacy, more secure than DES but still limited

> [!WARNING] Key Distribution Problem
> If the secret key is shared or lost, security is no longer guaranteed. The distribution, storage, and exchange of keys is critical.

---

## Asymmetric Encryption (Public-Key)

Uses two different keys:
- A `public key` to encrypt data (anyone can use it)
- A `private key` to decrypt data (only the recipient has it)

Examples: RSA, PGP, ECC

Applications:

| | | |
| --- | --- | --- |
| E-Signatures | SSL/TLS | VPNs |
| SSH | PKI | Cloud |

**Advantage:** No need to exchange keys secretly — the public key can be accessible to everyone. Also enables authentication with digital signatures.

---

## Data Encryption Standard (DES)

A symmetric-key block cipher using a combination of one-time pad, permutation, and substitution applied to bit sequences.

- Key: `64 bits` (8 bits used as checksum → actual key length = `56 bits`)
- Encrypts 64-bit blocks of plaintext to 64-bit blocks of ciphertext

**Triple DES / 3DES** — encrypts three times (encrypt → decrypt → encrypt) with multiple keys. More secure than DES but still limited by 56-bit key size.

---

## Advanced Encryption Standard (AES)

Successor to DES. Uses `128-bit` (AES-128), `192-bit` (AES-192), or `256-bit` (AES-256) keys. Faster than DES due to more efficient algorithm structure — can be applied to multiple data blocks at once.

Found in:

| | | |
| --- | --- | --- |
| WLAN IEEE 802.11i | IPsec | SSH |
| VoIP | PGP | OpenSSL |

---

## Cipher Modes

A cipher mode defines how a block cipher algorithm processes and combines fixed-size blocks (usually 64 or 128 bits) to encrypt a message of any length.

> **Question:** AES splits data into 16-byte blocks. **How should AES encrypt multiple blocks?** That's what cipher modes decide.

### ECB (Electronic Codebook) ❌

Each block is encrypted **independently**.

```
Block1 → Encrypt → Cipher1
Block2 → Encrypt → Cipher2
Block3 → Encrypt → Cipher3
```

**Problem:** Identical plaintext blocks produce identical ciphertext. Patterns remain visible (the famous encrypted penguin image).

### CBC (Cipher Block Chaining) ✅

Each block depends on the previous one. Identical plaintext blocks produce different ciphertext. Default mode for AES.

Used in: Disk encryption, older TLS/SSL, VeraCrypt

### CFB (Cipher Feedback) ✅

Converts a block cipher into a **stream cipher**. Encrypts data continuously — perfect for network packets, live communication.

### OFB (Output Feedback) ✅

Similar to CFB but feeds the generated keystream back instead of ciphertext. Transmission errors less likely to propagate. Used in SSH.

### CTR (Counter Mode) ⭐

Encrypts a counter value for each block. Very fast, blocks can be encrypted **in parallel**.

Used in: IPsec, disk encryption, high-speed networking (BitLocker)

### GCM (Galois/Counter Mode) ⭐⭐⭐

CTR + Authentication. Provides both **confidentiality** (encryption) AND **integrity** (detects tampering).

Used in: HTTPS (TLS 1.2/1.3), VPNs, Wi-Fi (WPA3), Cloud services

---

### Cipher Modes Comparison

| Mode | Good? | Main Idea | Common Uses |
| --- | --- | --- | --- |
| **ECB** | ❌ No | Each block encrypted independently | Avoid |
| **CBC** | ✅ Older | Each block depends on the previous one | Older TLS, VeraCrypt |
| **CFB** | ✅ | Stream encryption using feedback | Live communication |
| **OFB** | ✅ | Stream encryption with output feedback | SSH, streaming |
| **CTR** | ⭐ Excellent | Encrypts counters instead of chaining | IPsec, BitLocker |
| **GCM** | ⭐⭐⭐ Best | CTR + Integrity check | HTTPS, TLS 1.3, VPNs |

### 10-Second Memory Trick

```
ECB  → Exposes patterns ❌
CBC  → Chains blocks together ⛓️
CTR  → Uses a Counter ⚡
GCM  → CTR + Integrity 🛡️ (Modern favorite)
```

> [!TIP] For Exams (HTB, CEH, Security+, OSCP)
> - ❌ **ECB** → Insecure because it reveals patterns
> - ✅ **CBC** → Chains blocks together; much safer than ECB
> - ✅ **CTR** → Fast, parallelizable, widely used in modern systems
> - ⭐ **GCM** → Modern standard: provides both **encryption and integrity** (authenticated encryption)
