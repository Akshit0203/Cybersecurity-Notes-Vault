### What is an inode (index number)?

The **inode** (also called the **index number**) is a unique identifier that the Linux filesystem assigns to every file and directory.

Think of it like this:

- **Filename** = Contact name in your phone ("John")
- **Inode** = John's actual phone number (the real identifier)

The operating system doesn't actually use the filename to access the file. It uses the **inode number**.

```
Filename        Inode
---------       -----
sudoers   --->  147627
passwd    --->  147610
shadow    --->  147611
```

When you run:

```
ls -li /etc/sudoers
```

you get

```
147627 -r--r----- 1 root root 755 Jan 18 2018 /etc/sudoers
^^^^^^
inode number
```

---

## What does an inode store?

The inode stores **metadata** about the file, such as:

- Owner (root)
- Group
- Permissions
- File size
- Creation/Modification time
- Links count
- Disk block locations (where the actual data is stored)

It **does NOT store the filename**.

```
           Inode 147627
          ┌────────────────────┐
          │ Owner: root         │
          │ Permissions: 440    │
          │ Size: 755 bytes     │
          │ Modified: Jan 18    │
          │ Blocks: 345,346...  │
          └────────────────────┘
                    ▲
                    │
             points to data blocks
                    │
          ┌────────────────────┐
          │ Actual file data   │
          └────────────────────┘
```

---

## Then where is the filename stored?

The filename is stored **inside the parent directory**.

For `/etc/sudoers`, the `/etc` directory contains an entry like:

```
Filename     Inode
--------     -----
passwd       147610
shadow       147611
sudoers      147627
hosts        147590
```

When you type

```
cat /etc/sudoers
```

Linux performs these steps:

1. Open `/etc`
2. Search for the filename `sudoers`
3. Find that it points to inode `147627`
4. Read inode `147627`
5. The inode tells Linux where the file's data blocks are
6. Linux reads those blocks and prints the file

---

## Why is this useful?

This design enables **hard links**.

Suppose you run:

```
ln file copy
```

Now:

```
ls -li
```

```
147627 file
147627 copy
```

Notice both names have the **same inode**.

That means:

```
          Inode 147627
               ▲
             /   \
          file   copy
```

There aren't two copies of the file. Both filenames point to the **same inode**, so both refer to the same underlying data.

## Nano (modeless editor)

In Nano, **every key you press is treated as text** unless it's a shortcut.

Example:

You open a file and press:

```
hello
```

Nano inserts:

```
hello
```

If you press `a`, it types `a`.  
If you press `d`, it types `d`.

You're always in "typing mode."

---

## Vim (modal editor)

Vim has **different modes**.

When Vim first opens, you're in **Normal Mode**.

In **Normal Mode**, **every key is interpreted as a command**, **not text**.

For example, if the file contains:

```
Hello World
```

and you press:

```
dd
```

Vim does **not** insert `dd`.

Instead:

```
dd
```

means

> Delete the current line.

Now the file becomes empty.

---

If you press:

```
x
```

It doesn't type `x`.

Instead:

> Delete one character.

---

If you press:

```
j
```

It doesn't insert `j`.

Instead:

> Move the cursor down.

---

If you press:

```
k
```

> Move the cursor up.

---

If you press:

```
h
```

> Move left.

---

If you press:

```
l
```

> Move right.

---

## Why?

Because in Normal Mode, Vim assumes:

> "The user wants to edit the document efficiently, not type text."

So every key becomes an editing command.

---

## Then how do I actually type?

You switch to **Insert Mode**.

Press:

```
i
```

Now you'll see something like:

```
-- INSERT --
```

Now every key becomes normal text.

If you type:

```
Hello
```

The file becomes:

```
Hello
```

Just like Nano.

---

When you're done typing, press:

```
Esc
```

Now you're back in **Normal Mode**.

Again:

- `dd` → delete line
- `yy` → copy line
- `p` → paste
- `u` → undo
- `x` → delete character

None of these get inserted as text.

Suppose your file is:

This modal design is why experienced Vim users can edit text **without constantly moving their hands between the keyboard and mouse**. They stay in Normal Mode for navigation and editing, briefly enter Insert Mode to type new text, then return to Normal Mode. This makes Vim extremely fast once you become familiar with its commands.

# 1. `-exec ls -al {} \;`

## Without `-exec`

Normally, `find` only prints the matching file names.

Example:

```
find /etc -name "*.conf"
```

Output:

```
/etc/ssh/sshd_config
/etc/dnsmasq.conf
/etc/resolv.conf
```

Notice it only prints the paths.

## What if we want more information?

Suppose we also want permissions, owner, size, etc.

Normally we'd have to run:

```
ls -al /etc/dnsmasq.conf
ls -al /etc/resolv.conf
ls -al /etc/ssh/sshd_config
```

That's tedious.

Instead, let `find` do it automatically.

---

## `-exec`

`-exec` means:

> **"For every file you find, execute another command."**

Syntax:

```
find ... -exec COMMAND {} \;
```

Think of it as:

```
Find file
     ↓
Run another command on it
```

---

## What does `{}` mean?

`{}` is a **placeholder**.

It means:

> "Replace me with the file that `find` found."

For example, suppose `find` finds:

```
/etc/dnsmasq.conf
```

Then

```
-exec ls -al {} \;
```

becomes

```
ls -al /etc/dnsmasq.conf
```

If it finds

```
/etc/sqlmap/sqlmap.conf
```

it becomes

```
ls -al /etc/sqlmap/sqlmap.conf
```

So `find` is effectively doing:

```
File found
        ↓
Replace {}
        ↓
Run ls -al on that file
```

---

## What does `\;` mean?

The semicolon (`;`) tells `find`:

> **"The command ends here."**

However, the shell also treats `;` as a command separator.

Example:

```
pwd; ls
```

means

```
Run pwd
Then run ls
```

If you wrote:

```
find ... -exec ls -al {} ;
```

the shell would think the command ended at `;` **before** `find` received it.

So we escape it:

```
\;
```

The backslash (`\`) tells the shell:

> "Don't interpret this semicolon—pass it literally to `find`."

---

## Internally

When `find` finds

```
/etc/dnsmasq.conf
```

it executes

```
ls -al /etc/dnsmasq.conf
```

Then it finds

```
/etc/sqlmap/sqlmap.conf
```

and executes

```
ls -al /etc/sqlmap/sqlmap.conf
```

and so on.

---

 │        ▼

# 2. `2>/dev/null`

This is called **redirection**.

Linux programs have three standard streams:

|Number|Name|Purpose|
|---|---|---|
|0|stdin|Input|
|1|stdout|Normal output|
|2|stderr|Error output|

---

Suppose you run

```
find / -name test
```

You'll likely get

```
find: '/root': Permission denied
find: '/proc/1234': Permission denied
find: '/run/user/1000': Permission denied
...
```

These are **error messages**.

They come from **stderr (file descriptor 2)**.

Meanwhile, matching files are printed to **stdout (file descriptor 1)**.

---

## What is `/dev/null`?

`/dev/null` is a special device.

Anything written to it is immediately discarded.

Think of it as a **black hole**.

```
Output
   │
   ▼
/dev/null
   │
   ▼
Gone forever
```

---

## So what does

```
2>/dev/null
```

mean?

Break it down:

```
2
```

means

> Redirect **stderr**.

```
>
```

means

> Send it somewhere else.

```
/dev/null
```

means

> Throw it away.

So

```
2>/dev/null
```

means:

> **Discard all error messages.**

---

## Example

Without redirection:

```
find / -name passwd
```

Output:

```
find: '/root': Permission denied
find: '/proc': Permission denied
/etc/passwd
/usr/share/passwd
```

With

```
find / -name passwd 2>/dev/null
```

Output:

```
/ etc/passwd
/usr/share/passwd
```

Only the useful results remain.

# File Descriptors and Redirections

---

A file descriptor (`FD`) in Unix/Linux operating systems is a reference, maintained by the kernel, that allows the system to manage Input/Output (`I/O`) operations. It acts as a unique identifier for an open file, socket, or any other I/O resource. In Windows-based operating systems, this is known as a file handle. Essentially, the file descriptor is the system's way of keeping track of active `I/O` connections, such as reading from or writing to a file.

Think of it as a ticket number you get when checking in your coat at a coatroom. The ticket (file descriptor) represents your connection to your coat (file or resource), and whenever you need to retrieve your coat (perform I/O), you present the ticket to the attendant (operating system) who knows exactly where your coat is stored (which resource the file descriptor refers to). Without the ticket, you'd have no way of efficiently accessing your coat among the many others stored, just as without a file descriptor, the operating system wouldn't know which resource to interact with. You will soon see why file descriptors are so important and why understanding them is crucial as we dive into the upcoming examples.

By default, the first three file descriptors in Linux are:

1. Data Stream for Input
    - `STDIN – 0`
2. Data Stream for Output
    - `STDOUT – 1`
3. Data Stream for Output that relates to an error occurring.
    - `STDERR – 2`

#### STDIN and STDOUT

Let us see an example with `cat`. When running `cat`, we give the running program our standard input (`STDIN - FD 0`), marked `green`, wherein this case "SOME INPUT" is. As soon as we have confirmed our input with `[ENTER]`, it is returned to the terminal as standard output (`STDOUT - FD 1`), marked **red**.

#### STDOUT and STDERR

In the next example, by using the `find` command, we will see the standard output (`STDOUT - FD 1`) marked in `green` and standard error (`STDERR - FD 2`) marked in red.

        shellsession
`Akshit023@htb[/htb]$ find /etc/ -name shadow`

In this case, the error is marked and displayed with "`Permission denied`". We can check this by redirecting the file descriptor for the errors (`FD 2 - STDERR`) to "`/dev/null`." This way, we redirect the resulting errors to the "null device," which discards all data.

        shellsession
`Akshit023@htb[/htb]$ find /etc/ -name shadow 2>/dev/null`

#### Redirect STDOUT to a File

Now we can see that all errors (`STDERR`) previously presented with "`Permission denied`" are no longer displayed. The only result we see now is the standard output (`STDOUT`), which we can also redirect to a file with the name `results.txt` that will only contain standard output without the standard errors.

        shellsession
`Akshit023@htb[/htb]$ find /etc/ -name shadow 2>/dev/null > results.txt`

![Terminal window with user 'htb-student@nixfund' executing 'find /etc/ -name shadow 2>/dev/null > results.txt' and 'cat results.txt'. Output shows '/etc/shadow'.](https://cdn.services-k8s.prod.aws.htb.systems/content/modules/18/find3.png)

#### Redirect STDOUT and STDERR to Separate Files

We should have noticed that we did not use a number before the greater-than sign (`>`) in the last example. That is because we redirected all the standard errors to the "`null device`" before, and the only output we get is the standard output (`FD 1 - STDOUT`). To make this more precise, we will redirect standard error (`FD 2 - STDERR`) and standard output (`FD 1 - STDOUT`) to different files.

        shellsession
`Akshit023@htb[/htb]$ find /etc/ -name shadow 2> stderr.txt 1> stdout.txt`

#### Redirect STDIN

As we have already seen, in combination with the file descriptors, we can redirect errors and output with greater-than character (`>`). This also works with the lower-than sign (`<`). However, the lower-than sign serves as standard input (`FD 0 - STDIN`). These characters can be seen as "`direction`" in the form of an arrow that tells us "`from where`" and "`where to`" the data should be redirected. We use the `cat` command to use the contents of the file "`stdout.txt`" as `STDIN`.

        shellsession
`Akshit023@htb[/htb]$ cat < stdout.txt`

#### Redirect STDOUT and Append to a File

When we use the greater-than sign (`>`) to redirect our `STDOUT`, a new file is automatically created if it does not already exist. #### Redirect STDIN Stream to a File

We can also use the double lower-than characters (`<<`) to add our standard input through a stream. In the next example, we will use the `cat` command to read our streaming input through the stream and direct it to a file called "`stream.txt`."

#### Pipes

Another way to redirect `STDOUT` is to use pipes (`|`). These are useful when we want to use the `STDOUT` from one program to be processed by another. One of the most commonly used tools is `grep`, which we will use in the next example. Grep is used to filter `STDOUT` according to the pattern we define. In the next example, we use the `find` command to search for all files in the "`/etc/`" directory with a "`.conf`" extension. Any errors are redirected to the "`null device`" (`/dev/null`). # What is `dpkg`?

`dpkg` is the **package manager database tool** on Debian-based Linux distributions (Ubuntu, Kali, Parrot, etc.).

Think of it as a database that keeps track of all software installed on the system.

For example, when you install:

```
sudo apt install nmap
```

`apt` downloads the package, but **`dpkg` records it as installed**.

---

# What does `dpkg -l` do?

The `-l` option means **list**.

```
dpkg -l
```

prints something like:

```
Desired=Unknown/Install/Remove/Purge/Hold
| Status=Not/Installed/Config-files/Unpacked/Half-installed
|/ Err?=(none)/Reinst-required
||/ Name            Version
ii  bash            5.2-2
ii  vim             9.0-1
ii  openssh-server  9.2p1
rc  oldpackage      1.0
un  notinstalled    <none>
```

Notice the **first two letters** on each line.

---

# What does `ii` mean?

Look at one line:

```
ii  bash  5.2-2
```

The first character tells the **desired state**.

The second character tells the **current state**.

---

## First column (Desired)

|Letter|Meaning|
|---|---|
|i|Install|
|r|Remove|
|p|Purge|

---

## Second column (Status)

|Letter|Meaning|
|---|---|
|i|Installed|
|c|Config files remain|
|u|Unpacked|
|f|Half configured|

---

So

```
ii
```

means

```
Desired: Install
Status: Installed
```

In other words,

> **This package is fully installed.**

# What does `rc` mean?

Example:

```
rc oldpackage
```

This means

```
Desired: Remove
Status: Config files remain
```

You removed the package, but Linux kept its configuration files.

So it is **not installed anymore**.

Now we only want the installed packages.

We filter using

`grep`

means

> Search for matching lines.

---

`^`

means

> Beginning of the line.

Example:

```
ii bash
```

starts with

```
ii
```

so it matches.

---

This line

```

```

starts with

```
rc
```

so it does **not** match.

---

This line

```

```

starts with

```
un
```

doesn't match either.

---

So

```
dpkg -l | grep '^ii'
```

returns

```
ii bash
ii vim
ii nmap
ii openssh
```

Everything else disappears.

Now we have

```

How many packages?

Instead of counting manually,

```
wc -l
```

counts the number of lines.

Output

```

```

# Entire flow

```
dpkg -l | grep '^ii' | wc -l
```

Imagine data flowing through pipes:

```
               dpkg -l
                   │
                   ▼
      List every package
                   │
                   ▼
         grep '^ii'
                   │
      Keep only installed packages
                   │
                   ▼
             wc -l
                   │
        Count the remaining lines
                   │
                   ▼
             1837
```

---

# Why not just use `dpkg -l | wc -l`?

Because `dpkg -l` includes:

- Header lines
- Removed packages (`rc`)
- Other package states

For example:

```
Desired=Unknown/Install/Remove...
||/ Name Version
ii bash
ii vim
rc oldpackage
ii nmap
```

`wc -l` would count **everything**, including the headers and non-installed packages.

`grep '^ii'` removes all that noise and leaves only the packages that are actually installed.

---

## Rule of thumb for HTB and OSCP

Whenever you're asked:

> **"How many packages are installed?"**

Use:

```
dpkg -l | grep '^ii' | wc -l
```

It counts **only fully installed packages**, which is almost always what the question is asking.

## Cut

Specific results with different characters may be separated as delimiters. Here it is handy to know how to remove specific delimiters and show the words on a line in a specified position. One of the tools that can be used for this is `cut`. Therefore we use the option "`-d`" and set the delimiter to the colon character (`:`) and define with the option "`-f`" the position in the line we want to output.

        shellsession
`Akshit023@htb[/htb]$ cat /etc/passwd | grep -v "false\|nologin" | cut -d":" -f1 root sync postgres mrb3n cry0l1t3 htb-student`

Think of this command as a **pipeline** where each command does one small job.

```
cat /etc/passwd | grep -v "false\|nologin" | cut -d":" -f1
```

---

## Step 1

```
cat /etc/passwd
```

Prints the contents of `/etc/passwd`.

Example:

```
root:x:0:0:root:/root:/bin/bash
daemon:x:1:1:daemon:/usr/sbin:/usr/sbin/nologin
postgres:x:1001:1001::/var/lib/postgresql:/bin/bash
htb-student:x:1000:1000::/home/htb-student:/bin/bash
```

Each line has **fields separated by `:`**.

---

## Step 2

```
grep -v "false\|nologin"
```

- `grep` = search
- `-v` = **invert** (exclude matching lines)

It removes users whose shell is:

- `false`
- `nologin`

So this:

```
daemon:x:1:1:daemon:/usr/sbin:/usr/sbin/nologin
```

gets removed.

Remaining:

```
root:x:0:0:root:/root:/bin/bash
postgres:x:1001:1001::/var/lib/postgresql:/bin/bash
htb-student:x:1000:1000::/home/htb-student:/bin/bash
```

These are users who can actually log in.

---

## Step 3

```
cut -d":" -f1
```

This is the important part.

### `-d ":"`

`-d` means **delimiter**.

Here the delimiter is:

```
:
```

So `cut` splits each line wherever it sees a colon.

For example:

```
root:x:0:0:root:/root:/bin/bash
```

becomes

```
Field 1 → root
Field 2 → x
Field 3 → 0
Field 4 → 0
Field 5 → root
Field 6 → /root
Field 7 → /bin/bash
```

---

### `-f1`

`-f` means **field**.

`-f1` means:

> Show **Field 1** only.

So

```
root:x:0:0:root:/root:/bin/bash
```

becomes

```
root
```

and

```
htb-student:x:1000:1000::/home/htb-student:/bin/bash
```

becomes

```
htb-student
```

## Final output

```
root
postgres
htb-student
```

Only the usernames of users who can log in.

## Awk

As we may have noticed, the line for the user "`postgres`" has one column too many. To keep it as simple as possible to sort out such results, the (`g`)`awk` programming is beneficial, which allows us to display the first (`$1`) and last (`$NF`) result of the line.

        shellsession
`Akshit023@htb[/htb]$ cat /etc/passwd | grep -v "false\|nologin" | tr ":" " " | awk '{print $1, $NF}' root /bin/bash sync /bin/sync postgres /bin/bash mrb3n /bin/bash cry0l1t3 /bin/bash htb-student /bin/bash`


`awk` is one of the most powerful text-processing tools in Linux. For HTB and OSCP, you mainly need to know that it **splits each line into fields** and lets you print the fields you want.

Let's break your command down.

---

## Original `/etc/passwd` entry

```
root:x:0:0:root:/root:/bin/bash
```

Fields are separated by `:`.

---

## Step 1

```
tr ":" " "
```

`tr` means **translate characters**.

It replaces every `:` with a space.

So

```
root:x:0:0:root:/root:/bin/bash
```

becomes

```
root x 0 0 root /root /bin/bash
```

Now the fields are separated by spaces.

---

## Step 2

```
awk '{print $1, $NF}'
```

### `$1`

means

> Print the **1st field**

Example:

```
root x 0 0 root /root /bin/bash
```

Field numbers:

```
$1  = root
$2  = x
$3  = 0
$4  = 0
$5  = root
$6  = /root
$7  = /bin/bash
```

So

```
print $1
```

prints

```
root
```

---

### `$NF`

`NF` means

> **Number of Fields**

So `$NF` means

> **The last field**, no matter how many fields there are.

For the line above:

```
root x 0 0 root /root /bin/bash
```

There are **7 fields**, so

```
NF = 7
```

Therefore

```
$NF = $7 = /bin/bash
```

---

## Why not just use `$7`?

Because **not every line has the same number of fields**.

Look at the `postgres` user:

Original:

```
postgres:x:113:118:PostgreSQL administrator,,,:/var/lib/postgresql:/bin/bash
```

After `tr`:

```
postgres x 113 118 PostgreSQL administrator,,, /var/lib/postgresql /bin/bash
```

Now the fields are:

```
$1 = postgres
$2 = x
$3 = 113
$4 = 118
$5 = PostgreSQL
$6 = administrator,,,
$7 = /var/lib/postgresql
$8 = /bin/bash
```

Notice:

- `/bin/bash` is **not** field 7 anymore.
- It moved to field 8 because the comment field contains spaces.

If you wrote:

```
print $1, $7
```

you'd get

```
postgres /var/lib/postgresql
```

❌ Wrong.

But

```
print $1, $NF
```

always prints

```
postgres /bin/bash
```

because `NF` automatically adjusts to however many fields are on that line.

---

## Final output

```
cat /etc/passwd \
| grep -v "false\|nologin" \
| tr ":" " " \
| awk '{print $1, $NF}'
```

Produces:

```

sync        /bin/sync
postgres    /bin/bash
mrb3n       /bin/bash
cry0l1t3    /bin/bash
htb-student /bin/bash
```

|Expression|Meaning|
|---|---|
|`$1`|First field|
|`$2`|Second field|
|`$3`|Third field|
|`$NF`|Last field|

## Sed

There will come moments when we want to change specific names in the whole file or standard input. One of the tools we can use for this is the stream editor called `sed`. One of the most common uses of this is substituting text. Here, `sed` looks for patterns we have defined in the form of regular expressions (regex) and replaces them with another pattern that we have also defined. Let us stick to the last results and say we want to replace the word "`bin`" with "`HTB`."

The "`s`" flag at the beginning stands for the substitute command. Then we specify the pattern we want to replace. After the slash (`/`), we enter the pattern we want to use as a replacement in the third position. Finally, we use the "`g`" flag, which stands for replacing all matches.

        shellsession
`Akshit023@htb[/htb]$ cat /etc/passwd | grep -v "false\|nologin" | tr ":" " " | awk '{print $1, $NF}' | sed 's/bin/HTB/g' root /HTB/bash sync /HTB/sync postgres /HTB/bash mrb3n /HTB/bash cry0l1t3 /HTB/bash htb-student /HTB/bash`

Good observation. **Sometimes yes, but not in general.** That's exactly why `sed` exists.

Let's compare them.

---

## `tr` (translate characters)

`tr` works on **individual characters**, not words.

Example:

```
echo "bin" | tr "b" "H"
```

Output:

```
Hin
```

Or

```
echo "bin" | tr "bin" "HTB"
```

Output:

```
HTB
```

Why?

Because `tr` performs **character-by-character mapping**:

```
b → H
i → T
n → B
```

It does **not** know that `"bin"` is a word.

---

### What if there is another word?

```
echo "binary" | tr "bin" "HTB"
```

Output:

```
HTBary
```

It changed every `b`, `i`, and `n` individually.

It did **not** replace the word `"bin"`.

---

# `sed`

`sed` works on **strings/patterns**.

Example:

```
echo "/bin/bash" | sed 's/bin/HTB/g'
```

Output:

```
/HTB/bash
```

Here, `sed` looks for the **substring** `"bin"` and replaces the whole substring with `"HTB"`.

---

## Why not use `tr` here?

Suppose you want to replace:

```
bash
```

with

```
zsh
```

With `sed`:

```
echo "/bin/bash" | sed 's/bash/zsh/'
```

Output:

```
/bin/zsh
```

Can `tr` do this?

No.

Because `tr` only maps one character to another.

---

## Another example

Suppose you have

```
administrator
administrator
administrator
```

You want

```
admin
admin
admin
```

With `sed`:

```
sed 's/administrator/admin/g'
```

Done.

With `tr`?

Impossible.

`tr` cannot replace a 13-character word with a 5-character word.

---

# Think of it this way

### `tr`

```
Input:

banana

Character mapping:

a → X

Output:

bXnXnX
```

It only knows characters.

---

### `sed`

```
Input:

banana

Replace:

ana → XYZ

Output:

bXYZna
```

It understands substrings (patterns), not just individual characters.

---

## In your HTB example

They used:

```
sed 's/bin/HTB/g'
```

because they're teaching the **substitute (`s`) command** in `sed`.

Could you get the same output with:

```
tr "bin" "HTB"
```

**Yes, in this very specific example**, because:

- `b → H`
- `i → T`
- `n → B`

happens to produce the same visible result for `/bin/bash`.

But it's mostly a coincidence. The moment you need to replace **words**, **substrings**, or **regular expression matches**, `tr` can't do it, while `sed` can.

### Rule of thumb

- **`tr`** → replace or delete **single characters**.
- **`sed`** → replace **words, substrings, or regex patterns**.

In penetration testing, you'll use `sed` far more often because logs, configs, and command output usually require pattern-based editing rather than simple character translation.

**`wc` stands for _Word Count_**, but it can count more than just words.

# Regular Expressions

---

Regular expressions (`RegEx`) are like the art of crafting precise blueprints for searching patterns in text or files. They allow you to find, replace, and manipulate data with incredible precision. Think of RegEx as a highly customizable filter that lets you sift through strings of text, looking for exactly what you need—whether it's analyzing data, validating input, or performing advanced search operations.

At its core, a regular expression is a sequence of characters and symbols that together form a search pattern. These patterns often involve special symbols called metacharacters, which define the structure of the search rather than representing literal text. For example, metacharacters allow you to specify whether you're searching for digits, letters, or any character that fits a certain pattern.

RegEx is available in many programming languages and tools, such as grep or sed, making it a versatile and powerful tool in a our toolkit.

---

## Grouping

Among other things, regex offers us the possibility to group the desired search patterns. Basically, regex follows three different concepts, which are distinguished by the three different brackets:

### Grouping Operators

||**Operators**|**Description**|
|---|---|---|
|1|`(a)`|The round brackets are used to group parts of a regex. Within the brackets, you can define further patterns which should be processed together.|
|2|`[a-z]`|The square brackets are used to define character classes. Inside the brackets, you can specify a list of characters to search for.|
|3|`{1,10}`|The curly brackets are used to define quantifiers. Inside the brackets, you can specify a number or a range that indicates how often a previous pattern should be repeated.|
|4|`\|`|Also called the OR operator and shows results when one of the two expressions matches|
|5|`.*`|Operates similarly to an AND operator by displaying results only when both expressions are present and match in the specified order|

Suppose we use the `OR` operator. The regex searches for one of the given search parameters. In the next example, we search for lines containing the word `my` or `false`. To use these operators, you need to apply the extended regex using the `-E` option in grep.

#### OR operator

        shellsession
`cry0l1t3@htb:~$ grep -E "(my|false)" /etc/passwd lxd:x:105:65534::/var/lib/lxd/:/bin/false pollinate:x:109:1::/var/cache/pollinate:/bin/false mysql:x:116:120:MySQL Server,,:/nonexistent:/bin/false`

Since one of the two search parameters always occurs in the three lines, all three lines are displayed accordingly. However, if we use the `AND` operator, we will get a different result for the same search parameters.

#### AND operator

        shellsession
`cry0l1t3@htb:~$ grep -E "(my.*false)" /etc/passwd mysql:x:116:120:MySQL Server,,:/nonexistent:/bin/false`

Basically, what we are saying with this command is that we are looking for a line where we want to see both `my` and `false`. A simplified example would also be to use `grep` twice and look like this:

        shellsession
`cry0l1t3@htb:~$ grep -E "my" /etc/passwd | grep -E "false" mysql:x:116:120:MySQL Server,,:/nonexistent:/bin/false`

# Permission Management

---

In Linux, permissions are like keys that control access to files and directories. These permissions are assigned to both users and groups, much like keys being distributed to specific individuals and teams within an organization. Each user can belong to multiple groups, and being part of a group grants additional access rights, allowing users to perform specific actions on files and directories.

Every file and directory has an owner (a user) and is associated with a group. The permissions for these files are defined for both the owner and the group, determining what actions—like reading, writing, or executing—are allowed. When you create a new file or directory, it automatically becomes "yours" and is associated with the group you belong to, similar to how a project within a company might default to your team’s oversight.

In essence, Linux permissions act like a set of rules or keys that dictate who can access or modify certain resources, ensuring security and proper collaboration across the system.

When a user wants to access the contents of a Linux directory, it's similar to unlocking a door before stepping inside. To "traverse" or navigate into a directory, the user must first have the right key—this key is the `execute` permission on the directory. Without it, even if the contents of the directory are visible to the user, they won't be able to enter or move through it.

In other words, having `execute` permissions on a directory is like having permission to walk through a hallway to access the rooms inside. It doesn't allow you to see or modify what's inside, but it does grant you the ability to step inside and explore the directory's structure. Without this permission, the user cannot access the directory's contents and will instead be presented with a “`Permission Denied`" error message.

        shellsession
`cry0l1t3@htb[/htb]$ ls -l drw-rw-r-- 3 cry0l1t3 cry0l1t3   4096 Jan 12 12:30 scripts cry0l1t3@htb[/htb]$ ls -al mydirectory/ ls: cannot access 'mydirectory/script.sh': Permission denied ls: cannot access 'mydirectory/..': Permission denied ls: cannot access 'mydirectory/subdirectory': Permission denied ls: cannot access 'mydirectory/.': Permission denied total 0 d????????? ? ? ? ?            ? . d????????? ? ? ? ?            ? .. -????????? ? ? ? ?            ? script.sh d????????? ? ? ? ?            ? subdirectory`

It is important to note that `execute` permissions are necessary to traverse a directory, no matter the user's level of access. Also, `execute` permissions on a directory do not allow a user to execute or modify any files or contents within the directory, only to traverse and access the content of the directory.

To execute files within the directory, a user needs `execute` permissions on the corresponding file. To modify the contents of a directory (create, delete, or rename files and subdirectories), the user needs `write` permissions on the directory.

The whole permission system on Linux systems is based on the octal number system, and basically, there are three different types of permissions a file or directory can be assigned:

- (`r`) - Read
- (`w`) - Write
- (`x`) - Execute

The permissions can be set for the `owner`, `group`, and `others` like presented in the next example with their corresponding permissions.

        shellsession
`cry0l1t3@htb[/htb]$ ls -l /etc/passwd - rwx rw- r--   1 root root 1641 May  4 23:42 /etc/passwd - --- --- ---   |  |    |    |   |__________| |  |   |   |    |  |    |    |        |_ Date |  |   |   |    |  |    |    |__________ File Size |  |   |   |    |  |    |_______________ Group |  |   |   |    |  |____________________ User |  |   |   |    |_______________________ Number of hard links |  |   |   |_ Permission of others (read) |  |   |_____ Permissions of the group (read, write) |  |_________ Permissions of the owner (read, write, execute) |____________ File type (- = File, d = Directory, l = Link, ... )`

## Change Permissions

We can modify permissions using the `chmod` command, permission group references (`u` - owner, `g` - Group, `o` - others, `a` - All users), and either a `+` or a `-` to add or remove the designated permissions. In the following example, let us assume we have a file called `shell` and we want to change permissions for it so this script is owned by that user, becomes not executable, and set with read/write permissions for all users.

        shellsession
`cry0l1t3@htb[/htb]$ ls -l shell -rwxr-x--x   1 cry0l1t3 htbteam 0 May  4 22:12 shell`

We can then apply `read` permissions for all users and see the result.

        shellsession
`cry0l1t3@htb[/htb]$ chmod a+r shell && ls -l shell -rwxr-xr-x   1 cry0l1t3 htbteam 0 May  4 22:12 shell`

We can also set the permissions for all other users to `read` only using the octal value assignment.

        shellsession
`cry0l1t3@htb[/htb]$ chmod 754 shell && ls -l shell -rwxr-xr--   1 cry0l1t3 htbteam 0 May  4 22:12 shell`

Let us look at all the representations associated with it to understand better how the permission assignment is calculated.

        shellsession
`Binary Notation:                4 2 1  |  4 2 1  |  4 2 1 ---------------------------------------------------------- Binary Representation:          1 1 1  |  1 0 1  |  1 0 0 ---------------------------------------------------------- Octal Value:                      7    |    5    |    4 ---------------------------------------------------------- Permission Representation:      r w x  |  r - x  |  r - -`

If we sum the set bits from the `Binary Representation` assigned to the values from `Binary Notation` together, we get the `Octal Value`. The `Permission Representation` represents the bits set in the `Binary Representation` by using the three characters, which only recognizes the set permissions easier.

## SUID & SGID

In addition to standard user and group permissions, Linux allows us to configure special permissions on files through the Set User ID (`SUID`) and Set Group ID (`SGID`) bits. These bits function like temporary access passes, enabling users to run certain programs with the privileges of another user or group. For example, administrators can use `SUID` or `SGID` to grant users elevated rights for specific applications, allowing tasks to be performed with the necessary permissions, even if the user themselves doesn’t normally have them.

The presence of these permissions is indicated by an `s` in place of the usual `x` in the file's permission set. When a program with the SUID or SGID bit set is executed, it runs with the permissions of the file's owner or group, rather than the user who launched it. This can be useful for certain system tasks but also introduces potential security risks if not used carefully.

One common risk is when administrators, unfamiliar with an application's full functionality, assign `SUID` or `SGID` bits indiscriminately. For example, if the `SUID` bit is applied to a program like `journalctl`, which includes a function to launch a shell from within its interface, any user running this program could execute a shell as root. This grants them complete control over the system, presenting a significant security vulnerability. More information about this and other such applications can be found at [GTFObins](https://gtfobins.github.io/gtfobins/journalctl/).

## Sticky Bit

Sticky bits in Linux are like locks on files within shared spaces. When set on a directory, the sticky bit adds an extra layer of security, ensuring that only certain individuals can modify or delete files, even if others have access to the directory.

Imagine a communal workspace where many people can enter and use the same tools, but each person has their own drawer that only they (or the manager) can open. The sticky bit acts like a lock on these drawers, preventing anyone else from tampering with the contents. In a shared directory, this means only the file's owner, the directory's owner, or the root user (the system administrator) can delete or rename files. Other users can still access the directory but can’t modify files they don’t own.

This feature is especially useful in shared environments, like public directories, where multiple users are working together. By setting the sticky bit, you ensure that important files aren’t accidentally or maliciously altered by someone who shouldn’t have the authority to do so, adding an important safeguard to collaborative workspaces.

        shellsession
`cry0l1t3@htb[/htb]$ ls -l drw-rw-r-t 3 cry0l1t3 cry0l1t3   4096 Jan 12 12:30 scripts drw-rw-r-T 3 cry0l1t3 cry0l1t3   4096 Jan 12 12:32 reports`

In this example, we see that both directories have the sticky bit set. However, the `reports` folder has an uppercase `T`, and the `scripts` folder has a lowercase `t`.

If the sticky bit is capitalized (`T`), then this means that all other users do not have `execute` (`x`) permissions and, therefore, cannot see the contents of the folder nor run any programs from it. The lowercase sticky bit (`t`) is the sticky bit where the `execute` (`x`) permissions have been set.

Excellent question. **Yes, we still use `rwx` permissions.** The sticky bit **does not replace** the normal `rwx` permissions—it **adds an extra rule** on top of them.

Think of it like this:

- **`rwx`** = Who can **read, write, and execute**.
- **Sticky bit** = Who is allowed to **delete or rename** files in a shared directory.

---

## Without Sticky Bit

Suppose we have a shared directory:

```
drwxrwxrwx shared/
```

Permissions:

- Everyone can read (`r`)
- Everyone can write (`w`)
- Everyone can enter the directory (`x`)

Now imagine:

```
shared/
├── alice.txt   (owned by Alice)
├── bob.txt     (owned by Bob)
```

Since everyone has **write permission on the directory**, Bob can delete Alice's file:

```
rm alice.txt
```

✅ Allowed.

---

## With Sticky Bit

Now set the sticky bit:

```
chmod +t shared
```

Permissions become:

```
drwxrwxrwt
```

Everything is **still**:

- Readable
- Writable
- Executable

But now:

- Alice can delete `alice.txt` ✅
- Bob **cannot** delete `alice.txt` ❌
- Root can delete everything ✅

So the sticky bit only changes **deletion and renaming** behavior.

---

## Why isn't `rwx` enough?

Suppose `/tmp` didn't have the sticky bit.

Permissions:

```
drwxrwxrwx
```

Every program creates temporary files there.

If User A creates:

```
/tmp/report.txt
```

Then User B could simply do:

```
rm /tmp/report.txt
```

That would be a security problem.

Instead, `/tmp` is:

```
drwxrwxrwt
```

Notice the **`t`** at the end.

Now User B cannot delete User A's file.

---

# What does `t` replace?

Look at the permissions:

Normal:

```
drwxrwxrwx
         ↑
         x
```

With sticky bit:

```
drwxrwxrwt
         ↑
         t
```

The `t` appears **where the "others execute (x)" permission normally appears**.

It doesn't remove execute—it means:

> **Execute permission is present AND the sticky bit is enabled.**

---

## Lowercase `t`

```
drwxrwxrwt
```

Means:

- Others have execute permission.
- Sticky bit is enabled.

---

## Uppercase `T`

```
drwxrwxrwT
```

Means:

- Sticky bit is enabled.
- Others **do not** have execute permission.

Notice:

Normal:

```
drwxrwxrw-
         -
```

After adding the sticky bit:

```
drwxrwxrwT
         ↑
         T
```

Since there was **no `x`** to replace, Linux shows **`T`** instead of `t`.

---

## Easy way to remember

|Ending|Meaning|
|---|---|
|`x`|Execute permission|
|`t`|Execute permission **+ Sticky Bit**|
|`T`|Sticky Bit **without** execute permission|

So **yes**, we absolutely still follow the `rwx` permission model. The sticky bit is simply an **additional permission** that affects **who may delete or rename files inside a directory**, especially useful for shared directories like `/tmp`.
