# AI Forensics

> How AI/ML capabilities are applied to Digital Forensics & Incident Response (DFIR) — practical tools, limitations, and legal considerations.

---

## Why AI Matters for DFIR

| Capability | How It Helps DFIR |
| ---------- | ----------------- |
| **Data Processing** | Parallelised deep learning & Transformer models process vast log/text datasets in milliseconds — providing classifications and insights that would take analysts days manually |
| **Anomaly Detection** | ML learns what "normal" looks like (users, systems, networks) and flags deviations — turning a haystack into a handful of hay. Can spot patterns humans can't comprehend at scale |
| **Scalability** | Modern infrastructure (cloud, hybrid, remote endpoints) generates more forensic data than ever. AI scales effortlessly across millions of events without proportional staffing increases |

## AI in the Wild — DFIR Tools

| DFIR Task | What AI Enables | Example Tools | How AI Solves It |
| --------- | --------------- | ------------- | ---------------- |
| **Anomaly Detection / UEBA** | Flags unusual user/system behaviour vs learned baseline | Splunk UEBA, Elastic ML, Exabeam | Unsupervised learning (Isolation Forests, Autoencoders) learns baseline; deviations flagged without predefined rules |
| **Phishing & Communication** | Detects phishing emails, flags risky language | Microsoft Defender for O365, Splunk NLP | Transformer models (BERT, RoBERTa) classify based on tone, structure, known attack patterns — detects impersonation, urgency, malicious links |
| **Malware / File Classification** | Classifies files as malicious/benign from static/dynamic features | Microsoft Defender (STAMINA), Cylance, VirusTotal ML | Analyses file metadata, code signatures, sandbox behaviour; trained on large malware corpora |
| **Alert Triage & Prioritisation** | Scores, ranks, and filters alerts to reduce analyst workload | Cortex XSOAR/XSIAM, IBM QRadar Advisor, CrowdStrike Charlotte AI | Analyses past alert data, analyst feedback, and incident outcomes to surface urgent issues first |
| **Timeline & Event Correlation** | Reconstructs attack timelines by clustering/linking logs across sources | Timesketch, Velociraptor, Jupyter-based analysis | Clusters similar events, identifies causal relationships, aligns activity across systems |

## AI Limitations in DFIR

### Probabilistic vs Deterministic

|                 | Traditional Software                                   | AI Systems                                                        |
| --------------- | ------------------------------------------------------ | ----------------------------------------------------------------- |
| **Behaviour**   | Deterministic — same input always produces same output | Probabilistic — predicts likely outputs based on learned patterns |
| **Example**     | Calculator: 5 + 5 = always 10                          | `"Explain phishing"` → different wording each time                |
| **Reliability** | Predictable within defined scope                       | Varies with temperature, prompt, context                          |

> **DFIR problem:** forensics demands **consistent, repeatable results**. Non-determinism can lead to different timelines being reconstructed from the same input data, and slight prompt changes can produce vastly different outputs.

**Best practice:** use AI to **assist** (summarise, surface anomalies, generate leads) — then humans **validate** evidence.

### Accuracy vs Precision vs Recall

When evaluating AI models for threat detection, no single metric tells the full story:

| Metric | What It Measures | Formula | Danger in Isolation |
| ------ | ---------------- | ------- | ------------------- |
| **Accuracy** | Overall correct predictions | Correct / Total | Misleading with imbalanced data — model predicting everything as "benign" on 99 benign + 1 malicious file = 99% accuracy but useless |
| **Precision** | When model says "malicious", how often is it right? | True Positives / All Flagged | Model may only flag obvious threats, missing subtle ones |
| **Recall** | How many actual threats did it catch? | True Positives / All Actual Positives | Model could flag everything as malicious — 100% recall but massive false positives |

> **In security:** typically prioritise **strong recall** (catch threats) with **reasonable precision** (don't drown analysts in false alerts). Always evaluate all three together.

### Garbage In, Garbage Out (GIGO)

The quality of AI output is directly determined by input quality. Bad training data (wrong labels, incomplete, biased, outdated) → model confidently asserting false predictions as fact.

> **DFIR implication:** when AI is used to pursue justice, bad data can mean missed evidence, false accusations, or wrong conclusions. AI can speed up analysis, but **cannot replace analyst judgment**.

## AI & DFIR — Key Application Areas

### Image & Video Forensics

| Technology | What It Does | Application |
| ---------- | ------------ | ----------- |
| **CNN (Convolutional Neural Networks)** | Learns visual patterns using small filters — detects tampering clues humans miss | Image/video analysis, object detection, forgery detection |
| **ELA + CNN Forgery Detection** | ELA highlights compression inconsistencies → CNN classifies regions as forged or genuine | Achieved 94% accuracy ([2024 study](https://peerj.com/articles/cs-2205/)) |
| **Deepfake Detection** | CNN-based detectors analyse subtle inconsistencies in facial videos (blinking, lip-sync, frame artifacts) | Identifying fake CEO videos, impersonation scams, fabricated identity proof ([state-of-the-art accuracy](https://link.springer.com/article/10.1007/s11042-024-20548-6)) |
| **GANs (Generative Adversarial Networks)** | Two neural networks compete — one generates fakes, one detects them; both improve | Arms race: attackers create better fakes, defenders train better detectors on realistic AI-generated forgeries |

### Communication Analysis

- **Phishing Email Detection:** Transformer models (BERT, RoBERTa) achieved **99% accuracy** classifying phishing vs legitimate emails ([study](https://www.mdpi.com/2076-3417/15/6/3396)). Moves beyond rule-based detection (known bad URLs/keywords) → context-aware, deep-learning models that catch new phishing styles
- **Chat Log & Social Media Analysis:** forensic platforms scan massive text datasets for keywords, threat patterns, and suspicious coordination — surfacing relevant communications that manual review would miss
- **Sentiment Analysis:** AI estimates emotional tone (angry, manipulative, threatening, urgent) — useful for identifying harassment, fraud planning, insider risk

### Timeline Reconstruction & User Behaviour

- **Automated Event Timeline:** ML ingests logs, filesystem timestamps, network records from multiple sources → builds a chronological timeline. Especially useful when attackers have deliberately altered logs
- **Anomaly Detection / UEBA:** AI learns what's "normal" per user/system → flags impossible logins, unusual data access, abnormal application behaviour. Applies to both user behaviour and web application traffic (WAF integration)

### Malware Detection & Analysis

- **File Classification:** deep neural networks classify files as malicious/benign — e.g., [Microsoft & Intel STAMINA project](https://www.cyberdefensemagazine.com/stamina-a-new-approach-to-malware-detection-by-microsoft-intel/) converts malware to visual representations for CNN classification
- **Dynamic Analysis:** AI observes runtime behaviour (API call sequences, encryption activity, persistence attempts, network beacons) → converts to 2D images for classification
- **EDR Integration:** ML-based detection is now standard in antivirus and endpoint detection response products

## Legal & Ethical Implications

### Explainability & Transparency

Many AI models are **black boxes** — they don't explain how they reached a conclusion. This clashes with forensic requirements for **transparent, defensible evidence**.

**Case study:** an LLM flagged emails as "suspicious" in civil litigation. Opposing counsel demanded to know *why*. The legal team couldn't explain the model's reasoning → **AI-generated evidence was excluded by the court**.

| Requirement | Why It Matters |
| ----------- | -------------- |
| **Daubert standard** (U.S.) | Expert/scientific testimony must be testable, reliable, accepted, and explainable |
| **Forensic defensibility** | Findings must withstand cross-examination — "the AI said so" is insufficient |

> **Rule:** use AI as a guide (prioritise, surface patterns), then **human expert validates and explains** findings.

### Bias & Fairness

AI trained on historical data inherits any biases in that data — skewed representations, prejudices, language imbalance.

| Context | Bias Risk | Real-World Impact |
| ------- | --------- | ----------------- |
| **Multilingual investigations** | AI better at English → de-prioritises non-English evidence | Relevant communications delayed or missed |
| **Facial recognition** | Higher error rates for minority groups | [At least 7 known wrongful arrests](https://www.aclu.org/news/privacy-technology/police-say-a-simple-warning-will-prevent-face-recognition-wrongful-arrests-thats-just-not-true) in the U.S. due to faulty face recognition — almost every victim was African American |

**Implications:**
1. **Legal:** if defence shows AI technique is biased → judge may exclude results
2. **Ethical:** forensic experts must validate and correct biases (diverse training data, bias audits, testing across groups/languages)

### Accountability & Chain of Custody

Courts require digital evidence to be handled in a **traceable, preservable** manner with integrity at each step.

| Issue | Problem | Solution |
| ----- | ------- | -------- |
| **Accountability** | Who answers for an algorithm's output? AI can't testify. | A human expert must explain and defend results |
| **Chain of custody** | Cloud-based AI tools operate opaquely — intermediate outputs may not be logged | Use on-premises systems, full logging, hashes, audit trails |
| **Privacy & data protection** | Uploading evidence to public cloud AI may expose sensitive data, violating GDPR or court orders | Run AI in secure offline environments; use federated/privacy-preserving methods; minimise data shared |

**Case study:** an LLM was used to summarise a suspect's mobile phone data, but intermediate AI outputs weren't logged → defence challenged forensic findings on procedural grounds due to broken chain of custody.

## DFIR Investigation Framework

A step-by-step methodology for conducting investigations using AI-assisted analysis.

### Thinking Framework

| Step | Action | Objective |
| :--- | :--- | :--- |
| **1. Incident Report** | Review reports of suspicious logins, data theft, or unauthorized access. | Build initial hypothesis (e.g., Account compromise vs. Insider threat). |
| **2. Authentication Trail** | Use AI to classify logs and surface unusual login events (off-hours, failed admin attempts). | Identify initial access, lateral movement, or privilege escalation. |
| **3. Event Correlation** | Question the sequence: Failed login $\to$ Success? Which user? What time? | Move beyond single log lines to establish an attack sequence. |
| **4. File Anomaly Detection** | Inspect artifacts in `/tmp`, hidden names (`.x`), or strange binaries flagged by AI. | Determine attacker activity post-login. |
| **5. Evidence Chain** | Link artifacts (e.g., `invoice_dump.txt` $\to$ Phishing lure $\to$ Macro $\to$ Credential harvesting). | Ensure every clue explains the subsequent attacker action. |
| **6. Initial Access** | Evaluate entry vectors: Brute force, Exploit, Phishing, or Stolen credentials. | Confirm the root cause of the breach. |
| **7. Privilege Escalation** | Check `sudo` logs, bash history, `cron`, SUID, and SSH keys. | Determine how the attacker moved from user to privileged status. |
| **8. Persistence** | Search for disguised binaries, cron jobs, services, or reverse shells. | Identify how access is maintained after reboots or detection. |
| **9. Objective & Impact** | Look for archives, encryption, compression, or unusual outbound traffic. | Understand the "Why": IP theft, espionage, or ransomware. |

### The Golden Reasoning Pattern

Use this structure for every case to ensure comprehensive coverage of the attack lifecycle:

> **Initial Access** $\to$ **Execution** $\to$ **Persistence** $\to$ **Privilege Escalation** $\to$ **Defense Evasion** $\to$ **Collection** $\to$ **Exfiltration**

### AI-Specific Lessons
- **Anomalies $\neq$ Intent:** AI flagged legitimate source code as suspicious because it was "unusual." AI detects patterns; humans determine semantic meaning and malicious intent.

### Investigation Checklist
1. **Entry:** How did they get in? What account was used first?
2. **Action:** What did they run? What did they access?
3. **Control:** How did they escalate? How did they stay persistent?
4. **Outcome:** What was stolen? What evidence proves each step?
