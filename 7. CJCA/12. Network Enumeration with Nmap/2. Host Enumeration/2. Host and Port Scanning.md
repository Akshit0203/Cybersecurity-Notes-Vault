# Host and Port Scanning

---

After discovering that a host is alive, the next goal is to answer:

1. **Which ports are open?**
2. **What services are running?**
3. **What versions are they?**
4. **What operating system is behind them?**

> Think of it like knocking on a house. First: "Is anyone home?" (Host Discovery). Then: "Which doors and windows are open?" (Port Scanning).

---

## Six Port States

Nmap can report six different states for a scanned port:

| State              | Description                                                                                                                                      |
|--------------------|--------------------------------------------------------------------------------------------------------------------------------------------------|
| `open`             | Connection established. A service is listening (TCP, UDP, or SCTP).                                                                              |
| `closed`           | Target responds with an `RST` flag. No service is listening, but the host is reachable.                                                          |
| `filtered`         | No response returned, or an error code received. Nmap cannot determine if the port is open or closed (usually a firewall).                       |
| `unfiltered`       | Only occurs during **TCP-ACK** scan. Port is accessible, but open/closed cannot be determined.                                                    |
| `open\|filtered`   | No response. Could be open or firewall-filtered — Nmap can't tell which.                                                                         |
| `closed\|filtered` | Only occurs during **IP ID idle** scans. Cannot determine if the port is closed or filtered. Rarely seen.                                         |

## Discovering Open TCP Ports

### Default Behavior

When you run `nmap <target>` without specifying ports or scan type:

- Nmap scans the **top 1000 TCP ports**
- As **root** → uses `-sS` (SYN scan)
- As **non-root** → uses `-sT` (Connect scan), because raw packets require root privileges

### Specifying Ports

| Method                   | Command                         | Scans                     |
|--------------------------|---------------------------------|---------------------------|
| Individual ports         | `nmap -p 22,25,80,139,445`     | Only listed ports         |
| Range                    | `nmap -p 22-445`               | Port 22 through 445      |
| Top N ports              | `nmap --top-ports=10`          | 10 most common TCP ports |
| Fast scan                | `nmap -F`                      | Top 100 ports             |
| All TCP ports            | `nmap -p-`                     | Ports 1–65535             |

## Tracing Packets (`--packet-trace`)

To see exactly what Nmap sends and receives, use `--packet-trace`. Disable ICMP echo (`-Pn`), DNS resolution (`-n`), and ARP ping (`--disable-arp-ping`) for a clear view:

```bash
sudo nmap 10.129.2.28 -p 21 --packet-trace -Pn -n --disable-arp-ping
```

```
SENT (0.0429s) TCP 10.10.14.2:63090 > 10.129.2.28:21 S ttl=56 id=57322 iplen=44  seq=1699105818 win=1024 <mss 1460>
RCVD (0.0573s) TCP 10.129.2.28:21 > 10.10.14.2:63090 RA ttl=64 id=0 iplen=40  seq=0 win=0

PORT   STATE  SERVICE
21/tcp closed ftp
```

### Understanding the SENT Line

| Field                        | Meaning                                                    |
|------------------------------|------------------------------------------------------------|
| `SENT (0.0429s)`             | Nmap sent a packet to the target                           |
| `TCP`                        | Protocol used                                              |
| `10.10.14.2:63090 >`        | Our IP and source port                                     |
| `10.129.2.28:21`            | Target IP and target port                                  |
| `S`                          | **SYN** flag — initiating connection                       |
| `ttl=56 id=57322 iplen=44...`| Additional TCP header parameters                          |

### Understanding the RCVD Line

| Field                        | Meaning                                                    |
|------------------------------|------------------------------------------------------------|
| `RCVD (0.0573s)`             | Received a packet from the target                          |
| `10.129.2.28:21 >`          | Target's IP and source port                                |
| `10.10.14.2:63090`          | Our IP and port being replied to                           |
| `RA`                         | **RST + ACK** flags — port is closed, connection refused   |

## TCP Connect Scan (`-sT`)

Unlike the SYN scan, the Connect Scan **completes the full three-way handshake**:

```
Client                 Server

SYN ------------------>

<------------------ SYN-ACK

ACK ------------------>
```

Connection fully established.

| Aspect         | Detail                                                                           |
|----------------|---------------------------------------------------------------------------------|
| **Accuracy**   | Very high — confirms exact port state                                            |
| **Stealth**    | Low — fully establishes a connection, creates logs, easily detected by IDS/IPS   |
| **Use case**   | When accuracy is a priority; behaves like a normal client ("polite" scan)         |

> SYN scan (`-sS`) is stealthier because it doesn't complete the handshake, minimizing the chance of triggering connection logs.

### Example: Connect Scan on TCP Port 443

```bash
sudo nmap 10.129.2.28 -p 443 --packet-trace --disable-arp-ping -Pn -n --reason -sT
```

```
CONN (0.0385s) TCP localhost > 10.129.2.28:443 => Operation now in progress
CONN (0.0396s) TCP localhost > 10.129.2.28:443 => Connected

PORT    STATE SERVICE REASON
443/tcp open  https   syn-ack
```

## Filtered Ports

When a port is shown as `filtered`, it means a firewall is handling the packets. Firewalls behave in two ways:

### 1. Drop (Silent)

```
You → SYN → Firewall → (Drops packet) → No Response
```

- Nmap receives nothing
- By default, Nmap retries up to 10 times (`--max-retries`)
- Scan takes much longer (e.g. `~2.06s` vs `~0.05s`)
- Result: `filtered`

```bash
sudo nmap 10.129.2.28 -p 139 --packet-trace -n --disable-arp-ping -Pn
```

```
SENT (0.0381s) TCP 10.10.14.2:60277 > 10.129.2.28:139 S ttl=47 id=14523 iplen=44  seq=4175236769 win=1024 <mss 1460>
SENT (1.0411s) TCP 10.10.14.2:60278 > 10.129.2.28:139 S ttl=45 id=7372 iplen=44  seq=4175171232 win=1024 <mss 1460>

PORT    STATE    SERVICE
139/tcp filtered netbios-ssn
Nmap done: 1 IP address (1 host up) scanned in 2.06 seconds
```

Two SYN packets sent, no response, scan took ~2 seconds.

### 2. Reject (ICMP Response)

```
You → SYN → Firewall → ICMP Port Unreachable
```

- Nmap immediately knows communication is blocked
- Still reported as `filtered`, but finishes much faster

```bash
sudo nmap 10.129.2.28 -p 445 --packet-trace -n --disable-arp-ping -Pn
```

```
SENT (0.0388s) TCP 10.129.2.28:52472 > 10.129.2.28:445 S ttl=49 id=21763 iplen=44  seq=1418633433 win=1024 <mss 1460>
RCVD (0.0487s) ICMP [10.129.2.28 > 10.129.2.28 Port 445 unreachable (type=3/code=3) ] IP [ttl=64 id=20998 iplen=72 ]

PORT    STATE    SERVICE
445/tcp filtered microsoft-ds
Nmap done: 1 IP address (1 host up) scanned in 0.05 seconds
```

> ICMP `type 3/code 3` = port unreachable. If we know the host is alive, we can strongly assume the firewall is rejecting packets on this port.

## Discovering Open UDP Ports

UDP is a **stateless protocol** — no three-way handshake. Nmap sends empty datagrams and waits for responses. Consequences:

- Timeout is much longer → **UDP scans are much slower** than TCP scans
- Many services don't respond even when the port is open
- Cannot always determine if the packet arrived

### Basic UDP Scan

```bash
sudo nmap 10.129.2.28 -F -sU
```

```
PORT     STATE         SERVICE
68/udp   open|filtered dhcpc
137/udp  open          netbios-ns
138/udp  open|filtered netbios-dgm
631/udp  open|filtered ipp
5353/udp open          zeroconf
Nmap done: 1 IP address (1 host up) scanned in 98.07 seconds
```

| Option | Description           |
|--------|-----------------------|
| `-F`   | Scans top 100 ports   |
| `-sU`  | Performs a UDP scan    |

### UDP Port States

**Open** — application responds:

```bash
sudo nmap 10.129.2.28 -sU -Pn -n --disable-arp-ping --packet-trace -p 137 --reason
```

```
SENT (0.0367s) UDP 10.10.14.2:55478 > 10.129.2.28:137 ttl=57 id=9122 iplen=78
RCVD (0.0398s) UDP 10.129.2.28:137 > 10.10.14.2:55478 ttl=64 id=13222 iplen=257

PORT    STATE SERVICE    REASON
137/udp open  netbios-ns udp-response ttl 64
```

**Closed** — target replies with ICMP Port Unreachable (`type=3/code=3`):

```bash
sudo nmap 10.129.2.28 -sU -Pn -n --disable-arp-ping --packet-trace -p 100 --reason
```

```
SENT (0.0445s) UDP 10.10.14.2:63825 > 10.129.2.28:100 ttl=57 id=29925 iplen=28
RCVD (0.1498s) ICMP [10.129.2.28 > 10.10.14.2 Port unreachable (type=3/code=3) ] IP [ttl=64 id=11903 iplen=56 ]

PORT    STATE  SERVICE REASON
100/udp closed unknown port-unreach ttl 64
```

**Open|Filtered** — no response at all:

```bash
sudo nmap 10.129.2.28 -sU -Pn -n --disable-arp-ping --packet-trace -p 138 --reason
```

```
SENT (0.0380s) UDP 10.10.14.2:52341 > 10.129.2.28:138 ttl=50 id=65159 iplen=28
SENT (1.0392s) UDP 10.10.14.2:52342 > 10.129.2.28:138 ttl=40 id=24444 iplen=28

PORT    STATE         SERVICE     REASON
138/udp open|filtered netbios-dgm no-response
Nmap done: 1 IP address (1 host up) scanned in 2.06 seconds
```

## Version Detection (`-sV`)

One of the most important scans. Instead of just reporting a port is open, `-sV` **probes the service** to identify names, versions, and additional host information.

```bash
sudo nmap 10.129.2.28 -Pn -n --disable-arp-ping --packet-trace -p 445 --reason -sV
```

```
PORT    STATE SERVICE     REASON         VERSION
445/tcp open  netbios-ssn syn-ack ttl 63 Samba smbd 3.X - 4.X (workgroup: WORKGROUP)
Service Info: Host: Ubuntu
```

| Option    | Description                                |
|-----------|--------------------------------------------|
| `-sV`     | Performs service version detection          |

> This is extremely valuable because exploits often depend on **service versions**, not just port numbers.

## Common Commands to Remember

| Command                       | Purpose                           |
|-------------------------------|-----------------------------------|
| `nmap target`                 | Default scan (top 1000 TCP ports) |
| `nmap --top-ports=10 target`  | Scan top 10 ports                 |
| `nmap -F target`              | Fast scan (top 100 ports)         |
| `nmap -p- target`             | Scan all TCP ports                |
| `nmap -p 80,443 target`      | Scan selected ports               |
| `nmap -sS target`            | SYN scan                          |
| `nmap -sT target`            | Connect scan                      |
| `nmap -sU target`            | UDP scan                          |
| `nmap -sV target`            | Service/version detection          |
| `--packet-trace`             | Show packets                       |
| `--reason`                   | Explain scan result                |
| `-Pn`                        | Skip host discovery                |
| `-n`                         | Disable DNS resolution             |

## Key Takeaways

- Always perform **host discovery first**, then scan ports
- Know the **six Nmap port states**: `open`, `closed`, `filtered`, `unfiltered`, `open|filtered`, `closed|filtered`
- Default behavior:
    - **Root** → `-sS` (SYN scan)
    - **Non-root** → `-sT` (Connect scan)
- Use:
    - `-p-` to scan **all 65,535 TCP ports**
    - `-F` for a quick scan of the top 100 ports
    - `--top-ports=10` for the most common ports
- **TCP SYN Scan (`-sS`)** is faster and stealthier — doesn't complete the handshake
- **TCP Connect Scan (`-sT`)** completes the handshake — more accurate but more detectable
- **UDP scans (`-sU`)** are slower because UDP has no handshake and many services don't respond
- **`-sV` (Version Detection)** is one of the most important options — identifies service names, versions, and sometimes additional host info that can directly guide exploitation
