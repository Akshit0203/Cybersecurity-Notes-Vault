# The AI Infrastructure Stack

---

## Overview

When you scan a traditional network, you know what to expect. Web servers on ports 80 and 443. SSH on 22. Databases on 3306 or 5432. You have seen these a hundred times. AI infrastructure looks nothing like that. It runs on ports most security professionals have never targeted, speaks protocols that standard HTTP scanners misinterpret, and exposes APIs that return data formats you will not find in any conventional web application.

Before we start probing anything, we need a mental map of the components. Think of this task as building your target list.

## Detailed Component Breakdown

### Model Serving Endpoints

These are the frameworks that load trained models into memory and expose prediction APIs. They are the front door of any AI deployment.

- **NVIDIA Triton Inference Server** — Exposes HTTP on port 8000, gRPC on port 8001, and Prometheus metrics on port 8002. Three ports for one service. Think of it as the "AI engine server."
  - 🔥 Risk: Exposed inference APIs, model abuse, prompt injection, model extraction
- **TensorFlow Serving** — Uses gRPC on 8500 and HTTP on 8501. Specifically for TensorFlow models.
- **TorchServe** — Exposes inference on 8080, a management API on 8081, and metrics on 8082. Official serving framework for PyTorch.
- **Ollama** — Runs on port 11434. Used for local LLM deployments (local ChatGPT-like systems, offline AI).
  - 🔥 Risk: Local model exposure, prompt injection, weak auth
- **vLLM** — Typically serves on port 8000. High-speed LLM serving engine, optimized for large-scale inference with OpenAI-compatible API format.

> [!NOTE] Why HTTP and gRPC?
> gRPC is faster for streaming large tensor payloads between internal services. HTTP/REST is easier for client applications to consume. So they run both.

---

### Orchestration and Experiment Tracking

These platforms manage the entire ML lifecycle, from experiment design through to model deployment. They are the **highest-value targets** during reconnaissance because they contain everything.

- **MLflow Tracking Server** — Port 5000. Records every experiment, every hyperparameter configuration, every training metric, and every model artifact the organisation produces. If you find an open MLflow instance, you have found their complete ML research history. Think of it as "GitHub + dashboard for ML."
  - 🔥 Risk: Model tampering, malicious model upload
- **Kubeflow** — Runs on Kubernetes (ports 80/443). Orchestrates training pipelines, notebook servers, and model deployments.
  - 🔥 Risk: Cluster compromise, pipeline abuse
- **Ray** — Dashboard on port 8265, server endpoint on port 8000. Distributed computing for AI — splits workloads across machines. The ShadowRay campaign targeted exactly this dashboard.
  - 🔥 Risk: Remote job execution, cluster abuse

---

### Vector Databases

These store embeddings (numerical representations of documents) and power semantic search for RAG pipelines. If an organisation has an AI chatbot or knowledge assistant, there is almost certainly a vector database behind it.

- **Qdrant** — Port 6333 for HTTP and 6334 for gRPC. Used in Retrieval-Augmented Generation.
  - 🔥 Risk: RAG poisoning, malicious document retrieval
- **Weaviate** — Port 8080. Includes a GraphQL endpoint and built-in module system.
- **Milvus** — Port 19530. Handles huge embedding datasets via gRPC.
- **Chroma** — Port 8000.

> [!TIP] Recon Value
> Schema endpoints reveal which embedding model the system uses and what kind of data it contains. A collection called "internal-hr-policies" with 768-dimensional vectors tells you quite a lot about what that RAG system is doing.

---

### Model Registries

A model registry stores the actual model files — serialised **.pkl, .pt, .onnx**, and **.mar** files, along with version history, stage transitions (staging, production, archived), artifact URIs pointing to cloud storage, and the identity of who created each version. An unsecured registry is the single highest-value reconnaissance target. It maps the organisation's entire ML product portfolio in one place.

---

### Supporting Infrastructure

- **Jupyter Notebooks** (port 8888) — Often run with `--ip=0.0.0.0` and no authentication. That **gives direct terminal access to anyone who reaches the port**. Data scientists also routinely store cleartext credentials in notebook cells. 🔥 VERY HIGH risk — executes arbitrary Python code, often weakly secured, common attack target.
- **MinIO** (ports 9000 and 9001) — Provides S3-compatible object storage for model artifacts. Bucket listing is frequently enabled. Think of it as "private AWS S3."
  - 🔥 Risk: Exposed buckets, data leaks
- **Prometheus Metrics** (Triton on 8002, TorchServe on 8082) — Leak model names, batch sizes, GPU utilisation, and inference latency. You can map the entire deployment topology without ever touching the inference API.
  - 🔥 Risk: Information leakage, infrastructure recon

## Port and Protocol Reference Table

> [!IMPORTANT]
> This is the reference table you will use for the rest of this room. Keep it handy.

| Component | Default Port(s) | Protocol(s) | Recon Endpoints |
|---|---|---|---|
| **NVIDIA Triton** _(Loads models into memory and serves predictions at scale)_ | 8000, 8001, 8002 | HTTP, gRPC, Prometheus | `/v2/health/ready`, `/v2/models` |
| **TensorFlow Serving** _(Google's model serving framework for TensorFlow models)_ | 8500, 8501 | gRPC, HTTP | `/v1/models/<name>` |
| **TorchServe** _(PyTorch's official model serving framework)_ | 8080, 8081, 8082 | HTTP | `/ping`, `/models` |
| **Ollama** _(Local runtime for running LLMs on your own hardware)_ | 11434 | HTTP | `/api/tags`, `/api/show` |
| **vLLM** _(High-throughput LLM serving engine with OpenAI-compatible API)_ | 8000 | HTTP | `/v1/models` |
| **MLflow** _(Tracks experiments, stores models, and manages the ML lifecycle)_ | 5000 | HTTP | `/api/2.0/mlflow/experiments/search` |
| **Kubeflow** _(Kubernetes-native platform for orchestrating ML pipelines)_ | 80, 443 | HTTP | `/pipeline/apis/v1beta1/pipelines` |
| **Ray** _(Distributed compute framework for scaling AI workloads)_ | 8265, 8000 | HTTP | `/api/jobs/`, Ray Dashboard |
| **Qdrant** _(Vector database for semantic search and RAG pipelines)_ | 6333, 6334 | HTTP, gRPC | `/collections` |
| **Weaviate** _(Vector database with built-in GraphQL and module system)_ | 8080 | HTTP, GraphQL | `/v1/schema`, `/v1/meta` |
| **Milvus** _(Distributed vector database for large-scale embedding storage)_ | 19530 | gRPC | Port 19530 connection |
| **Jupyter Notebook** _(Interactive coding environment used by data scientists)_ | 8888 | HTTP | `/api/kernels`, `/api/contents` |
| **MinIO** _(S3-compatible object storage often used for model artifacts)_ | 9000, 9001 | HTTP (S3-compatible) | Bucket listing |
| **Prometheus metrics** _(Exposed by Triton on 8002, TorchServe on 8082, etc.)_ | 8002, 8082 | HTTP | `/metrics` |

That is 14 components across 20+ ports. Compare that to a traditional web application, which might add 3–5 ports to a network. Adding an AI stack roughly **triples the attack surface** at the network layer alone.

### Protocol Quick Reference

| Protocol   | Meaning                     |
| ---------- | --------------------------- |
| HTTP       | Normal web communication    |
| gRPC       | Faster API communication    |
| GraphQL    | Flexible query API          |
| Prometheus | Metrics/monitoring data     |

## Case Study: What Exposed AI Infrastructure Actually Looks Like

In Task 1, we mentioned that a January 2026 Shodan scan found 42,665 exposed AI agent instances. The most commonly exposed services included:

- MLflow dashboards sitting on port 5000 with no authentication
- Unauthenticated Jupyter notebooks on port 8888, some already compromised with cryptomining malware (Monero miners like peer2profit), deployed by earlier attackers who found them first
- Open Ray dashboards on port 8265
- Triton inference endpoints on port 8000

These were not isolated findings. They were connected systems. IBM X-Force documented this pattern in their [2025 research on ML training infrastructure attacks](https://www.ibm.com/think/x-force/becoming-the-trainer-attacking-ml-training-infrastructure).

### Attack Chain Example

In one case, they mapped a complete chain where every component trusted the network boundary, so compromising one compromised the rest:

```
1. Jupyter Notebook (exposed on Azure ML)
   └── contained cleartext MLflow credentials in a notebook cell

2. MLflow Tracking Server
   └── model registry contained artifact URIs

3. S3 Storage Buckets
   └── held the actual model files, datasets, artifacts
```

> [!WARNING] Core Problem
> Every component trusted: "If request comes from inside network, it must be safe." No strong internal security. One weak point compromised the entire ML pipeline.

### Shodan Dorks That Found These

The queries were not complicated:

| Dork | Target |
|---|---|
| `port:5000 "MLflow"` | Exposed MLflow instances |
| `port:8888 title:"Home Page - Select or create a notebook"` | Unauthenticated Jupyter notebooks |
| `http.title:"Ray Dashboard"` | Exposed Ray cluster dashboards |
| `port:8001 "triton"` | Triton gRPC endpoints |

Simple queries. Massive results. If you know the ports and the service banners, finding AI infrastructure is not hard. The hard part is knowing to look in the first place.

> [!NOTE] What Is a Shodan Dork?
> Shodan is like "Google for exposed servers/devices." Instead of websites, it indexes ports, banners, dashboards, and services. Each AI service has default ports and recognizable titles/banners, making them easy to discover if publicly accessible.

> [!WARNING] The Real Problem
> Admins expose these services publicly — no auth, weak auth, internal dashboards reachable from the internet. Then Shodan indexes them automatically. The attack isn't sophisticated — the exposure itself is the vulnerability.

> [!WARNING] Did You Check the Full Port Range?
> The initial scan only checked `5000,6333,6334,8000,8001,8002,8888,9000,9001`. But the reference table also includes:
>
> - 11434 (Ollama)
> - 8080/8081/8082 (TorchServe / Weaviate)
> - 8500/8501 (TensorFlow Serving)
> - 8265 (Ray)
>
> There could still be hidden AI services on these ports.

> [!IMPORTANT] Key Lesson
> Traditional recon targets `80, 443, 22`. AI recon requires scanning many specialized ports. AI infrastructure dramatically expands the attack surface, and knowing the default ports makes reconnaissance and discovery much easier.
