# Fingerprinting AI Services

---

## Overview

In Task 2, we built a mental map of the AI infrastructure stack: components, ports, and protocols. Now we need to figure out what is actually running behind each open port. This is where **fingerprinting** comes in.

Standard service detection (`nmap -sV`) often mislabels AI services. It sees HTTP on port `8000` and calls it `"http-alt"`. It sees gRPC on port 8001 and does not know what to do with it. If you rely on the default Nmap output alone, you will miss what these services actually are.

Fingerprinting AI services requires a different approach — you need to look at:

- HTTP headers
- JSON response structures
- Error messages
- Endpoint naming conventions

Each AI framework has its own distinct signature, and once you know what to look for, identification becomes quick and reliable.

## 1. HTTP Header Fingerprinting

Response headers are often the fastest way to identify an AI framework. Many inference engines broadcast their identity unless an administrator specifically masks them behind a reverse proxy.

- **TorchServe** returns a `Server: TorchServe/0.x.x` header.
    - That is a direct identification with no ambiguity.
- **Triton Inference Server** includes a `NV-Status` header in its responses.
    - It also responds to a specific request header: if you send `endpoint-load-metrics-format: text`, Triton returns hardware telemetry (CPU and GPU utilisation numbers) directly in the response headers.
    - No other framework does this: if you see GPU utilisation data in an HTTP header, you are talking to Triton.
- **FastAPI-based ML** services show `server: uvicorn` in the response.
    - When you combine that with routes like `/predict` or `/embeddings`, you have a strong indicator of a Python ML backend.
- **OpenAI-compatible wrappers** (vLLM, LiteLLM, Ollama) return `x-request-id` headers and structured JSON with an `"object": "model"` field on their `/v1/models` endpoint.

---

## 2. API Response Signatures

Each framework returns distinctly structured JSON. Once you have seen these a few times, you can identify the framework from the response body alone.

- **TensorFlow Serving** returns: `{"model_version_status": [{"version": "1", "state": "AVAILABLE"}]}`
- **Triton** returns: `{"name": "fraud_detector", "versions": ["1"], "platform": "tensorflow_graphdef"}`
- **MLflow** error responses include stack traces referencing `mlflow.server` and `mlflow.tracking` namespaces. Even the error tells you what you are talking to.
- **OpenAI-compatible endpoints** return: `{"object": "model", "id": "llama-3.1-8b", "created": 1700000000}`

If you hit an endpoint and get back JSON containing `"object": "model"`, you are talking to something that speaks the OpenAI API format. That narrows it down to vLLM, LiteLLM, Ollama, or a custom wrapper.

---

## 3. Error Message Fingerprinting

This is one of the most reliable identification techniques, and it works because AI inference APIs are rigid. They expect specific tensor shapes and data types. Send something wrong, and they complain in ways that reveal exactly what they are.

The technique is simple: **send a deliberately malformed payload and read the error response.**

- Send a flat list of integers to a **TensorFlow Serving endpoint** that expects a complex tensor object → error mentioning `tensorinfo_map`. That string only appears in TF Serving errors.
- Send a bad request to an **MLflow server** → stack trace references `mlflow.server`, `mlflow.tracking`, or `databricks` namespaces.
- **MLflow path traversal errors** (CVE-2024-1558) go further, exposing full server filesystem paths.
- **Databricks Mosaic AI** returns Java exceptions `io.jsonwebtoken.IncorrectClaimException` for malformed tokens. That is an instant identifier.

> [!NOTE] Why This Works
> AI frameworks produce errors that are much more verbose than those in traditional web applications. Data scientists need detailed debugging information during model development. Those debug-friendly defaults rarely get turned off before production deployment.

---

## 4. Endpoint Naming Conventions

Traditional REST APIs use resource nouns: `/users`, `/accounts`, `/products`. AI endpoints use computational action terms that stand out immediately during directory brute-forcing.

- **Inference endpoints:** `/predict`, `/invocations` (the SageMaker convention), `/infer`, `/generate`, `/embeddings`, `/score`
- **Model management:** `/v1/models`, `/v2/models`
- **MLflow internal API:** `/api/2.0/mlflow/` (this prefix is distinctive and does not appear in any other framework)
- **Kubeflow pipelines:** `/pipeline/apis/v1beta1/`

> [!TIP]
> If you are running ffuf or feroxbuster against a target, add these paths to your wordlist. Standard wordlists from SecLists will not include them.

## 5. gRPC Fingerprinting

Many AI services expose gRPC alongside HTTP:

- **Triton** uses gRPC on **port 8001**
- **TensorFlow Serving** uses it on **port 8500**

Traditional HTTP scanners miss these entirely because gRPC is a binary protocol that does not respond to standard HTTP probes.

The tool for this is `grpcurl`. If gRPC reflection is enabled (common in development environments that get pushed to production without hardening), you can dump the entire protobuf schema:

```bash
grpcurl -plaintext target:8001 list
grpcurl -plaintext target:8001 describe inference.GRPCInferenceService
```

That output reveals all available RPCs, the exact structure of every input tensor, and the format of every output. Think of it as the gRPC equivalent of finding a `/openapi.json` file on a REST API.

### What Is gRPC?

gRPC (**g**oogle **R**emote **P**rocedure **C**all) is a high-performance framework for communication between applications, especially **microservices**. It lets one application call a function on another application as if it were a local function, even if they're running on different machines.

Instead of sending REST requests like:

```
GET /users/123
```

you define a service and methods in a **Protocol Buffers (.proto)** file:

```protobuf
service UserService {
  rpc GetUser(GetUserRequest) returns (User);
}
```

The gRPC tools generate client and server code automatically. Your client simply calls:

```python
user = client.GetUser(GetUserRequest(id=123))
```

Behind the scenes, gRPC:

- Serializes the request using **Protocol Buffers (Protobuf)**
- Sends it over **HTTP/2**
- Receives the response
- Deserializes it back into an object

**Why use gRPC?**

- **Fast** — Uses compact binary serialization (Protobuf). Much smaller messages than JSON. Lower latency.
- **Strongly typed** — API contracts are defined in `.proto` files. Client and server code is generated automatically. Reduces serialization and integration bugs.

### gRPC vs REST

| Feature          | gRPC                | REST                |
| ---------------- | ------------------- | ------------------- |
| Transport        | HTTP/2              | HTTP/1.1 or HTTP/2  |
| Data format      | Protobuf (binary)   | JSON (text)         |
| Speed            | Faster              | Slower              |
| Streaming        | Native support      | Limited             |
| Browser support  | Limited             | Excellent           |
| Human-readable   | No                  | Yes                 |
| Code generation  | Automatic           | Optional            |

## 6. TLS Fingerprinting (JA3/JA4)

AI deployments have distinctive TLS signatures because internal service-to-service traffic is dominated by Python libraries (`requests`, `urllib`, gRPC implementations) rather than web browsers. JA3 and JA4 hash analysis can differentiate automated ML pipeline traffic from human web browsing at the network level.

### What Is TLS?

TLS (**Transport Layer Security**) is the protocol that makes **HTTPS** secure. It ensures data exchanged between a client and server is:

- **Confidential** → Nobody can read it while it's in transit
- **Authentic** → You're talking to the real server, not an impostor
- **Tamper-proof** → Nobody can modify the data without detection

Without TLS:

```
You -----------------------> Website

"username=alice
password=123456"
```

Anyone who can observe the network (e.g., someone on the same public Wi-Fi) can read it.

With TLS:

```
You -----------------------> Website

X9F!k2#asL@91...
```

An observer only sees encrypted bytes.

### Where TLS Fits

When you visit `https://google.com`, the sequence is:

```
Browser
     │
     │ DNS Lookup
     ▼
Google IP
     │
     │ TCP Connection
     ▼
TLS Handshake
     │
     ▼
Encrypted HTTP (HTTPS)
```

HTTP happens only after TLS has established a secure connection.

### The TLS Handshake

```
Client                        Server
   |                              |
   |------- ClientHello --------->|
   |<------ ServerHello ----------|
   |<------ Certificate ----------|
   |<------ Key Exchange ---------|
   |------- Key Exchange -------->|
   |                              |
   |==== Encrypted Communication ==|
```

After the handshake, both sides share the same secret encryption keys.

**Step 1 — ClientHello:** The client announces what it supports (TLS version, cipher suites, extensions, curves). This is where **JA3** comes from.

```
ClientHello

TLS Version:      TLS 1.3
Cipher Suites:    TLS_AES_128_GCM_SHA256, TLS_AES_256_GCM_SHA384, TLS_CHACHA20_POLY1305_SHA256
Supported Curves: X25519, secp256r1
Extensions:       SNI, ALPN, Supported Versions, Key Share, Signature Algorithms...
```

The client is essentially saying: "Here's what I support. Pick something we both understand."

**Step 2 — ServerHello:** The server selects one cipher suite and curve from the client's offer.

**Step 3 — Certificate:** The server proves its identity by sending a digital certificate. Your browser verifies: Is it signed by a trusted CA? Has it expired? Does it match the hostname?

**Step 4 — Key Exchange:** Both independently derive **the same symmetric session key** using ECDHE, without ever sending that key directly over the network. An eavesdropper can see the exchanged messages but cannot compute the shared secret.

**Step 5 — Encrypted Communication:** All HTTP requests are now encrypted. Only the client and server can decrypt them.

> [!NOTE] Why Doesn't TLS Use Public-Key Encryption for Everything?
> Public-key cryptography (RSA, ECDSA) is much slower than symmetric encryption. TLS uses a hybrid approach:
> - **Public-key cryptography** → Authenticate the server and establish shared keys
> - **Symmetric encryption (AES or ChaCha20)** → Encrypt all subsequent data efficiently

### What Are Cipher Suites?

A cipher suite defines **how encryption and authentication will work**. For example:

```
TLS_AES_128_GCM_SHA256
```

means:

- Encryption: AES-128
- Mode: GCM
- Hash: SHA-256

The client offers several options, and the server chooses one both support.

### How JA3 Works

JA3 fingerprints the **ClientHello**. Different clients send different ClientHello messages:

Client A:

```
TLS 1.3, Cipher Suites: AES128 AES256 CHACHA20, Extensions: SNI ALPN Supported_Versions Key_Share
```

Client B:

```
TLS 1.3, Cipher Suites: CHACHA20 AES128, Extensions: SNI Supported_Versions
```

Both connections work, but the ClientHello messages are different. JA3 converts those handshake fields into a canonical string and then hashes it:

```
772,4865-4866-4867,0-11-10-13-16
```

becomes:

```
MD5(772,4865-4866-4867,0-11-10-13-16)
↓
e7d705a3286e19ea42f587b344ee6865
```

That hash is the **JA3 fingerprint**.

Different software often produces different ClientHello messages:

| Client              | Typical TLS Fingerprint      |
| ------------------- | ---------------------------- |
| Chrome              | Browser-specific JA3         |
| Firefox             | Different browser JA3        |
| curl                | curl JA3                     |
| Python `requests`   | Python JA3                   |
| Go HTTP client      | Go JA3                       |
| gRPC client         | gRPC/library-specific JA3    |

A network defender can observe the TLS handshake and infer: "This connection looks like Chrome," or "This looks like a Python automation script," or "These 1,000 requests all come from the same tool, even though the IPs are different."

> [!IMPORTANT]
> JA3 does not decrypt TLS traffic. It only fingerprints the unencrypted **ClientHello**, which must be sent in the clear so the server knows how to establish the secure connection.

### JA4 — The Successor to JA3

JA3 had several problems:

- Easy to evade
- Sensitive to extension ordering
- Not robust across TLS changes

JA4 improves this by:

- Better normalization
- More consistent fingerprints
- Additional variants for HTTP and server behavior (e.g., JA4H)

It produces fingerprints that remain stable across modern TLS implementations.

### Why AI Deployments Are Easy to TLS-Fingerprint

Most AI systems are **not accessed directly by a web browser**. Internal traffic looks like:

```
Web App → Python FastAPI → gRPC → LLM Server → Vector Database → Redis → Embedding Service
```

Most internal requests come from Python `requests`, `urllib`, gRPC clients, LangChain, OpenAI SDK, or Anthropic SDK. These libraries all have characteristic TLS fingerprints.

A network sensor can distinguish `Browser → JA4 = Browser fingerprint` from `Python Requests → JA4 = Python fingerprint` even though the contents are encrypted.

## Case Study: GreyNoise LLM Endpoint Reconnaissance

Between **October 2025 and January 2026**, GreyNoise captured over **91,000 attack sessions** targeting AI deployments through their Ollama honeypot infrastructure. One campaign stood out — over 11 days starting December 28, attackers generated **80,000+ requests** probing conversational endpoints to determine whether each target was compatible with OpenAI, Gemini, or Anthropic API schemas. They targeted over **73 different LLM model endpoints**, including GPT-4o variants, Claude models, Llama, Gemini, DeepSeek, Mistral, Qwen, and Grok.

### Fingerprinting Technique: Innocuous Prompts

The attackers sent simple prompts and analysed the response schemas:

- `"hi"` appeared 32,716 times
- `"How many states are there in the United States?"` appeared 27,778 times
- `"How many letter 'r' are in the word strawberry?"` was another common test

These prompts were not random. Each one produces a response that differs in structure, format, and content depending on which model is running.

**Example — "hi" sent to different providers:**

OpenAI response schema:

```json
{
  "id":"chatcmpl-...",
  "choices":[
      {
          "message":{
              "role":"assistant",
              "content":"Hello!"
          }
      }
  ]
}
```

Anthropic response schema:

```json
{
  "type":"message",
  "content":[
      {
          "type":"text",
          "text":"Hello!"
      }
  ]
}
```

Gemini response schema:

```json
{
  "candidates":[
      {
          "content":{
              ...
          }
      }
  ]
}
```

The **schema alone** identifies the provider.

**Why "How many states?"** — Different models differ in wording, formatting, punctuation, metadata, confidence fields, token accounting, and tool invocation behavior. Those subtle differences act like a fingerprint.

**Why "How many r's in strawberry?"** — This prompt became famous because many language models historically handled it differently. Responses ranged from `2` to `3` to `"The word contains three r's."` Different models — and even different versions of the same model — often produce distinct outputs. Attackers compare these responses against known behavior to infer the underlying model.

### JA4 Finding

GreyNoise observed:

- **62 different IP addresses** from **27 countries**
- Yet **99% of the traffic shared the same JA4H fingerprint**

This suggests all those systems were using the same HTTP client implementation or automation framework, likely controlled by a single threat actor or organisation. Even though the source IPs varied, the network fingerprint remained nearly identical.

### Infrastructure Overlap

GreyNoise traced the IPs and found overlap with infrastructure previously used to exploit over **200 known CVEs**, including React2Shell (CVE-2025-55182). Their assessment:

> *"Professional threat actor conducting reconnaissance. The infrastructure overlap with established CVE-scanning operations suggests that this enumeration feeds into a larger exploitation pipeline. They're building target lists."*

The full attack workflow:

```
Internet Scan
      ↓
Find AI Endpoints
      ↓
Identify Model & Framework
      ↓
Categorize Targets
      ↓
Match Against Known Vulnerabilities
      ↓
Select High-Value Targets
      ↓
Potential Exploitation
```

> [!WARNING] Key Insight
> This was AI fingerprinting at scale. No exploitation. No payloads. Just systematic identification of what is deployed and how it responds. The exposure itself was the vulnerability — the attack wasn't sophisticated, but the reconnaissance was thorough.
