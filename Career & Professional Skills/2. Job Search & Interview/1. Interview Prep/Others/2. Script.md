## GitHub Repo Analysis

Who has found bugs and got bounties by analysing GitHub repos?
Now the question is: **How do you scale it for real-world testing?**

If you have 2,000 GitHub repos, how will you analyse them?
The task was Given by a BFSI Client 
1. Check HTTP status codes — write a Python script (Checked which repos have 200 - means repo was live , 301 - means it was redirecting to the original repo , 401 - means the repo was ) then I brought down the count to 1500, so we directly removed 500 repositories
2. Handle IP rate limiting — make a new script, add delay
3. Analyse for secrets using tools — use Gitleaks or TruffleHog (faster) ; came down to 700 repositories which had commited some secrets like api keys , usernames and passwords
4. Keep only verified keys (saw only the "true" values , manually checked some gemini api keys , uploaded files on it ; dont know where it went) ; came down to 400 repos
5. Check which repos have employee email commits ; make a python to check if commit was from company@email.com ; came down to 100
6. Remove test keys ; came down to 5 
7. Remove duplicates
8. finally came down to 2 repositories and reported it to the client

> [!tip] "Tell me about something you did at CloudSEK." → **The 2,000 repo story**
> BFSI client, one day to check ~2,000 GitHub repos for leaked payment secrets. Most seniors said it couldn't be done. I broke it into steps and asked different people about each piece:
> 1. Python script to check HTTP status (live / redirect / gone) → **~1,500**
> 2. Handle rate limiting (delays / new script)
> 3. Secret scanning with Gitleaks / TruffleHog → **~700**
> 4. Keep only verified secrets → **~400**
> 5. Filter to commits from company emails → **~100**
> 6. Remove test keys → **~5**
> 7. Deduplicate → **2 verified findings** reported to the client
>
> **Lesson:** When something looks impossible, break it into small problems and solve each one methodically.
