# Cryptography — Notes & Check-In Quiz

## 1. What is Cryptography?

**Cryptography** is the science of protecting information using mathematical techniques.

Main goals:
- 🔒 **Confidentiality** → only authorised people can read it
- 🛡️ **Integrity** → data wasn't changed
- 👤 **Authentication** → verify who someone is
- ✍️ **Non-repudiation** → provide evidence of who signed something

```
Original message → Cryptography → Protected information
```

---

## 2. Encryption 🔒

**Encryption converts readable data (plaintext) into unreadable data (ciphertext).** The authorised person uses a **key** to decrypt it.

### Symmetric Encryption

Same key is used to encrypt **and** decrypt.

```
       Same key
          ↓
Plaintext → Ciphertext → Plaintext
```

Examples: **AES**, ChaCha20

### Asymmetric Encryption

Uses a **public key + private key** pair.

```
Public Key  → Encrypt
Private Key → Decrypt
```

**Example:** Alice wants to send Bob a private message:
- Alice encrypts using **Bob's public key**
- Only **Bob's private key** can decrypt it

> 🧠 **Encrypt → receiver's public key**
> **Decrypt → receiver's private key**

Examples: **RSA**, **ECC**

## 3. Hashing 🔢

Hashing is **not encryption**. A hash function converts data into a **fixed-size value** (digest). You generally **cannot reverse a hash** to get the original data.

```
hello → SHA-256 → 2cf24dba5...
```

### Where is Hashing Used?

Passwords are commonly stored as hashes rather than plaintext:

```
Password entered → Hash → Compare with stored hash
```

### Common Hashing Algorithms

- **SHA-256** / **SHA-512** / **SHA-3** — secure
- **MD5** ❌ — cryptographically broken for collision resistance
- For password storage: **bcrypt**, **scrypt**, **Argon2**, or **PBKDF2**

### The Avalanche Effect

Changing even one character completely changes the hash output:
- `Hello` → completely different hash than `hello`

This is because operations inside the hash algorithm cause changes to **propagate through the internal state**.

### How Hashing Works Internally (MD5 Example)

Your computer doesn't "look up" the hash — it processes the file's **bytes through a mathematical algorithm**:

```
file.txt → Read raw bytes → Split into 512-bit blocks → Process each block → 128-bit hash
```

**Key operations:** Addition, XOR, AND, OR, bit shifting, bit rotation

For a 5-byte file like `Hello`:

```
H = 0x48 = 01001000
e = 0x65 = 01100101
l = 0x6c = 01101100
l = 0x6c = 01101100
o = 0x6f = 01101111
```

Only 40 bits — MD5 **pads** it to fill a 512-bit block, then processes through 4 rounds to produce a 128-bit hash.

**For large files**, the hash is computed by streaming through blocks:

```
File
 ├── Block 1 (512 bits) → process → update state
 ├── Block 2 (512 bits) → process → update state
 ├── ...
 └── Last block + padding
              ↓
         Final hash
```

**MD5 always produces 128 bits** regardless of input size:

```
"Hi"     → 128-bit hash
1 MB     → 128-bit hash
10 GB    → 128-bit hash
```

> A hash is a **digital fingerprint** — you don't reconstruct the person from their fingerprint.

### File Permissions and Hashing

Running `md5sum file.exe` doesn't require admin privileges — the program gets **the same file permissions as your user account**:

```
certutil -hashfile C:\Users\Akshit\Documents\report.pdf MD5
```

Windows checks whether your current account can read the file. If not → `Access is denied.`

## 4. Digital Signatures ✍️

A digital signature provides **authentication + integrity** and can support **non-repudiation**.

```
Message → Hash → Sign with sender's private key → Digital Signature
```

The receiver uses the sender's **public key** to verify the signature.

**Example:** You download software. The developer publishes `software.exe` + `signature`. Your system verifies:
1. The software came from the expected signer
2. The software wasn't modified after signing

> **Encryption → keep data secret**
> **Digital signature → prove who signed it + detect modification**

> 🧠 **Sign → sender's private key**
> **Verify → sender's public key**

## 5. Common Cryptographic Algorithms

### Encryption Algorithms

| Algorithm | Type | Status | Use Cases |
|---|---|---|---|
| **AES** | Symmetric | ✅ Secure | VPNs, full-disk encryption, TLS, messaging |
| **DES** | Symmetric | ❌ Broken | Legacy only (56-bit key) |
| **3DES** | Symmetric | ⚠️ Deprecated | Legacy banking, older hardware |
| **Blowfish** | Symmetric | ⚠️ Aging | File encryption, some VPNs |
| **Twofish** | Symmetric | ✅ Secure | VeraCrypt, file encryption |
| **RSA** | Asymmetric | ✅ Secure (≥2048-bit) | Key exchange, digital signatures, TLS |
| **ECC** | Asymmetric | ✅ Secure | TLS, mobile, crypto (ECDSA/ECDH) |
| **Diffie-Hellman / ECDH** | Asymmetric (key exchange) | ✅ Secure | TLS, VPNs |

### Hashing Algorithms

| Algorithm | Status | Use Cases |
|---|---|---|
| **SHA-1** | ❌ Broken | Legacy only |
| **SHA-2** (SHA-256, SHA-512) | ✅ Secure | TLS, signatures, blockchain |
| **SHA-3** | ✅ Secure | Alternative to SHA-2 |
| **MD5** | ❌ Broken | Non-security checksums only |
| **bcrypt** | ✅ Secure | Password hashing (salted, slow) |
| **scrypt / Argon2** | ✅ Secure | Password hashing (CPU + memory intensive) |

### TL;DR

- Use **AES** or **Twofish** for symmetric encryption
- Use **RSA** or **ECC** for key exchange and digital signatures
- Use **SHA-2** or **SHA-3** for hashing
- Use **bcrypt**, **scrypt**, or **Argon2** for password storage
- Avoid **DES**, **3DES**, **MD5**, and **SHA-1**

### Quick Memory

```
AES       → Encryption
RSA/ECC   → Public-key cryptography
SHA-256   → Hashing
```

```
Base64 decode, URL decode, Hex decode, Hash data, Encode/decode, Convert formats

```

## 7. Certificates and PKI 📜

### What is PKI?

**PKI = Public Key Infrastructure** — the whole system used to create, issue, manage, verify, renew, and revoke digital certificates and public/private keys.

### The Components

| Component | Role |
|---|---|
| **Certificate Authority (CA)** | Trusted org that issues/signs certificates (Let's Encrypt, DigiCert, Sectigo) |
| **Certificate** | Digital document binding an identity/domain to a public key |
| **Public & Private Keys** | Certificate contains public key; private key stays on server |
| **Trust Store** | Collection of trusted root CA certificates on your browser/OS |

### How a Website Gets a Certificate

```
Website owner
     ├── Generates private key 🔑 (kept secret)
     ├── Generates public key 🔓 (can be shared)
     ↓
Requests certificate from CA
     ↓
CA verifies domain/identity
     ↓
CA signs and issues certificate containing:
  - Domain: example.com
  - Public Key: XXXXX
  - Issuer: Let's Encrypt
  - Validity: ...
  - CA's Digital Signature: XXXXX
```

The **private key stays with the website**. The CA does not need it.

### Certificate Chain of Trust

```
Root CA (in your trust store)
   ↓ signs/trusts
Intermediate CA
   ↓ signs
Website Certificate
```

Browser verifies signatures down the chain + checks domain, validity, and trust.

### Why Do Certificates Expire?

1. **Limit damage** if private key is compromised
2. **Keep information up to date** (domain owner can change)
3. **Allow newer security standards**

```
Certificate expires → Website must renew → CA revalidates
```

The **certificate expires**, but the key pair doesn't automatically disappear. Modern certificates use **automatic renewal** (e.g., ACME/Let's Encrypt).

> 🔑 Keys = cryptographic credentials
> 📜 Certificate = CA-signed proof connecting identity to a public key
> ⏰ Certificate expires = trust must periodically be renewed

### PKI Security — Trust Model

```
                 REAL CA
                    │
             CA private key 🔐 (extremely protected with HSMs, multi-person controls, auditing)
                    │
              signs certificate
                    ↓
             Website certificate
                    ↓
                  Browser
                    │
          CA public certificate (in trust store)
                    │
             "I trust this CA"
                    ↓
                 TRUST ✅
```

**Important security points:**
- Your browser/OS stores the CA's **public certificate**, not its private key
- If you modify your local trust store, it only affects **that machine** — not the real CA
- If an attacker gains admin control and installs a malicious root CA → they can intercept TLS on that machine
- A real CA compromise would be a **major security incident** (HSMs, restricted access, etc. protect against this)

> **Compromising a certificate ≠ compromising the CA**
> **Compromising a CA's private key = potentially a huge PKI compromise**
> **Compromising your computer's trust store = compromising HTTPS trust on that computer**

### PKI Analogy

```
Website    → "I am example.com"
Certificate → ID card
CA         → Trusted authority that issued/signed the ID
Browser    → Checks whether the ID is genuine
TLS        → Establishes the secure conversation
```

### Where is PKI?

PKI is **distributed**, not stored in one place:

```
                 PKI
                  │
     ┌────────────┼────────────┐
     ↓            ↓            ↓
   CA servers   Certificates   Your computer
     │                           │
     └─ CA private keys          └─ Trusted CA certificates
```

## 8. HTTPS, TLS and SSL 🔐

### HTTP vs HTTPS

```
HTTP:  Browser ──────────────> Website  (not protected by encryption at protocol level)
HTTPS: Browser ←→ TLS ←→ Website       (HTTP protected by TLS)
```

### What About SSL?

**SSL is the older predecessor to TLS.** SSL versions are obsolete. When people say "SSL certificate" they usually mean a **TLS certificate**.

### The Complete HTTPS Journey

When you type `https://example.com`:

#### Step 1 — DNS Lookup 🌐

Your computer needs an IP address for the domain:

```
Browser DNS cache → OS DNS cache → DNS Resolver
```

If the resolver doesn't know, it walks the **DNS hierarchy**:

```
Your PC
   ↓
DNS Resolver (e.g., 1.1.1.1 Cloudflare, 8.8.8.8 Google, ISP, or router)
   ↓
Root DNS ("I don't know example.com, but .com is handled over there")
   ↓
.com TLD DNS ("example.com is handled by these authoritative nameservers")
   ↓
Authoritative DNS for example.com ("www.example.com → 93.184.x.x")
   ↓
Resolver caches result + returns IP to your PC
```

**Key DNS servers to remember:**

| Server | Role |
|---|---|
| **Recursive DNS Resolver** | Finds the answer for you (middleman) |
| **Root DNS** | Tells resolver where TLD servers are (13 logical identities, A–M, globally distributed via anycast) |
| **TLD Server** (.com, .org, .in) | Tells resolver which authoritative nameserver handles the domain |
| **Authoritative DNS** | Holds the actual DNS records for the domain |

> **Root DNS = a global infrastructure/system, not a single company**
> **.com TLD** is operated by **Verisign** (manages registry + TLD DNS servers)
> The resolver does the work — your PC doesn't personally query all three levels

**DNS Caching** makes subsequent lookups fast:
```
First request:  PC → Resolver → Root → .com → Authoritative → IP
Second request: PC → Resolver → Cache → IP (instant)
```

#### Step 2 — TCP Connection 📡

For HTTPS over TCP, establish connection via **three-way handshake**:

```
Your PC                         Server
  │──── SYN ─────────────────────>│
  │<─── SYN + ACK ────────────────│
  │──── ACK ─────────────────────>│
```

#### Step 3 — TLS Handshake 🔐

```
Browser                         Server
   │──── TLS ClientHello ─────────>│  ("I support these TLS options")
   │<─── ServerHello + Certificate │  ("Here's my certificate")
```

#### Step 4 — Certificate Verification 📜

Browser checks:
```
✓ Correct domain?       ✅
✓ Currently valid?      ✅
✓ Trusted CA chain?     ✅
✓ Valid CA signature?    ✅
```

#### Step 5 — Key Exchange (ECDHE) 🔑

Modern TLS uses ephemeral key agreement (e.g., **ECDHE**):

```
Browser                         Server
Private A                       Private B
   │                               │
Public A ─────────────────────────>│
   │<────────────────────── Public B
   ↓                               ↓
calculate                       calculate
   └────── same shared secret ─────┘
```

Private values are **not sent across the network**. Both sides derive symmetric session keys.

#### Step 6 — Encrypted Communication

TLS uses **symmetric authenticated encryption** (AES-GCM or ChaCha20-Poly1305) for speed:

```
TLS handshake → Session keys → AES-GCM / ChaCha20-Poly1305 → Fast encrypted communication
```

#### Step 7 — HTTP Request & Response

```
GET / HTTP/1.1
Host: example.com
```

Sent **inside** the encrypted TLS connection. The server processes the request and returns HTML (also encrypted).

#### Step 8 — Browser Renders Page

```
HTML → DOM → CSS → Style → JavaScript → Dynamic behaviour → Screen 🖥️
```

The browser may make additional HTTPS requests for CSS, JS, images, fonts, APIs.

### 🧠 The Entire Journey — Summary

```
You type URL → URL parsing → DNS lookup → Get IP → TCP connection → TLS handshake
→ Certificate verification → Session keys → HTTP request → Web server → Application
→ HTTP response → TLS decrypts → Browser processes HTML/CSS/JS → Page displayed
→ You interact → More HTTPS requests/responses
```

### Three Distinct Layers

```
DNS → FIND    ("Where is example.com?")
TLS → TRUST + PROTECT   ("Can I trust this server? Establish encryption.")
HTTP → COMMUNICATE      ("Give me this webpage / submit this data.")
```

### Network Protocol Stack

```
HTTP        "What message am I sending?"
TLS         "Keep the message private."
TCP         "Make sure the message arrives correctly."
IP          "Which computer should it go to?"
Wi-Fi/Eth   "How do I physically send the data?"
```

> **HTTP defines the web conversation; TCP/QUIC handles transport.**

### HTTP Versions and Transport

```
HTTP/1.1 → TCP
HTTP/2   → TCP
HTTP/3   → QUIC → UDP
```

### The Certificate Does NOT Encrypt All Traffic

The certificate mainly helps the browser establish:
> **"This public key is associated with this website."**

Then **TLS uses that authenticated connection to establish encryption keys for the actual session**.

## 9. Common Cryptographic Attacks ⚔️

### Brute Force

Try many possible keys/passwords:
```
password1, password2, password3, ..., password999999
```

### Dictionary Attack

Try passwords from a list of commonly used words/passwords:
```
password, admin, qwerty, letmein, ...
```

### Collision Attack

Two different inputs produce the **same hash**:
```
Input A ──→ Hash X
Input B ──→ Hash X
```

Particularly relevant to weak algorithms like MD5.

### Man-in-the-Middle (MITM)

An attacker gets between two communicating parties:
```
Alice ←→ Attacker ←→ Bob
```

Proper TLS authentication helps prevent this.

### Downgrade Attack

Force communication to use a **weaker cryptographic protocol or algorithm**.

### Replay Attack

Capture legitimate communication and **reuse it later**:
```
Legitimate request → Captured → Replayed later
```

### Rainbow Table Attack

Precomputed table of hashes for common passwords. **Defeated by salting** (adding random data before hashing).

## 🧠 Cryptography — Big Picture

```
                 CRYPTOGRAPHY
                      │
       ┌──────────────┼──────────────┐
       ↓              ↓              ↓
  Encryption       Hashing       Signatures
       │              │              │
    AES/RSA        SHA-256        RSA/ECDSA
       │              │              │
   Keep secret    Integrity      Identity +
                                 Integrity
                      │
                      ↓
                    PKI
                      │
                Certificates
                      │
                      ↓
                    TLS
                      │
                      ↓
                   HTTPS
```

### Key Distinctions to Memorise

> **Encryption = confidentiality**
> **Hashing = integrity / one-way transformation**
> **Digital signature = authentication + integrity**
> **Certificate = binds an identity to a public key**
> **PKI = infrastructure for managing certificates/keys**
> **TLS = secure communication protocol used by HTTPS**
> **SSL = obsolete predecessor to TLS**
