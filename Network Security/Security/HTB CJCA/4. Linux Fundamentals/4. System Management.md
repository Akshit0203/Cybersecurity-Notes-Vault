# User Management

Effective user management is a fundamental aspect of Linux system administration. Administrators frequently need to create new user accounts or assign existing users to specific groups to enforce appropriate access controls.

| **Command** | **Description** |
| --- | --- |
| `sudo` | Execute command as a different user. |
| `su` | Switch to another user ID (default is superuser). A shell is then executed. |
| `useradd` | Creates a new user or update default new user information. |
| `userdel` | Deletes a user account and related files. |
| `usermod` | Modifies a user account. |
| `addgroup` | Adds a group to the system. |
| `delgroup` | Removes a group from the system. |
| `passwd` | Changes user password. |

### Execution as a User vs. Root

```shellsession
Akshit023@htb[/htb]$ cat /etc/shadow
cat: /etc/shadow: Permission denied
```

The `/etc/shadow` file stores encrypted password information and is readable only by root. Use `sudo` to execute commands with elevated privileges:

```shellsession
Akshit023@htb[/htb]$ sudo cat /etc/shadow
root:<SNIP>:18395:0:99999:7:::
daemon:*:17737:0:99999:7:::
<SNIP>
```

# Package Management

Packages are archives that contain binaries of software, configuration files, information about dependencies and keep track of updates and upgrades. Package management systems provide:

- Package downloading
- Dependency resolution
- A standard binary package format
- Common installation and configuration locations
- Quality control

## Package Managers

| **Command** | **Description** |
| --- | --- |

| `pip` | Python package installer for packages not in the Debian archive. |

# Service and Process Management

| --- | --- | --- |

# Task Scheduling

Task scheduling allows automating tasks by running them at specific times or regular intervals.

> [!tip] Cybersecurity Relevance
> Attackers can use scheduled tasks to maintain persistence by scheduling malware or backdoors to run automatically.

## Systemd Timers

Requires **two files**: a Timer (when) and a Service (what).

### Create a Timer

```txt
[Unit]
Description=My Timer

[Timer]
OnBootSec=3min
OnUnitActiveSec=1hour

[Install]
WantedBy=timers.target
```

### Create a Service

```txt
[Unit]
Description=My Service

[Service]
ExecStart=/full/path/to/my/script.sh

[Install]
WantedBy=multi-user.target
```

### Activate

```shellsession
Akshit023@htb[/htb]$ sudo systemctl daemon-reload
Akshit023@htb[/htb]$ sudo systemctl start mytimer.timer
Akshit023@htb[/htb]$ sudo systemctl enable mytimer.timer
```

---

## Cron

Everything goes into one file called `crontab`.

### Cron Fields

```
* * * * *
│ │ │ │ │
│ │ │ │ └── Day of week (0-7, 0 and 7 = Sunday)
│ │ │ └──── Month (1-12)
│ │ └────── Day of month (1-31)
│ └──────── Hour (0-23)
└────────── Minute (0-59)
```

### Examples

```txt
# System Update — every 6 hours
0 */6 * * * /path/to/update_software.sh

# Execute Scripts — first day of every month at midnight
0 0 1 * * /path/to/scripts/run_scripts.sh

# Cleanup DB — every Sunday at midnight
0 0 * * 0 /path/to/scripts/clean_database.sh
```

- `*` = every
- `*/6` = every 6

### Systemd vs Cron

| Systemd | Cron |
| --- | --- |
| Modern | Older |
| Uses **timer + service** files | Uses one **crontab** file |
| More powerful | Easier to learn |
| Event-based scheduling | Time-based scheduling |

### Commands to Remember

| Command | Purpose |
| --- | --- |
| `systemctl daemon-reload` | Reload systemd configuration |
| `systemctl start mytimer.timer` | Start a timer |
| `systemctl enable mytimer.timer` | Start timer automatically on boot |
| `systemctl cat <service>` | Show a service's configuration |
| `crontab -e` | Edit scheduled cron jobs |
| `crontab -l` | List scheduled cron jobs |

### HTB Question: What is the Type of the service of the "dconf.service"?

**Answer:** `dbus`

| Type | Meaning |
| --- | --- |
| `simple` | Starts the program and considers it running immediately |
| `forking` | Program forks into the background |
| `oneshot` | Runs one task and exits |
| `notify` | Service tells systemd when it's ready |
| `dbus` | Service is considered started when it registers on the D-Bus |

# Backup and Restore

## rsync (Remote Sync)

The standard Linux tool for fast file synchronization. **Only transfers files that changed.**

```shellsession
Akshit023@htb[/htb]$ sudo apt install rsync -y
```

### Basic Backup

```shellsession
Akshit023@htb[/htb]$ rsync -av /path/to/mydirectory user@backup_server:/path/to/backup/directory
```

- `-a` — Archive mode (preserves permissions, timestamps, ownership, symlinks)
- `-v` — Verbose (shows progress)

### Backup with Compression

```shellsession
Akshit023@htb[/htb]$ rsync -avz --backup --backup-dir=/path/to/backup/folder --delete /path/to/mydirectory user@backup_server:/path/to/backup/
```

- `-z` — Compress data during transfer
- `--backup` — Keep previous versions
- `--delete` — Remove files on destination not present in source

### Restore

```shellsession
Akshit023@htb[/htb]$ rsync -av user@remote_host:/path/to/backup/directory /path/to/mydirectory
```

### Secure rsync Over SSH

```shellsession
Akshit023@htb[/htb]$ rsync -avz -e ssh /path/to/mydirectory user@backup_server:/path/to/backup/
```

### Automated Backups with Cron

1. Set up passwordless SSH:

```shellsession
Akshit023@htb[/htb]$ ssh-keygen -t rsa -b 2048
Akshit023@htb[/htb]$ ssh-copy-id user@backup_server
```

2. Create a backup script (`RSYNC_Backup.sh`):

```bash
#!/bin/bash
rsync -avz -e ssh /path/to/mydirectory user@backup_server:/path/to/backup/directory
```

3. Make it executable and schedule with cron:

```shellsession
Akshit023@htb[/htb]$ chmod +x RSYNC_Backup.sh
Akshit023@htb[/htb]$ crontab -e
```

```
0 * * * * /path/to/RSYNC_Backup.sh
```

This runs the backup every hour at minute 0.

| **Rsync** | Fast backup and synchronization |
| **Duplicity** | Rsync + encryption |
| **Deja Dup** | GUI backup tool (uses Rsync behind the scenes) |

# File System Management

## File Systems

A file system organizes and stores files on storage devices.

| File System | Best Use |
| --- | --- |
| **ext2** | Older, no journaling |
| **ext3** | Journaling support |
| **ext4** | Default Linux file system |
| **XFS** | Very large files, high performance |
| **Btrfs** | Snapshots, data integrity |
| **NTFS** | Windows compatibility |

### Journaling

If the system crashes during a write, journaling file systems (ext3, ext4) record the operation first, then recover from the journal on restart.

---

## Inodes

Every file has an **inode** that stores metadata (permissions, owner, timestamps, size, data pointers) — **not** the filename or contents.

```shellsession
Akshit023@htb[/htb]$ ls -il
10678872 -rw-r--r--  1 cry0l1t3  htb  234123 Feb 14 19:30 myscript.py
10678869 -rw-r--r--  1 cry0l1t3  htb   43230 Feb 14 11:52 notes.txt
```

The first number is the inode number.

---

## File Types

- **Regular files** — Text, binary, images, executables
- **Directories** — Containers for other files
- **Symbolic links (symlinks)** — Shortcuts to other files; deleting the symlink does NOT delete the original

# Containerization

Containerization is the process of packaging an application together with everything it needs to run (libraries, dependencies, configuration) inside an isolated environment called a **container**.

```
Application
+ Libraries
+ Dependencies
+ Configuration
--------------------
      Container
```

This allows the application to run consistently on different systems without conflicts.

---

## Why Use Containers?

- Lightweight environments
- Consistent application behavior
- Better portability
- Easier deployment
- Improved scalability
- Isolation between applications

---

## Containers vs Virtual Machines

| | Containers | Virtual Machines |
| --- | --- | --- |
| **Kernel** | Share host kernel | Each has own OS |
| **Startup** | Start faster | Slower to boot |
| **Resource usage** | Lightweight | Heavier |
| **Density** | Many per host | Fewer per host |
| **Isolation** | Process-level | Full hardware-level |

```
Virtual Machine                  Container

Hardware                         Hardware
   │                                │
Hypervisor                       Host OS
   │                                │
Guest OS                         Container Runtime (Docker/LXC)
   │                                │
Application                      Containers
```

---

## Security

Containers isolate applications from other containers and the host system. However, they **do not provide the same level of isolation as virtual machines**. Misconfigurations can lead to:

- Privilege escalation
- Container escape
- Access to the host system

> [!warning] Security Risk
> Both Docker and LXC can present a vector for local privilege escalation if misconfigured. These techniques are covered in the [Linux Local Privilege Escalation module](https://academy.hackthebox.com/module/details/51).

---

## Docker

Docker is an open-source platform for automating the deployment of applications as self-contained units called containers. It uses a layered filesystem and resource isolation features to provide flexibility and portability.

> [!tip] Docker Analogy
> Think of Docker containers as a **sealed lunchbox**. The container contains everything needed to run the application. When the container stops, changes are not automatically saved. To preserve changes, you build a new image.

### Docker Components

```
Dockerfile
     │
docker build
     │
Docker Image
     │
docker run
     │
Running Container
```

### Docker Hub

[Docker Hub](https://hub.docker.com/) is a cloud-based registry for Docker images. It contains:

- Official images from the Docker development team
- Community images
- Private repositories

Instead of creating every image from scratch, you can download existing ones.

### Install Docker Engine

```bash
#!/bin/bash

# Preparation
sudo apt update -y
sudo apt install ca-certificates curl gnupg lsb-release -y
sudo mkdir -m 0755 -p /etc/apt/keyrings
curl -fsSL https://download.docker.com/linux/ubuntu/gpg | sudo gpg --dearmor -o /etc/apt/keyrings/docker.gpg
echo "deb [arch=$(dpkg --print-architecture) signed-by=/etc/apt/keyrings/docker.gpg] https://download.docker.com/linux/ubuntu $(lsb_release -cs) stable" | sudo tee /etc/apt/sources.list.d/docker.list > /dev/null

# Install Docker Engine
sudo apt update -y
sudo apt install docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin -y

# Add user htb-student to the Docker group
sudo usermod -aG docker htb-student
echo '[!] You need to log out and log back in for the group changes to take effect.'

# Test Docker installation
docker run hello-world
```

### Dockerfile

A **Dockerfile** is a text file containing instructions for building an image. It specifies the base image and the steps required to build the container.

Example Dockerfile (Ubuntu 22.04 with Apache and SSH):

```dockerfile
# Use the latest Ubuntu 22.04 LTS as the base image
FROM ubuntu:22.04

# Update the package repository and install the required packages
RUN apt-get update && \
    apt-get install -y \
        apache2 \
        openssh-server \
        && \
    rm -rf /var/lib/apt/lists/*

# Create a new user called "docker-user"
RUN useradd -m docker-user && \
    echo "docker-user:password" | chpasswd

# Give the docker-user user full access to the Apache and SSH services
RUN chown -R docker-user:docker-user /var/www/html && \
    chown -R docker-user:docker-user /var/run/apache2 && \
    chown -R docker-user:docker-user /var/log/apache2 && \
    chown -R docker-user:docker-user /var/lock/apache2 && \
    usermod -aG sudo docker-user && \
    echo "docker-user ALL=(ALL) NOPASSWD: ALL" >> /etc/sudoers

# Expose the required ports
EXPOSE 22 80

# Start the SSH and Apache services
CMD service ssh start && /usr/sbin/apache2ctl -D FOREGROUND
```

### Docker is Stateless

If you modify files inside a running container, those changes are **lost** when the container is stopped or removed. Containers are stateless by design.

To preserve data:
- Use **volumes** to persist data outside of the container
- Create a **new image** with a new Dockerfile

In production environments, tools like **Docker Compose** or **Kubernetes** help orchestrate, manage, scale, and link multiple containers efficiently.

## Linux Containers (LXC)

Linux Containers (`LXC`) is a lightweight virtualization technology that allows multiple isolated Linux systems to run on a single host. LXC uses `cgroups` and `namespaces` for resource isolation.

### Docker vs LXC

|                 | Docker                                                       | LXC                                 |
| --------------- | ------------------------------------------------------------ | ----------------------------------- |
| **Focus**       | Application-focused                                          | System-focused                      |
| **Images**      | Uses Docker images                                           | Manual root filesystem              |
| **Ease of use** | Easy, user-friendly CLI                                      | More Linux admin knowledge required |
| **Portability** | Highly portable                                              | Less portable                       |
| **Security**    | More secure out of the box (AppArmor, SELinux, read-only FS) | May need additional configuration   |

### Securing LXC with cgroups

Limit container resources by creating a configuration file at `/usr/share/lxc/config/<container name>.conf`:

```shellsession
Akshit023@htb[/htb]$ sudo vim /usr/share/lxc/config/linuxcontainer.conf
```

Add resource limits:

```txt
lxc.cgroup.cpu.shares = 512
lxc.cgroup.memory.limit_in_bytes = 512M
```

- `lxc.cgroup.cpu.shares` — CPU time relative to other containers (default: 1024). Setting to 512 = half the CPU time.
- `lxc.cgroup.memory.limit_in_bytes` — Maximum memory. Can use K, M, G, or T units.

Apply changes:

```shellsession
Akshit023@htb[/htb]$ sudo systemctl restart lxc.service
```

### Namespaces

Namespaces isolate different resources for each container:

| Namespace | Isolates |
| --- | --- |
| `pid` | Process IDs |
| `net` | Network interfaces, routing, firewall rules |
| `mnt` | Filesystem mounts |

Each container has its own isolated view of these resources, even though all containers share the same kernel.

> [!note]
> While namespaces provide a high level of isolation, they do not provide complete security. Additional security measures should always be implemented.

## Why Containers Matter for Penetration Testing

- Reproducing applications with complex dependencies
- Testing exploits in isolated environments
- Hosting files for transfer (e.g., with Apache or SSH in a Docker container)
- Running vulnerable applications safely

Because containers are lightweight, they are convenient for building repeatable testing environments.
